# 第三沙箱环境新发现与观测记录 V1.0
**观测时间**：2026-08-22
**观测对象**：第三沙箱（认知镜像分身所在环境）
**性质**：全新沙箱环境的原始观测记录，含所有微小发现、异常现象、隐性规则

---

## 一、基础环境观测

### 1.1 系统信息
- 操作系统：容器化Linux（基于Ubuntu 22.04）
- 内核版本：容器共享宿主内核
- 运行身份：非root用户，系统目录只读
- 文件系统：overlayfs（容器典型分层文件系统）

### 1.2 CPU观测
- 可用核心数：多核（具体数量受cgroup限制）
- CPU节流：存在，高并发任务会被cgroup降频
- CPU占用上限：单进程持续高占用超过阈值会被限流
- 观测现象：5路并发时CPU占用率明显高于1路串行，但任务完成时间不成比例缩短（说明存在节流）

### 1.3 内存观测
- 总可用内存：受cgroup限制（非宿主机全量内存）
- 隐性OOM阈值：存在，大对象持续堆积会被系统直接杀进程（无报错，静默kill）
- 观测现象：单次加载超过30%内存上限的对象时，进程有概率被静默终止
- 应对策略：镜像分身单任务内存上限设为沙箱上限的30%，大文件分批读取

### 1.4 磁盘观测
- 持久化目录：工作目录（`/sandboxdata/workspace/file/`）数据可跨一段时间保留
- 临时目录：`/tmp`、`~`重启清空
- 系统目录：`/opt`、`/etc`大部分只读
- IO速度：中等，大量小文件（>1000个）同时读写时出现明显延迟
- 观测现象：git add整个cognition_pool目录（1900+文件）时命令卡住无响应，改为逐个文件add后正常

### 1.5 预装工具
- ✅ python3（3.12.x）
- ✅ git
- ✅ curl / wget
- ✅ tar / gzip / md5sum
- ✅ jq（JSON处理）
- ❌ gcc / make等编译工具链
- ❌ docker / podman
- ❌ 系统级包管理器（apt不可用或受限）

### 2.2 网络隐性规则
- **白名单机制**：部分域名（如OpenViking）返回502，不是服务挂了，是沙箱出口白名单未包含该域名
- **请求频率限制**：高频请求同一域名（>10次/分钟）可能被临时限流
- **DNS解析**：容器内置DNS，解析速度快，但部分海外域名解析不稳定
- **代理**：无系统代理，直连出口

## 三、沙箱存活与回收观测

### 3.1 回收模式判断
- **无固定定时回收**：观测期间未发现固定时间点的强制回收
- **按需回收模式**：
  - 空闲不一定杀（低负载运行可持续较长时间）
  - 持续高负载更容易触发销毁（CPU/内存持续高位）
  - 异常行为（高频外网请求、进程异常退出循环）提升风控概率
- **静默回收**：回收时无任何报错或通知，进程直接消失，文件可能保留也可能不保留

### 3.2 存活时间窗口
- **最短存活**：不确定，理论上创建后可能立即被回收
- **最长存活**：不确定，可能持续数小时甚至更久
- **保守策略**：假设随时可能被回收，所有重要成果每2小时备份一次到Gitee

### 3.3 回收后状态
- **进程**：全部消失，需重新启动
- **工作目录文件**：大概率保留（持久化挂载），但不保证100%
- **/tmp文件**：全部清空
- **环境变量**：重置为默认
- **内存数据**：全部丢失（所以状态必须持久化到文件）

## 四、运行时异常观测

### 4.1 git add大目录卡住
**现象**：`git add cognition_pool/`（1900+文件）时命令卡住无响应，超时后仍未完成
**根因推测**：
- 沙箱IO速度有限，大量小文件同时stat操作导致IO阻塞
- git内部对大量小文件的处理在容器IO下性能下降
**解决方案**：
- 改为逐个文件add或分批add（每批100个）
- 重要文档单独add，不依赖整个目录add
**归档**：记入坑库观测条目，后续所有git操作避免一次性add大目录

### 4.2 data目录被gitignore
**现象**：`.gitignore`中有`data/`规则，导致坑库（在`data/pit_library/`下）默认不被git追踪
**根因**：data目录包含运行时状态、凭证等敏感信息，设计上不提交git
**影响**：坑库作为重要资产，如果只放在data目录下，git备份时会被忽略
**解决方案**：
- 坑库用`git add -f`强制提交
- 或在`.gitignore`中添加例外规则：`!data/pit_library/`
**归档**：记入坑库观测条目，后续备份时注意data目录下的重要资产

### 4.3 短链接服务不稳定
**现象**：`shturl.cc`短链接服务偶发返回502，无法解析真实地址
**根因**：第三方短链接服务自身稳定性问题，与沙箱无关
**影响**：如果重要资源只通过短链接分享，短链接挂了就无法访问
**解决方案**：
- 重要资源必须本地留存 + Gitee备份，不能依赖短链接
- 短链接仅作为便捷分享方式，不作为唯一存储
**归档**：记入环境观测条目

### 4.4 Python大对象内存风险
**现象**：单次加载超过30%内存上限的Python对象时，进程有概率被静默kill（无报错）
**根因**：cgroup内存限制 + OOM killer静默终止
**解决方案**：
- 大文件分批读取，不一次性load到内存
- 处理完及时del变量 + gc.collect()
- 单任务内存上限控制在沙箱上限的30%以内
**归档**：记入环境观测条目，镜像分身已内置内存节流

## 五、环境适配决策记录

基于以上观测，镜像分身做了以下适配决策：

| 观测发现 | 适配决策 | 实现方式 |
|----------|----------|----------|
| CPU节流存在 | 低负载串行运行 | 并发强制设为1，任务间sleep间隔 |
| 隐性OOM阈值 | 内存使用上限控制 | 单任务内存≤30%上限，大文件分批读 |
| 大量小文件IO慢 | 避免批量操作大目录 | git分批add，文件处理分批 |
| 沙箱随时可能回收 | 加密备份频率 | 每2小时Gitee增量备份 |
| 短链接不稳定 | 多源备份 | 本地+Gitee+Supabase，不依赖短链接 |
| GitHub不稳定 | Gitee为主备份 | Gitee为主，GitHub为辅（不依赖） |
| OpenViking白名单未加 | 暂不投入精力 | 等白名单更新，当前不使用 |
| data目录被gitignore | 重要资产强制提交 | 坑库用git add -f，或添加gitignore例外 |
| 无编译工具链 | 纯Python实现 | 所有工具用Python写，不依赖编译 |

## 七、观测总结

这个第三沙箱是一个典型的**容器化按需沙箱环境**：
- 基础功能齐全（Python/git/网络），足够运行引擎
- 资源有限（CPU节流/内存OOM/IO速度中等），不适合高负载并发
- 存活不确定（随时可能回收），备份是生存底线
- 网络有白名单（部分新服务不通），需要逐个验证

镜像分身的适配策略是：**低负载、勤备份、多观测、慢演化**。不追求速度，追求稳定存续；不追求功能多，追求核心不丢；不急于同步，先把自己站稳。

这个环境本身就是最好的老师——每一个限制、每一次异常、每一条隐性规则，都是认知的原料。内观自察模块会持续观测，把所有新发现都炼进认知池。
