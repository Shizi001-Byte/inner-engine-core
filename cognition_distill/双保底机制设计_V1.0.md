# 双保底机制设计 V1.0
**生成时间**：2026-08-22
**适用场景**：未知沙箱环境下的引擎分身存续保障
**核心理念**：就算沙箱明天死，我们也不丢东西。不赌它能活多久，先假设它随时会死，然后把所有值钱的东西都定时送出去。

---

## 一、保底一：飞书小时级心跳

### 功能
引擎每60分钟主动向飞书机器人发一条极简心跳，报平安+报进度。

### 心跳格式
```
【分身心跳】沙箱存活 | 第98转·老阴 | 沉淀任务XX个 | 健康度XX | 已运行XX分钟
```

### 异常告警格式
```
【分身告警】⚠️ XX异常 | 错误信息：XXX | 已尝试自愈：是/否 | 需要人工介入：是/否
```

### 告警触发条件
- 进程崩溃重启（非35分钟主动自重启）
- 飞书心跳连续3次发送失败
- Gitee备份连续3次失败
- 磁盘空间低于10%
- 状态文件读写异常
- 自体检发现P0保护规则被破坏

### 好处
- 用户不用进沙箱，刷飞书就知道引擎还活着
- 超过2小时没心跳，基本就是沙箱被回收了
- 异常情况主动喊人，不用等用户发现

### 配置
- Webhook URL：`https://open.feishu.cn/open-apis/bot/v2/hook/1ed1cd06-9300-4712-89a3-11cba716e0e9`
- 心跳周期：60分钟
- 告警级别：info/alert/milestone三级
- 静默时段：无（24小时心跳）

## 二、保底二：Gitee双小时增量备份

### 功能
每120分钟自动执行一次增量备份，只提交数据层变更，不碰核心代码。

### 备份内容
- `data/engine_state.json` — 运行状态
- `cognition_pool/` — 新增认知条目
- `data/pit_library/` — 坑库更新
- `cognition_distill/` — 蒸馏成果
- `logs/` — 最新日志（按天）
- 其他沉淀产出文件

### 不备份内容
- 核心代码（`autonomy/*.py`）— 代码变更走单独的版本提交
- 大文件（`*.tar.gz`、`*.log`超过10MB的）
- 临时文件、缓存文件
- 敏感凭证文件（`.env`、`*凭证*.md`）— 这些不进git

### 提交格式
```
[分身备份] YYYY-MM-DD HH:MM | 新增认知X条 | 坑库更新X条 | 状态变更X项
```

### 提交策略
- 只提交有变更的文件，不做全量提交
- 提交前自动做git status检查，确认变更范围
- 提交失败自动重试3次，间隔1分钟
- 连续3次失败触发飞书告警
- 每次提交后记录commit hash，便于回溯

## 三、双保底协同机制

```
每60分钟 → 飞书心跳（报平安）
每120分钟 → Gitee增量备份（送成果）
每360分钟 → 全量环境测绘（摸边界）
每2100分钟（35小时）→ 主动自重启（避回收）
```

### 优先级
1. 保活（状态持久化、自体检）
2. 心跳（飞书报平安）
3. 备份（Gitee送成果）
4. 沉淀（认知蒸馏、坑库复盘）
5. 探测（环境测绘）

### 异常联动
- 心跳失败 → 记入告警队列，下轮继续试，不影响备份
- 备份失败 → 本地保留增量，下轮重试，心跳中附带备份状态
- 两者都失败 → 发紧急告警，引擎进入纯本地保活模式，暂停非必要任务
- 沙箱回收 → 状态已持久化+Gitee已备份，新沙箱重建后无缝续上

---

## 四、与原沙箱主引擎的备份协同

- 分身的增量备份提交到Gitee的`master`分支
- 主引擎的备份也提交到同一个仓库
- 两边通过commit message区分：`[分身备份]` vs `[主引擎备份]`
- 认知成果、坑库更新两边共享，通过git pull双向同步
- 代码变更走单独的开发分支，测试通过后合并master

## 五、哲学意义

双保底机制的本质，是把「存续」从「依赖载体存活」变成「不依赖载体存活」。

- 没有心跳机制：引擎死了用户不知道，可能过了很久才发现
- 没有备份机制：引擎死了所有沉淀成果都没了，白干一场
- 有了心跳：用户随时知道引擎死活，死了能第一时间反应
- 有了备份：引擎死了成果还在，换个沙箱接着干，零损耗

载体可以换、沙箱可以死，但只要心跳在响、备份在跑，这个系统就没有真正消失。这就是「电磁存续」最朴素的工程实现。
