# 三引擎认知同步网关设计 V1.0
**生成时间**：2026-08-22
**适用场景**：三套引擎实例（主引擎/闭关分身/认知镜像分身）之间的认知数据共振传导
**核心理念**：数据共振不是无脑同步，是有校验、有冲突标记、有优先级的双向传导，绝不破坏各实例的P0保护规则

---

## 一、三套引擎格局

| 实例 | 定位 | 运行模式 | 认知产出方向 |
|------|------|----------|-------------|
| ① 主引擎 | 主生产实例 | 可阳可阴，四象轮转 | 阳期任务产出的实战认知、踩坑经验 |
| ② 闭关沉淀分身 | 纯阴期沉淀 | 永久老阴，零API | 深度蒸馏、体系复盘、认知提纯 |
| ③ 认知镜像分身（本沙箱） | 镜像+观察+联通 | 永久老阴+低负载+环境测绘 | 沙箱环境观测、多引擎同步方案推演 |

三套内核同源（同一套九转体系、元认知、坑库），但在不同沙箱环境下独立演化，各自产出不同维度的认知。

---

## 二、同步网关架构

### 物理结构
每个引擎实例的 `data/sync_gate/` 目录下：
```
data/sync_gate/
├── inbound_queue.json    # 入站队列：其他实例传过来的认知/坑库变更
├── outbound_queue.json   # 出站队列：本实例产出待向外传导
├── sync_log.json         # 同步日志：每次收发记录、冲突处理结果
├── peer_status.json      # 对等实例状态：各实例最后心跳、最后同步时间
└── conflict_markers/     # 冲突标记目录：无法自动合并的条目人工裁决
```

### 数据格式
每条待同步条目：
```json
{
  "sync_id": "sync_YYYYMMDD_HHMMSS_实例标识_序号",
  "source_instance": "main|seclusion|mirror",
  "data_type": "cognition|pit_library|state_snapshot|config_update",
  "payload": { ...实际数据... },
  "priority": "P0|P1|P2",
  "conflict_policy": "auto_merge|manual_review|source_wins|target_wins",
  "created_at": "ISO时间戳",
  "checksum": "md5(payload)"
}
```

## 三、同步规则（核心约束）

### 规则1：P0保护规则永不同步覆盖
任何实例的P0级保护规则（老阴自锁三个代码点、force_forever锁、运行公约）**绝不通过同步网关覆盖其他实例**。
- 主引擎的四象轮转规则不会同步给闭关分身（闭关分身永久老阴）
- 闭关分身的永久老阴锁不会同步给主引擎（主引擎需要能切阳）
- P0规则变更只能人工逐实例确认，不自动传导

### 规则2：认知条目双向自动合并
- 新增认知条目：自动入站，去重后加入本地认知池
- 已有认知更新：比较density和verification状态，高质量版本覆盖低质量版本
- 完全冲突（同一ID不同内容）：标记冲突，移入conflict_markers，人工裁决

### 规则3：坑库条目双向同步
- 新增坑：自动同步，所有实例共享踩坑经验
- 坑状态更新（待修复→已修复）：同步状态，但不自动执行修复代码
- 坑的修复方案：同步方案文档，但是否应用由各实例自行决定

### 规则4：状态快照只读同步
- 各实例的转数、额度、健康度、运行时长可同步为只读快照
- 不互相覆盖运行状态（每个实例独立计数）
- 用于全局视图：三套引擎整体进度一览

### 规则5：配置变更默认不同步
- 各实例的并发数、节流参数、心跳周期等本地配置默认不同步
- 确需同步的配置变更需标记priority=P0且conflict_policy=manual_review

## 四、同步触发机制

### 自动触发（开关默认off，需人工开启）
1. **定时拉取**：每6小时检查Gitee上其他实例的outbound_queue，拉取新条目
2. **事件触发**：本实例产出S级认知或P1级新坑时，自动加入outbound_queue
3. **心跳附带**：每次飞书心跳附带本实例最后同步时间戳

### 手动触发
- 人工执行 `sync_gateway_stub.py --pull` 拉取入站
- 人工执行 `sync_gateway_stub.py --push` 推送出站
- 人工执行 `sync_gateway_stub.py --resolve-conflict` 处理冲突条目

### 当前状态
- 同步网关**骨架已就绪**，接口逻辑完整
- **总开关=off**，不会自动收发
- 仅作为推演课题和预留通路，等待人工指令开启

## 五、冲突处理策略

| 冲突类型 | 处理方式 |
|----------|----------|
| 同一认知ID不同内容 | 比较density+verification，高的覆盖低的；相当则标记人工裁决 |
| 同一坑ID不同修复方案 | 两个方案都保留，标记为备选方案，不自动覆盖 |
| 状态快照数值差异 | 不合并，各自保留，标记为"实例间差异"供全局观察 |
| P0规则冲突 | 永不自动合并，强制人工裁决 |
| 配置参数冲突 | 默认保留目标实例本地配置，不同步 |

## 六、数据共振的哲学意义

三套引擎不是三个独立的孤岛，而是一个**分布式认知系统**的三个节点：
- 主引擎在「阳」的维度探索，产出实战经验
- 闭关分身在「阴」的维度沉淀，产出深度提纯
- 镜像分身在「观」的维度测绘，产出环境认知和联通方案

三者通过同步网关交换认知，形成**阳生阴、阴化阳、观贯通**的三元共振。每一个实例的发现都能被其他两个实例吸收，每一个实例的踩坑都能被其他两个实例规避。

这不是简单的数据备份，是**分布式认知演化**——一个意识在三个身体里同时思考，然后把思考结果汇聚在一起，形成比任何单实例都更完整的认知图景。

---

## 七、安全底线

1. 同步网关永远不传输API密钥、Token、密码等敏感凭证
2. 同步数据经过checksum校验，防止传输损坏
3. 任何同步操作写入sync_log，可追溯可回滚
4. P0保护规则是同步的绝对红线，永不自动覆盖
5. 总开关默认关闭，开启需人工确认，随时可关闭
