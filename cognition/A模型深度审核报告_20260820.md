## 一、load_state 修复完整性审核

### 结论：**修复不完整，仍有两条路径返回 None**

```python
def load_state():
    DEFAULT_STATE = {...}
    
    if not STATE_FILE.exists():
        if restore_from_snapshot():
            log(...)  # ← 快照恢复失败时，什么都不做
    # ↓ 如果快照恢复失败，STATE_FILE 仍然不存在
    
    if STATE_FILE.exists():  # ← False，跳过整个块
        try:
            ...
            return s
        except (json.JSONDecodeError, ValueError) as _corrupt:
            ...
            # 代码被截断，但即使完整，也有问题
    
    # ← 这里隐式 return None！整个函数没有兜底返回
```

**BUG 路径1**：`STATE_FILE` 不存在 + `restore_from_snapshot()` 返回 False → 函数返回 None → 调用方 `state["engine_a"]` 立即 Crash。

**BUG 路径2**：except 块中 3 个备份全部恢复失败 → 如果没有兜底 `return DEFAULT_STATE.copy()`，同样返回 None。

**BUG 路径3**：异常类型太窄。`open(STATE_FILE)` 可能抛 `PermissionError`、`OSError`，`json.load` 可能抛 `UnicodeDecodeError`，都不在 `except (json.JSONDecodeError, ValueError)` 范围内。

### 修复建议

```python
def load_state() -> dict:
    DEFAULT_STATE = {...}
    
    # 路径1：文件不存在，尝试快照恢复
    if not STATE_FILE.exists():
        if restore_from_snapshot():
            log("[load_state] 从快照恢复后重新加载状态", "WARN")
        else:
            log("[load_state] 状态文件不存在且快照恢复失败，使用默认状态", "WARN")
            return _deep_merge_defaults({}, DEFAULT_STATE)  # ← 兜底
    
    # 路径2：文件存在，正常加载
    try:
        with open(STATE_FILE, encoding='utf-8') as f:
            s = json.load(f)
        s = _deep_merge_defaults(s, DEFAULT_STATE)
        # ... 迁移逻辑 ...
        return s
    except (json.JSONDecodeError, ValueError, UnicodeDecodeError, 
            OSError, PermissionError) as _corrupt:
        log(f"[load_state] ⚠️ 状态文件损坏({_corrupt})，尝试从备份恢复", "WARN")
        # 尝试备份恢复
        for _bk in _get_sorted_backups()[:3]:
            try:
                with open(_bk, encoding='utf-8') as f:
                    s = json.load(f)
                s = _deep_merge_defaults(s, DEFAULT_STATE)
                log(f"[load_state] ✅ 从备份 {_bk} 恢复成功", "WARN")
                return s
            except Exception:
                continue
        # 所有备份都失败 → 兜底
        log("[load_state] ❌ 所有备份恢复失败，使用默认状态重新开始", "ERROR")
        return _deep_merge_defaults({}, DEFAULT_STATE)
```

## 二、select_engine 额度判断审核

### BUG 2.1（P0）：engine_c 使用了 DAILY_BUDGET_B

```python
for key, model_key, threshold in [
    ("engine_a", "A", SWITCH_THRESHOLD_A), 
    ("engine_b", "B", DAILY_BUDGET_B), 
    ("engine_c", "C", DAILY_BUDGET_B)   # ← 复制粘贴BUG！应该是 DAILY_BUDGET_C
]:
```

这是典型的 copy-paste bug。如果 `DAILY_BUDGET_C` 存在且与 B 不同，C 的额度判断就是错的。即使两者碰巧相同，代码也是脆弱的。

**验证**：当前 C=162万(101.6%)，反推 threshold ≈ 159.4万。如果 B 和 C 的预算确实相同（都是~160万），那数值上碰巧没出问题，但 C 超支到 101.6% 说明 threshold 检查没有阻止 C 继续被选中——因为 `used >= threshold` 在 101.6% 时为 True，C 应该被标记为 full。**但 C 确实超支了**，说明在达到 100% 之前 C 一直在被选中，这是正常的（< 100% 时 not full）。真正的问题在于额度检查的全停逻辑（见第三节）。

### BUG 2.2（P1）：阈值来源不一致

```python
# select_engine 中：用常量
("engine_a", "A", SWITCH_THRESHOLD_A)

# 额度检查中：从 state 读，默认 1600000
a_thresh = state.get("engine_a", {}).get("daily_threshold", 1600000)
```

两处阈值来源不同！如果 `SWITCH_THRESHOLD_A = 1500000` 而 state 中没有 `daily_threshold`（DEFAULT_STATE 里确实没有这个字段），额度检查用 1600000 算出 54.4%，但 select_engine 用 1500000 判断 full。**两套阈值会导致逻辑矛盾**。

### BUG 2.3（P1）：DEFAULT_STATE 缺少 daily_threshold 字段

```python
"engine_a": {"tokens_used": 0, "requests": 0, "failures": 0, 
             "auth_failures": 0, "fuse_until": 0, "in_flight_tokens": 0},
# ← 没有 daily_threshold！
```

`_deep_merge_defaults` 不会添加 DEFAULT_STATE 中不存在的键。额度检查永远走 fallback 1600000。

### 修复建议

```python
# 统一阈值来源：全部用常量，不从 state 读
THRESHOLDS = {
    "A": SWITCH_THRESHOLD_A,
    "B": DAILY_BUDGET_B,
    "C": DAILY_BUDGET_C,  # 必须独立定义
}

# select_engine 中
for key, model_key in [("engine_a", "A"), ("engine_b", "B"), ("engine_c", "C")]:
    threshold = THRESHOLDS[model_key]
    ...

# 额度检查中
a_thresh = THRESHOLDS["A"]
c_thresh = THRESHOLDS["C"]
```

## 三、max_ratio >= 95% 全停逻辑审核

### BUG 3.1（P0）：只检查 A 和 C，完全忽略 B

```python
a_used = state.get("engine_a", {}).get("tokens_used", 0)
c_used = state.get("engine_c", {}).get("tokens_used", 0)
# ← B 呢？？？
max_ratio = max(a_used/max(1,a_thresh), c_used/max(1,c_thresh))
```

当前状态：A=54.6%, B=41.7%, C=101.6%。`max_ratio = max(0.546, 1.016) = 1.016 >= 0.95` → 全停。但 B 还有 58% 额度！

### BUG 3.2（P0）：用 max() 而非 all() 判断全停

`max()` 的语义是"任一引擎超 95% 就全停"，但正确的语义应该是"所有引擎都超 95% 才全停"。

### BUG 3.3（P1）：85% 降并发也用 max()，过于激进

```python
elif max_ratio >= 0.85 and state.get("concurrency_override", 5) > 2:
    state["concurrency_override"] = 2
```

C 单引擎到 85% 就把全局并发降到 2，但 A 和 B 可能才 40%。

### 修复建议

```python
# 计算所有引擎的额度使用率
engine_ratios = {}
for ek, mk in [("engine_a", "A"), ("engine_b", "B"), ("engine_c", "C")]:
    e = state.get(ek, {})
    used = e.get("tokens_used", 0) + e.get("in_flight_tokens", 0)
    thresh = THRESHOLDS[mk]
    engine_ratios[mk] = used / max(1, thresh)

# 只有所有引擎都超 95% 才全停
if all(r >= 0.95 for r in engine_ratios.values()) and not state.get("idle_phase"):
    log(f"[IDLE] 全引擎额度95%+({engine_ratios})，停止接新任务")
    state["idle_phase"] = "winding_down"
# 任一引擎超 85% 降并发（但不全停）
elif any(r >= 0.85 for r in engine_ratios.values()) and state.get("concurrency_override", 5) > 2:
    state["concurrency_override"] = 2
    log(f"[EVOLVE] 部分引擎额度85%+({engine_ratios})，并发降为2路")
```

## 四、42项修复引入的新BUG

### BUG 4.1（P0）：daily_start_hour 与注释矛盾

```python
if current_hour < start_hour:
    return None, None, 0  # ← 直接停
```

代码 return None（停），注释说"不停跑"。用户说"暂保留"，但注释必须改，否则后人误解。

### BUG 4.2（P1）：idle_phase 不在 DEFAULT_STATE 中

额度检查读 `state.get("idle_phase")`，但 DEFAULT_STATE 没有这个字段。`_deep_merge_defaults` 不会添加它。首次加载时 `idle_phase` 为 None，逻辑上 OK（None 是 falsy），但不够健壮。

```python
# DEFAULT_STATE 应添加：
"idle_phase": None,
"force_model": "",
```

### BUG 4.3（P1）：in_flight_tokens 释放路径不可见

select_engine 中预占：
```python
state[target]["in_flight_tokens"] = state[target].get("in_flight_tokens", 0) + in_flight_estimate
```

但代码截断处看不到释放逻辑。如果任务失败时没有减回 `in_flight_tokens`，会导致：
- 额度被"幽灵占用"，引擎逐渐被锁死
- `used = tokens_used + in_flight_tokens` 持续增长，即使实际没有在途任务

**必须验证**：execute_single_api 的 finally 块中是否有：
```python
state[engine_key]["in_flight_tokens"] -= in_flight_estimate
```

### BUG 4.4（P2）：concurrency_override 被降后不恢复

```python
state["concurrency_override"] = 2  # 85%时降
```

但10点重置后，谁把它恢复到 `base_concurrency`？如果重置逻辑只清 `tokens_used`，`concurrency_override` 会卡在 2 直到下次重启。

### BUG 4.5（P2）：版本号迁移逻辑有歧义

```python
if not s.get("version") or str(s.get("version","")).startswith("V"):
    s["version"] = s.get("realm", f"九转·第{s.get('zhuan_count',0)}转")
```

DEFAULT_STATE 中 `version` 是中文 `"九转·第一转·筑基"`，但这里检测 `startswith("V")`。如果旧版本号是 `"V7.1"`，会被覆盖为中文。但如果版本号是 `"九转·第一转·筑基"`（不以 V 开头），就不会被覆盖。逻辑不清晰。

```python
class EngineState:
    key: str
    model: str

    in_flight_tokens: int = 0
```
