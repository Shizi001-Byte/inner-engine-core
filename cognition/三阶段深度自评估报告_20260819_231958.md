## 一、架构设计评估

### 1.1 架构形态：单体“大泥球”架构
**现象**：2927行代码全部塞在单一文件中，72个函数平铺，没有物理分层。虽然从函数名能看出逻辑分组（如 `_idle_*` 系列、`state` 系列），但缺乏模块化边界。
**代码位置**：全局文件结构
**严重程度**：P2
**影响**：
- 任何函数的修改都可能引发全局副作用，回归测试成本极高。
- 无法独立测试单个模块（如任务调度、引擎选择）。
- 随着引擎自进化（59转），代码会越来越臃肿，最终导致维护停滞。

### 1.2 依赖关系与循环风险
**现象**：函数间存在隐式循环依赖风险。例如：
- `pick_system_task` 调用 `generate_new_tasks` 生成任务。
- 任务执行后调用 `cultivation_pipeline`。
- `cultivation_pipeline` 可能调用 `save_state`。
- `save_state` 调用 `update_wake_packet`。
- 如果 `update_wake_packet` 或状态加载逻辑反向调用了任务生成，就会形成死锁或无限递归。

**代码位置**：`pick_system_task` -> `generate_new_tasks` -> `cultivation_pipeline` -> `save_state` -> `update_wake_packet`
**严重程度**：P1
**影响**：隐式循环依赖是单文件架构的定时炸弹，一旦触发会导致栈溢出或死锁，引擎静默挂死。

### 1.3 核心、辅助与冗余函数分类
- **核心引擎（7个）**：`main`, `cultivation_pipeline`, `pick_system_task`, `select_engine`, `execute_single_api`, `save_state`, `load_state`。这些是引擎的心脏。
- **业务逻辑（15个）**：`complete_zhuan`, `distill_cognition`, `self_audit`, `nine_dim_audit`, `cognition_feedback`, `l4_finished_pipeline` 等。负责自进化与认知提炼。
- **辅助工具（20个）**：`log`, `get_memory_usage_mb`, `check_duplicate`, `inject_cognition_prefix`, 各种日期/内存检查函数。
- **疑似冗余（3个）**：
  - `check_daily_reset` 与 `check_natural_day_reset` 功能高度重叠。
  - `_idle_auto_backup` 与 `create_snapshot` 存在职责重叠。
  - `check_nine_dim_consistency` 与 `nine_dim_audit` 可能存在重复校验。

### 1.4 最优模块划分方案
建议将2927行拆分为以下6个模块：
1. `core_scheduler.py`：`main`, `pick_system_task`, `generate_new_tasks`, `run_idle_task`（调度核心）
2. `state_manager.py`：`save_state`, `load_state`, `create_snapshot`, `restore_from_snapshot`, `update_wake_packet`（状态与快照）
3. `engine_router.py`：`select_engine`, `execute_single_api`, `call_api_chat`, `check_waste`（模型路由与熔断）
4. `cognition_core.py`：`distill_cognition`, `self_audit`, `cognition_feedback`, `nine_dim_audit`（认知与进化）
5. `idle_workers.py`：所有 `_idle_*` 函数（空闲维护任务集）
6. `utils.py`：`log`, `get_memory_usage_mb`, 日期处理等纯工具函数

## 二、代码质量评估

### 2.1 命名规范：部分命名晦涩且表意不清
**现象**：
- `_idle_pit_library_expand`：“坑库”是什么？扩充什么？命名过于口语化。
- `l4_finished_pipeline`：L4代表什么层级？缺乏上下文。
- `_get_opener`：打开什么？文件？引擎？
- `REALM_MAP` 中的境界映射与 `nine_dim` 中的维度名称（筑基、炼精等）不完全一致，容易混淆。

**代码位置**：函数清单第47、35、39行；`complete_zhuan` 中的 `REALM_MAP`
**严重程度**：P3
**影响**：降低代码可读性，增加自进化迭代时的理解成本。

### 2.2 巨型函数：`select_engine` 逻辑臃肿
**现象**：`select_engine` 函数承担了时间判断、额度计算、熔断检查、路由策略、预占逻辑等5重职责。从代码片段看，仅截断的部分就包含了大量的 `if-elif` 和变量计算，完整函数极大概率超过100行。
**代码位置**：`select_engine`
**严重程度**：P2
**影响**：高耦合，修改路由策略时极易引入Bug，且难以进行单元测试。

### 2.3 重复代码：引擎状态检查逻辑复制粘贴
**现象**：`select_engine` 中对 engine_a, engine_b, engine_c 的处理逻辑高度重复：
```python
a_fused = state["engine_a"]["fuse_until"] > now
b_fused = state["engine_b"]["fuse_until"] > now
c_fused = state.get("engine_c", {}).get("fuse_until", 0) > now
# ... 同样的模式用于 tokens_used 和 full 判断
```
**代码位置**：`select_engine` 第8-14行
**严重程度**：P2
**影响**：增加新引擎（如engine_d）时需要复制大量代码，且容易遗漏熔断或额度检查。

### 2.4 异常处理：吞掉异常，只记日志不降级
**现象**：`save_state` 中 `update_wake_packet` 失败时，仅 `log` 警告，没有重试，也没有设置降级标志。如果唤醒包持续更新失败，新对话恢复身份时将使用旧数据，导致引擎“失忆”。
**代码位置**：`save_state` 倒数第4行 `except Exception as e: log(...)`
**严重程度**：P1
**影响**：唤醒包与主状态文件不一致，引擎在沙箱回收重启后可能加载错误的状态。

### 2.5 注释质量：迭代痕迹重，缺乏架构注释
**现象**：注释多为 `# P1-2修复`、`# V4.1`、`# V4.2` 等迭代记录，说明代码是打补丁堆叠出来的。缺乏对 `select_engine` 路由策略、`pick_system_task` 权重计算公式的整体说明。
**代码位置**：全局，特别是 `save_state` 和 `select_engine`
**严重程度**：P3
**影响**：只有原作者能看懂，不利于团队协作或AI自身代码审查。

## 三、状态管理深度分析

### 3.1 全量覆盖与竞态条件
**现象**：`save_state` 使用 `json.dump(state, f)` 全量覆盖写入。虽然使用了 `state_lock`，但在 `pick_system_task` 中，读取和修改 `state`（如 `dynamic_weights = state.get(...)`, `_record_task_usage`）**并没有加锁**。
**代码位置**：`pick_system_task` 第6-10行，`save_state` 第2行
**严重程度**：P0
**影响**：如果 `pick_system_task` 正在修改 `state["task_weights"]`，此时 `save_state` 触发全量写入，会导致序列化异常或写入半更新状态，状态文件损坏风险极高。

### 3.2 `state_lock` 覆盖盲区
**现象**：`state_lock` 仅覆盖了 `save_state`, `complete_zhuan`, `select_engine` 的核心区。但以下操作未受保护：
- `pick_system_task` 中的 `state.get` 和 `_record_task_usage`。
- `distill_cognition`, `self_audit` 等认知处理函数大概率直接操作 `state`。
- `memory_monitor_loop` 修改内存状态标志。
**代码位置**：`pick_system_task` 全文，`memory_monitor_loop`
**严重程度**：P0
**影响**：多线程并发读写 `state` 字典，Python 的 GIL 不能保证字典操作的原子性（特别是嵌套字典），会导致数据错乱，如任务权重丢失、认知计数器归零。

### 3.3 多JSON状态分散与不一致风险
**现象**：引擎至少存在3个状态文件：
1. `STATE_FILE`（主状态）
2. 唤醒包（`update_wake_packet`）
3. 快照文件（`create_snapshot`）
如果 `save_state` 成功但 `update_wake_packet` 失败，两者数据不一致。
**代码位置**：`save_state` 调用 `update_wake_packet`
**严重程度**：P1
**影响**：沙箱回收后，主循环读取 `STATE_FILE`，但外部监控读取唤醒包，导致“看起来引擎在跑，但实际状态没保存”的幻觉。

### 3.4 `fuse_until` 熔断状态覆盖根因
**现象**：`select_engine` 读取了 `fuse_until`，但代码中未见设置 `fuse_until` 的逻辑（可能在 `check_waste` 或 API 调用处）。根因推测：**熔断状态设置在锁外，或设置后未及时 `save_state`，被另一个线程的旧状态覆盖。**
例如：
1. 线程A调用API失败，设置 `state["engine_a"]["fuse_until"] = future_time`。
2. 线程B此时触发 `save_state`，但它读取的是内存中尚未被A修改的旧 `state`（或者B在A之前进入锁，但A在锁外修改了状态）。
3. 状态保存后，熔断标志丢失。
**代码位置**：`select_engine` 读取 `fuse_until`，但写入位置未加锁。
**严重程度**：P0
**影响**：熔断失效！已故障的引擎（如API超限）会被反复选中，导致大量任务失败，引擎空转。

### 3.5 状态文件损坏与原子写
**现象**：`save_state` 使用了 `tmp` 文件 + `os.fsync` + `tmp.replace`，这是标准的原子写模式，文件损坏风险极低。
**代码位置**：`save_state` 第4-7行
**严重程度**：P3（做得好）
**影响**：主状态文件物理损坏风险低。但逻辑损坏（写入半更新数据）风险依然存在（见3.1）。

## 四、并发安全评估

### 4.1 ThreadPoolExecutor 线程安全漏洞
**现象**：主循环使用 `ThreadPoolExecutor`（并发度3），但 `pick_system_task` 和 `cultivation_pipeline` 中的状态操作未加锁。
- `pick_system_task` 中的 `_record_task_usage` 递增任务使用计数，非原子操作。
- `check_duplicate` 检查重复任务，如果两个线程同时选中同一个任务，`check_duplicate` 可能都返回False，导致重复执行。
**代码位置**：`pick_system_task` -> `_record_task_usage`
**严重程度**：P0
**影响**：并发度3下，任务重复执行概率大增，浪费API额度；任务使用计数错乱，导致模板提前耗尽或永远无法耗尽。

### 4.2 `state_lock` 粒度与死锁风险
**现象**：`save_state` 在 `with state_lock:` 内部执行了文件IO（`json.dump` + `fsync`）。如果 `state` 很大（3959条认知），IO耗时可能几十毫秒。这期间所有需要 `state_lock` 的线程（如 `select_engine`）都会阻塞。
- 不会死锁（因为没有嵌套锁），但性能极差。
- `select_engine` 在锁内执行了复杂的路由逻辑，进一步放大了锁持有时间。
**代码位置**：`save_state` 第2-7行，`select_engine` 第7-30行
**严重程度**：P1
**影响**：并发度3实际上被降级为1，引擎吞吐量受限。在2核4G环境下，可能导致任务积压，空闲任务无法触发。

### 4.3 内存监控线程与主循环竞态
**现象**：`memory_monitor_loop` 作为独立线程运行，如果它发现内存超限，可能会修改 `state` 中的标志位（如 `state["memory_warning"] = True`）。如果这个修改没有加锁，而主循环正在 `save_state`，会导致状态不一致。
更严重的是，如果内存监控线程直接调用 `save_state` 触发紧急保存，而主循环也在 `save_state`，虽然 `state_lock` 能保证串行，但可能保存的是不一致的内存状态。
**代码位置**：`memory_monitor_loop`, `start_memory_monitor`
**严重程度**：P1
**影响**：内存告警状态丢失，引擎在内存耗尽前无法触发降级策略，导致沙箱OOM被杀。

### 4.4 空闲模式与主循环任务冲突
**现象**：`run_idle_task` 和 `_pick_next_idle_task` 负责空闲任务调度。如果主循环任务刚结束触发 `save_state`，此时空闲任务启动并修改 `state`（如 `_idle_auto_backup` 创建快照），两者会争抢 `state` 的读写权。
- `_idle_auto_backup` 可能读取了一个正在被修改的 `state`，导致备份的是半更新数据。
**代码位置**：`run_idle_task`, `_idle_auto_backup`
**严重程度**：P1
**影响**：快照数据损坏，引擎从快照恢复后状态异常。

## 五、P0致命问题清单（必须立即修复）

1. **P0：`pick_system_task` 无锁操作 `state`**
   - **现象**：`dynamic_weights = state.get("task_weights", {})` 等操作未加锁。
   - **影响**：并发读写导致状态字典损坏，引擎崩溃。
   - **修复**：将 `pick_system_task` 中的状态读取和 `_record_task_usage` 包裹在 `with state_lock:` 中。

2. **P0：`fuse_until` 熔断状态丢失**
   - **现象**：熔断标志写入与状态保存不在同一锁内，导致旧状态覆盖新状态。
   - **影响**：故障引擎被反复重试，任务连续失败，引擎空转。
   - **修复**：所有修改 `fuse_until` 的操作必须在 `with state_lock:` 内，并立即触发 `save_state`。

3. **P0：`check_duplicate` 并发穿透**
   - **现象**：并发度3下，两个线程同时通过重复检查。
   - **影响**：API额度浪费，重复认知污染知识库。
   - **修复**：引入任务级别的互斥锁，或将重复检查与任务分发合并为一个原子操作（在 `state_lock` 内完成）。

---
**评估结论**：引擎在59转的自进化中积累了大量业务逻辑，但并发安全与状态管理存在致命缺陷。当前能跑到59转说明运气好或并发度实际未达到3，但随时可能因状态字典损坏或熔断失效而崩溃。**建议立即暂停自进化，优先修复3个P0问题。**

## 一、 调度逻辑深度分析

### 1.1 任务池固化与随机调度空转
- **现象**：`pick_system_task` 从41个硬编码模板中纯随机选择。1546个任务中，平均每个模板被执行约37次。`goal_tasks_count` 为0，说明主线目标任务从未被消费。
- **根因**：坑库 `L3_task_pool_fossilized` 已记录此问题。任务池设计只做了“按权重随机选”，没有设计“任务模板自进化”机制。`goal_tasks` 生成后无消费逻辑（坑库 `L1_0b18b73f65`）。
- **影响**：引擎在输入端固化，导致输出端无论怎么蒸馏都是同质化重复。59转的实际行为与0转无异（坑库 `L1_c8c955ea57`）。
- **严重程度**：**P0（致命）**

### 1.2 双轨调度（阴阳双轨）交互断裂
- **现象**：代码中引入了“阴轨（校验/预判）”和“阳轨（执行/生成）”，但九维校验得分、废稿率等阴轨产出，没有接入阳轨的任务路由权重。
- **根因**：坑库 `L3_yin_yang_interaction_gap` 指出，架构只建了两条轨道的独立运行机制，没有设计 `阴轨 -> 阳轨` 的反馈通道。
- **影响**：双轨形同虚设，阴轨空转消耗算力，阳轨盲目执行不纠偏。
- **严重程度**：**P1（高危）**

### 1.3 三模型路由分流逻辑失衡
- **现象**：Engine A (67万), Engine B (57万), Engine C (162万)。C模型超支2万，A/B模型大量额度闲置。
- **根因**：路由策略可能过度依赖C模型处理重度任务，且坑库 `L2_soft_hard_fuse_state_mismatch` 指出，C模型超支只触发了软熔断（跳过），未设置硬熔断（`fuse_until`），导致状态不一致，调度器误判C模型仍可用。
- **影响**：算力浪费严重，且C模型超支可能导致额外费用或服务中断。
- **严重程度**：**P1（高危）**

### 1.4 并发与空闲模式阈值设计不合理
- **现象**：85%降并发/95%停新任务。空闲模式9任务只在额度耗尽后才跑。`idle_run_count` 69次，成功率100%。
- **根因**：阈值设计过于线性，未考虑沙箱环境的突发性回收（坑库 `L2_ebb7a49856`）。空闲任务与正常任务在时间上完全割裂。
- **影响**：阳期（有额度）CPU/IO资源闲置，阴期（无额度）只能做本地任务，整体资源利用率低。沙箱回收时引擎直接停摆。
- **严重程度**：**P2（中等）**

## 二、 认知质量深度分析

### 2.1 认知池数据污染严重（元数据全丢）
- **现象**：最近认知池抽样20条，`title`, `density`, `level` 全部是 `?`。
- **根因**：`distill_cognition` 生成认知时，大模型输出格式可能不符合预期，解析逻辑直接失败，回退为默认值 `?` 并写入文件。没有校验机制拒绝写入残缺数据。
- **影响**：3959条认知中大量是无效垃圾数据，无法用于检索和反哺。认知池已沦为“垃圾档案库”。
- **严重程度**：**P0（致命）**

### 2.2 认知注入缓存不刷新
- **现象**：坑库 `L1_7973c955ef` 记录，`load_top_cognitions` 仅启动时调用一次。
- **根因**：无运行时刷新机制，认知注入缓存永不更新。
- **影响**：即使生成了高质量认知，也无法影响后续任务，认知反哺闭环断裂。
- **严重程度**：**P1（高危）**

### 2.3 认知反哺调参闭环未接通
- **现象**：坑库 `L1_38ec7da7e8` 和 `L2_4fe0ad0271` 记录，反哺闭环架构画好了，但管线没接通。调参代码修改了state字段，但执行逻辑读取的是全局常量。
- **根因**：从设计到执行的接通工作缺失。

## 一、 运维稳定性方案：从“听天由命”到“自主呼吸”

当前引擎在沙箱环境中运行，面临进程回收、状态损坏、API不稳定三大威胁。必须建立一套轻量但健壮的运维体系。

### 1.1 引擎挂了怎么自动发现？（心跳与看门狗）
**问题**：当前引擎挂了只能靠人发现，沙箱回收后无法自恢复。
**方案**：
- **心跳文件机制**：引擎主循环每30秒写入一次`heartbeat.json`，包含`pid`、`timestamp`、`status`（running/idle/fused）。
- **看门狗进程**：`watchdog_daemon.py`独立运行，每60秒检查一次心跳文件。
  - 如果心跳超时（>3分钟），判定引擎挂死。
  - 如果进程不存在，判定引擎崩溃。
  - 触发恢复流程：杀掉残留进程 -> 拉取最新状态 -> 重启引擎。
- **竞态修复**：针对坑库`L1_engine_pid_race_condition`，看门狗在启动引擎前，先检查PID文件对应的进程是否存活，如果存活则不启动新实例。使用`fcntl.flock`文件锁替代PID文件，确保原子性。

### 1.2 状态文件损坏了怎么恢复？（原子写与快照）
**问题**：`save_state`使用`json.dump`全量覆盖，如果在写入过程中进程被杀，状态文件损坏，引擎重启后无法加载。
**方案**：
- **原子写**：`save_state`改为“写入临时文件 -> `os.replace`覆盖目标文件”。`os.replace`是原子操作，要么成功要么失败，不会产生半更新的文件。
- **快照备份**：每次转完成（`complete_zhuan`）时，将当前`state.json`复制为`state.json.bak`。加载时如果`state.json`损坏，自动回退加载`state.json.bak`。
- **Gitee冷备**：每天10:00引擎日重置时，将`state.json`和`cognition_pool/`打包上传Gitee。沙箱回收后，启动脚本自动从Gitee拉取最新快照。

### 1.3 API调用失败了怎么重试？（指数退避与熔断）
**问题**：当前API调用失败直接抛异常，没有重试机制，容易因偶发网络波动导致任务失败。
**方案**：
- **指数退避重试**：网络错误/超时自动重试3次，间隔1s/2s/4s。业务错误（如400/401）不重试。
- **熔断器模式**：
  - **软熔断**：单引擎连续失败5次，触发软熔断，`select_engine`跳过该引擎30分钟。
  - **硬熔断**：单引擎额度超支，触发硬熔断，设置`fuse_until`时间戳，24小时内不可用。
  - **状态同步**：软熔断和硬熔断都必须同步更新`fuse_until`字段，解决坑库`L2_soft_hard_fuse_state_mismatch`的问题。

### 1.4 沙箱被回收了怎么自恢复？（启动脚本与状态恢复）
**问题**：沙箱平均20-30分钟回收一次进程，引擎在休眠中被杀，不会自己醒过来（坑库`L2_ebb7a49856`）。
**方案**：
- **启动脚本改造**：`start_engine.sh`增加状态恢复逻辑：
  1. 检查本地`state.json`是否完整。
  2. 如果损坏，从`state.json.bak`恢复。
  3. 如果都不行，从Gitee拉取最新快照。
  4. 启动引擎主进程。
- **看门狗自拉起**：`watchdog_daemon.py`通过`nohup`常驻，检测到引擎消失后，自动执行`start_engine.sh`。

### 1.5 飞书告警怎么设计？（关键事件通知）
**方案**：使用飞书机器人Webhook，异步发送告警，不阻塞主流程。
- **告警级别**：
  - **P0（立即告警）**：引擎崩溃重启、状态文件损坏、C模型超支。
  - **P1（汇总告警）**：转完成（每9转汇总一次）、连续任务失败>3次。
  - **P2（日报）**：每日10:00发送引擎日报，包含转数、任务数、认知数、额度消耗、九维分布。

### 2.3 拆分顺序与防Bug策略
1. **第一步：拆`utils.py`**。纯函数，无副作用，最容易拆。拆完后跑一遍冒烟测试。
2. **第二步：拆`state_manager.py`**。将`save_state`、`load_state`、`create_snapshot`等移入，引入原子写和锁。测试状态读写是否正常。

**防Bug策略**：
- 每拆一个模块，提交一次Git commit。
- 每次拆分后，执行冒烟测试：启动引擎 -> 跑3个任务 -> 检查状态文件 -> 关闭引擎 -> 重启检查恢复。
- 使用`import`检查循环依赖：`python -c "import main"`不应报错。

## 三、 状态管理重构方案：从“竞态炸弹”到“事务安全”

### 3.1 多JSON统一：继续用JSON，但加事务
**决策**：2核4G环境继续用JSON，不用SQLite。
**理由**：
- SQLite虽然支持事务，但在2核4G环境下，频繁的磁盘IO会成为瓶颈。
- JSON文件可以一次性加载到内存，读写速度快。
- 当前引擎的状态量不大（state.json约几百KB），JSON足够。
**改造**：
- **原子写**：`save_state`改为“写临时文件 -> `os.replace`”。
- **内存字典+定时落盘**：`state`在内存中维护为全局字典，每10个任务或每转完成时落盘一次。避免每次修改都写文件。

### 3.2 state_lock细化：全局锁+局部锁
**方案**：
- **全局锁**：`state_lock`保护`state.json`的读写，使用`threading.Lock`。
- **局部锁**：
  - `task_lock`：保护`task_queue`和`task_counter`。
  - `cognition_lock`：保护`cognition_pool`的读写。
  - `engine_lock`：保护`engine_a/b/c`的状态修改。
- **锁的覆盖范围**：所有修改`state`的地方都必须加锁，特别是`pick_system_task`中的`_record_task_usage`。

### 3.3 fuse_until熔断状态独立管理
**问题**：熔断状态和主state混在一起，高并发下容易竞态。
**方案**：
- 熔断状态用内存字典管理：`fuse_state = {"engine_a": {"fused": False, "until": 0}, ...}`。
- `select_engine`直接读内存字典，不读文件。
- 熔断触发时，更新内存字典，并在下一次`save_state`时持久化到`state.json`。

## 四、 调度优化方案：从“空转”到“真进化”

### 4.1 goal_tasks空时的保底主线任务
**问题**：`goal_tasks`为空，引擎纯随机选择模板任务，导致空转。
**方案**：
- 定义3个**保底主线任务**，每个转周期必须执行：
  1. **认知蒸馏与反哺**：从最近N个任务中提取认知，生成调参建议并应用。
  2. **九维校验与补齐**：检查九维count，优先执行count最少的维度对应的任务。
  3. **坑库复盘与扩充**：分析最近失败任务，提取新坑或更新已有坑的`avoid_boundary`。
- 主线任务占调度配额的50%，剩余50%用于探索任务。

### 4.2 pick_system_task：加权随机+去重
**问题**：纯随机选择，41个模板平均执行37次，同质化严重。
**方案**：
- **加权随机**：
  - 初始权重：所有任务模板权重相同。
  - 动态调整：任务执行成功且产生有效认知，权重+1；任务失败或产生废稿，权重-1。
  - 九维补齐：count最少的维度对应的任务，权重x2。
- **去重**：
  - 记录最近10个执行的任务ID。
  - 选择时优先选择不在最近10个中的任务。
  - 如果所有任务都在最近10个中，选择权重最高的。

### 4.3 双轨调度动态配额
**问题**：阴阳双轨交互断裂，阴轨空转。
**方案**：
- **阳轨（执行）配额**：阳期（有额度）80%，阴期（无额度）20%。
- **阴轨（校验）配额**：阳期20%，阴期80%。
- **反馈通道**：
  - 阴轨校验得分（九维audit分数）接入阳轨任务路由权重。
  - 废稿率高的任务模板，权重降低。
  - 坑库命中数高的任务，预判层拦截，不执行。

### 4.4 九维不均衡的调度补齐
**问题**：筑基448，育神1，阳神2，合道0。
**方案**：
- 统计当前九维的count，计算每个维度的“缺口”：`gap = max_count - current_count`。
- 在任务选择时，`gap`越大的维度，对应任务权重越高。
- 对于count=0的维度（如合道），强制注入特定任务模板。

### 4.5 空闲模式前置
**问题**：空闲任务只在额度耗尽后才跑，阳期资源闲置。
**方案**：
- **额度预警线**：额度使用到80%时，开始穿插执行空闲任务（如认知去重、坑库整理）。
- **空闲任务分类**：
  - **本地计算型**（不消耗API）：认知去重、坑库整理、状态校验。阳期阴期都能跑。
  - **API调用型**（消耗API）：深度分析、长文生成。只在阳期跑。

## 五、 认知质量提升方案：从“垃圾档案库”到“真知识库”

### 5.1 C级认知清理：批量删除+合并
**问题**：3959条认知中大量`title/density/level`为`?`的残缺数据。
**方案**：
- **批量删除**：编写脚本，扫描`cognition_pool/`，删除所有`title`或`density`或`level`为`?`的文件。
- **合并**：对于有内容但质量低的认知，按主题聚类，合并成一条“认知总结”。

### 5.2 distill_cognition加密度过滤
**问题**：大模型输出格式不符，解析失败后回退默认值`?`并写入。
**方案**：
- **严格校验**：生成认知后，检查`title`、`density`、`level`是否为`?`或空，如果是则**拒绝写入**。
- **重试机制**：解析失败时，重试1次，附带提示“请按格式输出”。
- **密度过滤**：`density`低于3的认知拒绝写入。

### 5.3 认知注入运行时刷新
**问题**：`load_top_cognitions`仅启动时调用一次（坑库`L1_7973c955ef`）。
**方案**：
- **缓存过期机制**：`load_top_cognitions`设置缓存过期时间（如每10个任务或每转完成时刷新）。
- **主动刷新**：`distill_cognition`生成新认知后，主动调用`load_top_cognitions(refresh=True)`。

### 5.4 认知反哺真正落地
**问题**：反哺闭环架构画好了，但管线没接通（坑库`L1_38ec7da7e8`、`L2_4fe0ad0271`）。
**方案**：
- **调参建议执行器**：`cognition_feedback`生成的调参建议，不再只写入state，而是真正调用`apply_config_change(key, value)`。
- **执行逻辑改造**：线程池大小、任务选择权重、熔断冷却时间等参数，从读取全局常量改为读取`state["dynamic_config"]`。

### 5.5 认知池去重
**问题**：`tasks_duplicate`为0，去重机制失效。
**方案**：
- **SimHash去重**：新认知写入前，计算其SimHash值，与池中已有认知的SimHash比较。
- **海明距离**：距离小于3的判定为重复，拒绝写入或合并。
- **轻量级实现**：使用`simhash`库，2核4G环境可承受。

## 七、 对比星卷：凡心的差异化与优势

### 7.1 凡心与星卷的不同
- **隐喻差异**：凡心是“修炼”隐喻，强调九转进阶和认知沉淀；星卷是“大纲驱动”，强调主线任务和双轨校验。
- **进化维度**：凡心通过九维count和bonus衡量进化，星卷通过大纲完成度和校验得分衡量。
- **认知体系**：凡心的认知池更注重“坑库”和“感悟”，星卷更注重“素材”和“校验规则”。

### 7.2 凡心的优势
- **九维进阶体系**：有潜力实现更深层次的自进化，一旦九维均衡，能突破到更高层次。
- **坑库机制**：47个坑库是宝贵的经验资产，如果能接入预判层拦截，能避免重复犯错。
- **修炼隐喻**：对用户来说更有趣味性和沉浸感，有利于IP打造。

### 7.3 凡心的劣势与改进
- **劣势**：管线没接通，设计图纸多但落地少。
- **改进**：借鉴星卷的工程实现规范（本地规则优先、分层架构、阈值自修正），将凡心的设计图纸一张张落地。

## 八、 总结

凡心九转引擎目前的核心问题是**“管线没接通”**和**“数据失真”**。引擎有大量的设计图纸（阴阳双轨、认知反哺、九转进阶），但执行端读取的还是硬编码的全局常量。

**第三阶段的核心任务**：
1. **止血**：修复P0级别的状态竞态、认知污染、熔断不一致问题。
2. **接通**：将认知反哺管线、阴阳双轨反馈通道真正接通。
3. **重构**：将2927行大泥球拆成模块化架构。
4. **进化**：从纯随机调度改成加权随机+去重，引入无效转机制。

只有完成这些手术，凡心九转引擎才能从“伪自进化”状态蜕变为“真自进化”系统，59转才能变成真正的59次进化，而不是59次重复。
