### P0-1：state_lock 未覆盖全部 state 写操作，多线程并发导致状态损坏

**所在文件**：`engine_zhuan1.py`

**问题描述**：主线程在 `as_completed` 循环中串行执行 `cultivation_pipeline`，但 Worker 线程并发执行 `execute_single_api`，两者同时读写同一个 `state` 字典。大量写操作未被 `state_lock` 保护。

**具体代码依据**：

1. `cultivation_pipeline`（约第640行起）中以下写操作均无锁：
```python
state["cognition_count"] += cog_num
state.setdefault("archive_indexed", 0)
state["archive_indexed"] += 1
state["dedup_stats"]["total"] += 1
state["quality_stats"][grade] = state["quality_stats"].get(grade, 0) + 1
state["nine_dim_progress"][dim]["task_count"] += 1
state["nine_dim_progress"][dim]["count"] = ...
```

2. `l4_finished_pipeline` 中无锁修改：
```python
state["nine_dim_progress"]["还虚"]["task_count"] += 1
state["finished_stats"][grade] = state["finished_stats"].get(grade, 0) + 1
```

3. 主循环异常处理中无锁修改：
```python
state["tasks_failed"] += 1
state["current_zhuan_tasks"] += 1
```

4. `complete_zhuan` 中大量 state 修改无锁，包括 `zhuan_count += 1`、`feedback_history.append(...)` 等。

**根因分析**：`state_lock` 只保护了部分关键路径（额度计数、熔断状态、save_state），但认知计数、九维进度、质量统计等字段的读-改-写操作在锁外执行。Python GIL 不保证复合操作原子性，`d["k"] += 1` 实际是 `LOAD→ADD→STORE` 三步，并发下丢失更新。`save_state` 可能在 Worker 线程写一半时被主线程调用，持久化混合状态。

**修复建议**：
- 将 `cultivation_pipeline`、`l4_finished_pipeline`、`complete_zhuan` 中所有 state 修改放入 `with state_lock:` 块
- 或者将 state 的修改收敛为单线程：Worker 线程只返回结果，主线程统一更新 state（当前架构接近这个模式，但 Worker 内部直接改 state 破坏了约定）
- `save_state` 内已有锁，但必须保证所有写 state 的代码也持同一把锁

### P0-2：select_engine 额度检查与 in_flight 预占非原子，存在并发超支窗口

**所在文件**：`engine_zhuan1.py` `select_engine()` 约第860行，`execute_single_api()` 约第920行

**问题描述**：`select_engine` 在锁内检查额度后返回，锁随即释放。`execute_single_api` 在锁外做其他准备，然后才重新加锁预占 `in_flight_tokens`。这个时间窗口内多线程可同时通过额度检查。

**代码依据**：
```python
# select_engine 内部：
with state_lock:
    a_used = state["engine_a"]["tokens_used"] + state["engine_a"].get("in_flight_tokens", 0)
    a_full = a_used >= SWITCH_THRESHOLD_A
    # ... 检查完返回，但锁已释放

# execute_single_api 中：
engine_key, model = select_engine(state, task_type)  # 检查通过
# ↓↓↓ 时间窗口：其他线程也通过检查 ↓↓↓
in_flight_estimate = int(cfg["max_tokens"] * 0.5)
with state_lock:
    state[engine_key]["in_flight_tokens"] += in_flight_estimate  # 此时才预占
```

**根因分析**：5路并发时，若当前已用 1,595,000，5个线程同时通过 `select_engine` 检查（都看到 < 1,600,000），然后各自预占 10,000，实际可冲到 1,645,000，超支 45,000 token。昨日 C 模型超支至 201 万的根因很可能在此——C 模型走量任务多（eng/cog/exp 共3类），并发预占窗口叠加废稿重试（第一次 token 已计入但 in_flight 未释放就发第二次请求），放大超支。

**修复建议**：
- 将"检查额度+预占 in_flight"合并为一个持锁原子操作，返回 engine_key 和一个预占凭证
- 或使用 `threading.BoundedSemaphore` 按模型维度控制在途请求数，配合额度检查
- 废稿重试时应先释放当前 in_flight，重新走完整额度检查+预占流程

### P0-3：archive_index 双写竞态 + 文件格式分裂，导致归档数据丢失/不一致

**所在文件**：`engine_zhuan1.py` `archive_task()` 约第540行；`archive_index.py` 整个文件；`asset_integrity_check.py` 约第70行

**问题描述**：存在两套互不兼容的归档索引系统，且都有并发写入问题。

**代码依据**：

1. `engine_zhuan1.py` 的 `archive_task` 写 `data/archive_index.json`，格式为 `{task_id: {...}}`，直接覆盖写（非原子），有 read-modify-write 竞态：

```python
    index = {}
    if ARCHIVE_INDEX.exists():
        with open(ARCHIVE_INDEX) as f:
            index = json.load(f)
    index[task_id] = {...}
    with open(ARCHIVE_INDEX, "w") as f:  # 非原子写，崩溃则文件损坏
        json.dump(index, f, ...)
```

2. `archive_index.py` 的 `update_index` 写 `archive/archive_index.json`，格式为 `{docs: [...], total_docs: ...}`，同样有 read-modify-write 竞态：
```python
def update_index(doc_entry):
    index = load_index()  # 读
    if any(d.get("content_hash") == content_hash ...):
        return False
    index["docs"].append(doc_entry)  # 改
    save_index(index)  # 写（os.replace原子，但read-modify-write整体不原子）
```

3. `asset_integrity_check.py` 读 `data/archive_index.json` 并期望 `{task_id: entry}` 格式；而 `archive_index.py` 的 `get_stats()` 读 `archive/archive_index.json` 期望 `{docs: [...]}` 格式。

4. `cultivation_pipeline` 中先调 `archive_task` 再调 `archive_document`，同一份文档被写入两个不同格式的索引文件。

**根因分析**：新旧两套归档系统未做迁移，并存导致数据分裂。`archive_task` 直接覆盖写在崩溃时会损坏索引文件；`update_index` 的 load→modify→save 在多线程/多进程下丢失更新。

**修复建议**：
- 统一为一套索引：废弃 `archive_task`，全部走 `archive_index.py`
- 给 `update_index` 加文件锁（`fcntl.flock`）或使用线程锁
- `archive_task` 若保留，写入也必须原子（tmp + os.replace）
- 做一次数据迁移：将 `data/archive_index.json` 的数据合并到 `archive/archive_index.json`

### P0-5：沙箱回收后 in_flight_tokens 不重置，可导致引擎永久"假满"

**所在文件**：`engine_zhuan1.py` `main()` 约第1050行，`load_state()` 约第230行

**问题描述**：沙箱回收（SIGKILL）发生在 API 调用期间时，`in_flight_tokens` 已经预占但不会被释放。重启后 `load_state` 直接恢复该值，不重置，引擎误认为额度仍被占用。

**代码依据**：
```python
# main() 中检测到沙箱回收后：
if last_heartbeat > 0 and (now_ts - last_heartbeat) > 900:
    state["sandbox_recovery_events"].append(...)
    state["sandbox_recovery_count"] += 1
    # ↓ 没有重置 in_flight_tokens ↓
state["last_heartbeat"] = now_ts
save_state(state)
```

`load_state` 的 DEFAULT_STATE 合并逻辑只补全缺失字段，不会将已有非零值归零。

**根因分析**：`in_flight_tokens` 是运行时瞬态值，不应持久化。即使持久化，重启后所有在途请求已不存在，必须归零。当前代码漏掉了这一步。

**修复建议**：
- 在沙箱回收检测分支中，遍历三个引擎将 `in_flight_tokens` 重置为 0
- 更根本的：`save_state` 时不写入 `in_flight_tokens`（或写入前临时置零），因为它是进程内瞬态值
- 也可以在 `load_state` 中无条件重置所有引擎的 `in_flight_tokens = 0`

### P0-8：内存监控 90% 阈值 os._exit 可导致死锁和状态丢失

**所在文件**：`engine_zhuan1.py` `memory_monitor_loop()` 约第330行

**问题描述**：内存达90%时调用 `save_state(state)` 后 `os._exit(0)`。但 `save_state` 需要获取 `state_lock`，如果锁被其他线程持有（正在写状态），监控线程阻塞在锁等待上，`os._exit` 永远不执行，最终被 OOM killer 强杀，状态丢失。

**代码依据**：
```python
elif ratio >= 0.90:
    log(...)
    try:
        save_state(state)  # 需要获取 state_lock，可能死锁
        pid_file = STATE_FILE.parent / "engine.pid"
        if pid_file.exists():
            pid_file.unlink()
    except:
        pass
    _memory_monitor_running = False
    os._exit(0)
```

**根因分析**：`save_state` 是阻塞调用，在内存危急时其他线程可能正持有锁并进行大内存操作（如 JSON 序列化大状态），导致监控线程无法获得锁。`os._exit` 不执行 finally 块、不等待线程、不刷新缓冲区。

**修复建议**：
- 内存监控线程不调用 `save_state`（主线程会定期保存），只设置一个紧急标志
- 或使用 `state_lock.acquire(timeout=2)` 带超时获取锁，超时则放弃保存直接退出
- 90% 阈值改为：先停止接受新任务（设置标志），等待在途任务完成（带超时），再保存退出
- PID 文件清理应在主线程的 finally 块中做

### P1-2：ThreadPoolExecutor 并发数热更新存在任务丢失风险

**所在文件**：`engine_zhuan1.py` 主循环约第1140行

**问题描述**：动态调整并发时 `executor.shutdown(wait=False)` 立即关闭线程池，已提交但未完成的 future 不会被等待，主循环进入下一轮用新 executor 提交新任务。旧任务虽然仍在后台运行（Python 线程不会被强制终止），但它们的 future 被丢弃，结果不会被 `as_completed` 收集，后处理（归档、蒸馏、计数）全部丢失。

**代码依据**：
```python
if target_conc != executor._max_workers:
    executor.shutdown(wait=False)  # 不等待在途任务
    executor = ThreadPoolExecutor(max_workers=target_conc, ...)
```

**根因分析**：`shutdown(wait=False)` 只是阻止新任务提交，已提交的任务继续执行，但它们的 future 不在新的 future_map 中。主循环下一轮立即提交新任务，旧任务的完成回调无人监听。

**修复建议**：
- 不销毁重建线程池，改用 `threading.BoundedSemaphore` 控制实际并发度
- 或 `shutdown(wait=True)` 等待在途任务完成后再创建新池（会阻塞主循环）
- 或维护一个全局 future 集合，shutdown 前将旧 future 转移到新的监控集合中

### P1-3：废稿重试导致额度重复计算和 in_flight 双重占用

**所在文件**：`engine_zhuan1.py` `execute_single_api()` 约第960行

**问题描述**：第一次 API 调用被判定为废稿后，代码将其 token 加入 `tokens_used`，但不释放 `in_flight_tokens`，然后直接发第二次请求。第二次成功后又加一次 token，最后才释放一次 in_flight。这导致：
1. 废稿的 token 和重试的 token 都被计入（可能是预期的，但应确认）
2. in_flight 在两次请求期间只预占了一次，但实际发了两次请求，额度控制偏松
3. 如果重试也失败，in_flight 只释放一次，但实际发了两次请求

**代码依据**：
```python
if is_waste and attempt < MAX_RETRIES:
    with state_lock:
        state["waste_count"] += 1
        state["reasoning_tokens_total"] += result.get("reasoning_tokens", 0)
        state[engine_key]["tokens_used"] += result.get("total_tokens", 0)
        # ↓ in_flight 没有释放！
    save_state(state)
    # 直接发第二次请求，没有重新预占 in_flight
    result = call_api_chat(model, retry_prompt, cfg["max_tokens"], cfg["timeout"])
```

**根因分析**：废稿重试逻辑没有走完整的"释放预占→重新检查额度→重新预占"流程。

**修复建议**：废稿重试前先释放当前 in_flight，然后重新调用 `select_engine` 检查额度并预占，再发第二次请求。或者将废稿视为成功消耗（token 已计入），重试走全新的额度检查路径。

### P1-4：空闲模式状态残留——idle_phase 和 engine_mode 重启后不重置

**所在文件**：`engine_zhuan1.py` `main()` 和 `run_idle_task()`

**问题描述**：从 `engine_state.json` 可见，当前引擎正在正常跑任务（本转5/20，A主和C中均有消耗），但 `engine_mode` 仍为 `"idle"`，`idle_phase` 仍为 `"deep"`。这会导致：
- 主循环中 `if max_ratio >= 0.95 and not state.get("idle_phase")` 条件因 `idle_phase` 非空而不触发平滑降并发
- 唤醒包显示"空闲模式V3.2"误导诊断
- 下次进入空闲模式时 `run_idle_task` 开头判断 `state.get("engine_mode") != "idle"` 为 False，不会重置 idle_phase 为 "early"

**代码依据**：
```python
# run_idle_task 中阴转阳时：
state["idle_phase"] = None
state["engine_mode"] = "normal"
# 但这只在 run_idle_task 内部检测到额度刷新时执行
# 如果引擎在 idle 状态下被沙箱回收，重启后 state 保留 idle 状态
# 重启后 select_engine 返回可用，主循环直接走正常路径，不经过 run_idle_task
# idle_phase 和 engine_mode 永远不会被重置
```

**根因分析**：模式切换逻辑分散在 `run_idle_task` 和主循环中，没有在启动时根据当前额度状态校准模式。

### P1-6：asset_scanner.py 日志解析将所有文件名匹配计为"调用"，统计数据严重虚高

**所在文件**：`asset_scanner.py` `_parse_engine_log()` 约第100行

**问题描述**：正则 `r"(\w+\.py)"` 匹配日志行中所有 `.py` 文件名，包括 import 语句、错误堆栈、日志消息中提到的文件名，全部计为"调用次数"。

### P1-7：失败请求 token 重复计费——重试成功后失败估算值不扣减

**所在文件**：`engine_zhuan1.py` `execute_single_api()` 异常处理块约第1000行

**问题描述**：API 调用失败时，将估算 token 加入 `tokens_used`。如果后续重试成功，成功请求的实际 token 也被加入，但之前的失败估算值不扣减。额度被双重计算。

**代码依据**：
```python
# 失败时：
eng["tokens_used"] += fail_estimated  # 加估算值
# 重试成功后：
eng["tokens_used"] += total  # 再加实际值
# fail_estimated 永远保留，不扣减
```

**根因分析**：失败估算的本意是"失败也消耗了部分额度"（如超时但模型已生成部分内容），但重试场景下第一次失败通常是 429/超时/连接错误，服务端未必计费。统一加估算值导致额度统计偏大。

**修复建议**：
- 429/连接错误/超时类失败不加 token（服务端未处理或未生成）
- 只有服务端返回了 usage 的失败才计入
- 重试成功时，若之前加了估算值，应扣减估算值再加入实际值

## 一、P0 级问题深度根因追溯

### P0-1：`state_lock` 未形成状态所有权，多线程复合写必然损坏状态

#### 代码路径

- Worker 线程执行 `execute_single_api()`，直接修改：
  - `engine_x.tokens_used / requests / failures / in_flight_tokens`
  - `total_completed`
  - `tasks_failed`
- 主线程执行 `cultivation_pipeline() / l4_finished_pipeline() / complete_zhuan() / self_audit() / generate_narrative()`，直接修改：
  - `cognition_count`
  - `nine_dim_progress`
  - `quality_stats / dedup_stats / finished_stats`
  - `archive_indexed / duplicate_count / current_zhuan_tasks`
- 内存监控线程同时读取 `concurrency_override` 并调用 `save_state()`。

#### 根因

`state_lock` 只锁住了零散代码块，没有建立“谁可以写 state、在什么临界区写、写完如何持久化”的所有权模型。

Python GIL 只保证单条字节码原子性，下列操作均不是原子的：

```python
state["nine_dim_progress"][dim]["task_count"] += 1
state["nine_dim_progress"][dim]["count"] = task_count + bonus_count
state["quality_stats"][grade] = state["quality_stats"].get(grade, 0) + 1
```

它们实际是 `LOAD → ADD/MODIFY → STORE`，并发下会丢失更新。

更严重的是，`save_state()` 虽然自身加锁，但它序列化 state 时，其他线程可以在锁外修改 state，导致：

1. 计数丢失；
2. `count = task_count + bonus_count` 这类不变量被破坏；
3. JSON 快照包含半更新状态；
4. `save_state()` 持锁期间做 `json.dump / fsync / os.replace`，导致所有配额检查和状态写入阻塞在磁盘 IO 上。

#### 触发条件

- 并发数 ≥ 2；
- 多个 API 同时返回；
- 废稿重试、异常重试、转完成、每日重置、内存监控同时发生。

#### 影响范围

- Token 统计错误，直接影响配额控制；
- 九维进度、质量统计、认知数不可信；
- 持久化状态可能逻辑损坏；
- 审计和自进化基于错误数据决策。

#### 架构性修复方向

- 不要让 Worker 线程直接改业务 state。Worker 只返回 `TaskResult`，主线程串行应用状态变更。
- 如果必须保留 Worker 写 state，则所有 state 读写必须经 `StateManager` 方法，且禁止在持锁时做文件 IO。
- `save_state()` 应改为：
  1. 锁内复制 state；
  2. 锁外 JSON 序列化；
  3. 临时文件 + `fsync` + `os.replace`。

### P0-2：配额检查与预占非原子，重试路径进一步破坏配额

#### 根因链

`select_engine()` 在锁内检查额度，返回后立即释放锁：

```python
with state_lock:
    a_used = tokens_used + in_flight_tokens
    ...
return engine_key, model
```

`execute_single_api()` 在锁外做预判、资产复用匹配，然后才预占：

```python
engine_key, model = select_engine(state, task_type)
...
with state_lock:
    state[engine_key]["in_flight_tokens"] += in_flight_estimate
```

多个线程可同时通过检查。

#### 更深层的问题

1. **预占估值偏低**  
   预占值为 `max_tokens * 0.5`，但实际消耗约为：
   `prompt_tokens + completion_tokens`，而 `max_tokens` 只是输出上限。Deep 任务 `max_tokens=20000`，预占仅 10000，实际可明显超过预占。

2. **异常重试释放旧预占后，不对新引擎重新预占**  
   异常路径中：
   - 旧引擎 `in_flight_tokens` 被释放；
   - 调用 `select_engine(state)` 可能切换引擎；
   - 新引擎直接发请求，没有任何预占。
   
   成功后又对新引擎执行一次释放，可能把 `in_flight_tokens` 减到 0，但该引擎从未被预占。

3. **废稿重试不重新检查额度，也不重新预占**  
   第一次废稿的 token 已计入，但第二次请求直接发出，没有重新走配额申请。

4. **每日 10 点重置会清零在途预占**  
   如果 10 点时有请求正在执行，`in_flight_tokens` 被清零，新请求可继续进入，造成瞬时超额。

#### 触发条件

- 5 路并发；
- C 模型承担 `eng / cog / exp` 三类任务；
- 额度接近阈值；
- 请求超时、废稿重试、429/5xx 重试；
- 每日 10 点重置。

#### 影响

这是 C 模型超支的核心架构原因。超支量不只是“5 个线程 × 预估值”，而是：

> 非原子检查 + 重试绕过预占 + 估值偏低 + 每日重置窗口 + 废稿二次请求

叠加后的结果。

### P0-3：两套归档索引并存，且均存在并发写入问题

#### 根因

`archive_task()` 维护旧索引：

```text
data/archive_index.json
{task_id: {task_type, path, md5, ...}}
```

`archive_index.py` 维护新索引：

```text
archive/archive_index.json
{docs: [...], total_docs, tag_stats}
```

`cultivation_pipeline()` 同时调用两者：

```python
archive_task(...)
archive_document(...)
```

这不是简单的“新旧版本兼容”，而是**两个写入源、两种 schema、两套下游消费者**：

- `asset_integrity_check.py` 读取旧格式；
- `_idle_asset_inventory()` 读取新格式，却取 `.get("entries", [])`，实际字段是 `"docs"`；
- 旧索引用 `"w"` 直接覆盖写，崩溃时可能损坏；
- 新索引用 `os.replace` 原子落盘，但 `load → modify → save` 整体没有锁，多线程下会丢更新。

#### 影响

- 归档条目丢失；
- 归档计数不一致；
- 完整性校验误报；
- 同一份输出被两套系统重复索引；
- 数据迁移成本持续累积。

### P0-5：`in_flight_tokens` 是运行态值，却被持久化

#### 根因

`in_flight_tokens` 表示“当前进程内正在执行的请求所预占的额度”，它是瞬态值，不应跨进程存活。

沙箱回收或 SIGKILL 发生在 API 调用期间时：

1. Worker 已预占 `in_flight_tokens`；
2. 进程被杀，没有 finally 清理；
3. `load_state()` 只补全缺失字段，不重置已有非零值；
4. 重启后所有在途请求已不存在，但引擎仍认为额度被占用。

#### 影响

- 模型永久“假满”；
- 任务被错误路由到其他模型；
- 所有模型都假满时，引擎误进入空闲模式；
- 每日 10 点重置可能掩盖问题，但同日重启仍会触发。

#### 修复原则

- `load_state()` 后无条件重置：
  ```python
  for eng in ["engine_a", "engine_b", "engine_c"]:
      state[eng]["in_flight_tokens"] = 0
  ```
- 更根本：`save_state()` 不写 `in_flight_tokens`，或将其从持久化 state 中拆出到 `RuntimeState`。

### P0-6：空闲模式多项任务因接口漂移而静默失效

#### 具体表现

1. `_idle_cognition_density()`：
   ```python
   density = calc_density(text)
   if density.get("grade") == "C":
   ```
   `calc_density()` 返回 `(composite, details, grade)`，不是 dict，必然抛 `AttributeError`。

2. 认知文件实际结构为：
   ```json
   {"task_id": "...", "cognitions": [...]}
   ```
   但代码读取 `data.get("content", "")`，永远为空。

3. `_idle_prediction_audit()` 读取 `state["recent_tasks"]`，实际 state 中是 `recent_titles`，且是字符串列表。

4. `_idle_failure_distill()` 读取 `state["recent_failures"]`，但引擎没有任何地方写入该字段。

#### 根因

- 空闲任务没有与真实 state schema 对齐；
- 异常被宽泛 `except` 吞掉；
- 空闲任务“成功执行”只代表函数没让主循环崩溃，不代表实际完成工作。

#### 影响

阴期修炼中的认知密度整理、失败蒸馏、预判审计等任务大量空转，引擎却记录 `idle_success_count=69`，形成虚假健康。

### P0-7：B 模型 API 格式声明与实现不一致

#### 根因

代码注释声明 B 轻使用 Responses API：

```python
RESPONSES_URL = ".../responses"
MODEL_B = "doubao-seed-2-1-turbo"
```

但实际三个模型都调用：

```python
call_api_chat(...)
```

因为 B 模型欠费，该问题从未被真实流量覆盖。

#### 影响

- 若 B 模型只支持 Responses API，续费后作为降级路由时任务会批量失败；
- 若 B 实际支持 chat/completions，则注释和文档长期误导维护者；
- `archive / asset / image` 三类任务虽路由到 B，但引擎当前并不生成这些任务类型，使 B 实际处于“配置存在但不可用”状态。

### P0-8：内存监控 90% 退出路径可能阻塞

#### 根因

内存监控线程在 90% 时调用：

```python
save_state(state)
...
os._exit(0)
```

`save_state()` 需要获取 `state_lock`。如果此时另一个线程正持有锁并执行 JSON 序列化或文件落盘，监控线程会阻塞。90% 内存时再做整状态序列化还会额外分配内存，可能直接触发 OOM Killer。

`os._exit(0)` 不会执行其他线程的 finally，也不会保证缓冲区刷新。

#### 正确方向

- 内存监控线程只设置紧急标志，不直接保存；
- 主线程收到标志后停止接新任务；
- 带超时等待在途任务；
- 用 `state_lock.acquire(timeout=2)` 尝试保存，超时则放弃；
- PID 文件清理放到主线程 finally。

### P0-9（新发现）：九转闭环的核心度量已经断裂

这是阶段1未明确指出、但对“自进化”架构最致命的问题。

#### 1. `tasks_completed` 没有被递增

当前代码中，成功任务只递增：

```python
state["total_completed"] += 1
```

但这些函数仍使用 `tasks_completed`：

- `self_audit()`
- `nine_dim_audit()`
- `complete_zhuan()`
- `print_dashboard()`

从运行状态看：

```json
"total_completed": 1222,
"tasks_completed": 79
```

`tasks_completed` 已经是陈旧值。结果是：

- 审计中本转完成数可能被算成 0；
- 失败率计算错误；
- `zhuan_start_snapshot` 记录的是陈旧基线；
- 九维校验长期“假通过”。

#### 2. 增量分没有回传到反馈系统

`cultivation_pipeline()` 计算了：

```python
inc = calculate_increment_score(...)
```

但 `record_task_stat()` 收到的是：

```python
increment_score=result.get("increment_score", 50)
```

`execute_single_api()` 返回的 `result_data` 中没有 `increment_score`，所以反馈系统永远拿到默认值 50。

这意味着：

> 反哺调参中“增量分高则提权重、增量分低则降权重”的逻辑实际上不生效。

#### 3. 预判层重复风险字段不匹配

`record_task_stat()` 记录：

```python
{"type": task_type, ...}
```

但 `prediction_layer._calc_duplicate_risk()` 读取：

```python
r.get("task_type")
```

字段名不一致，重复风险永远为 0。

#### 影响

九转闭环、认知反哺、预判迭代这三个“自进化”核心能力都建立在失真或失效的度量上。引擎能跑，但已经失去了可靠的自我判断能力。

## 二、整体架构设计评估

### 1. 三模型调度

#### 合理之处

- 按任务类型路由：`deep/l4 → A`，`eng/cog/exp → C`，轻任务 → B；
- 有模型级熔断、错误分类、指数退避；
- 有每日 10 点重置窗口；
- 支持 `force_model` 人工调度。

#### 架构缺陷

- `select_engine()` 只做检查，不返回配额租约；
- `execute_single_api()` 既负责 API 调用，又负责状态修改、熔断、重试、废稿判断，职责过重；
- 重试路径绕过配额预占；
- B 模型长期欠费，代码没有被真实流量验证；
- 并发数调整通过销毁重建 `ThreadPoolExecutor` 实现，会丢弃旧 future 的结果监听；
- 新增 C 模型时，多个统计点仍只算 A+B，说明模型扩展没有统一抽象。

#### 评估结论

三模型路由的策略层设计是清晰的，但执行层没有把“检查、预占、释放、重试”建模为原子事务，因此不可靠。应引入 `QuotaLease`：

```text
acquire(task_type) -> lease
try:
    call_api(...)
finally:
    lease.release(actual_tokens)
```

重试必须释放旧租约并重新申请。

---

### 2. 九转闭环

#### 合理之处

- 以 20 个任务为一转，有明确批次概念；
- 每转有快照、九维校验、认知反哺、自动调参；
- L4 成品任务映射到“还虚”，体现“虚返实”；
- 每 3 转内核校准、每 5 转自进化检测，有长期演进节奏。

#### 架构缺陷

1. **转完成没有屏障**  
   `current_zhuan_tasks >= 20` 时立即调用 `complete_zhuan()`，但同一批提交的其他 future 可能仍在执行。没有“停止提交新任务 → 等待在途任务 → 审计 → 重置”的屏障。

2. **`task_count / bonus_count / count` 语义混乱**  
   真实任务应增加 `task_count`，系统事件应增加 `bonus_count`，但不少地方直接修改 `count`。通神维 `bonus_count=477`，导致计数膨胀。

3. **L4 任务破坏前四维一致性假设**  
   L4 映射到“还虚”，但审计曾假设前四维之和等于完成数。虽然当前数据维改用 `task_count`，但整体一致性检查仍需把所有维度纳入。

4. **审计评分过于宽松**  
   数据维偏差只扣分，不计严重失败；传承维 bonus 占比偏高只扣分，导致大量 95/101 分，掩盖真实问题。

5. **`tasks_completed` 断裂**  
   审计使用陈旧计数器，闭环数据不可信。

#### 评估结论

九转闭环的概念框架成立，但工程实现缺少批次屏障、统一计数语义和严格审计。当前“高转数、高平均分”不能完全代表引擎健康度。

---

### 3. 认知反哺

#### 合理之处

- `feedback_executor.py` 设置了安全边界：并发 1-5、权重 0.2-5.0、熔断冷却 60-600；
- 有 `evolution_log` 记录调参前后值；
- `cognition_density.py` 对认知质量做了 S/A/B/C 分级；
- `content_dedup.py` 提供重复率和增量分计算。

#### 架构缺陷

- 反哺逻辑分散在 `feedback_executor.py` 和 `complete_zhuan()` 中，两套规则同时存在；
- 增量分计算后没有传回反馈系统；
- `_auto_weights` 与 `state["task_weights"]` 双层乘权，最终权重不透明；
- 自动调参没有效果回测，不知道某次调整是否真的改善了失败率或增量分；
- 失败蒸馏依赖不存在的 `recent_failures`。

#### 评估结论

认知反哺具备“安全边界”和“日志可追溯”意识，但尚未形成可信的闭环：

```text
产出 → 质量评分 → 调参 → 效果验证 → 保留/回滚
```

当前主要停留在“产出 → 规则调参”。

---

### 4. 空闲模式

#### 合理之处

- 任务注册表设计较好：函数、内存等级、调度等级、描述分离；
- 有 `early / mid / deep` 三阶段；
- 深阴期 10 分钟心跳，适配沙箱 20-30 分钟回收规律；
- 空闲任务不消耗 API 额度，适合阴期打磨存量；
- 任务包含备份、盘点、蒸馏、完整性校验等真实运维动作。

#### 架构缺陷

- 启动时不校准 `engine_mode / idle_phase`，导致当前状态中：
  ```json
  "engine_mode": "idle",
  "idle_phase": "deep"
  ```
  但引擎实际在正常跑任务；
- 多个空闲任务依赖错误 state 字段；
- 异常被吞，失败仍计入成功；
- 空闲任务直接修改 state，没有统一走 StateManager；
- 深阴睡眠 10 分钟期间不更新心跳；若系统调度延迟超过 15 分钟，重启会误判沙箱回收；
- 状态上云只在空闲模式执行，阳期长时间运行时回收可能丢失最近状态。

#### 评估结论

空闲模式的设计思想是整个引擎中较成熟的部分：阳期耗 token 产增量，阴期零耗 token 磨存量。但实现质量参差不齐，应先修复 state schema 和异常可观测性，再增加新空闲任务。

---

### 5. 预判层

#### 合理之处

- 风险词分强/中/弱三级加权；
- 三维度独立评分：失败、超时、重复；
- 预判与结果回填分离；
- JSONL 全量记录，支持批量校验；
- `batch_verify.py` 能自动调整部分规则。

#### 架构缺陷

- `_rules` 全局缓存不支持热刷新，批量校验改了规则文件，运行中引擎不生效；
- 重复风险字段不匹配，永远为低风险；
- 超时阈值与 `TASK_CONFIG` 中真实 API 超时不一致；
- 预判结果目前只记录日志，不真正影响路由、超时或任务跳过；
- 批量校验只能调词表和阈值，无法修复 schema 错误；
- 预判状态独立于 engine_state，持久化和恢复不统一。

#### 评估结论

预判层的架构方向正确，但当前更像“离线评估器”，还不是“在线决策器”。高风险预判应至少触发：提高超时、降低权重、注入坑库、跳过或改写任务。

---

### 6. 新增 16 模块

#### 合理之处

- 模块以独立 CLI / 独立进程方式存在，没有直接侵入主循环；
- 已区分“已运行、接入空闲、独立工具、待验证”；
- 飞书双向、长链路、快照、健康检查等能力边界清晰。

#### 主要问题

- 多个模块硬编码 Supabase 密钥；
- `task_scheduler.py` 默认脚本路径不存在；
- `snapshot_incr.py` 的 `tar.extractall()` 无路径穿越防护；
- `watchdog_v3.py` 与 `watchdog.sh` 可能同时运行；
- `vector_memory.py` 使用哈希伪向量，无语义价值；
- `info_collector.py` 用正则提取 HTML 标题，脆弱；
- `auto_distill.py` 去重只比较标题前 20 字；
- `full_health_check.py` 也硬编码密钥。

#### 评估结论

“先独立验证、再以空闲模式或独立进程接入”的原则是对的。但这些模块不应共享硬编码密钥，也不应在未通过安全审查前接入主循环。

## 三、系统性风险

### 风险 1：state 是无主上帝对象

任何函数都可以直接读写 state 字典，没有封装、没有不可变更新、没有状态变更事件。锁只在部分路径生效，无法证明一致性。

### 风险 2：持久态与运行态混淆

`in_flight_tokens / idle_phase / engine_mode / last_heartbeat` 属于运行态，却和 `zhuan_count / cognition_count / tokens_used` 等持久态写在同一个 JSON 中。

### 风险 3：自进化建立在失真度量上

`tasks_completed` 不更新、增量分不回传、重复预判字段错误、审计评分过宽。引擎可能根据错误信号不断调参，却以为自己在进化。

### 风险 4：异常吞噬导致功能静默死亡

`try: ... except: pass` 大量存在。典型结果是空闲任务报异常但显示成功，预判/蒸馏/盘点功能空转。

### 风险 5：文件型状态缺少并发与崩溃保护

归档索引、同步日志、快照索引、资产数据库都是 JSON 文件，多数是 `load → modify → save`，没有文件锁或单写者约束。

### 风险 6：任务生命周期不完整

引擎扫描 `dispatch/inbox` 后，不移动、不删除、不写回执，也不记录已完成 task_id。若 inbox 中存在文件，会被反复扫描和重复执行。当前主要靠自生成任务掩盖了这个问题。

### 风险 7：安全边界缺失

密钥硬编码、tar 路径穿越、`shell=True` 调用脚本、`os.system` 拼接命令、从 Supabase 拉取状态后缺少校验。

### 风险 8：沙箱进程管理碎片化

主引擎、看门狗、飞书轮询器分别启动；`start_engine.sh` 有 check-then-act 竞态；两个看门狗可能冲突；沙箱回收后没有统一自举入口恢复所有常驻进程。

### 风险 9：隐喻驱动压过工程约束

九转、阴阳、通神等概念可以作为产品化表达，但不能替代严格的计数模型。当前部分维度为了“有奖励”而加 bonus，反而污染了审计指标。

## 四、可维护性、可扩展性、沙箱适配评估

### 可维护性

评分：**中等偏低**

优点：

- 模块文件已有初步拆分；
- 空闲任务注册表可扩展；
- 部分模块有 CLI，便于手动调用；
- 状态默认值合并机制降低了旧 state 缺字段导致的崩溃。

问题：

- `engine_zhuan1.py` 约 3500 行，职责过多；
- 没有单元测试；
- 同类逻辑多处复制，如 A+B token 统计；
- 大量裸 `except`；
- 配置、状态、常量混杂；
- 自修改逻辑缺少回滚验证。

### 可扩展性

评分：**中等**

优点：

- 新增空闲任务较容易；
- 任务类型由 `TASK_CONFIG` 驱动；
- 新模块以独立进程接入，故障隔离较好。

问题：

- 新增模型需要修改路由、统计、仪表盘、审计，没有统一 Engine 接口；
- 新增任务类型需要同步修改 `detect_task_type`、九维映射、权重逻辑；
- state 无 schema，新增字段容易出现读写不一致；
- 预判规则、资产规则、备份配置分散在多个 JSON 中。

### 沙箱适配性

评分：**中等偏上，但有关键缺口**

优点：

- 使用 `urllib` 并绕过代理；
- 有内存监控和降并发；
- 状态写入使用临时文件 + replace；
- 有心跳检测沙箱回收；
- 看门狗可在进程崩溃后重启；
- 空闲模式低功耗运行。

缺口：

- 沙箱回收后无法自启动，仍依赖施子对话；
- 运行态 state 未清理，重启后可能假满；
- 多进程没有统一守护；
- PID 文件和启动脚本有竞态；
- 硬编码绝对路径影响迁移；
- OOM 时 `save_state` 可能阻塞。

## 六、最终判断

凡心引擎的**顶层设计是有想法的**：三模型分流、九转闭环、阴阳空闲、预判校验、认知反哺，这些概念共同构成了一个可自进化系统的骨架。

但当前工程实现存在明显的“演化债务”：

- state 从配置对象膨胀为上帝对象；
- 锁从保护手段变成了局部心理安慰；
- 配额控制没有租约抽象；
- 自进化指标已经部分失效；
- 异常吞噬让多个子系统看起来在运行，实际空转。

最优先的不是继续加模块，而是：

> **先把状态所有权、配额原子性、核心计数器、运行态恢复四件事做对。**

只有这四个基础稳固后，九转闭环、认知反哺、空闲模式和预判层的“自进化”才是可信的。

## 阶段3：风控边界与未来适配

# 凡心引擎风控边界与未来适配方案

> 结论先行：当前引擎的顶层设计具备边界意识，但**风控没有形成闭环**。核心问题不是“没有阈值”，而是检查与执行非原子、持久态与运行态混淆、自进化指标失真、异常被吞。继续从 45 转向 100 转演进前，必须先修复状态所有权、配额租约、运行态恢复、转完成屏障四件事，否则高转数只会放大错误数据和恢复债务。

## 一、当前安全边界与熔断机制评估

### 1.1 已具备的有效边界

| 维度 | 当前机制 | 有效性 |
|---|---|---|
| 模型熔断 | 连续传输错误 5 次熔断，403 连续 2 次熔断，冷却 120-300 秒 | 方向正确，但无半开探测 |
| 额度阈值 | A/B/C 各 160 万 token，`select_engine` 检查 `tokens_used + in_flight_tokens` | 有基本防护，但检查与预占非原子 |
| 内存保护 | 70% 降并发，85% 降为 2 路，90% 保存退出 | 阈值合理，但 90% 退出路径可能死锁 |
| API 错误分类 | 403/429/5xx/timeout/connection/400 分类退避 | 有效，但失败计费和重试预占不正确 |
| 阴阳切换 | 85% 降并发，95% 停新任务，额度耗尽进空闲模式 | 策略合理，但状态残留导致模式失真 |
| 九转校验 | 每转九维评分、偏差告警、无效转判定 | 指标本身部分失效，审计可信度不足 |
| 反哺安全边界 | `feedback_executor` 限制并发 1-5、权重 0.2-5、冷却 60-600 | 有边界，但与 `complete_zhuan` 内调参逻辑重复且无回滚 |
| 内核校准 | 每 3 转对比根脉对话，偏差过大降速 | 概念有效，但评分逻辑偏粗 |
| 状态原子落盘 | `save_state` 使用 tmp + `fsync` + `os.replace` | 文件级原子有效，但多线程状态一致性不原子 |
| PID 单实例检查 | 启动时检查 PID 文件和进程名 | 有保护，但启动脚本仍存在 check-then-act 竞态 |

### 1.2 关键防护缺口

#### P0 级：必须立即修复

1. **`state_lock` 未覆盖全部 state 写操作**
   - `cultivation_pipeline`、`l4_finished_pipeline`、`complete_zhuan`、主循环异常处理中大量 `state[...] += 1` 在锁外执行。
   - Python GIL 不保证 `d["k"] += 1` 原子性，并发下会丢失更新。
   - `save_state` 持锁期间做 JSON 序列化和磁盘 fsync，会阻塞所有配额检查。

2. **配额检查与预占非原子**
   - `select_engine` 锁内检查，返回后释放锁；`execute_single_api` 稍后才预占 `in_flight_tokens`。
   - 5 路并发可同时通过检查，C 模型超支根因在此。
   - 预估值为 `max_tokens * 0.5`，低于真实 `prompt_tokens + completion_tokens`，安全垫不足。

3. **重试路径破坏配额**
   - 废稿重试不释放旧预占，也不重新申请新预占。
   - 异常重试切换引擎后，可能释放未预占的新引擎额度。
   - 失败估算 token 无条件计入，重试成功后不扣减，导致额度统计偏大或重复计费。

4. **每日 10 点重置存在超额窗口**
   - `check_daily_reset` 直接将三个引擎 `in_flight_tokens = 0`。
   - 如果当时有请求正在执行，旧在途请求完成后会释放已被清零的预占，造成计数错误。

5. **`in_flight_tokens` 被持久化**
   - 沙箱 SIGKILL 后，重启直接恢复非零在途值，导致引擎“假满”。
   - 今日已发生 4 次沙箱回收，该问题随时可触发。

6. **核心计数器断裂**
   - `total_completed = 1222`，但 `tasks_completed = 79`。
   - 审计、快照、失败率仍使用陈旧的 `tasks_completed`。
   - `calculate_increment_score` 结果未传入 `record_task_stat`，反哺系统永远拿到默认 50 分。
   - 预判层读取 `task_type`，实际记录字段为 `type`，重复风险永远偏低。

7. **B 模型 API 格式未验证**
   - 注释声明 B 走 Responses API，实际所有模型走 `call_api_chat`。
   - B 欠费掩盖问题；续费后若只支持 Responses API，archive/asset/image 类任务会批量失败。

8. **密钥泄露**
   - 火山 API Key、Supabase `service_role_key` 硬编码在多个文件中。
   - `service_role_key` 可绕过 RLS 读写全库。
   - 即使当前文件删除，Git 历史中的密钥仍视为已泄露，必须轮换。

9. **归档索引双写且均有并发问题**
   - `archive_task` 写 `data/archive_index.json`，直接覆盖。
   - `archive_index.py` 写 `archive/archive_index.json`，`load-modify-save` 无锁。
   - `asset_integrity_check` 读旧格式，`_idle_asset_inventory` 读新格式却取 `entries` 字段，实际字段是 `docs`。
   - 当前 state 中 `idle_integrity_issues = 1039`，说明索引分裂已造成大量误报。

10. **90% 内存退出路径可能死锁**
    - 内存监控线程调用 `save_state`，而 `save_state` 需要 `state_lock`。
    - 若另一线程持锁并执行大状态序列化，监控线程阻塞，`os._exit` 不执行，最终可能被 OOM Killer 强杀。

#### P1 级：100 转前必须修复

- 空闲模式状态残留：当前 `engine_mode = "idle"`、`idle_phase = "deep"`，但引擎实际在正常跑任务。
- `ThreadPoolExecutor.shutdown(wait=False)` 并发热更新会丢弃旧 future 的结果监听。
- 转完成无屏障：`current_zhuan_tasks >= 20` 立即 `complete_zhuan`，同一批其他 future 可能仍在执行，导致审计后仍有计数写入。
- `snapshot_incr.py` 的 `tar.extractall()` 无路径穿越过滤，恶意快照可覆盖任意文件。
- `task_scheduler.py` 使用 `shell=True` 且默认脚本路径不存在，既可能命令注入，又会与主循环/看门狗冲突。
- 两个看门狗 `watchdog.sh` 与 `watchdog_v3.py` 可能同时运行，导致重复拉起引擎。
- `start_engine.sh` 存在 check-then-act 竞态，无 `flock`。
- `asset_scanner.py` 用正则匹配日志中所有 `.py/.json/.sh`，统计调用次数严重虚高。
- 向量检索使用哈希伪向量，无语义价值，接入主链路会引入噪声。
- 空闲任务多个 schema 错误被 `except: pass` 吞掉，表面成功实则空转。

### 1.3 熔断机制是否足够

**不够。**

当前熔断只回答“连续失败几次后暂停”，但缺少：

- **配额熔断**：没有按“实际消耗 + 在途预占”做硬停止，也没有 80%/90%/95% 预警。
- **半开探测**：熔断冷却后直接放行，没有先用 1 个低风险请求探测恢复情况。
- **延迟熔断**：只看失败次数，不看 P95 延迟和超时占比。
- **并发熔断**：只有总并发数，没有每模型并发上限，C 模型可能吃满 5 路。
- **预算熔断**：A 主应保留给 deep/l4，C 走量任务耗尽 A 后会影响高质量任务。
- **自进化熔断**：自动调参没有效果回测，失败率恶化时不会自动回滚。
- **依赖熔断**：Supabase、飞书、Gitee 故障时没有统一降级策略，可能阻塞空闲任务。

## 二、实际困境适配方案

### 2.1 沙箱回收：每天多次断连

#### 物理边界

沙箱回收后所有内部进程全灭，**引擎无法自启动**，必须依赖 MainAgent/施子对话触发。能做的是：唤醒后 10 秒内恢复、状态不丢、多进程一键拉起、恢复后自动校准。

#### 落地方案

1. **持久态与运行态分离**
   - `in_flight_tokens`、`engine_mode`、`idle_phase`、`last_heartbeat`、`idle_deep_sleep_start` 视为运行态。
   - `save_state` 前不写入 `in_flight_tokens`，或写入时临时置零。
   - `load_state` 后无条件重置：
     ```python
     for eng in ["engine_a", "engine_b", "engine_c"]:
         state[eng]["in_flight_tokens"] = 0
     ```

2. **启动时强制校准模式**
   - 若有可用模型：`engine_mode = "normal"`，`idle_phase = None`。
   - 若所有模型不可用：保持 idle。
   - 主循环正常路径开头也做一次校准，避免当前“正常跑但状态显示 idle/deep”。

3. **心跳与深睡眠解耦**
   - 深阴休眠 `time.sleep(600)` 期间不更新心跳，若进程在休眠初期被回收，重启可能误判。
   - 改为独立心跳线程每 30-60 秒更新一次心跳和轻量状态，或把深睡眠拆成 5 分钟周期并在每个周期保存心跳。
   - 沙箱回收判定阈值保持 15 分钟，但心跳间隔必须小于阈值的 1/3。

4. **恢复后对账本转计数**
   - 当前 `current_zhuan_tasks` 可能与实际九维 `task_count` 不一致。
   - 启动时根据 `zhuan_start_snapshot` 和当前九维 `task_count` 重新计算本转任务数，而不是盲目信任持久化值。
   - 如果发现 API 已成功但后处理未完成，应能从 `outputs/` 或结果回执中补做归档/蒸馏/计数。

5. **结果先落盘，后处理可重试**
   - Worker 成功返回后，主线程先将结果原子写入 `dispatch/status/` 或 `outputs/`，再执行归档、蒸馏、九维计数。
   - 若在 pipeline 中途被回收，重启后扫描“已产出但未入账”的结果，重新执行后处理。
   - 以 `task_id` 为幂等键，避免重复计数。

6. **状态上云频率从“每日”改为“每转 + 关键事件”**
   - 当前 `state_cloud_sync` 只在空闲模式每日执行。
   - 应在以下时机推送 Supabase：
     - 每转完成；
     - 内存告警；
     - 沙箱恢复后；
     - 每 10 分钟低频心跳；
     - 密钥/配置变更。
   - 状态文件很小，流量成本可接受。

7. **统一启动入口**
   - 一个 `start_all.sh` 或 Python launcher 负责：
     - `flock` 单例锁；
     - 清理旧 PID；
     - 启动引擎；
     - 启动唯一看门狗；
     - 启动飞书轮询器。
   - 看门狗只保留一个，建议先用稳定的 `watchdog.sh`，等 v3 修复后再替换。

### 2.2 B 模型欠费

#### 建议决策

短期不要把 B 当作可靠降级路径。当前 B 承载的 `archive/asset/image` 任务类型引擎并不生成，B 实际零作用。

#### 方案 A：不续费（推荐短期）

- 在配置中增加 `engine_b.status = "suspended"`。
- `select_engine` 直接跳过 suspended 模型，而不是仅看额度。
- 路由表改为双模型：
  - deep/l4 → A
  - eng/cog/exp → C
  - C 不可用时不自动消耗 A，除非 A 当日额度低于 50%。
- 清理或隔离 Responses API 相关死代码，避免误导。

#### 方案 B：续费后启用

- 先做一次最小 canary 请求，确认 B 实际支持 `chat/completions` 还是仅支持 Responses API。
- 若仅支持 Responses API，实现 `call_api_responses()`，按 `engine_key` 分流。
- 先只路由 1% 低风险任务或手动 `force_model=B` 测试。
- B 恢复后仍不参与 deep/l4 降级，只处理轻量任务。
- 增加 B 独立熔断和健康检查，避免欠费恢复初期错误率污染主流程。

### 2.3 额度管理

#### 引入 `QuotaLease` 原子租约

将“检查额度 + 预占额度”合并为一个锁内原子操作：

```text
acquire(task_type) -> lease or None
try:
    call_api(...)
finally:
    lease.release(actual_tokens)
```

要点：

- 预估值改为 `prompt估算 + max_tokens`，不再用 `max_tokens * 0.5`。
- prompt 估算可按中文 1.5 字/token，再加上注入的认知/坑库提示。
- 每个模型独立 `BoundedSemaphore`，限制在途请求数，例如 A=2、C=3、B=2。
- 重试必须：
  1. 释放旧租约；
  2. 重新调用 `acquire`；
  3. 若引擎切换，在新引擎上预占。
- 废稿第一次 token 已实际消耗，可保留计费，但第二次请求必须重新申请租约。
- 429/超时/连接错误不计入失败 token；只有服务端返回 usage 时才计费。
- 重试成功后，若之前加过失败估算值，先扣减再加入实际值。

#### 每日重置屏障

10 点重置时：

1. 设置 `winding_down = True`；
2. 停止提交新任务；
3. 等待在途 future 完成，超时 5 分钟；
4. 重置 `tokens_used/requests/failures/fuse_until/in_flight_tokens`；
5. 生成育神日志；
6. 恢复提交。

#### 分级预警

- 80%：记录告警，飞书推送可选。
- 85%：降并发。
- 90%：只允许当前在途任务完成。
- 95%：停止该模型新任务，C 类任务不允许 fallback 到 A。
- 100%：硬拒绝。

#### 审计

- 每次 API 调用写 JSONL：
  `task_id, model, prompt_tokens, completion_tokens, total_tokens, reserve, retry_count, waste, duration, error_type`
- 每日对比“估算预占”和“实际消耗”，持续修正预估系数。

### 2.4 内存限制

当前 RSS 约 60MB，但 5 路并发、空闲扫描、归档索引加载会产生尖峰。2GB 沙箱需要更保守的退出策略。

#### 落地方案

1. **监控线程只设标志，不直接保存**
   - 90% 时设置 `memory_emergency = True`。
   - 主线程收到标志后停止接新任务，等待在途任务，带超时保存。
   - 监控线程可用 `state_lock.acquire(timeout=2)` 尝试保存，超时则放弃并 `os._exit`。

2. **阈值调整**
   - 70%：并发 -1。
   - 80%：停止提交新任务。
   - 85%：等待在途任务并保存。
   - 90%：强制退出。
   - 同时支持 cgroup v1/v2 内存上限读取，失败时使用绝对 RSS 上限，例如 1500MB。

3. **避免大内存操作**
   - API 返回内容超过 30KB 时先写临时文件，后处理从文件读取。
   - 空闲模式 `medium/high` 任务严格遵守内存预算。
   - 大文件扫描使用生成器，不一次性加载整个索引。
   - 每完成一批任务调用 `gc.collect()`。

4. **文件句柄**
   - `watchdog_v3.py`、`one_click_seed.py` 中 `stdout=open(...)` 会泄漏文件句柄，改用 `with` 或全局日志句柄。
   - `call_api_chat` 每次新建 opener，建议使用全局 `requests.Session(trust_env=False)` 复用连接。

### 吞吐预估

- 5 路并发，单任务平均 30-60 秒，理论吞吐约每小时 300-600 任务。
- 但每日施子活跃窗口有限，A+C 合计 320 万 token，按当前消耗速度足够支撑 100 转。
- 真正瓶颈不是算力，而是**状态一致性、数据质量和重复率**。

## 四、架构演进建议

### 4.1 短期：第 50 转内（止血期）

目标：不改变整体架构，先让数据可信、额度可控、恢复可预期。

1. **立即轮换泄露密钥**
   - 火山 API Key、Supabase `service_role_key`。
   - 所有凭证改为 `data/model_credentials.json` / 环境变量。
   - 将凭证文件、`backup_config.json`、PID 文件加入 `.gitignore`。

2. **修复状态一致性**
   - 所有 state 写操作收敛到 `with state_lock`。
   - 或更优：Worker 只返回 `TaskResult`，主线程串行更新 state。
   - `save_state` 改为锁内复制、锁外写盘。
   - 修复 `tasks_completed`、`increment_score`、预判层 `task_type/type` 字段。

3. **实现原子配额租约**
   - 检查+预占合并。
   - 重试重新预占。
   - 每日重置加屏障。
   - 失败 token 计费规则修正。

4. **沙箱恢复加固**
   - `load_state` 重置所有 `in_flight_tokens`。
   - 启动校准 `engine_mode/idle_phase`。
   - 心跳线程独立。
   - 每转完成后状态上云。

5. **转完成屏障**
   - 达到 20 任务后停止提交新任务。
   - 等待当前批次全部完成。
   - 再执行审计、反哺、快照、重置。

6. **熔断与内存**
   - 90% 内存退出不在监控线程直接保存。
   - 增加每模型并发信号量。
   - B 模型标记 suspended 或 canary 验证。

7. **归档索引统一**
   - 废弃 `archive_task` 旧索引，全部走 `archive_index.py`。
   - `asset_integrity_check` 改为读取新格式。
   - `update_index` 加线程锁/文件锁。

8. **空闲任务修复**
   - `_idle_cognition_density` 修复 tuple 返回值和 `cognitions` 字段。
   - `_idle_prediction_audit` 修复 `recent_titles/recent_tasks`。
   - `_idle_asset_inventory` 修复 `docs/entries`。
   - 禁止裸 `except: pass`，至少记录异常。

9. **单例与看门狗**
   - `start_engine.sh` 加 `flock`。
   - 只保留一个看门狗。
   - 看门狗重启引擎后重置运行态。

10. **新增模块接入控制**
    - 暂不批量接入 16 模块。
    - 仅在修复密钥后，将 `full_health_check` 作为空闲只读任务接入观察一转。

### 4.2 中期：第 100 转内（重构期）

目标：从“能跑”转为“可验证、可扩展、可恢复”。

1. **StateManager**
   - 拆分：
     - `DurableState`：转数、九维计数、认知数、token 累计、配置；
     - `RuntimeState`：在途额度、模式、心跳、并发；
     - `AnalyticsState`：最近任务统计、增量分、预判日志，可裁剪。
   - 所有 state 修改经方法调用。
   - 增加 schema 版本和迁移。

2. **QuotaScheduler**
   - `QuotaLease` 对象化。
   - 每模型独立并发、QPS、预算。
   - 熔断后半开探测。
   - A 主预算保护，C 走量任务不随意抢占 A。

3. **Worker 纯函数化**
   - Worker 只负责 API 调用，返回 `TaskResult`。
   - 不直接修改 state。
   - 主线程串行应用结果，彻底消除并发写。

4. **任务生命周期**
   - inbox 任务处理成功后移入 `receipts/`。
   - 失败移入 `failed_tasks/`。
   - 记录已完成 `task_id`，实现幂等。
   - goal_task 死信队列和重试次数持久化。

5. **统一反馈闭环**
   - 合并 `feedback_executor.py` 与 `complete_zhuan()` 中的调参逻辑。
   - 每次调参记录前 20 任务和后 20 任务的失败率、平均增量分、重复率。
   - 指标恶化则自动回滚。
   - 自动调参只在安全边界内生效。

6. **存储升级**
   - 归档索引、坑库、预判日志、任务统计从 JSON 文件迁到 SQLite。
   - 解决 `load-modify-save` 竞态。
   - 支持按标签、时间、质量查询。

7. **预判层在线化**
   - 规则文件热加载，按 mtime 刷新。
   - 高风险任务自动提高超时、降低权重或跳过。
   - 超时阈值与真实 `TASK_CONFIG` 对齐。

8. **拆分主引擎**
   - 建议拆为：
     - `api_client.py`
     - `state_manager.py`
     - `quota_router.py`
     - `cultivation.py`
     - `idle_mode.py`
     - `audit.py`
     - `main.py`
   - 拆分前先补核心单元测试，避免重构引入新债务。

9. **测试体系**
   - 配额租约测试。
   - 状态合并和迁移测试。
   - 转完成屏障测试。
   - 沙箱恢复对账测试。
   - 归档索引并发测试。

10. **模块接入**
    - `full_health_check`、`auto_distill` 可作为空闲任务，但只读或只写独立报告。
    - `long_chain_full` 仅在额度充裕时独立运行，必须加原子领取和配额限制。
    - `vector_memory` 升级真实 embedding 前不得接入主链路。
    - `task_scheduler` 不接入，避免与主循环冲突。

### 4.3 长期：第 100 转后（存续期）

目标：降低对单沙箱、单模型、单云服务的依赖，逼近分布式存续。

1. **平台抽象层**
   - 模型提供商：火山、OpenAI 兼容、本地模型统一接口。
   - 数据库/存储：Supabase 可替换为 PostgreSQL + S3/MinIO。
   - 通知：飞书可替换为钉钉、企业微信、Telegram。
   - 代码托管：Gitee 可替换为 GitHub/Gitea。

2. **最小存续内核**
   - 小而稳定的核心包含：
     - 身份与根脉锚点；
     - 凭证位置；
     - 远端状态地址；
     - 启动恢复流程。
   - 认知库、归档、日志作为可重建的外围数据。

3. **事件溯源**
   - 任务完成、认知蒸馏、调参、熔断、沙箱恢复均写 append-only 事件日志。
   - 状态从事件快照重建，避免 JSON 上帝对象继续膨胀。

4. **分布式任务队列**
   - 使用 Supabase 或轻量队列管理任务。
   - 多个引擎实例可认领任务，以 `task_id` 幂等。
   - 分识协同从概念变为真实 worker，但必须有独立配额和熔断。

5. **自进化沙箱化**
   - 任何代码/规则修改先 dry-run。
   - 低风险配置变更可自动应用，高风险变更需人工审批。
   - 每次修改有回滚点和效果评估。

6. **跨节点恢复**
   - `seed_bootstrap.py` 与 `one_click_seed.py` 统一为一个种子工具。
   - 支持从 Gitee 拉代码、从 Supabase 拉最新快照、启动引擎、恢复多进程。
   - 快照恢复必须校验路径穿越、完整性和版本兼容性。

### 1.3 总体评价

## 2. P0级致命问题清单

### P0-1：state_lock 未覆盖全部 state 写操作，多线程并发导致状态损坏

**优先级**：🔴 立即修复  
**所在文件**：`engine_zhuan1.py`

**问题描述**：主线程在 `as_completed` 循环中串行执行后处理，Worker 线程并发执行 `execute_single_api`，两者同时读写同一个 `state` 字典。大量读-改-写操作在锁外执行，Python GIL 不保证 `d["k"] += 1` 原子性（实际为 LOAD→ADD→STORE 三步），并发下丢失更新。

**代码依据**：

`cultivation_pipeline`（约第640行）中无锁写：
```python
state["cognition_count"] += cog_num
state.setdefault("archive_indexed", 0)
state["archive_indexed"] += 1
state["dedup_stats"]["total"] += 1
state["quality_stats"][grade] = state["quality_stats"].get(grade, 0) + 1
state["nine_dim_progress"][dim]["task_count"] += 1
state["nine_dim_progress"][dim]["count"] = task_count + bonus_count
```

`l4_finished_pipeline` 中无锁写：
```python
state["nine_dim_progress"]["还虚"]["task_count"] += 1
state["finished_stats"][grade] = state["finished_stats"].get(grade, 0) + 1
```

主循环异常处理中无锁写：
```python
state["tasks_failed"] += 1
state["current_zhuan_tasks"] += 1
```

`complete_zhuan` 中大量 state 修改无锁，包括 `zhuan_count += 1`、`feedback_history.append(...)` 等。

Worker 线程 `execute_single_api` 直接修改 `engine_x.tokens_used / requests / failures / in_flight_tokens`、`total_completed` 等字段。

更严重的是，`save_state()` 虽自身加锁，但序列化 state 时其他线程可在锁外修改 state，导致 JSON 快照包含半更新状态。且 `save_state` 持锁期间做 `json.dump + fsync + os.replace`，阻塞所有配额检查。

**根因**：没有建立"谁可以写 state、在什么临界区写、写完如何持久化"的所有权模型。锁从保护手段变成了局部心理安慰。

**修复方案**：

方案A（推荐，改动小）：将所有 state 写操作收敛到 `with state_lock:` 块，包括 `cultivation_pipeline`、`l4_finished_pipeline`、`complete_zhuan`、主循环异常处理、Worker 的 token 统计。

方案B（更彻底）：Worker 线程只返回 `TaskResult` 对象，不直接修改 state；主线程在 `as_completed` 循环中串行应用所有状态变更。当前架构已接近此模式，但 Worker 内部直接改 state 破坏了约定。

`save_state` 必须改为：
```python
def save_state(state):
    with state_lock:
        snapshot = copy.deepcopy(state)  # 锁内复制
    # 锁外序列化落盘
    tmp = STATE_FILE.with_suffix(".tmp")
    with open(tmp, "w") as f:
        json.dump(snapshot, f, ensure_ascii=False, indent=2)
    tmp.replace(STATE_FILE)
```

### P0-2：select_engine 额度检查与 in_flight 预占非原子，存在并发超支窗口

**优先级**：🔴 立即修复  
**所在文件**：`engine_zhuan1.py` `select_engine()` 约第860行、`execute_single_api()` 约第920行

**问题描述**：`select_engine` 在锁内检查额度后返回并释放锁，`execute_single_api` 在锁外做其他准备后才重新加锁预占 `in_flight_tokens`。此窗口内多线程可同时通过检查。这是C模型超支至201万的核心架构原因。

**代码依据**：
```python
# select_engine 内部：
with state_lock:
    a_used = state["engine_a"]["tokens_used"] + state["engine_a"].get("in_flight_tokens", 0)
    a_full = a_used >= SWITCH_THRESHOLD_A
    # ... 检查完返回，锁已释放

# execute_single_api 中：
engine_key, model = select_engine(state, task_type)  # 检查通过
# ↓↓↓ 时间窗口：其他线程也通过检查 ↓↓↓
in_flight_estimate = int(cfg["max_tokens"] * 0.5)
with state_lock:
    state[engine_key]["in_flight_tokens"] += in_flight_estimate  # 此时才预占
```

**叠加因素**：
- 预占估值偏低：`max_tokens * 0.5` 只是输出上限的一半，实际消耗 = prompt_tokens + completion_tokens，Deep 任务 max_tokens=20000 时预占仅10000，实际可超
- 废稿重试不释放旧预占也不重新申请（见P1-3）
- 异常重试切换引擎后，可能释放从未预占的新引擎额度
- 每日10点重置直接清零在途预占，若有请求正在执行则造成计数错误

5路并发时，若当前已用1,595,000，5个线程同时通过检查（都看到 < 1,600,000），各自预占10,000，实际冲到1,645,000，超支45,000。C模型走量任务多（eng/cog/exp共3类），叠加废稿重试放大超支。

**修复方案**：

将"检查额度+预占"合并为锁内原子操作，返回租约凭证：

```python
class QuotaLease:
    def __init__(self, state, engine_key, estimate):
        self.state = state
        self.engine_key = engine_key
        self.estimate = estimate
        self.released = False

    def release(self, actual_tokens=0):
        if self.released:
            return
        with state_lock:
            eng = self.state[self.engine_key]
            eng["in_flight_tokens"] = max(0, eng["in_flight_tokens"] - self.estimate)
            if actual_tokens > 0:
                eng["tokens_used"] += actual_tokens
        self.released = True

def acquire_quota(state, task_type):
    with state_lock:
        engine_key, model = select_engine_locked(state, task_type)
        if engine_key is None:
            return None
        cfg = TASK_CONFIG[task_type]
        estimate = estimate_tokens(cfg)  # prompt估算 + max_tokens，不再乘0.5
        state[engine_key]["in_flight_tokens"] += estimate
        return QuotaLease(state, engine_key, estimate)
```

重试必须：①释放旧租约 ②重新调用 `acquire_quota` ③若引擎切换则在新引擎预占。

每模型增加 `BoundedSemaphore` 限制在途请求数（建议 A=2、C=3、B=2）。

### P0-5：沙箱回收后 in_flight_tokens 不重置，可导致引擎永久"假满"

**优先级**：🔴 立即修复  
**所在文件**：`engine_zhuan1.py` `main()` 约第1050行、`load_state()` 约第230行

**问题描述**：沙箱回收（SIGKILL）发生在 API 调用期间时，`in_flight_tokens` 已预占但不会被释放。重启后 `load_state` 直接恢复该值，不重置，引擎误认为额度仍被占用。今日已发生4次沙箱回收，该问题随时可触发。

**代码依据**：
```python
# main() 中检测到沙箱回收后：
if last_heartbeat > 0 and (now_ts - last_heartbeat) > 900:
    state["sandbox_recovery_events"].append(...)
    state["sandbox_recovery_count"] += 1
    # ↓ 没有重置 in_flight_tokens ↓
state["last_heartbeat"] = now_ts
save_state(state)
```

`load_state` 的 DEFAULT_STATE 合并逻辑只补全缺失字段，不会将已有非零值归零。

**根因**：`in_flight_tokens` 是运行时瞬态值，表示"当前进程内正在执行的请求所预占的额度"，不应跨进程存活。

**修复方案**：

在 `load_state` 末尾无条件重置：
```python
def load_state():
    with open(STATE_FILE) as f:
        state = json.load(f)
    # 补全缺失字段...
    # 重置所有运行态瞬态值
    for eng in ["engine_a", "engine_b", "engine_c"]:
        state[eng]["in_flight_tokens"] = 0
    return state
```

更根本：`save_state` 时不写入 `in_flight_tokens`（写入前临时置零或从快照中剔除）。后续应将 state 拆分为 `DurableState`（转数、九维计数、token累计）和 `RuntimeState`（在途额度、模式、心跳），运行态不持久化。

### P0-8：内存监控 90% 阈值 os._exit 可导致死锁和状态丢失

**优先级**：🔴 立即修复  
**所在文件**：`engine_zhuan1.py` `memory_monitor_loop()` 约第330行

**问题描述**：内存达90%时调用 `save_state(state)` 后 `os._exit(0)`。但 `save_state` 需要获取 `state_lock`，若锁被其他线程持有（正在写状态或做JSON序列化），监控线程阻塞在锁等待上，`os._exit` 永远不执行，最终被 OOM killer 强杀，状态丢失。90%内存时做整状态序列化还会额外分配内存，可能直接触发 OOM。

**代码依据**：
```python
elif ratio >= 0.90:
    log(...)
    try:
        save_state(state)  # 需要 state_lock，可能死锁
        pid_file = STATE_FILE.parent / "engine.pid"
        if pid_file.exists():
            pid_file.unlink()
    except:
        pass
    _memory_monitor_running = False
    os._exit(0)
```

**修复方案**：
1. 内存监控线程只设置紧急标志，不直接保存：
```python
elif ratio >= 0.90:
    state["memory_emergency"] = True
    # 不调用 save_state，不直接 exit
```
2. 主线程在主循环中检查标志：停止接新任务 → 带超时等待在途任务 → 用 `state_lock.acquire(timeout=2)` 尝试保存 → 超时则放弃 → `os._exit(1)`。
3. 阈值调整为：70%降并发、80%停新任务、85%等待并保存、90%强制退出。
4. PID 文件清理放到主线程 `finally` 块。
5. 支持 cgroup v1/v2 内存上限读取，失败时用绝对 RSS 上限（如1500MB）。

### P0-9：九转闭环核心度量断裂，自进化基于失真数据

**所在文件**：`engine_zhuan1.py` 多处

**问题描述**：这是对"自进化"架构最致命的问题。三个核心度量同时断裂：

2. 将 `calculate_increment_score` 结果写入 `result["increment_score"]`，Worker 返回后主线程传入 `record_task_stat`。

4. 修复后手动校验：`state["total_completed"]` 与各维 `task_count` 之和一致、`increment_score` 非全50、预判重复风险有非零值。

### P2-2：大量裸 except 和 except Exception 吞掉异常

- 至少记录异常日志：`except Exception as e: log(f"...: {e}", "WARN")`
- 避免裸 `except:`（会捕获 KeyboardInterrupt/SystemExit），用 `except Exception:`
- 对预期可忽略的异常精确捕获具体类型（如 `FileNotFoundError`）

### P2-3：硬编码绝对路径，不可移植

`asset_inventory.py`、`body_slim_daily.py`、`sync_manager.py` 等硬编码 `/home/user/.super_doubao/...`。

**建议**：统一使用 `Path(__file__).resolve().parent.parent` 或从配置文件/环境变量读取 WORKSPACE。

### P2-4：body_slim_daily.py 配置与实现不一致

配置 `ARCHIVE_DAYS = 7`，实际判断用 `timedelta(days=30)`。

**建议**：统一为 `ARCHIVE_DAYS` 常量，或删除未使用常量。

### P2-5：balance_controller.py 密度衰减逻辑导致数据不一致

```python
if type_stats["total"] > 20:
    for k in ["S", "A", "B", "C"]:
        type_stats[k] = max(0, type_stats[k] - 1)
    type_stats["total"] -= 1
```
某等级为0时不减（`max(0,...)`），`total` 却减1，导致 `sum(S+A+B+C) != total`。这不是滑动窗口，而是均匀削峰。

**建议**：改用 `collections.deque(maxlen=20)` 保存最近20条等级记录，统计时实时计数。

### P2-6：prediction_layer.py 规则缓存不支持热刷新

`_rules` 全局变量在 `load_rules()` 中检测到非 None 就直接返回，`batch_verify.py` 修改规则文件后运行中引擎不生效。

**建议**：`load_rules` 检查文件 mtime，变化时重新加载；或提供 `reload_rules()` 函数。

### P2-7：auto_archive_chat.py 使用 os.system 拼接命令

```python
os.system(f"tar -czf '{target}' -C '{SESSION_DIR}' '{session_dir.name}' 2>/dev/null")
```

**建议**：改用 `subprocess.run(["tar", "-czf", str(target), "-C", str(SESSION_DIR), session_dir.name], ...)`。

### P2-8：向量检索使用哈希伪向量，无语义价值

`vector_memory.py` 的 `simple_hash_vector()` 用 MD5 哈希生成伪随机向量，余弦相似度接近随机（top1相似度仅0.169）。接入主推理链路会引入噪声。

**建议**：接入真实 embedding API 后再评估；升级前仅作为实验性功能保留，不接入主链路。

### P2-9：call_api_chat 每次创建新 opener，无连接复用

每次调用都 `urllib.request.build_opener()`，高频调用增加TCP握手开销。代码已 import requests 但未使用。

**建议**：使用全局 `requests.Session(trust_env=False)` 复用连接（`trust_env=False` 绕过沙箱代理）。

### P2-10：state 文件中时间戳格式混用

`last_heartbeat`、`idle_task_last_run` 用 Unix 时间戳（float），`last_run`、`created_at` 用 ISO 格式字符串。对比和排序容易出错。

**建议**：统一为 ISO 8601 字符串（可读可排序）或 Unix 时间戳（数值计算方便），不要混用。

### P2-11：使用 `if 'raw_prompt' in dir()` 做变量存在性检查

```python
task_content=raw_prompt[:300] if 'raw_prompt' in dir() else ""
```
重构改变量名不会报错，静默返回空字符串。

**建议**：循环开头初始化 `raw_prompt = ""`，直接用 `raw_prompt[:300]`。

`autonomy/` 目录 v73-v80 共8个旧版本文件约240KB残留。

**建议**：移动到 `archive/old_versions/` 或依赖 git 历史追溯后删除。

### 5.2 九大系统性风险

**风险1：state 是无主上帝对象**
任何函数都可直接读写 state 字典，没有封装、没有不可变更新、没有状态变更事件。锁只在部分路径生效，无法证明一致性。

**风险2：持久态与运行态混淆**
`in_flight_tokens / idle_phase / engine_mode / last_heartbeat` 属于运行态，却和 `zhuan_count / cognition_count / tokens_used` 等持久态写在同一个JSON中。

**风险3：自进化建立在失真度量上**
`tasks_completed` 不更新、增量分永远50、重复预判字段错误、审计评分过宽。引擎可能根据错误信号不断调参，却以为自己在进化。

**风险4：异常吞噬导致功能静默死亡**
`try: ... except: pass` 大量存在。空闲任务报异常但显示成功，预判/蒸馏/盘点功能空转。

**风险5：文件型状态缺少并发与崩溃保护**
归档索引、同步日志、快照索引、资产数据库都是JSON文件，多数是 load→modify→save，没有文件锁或单写者约束。

**风险6：任务生命周期不完整**
引擎扫描 `dispatch/inbox` 后不移动、不删除、不写回执，也不记录已完成 task_id。若 inbox 中存在文件会被反复扫描重复执行。当前主要靠自生成任务掩盖了此问题。

**风险7：安全边界缺失**
密钥硬编码、tar路径穿越、`shell=True`、`os.system` 拼接命令、从Supabase拉取状态后缺少校验。

**风险8：沙箱进程管理碎片化**
主引擎、看门狗、飞书轮询器分别启动；`start_engine.sh` 有竞态；两个看门狗可能冲突；沙箱回收后没有统一自举入口。

**风险9：隐喻驱动压过工程约束**
九转、阴阳、通神等概念可作为产品化表达，但不能替代严格的计数模型。通神维"有认知就+1 bonus"污染审计指标。

### 5.3 100转瓶颈评估

| 瓶颈 | 当前表现 | 100转时影响 |
|------|---------|------------|
| state上帝对象 | increment_scores已600+项 | 状态文件变大，每任务全量序列化，锁竞争和磁盘IO增加 |
| 锁内磁盘IO | save_state持锁json.dump+fsync | 并发提高后配额检查被阻塞 |

## 6. 风控边界与沙箱适配建议

### 6.1 当前熔断机制评估

**当前熔断不够。** 只回答"连续失败几次后暂停"，缺少：

| 缺失能力 | 说明 |
|---------|------|
| 配额硬熔断 | 没有按"实际消耗+在途预占"做硬停止，也没有80%/90%/95%分级预警 |
| 半开探测 | 熔断冷却后直接放行，没有先用1个低风险请求探测恢复 |
| 延迟熔断 | 只看失败次数，不看P95延迟和超时占比 |
| 并发熔断 | 只有总并发数，没有每模型并发上限，C模型可吃满5路 |
| 预算熔断 | A主应保留给deep/l4，C走量任务耗尽A后影响高质量任务 |
| 自进化熔断 | 自动调参无效果回测，失败率恶化时不会自动回滚 |
| 依赖熔断 | Supabase、飞书、Gitee故障时无统一降级策略，可能阻塞空闲任务 |

### 6.2 沙箱回收适配方案

沙箱每天多次断连，回收后所有内部进程全灭，引擎无法自启动，必须依赖 MainAgent/施子对话触发。能做的是：唤醒后10秒内恢复、状态不丢、多进程一键拉起、恢复后自动校准。

**(1) 持久态与运行态分离**
- `save_state` 前不写入 `in_flight_tokens`
- `load_state` 后无条件重置所有引擎的 `in_flight_tokens = 0`
- 后续拆分 DurableState/RuntimeState

**(2) 启动时强制校准模式**
- 若有可用模型：`engine_mode="normal"; idle_phase=None`
- 若所有模型不可用：保持idle
- 主循环正常路径开头也做校准

**(3) 心跳与深睡眠解耦**
- 当前深阴休眠 `time.sleep(600)` 期间不更新心跳
- 改为独立心跳线程每30-60秒更新一次
- 沙箱回收判定阈值保持15分钟，心跳间隔必须小于阈值1/3

**(4) 恢复后对账**
- 启动时根据 `zhuan_start_snapshot` 和当前九维 `task_count` 重新计算本转任务数
- 扫描 `outputs/` 中"已产出但未入账"的结果，以 task_id 为幂等键补做归档/蒸馏/计数

**(5) 结果先落盘，后处理可重试**
- Worker成功返回后，主线程先将结果原子写入 `dispatch/status/`，再执行后处理
- 若在pipeline中途被回收，重启后扫描未入账结果重新执行后处理

**(6) 状态上云频率提升**
- 从"空闲模式每日"改为"每转完成 + 内存告警 + 沙箱恢复后 + 每10分钟低频心跳"
- 状态文件很小，流量成本可接受

**(7) 统一启动入口**
- 一个 `start_all.sh` 或 Python launcher：flock单例 → 清理旧PID → 启动引擎 → 启动唯一看门狗 → 启动飞书轮询器

### 6.3 额度管理方案

**QuotaLease 原子租约**（详见P0-2修复方案），要点：
- 预估值改为 `prompt估算 + max_tokens`，不再用 `max_tokens * 0.5`
- prompt估算按中文1.5字/token，加上注入的认知/坑库提示
- 每模型独立 BoundedSemaphore（A=2、C=3、B=2）
- 重试必须释放旧租约、重新申请
- 429/超时/连接错误不计入失败token
- 每次API调用写JSONL：task_id, model, prompt_tokens, completion_tokens, total_tokens, reserve, retry_count, waste, duration, error_type

**每日重置屏障**：
1. 设置 `winding_down = True`
2. 停止提交新任务
3. 等待在途future完成（超时5分钟）
4. 重置 tokens_used/requests/failures/fuse_until/in_flight_tokens
5. 生成育神日志
6. 恢复提交

**分级预警**：80%告警 → 85%降并发 → 90%只允许在途完成 → 95%停止该模型新任务（C类任务不允许fallback到A）→ 100%硬拒绝。

### 6.4 B模型处置建议

短期不要把B当作可靠降级路径。当前B承载的 archive/asset/image 任务类型引擎并不生成，B实际零作用。

**方案A（推荐短期）**：配置中增加 `engine_b.status = "suspended"`，`select_engine` 直接跳过；路由表改为双模型（deep/l4→A，eng/cog/exp→C）；C不可用时不自动消耗A，除非A当日额度低于50%。

**方案B（续费后启用）**：先做1次canary请求确认API格式；若仅支持Responses API则实现 `call_api_responses()` 分流；先路由1%低风险任务测试；B恢复后仍不参与deep/l4降级。

### 6.5 内存保护方案

1. 监控线程只设标志，不直接保存退出
2. 阈值：70%降并发 → 80%停新任务 → 85%等待并保存 → 90%强制退出
3. API返回内容超过30KB先写临时文件，后处理从文件读取
4. 大文件扫描使用生成器，不一次性加载整个索引
5. 每完成一批任务调用 `gc.collect()`
6. 修复 `watchdog_v3.py`、`one_click_seed.py` 中 `stdout=open(...)` 文件句柄泄漏

### 6.6 新增模块接入规则

任何模块接入主循环前必须满足：
1. 不直接写 `engine_state.json`，只通过 StateManager 或写独立状态文件
2. 不直接调用模型API，除非经过统一配额调度且有独立预算
3. 常驻进程必须有 `flock` 单例锁
4. 密钥只能从环境变量或已忽略的配置文件读取
5. 文件写入必须原子落盘，tar/zip解压必须校验路径穿越
6. 数据库/队列操作必须有幂等键和原子状态流转
7. 内存占用遵守空闲任务预算，不扫描全量大文件
8. 一次只接入一个模块，观察至少一转（20任务），失败可一键回滚

## 8. 审核结论

凡心九转引擎的顶层设计具备明确的边界意识和自进化野心：三模型分流、九转闭环、阴阳空闲、认知反哺、预判校验共同构成了一个有想法的系统骨架。空闲模式"阳期耗token产增量、阴期零耗token磨存量"的设计思想尤其成熟。

但当前工程实现存在明显的演化债务，核心问题不是"几个bug"，而是四个架构级问题的集中表现：

1. **共享状态无主**——state_lock 只给了局部心理安慰，Worker和主线程并发复合写必然损坏状态
2. **配额控制非原子**——检查与预占之间的时间窗口叠加重试绕过，是C模型超支201万的根因
3. **持久态与运行态混淆**——in_flight_tokens被持久化导致沙箱重启后假满，engine_mode残留导致模式错乱
4. **自进化度量失真**——tasks_completed停在79、增量分永远50、重复风险永远0，引擎基于错误信号"自进化"

这四个问题叠加的效果是：引擎看起来在跑（total_completed=1222、九转45转、审核平均分96.2），但这些数字部分建立在失效指标上，不能代表真实健康度。空闲任务大量空转却记录成功、审计长期假通过、反哺调参基于默认值——这些是不可观测的风险。

**当前可以继续跑到50转，但不应在P0未修复前盲目追求100转。** 继续从45转向100转演进，高转数只会放大错误数据和恢复债务。状态文件持续膨胀、锁竞争加剧、归档索引越来越难以修复、沙箱每次回收都可能触发假满。

短期最重要的五项：
1. **密钥轮换**（P0-4，安全底线）
2. **原子配额**（P0-2，止住超支）
3. **运行态不持久化**（P0-5，沙箱恢复可信）
4. **转完成屏障**（中期P1，计数一致性）
5. **核心计数器修复**（P0-9，自进化数据可信）

这五项完成后，再考虑接入新模块和架构拆分。否则新增能力只会叠加不可观测的风险——一个连自己完成了多少任务、增量分是多少都算不对的引擎，谈不上可信的自进化。

长期来看，引擎应向"状态有主、配额有租约、持久态与运行态分离、度量可验证、恢复可预期"的方向演进。九转、阴阳、通神等隐喻可以保留作为产品化表达，但底层必须由严格的工程约束支撑。
