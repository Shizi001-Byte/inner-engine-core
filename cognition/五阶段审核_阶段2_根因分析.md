### P0-1 `mem_reason` 变量未定义

**直接原因**  
`load_state`段末行日志语句引用 `mem_reason`，但该变量在从函数入口到该行的所有可见代码路径中从未被赋值。Python在执行到该行时会抛出 `NameError: name 'mem_reason' is not defined`。

**根本原因**  
这是典型的**重构残留**——删除了赋值逻辑但保留了消费逻辑。从变量名 `mem_reason` 推断，原本存在一段内存压力评估逻辑，大致形如：

```python
mem_reason = "memory_pressure" if get_memory_usage() > MEMORY_CRITICAL else "normal"
```

在V7.x迭代中，内存检查逻辑可能被移除或迁移到不可见代码段（注意P3-1指出 `MEMORY_*` 系列常量定义了但未使用），但日志语句中的引用未被清理。

另一种可能：`mem_reason` 原本是从state中读取的（`mem_reason = state.get("mem_reason", "unknown")`），某次重构将内存管理逻辑外移，读取语句被删除。

**影响链**  
```
idle任务正常完成
  → 执行末行log语句
  → NameError抛出
  → 若idle循环有外层try/except：异常被捕获，日志丢失，但idle循环可能继续
  → 若无外层保护：idle循环崩溃
  → 主循环检测到idle线程死亡，可能重启
  → 重启后再次执行idle任务 → 再次崩溃
  → 无限崩溃-重启循环
```
最坏情况：idle机制完全瘫痪，引擎无法执行任何idle任务（archive/backup/distill等），系统维护能力归零。

**触发条件**  
**必现**。每次idle任务执行到最后一行log就会触发。不依赖任何外部条件，不依赖并发，不依赖时间——只要idle任务被执行，就必然崩溃。

**历史溯源**  
从 `MEMORY_*` 常量定义但未使用（P3-1）推断，内存管理模块在V7.0→V7.2迭代中经历了重构。原本的内存检查逻辑设置了 `mem_reason`，重构后逻辑被移除/外迁，但日志引用遗留。时间点很可能在V7.1引入内存压力降级机制时——当时添加了内存检查，后来发现逻辑有问题又删除了检查但保留了日志。

### P0-2 select_engine 0-10点返回None

**直接原因**  
```python
if current_hour < start_hour:
    return None, None, 0  # 注释说"不停跑"，代码却返回None
```
注释描述的是"消耗昨天剩余额度，计入今天统计，不停跑"的跨日额度管理策略，但代码实现的是直接返回None停止所有工作。

**根本原因**  
这是**注释与代码不同步**的典型案例，但深层原因是**跨日额度管理的设计复杂度超出了实现能力**。

注释描述的策略实际上非常复杂：
1. 0-10点使用"昨天周期剩余额度"——需要保存昨天的额度状态
2. "消耗计入今天统计"——今天的统计要加上0-10点的消耗
3. "不停跑"——不能返回None

实现这个策略需要：
- 在每日重置时保存昨天的剩余额度
- 0-10点时从昨天的剩余额度中扣减
- 统计时将0-10点的消耗归入今天

这个逻辑涉及跨日状态管理和额度归属，实现复杂度高。开发者可能先写了 `return None` 作为占位，计划后续实现，但一直未完成。后来修改了注释描述期望行为，但代码仍是占位状态。

**影响链**  
```
每天0:00
  → current_hour(0) < start_hour(10)
  → select_engine返回None
  → 所有任务提交被阻塞
  → 引擎空转8小时
  → 10:00后恢复
  → 每天8小时生产力损失（占全天1/3）
```
连锁影响：
- 日额度统计偏低（少了8小时的消耗）
- idle任务在0-10点也无法执行（如果idle也依赖select_engine）
- 如果有定时任务在凌晨执行（如backup），全部失败

**触发条件**  
**必现**。每天0:00-10:00之间，每次调用select_engine都返回None。

**历史溯源**  
从注释的复杂程度看，这是V7.0引入日额度管理时的设计。当时定义了"灰色时段"概念（0-10点），计划实现跨日额度结转。但实现时只完成了最简单的 `return None`，注释写的是设计意图。后续迭代中可能多次"计划修复"但始终未完成。

### P0-3 max_ratio 忽略B引擎

**直接原因**  
```python
max_ratio = max(a_used/max(1,a_thresh), c_used/max(1,c_thresh))
```
熔断判断只计算A和C引擎的使用率，B引擎完全缺席。

**根本原因**  
B引擎在系统中的角色定位模糊，导致集成不完整。从多个信号推断B引擎是后期添加的：

1. **路由矛盾**（P1-1）：注释说 `eng→C, exp→C`，但字典写 `eng→A, exp→B`——B的路由是后加的，注释没更新
2. **预算共用**（P1-6）：C引擎用 `DAILY_BUDGET_B` 常量——B的预算管理是仓促添加的
3. **API未适配**（P1-11）：B需要Responses API但无可见适配——B的调用逻辑不完整
4. **注释遗漏**（P3-2）：路由字典有8种类型（含image），注释只提7种——image→B是后加的

B引擎很可能是V7.1或V7.2引入的"轻量级引擎"，用于处理archive/asset/exp/image等辅助任务。添加B引擎时：
- ✅ 添加了路由配置
- ✅ 添加了预算常量（虽然命名有问题）
- ❌ 没有更新熔断公式
- ❌ 没有适配API格式
- ❌ 没有更新注释

这是**功能集成不完整**的典型模式——新引擎的"能路由到"完成了，但"能被监控"没完成。

**影响链**  
```
场景1：B引擎超额消耗
  → B引擎使用率超过100%
  → max_ratio不包含B → 不触发熔断
  → B引擎API调用全部失败（额度耗尽）
  → 路由到B的任务（archive/asset/exp/image）全部失败
  → 系统维护能力受损

场景2：B引擎满载但不降级
  → B引擎使用率95%
  → max_ratio只看A和C，可能都低于85%
  → 不触发降级
  → 继续向B提交任务
  → B引擎API调用失败率升高
```
最坏情况：B引擎额度耗尽，所有辅助任务失败，但系统不知道原因（因为熔断没触发，没有告警）。

**触发条件**  
**偶现**。当B引擎使用率超过A和C时触发。取决于任务分布——如果大部分任务路由到B（如大量archive任务），则B先满载但不熔断。

**历史溯源**  
B引擎在V7.1或V7.2引入。引入时只完成了路由和预算配置，熔断公式未更新。从P1-6（C用B的预算常量）看，B和C的集成是同时进行的，且比较仓促。

### P0-4 `concurrency_override` 默认值矛盾

**直接原因**  
同一函数内两处对 `state.get("concurrency_override", ...)` 使用不同默认值：
```python
# 位置1：85%检查
if state.get("concurrency_override", 5) > 2:  # 默认5
    ...
# 位置2：target_conc计算
target_conc = min(state.get("concurrency_override", CONCURRENCY), conc_cap)  # 默认3
```

**根本原因**  
两种可能：

**可能性A：CONCURRENCY常量被修改过**  
最初 `CONCURRENCY = 5`，两处默认值一致。后来调优将 `CONCURRENCY` 改为3，但位置1的硬编码5未同步更新。这是"修改常量但遗漏硬编码引用"的经典问题。

**可能性B：85%检查逻辑是后加的**  
位置2是原有代码，使用 `CONCURRENCY` 常量。位置1的85%检查是后来添加的，开发者随手写了5，没注意到下方已有使用 `CONCURRENCY` 的代码。

从P1-3（常量定义但未使用）看，这个代码库普遍存在"定义了常量但代码中用魔法数字"的问题，可能性B更高——85%检查是紧急添加的降级逻辑，没遵循常量规范。

**影响链**  
```
首次运行（state中无concurrency_override）：
  → 位置1：get默认5 → 5 > 2 → 触发降级逻辑
  → 位置2：get默认3 → target_conc = min(3, conc_cap)
  → 降级逻辑可能将concurrency_override设为2
  → 但位置2已经用3计算了target_conc
  → 行为不一致：降级逻辑认为当前并发是5，实际是3
  → 可能执行不必要的降级（从3降到2，而非从5降到2）

后续运行（state中有concurrency_override）：
  → 两处读到相同值
  → 问题消失
```
这意味着问题只在**首次运行**或**state被清零后**出现，但首次运行的错误降级可能导致并发永久偏低（因为P1-14：降级后无恢复路径）。

**触发条件**  
**首次运行必现**。后续运行偶现（仅当state中concurrency_override被清除时）。

**历史溯源**  
如果可能性B成立，85%降级检查是在V7.2添加的（V7.2引入了额度管理增强）。添加时是紧急修复，没遵循常量规范。

### P0-5 `in_flight_tokens` 只增不减 ★重点分析

**直接原因**  
```python
# select_engine中预占
state[target]["in_flight_tokens"] = state[target].get("in_flight_tokens", 0) + in_flight_estimate
```
整个可见代码中无任何位置执行 `state[target]["in_flight_tokens"] -= ...`。

**根本原因——为什么会忘记释放？**

这是整个代码库最严重的架构问题。深入分析遗忘的原因：

**原因1：职责分离不清**  
select_engine承担了两个职责：
1. 选择引擎（路由决策）
2. 预占额度（资源管理）

这两个职责应该分离。select_engine应该只返回决策结果，预占应该由任务提交逻辑执行，释放应该由任务完成回调执行。但代码将预占逻辑放在了select_engine中，导致"预占"和"释放"分散在不同函数中，容易遗漏。

**原因2：异步回调模型的理解不足**  
任务通过ThreadPoolExecutor提交，完成是异步的。释放逻辑应该在 `future.add_done_callback()` 中执行。但开发者可能：
- 不熟悉回调模式，忘了添加回调
- 或认为任务完成后"实际消耗"会自动覆盖"预估值"——混淆了预占和实际消耗的概念

**原因3：异常路径未考虑**  
即使正常路径有释放，异常路径（超时、取消、异常）也需要释放。如果开发者只考虑了正常路径，异常路径的遗漏会导致泄漏。

**原因4：in_flight_tokens的设计本身有问题**  
in_flight_tokens是"预估值"（`max_tokens * 0.5`），不是实际消耗。任务完成后：
- 预估值应该被减去
- 实际消耗应该被加上
- 但代码中可能没有"实际消耗"的统计逻辑

如果设计时假设"预估值≈实际消耗，不需要单独释放"，那就是设计层面的错误——预估值和实际消耗几乎不可能精确相等。

**释放逻辑应该在哪里？**

```python
# 方案1：在future回调中释放（推荐）
def submit_task(task, target, in_flight_estimate):
    future = executor.submit(task)
    def on_complete(f):
        try:
            result = f.result()
            # 实际消耗加到used中
            actual_tokens = count_tokens(result)
            with state_lock:
                state[target]["used"] += actual_tokens
        finally:
            # 无论成功失败，释放预占
            with state_lock:
                state[target]["in_flight_tokens"] = max(0, 
                    state[target].get("in_flight_tokens", 0) - in_flight_estimate)
    future.add_done_callback(on_complete)

# 方案2：用try/finally包裹任务执行
def run_task_with_release(task, target, in_flight_estimate):
    try:
        return task()
    finally:
        with state_lock:
            state[target]["in_flight_tokens"] = max(0,
                state[target].get("in_flight_tokens", 0) - in_flight_estimate)
```

**影响链**  
```
每次任务提交
  → in_flight_tokens += in_flight_estimate（约max_tokens*0.5）
  → 任务完成但in_flight_tokens不减少
  → used = 实际used + in_flight_tokens（持续增长）
  → used >= threshold → 引擎判定为full
  → 三个引擎陆续"满载"
  → select_engine无引擎可选 → 返回None
  → 引擎永久停摆
  → 必须手动重置state文件中的in_flight_tokens
```
增长速度估算：假设每次任务预占 `max_tokens * 0.5`，如果max_tokens=8000，每次预占4000。提交100个任务后，in_flight_tokens = 400,000。如果threshold=1,600,000，约400个任务后引擎停摆。

**触发条件**  
**必现**。只要任务持续提交，in_flight_tokens就单调递增。不依赖并发、不依赖时间、不依赖外部条件。

**历史溯源**  
in_flight_tokens是V7.x引入的额度预占机制。从P0-8（state[target]直接索引）和P1-6（C用B的预算常量）看，这套机制实现得非常仓促。很可能在V7.1→V7.2迭代中引入，设计文档中写了"预占+释放"两步，但只实现了预占部分。释放逻辑可能在TODO列表中，但被遗忘。

### P0-6 state修改在锁外执行 ★重点分析

**直接原因**  
以下state修改在 `with state_lock:` 块外执行：
```python
state["idle_phase"] = None                    # 锁外
state["idle_pit_before"] = state.get(...)     # 锁外
state["idle_cycles"] += 1                      # 锁外，复合操作！
state["total_growth_score"] += growth_score    # 锁外，复合操作！
state["idle_phase"] = "winding_down"          # 锁外
state["concurrency_override"] = 2              # 锁外
```

**根本原因——为什么会有这种不一致？**

这反映了代码的**渐进式加锁**演化过程：

1. **最初**：代码是单线程的，不需要锁。所有state修改都在锁外。
2. **引入多线程**：在"最关键"的地方（select_engine的引擎选择）加了锁。
3. **逐步扩展**：发现更多竞态条件，在更多地方加锁。
4. **遗漏**：一些"看起来不重要"的修改没有同步加锁。

另一个可能：锁的范围是按"代码块"而非"逻辑操作"划分的。开发者在某个 `with state_lock:` 块内修改了部分state，出了块后继续修改其他state，没有意识到这些修改也需要保护。

**哪些修改是安全的，哪些不安全？**

在CPython的GIL保护下：

| 修改类型 | 安全性 | 原因 |
|---------|--------|------|
| `state["x"] = value`（单次赋值） | ⚠️ 相对安全 | GIL保证单次赋值是原子的，不会损坏数据，但可能被其他线程覆盖（丢失更新） |
| `state["x"] += 1`（复合操作） | ❌ 不安全 | 读-改-写三步，可能在读和写之间被其他线程插入 |
| `state["x"]["y"] = value`（嵌套修改） | ❌ 不安全 | 两步操作（先获取state["x"]，再修改["y"]），可能与其他线程冲突 |
| `state.get("x")`（读取） | ⚠️ 相对安全 | 可能读到过期数据，但不会崩溃 |

具体到每个修改：

| 修改 | 安全性 | 分析 |
|------|--------|------|
| `state["idle_phase"] = None` | ⚠️ | 单次赋值，不会崩溃。但如果另一线程同时设置 `idle_phase = "winding_down"`，结果不可预测。哪个后执行哪个生效。 |
| `state["idle_pit_before"] = ...` | ⚠️ | 单次赋值，同上。 |
| `state["idle_cycles"] += 1` | ❌ | **复合操作！** 读-改-写三步。如果两个idle线程同时执行（不太可能但设计上不应假设），计数会丢失。更现实的风险：与save_state的序列化竞争——序列化时读到中间状态。 |
| `state["total_growth_score"] += growth_score` | ❌ | **复合操作！** 同上。growth_score累积值可能偏小。 |
| `state["idle_phase"] = "winding_down"` | ⚠️ | 单次赋值，但与锁内的 `idle_phase = None` 竞争。如果"winding_down"在锁外设置后，另一线程在锁内设置None，winding_down被清除——95%熔断形同虚设。 |
| `state["concurrency_override"] = 2` | ⚠️ | 单次赋值，但影响并发控制。如果另一线程同时在锁内调整concurrency_override，结果不可预测。更严重的是，这个修改与P0-9（可能反向提升并发）叠加。 |

**影响链**  
```
多线程并发时：
  → idle_cycles += 1 丢失更新 → 计数偏小
  → total_growth_score += growth_score 丢失更新 → 成长值偏小
  → idle_phase竞争 → 状态错乱（可能同时是None和winding_down）
  → concurrency_override竞争 → 并发数不可预测
  → save_state序列化时读到中间状态 → state文件数据不一致
```
最坏情况：state文件写入时数据不一致，反序列化后状态错乱，引擎行为不可预测。

**触发条件**  
**偶现**。需要多线程并发访问state时触发。单线程测试无法复现，只在生产环境高并发时出现。这使得问题极难调试——测试通过但生产环境偶发异常。

**历史溯源**  
锁是逐步引入的。最初可能只有select_engine中的锁（保护引擎选择这一最关键操作），load_state段的锁是后加的。加锁时只覆盖了"最明显需要保护"的修改，其他修改被遗漏。这反映了**缺乏统一的并发安全策略**——没有系统地审查所有state修改点。

### P0-7 `raw_goals` 获取的是引用而非副本

**直接原因**  
```python
raw_goals = state.get("goal_tasks", [])  # 返回list引用
# ... 锁外对raw_goals的修改直接改写state["goal_tasks"]
```

**根本原因**  
Python的 `dict.get()` 返回值的引用，不是副本。这是语言特性，但容易出错。开发者可能：
1. 不知道get()返回引用（Python新手常见误区）
2. 知道但认为"在锁内取出后，锁外修改是安全的"——错误：锁只保护取出时刻的一致性，不保护后续修改
3. 原本raw_goals只在锁内使用，后来代码演化导致部分修改移到锁外

**影响链**  
```
锁内取出raw_goals引用
  → 锁外修改raw_goals（append/remove/clear等）
  → 直接修改state["goal_tasks"]
  → 其他线程可能同时读取goal_tasks → 看到中间状态
  → 如果raw_goals被clear()后重新填充 → 其他线程可能看到空列表
  → save_state序列化时可能序列化到中间状态
```
最坏情况：goal_tasks被破坏，idle任务调度错乱——可能重复执行已完成的任务，或跳过未完成的任务。

**触发条件**  
**偶现**。多线程且goal_tasks被修改时触发。如果goal_tasks只在idle线程中修改（单线程），则不触发。但如果save_state在另一线程执行，序列化时可能读到中间状态。

**历史溯源**  
goal_tasks管理逻辑可能在某次迭代中从锁内移到锁外，或从未考虑过需要副本。从P0-6的普遍锁外修改看，这个代码库对并发安全的意识不强。

### P0-8 `state[target]` 直接索引可能KeyError

**直接原因**  
```python
state[target]["in_flight_tokens"] = state[target].get("in_flight_tokens", 0) + in_flight_estimate
```
`state[target]` 直接索引，如果target键不存在则抛KeyError。

**根本原因**  
开发者假设state初始化总是完整的——engine_a/engine_b/engine_c键总是存在。正常情况下确实如此（初始化函数会创建这些键），但异常情况下（state文件损坏）这个假设不成立。

这与P0-11（save_state无异常保护）直接相关：
1. save_state写入时磁盘满 → 异常 → 文件被截断
2. 下次load_state读取截断的文件 → JSON解析可能成功但数据不完整
3. state缺少engine_a/b/c → select_engine直接索引抛KeyError

**影响链**  
```
state文件损坏（截断/部分写入）
  → load_state读取不完整的state
  → state缺少engine_a/b/c
  → select_engine执行 state[target]["in_flight_tokens"] = ...
  → KeyError抛出
  → select_engine崩溃
  → 如果有外层重启逻辑 → 反复崩溃重启
  → 如果没有 → 引擎死亡
```

**触发条件**  
**条件触发**。state文件损坏时必现。正常情况下不触发。但state文件损坏的概率不低——磁盘满、进程被kill、文件系统错误都可能导致。

**历史溯源**  
这与"状态文件清零bug"直接相关。清零bug（save_state写入时异常导致文件截断）是根本原因，直接索引是放大器——如果使用 `state.setdefault(target, {})` 模式，即使state不完整也不会崩溃，只是功能受限。

### P0-9 `concurrency_override=2` 可能反向提升并发

**直接原因**  
```python
state["concurrency_override"] = 2  # 不检查当前值
```
85%降级时直接设为2，不检查当前是否已经低于2。

**根本原因**  
降级逻辑只考虑了"额度压力"单一维度，没有考虑"内存压力"可能已经将并发降到更低。

系统中存在两个独立的降级机制：
1. **内存压力降级**（不可见代码）：将concurrency_override设为1
2. **额度压力降级**（可见代码）：将concurrency_override设为2

这两个机制没有协调——额度降级不知道内存降级已经执行过，直接覆盖为2。

这反映了**多维降级机制缺乏统一协调器**的设计缺陷。正确的做法是：
```python
# 取当前值和目标值的最小值
current = state.get("concurrency_override", CONCURRENCY)
state["concurrency_override"] = min(current, 2)  # 只降不升
```

**影响链**  
```
内存压力 → concurrency_override = 1（内存降级）
  → 额度使用率 > 85%
  → concurrency_override = 2（额度降级，覆盖了1）
  → 并发从1提升到2
  → 内存压力加剧
  → 可能触发OOM
  → 进程被kill → 引擎死亡
```
最坏情况：在内存+额度双重压力下，额度降级反向提升了并发，触发OOM，引擎死亡。

**触发条件**  
**偶现**。需要内存降级先执行（设为1），然后额度降级执行（设为2）。时序依赖：
1. 内存压力出现 → 内存降级设为1
2. 内存压力未缓解，额度压力出现 → 额度降级设为2
3. 并发提升 → OOM

如果额度降级先于内存降级执行，则不触发（额度降级设为2，内存降级设为1，最终是1）。

**历史溯源**  
内存降级和额度降级是不同时期添加的。内存降级可能在V7.1引入（`MEMORY_*` 常量定义了但未使用），额度降级在V7.2引入。两者没有协调机制。

### P0-10 `idle_phase="winding_down"` 设置后无消费

**直接原因**  
```python
state["idle_phase"] = "winding_down"  # 设置了
# ... 但可见代码中无任何位置检查此值
```

**根本原因**  
这是**写了一半的代码**。设计意图是完整的：
1. 95%熔断时设置 `idle_phase = "winding_down"`
2. 任务提交逻辑检查 `if state.get("idle_phase") == "winding_down": 拒绝新任务`
3. 在途任务完成后，清除 `idle_phase`
4. 但第2步和第3步从未实现

95%熔断形同虚设——设置了状态但没有任何效果。

**触发条件**  
**必现**。额度使用率超过95%时，winding_down被设置但不生效。

**历史溯源**  
winding_down机制是V7.2新增的安全机制（V7.2引入了额度管理增强）。只完成了"设置"部分，"检查"部分在TODO中。从P1-14（降级无恢复）看，V7.2的状态管理普遍存在"只设置不恢复"的问题。

### P0-11 `save_state` 无异常保护

**直接原因**  
所有 `save_state(state)` 调用均无try/except包裹。

**根本原因**  
开发者假设磁盘I/O总是成功。这在开发环境成立，但生产环境有多种失败可能：
- 磁盘空间不足
- 文件权限问题
- 网络文件系统超时
- state文件被其他进程锁定
- 文件系统错误

save_state从"调试用途"演变为"关键路径"但异常处理没跟上。最初可能只是偶尔调用，后来成为每次任务执行后的必需操作，但异常处理没有同步升级。

**影响链**  
```
save_state调用
  → 磁盘满 → IOError抛出
  → 异常向上传播
  → 如果在idle循环中 → idle循环崩溃
  → 如果在select_engine中 → 引擎选择崩溃
  → 如果在任务提交后 → 任务结果丢失（state未保存）
  → 最坏情况：每次save_state都失败 → 引擎反复崩溃
```
连锁影响：save_state失败 → state文件可能被截断 → P0-8（KeyError）触发。

**触发条件**  
**条件触发**。磁盘满或权限问题时必现。正常情况下不触发。但磁盘空间是消耗性资源——长时间运行后磁盘可能被日志/state文件填满。

**历史溯源**  
save_state最初可能只是偶尔调用（如程序退出时），后来在V7.x迭代中调用频率增加（每次任务执行后都调用），但异常处理没跟上调用频率的增加。

### P1-4 `idle_start_time` 阴转阳后未重置

**直接原因**  
阴转阳恢复后，`idle_start_time` 未被清除。下次进入idle时 `idle_start = state.get("idle_start_time", time.time())` 读到旧值。

**根本原因**  
阴转阳逻辑只关注"恢复引擎模式"（设engine_mode="normal"），没关注"清理idle相关状态"。这反映了**状态转换不完整**——只转换了模式，没清理相关状态。

**影响链**  
```
第一次idle：idle_start_time = T1
  → 阴转阳：engine_mode = "normal"，但idle_start_time仍为T1
  → 第二次idle：idle_start = state.get("idle_start_time") = T1（旧值！）
  → idle_duration = now - T1（包含了第一次idle+中间工作时间+第二次idle）
  → idle_duration严重偏大
  → growth_score计算错误
```

**触发条件**  
**必现**。每次阴转阳后进入新idle周期时。

**历史溯源**  
阴转阳逻辑是后加的，idle_start_time管理是先有的，两者未协调。与P1-5、P1-13同源——阴转阳的状态清理不完整。

### P1-5 `idle_pit_before` 赋值时机错误

**直接原因**  
在阴转阳结束时设置 `idle_pit_before`，但此值应在idle阶段**开始时**设置。

**根本原因**  
对 `idle_pit_before` 的语义理解错误。正确语义是"本次idle开始时的pit_total"，用于计算idle期间的pit增量。但在阴转阳结束时设置，记录的是"上次idle结束时的pit_total"。

如果两次idle之间pit_total有变化（如其他线程修改了pit相关state），`pit_gain = pit_total_now - idle_pit_before` 计算错误。

**影响链**  
pit_gain计算错误 → 成长值统计不准确 → 坑沉淀成长值失真。

**触发条件**  
两次idle之间pit_total有变化时必现。

**历史溯源**  
idle_pit_before的语义在迭代中发生了变化（可能最初确实是"阴转阳结束时"的语义，后来改为"idle开始时"但赋值位置未调整）。与P1-4同源——阴转阳逻辑与idle状态管理未协调。
