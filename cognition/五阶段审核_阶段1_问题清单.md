# 九转引擎V7.2 阶段1：问题清单

---

## P0 致命问题（11项）

### P0-1 `mem_reason` 变量未定义
- **位置**：`load_state`段末行 `log(f"[IDLE] {task_name} 结束，30秒后下一项 ({mem_reason})")`
- **描述**：`mem_reason` 在可见代码中从未赋值，直接引用将抛出 `NameError`，导致idle任务循环崩溃
- **影响**：每次idle任务正常完成后引擎崩溃，无法进入下一轮idle

### P0-2 select_engine 0-10点返回None（已知BUG）
- **位置**：`select_engine` 第3-6行
- **描述**：`if current_hour < start_hour: return None, None, 0`。注释写"0-10点灰色时段：用昨天周期剩余额度，消耗计入今天统计，不停跑"，但代码直接返回None停止所有工作
- **影响**：每天0-10点引擎完全停摆，8小时空转

### P0-3 max_ratio 忽略B引擎（已知BUG）
- **位置**：额度检查段 `max_ratio = max(a_used/max(1,a_thresh), c_used/max(1,c_thresh))`
- **描述**：只计算A和C的使用率，B引擎使用率完全不参与熔断判断
- **影响**：B引擎可超额消耗至无限，或B引擎满载时不触发降级/停止

### P0-4 `concurrency_override` 默认值矛盾
- **位置**：
  - 额度检查段：`state.get("concurrency_override", 5) > 2`（默认5）
  - 同段下方：`state.get("concurrency_override", CONCURRENCY)`（默认3，即CONCURRENCY常量）
- **描述**：同一函数内对同一state键使用两个不同的默认值（5 vs 3）
- **影响**：首次运行时85%检查看到默认5>2触发降级，但下方target_conc计算用默认3，逻辑不一致导致并发行为不可预测

### P0-5 `in_flight_tokens` 只增不减
- **位置**：`select_engine` 中 `state[target]["in_flight_tokens"] = state[target].get("in_flight_tokens", 0) + in_flight_estimate`
- **描述**：预占 `in_flight_tokens` 在select_engine中原子化添加，但可见代码中无任何位置释放（任务完成/失败后应减去对应值）
- **影响**：`in_flight_tokens` 单调递增，最终所有引擎 `used >= threshold` 判定为full，引擎永久停摆

### P0-6 state修改在锁外执行（多处竞态）
- **位置**：`load_state`段多个位置
  - `state["idle_phase"] = None`（锁外）
  - `state["idle_pit_before"] = state.get("idle_pit_total", 0)`（锁外）
  - `state["idle_cycles"] += 1`（锁外）
  - `state["total_growth_score"] += growth_score`（锁外）
  - 额度检查段 `state["idle_phase"] = "winding_down"`（锁外）
  - 额度检查段 `state["concurrency_override"] = 2`（锁外）
- **描述**：这些state修改未在 `state_lock` 保护下执行，而同函数内其他state修改在锁内执行
- **影响**：多线程并发时数据竞争，state值不可预测，可能导致计数丢失、phase状态错乱

### P0-7 `raw_goals` 获取的是引用而非副本
- **位置**：额度检查段 `raw_goals = state.get("goal_tasks", [])`
- **描述**：`dict.get()` 返回list的引用，在 `with state_lock` 内取出后，锁外对 `raw_goals` 的任何修改直接改写state中的原始list
- **影响**：锁外修改goal_tasks导致竞态条件，且不易察觉

### P0-8 `state[target]` 直接索引可能KeyError
- **位置**：`select_engine` 中 `state[target]["in_flight_tokens"] = ...`
- **描述**：`target` 是 `"engine_a"/"engine_b"/"engine_c"` 之一，直接用 `state[target]` 索引。若state初始化不完整或被部分清零（参见已知BUG#1），将抛出 `KeyError`
- **影响**：状态文件被清零后，select_engine直接崩溃

### P0-9 `concurrency_override=2` 可能反向提升并发
- **位置**：额度检查段 `state["concurrency_override"] = 2`
- **描述**：85%降级时直接设为2，但不检查当前值。若内存压力已将并发降到1，此处会反向提升到2
- **影响**：在内存紧张+额度紧张双重压力下，反而提升并发，可能触发OOM

### P0-10 `idle_phase="winding_down"` 设置后无任何代码消费
- **位置**：额度检查段 `state["idle_phase"] = "winding_down"`
- **描述**：设置了 "winding_down" 状态，但可见代码中无任何位置检查此值来实际停止接新任务或排空在途
- **影响**：95%熔断形同虚设，新任务继续提交

### P0-11 `save_state` 无异常保护
- **位置**：多处 `save_state(state)` 调用（load_state段至少3次，额度检查段也有）
- **描述**：`save_state` 调用无 try/except 包裹。若磁盘满或权限问题，异常向上传播导致引擎崩溃
- **影响**：磁盘空间不足时引擎直接死亡，无法优雅降级

## P1 重要问题（16项）

### P1-1 路由注释与实际路由字典矛盾
- **位置**：注释 `# 三级分流：deep/l4→A，eng/cog/exp→C，archive/asset→B` vs `TASK_MODEL_ROUTING` 字典
- **描述**：注释说 `eng→C`，字典写 `"eng": "A"`；注释说 `exp→C`，字典写 `"exp": "B"`
- **影响**：开发者被注释误导，排错方向错误

### P1-2 API_KEY 硬编码在源码中
- **位置**：常量段 `API_KEY = "ark-6c0c1704-78c4-42a0-be0d-0011fab46ca6-2688e"`
- **描述**：API密钥明文写死在代码中
- **影响**：代码泄露即密钥泄露，安全风险极高

### P1-3 已定义常量未使用，代码中用魔法数字
- **位置**：
  - 定义了 `QUOTA_STOP_RATIO = 0.95` / `QUOTA_DEGRADE_RATIO = 0.85`，但额度检查段硬编码 `0.95` 和 `0.85`
  - 定义了 `MEMORY_*` / `DEDUP_*` / `HEALTH_*` / `LOG_ROTATE_*` 等常量，可见代码中均未引用
- **描述**：常量定义了但不用，实际逻辑用硬编码数字
- **影响**：修改常量不生效，维护者产生虚假安全感

### P1-4 `idle_start_time` 阴转阳后未重置
- **位置**：`load_state`段 `idle_start = state.get("idle_start_time", time.time())`
- **描述**：阴转阳恢复后，`idle_start_time` 未被清除/重置。下次进入idle时仍用旧时间戳，`idle_duration` 计算错误
- **影响**：成长值计算基于错误的idle时长，统计数据失真

### P1-5 `idle_pit_before` 赋值时机错误
- **位置**：`load_state`段 `state["idle_pit_before"] = state.get("idle_pit_total", 0)`
- **描述**：在阴转阳结束时设置 `idle_pit_before`，但此值应在idle阶段**开始时**设置。若两次idle之间 `idle_pit_total` 有变化，下次 `pit_gain` 计算错误
- **影响**：坑沉淀成长值统计不准确

### P1-6 `DAILY_BUDGET_B` 用于C引擎
- **位置**：`select_engine` 循环 `[("engine_b", "B", DAILY_BUDGET_B), ("engine_c", "C", DAILY_BUDGET_B)]`
- **描述**：C引擎使用名为 `DAILY_BUDGET_B` 的常量作为阈值，命名严重误导
- **影响**：开发者误以为C有独立阈值配置，实际共用B的常量

### P1-7 `SWITCH_THRESHOLD_A` 命名误导
- **位置**：常量段 `SWITCH_THRESHOLD_A = 1_600_000`
- **描述**：名称暗示"切换阈值"，但代码中用作A引擎的日额度上限。与 `DAILY_BUDGET_B` 命名风格不一致
- **影响**：理解歧义，可能误修改

### P1-8 `executor._max_workers` 访问私有属性
- **位置**：额度检查段 `if target_conc != executor._max_workers:`
- **描述**：直接访问ThreadPoolExecutor的私有属性 `_max_workers`
- **影响**：Python版本升级或executor实现变更可能导致属性名变化，代码脆弱

### P1-9 `daily_start_hour` 未做范围校验
- **位置**：`select_engine` 中 `start_hour = state.get("daily_start_hour", 10)`
- **描述**：若state中 `daily_start_hour` 被设为非法值（如-1、25、None），`current_hour < start_hour` 行为不可预测
- **影响**：配置错误可能导致引擎永久返回None或永不触发

### P1-10 `task_func(state)` 无超时保护
- **位置**：`load_state`段 `result_msg = task_func(state)`
- **描述**：idle任务函数调用无超时机制。若task_func内部卡死（如网络请求无超时），idle循环永久阻塞
- **影响**：一个卡死的idle任务冻结整个idle机制

### P1-11 MODEL_B 使用Responses API但无可见适配
- **位置**：常量段注释 `# B轻：Seed2.1 Turbo（Responses API格式）`，定义了 `RESPONSES_URL` 但可见代码中无使用
- **描述**：B模型需要用Responses API格式，但可见代码中无根据engine_key选择URL/请求格式的逻辑
- **影响**：B引擎API调用可能全部失败（用错URL/格式）

### P1-12 `datetime.now()` 时区依赖
- **位置**：`select_engine` 中 `current_hour = datetime.now().hour`
- **描述**：使用本地时间，依赖服务器时区配置。API URL为 `cn-beijing`，若服务器非北京时区，10点重置时间偏移
- **影响**：非北京时区服务器上，额度重置时间与预期不符

### P1-13 `idle_success_count`/`idle_run_count`/`idle_task_stats` 永不重置
- **位置**：`load_state`段，阴转阳后这些统计值未清零
- **描述**：阴转阳代表一个idle周期结束，但统计数据跨周期累积，无法区分单周期表现
- **影响**：无法评估单次idle周期的效率，统计值无限膨胀

### P1-14 `concurrency_override` 降级后无恢复路径
- **位置**：额度检查段设为2，但可见代码中无恢复逻辑
- **描述**：85%降级到2后，额度重置（降到85%以下）时无代码恢复原并发数
- **影响**：每次降级后并发永久降低，直到手动重启

### P1-15 `save_state` 在锁内调用导致I/O阻塞
- **位置**：`load_state`段 `with state_lock:` 块内无save_state，但select_engine的 `with state_lock:` 块内修改state后，若调用方在锁内save_state，I/O会阻塞其他线程
- **描述**：state_lock保护内存操作，但若save_state（磁盘I/O）在锁内执行，会序列化所有线程
- **影响**：高并发时磁盘I/O成为瓶颈

### P1-16 `force_model` 大小写敏感
- **位置**：`select_engine` 中 `if force in ("A", "B", "C")`
- **描述**：若state中 `force_model` 设为 `"a"`（小写），不匹配，静默忽略
- **影响**：用户配置小写不报错也不生效，难以排查

## P2 优化问题（14项）

### P2-1 `growth_score` 权重为魔法数字
- **位置**：`pit_gain * 10 + c_archived * 2 + distilled * 5 + backup_ok * 15`
- **描述**：权重10/2/5/15硬编码，无常量定义，无注释说明依据
- **影响**：调整权重需改代码，无法配置

### P2-2 `in_flight_estimate` 0.5系数魔法数字
- **位置**：`select_engine` 中 `in_flight_estimate = int(cfg["max_tokens"] * 0.5)`
- **描述**：0.5系数无注释说明，假设任务平均使用50%的max_tokens
- **影响**：预估值不准确可能导致过度保守或过度乐观

### P2-3 错误信息截断80字符
- **位置**：`load_state`段 `result_msg = f"{type(e).__name__}: {str(e)[:80]}"`
- **描述**：异常信息截断为80字符，可能丢失关键调试信息
- **影响**：复杂异常链的根因信息丢失

### P2-4 `save_state` 冗余调用
- **位置**：`load_state`段，函数开头1次、task执行后1次、阴转阳后1次，共3次
- **描述**：同一函数内多次save_state，若中间无重要状态变更则为冗余I/O
- **影响**：不必要的磁盘写入，影响性能

### P2-5 select_engine 无决策日志
- **位置**：`select_engine` 全函数
- **描述**：引擎选择、force跳过、降级fallback等关键决策无任何日志输出
- **影响**：无法追踪引擎路由决策，排错困难

### P2-6 `conc_cap=5` 与 `CONCURRENCY=3` 矛盾
- **位置**：额度检查段 `conc_cap = 3 if is_blind_zone() else 5` vs 常量 `CONCURRENCY = 3`
- **描述**：CONCURRENCY=3但实际允许到5，常量名暗示是最大并发但实际不是
- **影响**：开发者误以为最大并发是3

### P2-7 `daily_threshold` 默认值1600000魔法数字
- **位置**：额度检查段 `state.get("engine_a", {}).get("daily_threshold", 1600000)`
- **描述**：get默认值1600000是魔法数字，应使用已定义的 `SWITCH_THRESHOLD_A` 常量
- **影响**：阈值修改时需改多处

### P2-8 `idle_c_level_archived` 等变量无类型校验
- **位置**：`load_state`段 `c_archived = state.get("idle_c_level_archived", 0)`
- **描述**：从state读取的值未校验类型，若被污染为字符串/None，后续算术运算报错
- **影响**：state文件损坏时阴转阳计算崩溃

### P2-9 `idle_backup_ok` 命名歧义
- **位置**：`backup_ok = state.get("idle_backup_ok", 0)`
- **描述**：名称暗示布尔值(0/1)，但用于 `backup_ok * 15` 算术运算。若实际是计数则命名应改为 `idle_backup_count`
- **影响**：语义不清

### P2-10 `time.sleep(30)` 阻塞主循环
- **位置**：额度检查段 `time.sleep(30)`
- **描述**：idle任务后sleep 30秒，期间主循环无法响应其他事件（如在途任务完成回调）
- **影响**：响应延迟，系统吞吐降低

### P2-11 `state["engine_mode"] = "normal"` 无对应idle设置
- **位置**：`load_state`段阴转阳后设为 `"normal"`
- **描述**：可见代码中无将engine_mode设为 `"idle"` 的位置，模式转换链不完整
- **影响**：mode状态机不完整，可能存在未可见的bug

### P2-12 `TASK_MODEL_ROUTING` 默认值"C"未文档化
- **位置**：`select_engine` 中 `preferred = TASK_MODEL_ROUTING.get(task_type, "C")`
- **描述**：未知task_type默认路由到C，无注释说明此设计决策
- **影响**：新增task_type时可能意外路由到不合适的引擎

### P2-13 `predict_task`/`find_reusable_assets` 在锁外调用
- **位置**：`execute_single_api` 中 `prediction = predict_task(...)` 和 `find_reusable_assets(...)`
- **描述**：这些函数若读取state，在锁外执行可能看到不一致数据
- **影响**：预判和资产查找可能基于过期状态

### P2-14 `idle_task_stats` 嵌套字典修改模式
- **位置**：`task_stats = state["idle_task_stats"].setdefault(task_name, {"runs": 0, "total_time": 0, "success": 0})`
- **描述**：setdefault返回的引用在锁内修改是安全的，但若state序列化时嵌套字典结构变更，反序列化可能失败
- **影响**：state文件格式升级时兼容性风险

## P3 建议问题（10项）

### P3-1 大量常量定义但可见代码未引用
- **位置**：常量段 `FUSE_THRESHOLD`/`FUSE_COOLDOWN`/`MAX_RETRIES`/`MAX_TASK_POOL_SIZE`/`MIN_AVAILABLE_TEMPLATES`/`MAX_USES_PER_TEMPLATE`/`LOG_ROTATE_*`/`DEDUP_*`/`HEALTH_*`/`MEMORY_*`
- **描述**：这些常量在可见代码段中均未使用，可能是未可见代码使用，也可能是死代码
- **影响**：代码膨胀，维护负担

### P3-2 `TASK_MODEL_ROUTING` 含 `"image": "B"` 但注释未提及
- **位置**：路由字典 vs 注释
- **描述**：注释只提7种任务类型，字典有8种（多了image）
- **影响**：文档不完整

### P3-3 `engine_key` 变量来源不可见
- **位置**：额度检查段 `if not engine_key:`
- **描述**：`engine_key` 的赋值在不可见代码中，可能是 `select_engine` 返回值的第一个元素
- **影响**：无法确认是否正确处理了select_engine的三元组返回值

### P3-4 `future_map = {}` 初始化后代码截断
- **位置**：额度检查段末尾
- **描述**：future_map初始化后代码被截断，无法评估后续任务提交逻辑
- **影响**：无法完整审查任务提交和结果收集逻辑

### P3-5 `is_blind_zone()` 函数实现不可见
- **位置**：额度检查段 `conc_cap = 3 if is_blind_zone() else 5`
- **描述**：函数定义不在可见代码中，推测检查0-10点，但实现未知
- **影响**：无法确认与select_engine的0-10点逻辑是否一致

### P3-6 `log` 函数签名不一致
- **位置**：多处 `log(msg)` 和 `log(msg, "ERROR")`
- **描述**：log函数支持可选level参数，但部分错误日志未传level
- **影响**：日志级别可能不正确

### P3-7 `state_lock` 类型未知
- **位置**：多处 `with state_lock:`
- **描述**：state_lock可能是threading.Lock或threading.RLock，若为Lock则嵌套加锁会死锁
- **影响**：若存在嵌套加锁场景，可能死锁

### P3-8 `TASK_CONFIG` 结构未知
- **位置**：`select_engine` 中 `cfg = TASK_CONFIG.get(task_type, TASK_CONFIG["exp"])`
- **描述**：TASK_CONFIG的结构和内容不在可见代码中，但被用于计算in_flight_estimate
- **影响**：无法验证max_tokens配置是否合理

### P3-9 `HEALTH_*` 权重总和验证
- **位置**：常量段 `HEALTH_QUOTA_WEIGHT=35 + HEALTH_SUCCESS_WEIGHT=25 + HEALTH_COGNITION_WEIGHT=25 + HEALTH_BALANCE_WEIGHT=15 = 100`
- **描述**：权重总和恰好100，设计合理但无注释说明
- **影响**：修改时可能破坏总和=100的约束

### P3-10 代码段标题"load_state"与实际内容不符
- **位置**：代码段标题
- **描述**：标题为"load_state"但实际内容是idle任务执行函数（run_idle_task或类似），真正的load_state函数（含已知BUG#1）未展示
- **影响**：审查者可能遗漏load_state的真正bug
