## P0-1 `mem_reason` 变量未定义

### 1. 修复风险

**修复方案**：在log语句前添加 `mem_reason = state.get("mem_reason", "unknown")`

| 风险点 | 评估 |
|--------|------|
| 掩盖缺失的内存检查逻辑 | **中风险**。默认值"unknown"会让日志看起来正常，但实际内存压力评估仍然缺失。运维人员可能误以为内存检查在正常工作 |
| state中无此键时的行为 | 低风险。`dict.get()` 的默认值机制已处理 |
| 恢复完整内存检查逻辑的风险 | 高风险。如果重新引入 `get_memory_usage()` 调用，该函数可能未定义或行为异常（P3-1指出MEMORY_*常量未使用，说明内存模块可能整体缺失） |

**替代方案对比**：
- **方案A**（推荐）：添加 `mem_reason = state.get("mem_reason", "legacy_ref")` — 用"legacy_ref"明确标注这是遗留引用，不是正常值
- **方案B**：删除日志中的 `({mem_reason})` 引用 — 最安全但丢失诊断信息
- **方案C**：恢复完整内存检查 — 最正确但依赖未验证的内存模块

### 2. 边界条件

```
条件1：state文件被清零 → state.get("mem_reason", ...) 返回默认值 → 日志正常 → ✅
条件2：state文件正常但无mem_reason键 → 同上 → ✅
条件3：内存检查逻辑恢复但get_memory_usage()抛异常 → NameError变成其他异常 → ⚠️ 需try/except
条件4：多线程同时读写state["mem_reason"] → 竞态条件 → ⚠️ 但只影响日志输出，不影响功能
条件5：idle任务在mem_reason赋值前被信号中断 → 仍会NameError → ⚠️ 概率极低
```

### 3. 回滚方案

```python
# 回滚操作：删除添加的赋值行
# 原始代码：
log(f"[IDLE] {task_name} 结束，30秒后下一项 ({mem_reason})")
# 回滚后：
log(f"[IDLE] {task_name} 结束，30秒后下一项")
# 或完全回滚到原始状态（含NameError）
```

回滚成本：极低。单行修改，无数据迁移，无状态依赖。

### 4. 验证方法

理由：

- 修复极简单（单行代码）

## P0-2 select_engine 0-10点返回None

### 1. 修复风险

**修复方案选项**：

| 方案 | 描述 | 风险 |

| A：删除early return | 0-10点正常工作，使用今天额度 | 低风险但可能过早消耗今日额度 |

**方案A的风险**：
- 0-10点消耗今天额度 → 白天可用额度减少33%

```
├── 引擎在0-10点重启时的状态恢复
└── 跨日时区问题（服务器时区 vs UTC）
```

```
条件7：10:00:00时刻的竞态 → 正在执行的任务用昨天还是今天额度？
```

## P0-3 max_ratio 忽略B引擎

### 1. 修复风险

**核心问题：max() → all() 的改造方向**

```
当前逻辑：max_ratio = max(a_ratio, c_ratio)
含义：任一引擎超阈值 → 触发熔断  ← 正确的熔断语义

如果改成：all(ratio > threshold for ratio in [a, b, c])
含义：所有引擎都超阈值 → 才触发熔断  ← 错误！更危险！

正确修复：max_ratio = max(a_ratio, b_ratio, c_ratio)
含义：任一引擎（含B）超阈值 → 触发熔断  ← 正确
```

| 风险点 | 评估 |
|--------|------|
| B引擎threshold配置不当 | **高风险**。B引擎使用DAILY_BUDGET_B（P1-6），如果threshold值设置不合理（过大或过小），加入max()后可能导致误熔断或不熔断 |
| B引擎used值未正确统计 | **高风险**。如果B引擎的API调用统计不完整（P1-11 API未适配），used值可能始终为0，加入max()无意义 |
| B引擎临时下线 | 中风险。如果B引擎被禁用但state中仍有残留used值，可能误触发熔断 |

### 2. 边界条件

```
条件1：B引擎threshold=0 → max(1, 0)=1 → b_ratio=used/1 → 可能极大 → 误熔断
条件2：B引擎used未初始化 → used=0 → b_ratio=0 → 不影响max → 安全
条件3：B引擎state不存在 → KeyError → 需要先修复P0-8
条件4：B引擎threshold远大于A/C → B永远不会触发熔断 → 形同虚设
条件5：B引擎threshold远小于A/C → B总是先触发熔断 → 过度保守
条件6：B引擎刚添加，历史used=0但threshold=100 → ratio=0 → 安全
条件7：三引擎额度单位不同（token vs request）→ ratio比较无意义 → 设计缺陷
```

### 3. 回滚方案

```python
# 回滚操作：从max()中移除B引擎
# 回滚后代码：
max_ratio = max(
    a_used / max(1, a_thresh),
    c_used / max(1, c_thresh)
)
# 回滚成本：极低。移除一个参数。
# 回滚影响：B引擎超额不被检测，但至少不会误熔断A/C
```

### 4. 验证方法

```python

    state = {
        "engine_a": {"used": 10, "threshold": 100},  # 10%

        "engine_c": {"used": 20, "threshold": 100},
    }
    # 不应除零，不应误熔断
    max_ratio = calculate_max_ratio(state)
```

### 5. 优先级排序

**修复优先级：7/11**

理由：
- B引擎超额风险存在但非必现
- 修复简单（加一个参数）但依赖B引擎统计正确
- 需要先确认B引擎的used/threshold统计是否可靠
- 建议与P0-8（state[target]兜底）一起修复

## P0-4 `concurrency_override` 默认值矛盾

### 1. 修复风险

**修复方案**：统一使用 `CONCURRENCY` 常量作为默认值

| 风险点 | 评估 |
|--------|------|
| 首次运行时 `CONCURRENCY(3) > 2` 为True | **中风险**。首次运行就触发降级，从3降到2。虽然不是错误（保守策略），但可能不是预期行为 |
| CONCURRENCY常量值变更 | 低风险。如果CONCURRENCY从3改为5，两处都跟着变，保持一致 |
| 85%检查逻辑本身 | 需要验证：首次运行时a_used/c_used都是0，ratio=0，不会到85%。所以 `3 > 2` 的判断只在ratio≥85%时才执行，首次运行不会触发 |

**深入分析**：
```python
# 实际执行路径：
# 1. max_ratio = max(0/100, 0/100) = 0  （首次运行）
# 2. if max_ratio >= 0.85:  ← False，跳过
# 3. state.get("concurrency_override", 5) > 2  ← 不会执行到这
# 所以首次运行不会触发降级，风险实际为低
```

### 2. 边界条件

```
条件1：CONCURRENCY=1 → 默认1 > 2 = False → 85%时不降级 → 可能有问题
条件2：CONCURRENCY=0 → 默认0 > 2 = False → 85%时不降级 → 有问题
条件3：state中concurrency_override=5（手动设置）→ 5 > 2 = True → 降级到2 → 正确
条件4：state中concurrency_override=1（内存压力设置）→ 1 > 2 = False → 不降级 → 正确（已经是低并发）
```

### 3. 回滚方案

```python
# 回滚：恢复原始矛盾默认值
# 第一处改回：state.get("concurrency_override", 5)
# 第二处保持：state.get("concurrency_override", CONCURRENCY)
# 回滚成本：极低
```

### 4. 验证方法

```python

    val1 = state.get("concurrency_override", CONCURRENCY)

    }

```

### 5. 优先级排序

**修复优先级：9/11**

理由：
- 影响范围有限（只在85%降级路径触发）
- 修复极简单
- 实际触发概率低（需要同时满足首次运行+85%额度）
- 但修复成本极低，可以顺手修

## P0-5 `in_flight_tokens` 只增不减

### 1. 修复风险

**这是最复杂的修复，风险最高。**

**修复方案**：在任务完成/失败/超时时释放in_flight_tokens

```
释放点设计：
┌─────────────────────────────────────────────────┐
│  select_engine: 预占 in_flight_tokens += estimate │
│                     │                             │
│                     ▼                             │
│              ┌──────────────┐                     │
│              │ 任务执行中    │                     │
│              └──────┬───────┘                     │
│                     │                             │
│         ┌───────────┼───────────┐                 │
│         ▼           ▼           ▼                 │
│      成功        失败        超时                 │
│      释放        释放        释放                  │
│         │           │           │                 │
│         │     ┌─────┘     ┌─────┘                │
│         ▼     ▼           ▼                      │
│      正常释放  可能重复释放！                      │
└─────────────────────────────────────────────────┘
```

| 风险点 | 评估 |
|--------|------|
| **重复释放** | **致命风险**。超时后任务可能仍在运行，完成后又触发成功回调，导致双重释放 |
| **遗漏释放** | **高风险**。任务被SIGKILL、进程崩溃、网络断开等场景下回调不执行 |
| **释放量不匹配** | **中风险**。预占的是estimate，实际消耗可能不同。释放estimate会导致tokens不准 |
| **释放时竞态** | **中风险**。释放操作 `-= estimate` 是read-modify-write，需要锁保护 |
| **引擎重启后陈旧值** | **高风险**。state文件中的in_flight_tokens记录了重启前的预占，但任务已不存在 |
| **负值问题** | **中风险**。重复释放或释放量大于当前值会导致负值，影响后续判断 |

**重复释放的详细场景**：
```python
# 场景：任务超时后实际完成
T=0:   select_engine → in_flight_tokens += 100  (total=100)
T=30s: 任务超时 → in_flight_tokens -= 100      (total=0)   ← 第一次释放
T=31s: API返回结果 → 成功回调 → in_flight_tokens -= 100  (total=-100) ← 重复释放！
T=32s: 另一个select_engine → in_flight_tokens=0-100=-100 → 判断错误
```

### 2. 边界条件

```
条件1：任务成功完成 → 正常释放 → ✅
条件2：任务失败（API返回错误）→ 释放 → ✅
条件3：任务超时但仍在运行 → 释放 → ⚠️ 可能重复释放
条件4：任务被取消 → 释放 → ✅
条件5：进程被SIGKILL → 无回调 → ❌ tokens永久泄漏
条件6：进程崩溃后重启 → state中in_flight_tokens陈旧 → ❌ 需要重置
条件7：任务重试 → 新预占+旧未释放 → ❌ tokens膨胀
条件8：in_flight_estimate=0 → 释放0 → 无影响但无意义
条件9：多任务并发释放 → 竞态条件 → ⚠️ 需要锁保护
条件10：释放后in_flight_tokens < 0 → 后续判断错误 → ❌ 需要max(0, ...)
```

### 3. 回滚方案

```python
# 回滚方案：移除所有释放逻辑
# 回滚后：in_flight_tokens继续单调递增
# 缓解措施：定期手动重置 state[engine]["in_flight_tokens"] = 0

# 回滚脚本：
def emergency_reset_in_flight(state_file):
    """紧急重置in_flight_tokens"""
    state = load_state(state_file)
    for engine in ["engine_a", "engine_b", "engine_c"]:
        if engine in state:
            old = state[engine].get("in_flight_tokens", 0)
            state[engine]["in_flight_tokens"] = 0
            log(f"[EMERGENCY] {engine} in_flight_tokens: {old} → 0")
    save_state(state)

# 回滚成本：中等。需要移除多处释放逻辑，但不会引入新问题
```

```python
        threads.append(t)
    for t in threads: t.start()
    for t in threads: t.join()
    assert state["engine_a"]["in_flight_tokens"] == 0  # 不是负数

# 长期运行测试
def test_long_running_stability():
    """长时间运行后in_flight_tokens稳定"""
    for i in range(1000):
        engine, _, est = select_engine(state)
        # 模拟任务完成
        release_in_flight(state, engine, token_id=f"t{i}", amount=est)
    # 验证in_flight_tokens没有单调递增
    for engine in ["engine_a", "engine_b", "engine_c"]:
        assert state[engine]["in_flight_tokens"] < 100  # 有上限
```

### 5. 优先级排序

**修复优先级：2/11**（仅次于P0-1）

理由：
- 不修复则引擎必然永久停摆（in_flight_tokens单调递增→所有引擎判定full）
- 修复复杂度最高，风险最大
- 是其他修复的基础——如果引擎自己停摆了，其他修复都无意义
- **必须与P0-6（state_lock）一起修复**——释放操作必须在锁内执行

**推荐实现方案**：
```python
# 使用token ID防止重复释放
def release_in_flight(state, engine_name, token_id, amount):
    """释放in_flight_tokens（幂等）"""
    with state_lock:
        eng = state.get(engine_name, {})
        released_set = eng.setdefault("_released_tokens", set())
        if token_id in released_set:
            log(f"[SKIP] token {token_id} already released")
            return
        released_set.add(token_id)
        current = eng.get("in_flight_tokens", 0)
        eng["in_flight_tokens"] = max(0, current - amount)
        log(f"[RELEASE] {engine_name} -{amount} → {eng['in_flight_tokens']}")

# 引擎重启时重置
def load_state_with_reset(filepath):
    state = load_state(filepath)
    for engine in ["engine_a", "engine_b", "engine_c"]:
        if engine in state:
            old = state[engine].get("in_flight_tokens", 0)
            if old > 0:
                log(f"[RESET] {engine} in_flight_tokens: {old} → 0 (restart)")
                state[engine]["in_flight_tokens"] = 0
    return state
```

## P0-6 state修改在锁外执行

### 1. 修复风险

**修复方案**：将所有state修改移入 `with state_lock:` 块

| 风险点 | 评估 |
|--------|------|
| **死锁** | **高风险**。如果锁内有I/O操作或嵌套锁获取 |
| **性能下降** | **中风险**。锁竞争增加，吞吐量下降 |
| **锁持有时间过长** | **中风险**。如果锁内操作多，其他线程长时间阻塞 |
| **异常导致锁不释放** | 低风险。使用 `with` 语句可自动释放 |

**死锁场景分析**：
```
场景1：state_lock + save_state的文件锁
  Thread A: 持有state_lock → 调用save_state → 尝试获取file_lock
  Thread B: 持有file_lock → 尝试获取state_lock
  → 死锁！

场景2：state_lock + 回调函数
  Thread A: 持有state_lock → 执行回调 → 回调中尝试获取callback_lock
  Thread B: 持有callback_lock → 尝试获取state_lock
  → 死锁！

场景3：RLock重入
  函数A持有state_lock → 调用函数B → 函数B也尝试获取state_lock
  如果用Lock → 死锁
  如果用RLock → 正常（同线程可重入）
```

**哪些操作必须在锁内**：
```python
# 必须在锁内（read-modify-write）：
state["idle_cycles"] += 1                    # 原子递增
state["total_growth_score"] += growth_score  # 原子递增
state["idle_phase"] = "winding_down"         # 条件后设置
state["concurrency_override"] = 2           # 条件后设置
raw_goals.append(task)                        # 修改共享list

# 不应在锁内（I/O或耗时操作）：
save_state(state)                             # 磁盘I/O
log(...)                                      # 日志I/O（低风险但非必要）
api_call(...)                                 # 网络I/O
```

### 2. 边界条件

```
条件1：锁内抛异常 → with语句自动释放锁 → ✅
条件2：锁内调用save_state → 可能死锁 → ❌ 需要避免
条件3：锁持有时间 > 其他线程超时 → 线程饥饿 → ⚠️
条件4：递归获取锁 → Lock死锁，RLock正常 → 需用RLock
条件5：信号中断锁内操作 → EINTR → ⚠️ 需要重试
条件6：锁对象被pickle → 不可序列化 → state文件不能包含锁
条件7：多进程而非多线程 → state_lock无效 → 需要文件锁
```

### 3. 回滚方案

```python
# 回滚方案：将部分操作移回锁外
# 回滚后：竞态条件恢复，但不会死锁

# 回滚判断标准：
# - 如果死锁频率 > 竞态频率 → 回滚（死锁更严重）
# - 如果竞态频率 > 死锁频率 → 保持修复（竞态更隐蔽但更频繁）

# 回滚成本：低。移动代码块位置即可。
# 回滚风险：竞态条件恢复，但不会引入新问题。
```

### 4. 验证方法


### 5. 优先级排序

**修复优先级：3/11**

理由：
- 竞态条件可能导致数据损坏，影响所有state操作
- 是P0-5（in_flight_tokens释放）的前置依赖
- 是P0-7（raw_goals复制）的前置依赖
- 修复风险中等（死锁风险可通过RLock+锁外I/O缓解）

**推荐实现**：
```python
# 使用RLock防止重入死锁
import threading
state_lock = threading.RLock()

# 模式：锁内修改，锁外持久化
def safe_state_update(state, updates: dict):
    """安全的state更新模式"""
    with state_lock:
        for key, value in updates.items():
            state[key] = value
        state_copy = copy.deepcopy(state)  # 锁内拷贝
    
    # 锁外执行I/O
    save_state(state_copy)  # 操作拷贝，不持锁
    log(f"[STATE] Updated: {list(updates.keys())}")
```

## P0-7 `raw_goals` 获取的是引用而非副本

### 1. 修复风险

**修复方案**：`raw_goals = list(state.get("goal_tasks", []))`

| 风险点 | 评估 |
|--------|------|
| 浅拷贝不充分 | **中风险**。如果goal_tasks内含dict/list，内部对象仍是共享引用 |
| 深拷贝性能 | 低风险。goal_tasks通常不大（几十项），深拷贝开销可忽略 |
| None值处理 | 低风险。`list(None)`会TypeError，需 `list(state.get("goal_tasks") or [])` |

**浅拷贝 vs 深拷贝**：
```python
# 浅拷贝（不够安全）：
raw_goals = list(state.get("goal_tasks", []))
raw_goals[0]["status"] = "done"  # 仍然修改了原始state中的dict！

# 深拷贝（安全）：
import copy
raw_goals = copy.deepcopy(state.get("goal_tasks", []))
raw_goals[0]["status"] = "done"  # 不影响原始state ✅
```

### 2. 边界条件

```
条件1：goal_tasks = [] → list([]) = [] → ✅
条件2：goal_tasks = None → list(None) → TypeError → ❌ 需 or []
条件3：goal_tasks = [{"task": "x"}] → 浅拷贝仍共享内部dict → ⚠️ 需深拷贝
条件4：goal_tasks非常大（10000+项）→ 深拷贝耗时 → ⚠️ 但概率低
条件5：goal_tasks包含不可序列化对象 → deepcopy可能失败 → ⚠️
```

### 3. 回滚方案

```python
# 回滚：恢复引用获取
raw_goals = state.get("goal_tasks", [])
# 回滚成本：极低
# 回滚影响：竞态条件恢复，但goal_tasks通常低频修改
```

### 4. 验证方法


### 5. 优先级排序

**修复优先级：10/11**

理由：
- 影响范围有限（goal_tasks修改频率低）
- 修复极简单
- 依赖P0-6（锁保护）才能完全解决

if target
