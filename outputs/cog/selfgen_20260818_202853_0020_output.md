# 任务类型: cog

## 复盘结论

**“简化版 SQL”不是简化，而是制造隐性契约断裂。**  
列不匹配往往不在执行时报错，而是在后续 INSERT / SELECT / JOIN / 索引使用时才暴露。基建脚本必须只接受“完整 schema 对齐版”，任何简化版都视为未经验证的突变，禁止直接进入部署流。

锚定推演：简化版 SQL 一旦 commit，就是一次“突变”；只有通过测试的版本才允许保留并部署；如果因列不匹配失败，立即回滚到上一稳定版本，这就是“净化选择”。

## 基建脚本检查清单

### 1. 变更入口
- [ ] 确认脚本不是从记忆、旧笔记或口头描述中手写的“简化版”。
- [ ] 脚本必须从版本库的 schema 基线 / 上一版 migration 生成。
- [ ] 任何“简化”必须在 PR 中给出完整 SQL diff，并说明理由；否则禁止合入。

### 2. 列级一致性
- [ ] 逐列核对：**列名、列顺序、数据类型、长度/精度、nullable、default、identity/自增、字符集/排序规则**。
- [ ] 核对约束：**主键、唯一键、外键、check、索引**。
- [ ] 核对表属性：**engine、partition、comment、auto_increment**。
- [ ] 用 `information_schema` 对比目标表与期望 schema，diff 必须为空。

### 3. 功能验证
- [ ] 在 staging 或临时库执行**完整脚本**，不能用简化版代替。
- [ ] 执行全列 `INSERT`，验证列数和顺序。
- [ ] 执行 `SELECT *`、`UPDATE`、`JOIN`，验证列语义，而不仅仅是“能跑通”。
- [ ] 必须跑“从上一个正式版本升级”的迁移测试，不能只从空库建表。

### 4. 自动化与超时
- [ ] CI 中加入 SQL 静态检查和 schema-diff 测试，任何列不匹配立即失败。
- [ ] 自动化校验任务设置合理 timeout：B 模型 turbo 用 300 秒，A 模型用 600 秒，避免校验超时导致漏判。

### 5. 部署与回滚
- [ ] 部署后跑一次线上列级一致性巡检，确认实际表结构与脚本期望一致。
- [ ] 若发生列不匹配：**立即回滚到上一稳定版本**。回滚是净化选择，不是失败。
- [ ] 将本次“简化版 SQL 导致列不匹配”标记为禁用模式，后续禁止使用同类写法。

### 6. 认知池刷新
- [ ] 本复盘结论在 30 分钟内注入认知池，并参与后续基建脚本任务。
- [ ] 每 10 个任务或每轮结束刷新认知缓存，避免认知池只进不出、变成静态档案库。

---

**一句话记住：基建脚本不允许“差不多”，只允许“完全一致”；所有变更都是突变，测试通过才保留，失败就回滚净化。**
