# 任务类型: cog

针对“基建脚本禁用简化版SQL导致列不匹配”这一事件，这是一次典型的**“为了图快反而埋雷”**的工程化教训。

以下是对该事件的深度复盘，以及提炼出的标准化检查清单。

---

### 一、 认知复盘：为什么“简化版”会引发灾难？

#### 1. 事件背景还原
在数据基建或底层表结构搭建时，为了图方便或快速验证，开发人员使用了“简化版”SQL脚本（例如：省略了全字段显式声明，使用 `SELECT *` 代替；或省略了严格的数据类型转换；或忽略了默认字段、分区字段的声明）。最终导致线上生成的表结构与标准基建规范不一致，上下游任务在读取或写入时发生**列不匹配**，引发数据倾斜、空值报错或任务大规模失败。最终团队决定**全面禁用简化版脚本**。

#### 2. 根因分析
*   **认知偏差：把“基建”当“业务”**。业务SQL可以灵活多变，但基建SQL（建表、数仓分层ODS/DWD、底层链路）是地基。地基不能有任何“模糊地带”。
*   **隐式依赖的毒害**：简化版SQL往往依赖引擎的“隐式推断”（如 `CREATE TABLE AS SELECT`）。上游表加减字段、修改类型时，简化版脚本生成的表结构会静默改变，下游无法感知，最终在某次上游变更时集中爆发列不匹配。
*   **绕过了防御机制**：完整的基建脚本通常包含严格的 Schema 校验、分区设置、生命周期管理。简化版跳过了这些步骤，导致表结构“残缺”。

#### 3. 经验教训
*   **基建代码不是脚手架，而是契约**。基建脚本一旦上线，就成为上下游共同的契约。契约必须显式、严格、白盒化，拒绝任何“黑盒推断”。
*   **“省事”的代码成本最高**：编写简化版SQL省下的10分钟，会带来后续数小时的排查时间和成百上千倍的修复成本。
*   **禁止 `SELECT *` 与 `CTAS` 用于持久化基建表**。这是铁律，不可妥协。

---

### 二、 基建脚本防列不匹配检查清单

在提交任何基建/底层表操作脚本前，请严格对照以下清单（适用于 Hive / Spark / MaxCompute / ClickHouse 等数据引擎）：

#### 📝 1. 建表阶段（DDL）检查
- [ ] **禁用隐式建表**：是否使用了 `CREATE TABLE AS SELECT` (CTAS)？如果是，**必须改为** `CREATE TABLE` 显式定义所有列后再 `INSERT OVERWRITE`。
- [ ] **禁用 SELECT \***：SQL中是否存在 `SELECT *`？必须显式枚举所需字段名。
- [ ] **字段显式声明**：每个字段是否都明确指定了数据类型（如 `BIGINT`, `STRING`, `DECIMAL(18,4)`），未依赖引擎自动推断？
- [ ] **字段顺序对齐**：DDL中的字段顺序是否与 `INSERT` 语句中 `SELECT` 的字段顺序**绝对一致**？
- [ ] **NULL值约束**：是否对不允许为空的字段进行了明确的校验或默认值赋值？
- [ ] **注释完整性**：表和核心字段是否都添加了清晰的业务注释？

#### 🔗 2. 上下游对齐检查
- [ ] **上游表结构感知**：是否检查了上游表近一周内是否有 DDL 变更（加列/删列/改类型）？
- [ ] **下游影响评估**：本次基建表产出后，下游消费方是否已感知表结构？是否会引起下游字段映射报错？
- [ ] **数据类型兼容性**：当下游需要 `INT` 时，本表是否错误地存为了 `BIGINT`？或当下游需要高精度 `DECIMAL` 时，是否被隐式降级为 `DOUBLE`？
- [ ] **测试环境联调**：该脚本是否在测试环境跑通了完整的上下游链路，而非仅仅跑通了一道建表语句？

#### ⚙️ 3. 引擎特性与表属性检查
- [ ] **分区表配置**：是否按规范设置了分区字段（如 `dt`, `hour`）？分区字段是否放在了DDL的最后？
- [ ] **生命周期管理**：表或分区是否设置了合理的生命周期（TTL），避免磁盘爆满？
- [ ] **存储格式**：是否指定了高效的列式存储格式（如 `ORC`, `PARQUET`），而非默认的文本格式？
- [ ] **压缩算法**：是否开启了合理的压缩（如 `SNAPPY`, `ZSTD`）？

#### 🚦 4. 脚本规范与流程检查
- [ ] **禁用简化版/临时版代码**：脚本中是否带有 `-- 简化版`、`-- 临时跑`、`-- 待完善` 等注释？严禁此类代码合入主干。
- [ ] **代码评审**：基建脚本是否经过了至少一位资深同学（或架构组）的 Code Review？
- [ ] **Schema Diff 校验**：脚本执行后，是否有自动化工具对生成的表结构进行 Diff 比对，确保与设计文档一致？

---

### 三、 总结与行动建议

1.  **工具化拦截**：在 CI/CD 环节引入 SQL 静态扫描工具（如 Apache Ranger, 自研 SQL Lint），拦截基建脚本中的 `SELECT *` 和 `CTAS` 语法。
2.  **模板化基建**：提供唯一的、官方的“基建表建立模板”，强制开发者填空填写字段名和类型，而不是从零写 SQL。
3.  **变更感知**：建立元数据监控，当核心基建表的 Schema（字段数量、字段类型）发生突变时，触发告警并熔断下游任务。

**核心记忆点：基建无简化，字段必显式。**
