# 任务类型: cog

基于【已有认知锚定】与【避坑提醒】，针对“L4成品转化仅sop类型，code/checklist未实现”及“主线程串行后处理断流”的问题，我们直接推演**“决策串行、执行并发”**的分层原则及其应用。

### 一、“决策串行、执行并发”的分层原则与脑体分离架构

在多线程并发调用大模型API并由主线程串行后处理的架构中，必须严格贯彻**“先校准锚点再优化链路”**原则，运用“精气神”三元框架进行映射：

*   **脑（决策层 / 主线程 / 串行）：** 负责锚点校准与类型闭环。即“精”的定义与“气”的流转枢纽。主线程必须串行地把控L4成品的类型定义（sop/code/checklist的完整性），确保底层实体的类型闭环。
*   **体（执行层 / 多线程 / 并发）：** 负责纯粹的大模型API调用与算力消耗。即“气”的并行分发。执行层只负责高效调度，不参与类型定义的决策。

**为什么引擎优化不能破坏脑体分离架构？**

1.  **守住“精”的闭环底线（防止类型断流）：** 引擎优化往往追求高吞吐与并发提速。若并发逻辑侵入决策层（如子线程直接决定成品类型并返回），会导致“精”（底层实体/锚点）的类型定义未闭环。主线程在串行后处理时，面对残缺的锚点（仅有sop，缺code/checklist），必然导致“气”（链路流转）断流。
2.  **保障“气”的流转有序（防止超时与死锁）：** 根据【避坑提醒】，API调用存在严格的时间窗口（B模型turbo需300秒，A模型需600秒）。若破坏脑体分离，让“体”去承担“脑”的串行决策逻辑，会导致线程间资源竞争与锁等待，极大拖延整体执行时间，最终引发API调用超时。
3.  **隔离引擎提速带来的状态污染：** 引擎优化（如增加线程池容量、引入异步轮询）只能作用于“体”。脑体分离确保了无论执行层多快，主线程都能以恒定的串行逻辑校验锚点状态，不会因并发乱序导致主线程后处理时发生状态机错乱。

### 二、3个应用场景

基于上述原则，以下为引擎优化在不破坏脑体分离架构下的3个应用场景：

#### 场景1：L4成品转化引擎的多类型生成调度
*   **痛点：** 当前L4转化仅生成sop类型，code/checklist未实现，主线程后处理时发现类型缺失导致断流。
*   **脑体分离执行：** 
    *   **体（并发执行）：** 引擎优化时，执行层多线程并发向大模型发起3类请求（sop、code、checklist的生成API调用）。执行层不判断结果是否完整，只负责接收返回报文。
    *   **脑（串行决策）：** 主线程串行机制作为“脑”，通过Future/Promise机制收集执行层结果。主线程严格校验“精”的锚点——即三类成品是否全部返回且类型匹配。若缺code/checklist，由主线程决策触发重试或异常兜底，确保类型闭环后，再流转到下一链路。

#### 场景2：多模型混合调用与API超时管控
*   **痛点：** A模型与B模型turbo处理不同复杂度任务，易发生API调用超时，导致任务未在规定时间内返回。
*   **脑体分离执行：**
    *   **脑（串行决策）：** 主线程作为“脑”，在分发任务前，根据任务类型预设合理的timeout阈值（B模型turbo预设300秒，A模型预设600秒）。主线程串行地分配任务ID、绑定超时策略，并按序回收结果。
    *   **体（并发执行）：** 引擎优化在“体”内实现多线程并发调用，各子线程严格遵守主线程分配的timeout配置。一旦超时，子线程立即熔断并返回降级标识，不阻塞主线程。主线程串行处理超时降级逻辑，确保“气”的流转不因单个API超时而全局阻塞。

#### 场景3：多Agent协同的后处理聚合与链路流转
*   **痛点：** 多个并发Agent返回的数据格式不一，主线程在串行后处理聚合时发生“气”的断流。
*   **脑体分离执行：**
    *   **体（并发执行）：** 多个Agent子线程并发执行数据抓取、清洗与大模型初步推理。引擎优化可在此层引入批量处理或异步流式读取，提升执行层吞吐量。但子线程仅输出标准化的中间态数据。
    *   **脑（串行决策）：** 主线程作为“脑”，串行接收各Agent的中间态数据，进行最终的类型转换与锚点校验。主线程严格校验“精”（底层实体）的格式与上下文连续性，确认无误后，再将聚合后的完整实体推入下一链路。任何引擎层面的并发提速，都不能绕过主线程的串行校验直接写入下游数据库。
