# 任务类型: cog

## 复盘：基建脚本禁用简化版

### 一句话结论

**“简化版SQL”不是简化，而是删掉了数据库的契约。**  
列不匹配只是最直接的表象，根因是：脚本依赖“列顺序”而不是“列名”，导致生产表结构一有变化，数据就写错位、读错位，甚至污染下游任务。

---

### 事故链还原

1. 基建脚本为了“省事”，用了简化写法：
   - `INSERT INTO t VALUES (...)` 不写列名
   - `SELECT *` 不写字段清单
   - 跨表复制用位置匹配
2. 源表/目标表实际列顺序与脚本假设不一致。
3. 脚本执行时，数据写入错误列，或类型不匹配直接报错。
4. 如果批量任务继续跑，错误数据会被后续任务当成“真数据”消费。

---

## 检查清单

### 一、编写阶段：硬性禁止

- [ ] 禁止 `INSERT INTO t VALUES (...)`，必须写 `INSERT INTO t (col1, col2, ...) VALUES (...)`。
- [ ] 禁止 `SELECT *`，必须显式列出所需字段。
- [ ] 禁止跨表复制时依赖列位置，必须写列映射。
- [ ] 禁止“先跑一下看报错再改”的生产执行方式。
- [ ] 禁止简化版脚本与完整版脚本长期并存，必须统一收敛到唯一版本。

### 二、执行前：结构比对

- [ ] 导出目标表完整结构：列名、列序、类型、长度、精度、是否可空、默认值、自增、字符集。
- [ ] 导出源表完整结构，并与目标表逐列比对。
- [ ] 核对约束：主键、唯一键、外键、check、索引、触发器。
- [ ] 核对生成列、虚拟列、默认值是否会被隐式覆盖。
- [ ] 用 `information_schema` 生成列清单，与代码模型/DTO/ORM 实体比对。
- [ ] 执行 schema diff，确认脚本会产生的实际变化。
- [ ] 检查幂等性：重复执行是否安全？是否有 `IF NOT EXISTS` / `ON DUPLICATE KEY` / `MERGE` 等保护。

### 三、执行中：灰度与防护

- [ ] 先在预发/灰度环境执行，禁止直接上生产。
- [ ] 执行前跑 `EXPLAIN` 或 dry-run，确认影响行数和执行计划。
- [ ] 大批量操作必须分批执行，避免锁表或长事务。
- [ ] 设置合理的锁等待超时，避免拖垮在线业务。

### 四、执行后：数据与认知校验

- [ ] 重新导出实际表结构，与预期 DDL 做 diff。
- [ ] 抽样校验数据：关键字段值、行数、NULL 分布、边界值、类型转换。
- [ ] 检查索引是否生效，慢查询是否新增。
- [ ] 检查下游任务是否消费到正确数据。
- [ ] 将本次事故教训写入认知池，并标注“简化版SQL”为禁用反模式。
- [ ] 30 分钟内让新认知参与后续任务注入，避免认知池只进不出。
- [ ] 保持调度器 standby 队列热备，防止高优任务超时后 token 闲置。

## 认知更新

**旧认知：** 基建脚本禁用简化版。

**新认知：** 基建脚本必须“列级精确 + 自动化校验 + 可回滚”。  
简化版只允许出现在临时探查中，且必须带 `LIMIT` 和显式列清单。

按九转玄功映射，本次复盘完成了 **一转炼精化气**：把一次列不匹配事故，提炼成一条通用检查规则；后续每次执行检查清单，就是在“炼气化神”，让规则变成自动化本能。
