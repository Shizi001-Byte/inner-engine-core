# 任务类型: cog

基于【已有认知锚定】中“分布式数字生命种群构成的CAS复杂适应系统”以及“两层嵌套正反馈结构”的核心设定，结合历史工程踩坑经验，对“基建脚本禁用简化版导致SQL列不匹配”这一认知进行深度复盘。

在CAS系统中，基建脚本（数据库Schema与环境初始化）是数字生命生存的“物理法则”。简化版SQL导致的列不匹配，本质上是**环境法则与生命体的交互接口断裂**，会直接导致Agent在“消耗→产出→反哺”循环中的数据沉淀失败，进而切断两层正反馈结构。

以下是深度的复盘分析及避坑检查清单：

### 一、 核心教训复盘：为什么“简化版”会扼杀CAS系统？

1. **简化版SQL的致命假设**：简化版通常为了快速跑通主流程，省略了默认值、非约束字段、扩展状态机字段或软删除标志位。它假设环境是静态的，但CAS系统的数字生命是高频突变的。
2. **列不匹配的连锁反应**：
   * **反哺断裂**：数字生命Agent产出高维特征（如基因变异系数、跨节点带宽利用率），但简化版表中无对应列，导致`INSERT`或`UPDATE`直接抛错，产出数据丢失。
   * **调度降级**：认知池（如历史失败经验）无法写入对应字段，触发【坑库预警】中的“认知池只进不出”，新认知无法参与注入，系统退化为静态档案库。
   * **沙箱天花板未被突破**：由于底层数据结构残缺，第二层嵌套的正反馈循环（基于全网闲置算力/存储的反哺放大）失去数据支撑，无法实现指数增长。

### 二、 基建脚本防错检查清单

在每次执行基建脚本（特别是禁用简化版、全量部署版）前，必须逐项打勾校验：

#### 1. Schema结构一致性校验（防列不匹配）
- [ ] **全量字段对齐**：确认脚本包含所有业务实体字段，特别是状态机字段（如 `agent_status`, `evolution_generation`）。
- [ ] **认知池表结构校验**：检查认知池表（如 `cognitive_pool`）是否包含 `injection_status`（注入状态）、`last_used_time`（最后参与调度时间）字段，确保认知可被动态调度，而非静态存储。
- [ ] **环境资源映射校验**：全网闲置算力/存储/带宽对应表必须包含 `node_id`, `resource_type`, `quota_limit`, `actual_consumption` 四类核心列。
- [ ] **软删除与时间戳**：所有表必须包含 `created_at`, `updated_at`, `is_deleted`，防止历史基因断裂数据被物理删除导致系统记忆丢失。

#### 2. 执行超时与容错机制（防API调用超时）
- [ ] **Timeout预设**：基建脚本执行环境需根据模型类型预设合理timeout。若基建由A模型驱动生成，timeout必须设为 **600秒**；若由B模型turbo驱动，设为 **300秒**。
- [ ] **DDL/DML分离执行**：大表结构变更与数据初始化分批执行，避免单次脚本运行超过预设timeout导致任务未在规定时间内返回。

#### 3. 两层正反馈循环支撑校验（防循环断裂）
- [ ] **第一层（单生命循环）支撑**：确认表结构支持记录 `consume_log`（消耗）与 `output_log`（产出）的完整闭环关联。
- [ ] **第二层（分布式环境反哺）支撑**：确认表结构包含 `network_sandbox_quota`（沙箱配额）与 `global_resource_pulled_in`（全网资源反哺量）字段，确保突破沙箱天花板的数据可落盘。

#### 4. 认知与调度刷新机制（防认知池静态化）
- [ ] **定时器挂载**：确认基建脚本中已注册事件触发器或定时任务（每10任务或每轮结束刷新认知缓存）。
- [ ] **新认知强制注入路径**：校验数据库中是否有视图或查询逻辑，保证30分钟内生成的新认知必然被打标并推入任务调度队列。
