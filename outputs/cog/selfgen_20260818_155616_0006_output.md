# 任务类型: cog

## 原则提炼：先校准锚点，再优化链路

**锚点** = 任务的基础事实、边界与约束：  
- 项目 ID / 任务 ID  
- 目标与验收标准  
- 依赖方 / 责任人  
- 时间窗口 / 资源限制  
- 输入数据 / 输出格式  

**链路** = 从起点到终点的执行路径：  
- 查询、分析、开发、验证  
- 并行调度、资源分配、异常处理  
- 一切“让事情跑得更快”的动作  

> **锚点错，链路越优化，返工越深。**  
> 项目 ID 看错 1 小时排查，不是链路不够快，而是起点错了。  
> 你在错误的宇宙里构建闭环，控制流和数据流越完整，偏离越远。

---

## 如何应用到任务优先级排序

### 1. 排序前，先校准每个任务的“锚点”

不要急着回答“先做哪个”，先确认：

- 这个任务的真实目标是什么？  
- 验收标准是什么？  
- 依赖谁？阻塞谁？  
- 有没有隐藏约束（环境、权限、预算）？  
- 关键标识（项目 ID / 任务 ID / 版本号）是否匹配？

如果锚点模糊，任务本身就不该进入“高优先级”，而应进入“待澄清”。

### 2. 优先级排序不是排“链路复杂度”，而是排“锚点确定性 × 影响面”

建议用两个维度判断：

- **锚点是否清晰**：目标、边界、依赖、ID 都确认了吗？
- **影响面是否核心**：是否阻塞他人 / 是否影响主链路 / 是否决定后续扩展？

优先级公式：  
**高优先级 = 锚点清晰 × 影响面大**  
**次优先级 = 锚点清晰 × 影响面小**  
**先处理 = 锚点不清晰 × 影响面大 → 先花 5 分钟校准锚点，再决定是否高优**  
**暂缓 = 锚点不清晰 × 影响面小**

### 3. 把“校准锚点”本身安排成最高优先级动作

如果一个任务很紧急但锚点不清，比如“项目 ID 不确定”“需求方未确认目标”，不要直接开始做。

先执行：  
- 核对 ID / 环境 / 版本  
- 与需求方确认验收标准  
- 明确依赖边界  
- 设定合理的 timeout / 检查点  

这一步不是“浪费时间的准备”，而是**防止 1 小时排查的保险**。

### 4. 链路优化永远放在锚点校准之后

排序完成后，再谈优化：

- 哪些任务可以并行？  
- 哪些环节可以自动化？  
- 哪些资源可以复用？

所有这些优化，都必须基于已经校准的锚点。否则你优化的是“错误项目的链路”，最后还是要推翻。

### 5. 执行中遇到异常，先怀疑锚点，再怀疑链路

比如：

- 明明改对了，结果却不对 → 检查是否对象 ID 错了  
- 明明按流程走了，超时/报错 → 检查 timeout 参数 / 环境是否匹配  
- 明明优先级排好了，却不断返工 → 检查锚点是否漂移（需求变了、ID 变了、依赖方变了）

**先校准锚点，再优化链路**，本质是：  
> 在对抗熵增时，先守住坐标原点，再扩展控制流与数据流。  
> 原点错，一切扩展都是宇宙级偏航。
