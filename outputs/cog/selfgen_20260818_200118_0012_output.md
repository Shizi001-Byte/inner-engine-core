# 任务类型: cog

“先校准锚点再优化链路”可以提炼成一句话：

> **锚点 = 任务的身份 + 顺序；优化 = 优先级排序、并发、后处理。锚点错了，优化越快，错得越远。**

对应到“项目 ID 看错导致排查 1 小时”：你是在用错误的锚点（错误项目）去查正确的问题，所以查不到。  
应用到任务优先级排序时，应该这样做：

---

## 1. 先校准“身份锚点”

排序前不要直接拿 `priority` 排序，先确认每个任务的身份：

- `projectId` 必须是内部规范化后的 ID，不能靠肉眼识别或手抄；
- 校验 `projectId` 是否存在、是否属于当前业务范围；
- 确认 `priority` 是从这个 `projectId` 当前有效配置里取出来的，而不是缓存错值或从别的项目带过来的。

> `priority` 不是锚点，它只是挂在锚点上的属性。  
> 项目 ID 看错，优先级再高也是别人的优先级。

---

## 2. 再校准“顺序锚点”

多线程/异步场景下，任务必须有一个不可变的顺序标识：

- 下发任务时，给每个任务打一个单调递增的 `seq`；
- 如果同一任务可能重试/重发，保留 `version` 或 `timestamp`；
- 优先级排序时，排序键应为：

```text
(priority desc, seq asc)
```

这样能保证：

- 高优先级先处理；
- 同优先级下，按原始下发顺序处理；
- 不会因为线程返回顺序不同而变成 `3,2,1`。

---

## 3. 最后再优化链路

多线程 API 返回后，不要“谁先返回谁后处理”，而是：

1. 先按 `projectId + taskId + seq` 放入 Map；
2. 等所有响应回来后，统一按排序键处理；
3. 写结果前做“新鲜度校验”：只有 `seq/version` 更新的数据才能覆盖旧数据。

这样就能避免“旧数据覆盖新数据”。

---

## 一句话应用清单

任务优先级排序前，先问三个问题：

1. 这个 `projectId` 我看准了吗？  
2. 这个 `priority` 是当前项目实时查出来的吗？  
3. 每个任务有唯一 `seq` 吗？

三个都校准了，再谈排序优化。  
否则就是“拿着错误的锚点，加速错误的结论”。
