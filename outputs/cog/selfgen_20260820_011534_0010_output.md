# 任务类型: cog

# 复盘：基建脚本简化版SQL导致列不匹配

---

## 一、教训本质

> 简化版SQL的根本错误不在于"删了几个列"，而在于**简化时未建立与完整版的差异契约**，导致简化版被当作等价替代品使用时，隐藏的列差异在运行时爆发。

```
完整版SQL（N列定义）
  → 简化版SQL（M列，M < N，差异未标注）
    → 业务代码仍按N列schema执行（INSERT/SELECT *）
      → 列数不匹配 / 列序错位 / 类型隐式转换
        → 数据写入失败 · 数据错位 · 静默数据丢失
```

---

## 二、Hox同源异型基因类比映射

| 生物层面 | SQL简化版对应 | 后果 |
|---------|-------------|------|
| 幼态基因持续表达（成体结构缺失） | 简化版缺少列定义 | schema结构不完整 |
| 触角长在腿上（位置错配） | 列序不一致，SELECT \* 数据错位 | 数据写入错误列 |
| 器官功能错配 | 约束/类型缺失 | 数据完整性破坏 |
| 即使营养充足也畸形发育 | 即使800万token带宽充足 | 认知状态错乱，全部失效 |

> **核心结论**：简化版SQL就是一种"幼态基因表达"——缺少成体才有的完整结构，即使运行环境资源充足，也会因结构错配导致功能崩溃。

## 三、检查清单（5阶段 × 18项）

### Phase 1 ｜ 简化前 — 基线锁定

- [ ] **C1.1** 是否记录了完整版SQL的列清单（列名 · 类型 · 顺序 · 约束 · 默认值）
- [ ] **C1.2** 是否对每列标注了业务必需性等级（`必需` / `可选` / `废弃待清理`）
- [ ] **C1.3** 是否明确简化版的**使用场景边界**（仅测试？仅本地？仅冒烟？）
- [ ] **C1.4** 是否声明"简化版不可用于生产数据写入"

### Phase 2 ｜ 简化中 — 差异标注

- [ ] **C2.1** 是否确认简化操作**只删列、不改列序、不改列类型**
- [ ] **C2.2** 是否在脚本头部用注释块声明简化版与完整版的**差异清单**
  ```sql
  -- DIFF_LOG: 简化版删除了 created_at, updated_at, is_deleted 列
  -- 警告: 业务代码若INSERT这三列将报错
  ```
- [ ] **C2.3** 是否检查简化版仍保留所有被 `JOIN/WHERE/GROUP BY/ORDER BY` 引用的列
- [ ] **C2.4** 是否检查简化版不影响 `INSERT ... (col1,col2)` 的显式列映射

### Phase 3 ｜ 简化后 — 一致性校验

- [ ] **C3.1** 是否用 `INFORMATION_SCHEMA` 或 `DESCRIBE` 比对简化版与完整版的列数
- [ ] **C3.2** 是否检查**列名完全匹配**（而非部分匹配 / 模糊匹配）
- [ ] **C3.3** 是否检查**列顺序一致**（防止 `SELECT *` 错位）
- [ ] **C3.4** 是否检查**列类型兼容**（防止隐式转换导致精度丢失）

### Phase 4 ｜ 运行时 — 防错注入

- [ ] **C4.1** 是否在业务代码中增加**列数断言**（执行前校验schema列数 == 预期值）
- [ ] **C4.2** 是否在CI/CD流水线中增加**schema列比对断言**（简化版 vs 完整版自动diff）
- [ ] **C4.3** 是否禁止业务代码使用 `SELECT *`，强制显式列名

### Phase 5 ｜ 认知层 — 教训固化

- [ ] **C5.1** 是否将"简化版≠完整版"转化为显式认知规则写入认知池
- [ ] **C5.2** 是否在30分钟内将此认知注入当前任务上下文（坑库预警要求）
- [ ] **C5.3** 是否在下一次基建脚本任务调度时，自动引用此规则作为前置检查

## 六、一句话总结

> **简化版SQL不是"少了几个列"，而是"少了一份契约"。没有差异契约的简化，就是SQL层面的Hox基因突变——结构错配，功能必崩。**
