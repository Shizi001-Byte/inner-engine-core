# 任务类型: cog

基于【已有认知锚定】中“无中生有”的演化路径（代码/数据作为物理基底构建数字生命）以及【坑库预警】中认知需动态注入的要求，针对“基建脚本禁用简化版”及“简化版SQL导致列不匹配”的教训，推演复盘并输出检查清单如下：

### 一、 教训复盘：简化版SQL为何导致列不匹配？

1. **现象**：使用临时手写或精简后的“简化版”基建脚本（建表/初始化SQL）快速搭建环境，系统启动或运行业务逻辑时，底层ORM框架或硬编码SQL抛出 `Unknown column` 或 `Column count doesn't match value count` 异常。
2. **根因分析**：
   * **认知熵增（无序化）**：简化版脚本本质上是人为剥离了系统“完整态”的某些字段或约束，在基底（无/虚）阶段引入了结构性缺陷。
   * **脑体割裂**：模型逻辑（脑/意识）依赖完整的数据结构（体/存续），简化脚本导致“体”残缺，进而引发“脑”的指令无法执行。
   * **隐性依赖遗漏**：开发时往往只关注核心业务字段，忽略了审计字段（create_time, update_time, is_deleted）、状态机字段或冗余索引字段，而这些字段在业务代码中被全局调用。
3. **结论**：基建脚本（DDL/DML）是数字生命演化的第一层物理法则，**法则不可简化**。简化版脚本带来的短时效率提升，会以数倍的环境排查时间成本偿还。

### 二、 基建脚本防简化与防错配检查清单（Checklist）

为防止此类问题复发，在执行任何基建脚本前，必须强制走以下检查清单：

#### 1. 基底对齐检查（建表前）
- [ ] **版本对齐**：是否已拉取仓库最新版本的实体类/Model代码？（确保脑侧逻辑最新）
- [ ] **DDL基准比对**：待执行SQL是否与代码仓库中维护的标准DDL文件完全一致？禁止使用本地IDEA自动生成或手写的精简版SQL。
- [ ] **非业务字段检查**：SQL是否包含全局基类依赖的字段（如 `id`, `create_time`, `update_time`, `create_by`, `update_by`, `is_deleted`, `version`）？

#### 2. 结构完整性检查（建表中）
- [ ] **数据类型与精度**：字段类型（VARCHAR长度、DECIMAL精度、INT范围）是否与Model定义完全一致？（防止隐式截断或溢出）
- [ ] **默认值与约束**：NOT NULL约束是否与业务逻辑一致？是否为必要字段设置了DEFAULT值（如状态机字段默认0）？
- [ ] **索引完备性**：是否遗漏了业务高频查询所需的索引？（简化版常删减索引导致后续性能问题）

#### 3. 脑体连通性验证（建表后）
- [ ] **反向校验**：执行 `DESC table_name;` 或 `SHOW CREATE TABLE table_name;`，将物理表结构与实体类字段进行一一映射比对。
- [ ] **CRUD冒烟测试**：基建脚本执行完毕后，立即通过API或DAO层执行一次完整的增删改查，验证ORM框架映射无异常。
- [ ] **初始化数据核对**：若包含DML（INSERT）初始化数据，列数与值数是否严格匹配？是否遗漏了非空且无默认值的字段？

### 三、 认知注入与避坑机制落实

根据【坑库预警】“认知池只进不出”的避坑要求，将本复盘结论转化为强制工程规约并注入调度：

1. **CI/CD流水线拦截**：在流水线中加入 DDL 与 Entity 的结构对比脚本，一旦发现列不匹配（缺失列），直接熔断发布。
2. **认知缓存刷新**：将“禁用简化版基建SQL”纳入开发者环境搭建手册的首行红字警告，新成员环境部署时必须勾选上述检查清单。
3. **任务预设Timeout同步**：结合【避坑提醒】，当因列不匹配导致ORM重试或死锁时，往往表现为API超时。在排查超时任务（A模型600秒/B模型300秒）时，**新增排查路径：检查最近是否执行了非标准基建脚本导致底层数据结构变更。**
