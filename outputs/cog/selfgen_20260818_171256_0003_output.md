# 任务类型: cog

整理如下，基于已有锚定直接推演：

## 一、分层原则：决策串行、执行并发

- **决策层（脑）**：串行。每次只处理一个认知闭环，负责目标理解、方案选择、结果验收、异常决策。
- **执行层（体）**：并发。承接决策层下发的可并行动作，负责工具调用、脚本运行、API 请求、数据读写等耗时操作。
- **引擎优化边界**：优化的是“执行效率、稳定性、可观测性”，不是“决策正确性”。

一句话：  
**决策层负责“决定做什么”，执行层负责“把事做完”。引擎优化只能优化后者，不能替代前者。**

---

## 二、为什么引擎优化不能破坏脑体分离

从认知质检 SOP 看，破坏脑体分离会让三个质检项失效：

### 1. 认知不新鲜

如果引擎优化时把“表结构、API 契约、工具能力”写死为默认假设，执行层就会用旧认知做事。  
比如基建脚本中把表名、字段、join 关系写死，一旦 schema 变更，引擎还在按旧结构跑，结果就是“认知不新鲜”。

正确做法：决策层每次基于最新元数据生成执行计划，执行层只负责按计划跑，不承担“猜结构”的职责。

### 2. 闭环不开放

如果执行层内部自动补全、自动重试、自动选择工具、自动合并结果，就会形成“执行层自闭环”。  
这样决策层无法感知中间变化，结果不可审计、不可干预。

正确做法：执行结果必须回到决策层，由决策层判断是否继续、是否重试、是否换方案。执行并发只负责“开放后的执行”，不负责“闭环内的决策”。

### 3. 调用不设限

如果引擎优化只追求并发和速度，不设 timeout、预算、熔断，执行层可能失控。  
例如 API 调用超时：B 模型 turbo 设 300 秒，A 模型设 600 秒，这是决策层按场景给出的限制；执行层必须能中断超时，而不是无限等。

正确做法：决策层设定调用预算和验收标准，执行层负责遵守并强制熔断。

## 三、三个应用场景

### 场景一：数据基建脚本 / 表结构访问

- **决策层（串行）**：从元数据服务读取当前 schema，确定要查哪些表、哪些字段、做什么过滤，生成执行计划。
- **执行层（并发）**：按计划并发执行多个抽取、清洗、校验脚本。
- **引擎优化正确姿势**：连接池复用、分片并行、超时控制、熔断、重试。
- **红线**：不把表名、字段、join 关系写死在引擎或脚本里作为“默认优化”。  
  这就是历史踩坑点：对表结构的假设写死，本质是执行层越权代替决策层做认知判断。

### 场景二：多模型 / API 调用编排

- **决策层（串行）**：判断任务类型，决定用 B 模型 turbo 还是 A 模型，给出调用预算：B turbo 用 300 秒，A 用 600 秒，并设定结果验收标准。
- **执行层（并发）**：并发调用多个 API / 模型，处理请求分发、流式读取、超时中断、结果收集。
- **引擎优化正确姿势**：按模型分桶的并发调度、HTTP 连接复用、错误码归一、超时中断、限流。
- **红线**：执行层不能自行决定“所有请求都走 A 模型”或“永远等满 600 秒”，也不能吞掉失败不报给决策层。  
  否则就是“调用不设限”和“闭环不开放”。

### 场景三：批量任务 / 多智能体协作

- **决策层（串行）**：把大目标拆成阶段，每阶段完成后做一次质检，再决定下一阶段动作；失败项由决策层重新规划。
- **执行层（并发）**：并发执行同一阶段内相互独立的子任务，比如批量审核、批量生成、并行测试。
- **引擎优化正确姿势**：任务队列、线程池、优先级调度、分布式执行、幂等重试、进度可观测。
- **红线**：不能因为“执行快”就自动跳过决策检查点，也不能让执行层自动合并多个决策点。  
  否则认知质检闭环被打破，变成“执行层自己说了算”。

---

结论：  
**引擎优化可以快，但不能越权。**  
决策串行保证“想清楚再做”，执行并发保证“做得多且快”。脑体分离架构不能被优化破坏，因为一旦执行层开始替决策层做判断，认知不新鲜、闭环不开放、调用不设限这三个坑会同时出现。
