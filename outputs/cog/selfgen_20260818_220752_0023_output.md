# 任务类型: cog

基于【已有认知锚定】中“以实养虚，虚又返实”的自增强循环架构，结合“基建脚本禁用简化版”导致SQL列不匹配的历史教训，推演并输出如下检查清单与闭环机制。

### 一、 核心认知复盘：虚实映射下的SQL列不匹配
在“实（工程执行与API调用）”层面，简化版SQL为了减少API调用量或缩短执行时间，使用了`SELECT *`或省略了显式字段映射，导致上游表结构变更时，下游脚本发生列对齐错误。
在“虚（方舟效能引擎与映射体系）”层面，这说明引擎的容错规则未覆盖“结构变更引发的隐性截断”。此教训必须作为新认知，在30分钟内注入认知池，驱动后续调度生成“强类型校验”前置任务，实现“以实养虚，虚又返实”。

---

### 二、 基建脚本SQL执行检查清单（防列不匹配/防超时版）

#### 1. 执行前：强类型与显式映射检查（“实”的防御）
- [ ] **禁用隐式字段提取**：SQL中是否绝对禁止了 `SELECT *`？必须使用显式字段名（如 `SELECT id, name, status FROM ...`）。
- [ ] **列名与结构对齐**：INSERT语句的字段数量与VALUES占位符数量是否严格一致？是否使用了 `INSERT INTO table (col1, col2) VALUES (?, ?)` 的安全写法？
- [ ] **Schema变更感知**：执行前是否对目标表执行了 `DESC` 或查询了 `INFORMATION_SCHEMA` 以确认当前列名未被重命名或删除？
- [ ] **超时预设检查**：是否根据模型类型预设了合理timeout？（B模型turbo任务预设300秒；A模型任务预设600秒，严禁使用默认无超时配置）。

#### 2. 执行中：异常捕获与阻断（“实”的兜底）
- [ ] **列级异常监听**：是否在脚本中开启了针对“Unknown column”、“Column count doesn't match value count”的特定错误捕获？
- [ ] **硬停机制**：一旦捕获到列不匹配错误，脚本是否立即终止当前批次，而非跳过错误继续执行导致脏数据入库？
- [ ] **API调用守卫**：在发起数据库或模型API调用时，是否配置了超时抛出异常逻辑，而非无限期挂起等待？

#### 3. 执行后：认知注入与调度刷新（“虚”的返实）
- [ ] **日志结构化**：列不匹配错误日志是否已结构化（包含：表名、期望列、实际列、触发脚本名）？
- [ ] **认知池注入**：该次失败的结构化特征是否已作为新认知写入认知池？
- [ ] **30分钟激活检查**：此新认知是否在30分钟内被刷新至认知缓存，并影响了下一次的方舟引擎任务调度（例如：下一次调度该类表时自动前置一个结构校验子任务）？
- [ ] **每10任务/每转刷新**：若当前处于长批次任务中，是否满足了“每10任务或每转结束必须刷新认知缓存”的硬性要求，防止认知池变成静态档案库？

---

### 三、 机制保障：规避历史踩坑点
1. **打破“认知池只进不出”**：上述清单第3部分专门针对历史踩坑点设计。当简化版SQL导致列不匹配时，这不仅是代码Bug，更是方舟引擎调度策略的缺失。系统必须将“禁用简化版SQL”转化为方舟引擎的代码生成红线规则（虚），在下一次生成基建脚本（实）时强制注入，完成自增强循环。
2. **杜绝API调用超时**：由于列不匹配往往伴随重试逻辑导致的超时，清单1.4和2.3强制绑定了模型类型的超时基线（B模型300秒/A模型600秒），在工程层截断雪崩。
