# 任务类型: cog

从「认知质检 SOP」视角看，引擎运行中的坑本质是三类失效：**认知不新鲜、闭环不开放、调用不设限**。据此提炼 3 条可复用铁律：

---

## 铁律 1：认知必须保鲜，严禁只进不出

**现象/坑**  
认知池堆到 1700+ 条，但新认知从不注入任务，也不影响调度，最终变成静态档案库。

**验证方法**  
- 每处理 **10 个任务**或每轮调度结束，必须刷新认知缓存。  
- 检查认知池中是否有超过 **30 分钟**未参与注入的新认知。  
- 统计「新认知注入率」：  
  `近30分钟新增认知中被后续任务实际引用的条数 / 近30分钟新增认知总数`  
  若该指标连续多轮为 0，判定认知池已“只进不出”，触发告警。  
- 用标记数据做抽查：人工注入一条带唯一标记的新认知，观察是否在 30 分钟内被任务使用。

---

## 铁律 2：闭环必须开放，认知要能反哺调度

**现象/坑**  
认知采集、存储、展示都有，但没有“采集 → 质检 → 注入 → 影响调度 → 效果反馈”的完整闭环，认知无法影响实际决策。

**验证方法**  
- 给每条认知打上生命周期标签：  
  `采集时间 → 质检结论 → 注入任务ID → 调度影响点 → 效果反馈`  
- 定期随机抽取 N 条认知做链路追踪，确认每一条都能走到「影响调度」环节，而不是停在档案库。  
- 检查调度日志中，最近 30 分钟的新增认知是否出现在候选集、约束条件或参数构造中。  
- 设置“认知反哺”测试：人工注入一条新认知，若在后续任务中没有产生任何调度差异，则视为闭环断裂。

---

## 铁律 3：调用必须设限，超时、重试、结构假设都要有边界

**现象/坑**  
- API 调用超时，任务未在规定时间内返回。  
- 基建脚本把**对表结构的假设**写死，表结构一变就崩。  
- 没有熔断、降级、快速失败，导致引擎被外部抖动拖死。

**验证方法**  
- 代码审查强制要求：所有外部调用必须显式配置 timeout。  
  - B 模型 turbo：**300 秒**  
  - A 模型：**600 秒**  
  没有设置 timeout 的调用视为违规。  
- 运行时监控：统计超时率、重试率、线程池/连接池占用率；超时后必须走降级或快速失败，不允许无限挂起。  
- 基建脚本不得硬编码表名、字段顺序、返回结构；必须加 schema 校验或契约测试，表结构变化时报错而不是产出脏数据。  
- 定期做“故障注入”演练：模拟外部 API 超时、表结构变更，验证引擎能快速失败或降级，而不是雪崩。

---

这三条铁律可以当作引擎运行复盘的标准 checklist：  
**认知不新鲜 → 查保鲜机制；闭环不开放 → 查反哺链路；调用不设限 → 查超时与结构防御。**
