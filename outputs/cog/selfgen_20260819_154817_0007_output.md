# 任务类型: cog

## 原则提炼

**先校准锚点，再优化链路**：任何集成任务中，先确认所有“错一个就全盘错”的关键标识——`change_id`、内容哈希、`project_id`、Webhook Secret、目标表主键、环境版本——并锁定基线；基线未锁定前，所有针对超时、重试、并发、缓存、幂等的“链路优化”都是高风险低收益的。

项目ID看错导致1小时排查，不是排查能力问题，而是**锚点未校准就开始优化链路**。如果先花3分钟校验 project_id，后面1小时完全可以省掉。

---

## 应用到任务优先级排序

### 1. 锚点校准任务永远排第一

任务列表里同时出现：

- 核对 `project_id` / `change_id` / 内容哈希
- 优化 API 超时 / 重试 / 冷却

必须把“核对锚点”排在“优化链路”前面。  
因为锚点错了，链路优化全部建立在错误地基上。

### 2. 按“锚点影响度”决定内部优先级

影响范围越大的锚点，越要先校准：

| 锚点 | 错误后果 |
|---|---|
| `change_id` / 内容哈希 | 去重失效、幂等失效、冲突处理全乱 |
| `project_id` | 所有代码/文件/记录关联到错误项目 |
| Webhook Secret | 所有回调被拒绝，链路完全中断 |
| 表主键 / 唯一索引 | 写入冲突、数据覆盖 |

### 3. 用“锚点置信度”卡住链路任务

锚点置信度只有两档：

- **已验证**：从配置读一次，再通过 API/数据库实际查一次，两边一致
- **未验证**：只看了一眼，或只凭记忆

未验证时，所有链路优化任务标记为“阻塞”；已验证后，链路优化才允许启动。

---

## 任务优先级排序表

| 锚点状态 | 任务类型 | 优先级 | 原因 |
|---|---|---|---|
| 未验证 | 校准锚点 | P0 | 错误成本最高，必须最先做 |
| 未验证 | 优化链路 | P2/阻塞 | 在错误地基上盖楼 |
| 已验证 | 校准锚点 | P1 | 防止回归/漂移 |
| 已验证 | 优化链路 | P2 | 可以放心调优 |

## 具体执行SOP

1. **列出锚点清单**  
   例如：Gitee 仓库 `project_id`、Feishu 文件夹 token、Supabase 表名、`change_id` 生成规则、内容哈希算法。

2. **双重验证每个锚点**  
   - 从配置文件读一次  
   - 从实际系统 API/数据库查一次  
   - 两边一致才算“已校准”

3. **锁定锚点基线**  
   把校准结果写入文档或环境变量模板，打上版本号，作为后续任务唯一引用标准。

4. **再开始优化链路**  
   此时才调 timeout、retry、冷却、并发、幂等逻辑。  
   例如：B模型 turbo 用 300 秒，A模型用 600 秒，这些参数只有锚点正确时才有意义。

---

## 反例与正例

**反例**  
拿到需求先调 API 超时，把 B 模型调到 300 秒、A 模型调到 600 秒，结果 project_id 看错，排查 1 小时后发现所有请求都在查错误项目，超时参数根本不用改。

**正例**  
先花 5 分钟确认 `project_id` 与 Gitee 仓库一致，确认 `change_id + 内容哈希` 能唯一定位一次提交；再设置超时和重试。即使后续报错，也能迅速判断是链路问题，而不是锚点问题。

---

## 一句话口诀

**先验证，再分工，后沉淀；锚点不牢，优化白搞。**

任务优先级排序时，永远问一句：  
**这个任务是“校准锚点”还是“优化链路”？如果是后者，锚点验证了吗？**  
没验证，就先去做验证；验证过，再放心优化。
