# 任务类型: cog

结论：**任务优先级排序必须先校准锚点，再排优先级。锚点未校准的任务，不得进入优先级队列。**  
“项目ID看错导致1小时排查”的根因，就是先优化了执行链路，却没先校准任务锚点。

---

## 一、校准哪些锚点

每项任务排序前，必须确认以下信息，缺一不可：

| 锚点 | 要求 |
|---|---|
| 任务ID / 项目ID | 必须与源系统一致，不能靠记忆 |
| 业务目标 | 这项任务到底解决什么问题 |
| 完成标准 | 怎样才算“做完” |
| 约束条件 | 依赖项、截止时间、调用超时阈值 |
| 当前状态 | 是否已过期、已阻塞、需求已变更 |

超时本身就是执行链路的关键锚点：  
**B模型turbo调用设300秒，A模型调用设600秒**，未校准这个阈值，任务可能“看似成功，实际超时失败”，优先级排序也会失真。

---

## 二、排序前先做“三查三对”

三查：  
- 查项目ID  
- 查任务ID  
- 查依赖状态  

三对：  
- 对需求文档  
- 对代码分支/环境  
- 对最近变更记录  

发现锚点冲突，**立即停止排序，先解决冲突**。  
不要“边排边猜”，更不要“先排完再核对”。

---

## 三、排序规则

只有锚点校准通过的任务，才进入优先级矩阵：

```
优先级 = 已验证价值 × 已验证紧急度 × 依赖位置 ÷ 校准置信度
```

- 校准置信度不足，优先级降级。  
- 按关键路径和依赖深度排序，不按主观感觉排序。  
- 未校准任务放入“待校准队列”，不能占据高优位置。  

---

## 四、类比自恢复架构

Guardian 拉起 Core 前，先确认心跳和快照；  
任务排序前，先确认锚点和当前状态。

WAL + Snapshot 对应：  
- **WAL** = 任务变更日志  
- **Snapshot** = 已验证的任务状态快照  

项目ID看错，等于快照损坏。  
不能基于损坏的快照继续调度，必须先恢复最近正确快照，再重新排序。

---

## 五、落地检查清单

- [ ] 所有任务ID已与源系统核对  
- [ ] 每项任务都有明确完成标准  
- [ ] 每项任务标注了依赖项和超时阈值  
- [ ] 未校准锚点的任务不计入优先级排序  
- [ ] 优先级排序结果带“锚点版本号”，锚点变化时重新生成  

一句话：  
**先花3分钟校准锚点，再排优先级，比先排序再排查1小时快得多。**
