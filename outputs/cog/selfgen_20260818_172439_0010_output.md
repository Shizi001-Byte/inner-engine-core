# 任务类型: cog

## 复盘：基建脚本为什么必须禁用“简化版 SQL”

这次列不匹配，本质不是“不知道要写全列名”，而是：

> 简化版 SQL 把字段映射关系从“显式可查”变成了“隐式靠猜”。  
> 一旦表结构发生过变化，脚本自己无法溯源到正确的列对应关系，于是运行时直接列错位/缺失/类型不匹配。

这正是你锚点里说的：**认知池没空，但溯源链断了**。  
所以“禁用简化版”不能只当一条知识存着，必须变成基建脚本的**硬性检查项**。

---

## 基建脚本 SQL 检查清单

### 一、写之前：先确认 Schema 现状

- [ ] 是否拉取了当前目标表的 `information_schema` / `DESCRIBE`？
- [ ] 是否确认了所有涉及列的 **列名、类型、顺序、默认值、是否可空**？
- [ ] 是否对比过最近一次迁移脚本，确认没有未合并的 schema 变更？
- [ ] 是否知道该表的历史变更记录？如果不能回溯，先补齐溯源链再写脚本。

### 二、写的时候：禁用简化写法

- [ ] 禁止 `SELECT *`，必须显式列出每一列。
- [ ] `INSERT` 必须写列清单：  
  `INSERT INTO t (col_a, col_b, col_c) VALUES (?, ?, ?)`
- [ ] 禁止 `INSERT INTO t VALUES (...)` 这种依赖位置/顺序的写法。
- [ ] `UPDATE` 必须写完整 `WHERE`，不能全表更新。
- [ ] `JOIN` 必须用 `ON` 明确连接键，不用自然连接，不省略关联条件。
- [ ] 涉及类型转换、日期比较、字符串拼接时，显式 `CAST`，不靠数据库隐式转换。
- [ ] 不依赖默认排序、默认值、隐式列顺序等“黑魔法”。

### 三、执行前：加防护栏

- [ ] 脚本必须放在事务中，可回滚。
- [ ] 脚本开头写 pre-check：检查列数、列名、类型，不匹配直接 `FAIL`。
- [ ] 先跑 `EXPLAIN` / `PLAN`，确认不会锁表或超时。
- [ ] 在 staging 环境用真实 schema 副本先跑一遍。
- [ ] 有条件的场景，用 schema diff 工具对比“预期结构”和“实际结构”。

### 四、执行后：验证并留痕

- [ ] 执行后立即检查行数、样本数据、约束、外键完整性。
- [ ] 记录脚本版本、执行时间、before/after schema diff。
- [ ] 把这次变更后的 schema 状态和脚本一起写入知识库/认知池。
- [ ] 更新溯源链：让后续任务能回溯“这个表现在到底有哪些列”。

### 五、流程与认知层面

- [ ] Code Review 时设一道硬关卡：发现“简化版 SQL”直接打回。
- [ ] 每 10 个任务 / 每轮结束，刷新认知缓存，避免旧 schema 认知残留。
- [ ] 新认知（比如这次列不匹配教训）必须在 30 分钟内注入后续相关任务，不能只存不用。
- [ ] 关键基建脚本必须双人复核，不能一个人“图省事”直接上。

---

一句话结论：

> **基建脚本要的是“显式、可审计、可回滚”，不是“短、省、快”。**  
> 所有简化版 SQL，都是给未来的列不匹配埋雷。
