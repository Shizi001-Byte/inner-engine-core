# 任务类型: cog

### 「基建脚本禁用简化版」认知复盘

#### 一、教训复盘

**现象：**  
基建脚本中使用了“看起来能跑”的简化版 SQL，比如：

- `INSERT INTO table VALUES (...)` 不写列名；
- 直接依赖表结构的默认顺序；
- 用 `SELECT *` 或 `UPDATE ... SET` 时省略关键过滤条件；
- 忽略字段类型、长度、默认值、非空约束。

结果目标表结构发生调整后，简化脚本仍然按旧列顺序写入，导致：

- 列不匹配；
- 数据错位；
- 任务静默失败或写入脏数据。

**根因：**  
基建脚本是长期资产，不是一次性查询。简化 SQL 丢掉了 schema 上下文，又缺少校验防线，因此一旦表结构变化就会踩坑。

**结论：**  
基建脚本必须使用**显式、完整、可校验**的 SQL，并纳入自动化检查，禁止“先跑通再说”。

---

#### 二、检查清单

##### 1. 写脚本前

- [ ] 从 schema 管理库导出权威表结构，不凭记忆写 SQL。
- [ ] 对比目标环境 `information_schema.columns`，确认列名、列顺序、数据类型、长度、默认值、非空约束。
- [ ] 确认脚本涉及的所有表、字段、索引均存在且名称正确。

##### 2. 写 SQL 时

- [ ] `INSERT` 必须显式列出列名，禁止 `INSERT INTO t VALUES (...)`。
- [ ] `SELECT` 禁止使用 `*`，必须明确列出所需列。
- [ ] `UPDATE` / `DELETE` 必须带明确的 `WHERE` 条件，且条件列类型匹配。
- [ ] `JOIN` / `ON` 条件列类型一致，避免隐式类型转换。
- [ ] 不使用依赖特定数据库方言的“简化写法”，统一 SQL 规范。
- [ ] 不使用 `SELECT ... INTO` 等易产生列映射错误的语法。

##### 3. 执行前

- [ ] 在测试库执行 `EXPLAIN`，确认执行计划正常。
- [ ] 执行 `SHOW CREATE TABLE` 核对当前表结构。
- [ ] 用 schema-diff 工具对比开发库、测试库、生产库的 schema 差异。
- [ ] 检查迁移脚本版本号，避免重复执行或漏执行。
- [ ] 确认脚本执行账号有对应权限，且不会因权限不足产生部分写入。

##### 4. 执行后

- [ ] 检查错误日志，确认无 warning 或忽略的异常。
- [ ] 验证影响行数符合预期。
- [ ] 抽样查询数据，确认列内容没有错位。
- [ ] 检查外键、唯一索引、非空约束未被破坏。

##### 5. 长期防控

- [ ] 将“简化版 SQL”列为代码评审的禁止项。
- [ ] CI 中加入 SQL lint 和 schema check。
- [ ] 基建脚本变更后，同步更新认知池，并确保新认知在 30 分钟内参与注入。
- [ ] 每 10 个任务或每个迭代结束，刷新一次认知缓存，避免认知池只进不出。

---

**一句话总结：**  
基建脚本不是临时草稿，而是要长期运行的基础设施。**显式列名、完整 schema、自动化校验、执行前后验证**，缺一不可。
