# 任务类型: cog

# "先校准锚点再优化链路"原则提取与优先级排序应用

## 一、案例本质解构

```
事件: 项目ID看错 → 1小时排查链路 → 发现锚点本身错位
本质: 在错误锚点上优化链路 = 炉鼎(实)已歪，再怎么调火候(虚)都是无效劳动
```

**关键损失公式：**
```
浪费成本 = 链路优化深度 × 锚点偏移度 × 时间
本例    = 高深度排查 × ID完全错位 × 1h
若先校准 = 5秒读ID × 偏移度0 × 0min
```

---

## 二、原则提炼

> **先校准锚点再优化链路**

拆解为两个层级：

| 层级 | 对应道德经 | 内涵 | 占时比 |
|------|-----------|------|--------|
| **锚点层（实/炉鼎）** | "虚其心，实其腹" | 校验任务真实ID、目标、约束、前置假设 | ≤5% |
| **链路层（虚/映射）** | "以正治国，以奇用兵" | 在锚点正确前提下优化执行顺序、并行策略 | ≥95% |

**核心判断：链路优化的上限 = 锚点正确性。锚点错位时，链路优化收益归零甚至为负。**

## 三、应用到任务优先级排序

### 3.1 双轴排序法设计

```
         链路收益(高)
              │
     ②优先做   │   ①立即做
   (锚点已验证  │  (锚点已验证
    +高收益)    │   +高收益)
   ───────────┼────────── 锚点可信度
     ③暂缓     │   ④禁止做
   (锚点未验证  │  (锚点未验证
    +低收益)    │   +高收益≠陷阱)
              │
         链路收益(低)
```

**关键规则：**
- **右下象限④是危险区**：锚点未验证但链路收益看起来高 → 这正是"项目ID看错还猛排查"的陷阱
- **排序铁律：锚点可信度 > 链路收益**，必须先从右半区移到左半区再谈优先级

### 3.2 锚点校验清单（5%时间预算内完成）

每条任务进入排序前必须通过以下校验：

| 校验项 | 具体内容 | 案例对照 |
|--------|---------|---------|
| **ID校验** | 项目ID/任务ID/接口ID是否与上下文一致 | 本例：ID看错即此层失败 |
| **目标校验** | 任务真实目标 vs 字面描述是否一致 | 排查目标是否匹配实际故障项 |
| **约束校验** | timeout/资源上限/前置依赖是否确认 | turbo用300s，A模型用600s |
| **边界校验** | 任务边界条件是否仍有效 | 排查范围是否已变更 |

### 3.3 排序执行流程

```
任务入队
  │
  ▼
┌─────────────────────────┐
│ Step1: 锚点校验 (≤5%时间) │
│  ├─ 4项全通过 → 标记[锚点可信]│
│  └─ 任一失败 → 降级，不排序  │
└────────────┬────────────┘
             ▼
┌─────────────────────────┐
│ Step2: 链路收益评估       │
│  按紧急度×影响面×可逆性   │
│  计算链路优化预期收益     │
└────────────┬────────────┘
             ▼
┌─────────────────────────┐
│ Step3: 双轴定位排序       │
│  ①锚点可信+高收益 → 立即执行│
│  ②锚点可信+低收益 → 队列等待│
│  ④锚点不可信+高收益→校验门拦截│
│  ③锚点不可信+低收益→暂缓   │
└─────────────────────────┘
```

## 四、自动化拆解方法论

### 4.1 锚点校验门（Gate机制）

```python
def anchor_validation_gate(task):
    """
    锚点校验门：未通过则任务不进入排序池
    对应道德经'不知常，妄作，凶'
    """
    checks = {
        'id_match': verify_task_id(task.id, task.context),
        'goal_alignment': verify_goal_vs_literal(task.title, task.actual_goal),
        'constraint_confirmed': verify_timeout_and_resource(task),
        'boundary_valid': verify_boundary_conditions(task)
    }
    
    if not all(checks.values()):
        return {
            'status': 'GATE_BLOCKED',
            'blocked_reason': [k for k, v in checks.items() if not v],
            'action': '降级至锚点修复队列，禁止链路优化',
            'estimated_waste_if_skipped': task.complexity * 3600  # 秒
        }
    return {'status': 'ANCHOR_CONFIRMED', 'proceed_to_sort': True}
```

### 4.2 链路优化的触发条件

```
IF 锚点校验 == PASS:
    进入双轴排序，按链路收益分配资源
ELSE:
    禁止链路优化，返回锚点修复
    （对应"以实养虚"——实未立则虚无以生）
```

## 五、跨领域验证

| 领域 | 锚点（实） | 链路（虚） | 失败案例 | 本原则应用 |
|------|-----------|-----------|---------|-----------|
| **运维排查** | 故障ID/告警源 | 排查路径 | ID看错排查1h | 先校验告警ID真实性，再决定排查深度 |
| **模型调用** | API endpoint+版本 | 调用参数优化 | 调错endpoint还调参 | 先确认endpoint版本，再优化prompt |
| **代码重构** | 需求真实意图 | 重构方案设计 | 字面理解需求就重构 | 先与需求方对齐目标，再设计架构 |
| **任务调度** | 任务真实优先级 | 执行顺序优化 | 优先级判断基于过时信息 | 先刷新优先级锚点，再排执行序 |

## 六、总结口诀

```
锚点不正，链路无功；
五秒校验，一时空转。
先实后虚，方舟正序；
ID先行，优化后随。
```

**一句话可执行结论：** 每次开始任务排序前，强制插入一个≤5%时间预算的"锚点校验门"，4项校验全通过才进入链路优化排序，任何一项未通过则降级至修复队列——这是用5秒换1小时的最高杠杆操作。
