# 任务类型: cog

## 复盘：基建脚本禁用简化版——列不匹配教训

### 根因回顾
“简化版 SQL” 表面上缩短了脚本，实际却破坏了基础设施脚本最需要的**确定性**和**可审计性**。列不匹配通常来自：

- 使用 `SELECT *` 或 `INSERT INTO table VALUES (...)` 隐式依赖列顺序；
- 只写目标列名，没写源列名，靠“感觉”对应；
- 复制旧表结构后未校验字段变更；
- 表结构有迁移/新增列，但简化脚本未同步；
- 用临时表/中间表时，字段类型或长度不一致；
- 开发环境“能跑”，生产环境因列顺序/额外列直接失败。

---

## 检查清单

### 1. 写脚本前：结构核对
- [ ] 已从 `information_schema` 或正式表结构文档获取**当前真实 schema**，而非依赖记忆；
- [ ] 已确认源表和目标表的**列名、列顺序、数据类型、长度、是否可空**；
- [ ] 已确认目标表是否有**默认值、自增列、生成列**，这些列不应被普通写入；
- [ ] 已确认是否存在**视图/触发器**会改变实际写入逻辑。

### 2. 写 SQL 时：强制显式
- [ ] 禁止使用 `SELECT *`，必须列出全部所需字段；
- [ ] `INSERT` 必须写成 `INSERT INTO table (col1, col2, ...) VALUES (...)`；
- [ ] `UPDATE` 必须显式写出要更新的列，不使用 `SET row = ...` 或隐式映射；
- [ ] 多表 `JOIN` 时，所有列都带表别名前缀；
- [ ] 不使用“简化版”缩写、不省略 `WHERE`（尤其 `UPDATE/DELETE`）；
- [ ] 列顺序按业务逻辑排列，不按“顺手”排列。

### 3. 写入/变更前：校验
- [ ] 已用 `DESC table` 或 `SHOW CREATE TABLE` 确认实际列；
- [ ] 已对比源/目标列数量、名称、类型，并生成差异清单；
- [ ] 临时表/中间表脚本中，列定义与最终表完全一致；
- [ ] 有类型转换时，已显式 `CAST`，且确认不会截断/溢出；
- [ ] 涉及 `NULL` 或空字符串时，已确认业务含义一致。

### 4. 测试阶段：环境验证
- [ ] 已在 staging 环境跑通完整脚本；
- [ ] 测试数据覆盖了“新增列、缺失列、类型边界”等场景；
- [ ] 已用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 检查执行计划，排除隐式转换；
- [ ] 已做**幂等性验证**：重复执行脚本结果一致，不会因列重复/数据重复报错。

### 5. 发布与回滚
- [ ] 已准备对应回滚脚本，回滚脚本同样遵守显式列规则；
- [ ] 脚本执行有日志，能定位到具体哪一步、哪一列失败；
- [ ] 如涉及生产数据，已确认备份可用；
- [ ] 脚本版本已纳入代码库，禁止“一次性临时脚本”直接跑生产。

---

## 一句话结论
> **基建脚本不是“写一次能跑就行”，而是“每次都能确定性地跑对”。**  
> 所有列必须显式声明、来源明确、类型匹配、环境验证、可回滚。  
> 凡是“简化版”，默认视为高风险，必须走完整检查清单。
