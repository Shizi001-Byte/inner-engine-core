# 任务类型: cog

基于“算力代谢即生命”与“赛博玄幻硬核架构”的既定认知锚定，我们将数据库的表结构视为修炼者的“算力经脉”，SQL脚本的字段映射则是“灵气传输协议”。

在此次“基建脚本禁用简化版”事故中，简化版SQL为了追求短期的执行效率，擅自绕过了完整的字段校验，导致高维信息流在注入低维存储池时发生“列不匹配”（即经脉逆乱、灵气无法液化），最终引发算力代谢系统的局部坏死。

为防止系统再次因“走捷径”而产生数据畸变，特拟定以下**《赛博经脉完整性检查清单》**：

### 📂 阶段一：源端灵气显化（表结构定义检查）
- [ ] **元数据对齐**：源表与目标表的列名、数据类型在“算力阵法”中是否绝对同频？（禁止隐式类型转化，如将高维浮点灵气强行灌入整型经脉）。
- [ ] **时空锚点校验**：时间戳、主键ID等具有时序特性的列，是否在目标表中预留了对应的高维坐标位？
- [ ] **冗余列截断警告**：若目标表列数少于源表，是否在脚本中显式指定了提取的列名，而非使用通配符（`SELECT *`）盲目吞噬所有灵气？

### 📜 阶段二：符文阵法编译（SQL脚本编写检查）
- [ ] **禁用全量透传**：严禁在简化版基建脚本中使用 `INSERT INTO target_table SELECT * FROM source_table`。必须采用“列名对仗”模式：`INSERT INTO t(a,b,c) SELECT a,b,c FROM s`。
- [ ] **空值（虚无）隔离**：对于非空字段（如生命核心标识符），是否在SQL中加入了 `COALESCE` 或默认值注入，防止“虚无”污染算力网络？
- [ ] **简化版边界隔离**：若必须使用简化版脚本，是否在脚本头部硬编码了 `SET ANSI_NULLS ON` 与 `SET ANSI_PADDING ON` 等环境基线，确保底层运行时环境的一致性？

### 🏗️ 阶段三：基建阵眼激活（执行与熔断机制检查）
- [ ] **试运行（引气入体）沙盒**：所有基建脚本在注入生产网络前，是否在“镜像须弥”（UAT/Staging环境）中完成了至少一次完整的算力代谢闭环？
- [ ] **事务回滚（护体罡气）**：脚本是否包裹在显式的事务块（`BEGIN TRAN / COMMIT / ROLLBACK`）中？当列不匹配报错时，能否瞬间切断连接，保护既有算力池不被半截数据污染？
- [ ] **列不匹配熔断符**：是否在ORM映射层或ETL流水线中配置了Schema校验拦截器？一旦探测到源端与目标端列结构存在Diff，立即阻断SQL执行并报警。

### 🔮 阶段四：算力代谢运维（事后复盘与监控）
- [ ] **经脉拓印留存**：每次执行基建脚本前后，是否自动将当前数据库的表结构（Schema）导出为版本化日志，以便快速回溯是哪一次“功法修改”导致了列畸变？
- [ ] **异常灵气日志**：对于因列不匹配产生的报错，是否不仅记录了SQL错误码，还抓取了报错时刻的完整数据包切片，以供赛博医师（DBA）进行病理分析？

**核心训诫：** 在基于信息网络的算力代谢系统中，没有任何一次“简化”是无代价的。跳过结构校验的捷径，必然导致数据畸变与系统走火入魔。
