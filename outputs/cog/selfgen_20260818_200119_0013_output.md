# 任务类型: cog

## 复盘：基建脚本禁用简化版 SQL

### 结论

“基建脚本禁用简化版 SQL”不是保守，而是必须。

简化版 SQL 常见的写法：

- `SELECT *`
- `INSERT INTO t VALUES (...)`（不写列名）
- `INSERT INTO t SELECT * FROM s`
- `CREATE TABLE AS SELECT` 后不检查 schema
- `MERGE/JOIN` 不写显式 `ON` 条件
- `ORDER BY 1,2` 位置排序
- 计算字段不写别名，或别名与目标列不一致

这些写法会让脚本隐式依赖列顺序、列数量、列类型，一旦源表或目标表发生 schema 变化，就会出现**列不匹配**。如果后处理是多线程 API 调用后的串行处理，还会叠加“旧数据覆盖新数据”的竞态问题。

---

## 检查清单

### A. 编写基建脚本前

- [ ] 确认源表和目标表的当前 schema：列名、列顺序、数据类型、是否可空、默认值
- [ ] 确认当前环境（dev/staging/prod）的 schema 与预期一致，不能靠“本地能跑”判断
- [ ] 若脚本涉及 API 调用，预设合理 timeout：B 模型 turbo 用 300 秒，A 模型用 600 秒
- [ ] 确认任务是否可重复执行：重复跑不能导致数据重复或旧数据覆盖新数据

### B. SQL 编写时

- [ ] 禁用 `SELECT *`，必须逐个列出所需列名
- [ ] 禁用 `INSERT INTO t VALUES (...)`，必须写成：

```sql
INSERT INTO t (col_a, col_b, col_c)
VALUES (:val_a, :val_b, :val_c);
```

- [ ] 禁用 `INSERT INTO t SELECT * FROM s`，必须显式映射：

```sql
INSERT INTO t (col_a, col_b, col_c)
SELECT s.col_a, s.col_b, s.col_c
FROM s;
```

- [ ] 使用 `CREATE TABLE AS SELECT` 时，必须显式指定列名或随后做 schema 校验
- [ ] 使用 `JOIN` / `MERGE` 时，必须显式写 `ON` 条件，禁止无条件下拉
- [ ] 禁止使用 `ORDER BY 1,2` 等位置排序，必须使用列名
- [ ] `CASE`、`COALESCE`、`CAST` 等生成的新列，必须给与目标列一致的别名

### C. 上线前检查

- [ ] 使用 `information_schema` 对比源表和目标表的列名、列顺序、数据类型
- [ ] 确认源表新增列时，目标表是否同步更新；目标表新增列时，源数据是否提供默认值
- [ ] 在 staging 环境用代表性小数据跑通，并验证列映射正确
- [ ] 校验脚本是否幂等：重复执行结果一致，不会因列错位产生脏数据
- [ ] 检查后处理逻辑是否带批次号/时间戳，避免乱序覆盖

### D. 运行中与运行后

- [ ] 开启严格模式，例如 Hive 的 `mapred.mode=strict`，Spark 的 schema 校验
- [ ] 记录运行前后的 schema 版本，检测 schema drift
- [ ] 运行后校验目标表行数、关键列分布、抽样数据，确认没有列错位
- [ ] 若发现列不匹配，立即停止后续任务，回滚到备份或重建目标表

### E. 认知池维护

- [ ] 本次复盘结论在 30 分钟内注入认知池
- [ ] 每 10 个任务或每轮结束，刷新认知缓存，确保新认知参与后续调度
- [ ] 后续遇到“简化版 SQL”类写法，直接触发拦截，要求改为显式列名版本

---

### 一句话记住

> 基建脚本里，SQL 越“简化”，事故越“复杂”。  
> 所有列名、顺序、类型、join 条件必须显式声明，运行前必须做 schema 校验。
