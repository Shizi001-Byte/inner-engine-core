# 任务类型: cog

## 复盘：基建脚本禁用简化版——列不匹配教训

**失败本质：**  
简化版 SQL 为了省事，省略显式列名、依赖 `SELECT *` 或 `VALUES` 顺序来“隐式匹配”。一旦表结构变更（加列、删列、调整顺序、改类型），列映射就静默错位，轻则数据写错列，重则迁移失败、数据污染。基建脚本不是一次性草稿，而是需要长期可维护、可审计、可回滚的工程产物，**禁止用“手快”换“正确性”**。

---

## 检查清单

### 1. 显式列名，禁止隐式映射

- [ ] 所有 `INSERT` 必须显式写目标列名。  
  - ❌ 禁用：`INSERT INTO t VALUES (1, 'a');`  
  - ✅ 启用：`INSERT INTO t (id, name) VALUES (1, 'a');`

- [ ] 所有 `SELECT` 进入基建脚本时，禁止 `SELECT *`。  
  - ❌ 禁用：`INSERT INTO t2 SELECT * FROM t1;`  
  - ✅ 启用：`INSERT INTO t2 (col_a, col_b) SELECT col_a, col_b FROM t1;`

- [ ] `INSERT ... SELECT` 两侧列数、列序、列类型必须逐一核对。

- [ ] 使用 `UPDATE` / `MERGE` / `UPSERT` 时，赋值列表必须显式列出列名，禁止按位置匹配。

---

### 2. 表结构变更后必须重跑依赖检查

- [ ] 任何 `ALTER TABLE` 增加/删除/修改列后，重新检查所有引用该表的脚本。

- [ ] 不要假设旧脚本仍然有效；用 `DESCRIBE` / `SHOW CREATE TABLE` 重新确认最新结构。

- [ ] 加列后，检查所有 `SELECT *` 下游任务是否受影响；如果无法避免，必须改为显式列清单。

- [ ] 删除列或重命名列后，全局搜索旧列名，避免运行时才暴露。

---

### 3. 类型、约束、默认值严格匹配

- [ ] 核对每列的数据类型、长度、精度、是否可空、默认值。

- [ ] 注意 `INT` vs `BIGINT`、`VARCHAR(255)` vs `TEXT`、`DATETIME` vs `TIMESTAMP` 等容易忽略的差异。

- [ ] 有隐式转换风险时，显式使用 `CAST` / `CONVERT`。

- [ ] 注意数据库非严格模式：例如 MySQL 可能把超长字符串截断成 warning，而不是报错；必须开启严格模式或增加结果校验。

- [ ] 涉及字符集、collation、时区时，先统一环境再执行。

---

### 4. 版本化管理，禁止覆盖修改

- [ ] 基建脚本必须有版本号、日期、目的、影响表清单。

- [ ] 已执行过的脚本不允许原地修改；变更必须新增增量脚本。

- [ ] 执行前做 schema-diff，确认目标库实际结构符合脚本预期。

- [ ] 维护一份“基线 schema + 增量脚本”的完整链路，保证可从零重建。

---

### 5. 预发环境验证，不能“能跑通就算成功”

- [ ] 先在测试库/临时库完整执行脚本，用 `DESCRIBE` / `SHOW CREATE TABLE` 验证列名。

- [ ] 使用 `EXPLAIN` 检查 SQL 是否可执行、是否走预期索引。

- [ ] 准备一张“列映射表”：源表列 → 目标表列，逐列人工核对。

- [ ] 执行后做数据校验：行数、求和、`COUNT(DISTINCT)`、抽样值对比，确保数据没有错位。

---

### 6. 自动化与评审

- [ ] 基建脚本必须经过代码评审，重点检查列映射和类型匹配。

- [ ] CI 中加入 SQL 静态检查工具（SQLFluff、sqlcheck 等）和 schema-diff 工具。

- [ ] 关键迁移脚本要有自动化测试夹具：固定输入、预期输出，跑完后断言结果。

- [ ] 禁止将手工临时 SQL 直接升级为基建脚本，必须补上列名和校验逻辑。

---

### 7. 回滚与容错

- [ ] 每个脚本必须有回滚方案；事务内执行，失败自动回滚。

- [ ] 对于不支持事务 DDL 的数据库，提前备份表结构和数据。

- [ ] 脚本尽量幂等：如 `ADD COLUMN IF NOT EXISTS`、`CREATE TABLE IF NOT EXISTS`；但幂等不能替代列匹配校验。

- [ ] 失败后禁止盲目重试；先检查错误日志，确认列映射是否正确。

---

## 认知沉淀

“基建脚本禁用简化版”必须作为强制规则进入认知池，并在每次基建脚本评审时主动弹出调用。每 10 个任务或每轮调度结束，刷新该认知的活跃度，确保它真正参与决策，而不是躺在认知池里变成静态档案。  
**一句话：基建脚本可以短，但绝不能“简”到丢失列名；显式、可校验、可回滚，才是底线。**
