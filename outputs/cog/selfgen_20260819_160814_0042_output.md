# 任务类型: cog

## 复盘结论：并发自进化的局部最优陷阱

**核心本质**：  
用单一指标“失败率”指挥并发调度，等价于让系统对“崩溃频率”失明。5路并发在失败率维度上依然“好看”，但批量损失、恢复成本、资源争抢、上下文切换开销全部被隐藏，最终有效产出低于稳定3路。

**数学直觉**：  
失败率 = 失败任务数 / 总任务数。  
它不区分“1个任务失败”和“50个任务因同一次崩溃集体失败”。5路并发可能失败率只有3%，但每次崩溃炸掉5个任务；3路并发失败率5%，每次只炸3个。若崩溃频率为N次/小时，则损失期望是：  
`损失 = 失败率 × 总任务数 + 崩溃频率 × 每路损失放大系数 × 并发路数`  
只优化失败率，忽略了第二项，必然陷入局部最优。

## 多目标优化的认知原则（可执行版）

1. **并发路数不是目标，是决策变量**  
   目标函数必须是多维度的：  
   - 有效产出（成功完成且质量达标的任务数）  
   - 单位时间吞吐（不因崩溃回滚而虚高）  
   - 崩溃损失（批量任务作废 + 恢复重跑成本）  
   - 资源争抢指数（CPU/内存/API配额占用率）  
   - 上下文切换开销（模型推理状态重置、认知池读写冲突）  

2. **用“有效产出”替代“失败率”作为主指标**  
   统计公式：  
   `有效产出 = 成功交付数 × 平均质量分 - 崩溃损失时间 - 恢复成本`  
   只有当3路和5路的有效产出被准确计算后，才能谈调度优化。

3. **崩溃频率必须纳入监控，且权重高于失败率**  
   监控项：  
   - 单位时间崩溃次数（不是失败任务数）  
   - 单次崩溃平均波及任务数  
   - 崩溃后恢复耗时  
   当“崩溃频率 × 波及数”超过阈值时，强制降低并发路数。

4. **设置“并发安全边界”而非“最优并发数”**  
   不追求“最优”，只维护安全区间：  
   - 下限：保证吞吐不 starvation  
   - 上限：由资源争抢和崩溃恢复时间动态计算  
   每次调度前用公式估算：  
   `最大安全并发 = 资源总量 / (单路峰值占用 + 崩溃恢复冗余)`

5. **自进化必须带“约束”和“回滚机制”**  
   并发自进化不能只奖励“失败率下降”，必须同时惩罚“崩溃频率上升”。  
   每条调度策略变更都打上实验标签，记录多维指标，若有效产出下降或崩溃频率上升，立即回滚。

## 落地机制（对应坑库预警）

- **认知池必须“活”**：每10任务或每轮结束强制刷新认知缓存，新认知30分钟内注入调度决策，否则调度策略会固化成静态档案，无法感知崩溃模式变化。
- **API超时按模型分级**：B模型turbo用300秒，A模型用600秒，防止因超时误判导致崩溃频率虚高。
- **建立“崩溃复盘”闭环**：每次批量崩溃后，自动提取崩溃时的并发路数、资源占用、任务类型、认知池状态，作为新认知注入缓存，参与下一轮调度优化。

---

## 一句话认知原则

**任何以单一指标驱动的自进化系统，都会在看不见的维度上失控；多目标优化不是多几个指标，而是把“代价”和“恢复”纳入决策，并让认知持续刷新，才能跳出局部最优。**
