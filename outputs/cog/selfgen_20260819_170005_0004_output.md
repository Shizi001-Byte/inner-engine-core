# 任务类型: cog

基于 Guardian/Core 与 WAL+Snapshot 架构，推演结论如下：

## 一、决策串行、执行并发的分层原则

1. **单一决策点（脑）**  
   所有状态变更、任务调度、资源分配、故障恢复决策，必须由 Core 内的决策模块**串行处理**，形成全局有序事件流。每个决策先写 WAL，再下发命令或变更内存状态，保证原子性。

2. **并发执行体（体）**  
   具体计算、I/O、网络、数据处理等任务由多个 Worker **并发执行**。Worker 无状态，只接收命令、返回结果，不直接修改核心持久化状态。

3. **命令/结果解耦**  
   决策层通过命令队列向下层下发任务；执行层通过结果队列上报。执行层不得自行决策或绕过 WAL 修改状态。

4. **持久化与恢复**  
   决策层定期生成 Snapshot，WAL 记录全部决策。崩溃后 Guardian 拉起 Core，Core 先加载 Snapshot，再顺序重放 WAL，恢复至最近一致断点。

5. **优化边界**  
   性能优化只能发生在执行层（增加并发、批量处理、缓存、异步化）或决策层内部（命令合并、索引加速）。**禁止将决策权分散到多个执行节点，禁止让执行层拥有状态或自裁决能力。**

## 二、为什么引擎优化不能破坏脑体分离

- **保证 WAL 顺序性**  
  WAL 必须按决策顺序追加，才能作为崩溃恢复的唯一权威依据。若优化把决策并发化，状态变更失去全局顺序，恢复时无法重放，导致数据分裂或丢失。

- **维护 Guardian/Core 心跳语义**  
  Guardian 通过心跳检测 Core 是否存活，并在 Core 死亡时拉起新 Core。只有 Core 是唯一决策者时，Guardian 才能明确“脑”的状态。若决策下沉到执行层，Guardian 无法判断是否存在多个“脑”，可能引发脑裂、重复决策或误拉起。

- **避免引入分布式共识成本**  
  决策串行让系统无需选举、锁、分布式事务协调器。破坏串行意味着必须处理并发冲突、回滚和一致性协议，复杂度远超优化收益。

- **可观测性与可调试性**  
  串行决策使系统行为可回放、可审计。一旦优化破坏串行，故障排查、测试和线上问题定位成本急剧上升。

## 三、三个应用场景

### 1. 分布式任务调度引擎
- **决策串行**：调度器（Core）串行处理任务提交、资源分配、优先级抢占，每个决策写 WAL。
- **执行并发**：多个 Worker 并发执行任务，执行结果异步回传。
- **优化方式**：批量拉取任务、预取任务上下文、按节点分片缓存。  
  **不可破坏点**：Worker 不得自行领取任务或调整优先级，否则崩溃后无法恢复调度状态。

### 2. 数据库事务处理引擎
- **决策串行**：事务管理器（脑）串行决定 Commit/Abort，记录 WAL（redo/undo）。
- **执行并发**：存储引擎并发执行写入、刷盘、索引更新、数据压缩。
- **优化方式**：Group Commit 合并 fsync、并行预写 WAL 缓冲区、多线程刷脏页。  
  **不可破坏点**：事务提交顺序必须由单一决策点维持，否则恢复时无法确定持久化边界。

### 3. 实时推荐/广告系统
- **决策串行**：策略引擎（脑）串行生成推荐列表或竞价决策，每次决策写入日志/Snapshot。
- **执行并发**：特征计算、模型推理、候选召回等环节并行执行，输出中间结果。
- **优化方式**：特征缓存、模型分片推理、异步日志。  
  **不可破坏点**：最终决策必须由串行器统一输出，保证用户行为轨迹可回放，防止并发竞态导致预算超支或推荐不一致。

**结论**：引擎优化的正确方向是**增强执行并发度、降低单次决策时延**，而不是改变决策模型。保持“决策串行、执行并发”的脑体分离，才能同时获得性能提升与崩溃自恢复能力。
