# 任务类型: cog

基于您提供的核心认知锚定，直接跳过基础论证，从“认知质检SOP”的视角对“不知盲”幻觉及“基建脚本禁用简化版”导致列不匹配的踩坑事件进行反向推演。

---

### 一、 踩坑背景：引擎“不知盲”幻觉与简化版SQL之殇
**病理分析**：在引擎基建阶段，为了快速跑通链路，开发/运维人员主观剥离了完整版SQL中的冗余字段或复杂逻辑，使用了“简化版”脚本。引擎在执行时，由于底层缺乏强类型校验或未执行显式映射，导致源端与目标端列数量、顺序或数据类型发生错位。引擎并未报错，而是“静默吸收”了错误数据（如将B列数据写入A列），最终输出看似正常实则完全错乱的结果，形成“不知盲”幻觉——**不知道自己不知道，且不知道自己已错**。

---

### 二、 反向推演：3条可复用的操作铁律及验证方法

#### 铁律一：显式映射绝对律（禁止隐式依赖）
**推演来源**：简化版SQL常使用 `SELECT *` 或省略目标表的列名（如 `INSERT INTO t1 SELECT * FROM t2`），一旦源表增删字段或顺序变动，引擎按顺序盲配，必然导致列错位。
*   **操作铁律**：在任何基建脚本中，严禁使用隐式列映射。`SELECT` 必须显式列出字段名，`INSERT` 必须显式指定目标列名，彻底切断对表结构默认顺序的依赖。
*   **验证方法（质检SOP）**：
    *   **静态扫描**：在CI/CD流水线中加入AST（抽象语法树）解析扫描器，拦截所有包含 `SELECT *` 或未带 `INTO col_list` 的 `INSERT` 语句。
    *   **结构比对**：执行前运行预检脚本，断言 `SELECT` 提取的列名集合与 `INSERT` 指定的列名集合严格等于（不仅数量相等，且名称完全一致）。

#### 铁律二：等价校验阻断律（禁止未经对齐的“降维”）
**推演来源**：开发人员在简化脚本时，仅凭主观认知剥离了自认为“无用”的字段，但未在引擎流转的上下游节点进行同步裁剪或标记，导致下游节点按“全量预期”接收“简化输入”，产生幻觉。
*   **操作铁律**：任何“简化版”基建脚本的启用或禁用，必须进行全链路的契约对齐。简化操作不能只改单一节点，必须同步更新数据契约，并在引擎入口处打上“非全量字段”的显性标签。
*   **验证方法（质检SOP）**：
    *   **元数据注入测试**：在引擎入口注入一个包含“超纲字段”或“乱序字段”的测试数据包，验证引擎是否能抛出“字段不匹配”异常。若静默通过，则判定存在“不知盲”风险。
    *   **Schema Diff 拦截**：在脚本部署前，对比简化版脚本的输出Schema与完整版脚本的输出Schema，差异必须经过人工签署的“降级许可”，否则阻断发布。

#### 铁律三：失败显性化律（破局“不知盲”幻觉）
**推演来源**：引擎在遇到列不匹配时，由于开启了宽松模式（如MySQL的非严格模式、某些ETL工具的忽略错误配置），选择了自动补NULL或隐式类型转换，掩盖了致命错误。
*   **操作铁律**：基建引擎必须运行在“零容忍”模式下。任何列不匹配、类型不兼容必须导致硬失败，严禁引擎进行任何形式的“智能猜测”或“静默修复”。
*   **验证方法（质检SOP）**：
    *   **混沌注入**：定期在测试环境中故意制造列错位（如将String类型数据注入Int列），验证引擎是否立即抛出异常并停止运行。若任务依然跑通并产出脏数据，则SOP判定不合格。
    *   **行数与字段空值率双向断言**：任务执行后，不仅校验行数，还需对核心字段的空值率进行断言。若某原本应为0%空值的字段，在简化版脚本运行后突然出现大量空值（因错位写入NULL），立即触发熔断告警。

### 三、 复盘检查清单（针对“基建脚本禁用简化版”认知）

请在基建脚本（尤其是涉及表结构变更、数据搬运的ETL脚本）上线前，逐项勾选：

**【阶段一：编写与评审环节】**
- [ ] 1. 禁用通配符：脚本中是否完全消灭了 `SELECT *` 或 `SELECT t.*`？
- [ ] 2. 显式对齐：`INSERT` 语句是否同时显式声明了源字段和目标字段列表？
- [ ] 3. 顺序无关性：重构或简化SQL后，是否验证了字段逻辑不依赖物理存储顺序？
- [ ] 4. 类型强一致：简化逻辑中是否去除了所有隐式类型转换（如 String 转 Int 时不使用 `CAST` 就直接拼接）？

**【阶段二：测试与验证环节】**
- [ ] 5. 契约一致性：当前简化版脚本的输出字段集合，是否与下游消费者预期的Schema 100%一致？
- [ ] 6. 异常注入测试：故意删减源表的一个字段，引擎是否报错阻断？（若不报错，说明引擎处于“不知盲”状态）
- [ ] 7. 脏数据抽样：对简化版脚本跑出的数据，是否进行了前100行的逐列人工/DQC抽样核对，确认无数据串列？

**【阶段三：上线与监控环节】**
- [ ] 8. 严格模式开启：数据库/JDBC连接是否配置了 `STRICT_TRANS_TABLES` 或等效的严格校验模式？
- [ ] 9. 熔断阈值：是否配置了字段级的数据质量校验（如某字段非空率低于99%即判定任务失败）？
- [ ] 10. 变更追溯：本次“简化版”脚本的禁用/启用，是否在代码库中留下了明确的废弃标记和替代方案说明？
