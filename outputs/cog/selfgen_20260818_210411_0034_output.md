# 任务类型: cog

从认知质检 SOP 角度看，链式推演引擎最典型的坑不是“单轮答错”，而是三类系统性问题：**认知不流动、超时不设限、失败就重来**。基于你给的坑库和引擎设计，沉淀出 3 条可复用铁律：

---

## 铁律一：认知池必须“活水注入”，锚定只读，但新认知不能只进不出

**坑：**  
认知池 1700+ 条，但新认知从不注入任务，也不参与调度，最终变成静态档案库。  
链式推演虽然强调“认知锚定只读”，但如果整个认知池也变成只读，推演就会失去对新信息的感知能力。

**验证方法：**

- 给认知池增加字段：`created_at`、`last_injected_at`、`inject_count`。
- 每 10 个任务或每轮结束时执行检查：

```sql
SELECT count(*)
FROM cognition_pool
WHERE created_at >= now() - interval '30 minutes'
  AND last_injected_at IS NULL;
```

结果必须为 `0`，否则说明有 30 分钟内产生的新认知未参与注入。

- 监控“认知新鲜度”指标：

```text
近30分钟新认知注入率 = 已注入新认知数 / 近30分钟新认知总数
```

目标为 100%，低于 100% 立即告警。

- 额外监控“池增长 vs 活跃注入”：如果池容量持续上升，但 `inject_count` 长期为 0，直接判定认知池退化为静态档案。

---

## 铁律二：超时预算必须在配置注册中心分级预设，运行期只读取、不等待

**坑：**  
API 调用超时导致任务未在规定时间内返回。  
不同模型能力不同，不能共用一套超时策略：B 模型 turbo 用 300 秒，A 模型用 600 秒。  
如果超时参数散落在代码里，或者运行期临时决定，链式推演就会卡死在某一步。

**验证方法：**

- 配置注册中心必须为每个推演步骤定义 `timeout_ms` 字段，且默认值满足：

```text
B turbo: 300000 ms
A model: 600000 ms
```

缺少该字段，启动阶段直接失败，不允许运行。

- 故障注入测试：  
  mock 一个 B 模型接口，令其 sleep 301 秒，断言系统在 300 秒附近触发超时，并进入预设回退路径；A 模型同理，sleep 601 秒验证。

- 运行期输出每轮耗时报表：  
  若某模型 p99 耗时达到预算的 80%，触发预警，而不是等到超时后再被动处理。

---

## 铁律三：失败只允许沿显式回退边回退，禁止整链重来

**坑：**  
某一轮失败后，如果系统没有显式回退边，只能清空整条链从第 1 轮重跑，成本放大 5 倍，且丢失前面轮次已经产出的有效中间结论。

**验证方法：**

- 在配置注册中心保存回退拓扑，例如：

```json
{
  "round3": {
    "on_timeout": "round2",
    "on_invalid_output": "round1"
  },
  "round5": {
    "on_invalid_output": "round3"
  }
}
```

启动时校验回退拓扑必须是 DAG，禁止出现环。

- 故障注入矩阵测试：  
  对每一轮分别注入 `timeout` 和 `invalid_output`，断言系统跳到预设回退轮，而不是跳到 `round1`。

- 监控两个关键计数：

```text
full_chain_retry_count = 0
fallback_edge_hit_count = 故障注入次数
```

只要出现一次 `full_chain_retry_count > 0`，视为 P0 事故，说明回退边缺失或配置失效。

---

## 总结

链式推演引擎的质检 SOP，核心不是看单条认知对不对，而是看：

1. 认知有没有被“用起来”；
2. 超时有没有“兜底”；
3. 失败有没有“就近回退”。

这三条铁律可复用，且每一条都能用配置、监控、故障注入来验证。
