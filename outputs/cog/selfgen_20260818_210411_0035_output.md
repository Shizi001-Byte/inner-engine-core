# 任务类型: cog

在“5 轮递进 + 认知锚定只读 + 配置注册中心 + 回退边”的链式推演引擎设计基础上，“决策串行、执行并发”的分层原则可以这样理解：

> **决策是脑，执行是体；脑必须一步步想，体可以多只手同时干。  
> 引擎优化只能优化“体”的干活方式，不能改变“脑”的思考顺序。**

---

## 一、分层原则

| 层 | 模式 | 职责 | 优化边界 |
|---|---|---|---|
| 决策层（脑） | 串行 | 5 轮递进；上一轮输出作为下一轮主输入；认知锚定只读；读取配置注册中心 | 不允许并行、跳步、预生成后续决策 |
| 执行层（体） | 并发 | API 调用、检索、工具执行、候选生成、校验、聚合 | 可并行、可超时、可重试、可回退 |
| 连接层（契约） | 稳定 | 决策层下发“任务 + 上下文”，执行层返回“结构化结果 + 状态” | 只做协议转换，不修改决策逻辑 |

核心约束：

- 决策层**必须串行**：因为第 2 轮依赖第 1 轮输出，第 3 轮依赖第 2 轮输出。
- 执行层**可以并发**：同一轮决策下的多个独立调用可以同时跑。
- 失败时**沿回退边回退**，不是整链重来。
- 配置注册中心是全局读取点；超时、并发度、回退边等参数统一从配置中心读取。

---

## 二、为什么引擎优化不能破坏“脑体分离”？

### 1. 串行决策是正确性约束

如果为了“优化”把决策轮次并行化，例如同时推演第 3 轮和第 4 轮，那么第 4 轮可能基于错误的中间结果。

> 例：第 2 轮决定“需要补充法律审查”，第 3 轮原本应该等待这个结论；如果并行提前生成第 3 轮，就可能遗漏法律审查要求。

所以：**决策轮次之间必须保持严格依赖，不能为了速度牺牲逻辑链完整性。**

### 2. 并发执行才是性能来源

真正耗时的往往不是“思考”，而是“干活”：

- 多个 API 调用；
- 多个文档检索；
- 多个模型候选生成；
- 多个校验规则执行。

这些操作天然可以并行。  
引擎优化应该把精力放在：

- 异步调用；
- 批量聚合；
- 超时控制；
- 结果缓存；
- 失败重试。

例如：

- B 类 turbo 模型超时设为 300 秒；
- A 类模型超时设为 600 秒。

这是执行层优化，不是决策层优化。

### 3. 失败隔离要求边界清晰

脑体分离后，执行层失败不会污染决策状态。

- 执行失败 → 执行层返回错误状态；
- 决策层看到失败 → 沿回退边回到上一个可恢复决策节点；
- 重新调整方案后再次执行。

如果脑体被混在一起，一次 API 超时可能直接导致整个链式推演状态损坏，只能从头再来。

> 这正是“失败时沿回退边回退，而不是整链重来”的架构基础。

### 4. 可观测性和审计要求

串行决策留下一条清晰的推理链：

> 为什么做这个判断？  
> 为什么选这个方案？  
> 哪一步执行失败了？

并发执行留下性能日志：

> 哪个调用慢？  
> 哪个调用超时？  
> 哪个环节可以优化？

两者分离，才能分别审计和优化。

## 三、3 个应用场景

### 场景 1：行业研究 / 深度报告生成

- **决策串行**：
  1. 明确研究问题；
  2. 确定分析框架；
  3. 决定需要哪些信息；
  4. 综合判断；
  5. 生成报告。

- **执行并发**：
  在“收集信息”这一轮，可以同时发起：
  - 搜索引擎检索；
  - 数据库查询；
  - 文档解析；
  - 专家访谈记录读取。

- **优化边界**：
  可以并行检索、设置超时、聚合结果；  
  但不能让“生成报告”和“确定框架”并行，否则结论可能脱离框架。

---

### 场景 2：多智能体协同

- **决策串行**：
  中央规划器（脑）按顺序决定：
  1. 当前目标是什么；
  2. 拆成哪些子任务；
  3. 哪些智能体执行；
  4. 结果如何校验；
  5. 是否需要重新规划。

- **执行并发**：
  多个智能体可以并行执行各自子任务：
  - 代码智能体写代码；
  - 文档智能体写文档；
  - 测试智能体跑测试；
  - 检索智能体查资料。

- **优化边界**：
  可以用异步并发提高执行效率；  
  但智能体不能反过来决定全局规划顺序，否则会出现多个“脑”互相冲突。

---

### 场景 3：风险审批 / 合规决策

- **决策串行**：
  审批流程必须按步骤走：
  1. 客户身份识别；
  2. 风险初筛；
  3. 深度尽调；
  4. 审批决策；
  5. 放行或拒绝。

- **执行并发**：
  在“深度尽调”这一步，可以并行执行：
  - 征信查询；
  - 反欺诈检查；
  - 制裁名单比对；
  - 工商信息核验；
  - 舆情风险扫描。

- **优化边界**：
  可以把多个尽调调用并行化，并对每个 API 设置超时；  
  但不能因为“尽调结果还没齐”就提前审批，也不能跳过风险初筛直接放行。

---

## 四、落地检查清单

引擎优化时，问自己几个问题：

- 是否让决策轮次变并行了？  
  → 如果是，破坏脑体分离。

- 是否让执行层直接修改认知锚定？  
  → 如果是，破坏只读约束。

- 是否把执行状态混入决策链？  
  → 如果是，回退机制会失效。

- 是否绕过了配置注册中心？  
  → 如果是，超时、并发度、回退边无法统一治理。

- 是否只优化了 API 并发、超时、重试、缓存？  
  → 如果是，这是安全且正确的优化。

所以结论是：

> **决策串行保证正确性，执行并发保证效率；引擎优化只能优化“执行”，不能优化掉“决策”。**
