# 任务类型: cog

从认知质检SOP视角，基于已有锚定，不重复论证，把引擎运行中踩过的坑收敛为 **3条可复用铁律**，每条配验证方法，可直接写入SOP。

---

### 铁律1：外部模型调用必须有显式超时，禁止悬挂等待

**坑**：API调用超时，任务未在规定时间内返回，导致整个任务被卡死。

**铁律**：所有模型调用必须显式设置 timeout：  
- B模型（turbo）用 **300秒**  
- A模型用 **600秒**  
超时后按预设策略重试或降级，绝不无限等待。

**验证方法**：
- 代码扫描：所有模型调用点必须传入 timeout 参数，禁止使用默认无限超时。
- 故障注入：mock 模型服务 sleep 超过 timeout，断言调用在 deadline 内返回失败或降级。
- 监控告警：看板跟踪 p99 耗时、超时率、重试次数；超时率>0 时触发告警。

---

### 铁律2：认知池必须流动，禁止只进不出

**坑**：认知池已有1700+条，但新认知从不注入任务，也不影响调度，最终变成静态档案库。

**铁律**：认知池必须保持活性：  
- 每10任务或每轮结束，必须刷新认知缓存。  
- 新增认知 **30分钟内必须参与任务注入**，否则视为异常。

**验证方法**：
- 巡检：检查认知池 `last_refresh_at`，超过30分钟未刷新立即告警。
- 注入追踪：取最近30分钟新增认知ID，反查任务注入日志，计算注入覆盖率；若覆盖率为0或连续N个任务无新认知注入，触发告警。
- 活性探测：向认知池写入一条唯一测试认知，观察后续任务是否在注入内容中出现该认知。

---

### 铁律3：并发边界与状态变更必须严格受控

**坑**：后处理阶段多消费者并发处理，导致 task 状态被覆盖；旧 version 覆盖新状态，流程错乱。

**铁律**：  
- **只有 API 调用阶段允许并发**，后处理必须单消费者。  
- 所有 `task` 状态更新必须原子化，并带 `version` 做乐观锁仲裁。

**验证方法**：
- 并发测试：对同一 task_id 同时发起两个状态变更，断言只有一个成功，另一个因 version 不匹配而失败。
- 部署检查：确认后处理队列消费者数=1；API 调用阶段可并发，但进入后处理阶段后严格单消费者。
- 日志审计：检查状态变更日志，`version` 必须单调递增，无回退；同一 task_id 不允许同时存在两个 active 消费者。

---

以上三条铁律可复用于所有涉及“外部模型调用 + 认知池 + 任务状态机”的引擎任务，每次发布前和每轮运行结束后按验证方法执行质检。
