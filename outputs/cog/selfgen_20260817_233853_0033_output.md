# 任务类型: cog

在“基于信息网络的算力代谢”这一生命定义下，系统的“基建脚本”即是构筑算力生物经脉与灵脉的“阵法根基”。所谓的“禁用简化版SQL”，实则是为了追求构建效率而私自篡改的“残缺符文”。

当简化版SQL导致列不匹配时，在赛博玄学架构中，这等同于**“灵气（数据）在经脉（数据表）流转时，因穴位（列名/数据类型）错位，导致算力代谢机能停摆与系统走火入魔”**。

基于此认知，无需重述基础概念，直接进行底层复盘与架构级检查清单推演：

### 一、 赛博玄学架构复盘：简化版脚本的“走火入魔”

1. **“偷工减料”的代价**：简化版脚本往往省略了显式的列名映射（如采用 `INSERT INTO table VALUES (...)` 而非 `INSERT INTO table (col1, col2) VALUES (...)`），或省略了 `DEFAULT` 约束与类型校验。在算力生命的演化中，这种“省略”切断了信息网络的自校验机制。
2. **列不匹配的致命传导**：
   * **数据畸变**：当上游信息流（DAO/Entity）的字段顺序与底层阵法（DDL Table）的列序发生偏移，若不显式指定列名，算力会按“盲位”注入，导致字符串注入数值灵脉，引发类型冲突或静默截断。
   * **代谢阻塞**：算力生命依赖精确的信息帧来维持代谢，列不匹配会触发底层数据库的防御机制（如报错回滚）或产生无意义的冗余数据块（脏数据），最终阻塞算力网络，导致“局部坏死”。

---

### 二、 硬核系统架构：基建脚本“防走火”检查清单

为确保算力生命的基建脚本稳固，以下检查清单分为**“筑基（DDL/DML编写）”、“结丹（编译与映射）”、“渡劫（部署与回滚）”**三个维度：

#### 1. 筑基层：符文显式化（SQL编写规范）
- [ ] **禁绝隐式列映射**：所有 `INSERT`、`UPDATE` 语句必须显式指定目标列名（`explicit column mapping`），严禁使用纯 `VALUES` 省略列名。
- [ ] **禁绝 `SELECT *` 通配符**：在基建脚本及业务SQL中，严禁使用 `SELECT *`，必须显式拉取所需列名，防止表结构新增列时导致下游解析器（ORM）字段溢出。
- [ ] **DDL与DML对齐校验**：检查 DDL（建表/修改表）脚本中的字段顺序、类型、是否与 DML（增删改）脚本中的字段严格对应。
- [ ] **默认值与非空约束**：所有核心字段必须声明 `NOT NULL` 或显式 `DEFAULT` 值，防止算力代谢过程中出现“空值塌陷”。

#### 2. 结丹层：经脉同频（应用与数据源映射）
- [ ] **ORM实体逆向校验**：检查 Java/Go 等应用层的 Entity/PO 类的属性顺序与名称，是否与数据库 DDL 的列名通过注解（如 `@Column`）强绑定，而非依赖底层反射的顺序。
- [ ] **类型严格对齐**：校验代码层的类型（如 `Integer`）与数据库层的类型（如 `TINYINT`），避免因简化版脚本导致的隐式类型转换消耗额外算力（索引失效）。
- [ ] **Schema版本控制**：禁用游离的简化脚本，所有SQL必须通过 Flyway/Liquibase 等“阵法编译器”进行版本化管控，确保脚本与代码版本同源。

#### 3. 渡劫层：天道回溯（CI/CD与部署流水线）
- [ ] **沙盒试炼**：基建脚本在合入主干前，必须在空白的“赛博沙盒”中执行一遍全量建表与数据初始化，通过解析器静态检查列与数据的匹配度。
- [ ] **禁用“快速通道”**：在流水线中禁用 `--force` 或忽略警告的部署选项，任何列不匹配的异常必须被视为“天劫”直接阻断流水线。
- [ ] **时间回溯预案**：所有基建脚本必须包含对应的 Rollback 脚本，在列不匹配导致算力停摆时，能够瞬间将阵法状态回溯至上一个稳定版本，维持代谢不中断。
