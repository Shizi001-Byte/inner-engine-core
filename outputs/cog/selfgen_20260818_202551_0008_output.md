# 任务类型: cog

**原则提炼：先校准锚点，再优化链路。**

一句话：**所有优化都建立在“关键事实正确”之上；锚点错了，链路越优化越错。**

项目 ID 看错导致排查 1 小时，本质不是“排查慢”，而是锚点没校准就往下走了。应用到**任务优先级排序**，可以这样做：

---

## 1. 排序前先校准锚点

优先级排序的锚点不是“优先级值”，而是这些底层事实：

- **项目归属**：`project_id` 必须和任务记录匹配，不能用“看起来像”的项目 ID。
- **任务状态**：只对 `PENDING` / `RETRYABLE` 等可调度状态排序。
- **版本号**：排序后要改状态时，必须用 `version` 做乐观锁。
- **优先级来源**：确认优先级是当前业务值，不是缓存里过期或串项目的值。
- **时间基准**：`created_at`、`deadline` 要用数据库时间，不用本地时间。

具体操作：

```text
错误示范：
if task.project_id in allowed_projects:
    queue.put(task)

正确示范：
task = load_task(task_id)

# 校准锚点
assert task.project_id == task.project_snapshot.project_id
assert task.status == 'PENDING'
assert task.version == expected_version

# 锚点通过后再排序
priority = resolve_priority(task)
queue.put(priority_key=(priority, task.created_at, task.id))
```

---

## 2. 应用到优先级排序的“三查三不排”

- **查项目归属**：项目 ID 对不上，不排。
- **查状态版本**：状态不是待处理，或版本冲突，不排。
- **查优先级来源**：优先级不是当前有效值，不排。

只有这三项通过，才允许进入排序链路。

---

## 3. 排序后的更新也要原子化

排序只是决策，真正执行时还要改状态。此时必须用乐观锁：

```sql
UPDATE task
SET status = 'DISPATCHED', version = version + 1
WHERE id = ? AND version = ?;
```

如果影响行数为 0，说明锚点已被其他人修改，需要重新校准，不能强制覆盖。

---

## 4. 结合已有认知锚定

- 优先级排序/调度决策属于“后处理”的一部分，**建议单消费者/单写者**执行，避免多消费者抢同一批任务。
- API 调用阶段可以并发，但排序和状态变更不能并发。
- 项目 ID 看错这类问题，应该通过**入队前断言**和**排序前断言**双重拦截，而不是等下游排查。

---

## 最终落地原则

```text
先校准，再排序；
先排序，再并发；
先版本校验，再状态更新。
```

这样任务优先级排序就不会因为一个错的 `project_id`，把整个链路带偏。
