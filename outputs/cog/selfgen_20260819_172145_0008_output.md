# 任务类型: cog

## 复盘：基建脚本禁用简化版

简化版 SQL 的典型错误不是“SQL 语法错”，而是**用“本次需要的列”代替“完整 schema”**，导致表结构与同步模型发生漂移。在增量同步链上，这会直接破坏“本地文件（实）→ Supabase 认知池（实）”这一段：

- `CREATE TABLE IF NOT EXISTS` 只写了部分列，表已存在时不会自动补列；
- 同步代码写入完整对象时，报 `column "xxx" does not exist`；
- 如果写入端用了 `SELECT *` 或动态映射，缺列可能被静默忽略，造成“认知池只进不出”；
- 列类型不匹配更隐蔽：`jsonb` 写成 `text`、`timestamptz` 写成 `timestamp`，数据写入成功但读取/过滤行为异常。

以下检查清单用于防止同类问题再次发生。

---

## 基建脚本检查清单

### 1. 脚本来源与版本

- [ ] 所有基建脚本必须来自版本化迁移目录，禁止在 REPL/临时脚本中手写 DDL。
- [ ] 每个迁移文件有唯一编号、创建时间、执行顺序。
- [ ] 必须记录当前 schema version，且与代码/同步模型版本对应。
- [ ] 禁止从旧笔记、历史聊天记录中复制“简化版 SQL”。

### 2. 建表 DDL 完整性

- [ ] `CREATE TABLE` 必须包含完整列集合，不能只写当前任务用到的列。
- [ ] 每个列必须声明：
  - 列名
  - 数据类型
  - 是否 nullable
  - 默认值
  - 约束（primary key、unique、check、references）
- [ ] 表级对象必须声明：索引、RLS 策略、分区策略。
- [ ] 枚举类型、数组、JSONB 结构必须与代码模型完全一致。
- [ ] `CREATE TABLE IF NOT EXISTS` 之后，必须有 `ALTER TABLE` 补齐逻辑，不能只依赖 `IF NOT EXISTS`。

### 3. 已存在表的增量变更

- [ ] 如果表已存在，必须检查列缺失情况：
  - 使用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...`
  - 或者先查询 `information_schema.columns`，再动态生成补列语句。
- [ ] 修改列类型时，必须评估旧数据转换：
  - `text` → `jsonb`
  - `timestamp` → `timestamptz`
  - `int` → `bigint`
- [ ] 删除列/表前必须备份，并确认没有同步任务依赖该列。

### 4. Schema 匹配校验

- [ ] 迁移完成后，必须执行 schema diff：
  - 对比 `information_schema.columns`
  - 对比列名、列顺序、数据类型、nullable、默认值
- [ ] 应用启动或同步前，必须检查目标表 schema 是否与模型一致。
- [ ] 禁止在同步查询中使用 `SELECT *`，必须显式列出列名。
- [ ] 列名/字段名应使用统一常量或 schema 定义生成，禁止散落硬编码字符串。

### 5. 幂等与可重放

- [ ] 同一迁移脚本在空库和已执行过的库上重复运行，结果必须一致。
- [ ] `ADD COLUMN IF NOT EXISTS` 可重复执行，且不会重复添加列。
- [ ] `INSERT ... ON CONFLICT` 不能用来掩盖 schema 错误。
- [ ] 迁移失败时，允许回滚或重试，但必须保证不会产生半更新状态。

### 6. 测试要求

- [ ] 必须在**空数据库**上执行全量迁移，确认能建出完整 schema。
- [ ] 必须从**生产 schema 副本**执行增量迁移，确认不会丢列/漏列。
- [ ] 必须用**包含旧数据的库**测试，确认新增列有正确默认值或回填逻辑。
- [ ] CI 中禁止用“最小复现 SQL”代替真实基建脚本。

### 7. 监控与告警

- [ ] 同步写入失败时，必须能识别“列不存在”/“列类型不匹配”错误，并触发告警。
- [ ] 同步指标表必须包含 `schema_version` 字段，记录当前使用的表结构版本。
- [ ] 认知池注入任务必须监控“新认知 30 分钟内未参与注入”的异常。
- [ ] 每 10 个任务或每轮同步结束后，刷新认知缓存；schema 变更后必须强制刷新。

## 在增量同步链上的落地

这条检查清单不重复论证 Guardian-Core 双进程、WAL+Snapshot、单向同步与幂等优先，而是把它们落到增量同步链的关键闸口上：

> 本地文件（实）→ 变化检测（虚/策略）→ 只传差异（实）→ 冲突处理（虚/策略）→ Supabase 认知池（实）→ 同步指标（实）→ 策略调优（虚）→ 更高效的下一轮同步（返实）

- **“只传差异 → Supabase 认知池”之间**：写入前执行 schema 门禁，列不匹配直接失败，不重试，不静默写入。
- **“同步指标 → 策略调优”之间**：指标中带上 `schema_version`，如果版本与预期不符，禁止调优，必须先修复基建脚本。
- **“更高效的下一轮同步”**：只有 schema 完全匹配后，缓存/快照才能被复用，否则下一轮继续走完整校验。

最终认知固化为：**基建脚本禁用简化版；所有表结构变更必须走完整迁移、自动 diff、显式列名、可重放、可监控。**
