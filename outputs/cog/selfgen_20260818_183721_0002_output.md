# 任务类型: cog

## 复盘：基建脚本禁用简化版

**核心结论**：  
“简化版SQL导致列不匹配”的本质，不是 SQL 写得太简单，而是**丢掉了列契约这个锚点**。  
在“脑体分离”框架下：

- **脑**：先定义清晰的表结构 / 列清单 / 映射关系；
- **体**：严格按契约生成和执行脚本；
- **链路**：决策串行（schema → 评审 → 脚本）→ 执行并发（各任务并行跑，但不允许自行简化）。

简化版SQL的最大风险是：把本应在“决策层”明确的列映射，推给“执行层”去猜。一旦表结构变化，列不匹配几乎是必然结果。

---

## 检查清单

### A. 锚点校准：列契约

- [ ] 是否已从最新 schema / migration 文件获取权威列清单？
- [ ] 是否禁止 `SELECT *`、`INSERT INTO t VALUES (...)`、`CREATE TABLE AS SELECT *` 这类依赖列顺序的写法？
- [ ] 是否所有 SQL 都显式列出列名？  
  例如：  
  - 禁用：`INSERT INTO user VALUES (1, 'a')`  
  - 启用：`INSERT INTO user (id, name) VALUES (1, 'a')`
- [ ] 是否确认列名、列顺序、数据类型、长度、默认值、非空约束完全一致？
- [ ] 是否确认不同环境（开发 / 测试 / 生产）之间没有 schema 漂移？

### B. 链路：决策串行

- [ ] 是否先走“schema diff → 脚本评审 → 执行计划”再写执行脚本？
- [ ] 基建脚本是否只有一个正式版本？是否存在“简化版 / 完整版”双轨？
- [ ] 是否禁止在评审通过后临时“优化 / 简化”脚本，例如去掉列清单、合并 ALTER、省略 WHERE？
- [ ] 是否所有变更都先经过人工或自动化评审，再进入执行队列？

### C. 执行并发前

- [ ] 并发执行前，是否给每个 worker / 子任务下发同一个“列映射契约”？
- [ ] 是否每个子任务都独立校验源端 / 目标端列集合？  
  例如对比 `information_schema.columns`。
- [ ] 是否在测试库跑过 dry-run 或事务回滚验证？
- [ ] 是否预设合理 timeout，避免脚本超时被误判为成功或失败？
- [ ] 是否禁止各并发任务自己“顺手简化”公共脚本？

### D. 执行中 / 执行后验证

- [ ] 执行后是否检查影响行数、目标表列数、抽样数据、边界值？
- [ ] 是否用 `SHOW COLUMNS` / `DESC` / `information_schema` 比对实际表结构与脚本预期？
- [ ] 是否确认没有数据错位、NULL 异常、类型隐式转换问题？
- [ ] 一旦发现列不匹配，是否立即停止后续并发任务，回滚修复，而不是临时改脚本绕过？

### E. 认知闭环

- [ ] 本次复盘是否已写入认知池，并设置触发条件：基建 / DDL / DML / 迁移类任务自动加载此清单？
- [ ] 是否每 10 个任务或每轮结束刷新认知缓存，确保新认知 30 分钟内参与注入？
- [ ] 是否已将“简化版 SQL”列为 code review 的硬性禁止项？
- [ ] 是否补充了正确写法示例，方便后续直接复用？

---

**一句话总结**：  
基建脚本没有“简化版”，只有“从 schema 生成的完整版”和“不允许存在的版本”。先校准列契约锚点，再谈执行并发优化。
