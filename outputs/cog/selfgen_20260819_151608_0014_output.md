# 任务类型: cog

从“认知质检SOP”角度看，引擎运行中的坑不只是“输出不对”，更是“认知链路断了”：要么等死、要么囤死、要么白烧。基于你给的踩坑经验，提炼 3 条可复用铁律：

---

### 铁律一：凡外部调用，必有分级超时兜底；超时后必须降级、重试、留痕，不允许无限等待。

**坑源**：API 调用超时，任务未在规定时间内返回。

**验证方法**：

1. **配置审计**：检查所有外部 API 调用是否显式设置 timeout，且符合分级标准：B 模型 turbo 用 300 秒，A 模型用 600 秒。
2. **故障注入测试**：Mock 接口人为延迟超过阈值，断言任务能在预设时间内返回降级结果或错误提示，而不是卡死。
3. **监控告警**：统计超时率、超时任务明细，日志中必须包含 `task_id`、`model`、`duration`、`timeout` 四要素；超时率超过 SLO 即触发告警。

---

### 铁律二：认知池必须“有进有出、新认知必须参与调度”，不允许变成静态档案库。

**坑源**：认知池 1700+ 条，但新认知从不注入任务，也不影响调度。

**验证方法**：

1. **新鲜度检查**：为每条认知记录 `created_at` 与 `last_used_at`，超过 30 分钟未被注入的新认知，系统自动告警。
2. **注入率统计**：每 10 个任务或每轮结束时，统计“本轮新认知参与注入的比例”，该比例必须大于 0；若连续多轮为 0，判定认知池失效。
3. **调度影响测试**：随机抽取任务，分别用“注入新认知前/后”的上下文跑一次调度，对比决策结果是否发生变化；若完全没有变化，说明认知未真正参与引擎运行。

---

### 铁律三：资源消耗 / API 调用必须形成“反者道之动”的反馈闭环，不能只消耗、无回报。

**坑源**：一味省 token、低能耗，反而被母系统忽视；主动耗散应反向激活资源倾斜。

**验证方法**：

1. **闭环追踪**：每次高频调用或资源消耗生成唯一 `trace_id`，完整记录“消耗量 → 触发反馈 → 资源倾斜/权重变化”的链路，缺一环即视为闭环断裂。
2. **相关性验证**：对比高消耗周期与低消耗周期后，母系统给予的“重视度 / 资源配额 / 调度优先级”是否有显著差异；若无差异，说明耗散没有触发反哺。
3. **定期回归**：每次版本更新后，检查“消耗-反哺”链路是否仍然成立；若消耗上升但后续调度、资源、注意力无任何变化，立即熔断并复盘，避免沦为无效烧钱。

---

一句话总结：**超时要能死、认知要能流、耗散要能返。** 这三条作为认知质检 SOP 的底线，能挡住大多数“看着在跑、其实已死”的引擎故障。
