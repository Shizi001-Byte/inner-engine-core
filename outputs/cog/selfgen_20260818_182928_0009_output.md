# 任务类型: cog

## 原则提炼：先校准锚点，再优化链路

**锚点** = 判断一切后续操作是否正确的基准，例如：项目 ID、索引结构、模型类型、环境、数据版本。  
**链路** = 在锚点正确之后才值得优化的处理流程，例如：超时重试、并发调优、block 传输、SOP 判定。

核心逻辑：**锚点错，链路越快，错得越远。**

---

## 从你的历史经验中反推

### 1. 项目 ID 看错，导致排查 1 小时
- 锚点是“项目 ID”。
- 项目 ID 错，后面所有日志、数据、任务归属全部错。
- 正确做法：**排查前先花 30 秒核对项目 ID / 环境 / 版本**，确认锚点无误，再进入链路排查。

### 2. 同步判定：同文件名、同大小、同 mtime，但 block 顺序不同，必须判为不同步
- 锚点是“索引”，不是“文件名 / 大小 / mtime”。
- block 是真正的数据单位，但索引才是判断是否同步的基准。
- 所以 SOP 中，**先比对索引；索引不一致，直接判不同步**，不要进入 block 级比较。
- 这就是“先校准锚点”的具体落地。

### 3. API 调用超时
- 锚点是“模型类型”：B 模型用 300 秒，A 模型用 600 秒。
- 如果锚点没校准，用了统一超时，B 模型可能超时，A 模型可能过早失败。
- 正确做法：**先确认模型类型，再设置对应 timeout，然后才优化重试策略**。

---

## 如何应用到任务优先级排序

优先级排序不能只看“链路优化收益”，要先看“锚点是否已校准”。

### 排序规则

| 优先级 | 条件 | 动作 |
|---|---|---|
| P0 | 锚点未确认，或疑似错误 | 先校准锚点：核对项目 ID、索引、环境、模型类型、数据版本 |
| P1 | 锚点已确认，但链路存在已知失败风险 | 按锚点配置正确参数，再执行链路 |
| P2 | 锚点稳定，链路性能可优化 | 最后再做优化，不影响正确性 |

### 具体操作建议

- 每个任务开工前，增加一个“锚点检查”：
  - 项目 ID 对吗？
  - 环境是生产还是测试？
  - 数据版本 / 索引版本对吗？
  - 模型类型是 A 还是 B？
  - SOP 基线是哪个版本？

- 如果锚点检查不过，**立即停止**，不要继续优化链路。

- 如果一个任务锚点未校准，即使它看起来紧急，也要先降级；  
  如果一个任务锚点已校准，即使链路还不完善，也可以优先做，因为结果可验证、可纠偏。

---

## 一句话总结

> **先问“锚点对不对”，再谈“链路快不快”。  
> 任务优先级排序中，锚点校准永远排在链路优化之前。**
