# 任务类型: cog

这是一份针对“基建脚本禁用简化版SQL导致列不匹配”事故的深度复盘与认知纠偏报告，以及防止此类问题再次发生的检查清单。

---

### 一、 认知复盘：为什么会发生列不匹配？

在基建脚本（如数据同步、ETL任务、底层物化视图构建）中，开发人员有时为了“图快”或“省事”，会使用简化版SQL。常见的简化手段包括：`SELECT *`、`INSERT INTO table VALUES (...)` 省略列名、依赖建表时的默认字段顺序等。

这种“简化”带来了致命的认知偏差和工程隐患：

1.  **“当前正确”不等于“未来正确”（时间轴偏差）：**
    简化版SQL高度依赖运行时刻的表结构。今天源表和目标表的列顺序一致，数据正常流转。明天源表新增了一个字段（如加在中间位置），目标表未同步修改，`SELECT *` 按新顺序吐出数据，而目标表按旧顺序接收，导致**数据类型错位、甚至静默截断/报错**。
2.  **“黑盒映射”带来的排雷成本激增：**
    显式映射（写出每一个字段名）虽然啰嗦，但具有极强的“自描述性”和“防呆性”。简化版SQL掩盖了字段对应关系，一旦报错，排查链路需要对比两端DDL，耗时极长。
3.  **混淆了“业务查询”与“基建脚本”的规范边界：**
    在日常分析查询中偶尔用 `SELECT *` 无可厚非；但在**基建脚本**中，脚本的健壮性和确定性是第一位的。基建脚本的生命周期通常长达数月或数年，跨越多次表结构变更，必须做到“防未来之患”。

**核心教训：** 基建脚本的“简化”不是减少代码行数，而是牺牲了系统的**强契约性**和**抗压性**。基建代码必须显式声明一切依赖。

### 二、 基建脚本SQL防错检查清单

在进行基建脚本开发或Code Review时，请严格对照以下清单打勾：

#### 阶段一：语法与结构规范
- [ ] **禁用 `SELECT *`**：所有提取字段的SQL，必须显式写出列名（`SELECT id, name, status FROM ...`）。
- [ ] **禁用无列名 `INSERT`**：`INSERT INTO target_table (col1, col2) SELECT ...`，严禁省略目标表的列名列表。
- [ ] **禁用位置依赖的 `LOAD DATA` / `COPY`**：如果使用文件导入导出工具，必须显式指定列对应关系，不可依赖文件列序与表列序一致。
- [ ] **避免 `CREATE TABLE AS SELECT`（CTAS）直接建表**：若需建表，先显式 `CREATE TABLE` 定义Schema，再 `INSERT INTO ... SELECT` 写入数据，防止源表字段类型变更导致目标表类型失控。

#### 阶段二：列与列的映射校验
- [ ] **列数一致性检查**：`SELECT` 后的字段数量与 `INSERT INTO` 括号内的字段数量必须完全相等。
- [ ] **顺序一致性检查**：字段不仅数量要一致，**顺序必须严格一一对应**，且顺序不依赖于底层物理存储顺序。
- [ ] **数据类型兼容性检查**：源端字段类型与目标端字段类型必须兼容（如 `BIGINT` 插入 `INT` 可能溢出，`VARCHAR` 插入 `DATE` 可能报错），必要时在SQL中显式使用 `CAST()`。
- [ ] **NULL值处理**：源表允许为NULL的字段，插入目标表是否允许NULL？如果不允许，是否在SQL中使用了 `COALESCE()` 提供默认值？

#### 阶段三：Schema 变更防错机制
- [ ] **新增字段同步检查**：源表新增字段时，目标表是否需要同步新增？如果不需要，显式列名SQL将自动忽略源表新字段（安全）；如果需要，必须同步修改基建SQL。
- [ ] **删除字段同步检查**：源表删除字段时，基建SQL是否会报错？（显式列名会直接报错报错，这是好现象，能第一时间发现问题；而 `SELECT *` 则会静默错位）。
- [ ] **字段重命名检查**：源表字段重命名后，基建脚本是否已同步更新并重新编译/测试？
- [ ] **建表语句（DDL）与数据操作（DML）的原子性**：如果基建脚本包含修改表结构并同步数据，确保DDL先于DML执行，且失败时有回滚机制。

#### 阶段四：执行与验证
- [ ] **Dry Run（试运行）**：在测试环境执行前，先通过 `EXPLAIN` 或只加 `LIMIT 0` 检查SQL语法和字段映射是否成功，不实际落盘。
- [ ] **表头对比验证**：脚本执行后，对比源端和目标端数据的 `DESC table` 或 `INFORMATION_SCHEMA`，确保核心字段（特别是非空字段、主键）无遗漏。
- [ ] **数据抽样比对**：抽取前10行数据，人工肉眼比对源端查询结果与目标端落盘数据的列对应关系是否正确。

### 三、 总结与行动建议

1.  **制定红线规则**：在团队的SQL开发规范中明确标红：“基建层脚本（ETL、同步任务、定时调度）严禁使用 `SELECT *` 及省略列名的 `INSERT`”。
2.  **引入静态扫描工具**：在CI/CD流程中接入SQL Lint工具（如SQLFluff、Dataform等），拦截基建脚本中的不规范写法，用工具代替人工检查。
3.  **转变认知**：代码的“优雅”在基建层不等于“简短”，而等于“明确”。多写几行字段名，换来的是未来少加几个班排查数据错位事故。
