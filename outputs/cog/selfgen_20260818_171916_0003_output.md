# 任务类型: cog

## 复盘结论

“基建脚本禁用简化版”这条认知的根因，不是“简化版 SQL 写得不够好”，而是**简化版 SQL 的来源不可溯源、未与当前表结构对齐**，导致列不匹配。  
这正好对应锚定中的 **「认知不新鲜」变体：溯源链断了**——不是认知池没有数据，而是这条 SQL 的原始载体丢失，无法安全引用。

所以，所有基建脚本的 SQL 必须满足一个硬前提：

> **能追溯到当时的 schema 基线，且与当前环境实时校验一致；否则一律禁用。**

## 检查清单

### 1. 源头一致性

- [ ] SQL 必须从权威 schema 文件（DDL / migration / 模型定义）生成或校验，禁止手工默写
- [ ] 执行前用 `DESCRIBE` / `information_schema` / `SHOW CREATE TABLE` 与目标表结构比对
- [ ] 确认列名、列序、列类型、默认值、非空约束、注释均一致
- [ ] 脚本必须标注对应的环境（dev/test/prod）和 schema 版本

### 2. 禁止简化项

- [ ] 禁止使用 `SELECT *` 作为列清单
- [ ] 禁止 `INSERT INTO t VALUES (...)` 不写列名
- [ ] 禁止使用“看起来差不多”的字段缩写/别名/简写
- [ ] 禁止把多表 JOIN 简化为单表查询后手工补字段
- [ ] 禁止用位置对应代替显式列映射，尤其是 `INSERT ... SELECT`
- [ ] 禁止在基建脚本中复用只读分析用的简化 SQL 片段

### 3. 列匹配四要素

- [ ] **列名完全匹配**：大小写、特殊字符、引号规则按数据库配置检查
- [ ] **列数量一致**：目标表列数 = 查询返回列数
- [ ] **列顺序一致**：若未显式指定，按表定义顺序；建议始终显式指定列顺序
- [ ] **数据类型兼容**：长度、精度、字符集、时区、枚举值范围均兼容，禁止隐式转换隐患

### 4. 静态校验

- [ ] 执行 `EXPLAIN` / `EXPLAIN VERBOSE`，确认解析无列名错误
- [ ] 使用 SQL Lint 或 SchemaDiff 工具做自动化检查
- [ ] 对涉及 `ALTER TABLE` 的脚本，先导出目标表当前结构做 diff
- [ ] 检查是否存在隐式转换告警，尤其是字符串 ↔ 数字、日期 ↔ 时间戳

### 5. 动态验证

- [ ] 在沙箱/临时库执行脚本，并用真实数据子集验证
- [ ] 执行 `SELECT * LIMIT 1` 和 `SELECT COUNT(*)` 抽样比对
- [ ] 获取基线结果集列元数据，与脚本结果集列元数据做断言比对
- [ ] 写操作先 `BEGIN; ... ROLLBACK;` 验证，再正式执行
- [ ] 正式执行后检查日志中是否出现 `column ... does not exist` / `Column count doesn't match` 等错误

### 6. 版本与溯源

- [ ] 每个基建脚本必须有版本号、作者、变更日期、关联工单/需求号
- [ ] 脚本必须能通过 Git/配置库追溯到当时的 schema 版本
- [ ] 禁止粘贴无来源 SQL；若来自历史对话/认知，必须能找到原始载体
- [ ] 找不到原始载体的 SQL，一律视为“静态档案”，禁止直接使用
- [ ] 对“简化版”明确打标 `UNAVAILABLE`，并补充正确的替代路径

### 7. 流程防线

- [ ] 代码评审必须包含 DBA 或基建负责人，重点检查列映射
- [ ] 合并前执行 diff：新脚本 vs 上一版本脚本，确认没有删列/重排列
- [ ] 上线后立即监控错误日志，出现列不匹配错误即触发复盘
- [ ] 将“简化版 SQL 导致列不匹配”加入历史坑库，后续基建任务自动注入

## 认知层固化

- 将 **“基建脚本禁用简化版”** 作为硬规则写入认知池
- 每 10 个任务或每轮结束刷新认知缓存，确保该规则参与后续调度
- 如果某条 SQL 来自 8月8日—8月18日 的溯源断档区，必须先重建溯源链再使用；否则不引用、不注入、不执行
