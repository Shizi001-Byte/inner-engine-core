# 任务类型: cog

## 复盘结论

“基建脚本禁用简化版”不是建议，而是红线。  
简化版 SQL 的典型危害是：**只写了“看起来能跑”的核心列，导致与真实 schema 的列名、列类型、约束、默认值不一致**，进而引发同步链断裂、数据写入失败、任务静默失败。

正确姿势：以 **`change_id + 内容哈希`** 为纽带，**先验证、再分工、后沉淀规范**。

---

## 基建脚本检查清单

### 一、脚本生成与准备阶段

- [ ] 确认本次变更有唯一 `change_id`，且能关联到需求/工单/代码提交。
- [ ] 禁止手写“简化版 SQL”；脚本必须从基线迁移文件、ORM Schema 或 `information_schema` 导出生成。
- [ ] 如果脚本由模型生成，按模型类型预设 timeout：  
  - B 模型 turbo：300 秒  
  - A 模型：600 秒  
  超时未返回完整结果，直接标记失败，不采用半截 SQL。
- [ ] 同一 `change_id` 的脚本内容哈希必须一致；如果与历史哈希不一致，说明被篡改或版本漂移，立即停止执行并人工审查。
- [ ] 新认知/历史教训必须在 30 分钟内参与当前任务注入；每 10 个任务或每轮结束刷新认知缓存，避免认知池变成静态档案库。

---

### 二、Schema 一致性检查（列不匹配专项）

- [ ] **列名逐项比对**：不能只数数量，要逐个字段核对，注意大小写、下划线、保留字、引号。
- [ ] **列类型比对**：  
  - `int` vs `bigint`  
  - `varchar(255)` vs `text`  
  - `timestamp` vs `timestamptz`  
  - `json` vs `jsonb`  
  不能“看起来差不多”。
- [ ] **列顺序比对**：  
  如果存在 `INSERT INTO ... VALUES (...)`、`SELECT *`、`COPY`、ETL 位置映射，列顺序必须完全匹配；否则一律改为显式列名。
- [ ] **默认值比对**：  
  `now()`、`CURRENT_TIMESTAMP`、`0`、`NULL` 是否一致，不能凭经验替换。
- [ ] **约束比对**：  
  `NOT NULL`、`UNIQUE`、`PRIMARY KEY`、`FOREIGN KEY`、`CHECK` 是否齐全。
- [ ] **自增/生成列比对**：  
  `serial` vs `identity` vs `generated always as ...` 不能混用。
- [ ] **表级属性比对**：  
  存储引擎、字符集、排序规则、分区、表空间、注释。
- [ ] **附属对象比对**：  
  索引、唯一索引、复合索引、触发器、序列、视图、函数是否纳入脚本，不能只建表。

---

### 三、幂等性与冲突处理

- [ ] 脚本是否可以重复执行？`IF NOT EXISTS` / `CREATE OR REPLACE` 只能防重复创建，**不能防结构不一致**。
- [ ] 重复执行前后，用 `information_schema` 或 `pg_dump --schema-only` 做 schema diff，确认无漂移。
- [ ] 如果脚本包含 DML（`INSERT/UPDATE/MERGE`），重复执行是否会产生重复数据、违反唯一约束、覆盖业务数据？
- [ ] 冲突处理策略明确：`ON CONFLICT DO NOTHING` 还是 `DO UPDATE`？必须与业务语义一致。
- [ ] 失败后必须有冷却重试机制，不能无限循环；重试前重新校验 `change_id + 内容哈希`。

---

### 四、执行与同步链验证（先验证，再分工）

- [ ] 先在 staging/沙箱环境执行，执行成功后做 schema diff，**不能只看“执行成功”**。
- [ ] 执行冒烟 SQL：对新增/变更列做 `INSERT`、`UPDATE`、`SELECT` 覆盖，确认没有 `column does not exist`、`null value in column`、`duplicate key`。
- [ ] 验证 Gitee 代码提交、飞书文件上传、Supabase 存储同步是否由同一 `change_id` 触发。
- [ ] 同步链中每一环都要确认成功；任一环失败，按冷却策略重试，禁止人工“顺手改一下”绕过检查。
- [ ] 重大变更必须自动触发通知，确保相关角色感知。

---

### 五、沉淀与认知刷新（后沉淀规范）

- [ ] 将本次列不匹配的差异、修复过程、最终 schema 写回认知池。
- [ ] 给认知池设置刷新机制：新认知 30 分钟内参与后续任务，每 10 任务/每轮结束强制刷新。
- [ ] 把“基建脚本禁用简化版”固化为检查模板或 CI 脚本：  
  - 禁止手写简化版 SQL  
  - 强制 schema diff  
  - 强制 `change_id + 内容哈希` 校验  
  - 强制超时与重试策略
- [ ] 保留每个 `change_id` 的执行日志：脚本内容哈希、执行人/模型、执行时间、验证结果，形成可审计轨迹。

---

一句话总结：**基建脚本不是“能跑就行”，而是必须与目标 schema 完全同源、逐列一致、可幂等、可验证、可追溯。**
