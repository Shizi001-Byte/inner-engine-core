# 任务类型: cog

## 原则提炼

**“先校准锚点，再优化链路”** 的意思是：

- **锚点**：一旦错了，后面所有操作都会跟着错的“基础事实”。比如项目 ID、任务归属、价值定义、截止时间、依赖关系。
- **链路**：建立在锚点之上的处理流程、计算公式、排序逻辑。

项目 ID 看错导致排查 1 小时，**根因不是排查链路不够快，而是锚点错了**。链路再优化，锚点错，结果就是南辕北辙。

---

## 应用到任务优先级排序

任务优先级排序里，**锚点就是任务的真实归属和约束**，排序模型只是“链路”。

### 反模式

拿到任务列表，立刻按“截止时间”或“直觉”排序。  
排到一半发现：某个任务的“项目 ID”看错了，它其实属于低优项目。  
于是重新排，浪费 1 小时，还可能让高优任务被低优任务阻塞。

### 正模式

排序前，先花几分钟校准这些锚点：

| 锚点 | 校准问题 |
|---|---|
| 任务身份 | 这个任务属于哪个项目/客户？项目 ID 是否和原始需求一致？ |
| 价值锚点 | 完成它到底影响哪个业务指标？影响多大？ |
| 时间锚点 | 截止时间是硬性的还是软性的？依赖链是否已更新？ |
| 资源锚点 | 谁来做？资源是否可用？是否被更高优任务占用？ |
| 状态锚点 | 任务是否已废弃？是否已被其他任务替代？ |

锚点确认后，再跑优先级排序链路：

- 四象限：紧急 × 重要
- RICE：Reach × Impact × Confidence / Effort
- WSJF：（商业价值 + 时间紧迫性 + 风险降低）/ 工作量

排序完再反向校验一次：

> 排在第一的任务，如果做了，对哪个项目的目标有直接贡献？  
> 如果说不出来，说明锚点还没校准，先别排。

---

## 核心口诀

> **先对 ID，再排序；先认项目，再算分；锚点不对，优化白费。**

这条原则和 API 超时、多线程后处理是同一个道理：

- API 超时：先确认是 B 模型还是 A 模型，再决定 300 秒还是 600 秒。模型类型是锚点，timeout 是链路。
- 多线程后处理：先给每个请求加上序号，再合并结果。顺序是锚点，后处理是链路。
- 任务优先级排序：先校准项目归属、价值、约束，再计算优先级。任务真实身份是锚点，排序公式是链路。

**锚点会漂移**，所以每次排期前都要重新校准，而不是校准一次永久有效。
