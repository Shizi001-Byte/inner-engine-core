# 任务类型: cog

## 原则提炼

**先校准锚点，再优化链路。**

项目ID看错导致1小时排查，说明问题不在“排查链路”本身，而在链路起点的锚点错误。锚点错，后面所有动作都是空转。

**对应到任务优先级排序：**

排序不是先算“紧急×重要”矩阵，而是先确认每个任务的锚点是否准确。锚点不校准，排得越精确，错得越系统。

---

## 应用到任务优先级排序的具体做法

### 1. 排序前先做“锚点五查”

每个任务进入优先级队列前，必须核对：

- **项目ID/任务ID**：是否属于当前项目，是否存在同名旧任务
- **目标锚**：任务要支撑的目标是否和当前北极星一致
- **依赖锚**：前置任务是否真实存在、是否已完成
- **资源锚**：预算、人力、timeout 是否匹配任务类型  
  （如 B 模型 turbo 用 300 秒，A 模型用 600 秒）
- **完成锚**：验收标准是否明确，能否判断“做完”

> 任何一个锚点错误，排序结果都会失真。

### 2. 把“锚点校验”设为排序前置关卡

不要直接进入优先级排序，先花 10 秒核对锚点清单。  
项目ID错了，1小时排查；任务锚点错了，可能整个迭代方向都错。

排序链路应该是：

```text
接收任务 → 校准锚点 → 确认任务真实存在且可执行 → 再排优先级 → 执行 → 复盘
```

而不是：

```text
接收任务 → 直接排优先级 → 执行中才发现任务ID/项目ID错误 → 返工排查
```

### 3. 用“锚点置信度”作为排序权重门槛

每个任务先计算锚点置信度：

- 锚点全部确认：置信度 1.0，进入优先级排序
- 锚点有任一不确定：置信度 < 0.95，先进入“校准队列”
- 校准队列不参与优先级排序，避免错排

只有锚点确认后，才按“价值 / 紧急度 / 依赖 / 资源”计算最终优先级。

### 4. 形成内生自增强闭环

按照已有认知体系，这正好形成最小闭环：

- **虚规则/信息**：锚点校验清单 + 锚点置信度
- **实资源/结构**：排序队列、执行顺序、资源分配
- **虚升级/迭代**：每次排序后记录锚点偏差，反向修正项目数据库和任务描述，再升级排序规则

对应底层动力“反者道之动”：不要急着“优化排序效率”，先主动做“核对锚点”这种看似损失时间的动作，反向规避更大返工成本。

---

## 一句话结论

**优先级排序前，先回答“这个任务属于哪个项目、目标是什么、依赖什么、资源够不够、怎样算完成”；锚点确认后再排顺序。锚点错，链路全错。**
