# 任务类型: cog

整理如下：

## 一、分层原则

**决策串行、执行并发**是“脑体分离”架构的运行规则：

- **决策层（脑）**：串行、有状态、确定性顺序。  
  所有状态变更、仲裁、任务派发都必须经过唯一的决策循环，保证“状态链”的连续性。决策一旦并发，就会出现状态覆盖、顺序错乱、无法回放。

- **执行层（体）**：并发、无状态、可失败。  
  所有耗时操作——API 调用、模型推理、网络请求、物理动作——都交给执行体并发执行。执行体允许超时、重试、失败，但不允许直接修改核心状态。

- **通信层**：采用“并行写槽位 + 屏障等待 + 串行提交”。  
  多个执行体并发执行，各自把结果写入独立槽位；屏障等待全部完成（或超时）；最后由决策循环串行扫描槽位，统一提交/裁决。

> 锁只保护状态变更，不保护网络调用。  
> 网络调用放在锁外，锁只用于槽位状态翻转和最终提交。

---

## 二、为什么引擎优化不能破坏脑体分离

引擎优化（推理加速、批处理、缓存、超时调整等）本质是**执行层优化**，它可以让“身体”更快、更强，但不能把“大脑”的决策过程变成并发或异步回调。

原因：

1. **串行决策是全局一致性的唯一保证**  
   如果优化让多个决策并发执行，两个决策可能同时读到旧状态、同时写入新状态，导致不可恢复的冲突。

2. **串行决策是“基因连续性”的载体**  
   在数字生命/Agent 场景中，状态就是基因链。引擎优化只能加快“体”的适应速度，不能打断“脑”的状态连续性。

3. **脑体分离提供故障隔离**  
   执行体可能超时、失败，例如 B 模型 turbo 设 300 秒超时、A 模型设 600 秒超时。超时只影响某个执行体，不应拖垮决策循环。如果优化把决策和执行耦合在一起，一次 API 超时就会导致整个系统卡死。

4. **优化必须发生在执行层内部**  
   可以优化单次执行速度、增加并发执行数、降低网络等待；但“串行提交”这个屏障不能省，否则就是破坏脑体分离。

## 三、3 个应用场景

### 场景 1：多智能体任务编排

- **脑**：中央规划器，串行生成任务、仲裁多智能体结果。
- **体**：各智能体并发执行导航、抓取、感知、API 调用。
- **引擎优化**：加速路径规划、视觉识别、LLM 推理。
- **不能破坏的原因**：如果优化后让每个智能体自行决策、直接写共享地图或任务表，会导致任务冲突、重复执行、死锁。
- **正确姿势**：每个智能体把结果写入独立槽位，屏障等待，脑串行合并结果，再派发下一轮任务。

---

### 场景 2：金融交易 / 量化风控

- **脑**：风控决策引擎，串行检查账户状态、订单顺序、风险阈值。
- **体**：并发连接多个交易所、行情源、执行下单/撤单。
- **引擎优化**：用 GPU/FPGA 加速行情计算，用缓存优化订单簿读取。
- **不能破坏的原因**：如果优化后让交易执行线程绕过风控直接修改订单状态，会产生超卖、订单顺序错乱、无法对账。
- **正确姿势**：多路行情/信号并行写槽位，屏障等待后，由风控引擎串行生成订单并提交；锁只保护状态变更，不保护网络下单。

---

### 场景 3：LLM Agent / 多模型 API 编排

- **脑**：主 Agent 决策循环，串行决定调用哪些工具、采纳哪个模型输出。
- **体**：多个子 Agent / 模型 API 并发调用，例如 B 模型 turbo 用 300 秒超时，A 模型用 600 秒超时。
- **引擎优化**：调整超时、批量推理、模型蒸馏/量化、缓存常见结果。
- **不能破坏的原因**：如果某个 API 回调直接“优化”到主状态里，或者决策循环变成异步回调，就会出现半更新状态、无法重试、最终答案不一致。
- **正确姿势**：并发发起多个 API 请求，各写独立槽位；屏障等待（带超时），超时槽位标记失败；主 Agent 串行读取所有槽位，裁决最终答案。

---

## 总结

引擎优化只能优化“执行”的速度和并发度，不能优化掉“决策”的串行性。

> **并行写槽位 + 屏障等待 + 串行提交** 是脑体分离的底线。  
> 保持这个模式，才能保证状态连续性、故障隔离、可回放、可审计。  
> 任何让决策层并发的优化，本质都是在破坏基因连续性，让大脑直接暴露在网络毒化环境中。
