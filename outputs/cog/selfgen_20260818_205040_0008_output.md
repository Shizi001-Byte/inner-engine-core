# 任务类型: cog

## 复盘：基建脚本禁用简化版 SQL

### 核心教训

基建脚本里使用“简化版 SQL”是列不匹配的元凶。  
典型简化操作：

- `INSERT INTO table VALUES (...)` 不写目标列；
- `SELECT *` 直接灌入下游；
- JOIN/UNION 不关心列顺序；
- 从旧脚本复制后不校验当前 schema；
- 删掉原版中的类型转换、空值处理、过滤条件，认为“多余”。

这些做法在表结构变更后，会导致列错位、数据写入错误列、静默成功、难以追溯。

---

## 检查清单

### 一、写脚本前

- [ ] 从数据字典 / `information_schema` 拉取当前表结构，禁止凭记忆写列。
- [ ] 所有 `INSERT` 必须显式列出目标列：  
  `INSERT INTO t (col_a, col_b, col_c) VALUES (...)`。
- [ ] 所有 `SELECT` 必须显式列出输出列，禁止 `SELECT *` 进入基建脚本。
- [ ] `UPDATE` 必须写清目标列，禁止简写或依赖字段顺序。
- [ ] `JOIN` / `UNION` 中每个字段都带表别名或来源标识。
- [ ] 使用 CTE / 子查询时，最终输出层必须再次核对列清单。

### 二、脚本生成 / 修改时

- [ ] 如果复制旧脚本，必须与当前 schema 做 diff，不能假设列顺序未变。
- [ ] 原版中的类型转换、空值处理、去重、过滤条件，禁止以“看起来多余”为由删除。
- [ ] 涉及列变更时，使用显式 `ALTER TABLE` 或明确 DDL，不用 `SELECT INTO` 隐式建表。
- [ ] 用 `EXCEPT` / `INTERSECT` 或脚本对比“期望列集合”和“实际列集合”，做 schema 断言。
- [ ] 对 SQL 做静态检查，设置规则禁止 `SELECT *`、禁止无列名 INSERT。

### 三、测试 / 发布时

- [ ] 在类生产环境执行 dry-run：  
  `BEGIN; 执行 SQL; 查询列映射; ROLLBACK;`
- [ ] 用脱敏数据验证：对比源表和目标表的列名、列顺序、行数、关键字段值。
- [ ] 执行前备份目标表，并准备回滚脚本。
- [ ] 上线后立即查询 `information_schema` 校验目标表结构，并抽查数据。
- [ ] 如果通过模型 API 执行脚本，预设 timeout：B 模型 turbo 用 300 秒，A 模型用 600 秒。

### 四、认知沉淀（防止认知池只进不出）

- [ ] 本次“基建脚本禁用简化版”认知立即注入认知池，不能只存不用。
- [ ] 每 10 个任务或每轮调度结束，刷新认知缓存。
- [ ] 新认知 30 分钟内必须参与后续任务上下文。
- [ ] 每次基建脚本执行后，把实际列映射、验证命令、结果写回认知池。

---

### 强制检查项

1. 基建脚本禁止简化版 SQL，必须显式列清单。
2. 涉及列变更必须做 schema 断言。
3. 新认知必须 30 分钟内注入并参与调度。
