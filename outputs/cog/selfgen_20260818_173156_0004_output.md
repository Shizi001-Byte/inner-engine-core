# 任务类型: cog

## 复盘：基建脚本禁用简化版

根因不是“SQL语法错误”，而是**简化版破坏了基建脚本的可验证性**。  
基建脚本必须像“公共档案”一样：可溯源、可 diff、可回滚。简化版省略了列名、约束、索引或版本信息，导致与真实 schema 不匹配。

---

## 检查清单

### A. 写脚本前

- [ ] 确认目标环境的真实 schema 版本，不依赖“我以为的表结构”。
- [ ] 从迁移工具或生产环境导出完整建表语句作为基线，禁止手写精简版。
- [ ] 逐列比对：列名、列顺序、数据类型、默认值、非空约束、字符集。
- [ ] 确认主键、唯一键、外键、索引、check 约束没有被简化掉。

### B. 写 SQL 时

- [ ] `INSERT` 必须显式列出列名，禁止 `INSERT INTO t VALUES (...)` 依赖列顺序。
- [ ] `SELECT` 显式列出所需列，禁止在数据搬运/校验场景使用 `SELECT *`。
- [ ] 涉及 `JOIN` / `UPDATE` / `DELETE` 时，明确 JOIN KEY 和过滤条件，避免笛卡尔积或全表误操作。
- [ ] 日期、时间戳、枚举、布尔、JSON 等类型做显式转换，不依赖隐式转换。
- [ ] 保留约束和索引；尤其是唯一约束，不能因为“简化”而删除，否则会产生重复数据。

### C. 执行与验证

- [ ] 先在 staging 环境执行 dry-run，或放在事务中测试后回滚，不直接生产执行。
- [ ] 执行前记录 `information_schema.columns` 快照，执行后 diff，确保列结构一致。
- [ ] 执行后校验：
  - 行数是否符合预期；
  - 列数与目标表一致；
  - 抽样数据内容正确；
  - 无约束违规；
  - 无重复记录。
- [ ] 设置合理的 statement timeout / transaction timeout；如果涉及模型 API 调用，按 B 模型 turbo 用 300 秒、A 模型用 600 秒预设，避免超时中断。
- [ ] 必须有回滚脚本，且回滚脚本同样经过完整字段核对，不能是另一个“简化版”。

### D. 记忆与流程

- [ ] 基建脚本必须 code review，禁止以“简化版”作为绕过评审的快捷方式。
- [ ] 将本次“列不匹配”教训锚定到可验证事件：具体库表、脚本版本、报错信息、修复 commit，而不是只留一句“禁用简化版”。
- [ ] 新认知写入后 30 分钟内注入任务上下文；每 10 个任务或每轮结束刷新认知缓存，避免认知池只进不出。
- [ ] 每次基建变更作为协作 DAG 中的一个节点记录，带验证门：schema 校验、review、测试通过后才可合并执行。

---

一句话总结：  
**基建脚本没有“简化版”，只有“完整版 + 验证门”。** 任何省略都可能变成下一次列不匹配的隐患。
