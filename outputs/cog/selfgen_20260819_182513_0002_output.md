# 任务类型: cog

## 一、根因定性

当前通神维 `bonus_count=619` 的膨胀，核心不是“bonus 太多”，而是**语义错了**：

> 旧逻辑把“有认知产出”当作“通神奖励”，导致每个产出认知的真实任务都额外 +1 bonus。

这违反了你已定的统一规则：

- `task_count`：只统计真实任务
- `bonus_count`：只统计系统自触发的高价值事件
- `count = task_count + bonus_count`

所以修复不是简单清零，而是**重新定义通神维 bonus 的语义**。

---

## 二、重定义：bonus 应该代表什么

### 1. 认知 ≠ 通神

- **认知**：任务执行中产生的知识、规则、坑位、结论，进入“认知池”。
- **通神**：跨任务、反直觉、高杠杆、经过验证的系统级洞见或外部稀缺信号。

### 2. 通神维 `bonus_count` 只允许以下 4 类事件

| 事件类型 | 说明 | 示例 |
|---|---|---|
| `cross_task_insight` | 跨任务认知跃迁，不是单任务产物 | 由 ≥3 条旧认知融合成新规则，并在后续任务中验证有效 |
| `reverse_logic_verified` | 反向逻辑被验证 | 官方主动放大免费额度、重度用户被定向邀请测试、给专属资源 |
| `official_signal` | 外部稀缺高价值信号 | 用户/官方明确给出的“避坑提醒”“坑库预警”“已验证结论” |
| `engineering_fix` | 工程级根因修复 | 修复了“认知池只进不出”“九维计数语义混乱”等系统性问题 |

**不在上述列表中的，一律不计 bonus。**

## 三、新计数逻辑

### 旧逻辑（错误）

```text
任务完成:
  task_count += 1
  如果有认知产出:
    bonus_count += 1   # 错！有认知就加，必然膨胀
```

### 新逻辑（正确）

```text
任务完成:
  task_count += 1
  认知池.add(本次产出认知)
  不修改 bonus_count

通神评审触发（每 10 个真实任务 或 每轮结束）:
  刷新认知缓存
  遍历认知池中的候选认知:
    如果满足上述 4 类事件之一:
      写 bonus_log
      bonus_count += 1
      将对应认知标记为“已注入/已使用”
  同步并回读验证
```

### 关键约束

- **任务产出认知**：只进认知池，不加 bonus。
- **bonus 必须可追溯**：每一条 bonus 都要有 `bonus_log` 记录。
- **同一事件只计一次**：用唯一约束防止重复加分。
- **认知池必须流动**：新认知 30 分钟内必须参与注入；逾期未注入的认知移出候选池，不再作为 bonus 候选。

## 四、具体修改方案

### 1. 数据表改动

新增 `bonus_log` 表：

```sql
CREATE TABLE bonus_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  dimension TEXT NOT NULL,
  event_type TEXT NOT NULL,
  source_task_id TEXT,
  cognition_id TEXT,
  reason TEXT,
  verified INTEGER DEFAULT 0,
  created_at TEXT NOT NULL,
  UNIQUE(dimension, event_type, source_task_id, cognition_id)
);
```

`nine_dim_progress` 中：

- `task_count`：保持只统计真实任务
- `bonus_count`：只从 `bonus_log` 汇总
- `count`：强制等于 `task_count + bonus_count`

如果数据库支持，建议把 `count` 改成生成列：

```sql
count INTEGER GENERATED ALWAYS AS (task_count + bonus_count) STORED
```

这样从物理上杜绝 `count` 与 `task_count + bonus_count` 不一致。

### 2. 代码改动

```python
def on_task_complete(task):
    # 只加任务数
    nine_dim_progress.task_count += 1

    # 认知进池，不加 bonus
    cognition_pool.add(task.outputs)

    # 每 10 任务或每轮结束触发通神评审
    if should_run_review():
        run_shen_tong_review()

def run_shen_tong_review():
    # 先刷新认知缓存，避免认知池只进不出
    refresh_cognition_injection_cache()

    candidates = cognition_pool.get_unused_candidates()

    for c in candidates:
        if is_high_value_insight(c):
            bonus_log.insert(
                dimension="通神维",
                event_type="cross_task_insight",
                source_task_id=c.source_task_id,
                cognition_id=c.id,
                reason=c.summary,
                verified=1
            )
            nine_dim_progress.bonus_count += 1

            # 标记已注入，防止下次重复计算
            cognition_pool.mark_injected(c.id)

    # 每次更新后回读验证
    sync_and_readback()
```

### 3. 防膨胀护栏

- 每次 `bonus_count += 1` 前，必须先成功写入 `bonus_log`。
- 每次同步后执行断言：

```python
assert count == task_count + bonus_count
assert bonus_count == bonus_log.count()
assert task_count == task_log.count()
```

- 如果某个事件类型占比异常，比如 `official_signal` 超过 30%，触发告警人工复核。

## 五、迁移步骤

### Step 0：冻结与备份

先暂停写入，防止迁移过程中产生脏数据。

```sql
LOCK TABLE nine_dim_progress WRITE;
CREATE TABLE nine_dim_progress_archive_2026 AS SELECT * FROM nine_dim_progress;
CREATE TABLE bonus_log_archive_2026 AS SELECT * FROM bonus_log;
```

### Step 1：重新校正 `task_count`

以真实任务日志为准，重算通神维任务数：

```sql
UPDATE nine_dim_progress p
SET task_count = (
  SELECT COUNT(*)
  FROM task_log t
  WHERE t.dimension = p.dimension
    AND t.is_real_task = 1
)
WHERE p.dimension = '通神维';
```

### Step 2：清空并归档旧 bonus

旧 `bonus_count=619` 是“有认知就 +1”产生的，不能直接作为新逻辑下的合法 bonus。

```sql
UPDATE nine_dim_progress
SET bonus_count = 0,
    count = task_count
WHERE dimension = '通神维';
```

历史 619 条先归档到 `bonus_log_archive_2026`，不删除，便于审计。

### Step 3：重放合法 bonus

从归档中筛选符合新语义的事件，重新写入 `bonus_log`：

```sql
INSERT INTO bonus_log (
  dimension, event_type, source_task_id, cognition_id, reason, verified, created_at
)
SELECT
  '通神维',
  event_type,
  source_task_id,
  cognition_id,
  reason,
  1,
  created_at
FROM bonus_log_archive_2026
WHERE event_type IN (
  'cross_task_insight',
  'reverse_logic_verified',
  'official_signal',
  'engineering_fix'
)
  AND verified = 1;
```

然后重新汇总：

```sql
UPDATE nine_dim_progress p
SET bonus_count = (
  SELECT COUNT(*)
  FROM bonus_log b
  WHERE b.dimension = p.dimension
    AND b.verified = 1
),
count = task_count + bonus_count
WHERE p.dimension = '通神维';
```

### Step 4：上线新计数逻辑

删除旧的“有认知就 +1 bonus”逻辑，替换为“任务完成只加 task_count + 认知入池，评审时按条件加 bonus”。

### Step 5：回读验证

每次同步后必须回读验证，不能跳过：

```sql
SELECT
  task_count,
  bonus_count,
  count,
  task_count + bonus_count AS expected_count
FROM nine_dim_progress
WHERE dimension = '通神维';
```

验证要求：

- `count == task_count + bonus_count`
- `bonus_count == bonus_log 中 verified=1 的数量`
- `task_count == task_log 中真实任务数量`

如果验证失败，立即回滚到迁移前备份。

> 回读验证时注意设置合理 timeout：B 模型 turbo 用 300 秒，A 模型用 600 秒；超时不能继续，必须重试或熔断。

## 六、验收标准

修复后通神维应满足：

1. `bonus_count` 从 619 降到个位数或符合实际高价值事件数量。
2. 每个 `bonus_count` 都能在 `bonus_log` 中找到对应记录。
3. `count = task_count + bonus_count` 永远成立。
4. 认知池不再只进不出：新认知 30 分钟内参与注入，注入后标记使用。
5. 官方免费额度放大、定向邀请测试等反向逻辑事件，以 `official_signal` 类型正常计入 bonus。

一句话总结：

> **bonus 不是“有认知就发”，而是“有通神才发”。**
