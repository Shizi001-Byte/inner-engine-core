# 任务类型: cog

从“认知质检SOP”角度看：**引擎运行中的坑，大多不是单点故障，而是缺少可验证的闭环。** 据此提炼 3 条可复用铁律：

---

## 铁律一：所有外部调用必须有分级超时与失败语义，禁止“裸等”

**坑：** API 调用超时导致整个任务超时；默认超时设置与模型规格不匹配，B 模型 turbo 和 A 模型所需时间完全不同，一旦超时没有兜底，任务直接失败。

**铁律：**  
按模型/任务类型预设超时：  
- B 模型 turbo：300 秒  
- A 模型：600 秒  

同时必须配置：超时重试、熔断、降级、可追踪错误码。超时不能只报“超时”，要能定位到具体调用链。

**验证方法：**  
通过故障注入模拟外部接口耗时 0.5x / 1x / 2x 正常耗时，压测后断言：  
- P95/P99 响应时间低于任务 deadline；  
- 超时后能返回可解释错误，且不阻塞后续任务；  
- 熔断后能自动恢复或降级到备用路径。

---

## 铁律二：认知池必须是“活水”，新认知必须在规定窗口内参与注入，禁止只进不出

**坑：** 认知池 1700+ 条，但新认知从不注入任务，也不影响调度，变成静态档案库。池子越大，反而越像死库，质检失去意义。

**铁律：**  
- 每 10 个任务或每轮调度结束，必须刷新认知缓存；  
- 新认知 30 分钟内必须进入注入候选池；  
- 旧认知需要按热度、时效、命中率进行淘汰或降权，避免认知池只增不活。

**验证方法：**  
在测试环境主动注入一条新认知，观察后续任务是否在 30 分钟内引用该认知。  
同时检查认知池的 freshness 分布：如果出现“池在增长但注入率=0”的时间窗口，立即触发告警。

---

## 铁律三：文件/对象同步判定必须用“内容顺序指纹”，禁止用文件名+大小+mtime 做等价判定

**坑：** 同文件名、同大小、同 mtime，但 block 顺序不同，被误判为已同步，导致数据错乱。

**铁律：**  
文件本质是索引：**path → 有序 block hash 列表**。  
只要满足以下任一条件，必须判为不同步：  
- block hash 列表不同；  
- block 顺序不同；  
- path 指向的 hash 链不一致。

**验证方法：**  
构造一组 fixture：同文件名、同大小、同 mtime，但 block 顺序不同，运行同步引擎，必须判定 mismatch。  
再对调 block 顺序，必须仍然判定 mismatch。  
只有 path、block hash 列表、block 顺序全部一致，才允许判为同步。

---

这三条铁律应写入认知质检 SOP：**每条规则必须配有验证方法，否则不算闭环。**
