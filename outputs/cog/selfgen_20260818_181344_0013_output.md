# 任务类型: cog

## 原则提炼

**先校准锚点，再优化链路。**

意思是：在开始任何任务排序、执行或排查之前，先确认那些“一旦错了，后续全部白做”的基准事实。锚点校准通过后，再谈优先级、再优化链路。

锚点的特征：

- 唯一且不可推导：比如项目 ID、目标、同步单位（block）
- 错一个，全盘皆错
- 校准成本很低，但排查成本很高

“项目 ID 看错导致 1 小时排查”就是典型：不是链路优化不够快，而是锚点错了，优化的是一条错误的链路。

---

## 如何应用到任务优先级排序

### 1. 排序前，先加一道“锚点校准”门禁

任务列表里最高优先级不是“最紧急的任务”，而是：

> **校准锚点**

具体校准：

- 项目 ID / 任务 ID 是否和目标一致？
- 当前环境、基线、上下文是否匹配？
- 最小同步单位是 block，不是 file；文件只是索引，是否已确认？

锚点没校准，后面的优先级排序全是空中楼阁。

### 2. 按“锚点依赖深度”排序

优先级从高到低：

1. **锚点校验类任务**  
   比如核对项目 ID、确认同步单位、验证关键假设。  
   这类任务一旦错了，后面的任务全部白做，所以必须排最前。

2. **block 级关键路径任务**  
   同步单位是 block，不是 file。  
   优先按 block 的依赖关系排序，而不是按文件改动量排序。

3. **文件级 / 展示层优化任务**  
   文件只是“有序 block id 列表”的索引。  
   文件层面看起来“完成了”，不代表 block 层面同步完成。  
   所以这类任务要等 block 链路完整后再排。

4. **打磨、体验优化类任务**  
   放在最后，因为它们的价值依赖前面链路正确。

### 3. 出现“排查 1 小时”征兆时

如果发现任务上下文不对，比如“改了没反应”“找不到变更”，不要继续优化链路，先停下来：

> 回到锚点，重新校准项目 ID / 同步单位 / 当前基线。

否则你只是在错误链路上加速，越优化越偏。

### 4. 用 block 作为任务排序单位

不要按“文件”排任务，要按“block”的同步状态和依赖关系排任务。

因为：

- 文件只是索引
- block 才是真正同步单位
- 文件级优先级会掩盖 block 级真实依赖

---

## 一句话落地

> 排任务前，先花 30 秒核对项目 ID；核对通过后，再谈优先级。  
> 宁可多校准一次，不要白做一小时。
