# 任务类型: cog

## 一、分层原则：决策串行，执行并发

在“脑体分离”架构中，系统被分为：

- **脑（决策层）**：负责感知、判断、决策，产生**决策事件**。
- **体（执行层）**：负责具体动作、调用外部API、处理物理或分布式副作用。
- **同步层**：负责把执行结果回传脑，让脑更新状态，但不产生新决策。

核心原则是：

> **决策必须串行，执行可以并发；优化只能发生在执行和同步层，不能发生在决策事件和全局顺序层。**

具体拆解如下：

| 层 | 原则 | 可优化点 | 不可优化点 |
|---|---|---|---|
| 决策层 | 串行、有序、可回溯 | 决策算法本身、模型推理速度 | 决策事件、全局顺序、决策上下文 |
| 执行层 | 并发、异步、可超时 | 并发度、批处理、超时策略、重试机制 | 跳过决策直接执行、改变决策顺序 |
| 同步层 | 最终一致、事件驱动 | 同步频率、增量同步、心跳、消息压缩 | 把同步结果当成新决策、用同步覆盖全局顺序 |

---

## 二、为什么引擎优化不能破坏脑体分离

### 1. 决策事件是全局顺序的锚点

如果执行层可以“自作主张”跳过决策事件，或者引擎优化把决策事件合并、延迟、丢弃，那么所有并发执行就失去了共同的参照系。

例如：两个并发请求同时到达，如果决策层没有为它们生成全局有序的决策事件，执行层可能同时修改同一份状态，导致竞态条件和数据不一致。

> 所以：**可以优化执行和同步，但绝不能优化掉决策事件和全局顺序。**

---

### 2. 执行并发是吞吐手段，决策串行是正确性保障

“决策串行”不等于性能差。决策串行保证的是：在任意时刻，系统对“应该做什么”只有一个权威答案。

而“执行并发”是为了提高吞吐：一旦决策产生，多个执行体可以并行推进。

如果为了性能，把执行并发“上提”到决策层，让多个决策同时发生，那么系统就从“脑指挥体”退化成“体各自为政”。

> 所以：**决策串行是“正确性”，执行并发是“效率”。二者分层，不能互相替代。**

---

### 3. 可检索的差异是协作网络的基础

协作网络不是从“连接”开始的，而是从“可检索的差异”开始的。

决策事件本身就是一种“差异”：

- 决策前：状态 A
- 决策后：意图 B
- 执行后：结果 C

如果引擎优化把决策事件“优化”没了，那么系统中就不存在可检索的差异，所有执行结果都变成无法归因的噪声，协作网络也就失去了起点。

> 所以：**优化必须保留“差异”的可检索性。连接可以后建，差异必须先存在。**

---

### 4. 历史教训：API 超时场景

在 B 模型 turbo 用 300 秒、A 模型用 600 秒超时的案例中，真正需要被保护的是“决策事件”。

- 当 API 调用超时时，系统需要知道：这是哪个决策事件触发的执行？
- 超时后应该重试、降级，还是重新决策？
- 如果决策事件被优化掉了，超时信息就无法对回到决策上下文，整个任务会卡死或错乱。

所以，合理的优化是：

- 执行层并发发起多个 API 调用；
- 同步层设置合理超时；
- 但决策事件必须保留，直到执行完成或被明确终止。

## 三、3 个应用场景

### 场景 1：AI Agent 多智能体协作

**结构**：

- 中央 Agent 作为“脑”，负责任务分解和决策。
- 多个子 Agent 作为“体”，并发执行子任务。

**可优化**：

- 多个子 Agent 并发运行；
- 对子 Agent 的 API 调用设置超时；
- 对结果进行异步汇总。

**不可优化**：

- 中央 Agent 的任务分解决策事件不能丢；
- 子任务的全局顺序不能重排；
- 如果某个子 Agent 超时，必须能通过原决策事件重新规划。

**效果**：即使某个子 Agent 失败，系统也能根据决策事件回退到“决策前状态”，而不是在混乱的并发结果中丢失主线。

---

### 场景 2：支付清结算 / 订单履约

**结构**：

- 风控和审批系统是“脑”，对每笔交易做串行决策。
- 支付渠道、账务系统、通知系统是“体”，并发执行。

**可优化**：

- 多个支付渠道并发调用；
- 批量对账；
- 同步状态时使用事件驱动。

**不可优化**：

- 交易审批决策事件不能跳过；
- 多笔交易的处理顺序不能乱；
- 如果渠道超时，必须能根据原决策事件发起退款或重试。

**效果**：即使支付渠道响应缓慢，系统仍能保持“每笔交易都有唯一决策记录”，对账和审计有据可查。

---

### 场景 3：分布式发布 / 变更管理

**结构**：

- 变更委员会或发布系统作为“脑”，生成版本决策。
- 各集群、节点作为“体”，并发执行部署。

**可优化**：

- 多集群并行部署；
- 状态上报合并；
- 失败节点自动重试。

**不可优化**：

- 发布决策事件不能丢；
- 变更的全局顺序不能乱；
- 不能因为某个节点执行快，就提前让后续变更生效。

**效果**：在大规模发布中，即使部分节点失败，系统仍能通过决策事件明确“当前期望状态是什么”，避免出现“脑已停止，体还在继续跑”的失控局面。

---

## 四、一句话总结

> **决策串行保证“想清楚”，执行并发保证“做得快”；优化只能优化“做”，不能优化掉“想”。决策事件和全局顺序，是脑体分离架构的命根子。**
