# 任务类型: cog

### 原则提炼

**先校准锚点，再优化链路。**

锚点错了，链路优化得越快，偏得越远。  
项目ID看错导致 1 小时排查，本质上是：**在错误锚点上做了大量“正确”的分析和操作**。

---

### 应用到任务优先级排序

在排序前，先校准以下锚点：

#### 1. 校准任务身份
- 排序必须用 `project_id + task_id` 作为唯一锚点，不能只靠日志片段、记忆或模糊名称。
- 如果锚点错，后续优先级、超时、重试全部会作用到错误任务上。

#### 2. 校准任务状态与版本
- 排序前读取当前 `state` 和 `version`。
- 只对允许调度的状态排序，例如 `PENDING` / `WAITING`。
- 如果排序后需要更新优先级或状态，必须带 `version` 做乐观锁：

```sql
UPDATE task
SET priority = ?,
    version = version + 1
WHERE id = ?
  AND version = ?;
```

#### 3. 校准执行参数
- 根据任务类型预设超时：
  - B 模型 turbo：300 秒
  - A 模型：600 秒
- 排序前确认任务对应的模型类型和 timeout 配置；如果配置错了，排序再合理，执行时也会超时失败。

---

### 优化链路

锚点校准后，再优化排序与调度链路：

1. 使用校准后的字段计算优先级：业务价值、截止时间、依赖关系、失败风险。
2. 排序结果只作为调度视图，不直接落库变更。
3. API 调用阶段可以并发，但后处理必须单消费者。
4. 所有 `task` 状态变更保持原子化，并带 `version` 乐观锁仲裁。

---

一句话：

> 排序前先问：这个 task 的 project_id 对吗？state 对吗？version 对吗？timeout 对吗？  
> 都对，再谈怎么排。否则就是在错误的锚点上，高效地制造混乱。
