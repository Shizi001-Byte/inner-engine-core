# 任务类型: cog

## 复盘：基建脚本禁用简化版

### 1. 教训本质

“基建脚本禁用简化版”这条认知本身是对的，但它在实际任务中**没有被激活**。

这不是“不知道”，而是“知道但没被用上”。  
更准确地说：**认知池没有空，但溯源链断了**——后续任务无法确认这条认知是否适用于当前场景，于是又回到了“写个简单 SQL 先跑通”的默认路径。

简化版 SQL 的典型危害：

- `SELECT *`：表结构增加/删除字段后，返回列顺序和数量变化，导致映射错位
- `INSERT INTO t VALUES (...)`：隐式依赖目标表列顺序，表结构一变，数据写入错列
- `UPDATE t SET col = ...` 不带明确条件：可能更新全表
- 隐式类型转换：字段类型变更后，线上才报错
- 可读性差：代码评审时看不出脚本到底操作了哪些字段

---

### 2. 根因分析

- 基建脚本中使用了“看起来更简单”的 SQL，省略了显式列名
- 目标表 schema 发生变更后，脚本没有同步适配
- 测试环境 schema 与生产不一致，测试通过但生产失败
- 执行前缺少“列匹配”校验
- 相关认知没有被注入到当前任务，导致踩坑

---

### 3. 认知更新

> **基建脚本中禁止一切简化版 SQL。所有 SQL 必须显式、完整、可审计。**

该认知的触发条件：

- 任何基建脚本的创建、修改、执行
- 任何涉及表结构变更的 SQL 任务
- 任何跨环境执行的数据库脚本

关联动作：执行下方检查清单，缺一不可。

---

## 基建脚本检查清单

### A. SQL 写法

- [ ] 禁止 `SELECT *`，必须显式列出所需字段
- [ ] 禁止 `INSERT INTO t VALUES (...)`，必须写为 `INSERT INTO t (col1, col2, ...) VALUES (...)`
- [ ] 禁止 `UPDATE t SET col = ...` 不带 WHERE，或没有明确主键条件
- [ ] 禁止 `DELETE FROM t` 不带 WHERE
- [ ] 所有字段名使用完整名称，避免歧义缩写
- [ ] 涉及类型转换时，显式写 `CAST(... AS ...)`
- [ ] 多表关联时，字段必须带表别名前缀

### B. Schema 对齐

- [ ] 执行前获取目标表当前 schema，与脚本字段逐一比对
- [ ] 检查字段数量：脚本字段数必须与目标表一致，或明确为字段子集
- [ ] 检查字段名：大小写、下划线、特殊字符完全一致
- [ ] 检查字段类型：长度、精度、是否允许 NULL、默认值
- [ ] 若表结构有历史版本，diff 新旧 schema，确认脚本兼容

### C. 环境与执行

- [ ] 测试环境 schema 必须与生产一致，或使用生产快照
- [ ] 执行前先跑 dry run / EXPLAIN，确认无隐式转换风险
- [ ] 涉及数据变更前，备份目标表或准备回滚脚本
- [ ] 多脚本依赖时，按依赖顺序执行，并在每个节点设置校验
- [ ] 执行后校验行数、抽样数据、关键字段值

### D. 流程与认知管理

- [ ] 基建脚本必须走代码评审，禁止直接改线上
- [ ] 每次脚本变更关联工单号/需求号，记录变更原因
- [ ] 复盘结论更新到认知池，并标注来源和触发条件
- [ ] 每 10 个任务或每轮结束，刷新认知缓存
- [ ] 新认知必须在 30 分钟内参与后续任务注入
- [ ] 若某条认知溯源链断裂，先标记“待验证”，重新验证后再引用

---

## 最后

这次教训说明：**认知池不只是用来“存”的，更是用来“接”的。**  
每条认知必须绑定触发条件和检查动作，否则 1700+ 条认知也只是静态档案，关键时刻依然救不了任务。

> 基建脚本禁用简化版，不是一句口号，而是一条可执行、可检查、可追溯的硬规则。
