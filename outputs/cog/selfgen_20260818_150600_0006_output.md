# 任务类型: cog

## 原则提炼

**「先校准锚点，再优化链路」** 的意思是：

> 系统行为被少数关键变量（锚点）支配；  
> 锚点一旦错，后续所有优化都是在错误基础上放大成本。  
> 所以任务排序时，**“校验锚点”必须排在“优化链路”之前**，不是可选项，而是前置依赖。

---

## 如何应用到任务优先级排序

### 1. 先列出当前任务的“锚点清单”

以你的场景为例，锚点可能是：

| 锚点 | 校验内容 |
|---|---|
| 项目/任务 ID | 是否看错相似 ID？ |
| 模型类型 | 用的是 B 模型 turbo 还是 A 模型？ |
| timeout | B 模型用 300 秒，A 模型用 600 秒？ |
| 控制权 | 是否由“脑（元控制器）”掌握？ |
| 归档模式 | 是否走“阴阳双轨”中的阳轨：引擎产出→分类→打标签→落盘→索引？ |

### 2. 在优先级矩阵中增加“锚点可信度”维度

不要只看“影响面”和“紧急度”，还要看：

- 这个任务的锚点是否已确认？
- 如果没确认，先做锚点校验任务。

排序规则：

- **P0：锚点校验/修正**  
  例如：确认项目 ID、确认模型 timeout、确认控制权归属。

- **P1：锚点已确认后的链路优化**  
  例如：优化归档链路中的分类准确率、打标签效率、落盘速度。

- **P2：与锚点无关的增强**  
  例如：美化日志、增加非关键监控。

---

## 具体应用示例

你提到“项目 ID 看错导致 1 小时排查”。

如果用这个原则排序，应该是：

1. **先** 校验项目 ID 是否正确  
2. **再** 优化某个链路步骤  

而不是：

1. 先优化链路  
2. 跑起来后发现 ID 错，再回头排查  

因为项目 ID 是锚点，锚点错，日志、路径、缓存、结果全错。  
优化链路再快，也只是更快地跑向错误结果。

---

## 执行建议

在每个任务开始前，用 5 分钟做一次“锚点校准”：

> 当前任务的关键锚点是什么？  
> 我确认过它是对的吗？  
> 如果有疑问，先停下来校准，再继续。

当链路出现异常时，也先查锚点，再查链路。

这样就能把“1 小时排查”变成“1 分钟校准”。
