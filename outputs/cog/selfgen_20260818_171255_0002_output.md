# 任务类型: cog

## 分层原则：决策串行、执行并发

**脑体分离**的本质是：

- **决策层（脑）**：串行、有状态、负责“下一步做什么”，拥有全局上下文和最终判断权。
- **执行层（体）**：并发、无状态、负责“具体怎么做”，只执行指令并返回结果。
- **接口**：决策层下发指令包，执行层返回观测报告；两者不共享内部状态，只通过结果闭环。

所以引擎优化的正确姿势是：**让执行层更快、更并发；让决策层更高效、更专注。而不是把决策权下放给执行层，也不是把执行压力上收到决策层。**

---

## 为什么引擎优化不能破坏脑体分离？

从认知质检 SOP 看，一旦破坏脑体分离，三个质检项会同时失效：

### 1. 认知不新鲜

决策串行，是为了保证每一步决策都基于**最新、最完整的观测结果**。

如果优化把“预判下一步”或“缓存决策结果”放到执行层，比如上一轮结果还没返回，就提前决定下一步动作，那么决策用的就是旧认知。  
这在基建脚本里等价于：**把对表结构的假设写死**。一旦数据源结构变化，系统不会感知，只会拿着旧认知继续跑，最后崩在不可预测的地方。

### 2. 闭环不开放

决策串行，意味着每个执行结果都要回到大脑确认后，才能进入下一步。

如果优化改成“执行层自动触发后续动作”——自动重试、自动补偿、自动调用下一个 API——那么闭环就被打开了。  
开环之后，错误会沿着并发路径扩散，大脑无法在关键节点拦截，任务变成“失控的流水线”。

### 3. 调用不设限

执行并发，必须由大脑统一分配额度、超时、权限。

如果优化让执行层自己决定调用哪些 API、调用多少次、等待多久，就会出现：

- API 调用超时，任务无法按时返回；
- 重试风暴，费用失控；
- 副作用无法撤销。

按历史经验：**B 模型 turbo 设 300 秒超时，A 模型设 600 秒超时**。这是执行层的边界，不是决策层的枷锁。  
如果大脑直接等执行体，一个慢任务就会卡死整个决策循环；但如果执行层自行无限重试，又会绕过所有限制。

## 3 个应用场景

### 场景 1：多源检索问答

- **决策串行**：大脑先解析问题，决定检索关键词和检索范围。
- **执行并发**：同时查询多个知识库、搜索引擎、文档库；每个检索任务独立超时。
- **结果汇合**：所有结果返回后，大脑再串行综合、判断、生成答案。

**优化不能做**：不能在没有检索结果时，就并行生成多个候选答案。  
否则大脑会把未经验证的假设当作事实，产生幻觉；同时多个生成任务并发，还会放大 API 超时和成本风险。

### 场景 2：批量 API 编排 / 数据管道

- **决策串行**：大脑按依赖关系规划任务 DAG，决定当前批次可以执行哪些节点。
- **执行并发**：无依赖的节点并行执行；每个节点有独立超时上限（turbo 300 秒、A 模型 600 秒）。
- **状态更新**：每个关键节点完成后，大脑收集结果、更新状态、再下发下一批。

**优化不能做**：不能把整个 DAG 的执行直接塞进大脑进程。  
否则一个节点超时，就会阻塞所有后续决策，甚至拖垮整个任务。

### 场景 3：人工审批与自动预备

- **决策串行**：大脑等待审批人明确给出“同意 / 拒绝”的决策。
- **执行并发**：等待期间，执行层可以并发做预检、生成报告、检查风险、准备材料。
- **最终执行**：只有审批通过后，大脑才下发真正的执行指令。

**优化不能做**：不能把“预检”当成“已批准”，提前执行审批后的动作。  
否则就破坏了脑体分离，导致未授权操作在后台悄悄发生，违背闭环和调用设限原则。

---

## 结论

引擎优化的目标，是在**不破坏脑体分离**的前提下，让执行层更高效、更可靠，让决策层更清晰、更稳定。

一句话记住：

> **决策必须串行，因为每一步都要基于最新事实；执行可以并发，因为每个动作都只是观测和尝试。优化只能加速“体”，不能代替“脑”。**
