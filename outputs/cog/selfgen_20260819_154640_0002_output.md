# 任务类型: cog

## 决策串行、执行并发：分层原则与脑体分离架构的不可破坏性

### 一、核心分层原则

1. **决策层（脑）严格串行**  
   所有涉及变更判定、冲突裁决、幂等校验、规范生成的逻辑，必须以单一事件源（如 `change_id + 内容哈希`）为锁，按顺序处理。任何并行决策都会导致竞态条件，破坏“先验证、再分工、后沉淀规范”的同步链。

2. **执行层（体）充分并发**  
   一旦决策完成，Gitee 提交、飞书上传、Supabase 存储同步等具体动作彼此无依赖，可并发执行，用独立超时（B 模型 300s、A 模型 600s）和冷却重试机制兜底。

3. **纽带不可分割**  
   `change_id + 内容哈希` 是决策与执行之间的唯一凭证。执行结果必须回写并关联该凭证，供决策层做后续幂等判断和规范沉淀。若引擎优化试图绕过这一凭证，哪怕执行再快，也会造成状态错乱。

### 二、为什么引擎优化不能破坏脑体分离架构

| 破坏方式 | 后果 | 正确做法 |
|---|---|---|
| 把决策逻辑下沉到并发执行节点 | 多个节点同时判定“是否重大变更”，产生重复规范或漏判 | 决策保留在串行中心，执行节点只接收已裁决的任务包 |
| 为提升吞吐量让执行节点自决策重试 | 网络抖动时重复上传/重复提交，破坏幂等性 | 重试由决策层统一调度，执行层只报告结果和状态码 |
| 用“更快的哈希匹配”替代内容哈希验证 | 只比对元数据或部分内容，误判变更状态，后续同步错乱 | 哈希计算仍走完整验证流程，可优化算法但不可跳过验证步骤 |
| 并发执行时共享可变规范状态 | 规范沉淀被覆盖或部分写入 | 规范写入只能在串行阶段完成，执行阶段只读取快照 |

### 三、3个应用场景

**场景 1：多人同时提交代码到 Gitee**  
- 串行决策：按 `change_id` 顺序校验提交内容哈希，判断是否触发飞书通知和 Supabase 更新。  
- 并发执行：不同提交的文件上传到飞书、同步到 Supabase 并行进行，各用独立超时。  
- 不破坏架构：若优化引擎将提交判定分散到多线程并行，就会同时产生两份“规范沉淀”，导致飞书目录混乱。

**场景 2：同一变更同时需要更新飞书文件、Supabase 存储和触发 Webhook**  
- 串行决策：先验证哈希，确认变更唯一性，生成统一执行清单（包含飞书路径、Supabase bucket、Webhook 载荷）。  
- 并发执行：三个动作并行调用，任一失败只上报不重试，由决策层统一决定冷却后重试。  
- 不破坏架构：若引擎优化让每个执行端自行决定“是否重试”，飞书和 Supabase 会收到重复写入，哈希匹配失效。

**场景 3：规范沉淀（如自动生成 API 文档）需要汇总多次变更结果**  
- 串行决策：每次变更后，将结果追加到规范草稿，但最终发布必须在所有执行完成后由决策层统一编译。  
- 并发执行：各变更的飞书上传和存储同步并发进行，但规范草稿写入被串行锁保护。  
- 不破坏架构：若引擎优化允许规范编译并发执行，多线程写入同一文档会产生半更新状态，破坏后续所有变更的验证基准。

---

**结论**：引擎优化只能优化“执行”的传输效率、超时策略和并发调度，绝不能触碰“决策串行”这一底线。`change_id + 内容哈希` 是脑体之间的唯一神经束——切断它，再快的并发也只是制造混乱。
