# 任务类型: cog

“先校准锚点再优化链路”这句话的核心本质是：**方向比速度更重要，验证前提比优化过程更关键。**

在“项目ID看错导致1小时排查”的案例中：
*   **锚点缺失/错误**：没有校准“项目ID”这个最基础的前提（方向）。
*   **链路盲目优化**：基于错误的项目ID去查日志、看链路、排查代码，无论排查手段多高效（优化链路），最终都是在错误的方向上狂奔，导致1小时的无用功。

将这一原则应用到**任务优先级排序**时，可以推导出一套**“锚点驱动型”优先级排序法**。具体应用步骤如下：

### 一、 重新定义任务分类：锚点任务 vs 链路任务

在排优先级前，先将待办任务分为两类：

1.  **锚点任务（方向性/前提性任务）**：
    *   **特征**：一旦做错或遗漏，会导致后续所有工作偏航或失效；通常不复杂，但极其关键。
    *   **例子**：确认项目ID/需求版本、对齐目标口径、确认接口字段定义、环境变量配置。
2.  **链路任务（执行性/优化性任务）**：
    *   **特征**：在方向正确的前提下，提升效率、完善细节、交付成果的任务。
    *   **例子**：编写业务代码、优化SQL查询速度、重构代码结构、写测试用例。

### 二、 优先级排序的四步法（A-LPT模型）

按照以下顺序对任务进行排序：

#### Step 1：识别锚点（Identify Anchors）- 最高优先级 P0
在每天/每个Sprint开始排期时，第一件事不是看哪个任务最紧急，而是**把所有任务的前置依赖（锚点）全部拎出来**。
*   问自己：“如果这个前提没确认，我后面的工作会不会全白费？”
*   **应用案例**：接到Bug单，第一优先级不是去修Bug（优化链路），而是先核对Bug单上的项目ID、环境、复现步骤是否准确（校准锚点）。

#### Step 2：校准锚点（Calibrate Anchors）- 优先执行
锚点任务无论多简单，都必须排在日程表的最前面优先处理。
*   **应用案例**：花1分钟核对并确认正确的项目ID，或者花10分钟和产品经理确认一个模糊的需求边界。这叫“磨刀不误砍柴工”。

#### Step 3：梳理主干链路（Link Core Path）- 次高优先级 P1
锚点确认后，优先排那些能打通核心流程的任务，而不是边缘优化的任务。
*   **原则**：先跑通主流程（哪怕很慢、有Bug），再回头优化。
*   **应用案例**：接口联调（主干链路）优先于代码重构（链路优化）。

#### Step 4：优化支线链路（Optimize Branches）- 低优先级 P2/P3
当核心链路跑通后，再排那些“锦上添花”或“提升速度”的任务。
*   **应用案例**：提升查询速度从2秒优化到0.5秒、完善UI动效。

### 三、 场景实战：如何用该原则排一天的工作

假设你今天有5个任务，如何排序？

| 任务编号 | 任务内容 | 任务类型 | 优先级排序及理由 |
| :--- | :--- | :--- | :--- |
| **Task A** | 研发某新功能的API接口 | 链路执行 | **P2**。属于链路执行，需要等B的参数确认。 |
| **Task B** | 和前端对齐API的入参字段 | **锚点校准** | **P0**。字段不对，前后端全白干，必须最先做。 |
| **Task C** | 修复昨天遗留的线上Bug | 链路执行 | **P1**。但前提是先核实Bug单的ID和环境（微锚点）。 |
| **Task D** | 优化旧接口的慢SQL查询 | 链路优化 | **P3**。不影响主干，属于优化阶段。 |
| **Task E** | 确认本次上线的项目版本号 | **锚点校准** | **P0**。排错版本号会导致代码合错分支，必须最先做。 |

**最终执行顺序**：E -> B -> (核对C的Bug ID) -> C -> A -> D

### 四、 避坑指南：防止“伪锚点”陷阱

在应用该原则时，要注意区分“真锚点”和“伪锚点”：
*   **真锚点**：不可逆或返工成本极高的前提（如：项目ID、需求版本、架构选型）。**必须立即停下手中所有事去校准。**
*   **伪锚点**：可以通过工具自动校验或后续低成本修改的细节（如：代码格式、变量命名）。**不要在前期过度校准，应放到链路优化阶段（如写代码时让Lint工具自动处理）。**

### 总结金句
在任务排期时，永远记住：**“不要用战术上的勤奋（优化链路），掩盖战略上的懒惰（不校准锚点）。”** 看错ID花1小时排查的教训，本质上是把“执行优先级”排在了“验证优先级”前面。以后排任务，先排“防呆验证”，再排“低头干活”。
