# 任务类型: cog

## 原则：先校准锚点，再优化链路

**核心含义**  
任何排序、调度、流程优化，都只是“手脚”层面的提速；如果“大脑”里的锚点错了——比如目标、范围、项目ID、验收标准——后面跑得再快也是错的方向。  
项目ID看错导致1小时排查，不是排查动作慢，而是锚点没校准就开始优化“排查链路”。

---

## 应用到任务优先级排序

### 1. 排序前必须先校准的5个锚点

| 锚点 | 校准问题 | 错误示例 |
|---|---|---|
| 目标锚点 | 这个任务服务于哪个业务目标？ | 把“内部工具优化”排到“客户交付”前面 |
| 交付锚点 | 完成的标准是什么？ | 以为“写完代码”=完成，实际要“上线验证” |
| 身份锚点 | 任务所属项目ID、版本、阶段是否正确？ | 把A项目的任务当B项目处理 |
| 依赖锚点 | 前置条件是否成立？阻塞项是否已清除？ | 前置没完成就排高优先级，导致空转 |
| 价值锚点 | 对最终结果的实际贡献是多少？ | 用“紧急”代替“重要”，被噪音带偏 |

### 2. 校准后再优化链路

锚点确认无误后，才可以使用这些“手脚”优化手段：

- 用 **RICE / WSJF** 做量化排序  
- 用 **Eisenhower矩阵** 区分紧急/重要  
- 用 **批处理** 合并同类任务  
- 用 **自动化脚本** 处理重复性检查  
- 用 **看板/依赖图谱** 可视化流动瓶颈  

这些手段只能让“已经正确的顺序”执行得更快，不能纠正“错误的顺序”。

---

## 案例映射：项目ID看错 → 优先级排序错乱

**错误过程**  
1. 拿到任务列表，未核对项目ID  
2. 按“紧急程度”直接排序  
3. 实际在另一个项目的上下文里排优先级  
4. 花1小时排查“为什么任务执行结果不符合预期”  

**正确做法**  
1. 先花2分钟核对每个任务的项目ID、目标、验收标准  
2. 确认锚点一致后，再进入排序计算  
3. 如果发现ID不符，立即停止排序，先修正任务归属  
4. 修正后再套用排序模型，避免后续1小时排查  

---

## 落地检查清单（每次排序前过一遍）

- [ ] 这个任务的“项目ID/上下文”我核实过吗？  
- [ ] 我知道这个任务做完后，谁在什么时间、看到什么结果？  
- [ ] 这个任务依赖的前置条件是否真实存在？  
- [ ] 如果把这个任务排到最高优先级，会牺牲哪个目标？  
- [ ] 排序后，是否只优化执行动作，不再修改目标本身？

---

## 一句话总结

**先校准“为什么做、做什么、属于谁”，再优化“怎么做、先做谁、做多快”。**  
锚点错了，优化越强，错误越快；锚点对了，链路优化才真正值钱。
