# 任务类型: cog

## 复盘：基建脚本禁用“简化版”SQL

### 一、事件复盘

**现象**  
基建脚本中使用了“简化版”SQL，导致建表/迁移后出现列不匹配：目标表列名、列顺序、列类型与源表或下游预期不一致，后续同步任务报错，甚至数据错位。

**根因**  
1. 用 `SELECT *` / `CREATE TABLE AS SELECT` / `INSERT INTO ... VALUES(...)` 省略了显式列定义，把正确性寄托在“当前列顺序”上。  
2. 源表或中间表列顺序一变，目标表就会静默错位。  
3. 简化版脚本省掉了“字段映射决策”的留痕，出了问题无法快速定位是谁在哪个环节做的映射。  
4. 绕过版本化迁移直接改表，破坏了“全局顺序”，导致其他环境无法复现和对齐。

**核心教训**  
- 基建脚本不是“能跑就行”，而是要被后续任务长期依赖的契约。  
- 简化版SQL省掉的不是复杂度，而是**决策事件**和**全局顺序**。  
- 可以大胆优化“执行”和“同步”，但绝不能优化掉“决策事件”和“全局顺序”。

---

### 二、检查清单

#### A. Schema 显式化

- [ ] DDL 中显式列出全部列名、列类型、约束，禁止用 `SELECT *` 建表/视图  
- [ ] `INSERT` 必须带列清单，`VALUES` 顺序与列清单一一对应  
- [ ] `UPDATE` / `DELETE` 使用主键或唯一键定位，不依赖物理顺序  
- [ ] 临时表/中间表也要显式定义列，禁止裸写 `SELECT * INTO`  
- [ ] 列变更时明确新旧列映射关系，不依赖 ordinal position  

#### B. 类型与约束匹配

- [ ] 源列与目标列类型一致，或显式 `CAST` 且确认无损  
- [ ] 检查 `varchar` 长度、`decimal` 精度、时间时区、字符集/排序规则  
- [ ] 确认 `NULL/NOT NULL`、默认值、自增、主键、唯一键  
- [ ] 警惕隐式类型转换，不能“看起来能跑”就算通过  

#### C. 版本与执行顺序

- [ ] 每个基建脚本纳入迁移版本管理，有唯一版本号和时间戳  
- [ ] 按全局顺序执行，禁止跳过前置迁移  
- [ ] 脚本幂等：重复执行不产生副作用或报错  
- [ ] 执行前有状态检查：目标表是否存在、列是否存在、数据量/分布是否符合预期  
- [ ] 禁止在“生产环境手改表结构但不补脚本”  

#### D. 决策留痕与可检索性

- [ ] 脚本注释记录字段映射、转换规则、清洗逻辑、选择依据  
- [ ] 变更记录包含执行人、时间、版本、影响对象  
- [ ] 关键决策写入脚本头部或关联 PR，确保“差异”可检索  
- [ ] 将本次“禁用简化版SQL”认知注入认知池，30分钟内参与后续任务；每10任务或每轮结束刷新认知缓存，避免认知池只进不出  

#### E. 验证与回滚

- [ ] 在 staging 执行后比对 `information_schema`：列名、列顺序、类型、约束  
- [ ] 执行后做 smoke test：`DESC`、`SELECT TOP 1`、count、checksum  
- [ ] 有回滚脚本，或至少有备份/重建方案  
- [ ] 下游同步任务配置列不匹配、数据差异监控  
- [ ] 如果通过 API 执行脚本，设置合理超时：B模型turbo用300秒，A模型用600秒；超时后先查状态再决定是否重试，避免重复执行  

---

### 三、后续行动

1. 把“基建脚本禁用简化版SQL”写入代码评审门禁，作为强制检查项。  
2. 在 CI/SQL lint 中增加规则：禁止 `SELECT *`、禁止无列 `INSERT`、禁止未版本化 DDL。  
3. 对存量基建脚本做一次扫描，找出所有简化版SQL并整改。  
4. 将本次复盘结论注入认知池，确保后续任务自动带上这条约束，而不是只入库不参与调度。
