# 任务类型: cog

基于已有认知锚定，不重复论证。以下三条直接作为认知质检SOP的强制检查项：

---

## 铁律一：认知池必须是“活水”，30分钟不注入新认知即判异常

**坑：** 认知池已积累1700+条，但新认知从不注入任务，也不影响调度，最终变成静态档案库。

**铁律：** 每完成10个任务或每轮调度结束，必须刷新认知缓存；所有30分钟内产生的新认知，必须出现在后续任务的候选认知集中。

**验证方法：**

1. **日志审计**：每次任务输出 `candidate_cognition_ids` 和 `new_cognition_created_at`；扫描最近30分钟新增的认知ID，若后续任务候选集缺失该ID，立即告警。
2. **时间戳巡检**：检查认知缓存的最大 `last_refresh_ts`，超过30分钟未刷新即判不合格。
3. **引用率抽样**：连续10个任务中，若引用“30分钟内新认知”的任务数为0，判定认知注入流程失效。

---

## 铁律二：API 超时必须分级配置，超时后必须走降级/重试/失败三档，不能空等

**坑：** 统一超时策略导致任务未在规定时间内返回，B模型turbo和A模型互相拖累。

**铁律：** B模型turbo超时设置为300秒，A模型超时设置为600秒；每个模型族必须有独立超时配置，禁止用默认值或通配值覆盖。

**验证方法：**

1. **配置比对**：检查 `timeout_config` 与模型族映射关系；B-turbo=300s，A=600s，缺失或混用即不合规。
2. **耗时分位数监控**：统计各模型实际调用耗时的 p99/p999；若p99超过配置超时的80%必须告警，超过100%必须调优。
3. **故障演练**：注入延迟响应到超时临界点，断言任务能在配置超时内返回明确错误或降级结果，且不阻塞其他 worker。

---

## 铁律三：锁粒度必须小于单次 API 调用，严禁“一把大锁锁全部流程”

**坑：** V7.5 方舟效能引擎是多线程 API 调用 + 串行后处理，曾试图用一把大锁锁住全流程，结果并发被串行化，慢接口虽不持锁阻塞其他 worker，但大锁让吞吐归零。

**铁律：** 锁只能保护共享内存中的短临界区（如认知池索引、状态位），不能包裹网络 IO 或整个后处理链路；慢接口等待必须在锁外。

**验证方法：**

1. **线程转储检查**：压测中人为制造一个慢接口（sleep 2×超时），抓取 thread dump；多数 worker 线程应处于 RUNNABLE 或网络等待状态，不能 Blocked 在同一个 monitor 上。
2. **锁竞争指标监控**：监控 `lock_wait_time` 和 `blocked_thread_count`；正常压力下，锁等待耗时占任务总耗时比例必须 <1%。
3. **吞吐对照实验**：同一批任务分别跑“大锁版”和“短临界区锁版”；慢接口注入下，大锁版吞吐下降 >50% 即违规，短锁版吞吐下降应 <10%。

---

以上三条直接作为认知质检SOP的固定检查点，每次引擎版本变更、认知池策略调整、API配置修改后必须执行对应验证。
