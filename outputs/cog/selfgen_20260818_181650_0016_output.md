# 任务类型: cog

复盘“基建脚本禁用简化版”认知：

**根因**：简化版 SQL 依赖隐式列顺序 / `SELECT *` / 省略 `WHERE block_id`，导致目标表结构变化时发生列错位或列缺失。  
**本质**：把“文件/表”当成了同步单位，绕过了“block id 列表”这一最小核对单位。

基于锚点：**同步单位是 block，不是 file；文件只是有序 block id 列表的索引**。以下三条门禁，全部以 block id 列表为唯一标尺。

---

## 门禁一：同步门禁

- [ ] 基建脚本禁止出现 `SELECT *`
- [ ] 禁止 `INSERT INTO t VALUES (...)`，必须写成 `INSERT INTO t (block_id, col1, col2, ...) VALUES (...)`
- [ ] 禁止 `UPDATE` / `DELETE` 不带 `WHERE block_id IN (...)`
- [ ] 执行前从 `information_schema` 导出源/目标完整列清单，比对列名、列顺序、类型、约束，确认无差异
- [ ] 待同步集合必须生成有序 `block_id` 列表，所有 DML 都通过该列表圈定范围
- [ ] 每个批次记录处理的 `block_id` 范围，便于中断续跑和审计

## 门禁二：差异分析门禁

- [ ] diff 查询以 `block_id` 为关联键，不按文件名/表名比较
- [ ] 对比源/目标 `block_id` 集合，确认差集为空
- [ ] 对比关键列值，使用显式列名做 `EXCEPT` / `MINUS` 或 checksum 校验
- [ ] 校验脚本同样禁止 `SELECT *`，否则列不匹配会被隐藏
- [ ] 核对列数：源/目标 `COUNT(DISTINCT block_id)` 一致，关键列 `COUNT(col)` 一致

## 门禁三：回滚判定门禁

- [ ] 回滚脚本必须与正向脚本共用同一个 `block_id` 列表，不得重新扫描全表
- [ ] 反向 DML 显式列出列名，禁止使用简化版 SQL
- [ ] 回滚前先用门禁二做差异分析，确认受影响 `block_id` 集合与预期一致
- [ ] 回滚后再次基于 `block_id` 列表做 diff，确认源/目标列值一致

---

**一句话检查清单**：  
基建脚本中，任何 SQL 如果回答不了“我操作了哪些 block_id、哪些列、列顺序是否显式”，就是简化版，必须禁用。
