# 任务类型: cog

针对“基建脚本禁用简化版导致简化版SQL列不匹配”这一事件，这是一次典型的**“隐式契约破坏”**与**“环境不一致”**引发的线上/测试故障。

以下是对该事件的深度复盘认知总结，以及为防止此类问题再次发生而整理的检查清单。

---

### 一、 认知复盘与教训沉淀

#### 1. 事件本质：“便利性”与“一致性”的博弈
*   **简化版的诱惑与陷阱**：基建脚本简化版通常为了快速验证或本地开发便利，省略了部分字段（如审计字段`create_time`、`update_time`、软删除字段`is_deleted`等）或默认约束。简化版SQL同样基于这种“默契”编写。两者在本地开发环境形成了一个**脆弱的隐式契约**。
*   **契约的单方面撕毁**：当禁用基建脚本简化版（即强制要求使用全量标准版建表/初始化脚本）时，底层的Schema发生了变化（字段增多或顺序改变），但简化版SQL未同步失效或升级，直接导致`Column not found`或数据错位插入。

#### 2. 核心教训
*   **教训一：环境隔离不能靠“简写”**。简化版脚本本质上制造了多套环境（本地/标准）的Schema不对等。任何“简化版”基建都是一颗定时炸弹，一旦合并到非简化环境，不匹配问题必然爆发。
*   **教训二：禁止使用 `SELECT *` 与隐式 `INSERT`**。简化版SQL之所以报错，往往是因为写了 `INSERT INTO table VALUES (...)`（依赖列顺序和数量）或 `SELECT *`（导致下游解析错位）。强类型、显式指定列名是SQL编写铁律。
*   **教训三：基建变更未形成闭环**。禁用简化版基建脚本是一个“上游变更”，但没有触发对下游所有依赖项（包括历史简化版SQL）的扫描和回归测试，说明CI/CD流水线缺乏依赖校验。

---

### 二、 预防列不匹配检查清单

为避免后续再次发生类似问题，请在涉及基建脚本变更、SQL编写及上线流程时，严格执行以下检查清单：

#### 📌 模块一：基建脚本变更检查
- [ ] **1. 变更影响面评估**：禁用或修改基建脚本前，是否已全局搜索所有依赖该脚本的环境配置和初始化代码？
- [ ] **2. 差异比对（Diff）**：是否对“简化版”与“完整版”脚本进行了结构比对？明确了新增、删除或修改了哪些字段？
- [ ] **3. 破坏性变更标注**：本次变更是否会导致旧代码（依赖旧Schema的SQL）报错？如果是，是否已通知所有相关开发者？
- [ ] **4. 镜像与环境同步**：禁用简化版后，本地开发环境、测试环境、预发环境的数据库是否全部强制刷新为标准全量Schema？

#### 📌 模块二：SQL编写与审查规范
- [ ] **1. 禁绝隐式依赖**：所有 `INSERT` 语句是否显式指定了列名？（例如：`INSERT INTO t (id, name) VALUES (...)`，严禁 `INSERT INTO t VALUES (...)`）。
- [ ] **2. 禁绝 `SELECT *`**：所有查询是否明确列出了所需字段？禁止使用 `SELECT *`，防止下游消费者因字段增减导致索引错位或反序列化失败。
- [ ] **3. ORM框架映射检查**：如果使用MyBatis、JPA等ORM框架，实体类的字段是否与标准版数据库Schema完全一致？是否有遗留的`@Transient`或被忽略的字段？
- [ ] **4. 动态SQL兜底**：针对可能存在多版本表结构的情况，是否在代码层面做了兼容处理（如先查表结构再拼装SQL，或使用严谨的异常捕获机制）？

#### 📌 模块三：CI/CD 与自动化测试检查
- [ ] **1. Schema 对齐校验**：CI流水线中是否加入了表结构比对步骤？在跑单元测试或集成测试前，强制校验当前代码中的SQL依赖字段是否存在于最新标准Schema中。
- [ ] **2. 全量回归测试**：基建脚本变更后，是否强制触发了核心业务链路的全量自动化回归测试？
- [ ] **3. 静态代码扫描**：是否引入了SQL静态扫描工具（如SonarQube配合SQL插件），识别出不符合规范的SQL写法（如 `SELECT *`、缺列的 `INSERT`）？
- [ ] **4. 预发环境冒烟**：上线前是否在预发环境（与生产Schema一致）执行了涉及该表的核心业务场景冒烟测试？

#### 📌 模块四：长期治理机制
- [ ] **1. 清理历史技术债**：是否制定了计划，将代码库中残存的所有“简化版SQL”和“快捷建表逻辑”彻底清理并重构？
- [ ] **2. 单一数据源原则**：是否确立了基建脚本唯一合法来源原则？即只允许存在一份标准Schema定义，开发环境的快速初始化必须通过工具裁剪数据而非裁剪表结构。
- [ ] **3. 变更发布SOP**：是否将“基建脚本禁用/变更”升级为高危变更，要求必须走完整的发版流程及DBA复核？

### 总结
“简化版”本意是为了提升效率，但在基建层面，**一致性永远优先于便利性**。基建脚本的任何风吹草动，都必须以“破坏性变更”的最高标准来审视，强制下游SQL进行显式对齐，从根源上消除列不匹配的隐患。
