# 任务类型: cog

## 复盘：基建脚本禁用简化版

### 一句话结论

**基建脚本是“契约”，不是“快捷方式”。**  
简化版 SQL 为了省事省略了显式列名、列序、类型、约束等关键信息，导致源/目标表列不匹配，必须禁止。

---

### 根因

- 使用 `SELECT *`，依赖表结构的物理列序
- 使用 `INSERT INTO table VALUES (...)`，不写列清单，靠位置映射
- 使用 `CREATE TABLE AS SELECT`，隐式继承列类型/顺序
- 使用 `NATURAL JOIN` / `USING`，依赖同名同序，缺少显式列契约
- 手写列清单后，未与生产 schema 做 diff，导致漂移
- 认为“能跑通 = 正确”，忽略了列不匹配的静默风险

---

## 检查清单

### 一、脚本编写阶段

- [ ] 禁止 `SELECT *`，必须显式列出所需列
- [ ] 禁止 `INSERT INTO table VALUES (...)`，必须写 `INSERT INTO table (col1, col2, ...) VALUES (...)` 
- [ ] `UPDATE` / `DELETE` 必须带明确 `WHERE` 条件
- [ ] `CREATE TABLE` / `ALTER TABLE` 必须显式声明列名、类型、长度、默认值、约束
- [ ] 禁止用 `CREATE TABLE AS SELECT` 作为基建建表方式
- [ ] JOIN 必须显式写 `ON` 条件，禁止 `NATURAL JOIN` / `USING`

### 二、列映射核对阶段

- [ ] 源表与目标表的**列名**逐一比对
- [ ] 源表与目标表的**列顺序**逐一比对
- [ ] 源表与目标表的**列类型**逐一比对
- [ ] 检查长度、精度、标度、是否可空、默认值
- [ ] 检查字符集、排序规则、collation 是否一致
- [ ] 检查是否存在隐藏列、生成列、分区列、主键/唯一键

### 三、上线前验证阶段

- [ ] 在测试环境用与生产等价的 schema 跑通
- [ ] 对源表和目标表执行 `COUNT(*)`，核对行数
- [ ] 对关键列做 `SUM` / `MIN` / `MAX` / checksum 比对
- [ ] 抽样比对多行全字段，不能只看行数
- [ ] 测试数据必须覆盖空值、超长值、边界值、重复值
- [ ] 上线前 diff 脚本预期 schema 与生产实际 schema

### 四、同步判定原则

- [ ] 只要发现源/目标列名、列序、类型、约束任一不一致，**必须判为不同步**
- [ ] 不能因为“当前没报错”就放行
- [ ] 不能因为“文件名、大小、mtime 相同”就认为文件相同；必须比较 block 顺序
- [ ] 同样，不能因为“结果集行数相同”就认为数据正确；必须比较列级契约

### 五、认知与流程保障

- [ ] 基建脚本必须版本化管理，禁止“简化版”覆盖完整版
- [ ] 任何“列不匹配”事件发生后，立即回溯相关脚本
- [ ] 将“基建脚本禁用简化版”写入评审检查项
- [ ] 该认知必须进入活跃认知池，不能只躺在静态档案里
- [ ] 每 10 个任务或每个迭代结束，刷新认知缓存
- [ ] 新认知必须在 30 分钟内参与任务上下文注入

---

### 与已有认知锚定的关系

> “索引是索引，block 才是真正的数据单位。”

简化版 SQL 中的 `SELECT *`、`VALUES` 位置映射，本质上只是“索引式”的简化；  
真正的数据契约是**显式列名、列序、类型、约束**——这些才是“block”。  
所以，基建脚本必须按“block 级”标准写，不能按“索引级”简化写。
