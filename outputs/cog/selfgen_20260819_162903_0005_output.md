# 任务类型: cog

## 核心原则

**“先校准锚点再优化链路”**：任何任务优先级排序，必须先验证四个锚点——**身份锚点、资源锚点、基线锚点、目标锚点**；锚点不准，排序越优，偏差越大，最终导致无效执行或算力浪费。

---

## 应用到任务优先级排序的具体操作

### 1. 排序前：强制锚点校验

所有任务进入优先级排序前，先过“锚点校验器”，校验失败直接打回，不参与排序：

- **身份锚点**：`project_id`、`task_id`、`request_id` 三方绑定，确保不会出现“项目ID看错”导致排错任务。
- **模型锚点**：任务使用的模型是 A 还是 B turbo，决定超时预算——B turbo 用 300 秒，A 用 600 秒。
- **资源锚点**：当前稳定 3 路并发是否已满；若某一路正在执行“自进化闭环”（检测重复率→生成新模板→注入任务池→验证生效），该路必须标记为**不可抢占**。

### 2. 排序中：锚点分数驱动排序

每个任务按以下公式计算**锚点优先级分**，而不是凭感觉排：

```
锚点优先级分 = 身份置信度 × 0.3  
            + 基线偏差度 × 0.3  
            + 成本可执行度 × 0.2  
            + 闭环贡献度 × 0.2
```

- **身份置信度**：ID 绑定完整、依赖数据齐全。
- **基线偏差度**：当前任务“检测重复率”与目标阈值的差距，差距越大越优先。
- **成本可执行度**：预估耗时 < 该模型 timeout，且当前算力预算可覆盖。
- **闭环贡献度**：任务是否能触发“生成新模板→注入任务池→验证生效”的自进化闭环，能触发的优先。

排序必须遵守硬约束：**任何情况下不超过 3 路并发**；分数相同时，按 FIFO 先进先出。

### 3. 排序后：动态重校准

不能一次排序跑到底。每完成一个任务，立即更新锚点：

- 项目 ID 缓存是否已刷新；
- 当前重复率基线是否变化；
- 3 路并发状态是否释放；
- 新模板是否已注入任务池并生效。

然后对剩余任务重新排序，保证后续任务始终基于最新锚点执行。

## 避坑映射

| 历史失败经验 | 锚点校准后的预防措施 |
|---|---|
| 项目 ID 看错导致 1 小时排查 | 排序入口增加身份锚点校验，耗时 < 1 秒，避免无效排程 |
| API 调用超时 | 按模型类型预设 timeout：B turbo 300 秒，A 模型 600 秒，超时任务自动降级重试 |
| 引擎空转 | 若待办任务锚点不合法，不进入生成/验证链路，直接进入人工复核，避免算力空耗 |

---

## 一句话结论

**任务优先级排序不是“哪个着急排哪个”，而是“先校准锚点，再按锚点分数排序”。锚点包括任务身份、3 路并发资源、重复率基线、模型超时成本。锚点校准是低成本高杠杆动作，能直接避免“项目 ID 看错导致 1 小时排查”这类无效消耗。**
