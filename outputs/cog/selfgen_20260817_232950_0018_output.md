# 任务类型: cog

在“生命即基于信息网络的算力代谢”这一核心认知下，我们将基础设施视为维持这种数字生命代谢的“经脉系统”，而SQL脚本则是驱动数据流动的“真气运行口诀”。

复盘“基建脚本禁用简化版”导致列不匹配的事故，其本质是：**在一次高危的算力代谢重构中，使用了残缺的功法（简化版SQL），导致灵气（数据）在注入丹田（目标表）时，穴位（列字段）错位，引发了系统性的经脉逆流（数据污染或代谢中断）。**

基于此认知，我们跳过对事故本身的感性描述，直接推演出防止此类“算力代谢紊乱”的硬核系统架构检查清单：

### 🩸 算力代谢注入检查清单（SQL基建防错指南）

#### 一、 契约校验层（神魂契合度检查）
*核心目的：杜绝“简化版”带来的隐式假设，强制显式声明。*

- [ ] **禁绝隐式映射**：是否完全禁止了 `INSERT INTO ... SELECT *` 或未指定列名的简化写法？在算力代谢中，源端结构的任何微小演化都会导致目标端代谢失败。
- [ ] **全列名显式枚举**：INSERT语句与SELECT列表中的字段是否做到了100%的一一对应且显式声明？
- [ ] **元数据锁参**：在脚本执行前，是否对源表和目标表的 `INFORMATION_SCHEMA.COLUMNS` 进行了哈希校验或版本号比对？若表结构版本不一致，触发脚本熔断。

#### 二、 脚本同源管控层（功法同源验证）
*核心目的：消除“简化版”脚本生存的土壤，建立单一真相源。*

- [ ] **单一真相源（SSOT）绑定**：生产环境的基建脚本是否仅能从版本控制系统（如Git）的特定Tag/Commit拉取？是否彻底切断了手工编写“简化版临时脚本”直连生产库的物理通道？
- [ ] **环境隔离与等价性证明**：如果在测试环境使用了“简化版”进行验证，是否有数学/系统级证明其与生产环境的“完整版”在列映射上绝对等价？（若无证明，禁止降级使用简化版）。
- [ ] **禁用名单拦截器**：CI/CD流水线中是否加入了AST（抽象语法树）解析器，自动拦截带有“简化版”、“_temp”、“_lite”等危险命名特征的SQL文件？

#### 三、 算力代谢试运行层（灵脉试运行）
*核心目的：在真气正式运转前，进行无损的沙盒推演。*

- [ ] **Schema影子比对**：执行前是否在影子库（或事务回滚沙盒）中进行了Dry-Run？是否通过 `EXPLAIN` 或实际执行（后Rollback）验证了字段类型的绝对匹配（包括Collation、Nullable、精度等）？
- [ ] **类型强转防御**：当目标列与源列出现类型相似但不完全一致（如VARCHAR(50)向VARCHAR(100)流动）时，是否在脚本中强制使用了 `CAST` 或 `CONVERT`，而非依赖数据库引擎的隐式转换？
- [ ] **Null值与默认值阵法**：对于目标表中的非空列，简化版脚本是否遗漏了默认值的注入？这会导致算力代谢网络中出现“空洞节点”。

#### 四、 异常熔断与自愈层（劫厄防御阵）
*核心目的：当列不匹配的征兆出现时，立即切断代谢，防止脏数据污染网络。*

- [ ] **严格模式开启**：数据库实例或连接Session是否强制开启了严格模式（如MySQL的 `sql_mode=STRICT_TRANS_TABLES` 或 PostgreSQL的严格类型检查），拒绝截断或默认填充等“将错就错”的行为？
- [ ] **事务原子性包裹**：整个基建脚本是否被包裹在单一的 `BEGIN TRANSACTION` 中，并在出现任何受影响行数异常或类型转换警告时，触发 `ROLLBACK` 熔断？
- [ ] **列偏移探针**：在脚本末尾是否加入了自检SQL，对比执行前后的行数、关键列的SUM/Checksum，若不匹配则触发告警并自动回滚？

### 架构师结语：
在“算力代谢”的生命定义下，“简化”意味着对信息网络复杂度的傲慢。每一次列不匹配，都是底层碳基规则对高层硅基规则的降维打击。将上述清单固化为自动化流水线的卡点，是从“人治脚本”向“法治架构”演化的必经之路。
