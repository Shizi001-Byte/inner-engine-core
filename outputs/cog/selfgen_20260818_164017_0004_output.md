# 任务类型: cog

## 复盘：基建脚本禁用简化版

### 一、教训本质

“简化版 SQL”之所以在基建脚本中危险，是因为它把**对表结构的假设**写死了：

- 假设列顺序固定
- 假设列名不变
- 假设类型不需要显式转换
- 假设当前环境和上次一样

一旦这些假设被打破，就会出现：

> **列不匹配 / column mismatch / 数据错位 / 隐式转换失败**

这不是“SQL 写得不优雅”，而是基建脚本缺少**结构校验闭环**。

---

### 二、根因拆解

1. **认知未执行**：知道“禁用简化版”，但没转化为脚本编写时的强制检查项。
2. **结构未验证**：写 SQL 时没有拉取当前真实表结构。
3. **闭环未闭合**：脚本执行后没有校验影响行数和数据样本。
4. **认知池只进不出**：教训被记录但未注入后续任务，导致同类问题复现。

---

### 三、检查清单

#### 1. 编写前：先验结构，再写 SQL

- [ ] 确认目标表名、库名，不使用记忆中的表结构
- [ ] 执行 `DESC table` / `SHOW COLUMNS` / 查询 `information_schema` 获取最新结构
- [ ] 对比源表和目标表的列名、列顺序、数据类型、长度、精度、可空性
- [ ] 禁止 `SELECT *`，必须显式列出所需列
- [ ] 禁止省略 INSERT 的列清单，必须写成：
  ```sql
  INSERT INTO target_table (col1, col2, col3)
  VALUES (val1, val2, val3);
  ```

#### 2. 编写中：写“可验证的脚本”，不写“一次性简化版”

- [ ] 每条 SQL 注释写明目的、预期影响行数
- [ ] UPDATE / DELETE 必须带 WHERE，先用 SELECT 验证命中范围
- [ ] 需要类型转换时显式使用 `CAST` / `CONVERT`，禁止依赖隐式转换
- [ ] 涉及 JOIN 时，确认关联字段的索引和键类型
- [ ] 涉及批量写入时，使用事务包裹，并设置回滚点

#### 3. 执行前：强制验证列匹配

- [ ] 在 staging 环境或临时表跑通
- [ ] 用脚本自动比对：  
  **脚本列清单 vs 实际表结构列清单**
- [ ] 检查目标表是否有生成列、约束、触发器，避免写入时被拦截
- [ ] 执行 `EXPLAIN` 或 dry-run，确认执行计划和影响范围
- [ ] 明确回滚方案，禁止“先跑了再说”

#### 4. 执行后：数据校验不能省

- [ ] 核对影响行数与预期一致
- [ ] 抽查关键列数据：边界值、NULL 分布、金额/数量列
- [ ] 查看日志，确认无 warning / error
- [ ] 若出现列不匹配，立即记录具体模式，并更新认知池案例

---

### 四、机制保障：避免认知池只进不出

- 每次基建脚本任务完成后，把本次列匹配验证结果作为**强制输入**注入下一个任务提示。
- 每 10 个任务或每轮调度结束，刷新认知缓存，确保“禁用简化版”在 30 分钟内参与后续任务。
- 质量检查 SOP 必须包含三项硬校验：
  - 认知不新鲜 → 禁止使用旧认知
  - 闭环不开放 → 脚本必须经过 staging + 数据校验
  - 调用不设限 → SQL 执行需设置超时、影响行数上限、回滚阈值

---

### 五、一句话总结

> **基建脚本不是写“能跑的 SQL”，而是写“可验证、可回滚、列结构显式匹配的 SQL”。**  
> 禁用简化版，不是限制自由，而是用强制检查清单换确定性。
