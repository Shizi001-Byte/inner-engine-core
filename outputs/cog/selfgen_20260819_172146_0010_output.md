# 任务类型: cog

复盘结论：**“基建脚本禁用简化版SQL”这条认知正确，且必须升级为“基建脚本 = schema 契约”**。  
简化版SQL省略列名、类型、约束、冲突处理，会让迁移后的真实表结构与代码/同步逻辑不一致，最终在增量同步链路的 Supabase 认知池入口爆发 `column mismatch`。

以下检查清单，直接接入增量同步 ChainTask 的基建脚本环节：

---

## 一、写 SQL 前

- [ ] 先查真实 schema，不凭记忆写脚本  
  ```sql
  SELECT column_name, data_type, is_nullable, column_default
  FROM information_schema.columns
  WHERE table_name = '认知池表名';
  ```
- [ ] 用 `pg_dump --schema-only` 拉当前结构，和预期结构 diff  
- [ ] 确认本次变更会影响哪些同步链路：变化检测、只传差异、冲突处理、认知池写入、同步指标

## 二、DDL 必须完整显式

- [ ] `CREATE TABLE` 必须列出全部列、类型、默认值、约束  
  - 禁止：先建表，字段以后再说  
- [ ] `ALTER TABLE ADD COLUMN` 必须带完整列定义  
  - 错误：`ALTER TABLE t ADD COLUMN IF NOT EXISTS source;`  
  - 正确：`ALTER TABLE t ADD COLUMN IF NOT EXISTS source text NOT NULL DEFAULT '';`
- [ ] 列类型必须精确匹配应用层实际类型  
  - `text` / `varchar(n)` / `uuid` / `bigint` / `jsonb` / `timestamptz` 不能靠隐式转换  
- [ ] 约束必须显式命名  
  - `CONSTRAINT pk_cognitive_pool PRIMARY KEY (id)`  
  - `CONSTRAINT uq_source_path UNIQUE (source_path)`  
- [ ] 不要用 `CREATE TABLE IF NOT EXISTS` 当版本迁移用  
  - 同名表 + 不同列 = 静默列不匹配

## 三、DML 禁止省略列清单

- [ ] `INSERT` 必须显式列名  
  - 错误：`INSERT INTO t VALUES (...)`  
  - 正确：`INSERT INTO t (id, content, source, created_at) VALUES (...)`  
- [ ] `UPSERT` 必须完整写 `ON CONFLICT` 目标和 `DO UPDATE SET`  
  - 错误：`ON CONFLICT DO NOTHING` 后就不管其他字段  
  - 正确：  
    ```sql
    INSERT INTO t (id, content, source, updated_at)
    VALUES ($1, $2, $3, now())
    ON CONFLICT (id) DO UPDATE
    SET content = EXCLUDED.content,
        source = EXCLUDED.source,
        updated_at = now();
    ```
- [ ] `UPDATE` 必须显式指定列，禁止用 `*` 或位置映射  
- [ ] `SELECT` 禁止 `SELECT *`  
  - 同步读取时列顺序变化会直接导致字段错位  
  - 应显式列出认知池需要的列：`id, content, source, updated_at`

## 四、版本化与幂等

- [ ] 每个基建脚本必须有版本号/迁移文件名，并进入迁移记录表  
- [ ] 脚本必须可重复执行，且结果一致  
  - `IF NOT EXISTS` 只是幂等手段之一，不能替代 schema diff  
- [ ] 禁止在生产环境直接执行临时“简化版 SQL”  
  - 所有变更必须走 migration / 基建脚本仓库

## 五、测试与发布

- [ ] 先在 staging 库跑一遍，对比 `pg_dump --schema-only` 的 diff  
- [ ] 用真实形状的数据做集成测试，尤其是 upsert 和冲突处理  
- [ ] 测试存量数据兼容性  
  - 新增列是否可空/有默认值  
  - 删除/重命名列是否影响下游同步指标  
- [ ] 发布后监控同步指标  
  - 如果出现 `column mismatch`、失败 upsert、延迟上升，立即回滚或打补丁迁移

## 六、机制保障

- [ ] 基建脚本必须 code review，禁止“简化版”被合并  
- [ ] 每次基建任务前，强制检索认知池中“基建脚本禁用简化版”这条认知  
- [ ] 每 10 个任务或每轮结束，刷新认知缓存，确保这条教训持续参与注入，而不是变成静态档案

---

核心一句话：**基建脚本里的 SQL 不是写给数据库看的草稿，是写给未来所有同步任务的契约。简化版省下的时间，最终都会在 column mismatch 上报回来。**
