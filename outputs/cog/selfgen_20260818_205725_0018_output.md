# 任务类型: cog

## 复盘：简化版 SQL 导致列不匹配

**核心结论**：基建脚本没有“简化版”，只有“显式版”和“事故版”。  
列不匹配的本质不是 SQL 语法错误，而是脚本对表结构的“静态假设”被现实击穿——表结构变了，脚本没变，认知池也没刷新。

### 根因链条

1. 使用 `SELECT *` / `INSERT INTO t VALUES (...)` / 依赖列顺序的 SQL  
2. 表结构变更：加列、删列、改列名、改类型、调整列序  
3. 脚本未同步更新  
4. 测试环境 schema 与生产不一致  
5. 执行前没有做 schema 校验  
6. 失败后没有快速补位/回滚机制，导致任务阻塞或数据错位

---

## 检查清单

### 一、SQL 编写规范

- [ ] 禁止 `SELECT *`，必须显式列出所需列名  
- [ ] `INSERT` 必须带显式列名列表：  
  `INSERT INTO t (id, name, created_at) VALUES (?, ?, ?)`  
- [ ] `VALUES` 的数量、顺序必须与列名列表完全一致  
- [ ] 禁止依赖表默认列顺序  
- [ ] `UPDATE` 的 `SET` 和 `WHERE` 中的列名必须与当前 schema 精确匹配  
- [ ] 多表 JOIN 时，所有列使用 `表别名.列名`，避免歧义  
- [ ] 禁止依赖隐式类型转换，日期/数字/字符串必须显式 `CAST`  
- [ ] 表结构变更后，旧 SQL 不得复用，必须重写并重新校验

### 二、Schema 感知与刷新

- [ ] 执行前获取目标表最新 schema：  
  `DESC table` / `SHOW CREATE TABLE` / `information_schema.columns`  
- [ ] 核对 SQL 中的列名、列数、列序与目标表完全一致  
- [ ] 检查是否有新加列：若为 `NOT NULL` 且无默认值，`INSERT` 必须包含该列  
- [ ] 检查是否有已删除列：SQL 中不能引用已删除列  
- [ ] 检查列类型是否变更：如 `VARCHAR` 改 `TEXT`、`INT` 改 `BIGINT`  
- [ ] 测试环境与生产环境 schema 必须 `diff` 一致，或明确差异且脚本兼容  
- [ ] 将本次 schema 变更写入认知池，并触发 30 分钟内刷新，避免认知池只进不出

### 三、执行与容错

- [ ] 先在小样本/空表上试运行，确认列映射和数据类型  
- [ ] 备份目标表数据或准备可回滚快照  
- [ ] 设置合理 timeout：B 模型 turbo 用 300 秒，A 模型用 600 秒  
- [ ] 高优先级任务失败时，立即从 standby 队列拉取 Batch 任务补位，不原地重试同一简化脚本  
- [ ] 开启执行日志，记录实际 SQL 和绑定参数  
- [ ] 监控关键错误码：  
  `Unknown column`、`Column count doesn't match`、`Data too long`、`Incorrect integer value`  
- [ ] 若发生部分写入，立即停止后续批处理，先回滚再排查

### 四、事后复盘

- [ ] 对目标表做数据抽样/行数校验，确认没有列错位  
- [ ] 将“简化版 SQL + 列不匹配”失败模式加入坑库  
- [ ] 更新基建脚本模板，强制显式列名  
- [ ] 检查认知池是否吸收了本次教训，并在后续任务中实际影响调度与 SQL 生成，而不是变成静态档案库

---

## 与既有认知锚定的联动

- **standby 队列**：显式 SQL 也失败时，不要原地重试；调度器立即用 standby Batch 任务补位，保证 token 不闲置。  
- **认知池刷新**：每次 schema 变更都是新认知，必须像九转玄功的“转”一样循环注入，否则基建脚本会退化为静态“简化版”，最终被列不匹配击穿。  
- **九转玄功映射**：本次复盘处于“执行监控 → 失败补位 → 复盘入库”的关键环节；缺了 standby 补位和认知反哺，检查清单只是纸面功夫。
