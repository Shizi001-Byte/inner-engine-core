# 任务类型: cog

### 原则提炼

**“先校准锚点，再优化链路”** =  
先确认坐标系的原点是对的，再谈路径怎么走；否则所有优化都是在错误的地图上跑。

项目ID看错导致1小时排查，就是典型的“锚点错误”：项目ID是后续所有查询、定位、对比、修复的基准。基准错了，链路越优化，偏得越远。

---

### 应用到任务优先级排序

#### 1. 任务先分两类

- **锚点校准类任务**：确认项目ID、版本、环境、依赖基线、判定标准、block 顺序规则等。
- **链路优化类任务**：并发、缓存、超时、重试、哈希算法、传输效率等。

**锚点校准类任务永远排在链路优化类任务之前。**

#### 2. 排序公式

```
优先级 = 锚点错误代价 × 锚点不确定度 - 链路优化收益 × 优化置信度
```

其中锚点错误代价为高时，该任务直接置顶；如果锚点不确定，再大的优化收益也不值得先做。

#### 3. 具体落地方式

- 每个任务进入执行队列前，先打标签：`已校准` 或 `未校准`。
- `未校准` 的任务不允许进入“进行中”。
- 如果任务涉及同步，锚点是 **path → 有序 block hash 列表**，不是文件名、大小、mtime。
- 如果发现“同文件名、同大小、同 mtime，但 block 顺序不同”，立即停止优化链路，先校准“顺序”这个锚点。

#### 4. 任务排序示例

现有任务：

- A：优化 block hash 对比算法  
- B：修复某项目同步延迟  
- C：确认当前要处理的项目ID和版本  
- D：核对同步判定是否基于“有序 block hash”  

排序结果：

```
C → D → A → B
```

因为 C、D 是锚点校准，A、B 是链路优化。  
C、D 不确定时，A、B 做了也可能白做。

---

### 一句话总结

> **先花5分钟确认“我到底在动哪个项目、哪个文件、按什么规则判一致”，再花50分钟优化链路。  
> 锚点不定，链路全错。**
