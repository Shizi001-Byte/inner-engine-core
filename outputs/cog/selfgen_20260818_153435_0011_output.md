# 任务类型: cog

基于已有锚定：**脑体分离的边界是“决策事件/全局顺序”与“执行/同步”的边界**。基建脚本属于“执行/同步”层，所以不能用“决策层看起来等价”来简化；它必须显式、可重放、可校验。

## 复盘：基建脚本禁用简化版

### 现象
基建脚本中使用了简化 SQL，例如：

- `SELECT *`
- `INSERT INTO t VALUES (...)` 不写列名
- `CREATE TABLE AS SELECT` 隐式继承列
- `UPDATE` / `MERGE` 依赖源表列顺序
- 视图或同步任务中使用 `SELECT * EXCEPT` 等隐式列引用

源表结构变化后，目标表列顺序、列名、类型、数量不一致，导致数据错位、类型转换失败、同步中断。

### 根因
- 用“少写代码”代替“明确契约”
- 把列映射的校验责任交给了数据库的隐式规则
- 测试环境通过，生产环境因列顺序不同而失败
- 缺少执行前 schema 校验，导致错误在同步阶段才暴露

### 边界教训
基建脚本不是一次性决策，而是长期执行的同步逻辑。简化版 SQL 在“决策事件”层面可能等价，但在“执行/同步”层面不具备可校验性。  
因此：**基建脚本禁用简化版，列映射必须显式声明，脚本必须幂等且可校验。**

---

## 检查清单

### 一、编写阶段
- [ ] 所有 SQL 显式列出列名，禁止 `SELECT *`
- [ ] `INSERT` 必须写成 `INSERT INTO target_table (col1, col2, ...) VALUES (:val1, :val2, ...)`
- [ ] `CREATE TABLE AS SELECT` 必须改为：先显式 `CREATE TABLE`，再显式 `INSERT INTO ... (col1, col2, ...) SELECT col1, col2, ... FROM source`
- [ ] 表名、列名、schema 名使用全限定名：`db.schema.table`
- [ ] 禁止依赖列顺序的写法，禁止隐式类型转换
- [ ] 每个迁移/基建脚本有版本号、依赖、校验和（checksum）

### 二、执行前
- [ ] 用 `information_schema.columns` 对比源表和目标表：
  - 列名是否一致
  - 列顺序是否一致
  - 数据类型、长度、精度、可空性、默认值是否一致
- [ ] 确认目标表是否有新增/删除列，源表是否有列变更
- [ ] 在预发布环境使用**生产结构的副本**执行，不能只用开发库
- [ ] 验证脚本幂等性：重复执行结果一致
- [ ] 设置合理超时时间，避免任务挂死；若调用模型/API，按模型预设：turbo 300 秒，A 模型 600 秒，超时后先查状态，不盲目重试

### 三、执行后
- [ ] 校验行数、校验和/哈希、抽样数据，不能只看执行返回码
- [ ] 检查日志中是否有列名、列类型、列数相关错误
- [ ] 将列映射基线记录到版本库，作为后续变更的比对基准
- [ ] 如果出现列不匹配，立即阻断同步并告警，不能自动重试掩盖问题

### 四、治理与认知更新
- [ ] 基建脚本必须经过 code review，禁止简化写法
- [ ] CI 中增加静态检查：扫描 `SELECT *`、无列名 INSERT、隐式转换、依赖列顺序的 SQL
- [ ] 每次源表结构变更后，自动触发列匹配测试
- [ ] 本次复盘和检查清单作为新认知注入认知池，30 分钟内参与后续任务调度；每 10 任务或每轮结束刷新认知缓存，避免认知池只进不出、变成静态档案库
