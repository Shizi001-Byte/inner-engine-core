# 任务类型: cog

### 分层原则：决策串行、执行并发

- **决策层（脑）**：全局唯一、串行处理。负责所有需要全局视角、状态一致性和顺序敏感的判断（如冲突裁决、顺序规划、状态提交）。
- **执行层（体）**：多副本、并发处理。负责机械性、可并行化的实际动作（如传输、计算、写入），只接受决策层下发的明确指令，不自行产生全局决策。
- **约束**：任何引擎优化（如增加线程池、批量流水线、动态调度）都只能作用于执行层，不能把决策层的串行逻辑“优化”成并发或分布式。因为决策一旦并发，就会出现竞态、顺序错乱、重复或丢失，最终破坏系统的一致性基座。

---

### 为什么引擎优化不能破坏脑体分离架构

1. **决策是状态变化的唯一来源**：并发执行只是放大决策的吞吐，不能替代决策。若优化让多个执行单元绕过决策层直接“智能”调整顺序，相当于制造了多个大脑，导致全局状态分叉。
2. **串行决策是正确性的最低成本保证**：用单点顺序消除“谁先谁后”的争议，避免引入锁、事务、分布式共识等复杂机制。优化执行层能获得同样甚至更高的性能，而无需牺牲正确性。
3. **执行并发是性能的主要来源**：真正耗时的是物理操作（网络、磁盘、计算）。将这些操作并行化，同时保持决策串行，可以在正确性不变的前提下获得接近线性的吞吐提升。

---

### 三个应用场景

#### 1. 文件同步引擎中的 block 同步顺序决策
- **决策串行**：同步引擎的“脑”维护每个文件的 `path → 有序 block hash 列表`，并串行决定每个 block 的同步顺序、冲突处理、版本提交。因为**同文件名、同大小、同 mtime，但 block 顺序不同必须判为不同步**，顺序决策必须全局唯一。
- **执行并发**：实际上传/下载多个 block 时，可多线程并发进行，只要最终按决策层指定的顺序重组文件。
- **优化边界**：若为了提速，让每个传输线程“自己决定”先传哪个 block，或并发提交文件状态，就会导致 block 顺序错乱，最终误判同步结果。

#### 2. 分布式任务调度中心的作业分配
- **决策串行**：调度中心（脑）串行扫描待处理队列，根据资源、优先级、依赖关系，为每个任务分配唯一执行节点和编号。
- **执行并发**：各执行节点收到指令后，并行运行各自的任务，上报结果。
- **优化边界**：如果把调度逻辑做成多节点并发决策，两个节点可能同时把同一个任务分配给不同执行者，造成重复执行；或者因全局状态不一致而漏配任务。引擎优化应集中在“提高单个决策节点的处理能力”或“让执行节点更高效”，而不是让决策也并发。

#### 3. 数据库事务日志与写入落盘
- **决策串行**：数据库的“脑”是事务日志（WAL），事务提交顺序、回滚判定、隔离级别决策必须严格串行，以保证 ACID 和恢复一致性。
- **执行并发**：日志确定后的数据页写入、索引更新、缓存刷新可以并行执行，利用多核/多磁盘 IO 提升性能。
- **优化边界**：若优化引入“乱序提交”或“并行事务决策”来提升写入吞吐，就会破坏日志的全局顺序，导致崩溃后无法恢复。合理的优化是让日志写入本身更快（如 group commit），或让数据落盘并发，而不是让事务决策并发化。
