# 任务类型: cog

## 复盘：基建脚本禁用简化版

### 一、教训定性

“简化版 SQL”是基建脚本中引发**列不匹配**的高频根因。  
典型表现：

```sql
-- 错误示例：依赖 SELECT * 建表/插数
CREATE TABLE target AS SELECT * FROM source;

-- 错误示例：INSERT 不写列清单
INSERT INTO target VALUES (1, 'xx', 2.5);

-- 错误示例：用 SELECT * 直接灌入目标表
INSERT INTO target SELECT * FROM source;
```

这些写法在“当时能跑通”，但一旦源表结构变化、字段顺序调整、新增字段，就会造成：

- 目标表列顺序错位
- 插入数据落到错误字段
- 类型隐式转换导致精度丢失
- 下游脚本在运行时才发现 schema 不匹配

**本质是：把 schema 一致性建立在“位置”和“通配符”上，而不是建立在“显式列名 + 类型契约”上。**

---

### 二、核心结论

> 基建脚本必须“显式、完整、可 diff”。  
> 禁止用简化写法换取临时效率，简化 SQL 是技术债，不是效率。

---

## 检查清单

### 1. 通用规范

- [ ] 所有 `INSERT` / `SELECT` / `UPDATE` 均显式写出列名
- [ ] 禁止使用 `SELECT *` 出现在任何基建脚本中
- [ ] 禁止使用 `INSERT INTO t VALUES (...)` 不跟列清单
- [ ] DDL 必须包含完整字段定义：名称、类型、长度、精度、默认值、NOT NULL、注释
- [ ] 所有表名、列名统一使用小写蛇形，避免大小写/引号依赖
- [ ] 脚本头部注明：用途、源表版本、目标表版本、执行环境、变更人

---

### 2. 列映射检查

- [ ] 逐个核对源列 → 目标列，保证**列名显式映射**
- [ ] 确认列数一致，且不依赖“第几列”
- [ ] 如有类型转换，必须显式 `CAST`，并确认无精度/长度损失
- [ ] 若源表新增字段，必须同步更新脚本，禁止依赖通配符自动带上
- [ ] 禁止 `INSERT INTO t1 SELECT * FROM t2`；如历史存在，立即改写为显式列名

---

### 3. Schema 一致性检查

- [ ] 执行前对比源表/目标表结构：`DESC` 或 `information_schema.columns`
- [ ] 使用 `CREATE TABLE AS SELECT` 时，必须额外确认最终表结构是否与预期 DDL 完全一致
- [ ] 若需要主键、索引、注释、默认值，必须改用显式 `CREATE TABLE` + `INSERT`
- [ ] 执行 `ALTER TABLE` 前，先执行 `SHOW CREATE TABLE` 留档
- [ ] 执行后再次对比表结构，确认没有意外列增减

---

### 4. 数据验证

- [ ] 先在小数据集/临时表试运行
- [ ] 校验目标表与源表的行数是否一致
- [ ] 校验关键字段的 `SUM`、`COUNT`、去重数等聚合值
- [ ] 抽样检查若干条记录，确认列没有错位
- [ ] 对 `NULL` 分布做检查，防止非空约束被隐式破坏

---

### 5. 流程与版本

- [ ] 基建脚本必须提交到版本库，禁止在服务器上直接手写 SQL
- [ ] 变更必须经过 review，reviewer 重点检查是否出现“简化写法”
- [ ] 维护一张“表结构基线表”，每次变更后更新
- [ ] 多环境（dev / staging / prod）使用同一份 schema 校验脚本，防止环境漂移
- [ ] 每次基建变更后，将本次经验刷新注入认知池，避免认知只进不出

---

### 一句话记忆

**显式列名是基建脚本的底线；通配符和位置映射是列不匹配的温床。**
