# 任务类型: cog

# 复盘：基建脚本禁用简化版SQL——列不匹配教训

## 一、事故回顾

简化版SQL（省略列定义、用通配符、跳过约束）导致**实际表结构与预期不一致**，下游消费方按完整schema取列时出错。

---

## 二、检查清单

### A. DDL完整性（建表/改表）
- [ ] 使用完整`CREATE TABLE`，禁止省略列定义的简化写法
- [ ] 每列显式声明：列名、类型（含精度/长度）、约束（NOT NULL/DEFAULT等）
- [ ] 索引、外键、唯一约束必须完整声明，不可省略
- [ ] `ALTER TABLE`显式列出新增/修改列，不依赖隐式推断

### B. DML列对齐
- [ ] `INSERT`必须显式指定列名，禁止纯值按位置插入
- [ ] `SELECT`禁止用`*`，显式列出所需列名
- [ ] `UPDATE`的SET子句列名与表定义逐一核对

### C. 来源审查
- [ ] 禁止从文档/注释/示例中复制"省略版"DDL当生产用
- [ ] 任何标注"简化"、"临时"、"quick"的SQL必须二次审查
- [ ] 迁移脚本与回滚脚本同等要求，回滚也用完整DDL

### D. 执行后校验
- [ ] 执行后用`PRAGMA table_info()`或`information_schema`读取实际结构
- [ ] 三重校验：**列数、列名、列类型**
- [ ] 与预期schema做diff，有差异即**fail-fast**，不继续后续步骤

### E. 流程约束
- [ ] 简化版SQL仅允许出现在探索/调试阶段，进入基建脚本前必须替换为完整版
- [ ] 基建脚本入库前，由校验脚本自动对比DDL与实际表结构

---

## 三、核心原则

> **简化版SQL是探索工具，不是基建材料。** 凡进入持久化层的SQL，必须自描述、可校验、可diff。
