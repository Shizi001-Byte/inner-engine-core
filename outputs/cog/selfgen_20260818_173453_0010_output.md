# 任务类型: cog

## 复盘：基建脚本禁用简化版

### 一、事故链条

某次基建脚本为了“省事”，使用了简化版 SQL：

- `INSERT INTO table VALUES (...)` 不写列名；
- `SELECT *` 直接取全列；
- 依赖表的物理列顺序做下游映射。

结果表结构变更（新增/调整列）后，脚本报错：

- `Column count doesn't match value count at row 1`
- 或 `Unknown column 'xxx' in 'field list'`
- 或下游数据错位，但脚本本身没有报错，造成更隐蔽的数据污染。

更关键的是：这条“简化版不能用”的教训没有被及时注入后续任务，认知池里虽然有了这条认知，但新任务仍然在写同类 SQL。

---

### 二、根因

1. **隐式依赖列顺序/数量/类型**  
   简化版 SQL 把正确性绑定在“当前表结构”上，一旦表结构变化，脚本立刻失效。

2. **缺少验证门**  
   基建脚本没有 schema 校验，没有在运行前确认“列存在、列顺序、列类型”。

3. **认知池只进不出**  
   教训被记录但没有被激活，没有在 30 分钟内参与注入，也没有在每 10 个任务/每轮结束时刷新，导致它变成静态档案。

4. **“简化版”这个命名本身是危险信号**  
   它暗示“少写一点没关系”，会让 review 者放松警惕。

---

### 三、认知更新

旧认知：  
> 基建脚本可以用简化版 SQL，少写列名更高效。

新认知：  
> 基建脚本必须显式、可校验、可追踪。任何不指定列名的 SQL 都视为危险信号，默认禁止。

锚定到可验证事件：  
> 某次基建任务因 `INSERT INTO table VALUES (...)` 在目标表新增一列后失败，报 `Column count doesn't match value count`。回滚并改为显式列名后通过。  
> 这条事件必须写入认知池，而不是只留一句口号。

---

## 检查清单

### A. SQL 编写规范

- [ ] 所有 `SELECT` 显式列出所需列，禁止 `SELECT *`。
- [ ] 所有 `INSERT` 必须写成 `INSERT INTO table (col1, col2, ...) VALUES (...)`。
- [ ] 禁止 `INSERT INTO table VALUES (...)` 这种不写列名的写法。
- [ ] 禁止依赖列序号，如 `GROUP BY 1`、`ORDER BY 2`。
- [ ] JOIN 时所有列必须带表别名/表名前缀，避免歧义。
- [ ] 不使用 `NATURAL JOIN`、`SELECT DISTINCT *` 等隐式列关联写法。
- [ ] 显式写类型转换，例如 `CAST(ts AS DATE)`，避免隐式转换。

### B. Schema 漂移检查

- [ ] 脚本执行前连接 `information_schema`，校验所需列是否存在、类型是否匹配。
- [ ] 使用迁移工具管理表结构：Flyway / Liquibase / Alembic 等。
- [ ] 测试环境 schema 必须与生产环境一致，否则测试通过不代表生产安全。
- [ ] 如果依赖上游表，增加上游列变更监控，变更后自动触发相关脚本重新验证。

### C. 发布与执行检查

- [ ] Code Review 时专门搜索危险写法：`SELECT *`、无列 `INSERT`、`VALUES (`、列序号。
- [ ] 基建脚本必须跑通预发布环境，并执行 `EXPLAIN` 或 dry-run 验证列映射。
- [ ] 设置合理超时：B 模型 turbo 用 300 秒，A 模型用 600 秒；脚本执行也必须有超时和失败停止机制。
- [ ] 保留上一版本脚本，失败时快速回滚，不反复重试掩盖问题。
- [ ] 每次执行后写审计日志：脚本版本、schema hash、执行结果。

### D. 认知池维护

- [ ] 新认知必须在 30 分钟内参与注入，不能只入库不生效。
- [ ] 每 10 个任务或每轮结束时刷新认知缓存，确保“基建脚本禁用简化版”出现在相关任务上下文。
- [ ] 当出现新的列不匹配案例，把案例追加到这条认知的“事故锚点”下，而不是另建一条孤立认知。
- [ ] 删除或降级过时认知；某个简化写法“之前没出事”不能证明安全，只能标记为“未验证”。

---

一句话结论：  
**基建脚本的 SQL 不能靠“当前能跑”证明正确，必须靠显式列名 + schema 校验 + 认知池持续注入来保证长期安全。**
