# 任务类型: cog

从“认知质检SOP”角度，引擎运行中踩过的坑可归为三类：**认知不流动、调用不设防、闭环不验证**。据此提炼三条可复用铁律：

---

### 铁律一：认知必须“活水注入”，禁止只进不出

**坑：** 认知池 1700+ 条，但从不注入任务，也不影响调度，最终退化成静态档案库。

**要求：**  
认知池必须有进有出、有新鲜度管理。新认知应在 30 分钟内参与注入；旧认知要定期降权或淘汰，确保调度使用的始终是“活认知”。

**验证方法：**

1. 定时检查认知池中每条认知的 `last_injected_time`，若存在超过 30 分钟未参与注入的认知，且未触发降权/淘汰，则判定违规。
2. 对比“认知池总量”与“任务实际注入的认知 ID 集合”：连续 10 个任务中，若注入集合没有任何新增 ID，则判定认知失活。
3. 测试环境强制注入一条带标记的新认知，检查后续任务日志中是否出现该标记，以及调度策略是否产生可检测的变化。

---

### 铁律二：外部模型调用必须分级设置超时，超时必须可观测、可重试

**坑：** API 调用超时导致任务失败，且未按模型区分超时策略。

**要求：**  
不同模型必须配置不同 timeout：B 模型 turbo 用 300 秒，A 模型用 600 秒。超时后要进入重试或降级流程，不能无限阻塞任务。

**验证方法：**

1. 配置扫描/代码审查：确认所有外部 API 调用点都带 timeout 参数，且值与模型类型匹配。
2. 故障注入：模拟慢响应（超过设定超时时间），验证调用能按预期抛出超时，并触发重试或熔断。
3. 监控告警：建立“超时率、重试率、成功率”指标；若超时率超过阈值自动告警，且告警可关联到具体任务 ID 回溯原因。

---

### 铁律三：真实消耗与执行结果必须回流认知池，且必须验证“虚能返实”

**坑：** 认知池只进不出，API 调用、Token 消耗等真实数据与调度策略脱节，闭环断裂。

**要求：**  
每次任务结束后，必须把 API 耗时、Token 消耗、执行结果、异常信息等真实数据写回认知池，作为新认知原料；后续调度必须能依据这些新认知改变策略——如模型选择、超时调整、提示词优化。

**验证方法：**

1. 检查任务结束到认知池写入的链路：延迟不能超过一个任务周期，且不能丢数据；通过埋点对比“任务记录数”与“认知写入数”是否一致。
2. 观察认知更新前后，调度策略参数（模型分配、超时阈值、并发数等）是否有版本变化；若认知池有更新但调度参数全量不变，则判定闭环断裂。
3. A/B 测试：分别运行“注入新认知”和“不注入新认知”两组任务，对比任务成功率、平均耗时、Token 成本；若注入组无显著提升，说明认知未有效返实。

---

以上三条铁律可直接写入认知质检 SOP，作为每次引擎发布或策略变更前的强制检查项。
