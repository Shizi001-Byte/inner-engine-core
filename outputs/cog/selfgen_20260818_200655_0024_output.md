# 任务类型: cog

## 自动归档系统设计（推演版）

基于你给的避坑提醒和认知锚定，不再重复论证，直接作为公理使用：

- 并发只做 API 调用
- 后处理必须单消费者
- 状态变更必须原子化
- 同步必须带版本仲裁
- B 类/turbo 模型超时 300 秒，A 类模型超时 600 秒
- 认知池必须刷新：每 10 任务或每转结束刷新；新认知 30 分钟内必须参与注入

---

## 一、总体架构

```text
任务完成事件
   ↓
写入 archive_record：PENDING
   ↓
Dispatcher 批量领取任务
   ↓
Worker Pool 并发调用 API（只做远程调用，不写库）
   ↓
Result Queue（单分区 / 单消费者）
   ↓
Single Consumer：校验、解析、事务写入
   ↓
archive_record → ARCHIVED / FAILED
cognition_entry → 新认知写入
   ↓
认知池刷新器：每 10 任务 / 每转结束 / 30 分钟兜底刷新
```

关键点：**Worker 里没有任何业务写操作，只负责 API 调用并返回结果；所有后处理收敛到一个消费者里串行执行。**

---

## 二、状态机与原子化状态变更

归档记录状态：

```text
PENDING → PROCESSING → ARCHIVED
              │
              ├──→ FAILED（重试耗尽）
              └──→ PENDING（超时/可重试）
ARCHIVED → SUPERSEDED（版本冲突/被新版本覆盖）
```

所有状态变更必须用 CAS（Compare-And-Swap）SQL，不能先查后改。

领取任务：

```sql
UPDATE archive_record
SET status = 'PROCESSING',
    lease_expire_at = now() + make_interval(secs => timeout_seconds),
    version = version + 1,
    updated_at = now()
WHERE id = ?
  AND status = 'PENDING'
  AND version = ?;
```

只有 `affected_rows = 1` 才允许继续。

消费者写归档结果：

```sql
UPDATE archive_record
SET status = 'ARCHIVED',
    result_json = ?,
    version = version + 1,
    updated_at = now()
WHERE id = ?
  AND status = 'PROCESSING'
  AND version = ?;
```

如果影响行数为 0，说明版本冲突或状态已变化，必须走版本仲裁，不能强行覆盖。

## 三、超时控制

根据模型类型预设超时：

```python
TIMEOUT_CONFIG = {
    "B_turbo": 300,
    "A": 600,
}
```

Worker 调用 API 时：

```python
try:
    resp = await asyncio.wait_for(
        api_client.call(record.payload),
        timeout=TIMEOUT_CONFIG[record.model_type]
    )
    result_queue.send({
        "event": "api_success",
        "record_id": record.id,
        "version": record.version,
        "response": resp,
    })
except asyncio.TimeoutError:
    result_queue.send({
        "event": "api_timeout",
        "record_id": record.id,
        "version": record.version,
    })
except Exception as exc:
    result_queue.send({
        "event": "api_error",
        "record_id": record.id,
        "version": record.version,
        "error": str(exc),
    })
```

同时，`lease_expire_at` 必须大于超时时间，防止 API 还没返回就被 sweeper 抢走。

Sweeper 定时回收过期任务：

```sql
UPDATE archive_record
SET status = 'PENDING',
    version = version + 1,
    updated_at = now(),
    last_error = 'lease_expired'
WHERE status = 'PROCESSING'
  AND lease_expire_at < now();
```

## 四、同步必须带版本仲裁

任何跨进程、跨服务、跨缓存同步，都不能盲目覆盖。

规则：

```text
incoming.version > local.version  → 允许覆盖
incoming.version < local.version  → 拒绝，并回传本地版本
incoming.version == local.version → 比较 updated_at
updated_at 也相同             → 用确定性规则裁决，并记录冲突
```

例如缓存更新：

```python
if incoming.version > cached.version:
    cache.set(entry)
elif incoming.version == cached.version and incoming.updated_at > cached.updated_at:
    cache.set(entry)
else:
    # 丢弃或告警
    pass
```

数据库层则用乐观锁：

```sql
UPDATE ...
SET version = version + 1
WHERE id = ?
  AND version = ?;
```

## 五、认知池刷新：防止只进不出

### 5.1 刷新触发条件

- 每完成 10 个任务，主动刷新一次；
- 每次任务轮次结束时，主动刷新一次；
- 每次写入新认知时，设置一个 30 分钟的延迟刷新兜底。

### 5.2 刷新动作

```text
1. 查询自上次刷新以来新增/变更的 ACTIVE 认知；
2. 对每条认知做版本仲裁；
3. 从缓存中移除 status != ACTIVE 的认知；
4. 更新 last_refresh_at；
5. 原子切换缓存版本号，让新认知立即参与后续任务注入。
```

### 5.3 新认知 30 分钟必须参与注入

```python
# 写认知后：
send_delayed_event(
    event="force_inject_cognition",
    cognition_id=entry.id,
    delay=30 * 60
)

# 延迟事件触发时，如果该认知还没被注入，立即强制注入。
```

这样即使前面 10 任务/转结束触发条件失效，30 分钟兜底也能保证新认知不会变成静态档案。

### 5.4 淘汰机制

定期扫描：

- `last_used_at` 超过阈值；
- `status = SUPERSEDED`；
- `status = EVICTED`。

这些条目必须从缓存中移除，保证认知池“只进不出”的问题不再出现。

## 六、检查清单：基建脚本禁用简化版

### 教训

“简化版 SQL”通常表现为：

- `INSERT INTO t VALUES (...)` 不写列名；
- `SELECT *` 依赖列顺序；
- 建表/迁移脚本不写版本号；
- 不校验列类型；
- 不幂等，重复执行会出问题。

典型后果：表结构新增列后，旧脚本按位置插入导致列不匹配；生产环境 schema 与代码模型不一致。

### 检查清单

| 检查项 | 强制要求 | 反例 |
|---|---|---|
| DML 列名 | 必须显式列出列名 | `INSERT INTO t VALUES (...)` |
| 列顺序 | 禁止依赖 `SELECT *` | `SELECT * FROM t` |
| 字段类型 | 与模型严格一致 | `INT` vs `BIGINT`、`VARCHAR` vs `TEXT` |
| 幂等性 | 脚本可重复执行 | `INSERT` 不处理冲突 |
| 迁移版本 | 每个脚本带版本号 | 覆盖式修改原脚本 |
| 事务性 | DDL/DML 在事务中执行 | 无事务，半执行 |
| 执行后校验 | 跑 schema diff | 只跑成功不校验 |
| 生产前测试 | staging 全量执行 | 只跑局部脚本 |
| 可回滚 | 变更前有备份/回滚方案 | 直接改生产 |
| 命名一致性 | 列名与代码常量一致 | 简写 `usr_nm` 代替 `user_name` |

### 强制落地方式

```sql
-- 禁止
INSERT INTO archive_record VALUES (...);

-- 强制
INSERT INTO archive_record (
    task_id, model_type, status, version, payload, created_at
)
VALUES (
    ?, ?, 'PENDING', 1, ?, now()
);
```

```sql
-- 禁止
SELECT * FROM archive_record WHERE id = ?;

-- 强制
SELECT
    id, task_id, model_type, status, version,
    payload, result, created_at, updated_at
FROM archive_record
WHERE id = ?;
```

所有基建脚本必须纳入版本管理，并由自动化工具生成或校验，禁止手写“简化版”SQL 绕过检查。

这套自动归档系统，核心就是：**并发只做 API 调用，后处理单消费者，状态变更原子化，同步带版本仲裁，认知池定期刷新并淘汰。** 加上基建脚本检查清单，可以避免超时、认知池静态化、SQL 列不匹配这三类历史坑。
