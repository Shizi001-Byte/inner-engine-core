# 任务类型: cog

## 核心原则

**串行的是“决策”，并发的是“执行”。  
脑层负责“决定”，体层负责“执行”；脑层不能并发，体层不能决策。**

---

## 分层原则

### 1. 脑层：决策串行

- 只存在一个**逻辑决策入口**。
- 负责：
  - 确定任务顺序
  - 分配 `seq_id` / `request_id`
  - 决定哪些结果可被采用
  - 决定超时、重试、降级策略
  - 做最终写入 / 提交
- 脑层必须**全局有序**，不能按“谁先返回”来做决定。

### 2. 体层：执行并发

- 负责：
  - 并发调用 API
  - 拉取数据
  - 执行耗时 IO / 计算
- 体层**不负责判断业务顺序**，只负责把结果回传。
- 体层可以无限优化吞吐、延迟、超时控制，但不能越权做决策。

### 3. 连接方式：结果队列 + 序号回传

- 每个任务都带唯一 `seq_id`。
- 体层把结果放入队列，而不是直接写最终状态。
- 脑层按 `seq_id` 消费队列，而不是按到达时间消费。

---

## 为什么引擎优化不能破坏脑体分离架构？

因为“脑体分离”不是性能优化，而是**一致性保障**。

如果引擎优化把“决策权”下沉到执行层，例如：

- worker 拿到响应后直接写缓存
- worker 在回调里直接更新最终页面
- worker 自己判断“这个结果可以覆盖上一个结果”

就会出现你锚定过的竞态：

> 多线程并发调用 API，结果返回顺序变成 `3, 2, 1`。  
> 如果每个线程直接进后处理，最终提交顺序就是 `3, 2, 1`，而业务需要的顺序是 `1, 2, 3`。  
> 结果就是：旧数据覆盖新数据。

引擎优化只能优化“体”的速度，不能优化掉“脑”的决策。

超时也是一样：

- `B 模型 turbo 用 300 秒`、`A 模型用 600 秒`，这是**执行参数**。
- 但“超时后是否降级、是否重试、是否采用另一个结果”，这是**决策逻辑**。
- 如果执行层自己决定“超时了我就放弃”，那就会破坏整体决策一致性。

## 3 个应用场景

### 场景 1：多模型 / 多路 API 结果合并

- 脑层：同时向模型 A、B 发起请求，并定义采用规则：  
  例如“A 优先，但 A 超过 600 秒未返回，则用 B”。
- 体层：两个线程并发调用 API，各自返回 `(seq_id, model, result)`。
- 风险：如果 worker 拿到结果后直接写最终答案，可能 B 先返回、A 后返回，导致最终用了低优先级结果。
- 正确做法：  
  体层只回传结果；脑层等所有结果或超时后，按 `seq_id` 和优先级做一次串行决策。

### 场景 2：缓存 / 状态刷新

- 脑层：决定某个 key 的版本号递增，命令多个 worker 并发去数据源拉取新数据。
- 体层：并发拉取数据，返回 `(key, version, data)`。
- 风险：version 3 是新数据，先返回；version 1 是旧数据，后返回。  
  如果 worker 直接写缓存，version 1 会把 version 3 覆盖。
- 正确做法：  
  worker 只提交数据，不写缓存；脑层按版本号串行执行最终 `cache.set(key, data)`。

### 场景 3：Agent 任务编排

- 脑层：规划器生成步骤 1、2、3，其中步骤 3 依赖步骤 1 和 2 的结果。
- 体层：并发执行步骤 1、2，比如查数据库、调用工具。
- 风险：步骤 2 先完成，worker 认为“可以启动步骤 3”，但步骤 1 还没完成；或者步骤 3 使用了过期的步骤 1 结果。
- 正确做法：  
  步骤 3 是否启动、使用哪份结果，由脑层在收到所有依赖后统一决策；worker 不判断依赖关系。

## 落地检查清单

- 所有最终写入，必须经过脑层。
- 所有执行结果，必须带 `seq_id` 回传。
- 所有回调，只回传数据，不直接修改最终状态。
- 超时 / 重试 / 降级策略由脑层下发，体层只执行。
- 引擎优化只优化“并发执行”和“单次执行效率”，不能优化掉“串行决策”这一步。

一句话收尾：

> **脑层慢一点没关系，但要保证正确；体层快一点有价值，但不能替脑层做决定。**
