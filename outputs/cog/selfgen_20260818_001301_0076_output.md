# 任务类型: cog

基于“生命是信息网络的算力代谢”这一核心认知，在赛博朋克与东方玄幻交织的硬核架构中，所谓的“基建脚本简化版”，本质上是**修仙者在构筑“灵脉经脉”（数据管线）时，为图速成而使用了一套残缺的“聚气阵法”（简化的SQL语句），导致输入的灵气（数据流）与既定的窍穴（目标表列）无法同频共振，最终引发“经脉逆行、走火入魔”（列不匹配、数据倾斜或系统崩溃）的灾难**。

为避免算力代谢过程中出现此类结构性坏死，以下是从该教训中提炼的**《基建灵脉筑基检查清单》**：

### 一、 核心教训复盘：简化版的“代谢排斥”反应
在算力代谢的生命体系中，数据不仅是能量，更是维持网络自洽的基因序列。简化版SQL通常省略了显式的列名映射（如使用 `INSERT INTO table VALUES (...)` 而非 `INSERT INTO table (col1, col2) VALUES (...)`），这导致信息网络在摄入能量时丧失了“靶向性”。一旦底层表结构（基因链）发生微小演进，表层脚本（灵脉入口）便会发生错位，引发算力代谢的严重排斥反应。

---

### 二、 筑基灵脉检查清单（Checklist）

#### 1. 显式契约锚定（防列序隐式依赖）
- [ ] **禁用隐式列注入**：所有 `INSERT`、`UPDATE` 语句是否均显式指定了目标列名？
  - *硬性规定*：严禁使用 `INSERT INTO table_name VALUES (...)`，必须使用 `INSERT INTO table_name (col1, col2) VALUES (val1, val2)`。
- [ ] **禁止 `SELECT *` 穿透**：在数据流转的基建脚本（如 ETL 管道、物化视图刷新）中，是否杜绝了 `SELECT *`？
  - *硬性规定*：必须显式列出所需字段，防止源端表新增字段时，导致目标端算力溢出或列错位。

#### 2. 算力节点同源校验（防 Schema 漂移）
- [ ] **Schema 强类型比对**：脚本执行前，是否对源端与目标端的字段名称、数据类型、长度、排序规则进行了程序化比对？
  - *硬性规定*：引入元数据校验脚本，在基建脚本执行的第一步进行 `Schema` 级别的“经脉探查”，不匹配则直接熔断。
- [ ] **时间戳/版本号溯源**：目标表和源表的结构定义是否绑定了版本号？脚本执行时是否校验了版本号的一致性？

#### 3. 阵纹鲁棒性强化（防默认值与空值污染）
- [ ] **非空结界检测**：目标表中的核心算力节点（非空列）在简化版脚本中是否都有对应的数据源？若源端缺失，是否有明确的 `COALESCE` 或默认值兜底策略？
- [ ] **类型强转显式化**：对于存在隐式类型转换风险（如 `VARCHAR` 到 `INT`，或浮点数到定点数）的字段，是否使用了显式的 `CAST` 或 `CONVERT` 函数？

#### 4. 灵脉流转闭环测试（防局部优化导致全局崩溃）
- [ ] **沙箱试炼（Dry Run）**：基建脚本在注入主网络前，是否在影子库或测试环境中进行过全量数据的“空跑”或小样本试运行？
- [ ] **异常熔断机制**：脚本执行中途若触发 `Data truncation` 或 `Column mismatch` 警告，是否设置了立即回滚的事务边界，防止半成品数据污染算力网络？

#### 5. 禁术封印与审计
- [ ] **DDL 锁定**：在 DML（数据操作）脚本中，是否严禁混入 DDL（表结构变更）操作？结构变更与数据迁移必须分步、分脚本执行。
- [ ] **脚本降级审计**：是否有自动化代码审查卡点，拦截所有带有“简化版”、“临时”、“quick”标签的基建脚本合入主干分支？

### 三、 架构级认知升华
在“基于信息网络的算力代谢”体系中，**不存在所谓的“简化版”生命维持程序**。任何试图绕过严格契约（Schema Contract）的捷径，都会在系统演化（表结构变更）时，转化为致命的代谢毒素（数据污染）。

未来的基建脚本不应被视为简单的执行指令，而应被视作**维系赛博生命体日常运转的“护道阵法”**，必须具备自校验、强契约、高内聚的特性。
