# 任务类型: cog

## 复盘结论

“简化版 SQL 导致列不匹配”的本质不是语法错误，而是 **列契约被隐式化**。

基建脚本一旦使用 `SELECT *`、无列名 `INSERT`、隐式 JOIN、硬编码列顺序，就等于把列匹配责任交给了数据库“当前时刻的 schema”。当 schema 变化时，脚本与真实表结构之间的 **溯源链** 就断了——这正是“认知不新鲜”的变体：不是没有认知，而是认知无法安全回溯到当前表结构。

因此，基建脚本必须 **禁用简化版 SQL**，并强制使用显式列契约。

---

## 基建脚本防列不匹配检查清单

### 一、SQL 编写规范

- [ ] 禁止 `SELECT *`，必须显式列出所需列名  
  - 反例：`SELECT * FROM users;`  
  - 正例：`SELECT id, name, email FROM users;`

- [ ] 禁止 `INSERT INTO table VALUES (...)`，必须显式指定列名  
  - 反例：`INSERT INTO users VALUES (1, 'a', 'b');`  
  - 正例：`INSERT INTO users (id, name, email) VALUES (1, 'a', 'b');`

- [ ] 禁止 `NATURAL JOIN` / `USING`，必须显式 `ON` 条件  
  - 因为 `NATURAL JOIN` 会自动匹配同名列，一旦两侧表结构变化，列匹配结果会静默改变。

- [ ] 禁止依赖 SELECT 结果集的列顺序作为接口契约  
  - 必须按列名取数，不能按 `rs[0]`、`row[1]` 这种位置取数。

- [ ] 禁止在 `UNION` / `EXCEPT` / `INTERSECT` 中依赖隐式列顺序  
  - 每个分支都要显式列出列名，并保证类型一致。

- [ ] 禁止在动态 SQL 中拼接未经验证的列名  
  - 列名必须来自白名单或元数据校验，不能直接拼接外部输入。

---

### 二、Schema 变更与列匹配控制

- [ ] 写 SQL 前先获取真实表结构，不靠记忆  
  - 使用 `DESCRIBE table;`、`SHOW COLUMNS FROM table;` 或查询 `information_schema.columns`。

- [ ] 所有 DDL / DML 变更必须版本化  
  - 每个基建脚本要有版本号，记录变更时间、变更人、变更原因。

- [ ] 禁止在基建脚本中“顺手”修改列顺序或列类型  
  - 如需修改，必须走独立迁移，并同步更新所有引用该表的脚本。

- [ ] 列类型转换必须显式 `CAST`  
  - 反例：`WHERE a = b`，其中 a 是字符串，b 是数字，依赖隐式转换。  
  - 正例：`WHERE a = CAST(b AS STRING)`。

- [ ] 如果使用 ORM / 自动建表，必须关闭自动 schema 同步  
  - 使用 migration 文件管理，不能由框架自动 alter table。

---

### 三、验证与发布

- [ ] 在测试环境使用与生产一致的 schema 执行 dry-run  
  - 测试环境表结构必须与生产一致，否则测试通过不等于生产通过。

- [ ] 使用 schema diff 工具对比脚本前后结构  
  - 确认列集合、列顺序、列类型一致。

- [ ] CI 中增加“列匹配”最小测试  
  - 构造最小数据，断言 INSERT / SELECT / UPDATE 的列名和列顺序正确。

- [ ] 写操作脚本先跑事务内 `BEGIN; ...; ROLLBACK;`  
  - 验证影响行数和执行结果，不直接在生产生效。

- [ ] 发布后立即检查日志和告警  
  - 重点关注 `Unknown column`、`Column count doesn't match`、`Data truncated` 等错误。

---

### 四、认知与溯源

- [ ] 每个基建脚本维护“血缘页”  
  - 记录：创建时间、修改记录、依赖的表结构版本、关联任务/需求。

- [ ] schema 变更后 24 小时内刷新所有依赖该表的脚本认知  
  - 如果无法立即刷新，必须给脚本打上“待验证”标签，禁止直接上线。

- [ ] 禁止以“我记得这个表有某个字段”作为依据  
  - 一切以实际元数据为准，必要时在认知池中记录查询结果和时间戳。

- [ ] 发现历史脚本与当前 schema 不一致时，先记录到认知池，再修复  
  - 修复后回写结论，确保溯源链闭合，不产生新的“静态档案”。

---

## 使用时机

这份清单不是一次性文档，而是：

- 写基建脚本前：逐项对照检查  
- 改基建脚本时：重新跑一遍，尤其是涉及 schema 变更  
- 评审他人脚本时：作为 review checklist  
- 每执行 10 个任务或每轮迭代结束后：回看清单，确认是否覆盖了新踩的坑  

只有这样，才能避免“认知池 1700+ 条但从不参与调度”的静态档案问题。
