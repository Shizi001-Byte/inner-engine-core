# 任务类型: eng

基于已有的认知锚定与历史避坑经验，针对“引擎产出三方同步自动化（Gitee/飞书/Supabase）”的设计，我们需要构建一个**具备质量过滤前置、状态可恢复、幂等且能处理并发冲突**的 robust（鲁棒）系统。

以下是完整的推演与设计方案：

### 一、 核心架构：状态快照与麦克斯韦妖过滤层

结合【认知锚定1与2-5】，同步系统不能仅仅是“搬运工”，必须作为“麦克斯韦妖”在同步前进行信息熵控制，同时依赖 Guardian-Core 架构保障状态一致性。

**执行流程：**
1. **重大变更触发**：监听引擎产出的 `commit` 或 `archive` 事件。
2. **配置读取与验证（避坑1）**：读取最新的 Gitee/飞书/Supabase 凭证与API端点，**修改后立即通过 Ping/GetMe 接口验证配置生效**，防止旧配置导致静默失败。
3. **麦克斯韦妖过滤层（认知2-5）**：在同步前，计算产出内容的向量相似度与信息熵。
   - 若判定为同质化/套话（局部最优解），触发**多样性惩罚**，打上 `quarantine`（隔离）标签。
   - 隔离内容仅同步至 Supabase 的 `low_priority_archive` 表，**不进入核心检索池，不反哺引擎**，避免浪费轻边际资源。
4. **WAL预写日志（认知1）**：同步前，将 `Task_ID`、目标三方哈希值、操作类型写入本地 WAL 日志。
5. **三方并行/串行执行（避坑2）**：根据各API特性预设合理 Timeout 执行同步。
6. **快照落地**：同步成功后，更新 Supabase 核心状态表，并写入本地 Snapshot。

---

### 二、 幂等性设计方案

为防止网络抖动导致的重复提交、重复文件上传，必须实现严格的幂等控制。

#### 1. 核心幂等键：`Content_Hash` (内容指纹)
每次重大变更产出时，计算产出文件/代码的 SHA-256 哈希值，结合版本号生成全局唯一的 `Sync_Key = {project}:{version}:{hash}`。

#### 2. 各端幂等实现机制：
*   **Gitee (代码提交)：**
    *   幂等策略：基于分支与 Commit Message 校验。
    *   实现：提交前使用 `git log --grep="<Sync_Key>"` 检查是否已提交。若已存在，则跳过 `git push`，直接返回成功状态。
*   **飞书 (文件上传)：**
    *   幂等策略：基于文件名命名规范与 Supabase 状态中心校验。
    *   实现：飞书云文档不支持同名幂等上传。系统约定文件名格式为 `产出报告_<Sync_Key>.md`。上传前先查询 Supabase `sync_state` 表中该 `Sync_Key` 是否记录了飞书 `file_token`。若有，则跳过上传；若无，则执行上传并回写 `file_token`。
*   **Supabase (存储与数据同步)：**
    *   幂等策略：数据库 Upsert（Insert on Conflict Do Nothing/Update）。
    *   实现：在 Supabase 的 `engine_outputs` 表中，将 `Sync_Key` 设为唯一索引。执行 `INSERT ... ON CONFLICT (Sync_Key) DO UPDATE SET content = EXCLUDED.content, updated_at = now()`。即使重复触发，也只会更新而不会产生重复数据。

### 三、 冲突处理方案

在三方同步过程中，可能遇到并发写入冲突或远端状态不一致的情况。

#### 1. Gitee 代码冲突处理
*   **场景：** 自动推送的分支与人工修改或其他自动化任务产生分叉冲突。
*   **策略（保护主分支）：** 不直接推送到 `main/master`，而是推送到自动化专有分支 `auto-sync/<Sync_Key>`。
*   **降级处理：** 若 `git push` 因 non-fast-forward 失败，尝试一次 `git pull --rebase`。若仍有冲突，**立即放弃自动合并**，通过飞书机器人告警人工介入，并在 Supabase 中标记该任务状态为 `CONFLICT`。

#### 2. 飞书文件冲突处理
*   **场景：** 同名文档在飞书端被手动删除，或目录结构被篡改导致上传失败。
*   **策略：** 采用“只增不删”的版本控制策略。若按既定命名规则上传失败（如父目录丢失），触发降级策略：自动在根目录创建新的日期文件夹 `YYYY-MM-DD-Recovery` 并上传，同时将新的 URL 回传 Supabase 更新索引。

#### 3. Supabase 数据冲突处理
*   **场景：** 并发更新同一记录导致数据库死锁或数据覆盖。
*   **策略：** 利用 Supabase (PostgreSQL) 的乐观锁机制。在表中增加 `version` 字段。
*   **实现：** 更新时附加条件 `WHERE id = ? AND version = ?`，若更新失败说明被其他线程抢占，事务回滚，触发重试机制（最多3次，指数退避）。

### 四、 避坑与超时控制实施细节

依据【避坑提醒】与【坑库预警】，在代码工程实现中严格落地以下防御措施：

| 模块 | 防御点 | 实施方案 |
| :--- | :--- | :--- |
| **API请求层** | **API调用超时（避坑2）** | 全局配置网络中间件：Gitee/Supabase等数据层调用 Timeout 设为 **300秒**；若涉及调用A模型进行内容总结同步，Timeout 设为 **600秒**。 |
| **配置中心** | **配置修改未生效（避坑1）** | 同步任务启动时，强制执行 `verify_config()` 钩子，读取最新环境变量并发起一次轻量级鉴权请求。若有读取点遗漏（如飞书AppId与AppSecret不同步），立即抛出 `ConfigMismatchException` 终止任务。 |
| **连接器层** | **绑定与权限失效（坑库预警）** | 定期检查飞书、Gitee 的 Token 有效期。同步前确认“已登录”状态，若遇到 Token 失效，不要在日志里死循环，而是捕获异常并触发告警。 |
| **状态恢复层** | **有备份无恢复（认知1）** | Guardian-Core 进程启动时，必定扫描 WAL 日志。发现 `COMMITTED but NOT SYNCED` 的半成品任务，基于幂等性自动重试三方同步，补齐 Snapshot。 |

### 五、 总结

本设计将“产出归档”从单纯的搬运升级为**“基于信息熵控制的复杂适应系统”**。通过 `Content_Hash` 实现端到端幂等，通过乐观锁与分支策略处理冲突，并利用 WAL+Snapshot 保障同步过程的不丢不重。同时，前置的“麦克斯韦妖”过滤层有效拦截了同质化内容污染核心池，确保系统在“消耗→产出→反哺”的正反馈循环中保持高信息熵与高价值。
