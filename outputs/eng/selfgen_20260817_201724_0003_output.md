# 任务类型: eng

设计一个链式推演机制（通常用于大模型复杂任务规划、多阶段数据分析等场景），核心在于**状态机管理**、**数据血缘追踪**和**幂等性控制**。

针对一个核心议题拆分为3-5轮递进任务，且前置输出作为后置输入的需求，以下是任务依赖图与断点续跑的完整设计方案。

---

### 一、 任务依赖图设计

我们采用**有向无环图 (DAG)** 来建模。虽然逻辑上是线性链路，但在实际引擎中，每一轮可能会包含多个并行子任务（如：检索、推理、反思）。

#### 1. 节点与边的数据结构
*   **节点：** 每一轮推演任务。
*   **边：** 数据流向，明确上一轮的哪些输出作为下一轮的输入。

**JSON Schema 示例：**
```json
{
  "workflow_id": "chain_001",
  "core_topic": "评估AI大模型对软件外包行业的影响",
  "nodes": [
    {
      "node_id": "round_1",
      "step": 1,
      "task_desc": "拆解核心议题，生成分析维度",
      "inputs": ["${core_topic}"],  // 引用全局变量
      "outputs": ["dimensions"],
      "status": "SUCCESS",
      "retry_count": 0
    },
    {
      "node_id": "round_2",
      "step": 2,
      "task_desc": "针对每个维度收集数据与案例",
      "inputs": ["${round_1.outputs.dimensions}"], // 依赖上一轮输出
      "outputs": ["raw_data"],
      "status": "PENDING",
      "retry_count": 0
    },
    {
      "node_id": "round_3",
      "step": 3,
      "task_desc": "基于数据进行深度推理与因果分析",
      "inputs": ["${round_1.outputs.dimensions}", "${round_2.outputs.raw_data}"], // 可能依赖多轮输出
      "outputs": ["analysis_report"],
      "status": "PENDING",
      "retry_count": 0
    }
    // ... round_4, round_5
  ]
}
```

#### 2. 上下文传递机制
由于大模型或复杂任务存在上下文窗口限制或状态污染，不能简单地把上一轮的所有内容丢给下一轮。
*   **显式映射：** 通过 `inputs` 字段的 `${node_id.outputs.field_name}` 严格定义传递的数据块。
*   **上下文压缩：** 每个节点执行完毕后，如果输出结果过大，需在节点内部做摘要再传给下一轮。

---

### 二、 状态机与存储模型

为了支持断点续跑，引擎必须具备“记忆”。推荐使用关系型数据库（如PostgreSQL）或文档数据库（如MongoDB）存储以下实体：

#### 1. 任务实例状态机
每个节点的生命周期状态包括：
`PENDING` (待执行) -> `RUNNING` (执行中) -> `SUCCESS` (成功) / `FAILED` (失败) -> `SKIPPED` (跳过)

#### 2. 存储模型设计
*   **Workflow 表：** 记录整个链路的全局状态、当前执行到的节点、核心议题。
*   **Node 表：** 记录每个节点的状态、输入快照、输出快照、错误信息、重试次数。
*   **Artifact 表 (产物表)：** 如果输出是大文件（如长文本、JSON数据集），存储在对象存储中，Node 表只记录引用指针（URI）。

### 三、 断点续跑机制

断点续跑的核心逻辑是：**引擎重启或任务失败恢复时，能够找到第一个未成功的节点，校验其输入是否完备，完备则从该节点开始继续执行。**

#### 1. 核心执行流程
引擎调度器的伪代码如下：

```python
def run_workflow(workflow_id):
    workflow = load_workflow_from_db(workflow_id)
    
    for node in workflow.nodes:
        if node.status == "SUCCESS":
            # 断点1：已完成节点直接跳过，但其输出结果需加载到内存上下文中供后续使用
            context.update(load_node_outputs(node.id))
            continue
            
        if node.status == "RUNNING":
            # 异常中断未恢复的节点，状态回滚到PENDING
            node.status = "PENDING"
            
        if node.status == "PENDING":
            # 1. 依赖检查 (断点续跑的安全保障)
            inputs = resolve_inputs(node.inputs, context)
            if not inputs.is_ready():
                raise Exception(f"输入数据不完整，缺少依赖: {inputs.missing}")
                
            # 2. 执行任务
            node.status = "RUNNING"
            save_node(node)
            try:
                outputs = execute_task(node.task_desc, inputs)
                
                # 3. 持久化输出 (断点续跑的关键)
                save_node_outputs(node.id, outputs)
                context.update(outputs)
                node.status = "SUCCESS"
                
            except Exception as e:
                node.status = "FAILED"
                node.error_msg = str(e)
                save_node(node)
                
                # 触发重试策略或中断
                if node.retry_count < MAX_RETRIES:
                    node.retry_count += 1
                    node.status = "PENDING"
                    save_node(node)
                    # 重新执行当前节点 (可加入退避延迟)
                    return run_workflow(workflow_id) 
                else:
                    raise Exception(f"节点 {node.id} 达到最大重试次数，链路中断")
                    
            save_node(node)
```

#### 2. 断点续跑触发场景

*   **场景 A：引擎崩溃/OOM重启**
    *   引擎启动时，扫描所有状态为 `RUNNING` 的节点。
    *   将这些节点状态重置为 `PENDING`。
    *   重新加载 Workflow，从第一个非 `SUCCESS` 的节点开始执行。
*   **场景 B：节点执行失败（如API超时、大模型拒绝回答）**
    *   节点状态置为 `FAILED`。
    *   调度器捕获异常，根据配置的重试次数（如3次）和退避策略（如等待5s, 10s, 30s），重新将该节点置为 `PENDING` 并执行。
    *   如果重试耗尽，整个 Workflow 状态置为 `PAUSED`，等待人工介入或修改 Prompt 后恢复。
*   **场景 C：人工干预与修改**
    *   如果第3轮结果不满意，人工将第3轮状态修改为 `PENDING`，并修改其输出。
    *   引擎再次运行时，会跳过前两轮，重新执行第3轮及后续依赖第3轮的节点。

#### 3. 幂等性保障
在断点重试时，同一个节点可能会被执行多次。必须保证：
1.  **外部副作用隔离：** 如果节点包含写数据库或发邮件操作，需通过唯一请求ID（如 `node_id + retry_count`）防重。
2.  **输出覆盖写：** 重试成功后，新的输出直接覆盖（或版本化追加）旧的失败记录。

### 四、 进阶优化设计：Check-pointing（检查点）

对于3-5轮的复杂推演，如果单轮任务耗时较长（例如包含多步Agent循环），仅做节点级别的断点续跑可能不够精细。

可以在节点内部引入 **Step-level Check-pointing**：
*   将一轮任务内部再拆分为多个 Step。
*   每完成一个 Step，将当前中间状态存入 `Node.checkpoint_data`。
*   如果节点执行失败重试，引擎会从 `checkpoint_data` 恢复，跳过已完成的内部 Step，而不是将整轮任务从头再来。

### 五、 总结架构图

```text
[核心议题] 
    │
    ▼
┌─────────────────────────────────────────────────┐
│              Workflow Orchestrator              │
│ (扫描DB, 寻找第一个非SUCCESS节点, 恢复Context) │
└────────────┬────────────────────────────────────┘
             │
             ▼
┌─────────────────────────────────────────────────┐
│ Round 1: 议题拆解 [SUCCESS - Output Persisted]  │ ──▶ 跳过执行，直接读取结果
└─────────────────────────────────────────────────┘
             │ (依赖: Round 1 Output)
             ▼
┌─────────────────────────────────────────────────┐
│ Round 2: 数据收集 [FAILED -> PENDING (Retry 1)]│ ──▶ 从断点恢复，重新执行
└─────────────────────────────────────────────────┘
             │ (依赖: Round 2 Output)
             ▼
┌─────────────────────────────────────────────────┐
│ Round 3: 深度推理 [PENDING]                     │ ──▶ 等待前置完成
└─────────────────────────────────────────────────┘
```

通过这种设计，你的推演引擎能够实现：
1. **数据不丢失**：每轮输出落库，避免内存崩溃导致全盘重来。
2. **灵活重试**：单轮失败不影响已成功的轮次，支持自动和手动恢复。
3. **上下文清晰**：通过显式的 DAG 依赖关系管理输入输出，避免长链路推演中的上下文混乱。
