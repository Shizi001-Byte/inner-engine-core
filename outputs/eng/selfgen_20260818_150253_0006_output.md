# 任务类型: eng

# 引擎产物自动归档系统设计（感知层·收口模块）

沿用锚定：由「脑（元控制器）」掌握控制权，不采用单线死局；将归档拆为**阴阳双轨**：

- **阳轨**：引擎产出 → 分类 → 打标签 → 落盘 → 索引  
- **阴轨**：配置校验、超时兜底、目录自愈、失败重试  

整个系统是“开放、有界、循环”的负熵机制：把引擎的无序输出，转化为有序、可检索、可复用的信息资产。

---

## 1. 系统边界

输入：

```json
{
  "task_id": "task_123",
  "task_type": "code_review",
  "model_type": "B-turbo",
  "payload": { "output": "..." }
}
```

输出：

```json
{
  "archive_id": "arc_xxx",
  "category": "code",
  "tags": ["code_review", "B-turbo", "20260612"],
  "path": "/data/archive/code/2026/06/12/task_123/output.json",
  "status": "archived"
}
```

## 2. 总体架构

```
引擎产出
   │
   ▼
接入网关 ──► 归一化 ArchiveUnit
   │
   ├─────────────── 阳轨 ───────────────┐
   │                                    │
   │  自动分类 ──► 自动打标签 ──► 目录落盘 ──► 索引/回执
   │                                    │
   └────────────────────────────────────┘
   │
   ├─────────────── 阴轨 ───────────────┐
   │                                    │
   │  配置热更新验证                     │
   │  模型调用超时兜底                   │
   │  目录自愈/文件一致性                │
   │  失败重试/死信队列                  │
   │                                    │
   └────────────────────────────────────┘
   │
   ▼
脑（元控制器）统一调度
```

## 3. 阳轨：归档主流程

### 3.1 归一化

所有引擎产出统一封装为 `ArchiveUnit`：

- `archive_id`
- `task_id`
- `task_type`
- `model_type`
- `payload`
- `created_at`
- `size`
- `md5`

归一化是“有生于无”的第一步：把原始字节流变成可处理的结构化单元。

---

### 3.2 自动分类

分类策略：**规则优先，模型兜底**。

1. 先按 `task_type` 映射：
   - `code_review` → `code`
   - `report` → `report`
   - `config_generate` → `config`
   - `data_analysis` → `analysis`
   - 默认 → `other`

2. 如果规则置信度低，调用模型分类器。

3. 模型分类器必须走统一调用网关，强制超时：

| 模型 | 超时上限 |
|---|---|
| B-turbo | 300 秒 |
| A | 600 秒 |

4. 超时后不阻塞归档，降级为规则分类，并标记：

```json
{
  "fallback_reason": "classify_timeout",
  "timeout_ms": 300000
}
```

分类结果必须带 `category` 和 `confidence`。

---

### 3.3 自动打标签

标签来源：

- 系统标签：`task_type`、`model_type`、`category`、日期
- 内容标签：从输出中按关键词表提取
- 业务标签：如 `bugfix`、`urgent`、`high-priority`

标签约束：

- 统一小写
- 白名单控制，避免无限发散
- 单个任务最多 10 个标签

标签写入：

```json
{
  "tags": ["code_review", "B-turbo", "20260612", "bugfix"]
}
```

---

### 3.4 目录落盘

目录规则：

```
{base_dir}/{category}/{yyyy}/{MM}/{dd}/{task_id}/
├── output.json
├── metadata.json
└── tags.json
```

写入方式：

- 先写临时文件 `.tmp`
- 再原子重命名到最终路径
- 防止归档过程中出现半截文件

`metadata.json` 示例：

```json
{
  "archive_id": "arc_xxx",
  "task_id": "task_123",
  "task_type": "code_review",
  "model_type": "B-turbo",
  "category": "code",
  "tags": ["code_review", "B-turbo", "20260612"],
  "path": "/data/archive/code/2026/06/12/task_123/output.json",
  "md5": "...",
  "created_at": "...",
  "archived_at": "...",
  "fallback_reason": null
}
```

---

### 3.5 索引与回执

归档完成后，写入索引库：

```sql
INSERT INTO archive_meta
(archive_id, task_id, task_type, model_type, category, tags, path, status, created_at, archived_at)
VALUES (?, ?, ?, ?, ?, ?, ?, 'archived', ?, ?);
```

然后返回回执：

```json
{
  "archive_id": "arc_xxx",
  "status": "archived",
  "path": "/data/archive/code/2026/06/12/task_123/output.json"
}
```

## 4. 阴轨：稳态机制

### 4.1 配置修改后必须立即生效

这是历史失败经验的重点：

- 所有配置统一存储在 `ConfigStore`
- 所有组件只能通过 `ConfigClient` 读取配置，不允许散落读取点
- 配置更新后自动触发验证：

```
新配置写入 ConfigStore
        │
        ▼
ConfigClient 加载到影子配置
        │
        ▼
执行探针归档任务，验证分类、标签、目录
        │
        ▼
通过 → 切换生效
失败 → 回滚旧配置，并告警
```

这样避免“配置改了但行为没变”。

---

### 4.2 API 超时兜底

所有外部模型调用统一走调用网关：

```yaml
model_timeout_map:
  B-turbo: 300000   # 300秒
  A: 600000         # 600秒
```

调用网关强制：

- 超时立即中断
- 返回超时标记
- 归档流程降级为规则模式
- 不让超时导致整个任务失败

重试策略：

- 最多重试 3 次
- 指数退避：1s、2s、4s
- 仍然失败进入死信队列

---

### 4.3 目录自愈

阴轨定时巡检：

- 目录是否存在
- 目录是否可写
- 文件与索引是否一致
- 元数据是否完整

发现问题自动修复：

- 目录缺失 → 重建
- 文件缺失 → 从暂存区恢复
- 索引缺失 → 重新扫描目录补索引

## 5. 核心接口设计

```python
class ArchiveService:
    def archive(self, task_id, task_type, model_type, payload):
        unit = self.normalize(task_id, task_type, model_type, payload)
        category = self.classify(unit)
        tags = self.tag(unit, category)
        dest = self.build_path(category, unit)
        self.write_atomic(dest, unit, tags)
        self.index(dest, unit, tags)
        return self.receipt(unit, dest)
```

## 6. 避坑清单

| 历史教训 | 本系统对策 |
|---|---|
| 配置修改后未生效 | 统一 ConfigClient + 探针验证 + 失败回滚 |
| API 调用超时 | 统一调用网关，B-turbo 300秒，A 600秒，超时降级 |
| 单线执行死局 | 阴阳双轨并行，归档和校验同时进行 |
| 归档文件损坏 | 临时文件 + 原子重命名 |
| 分类不准 | 规则 + 模型 + 置信度 + 人工兜底目录 |

---

## 7. 最终效果

引擎每次产出后，系统自动完成：

- 任务分类
- 自动打标签
- 存入对应目录
- 建立索引
- 返回归档回执

并且整个流程在脑（元控制器）的稳态机制下，保持开放、有界、循环，持续把“无”序输出转化为“有”序资产。
