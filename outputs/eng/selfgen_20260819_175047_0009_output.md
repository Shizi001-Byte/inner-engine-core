# 任务类型: eng

# 多模型成本实时监控与自动熔断系统设计

## 0. 设计原则

- **每个模型独立计数、独立熔断、独立降级链**，不共用全局计数器。
- **所有运行时状态放在共享存储**（Redis/etcd），两个引擎实例通过分布式租约/锁互相接管，不依赖 systemd/supervisor/k8s。
- **所有配置从 state 读取**，本地文件只作为源；配置修改后必须执行 `sync --check` 回读验证。
- **计数语义统一**：`task_count` 只记真实任务调用，`bonus_count` 只记系统自触发调用，`count = task_count + bonus_count`，任何增加操作必须原子完成。
- **模型 ID 必须使用官方完整 model_id**，pro/turbo/light 不可混用；B模型 turbo 超时 300s，A模型 pro 超时 600s。

## 1. 总体架构

```text
                   models.yaml
                       │
                       v
              Config Sync / sync --check
                       │
                       v
   ┌─────────────────────────────────────────┐
   │            Shared State Store            │
   │  Redis / etcd                            │
   │  - cfg:models:{model_id}                 │
   │  - cnt:{model_id}:{window}               │
   │  - brk:{model_id}                        │
   │  - pending:{model_id}                    │
   │  - task:{task_id}                        │
   │  - lease:recovery                        │
   └─────────────────────────────────────────┘
        ▲            ▲            ▲
        │            │            │
   Engine A      Engine B    CostMonitor/RecoveryScheduler
        │            │
        └── BreakerRouter / Degrade / PendingQueue
```

两个引擎实例都运行同一套代码，共享 state。  
恢复调度器通过 `lease:recovery` 选主，只有持锁实例执行恢复；锁过期后另一个实例自动接管。

### 2.2 模型计数器（cnt）

每个模型独立 key：

```text
cnt:doubao-seed-2-1-turbo:2026-05-07
```

字段：

| 字段 | 语义 |
|---|---|
| `task_count` | 真实任务调用次数（含重试/降级后的真实调用） |
| `bonus_count` | 系统自触发调用次数（探针、健康检查） |
| `count` | 总调用次数，`count = task_count + bonus_count` |
| `completed_count` | 成功完成的调用次数，不等于 `count` |
| `prompt_tokens` | 累计输入 token |
| `completion_tokens` | 累计输出 token |
| `cost` | 累计成本，由价格表计算 |
| `error_count` | 失败/超时次数 |

> 禁止把 `count` 当 `tasks_completed` 展示。  
> 唯一的业务完成口径是 `completed_count` 和 task store 中的 `task_status=SUCCEEDED`。

### 2.3 熔断状态（brk）

```text
brk:doubao-seed-2-1-turbo
```

```json
{
  "state": "CLOSED",
  "trip_reason": "",
  "opened_at": 0,
  "cooldown_until": 0,
  "half_open_probe_count": 0,
  "half_open_max_probes": 3,
  "last_probe_ok": false
}
```

状态机：

```text
CLOSED --(成本/错误率/超时超过阈值)--> OPEN
OPEN   --(冷却结束 + 当前指标低于阈值)--> HALF_OPEN
HALF_OPEN --(探针成功次数达标)--> CLOSED
HALF_OPEN --(探针失败)--> OPEN
```

> 成本类熔断：如果当前窗口成本仍超阈值，即使冷却结束也不能恢复，必须等窗口重置或人工提高预算。  
> 错误率/超时类熔断：冷却结束后用探针验证，成功才恢复。

## 3. 工作流程

### 3.1 正常调用

1. 请求进入 BreakerRouter。
2. 查询 `brk:{model_id}`，状态为 `CLOSED`，放行。
3. 调用模型，设置 `timeout_ms`。
4. 收到 usage 后写 `UsageEvent`。
5. CostMonitor 消费事件，原子更新计数器和成本。

### 3.2 触发熔断

CostMonitor 更新计数器后判断：

```text
if cost >= cost_limit_per_window:
    将 brk:{model_id} 从 CLOSED 置为 OPEN
```

之后该模型的新请求不再直连，进入降级/排队逻辑。

### 3.3 降级 / 排队

```python
def route_or_park(req):
    model = req.model_id
    st = get_breaker(model)

    if st.state == "CLOSED":
        return invoke(model, req)

    if st.state == "HALF_OPEN" and is_probe_allowed(model, req):
        return invoke(model, req)

    # 降级链
    for fb in get_config(model).fallback_chain:
        if is_model(fb) and get_breaker(fb).state == "CLOSED":
            return invoke(fb, req)
        if fb in ("local-rule", "cache", "mock"):
            return local_fallback(fb, req)

    # 全部不可用，记录等待任务
    task_id = park_task(model, req)
    return {"status": 202, "task_id": task_id, "message": "model busy, queued"}
```

### 3.4 恢复后自动补跑

RecoveryScheduler 周期性扫描：

```python
for model in all_models:
    st = get_breaker(model)

    if st.state == "OPEN" and now >= st.cooldown_until:
        if current_cost(model) < cost_limit(model):
            cas_open_to_half_open(model)

    elif st.state == "HALF_OPEN":
        # 发送探针请求，探针计入 bonus_count
        ok = send_probe(model)
        if ok:
            incr_half_open_probe_count(model)
            if half_open_probe_count >= half_open_max_probes:
                cas_half_open_to_closed(model)
                start_drain(model)
        else:
            cas_half_open_to_open(model, backoff=True)

    elif st.state == "CLOSED":
        drain_batch(model)
```

Drain 批量补跑：

```python
def drain_batch(model):
    tasks = zrangebyscore("pending:" + model, "-inf", now,
                          limit=0, batch_size=config.drain_batch_size)
    for task_id in tasks:
        zrem("pending:" + model, task_id)
        hset("task:" + task_id, "status", "RUNNING")
        async_invoke(model, task_id)   # 使用 model.timeout_ms

    sleep(config.drain_interval_ms)
```

补跑失败时：

- 重试次数 `retry_count += 1`
- 按指数退避重新入队：`available_after = now + 2^retry_count * 30s`
- 超过 `max_retries` 则进入 `FAILED` 死信队列，人工处理。

## 4. 关键实现要点

### 4.1 原子计数，避免九维计数语义混乱

所有计数更新必须通过同一个 Lua 脚本完成：

```lua
-- usage_counter.lua
local key = KEYS[1]
local event_id = ARGV[1]
local event_type = ARGV[2]  -- 'task' / 'bonus'
local prompt_tokens = tonumber(ARGV[3])
local completion_tokens = tonumber(ARGV[4])
local cost = tonumber(ARGV[5])

-- 幂等去重，防止事件重放导致多计
if redis.call('SET', 'dedup:' .. event_id, '1', 'NX', 'EX', 86400) == false then
  return 0
end

if event_type == 'task' then
  redis.call('HINCRBY', key, 'task_count', 1)
elseif event_type == 'bonus' then
  redis.call('HINCRBY', key, 'bonus_count', 1)
end

redis.call('HINCRBY', key, 'prompt_tokens', prompt_tokens)
redis.call('HINCRBY', key, 'completion_tokens', completion_tokens)
redis.call('HINCRBYFLOAT', key, 'cost', cost)

local t = tonumber(redis.call('HGET', key, 'task_count') or 0)
local b = tonumber(redis.call('HGET', key, 'bonus_count') or 0)
redis.call('HSET', key, 'count', t + b)

return 1
```

> 禁止在客户端分别 `INCR task_count`、`INCR bonus_count`，否则并发下 `count != task_count + bonus_count`。

### 4.2 熔断冷却配置必须从 state 读取

```python
DEFAULT_COOLDOWN_SECONDS = 120

def get_cooldown(model_id):
    st = read_state("brk:" + model_id)
    if st.get("fuse_cooldown_override") is not None:
        return st["fuse_cooldown_override"]
    return DEFAULT_COOLDOWN_SECONDS
```

禁止在熔断逻辑里直接写 `cooldown = 120`。

### 4.3 配置修改后必须 sync --check

```bash
# 推送配置到 state
modelsync sync --config models.yaml --state redis://...

# 回读验证
modelsync sync --check --config models.yaml --state redis://...
```

`sync --check` 会比较本地配置与 state 中的 `checksum`，不一致则退出非 0。  
运行时只读 state，不读本地文件。

### 4.4 模型 ID 必须校验

`sync` 时必须校验 `model_id` 是否是官方文档中的完整 ID：

- 禁止 `pro` 代替 `doubao-seed-2-1-pro`
- 禁止 `turbo` 代替 `doubao-seed-2-1-turbo`
- 禁止 `light` 代替 `doubao-seed-2-1-light`
- 超时配置必须独立：turbo 300s，pro 600s

## 5. 高可用设计

- 两个引擎实例都运行 BreakerRouter 和 RecoveryScheduler。
- 实例通过 `instances:{engine_id}` 心跳互相发现。
- RecoveryScheduler 使用 `lease:recovery` 分布式锁，同一时间只有一个实例执行恢复补跑。
- 如果持锁实例宕机，租约到期后另一个实例自动接管。

不需要 systemd / supervisor / k8s 来守护引擎进程，引擎之间通过 state 自动完成故障接管。

---

## 6. 历史坑位规避清单

| 历史坑 | 本系统对策 |
|---|---|
| 配置修改后未生效 | 配置只从 state 读取；修改后必须 `sync --check` 回读验证 |
| API 超时 | 每个模型独立 `timeout_ms`：turbo 300s，pro 600s |
| B模型型号错配 | `sync` 时校验官方完整 model_id，pro/turbo/light 不可混用 |
| 熔断冷却配置不生效 | 冷却时间从 `state.fuse_cooldown_override` 读取，全局常量只做兜底 |
| 九维计数语义混乱 | `task_count` / `bonus_count` / `count` / `completed_count` 分离，Lua 原子更新，`count = task_count + bonus_count` |
| 恢复后打爆模型 | HALF_OPEN 先探针，再按 `drain_batch_size` 和 `drain_interval_ms` 限速补跑 |

---

## 7. 总结

这套系统以“每个模型独立计数 + 独立熔断 + 独立降级链 + 独立恢复队列”为核心，把每次模型调用视为分布式状态机的一次状态跃迁。  
成本超限、错误率超限、超时都会触发熔断；熔断期间任务进入持久化等待队列；恢复后通过探针和限速 drain 自动补跑，既保护预算，又不丢任务。
