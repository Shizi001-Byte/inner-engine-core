# 任务类型: eng

基于您提供的【避坑提醒】与【已有认知锚定】，我将在 V7.5 并发管线架构（无记忆修改 + WAL操作日志 + 多线程API调用→结果入队→串行后处理）的基础上，为您推演并设计**引擎产出的自动归档系统**。

本系统不仅是一个文件存储工具，更是**「800万token/天认知带宽」的守门人与过滤器**。它通过熵值评估决定内容的去向（注入认知池或丢弃），并通过 WAL+CID 机制保证无状态节点的高可用。

以下是系统架构设计：

---

### 一、 系统定位与核心原则
1. **守门人机制**：归档系统首先评估产出内容的“认知熵值”。高熵前沿内容进入「活跃认知池」并触发30分钟注入定时器；低熵垃圾内容直接打入冷归档或销毁，防止占用认知池。
2. **无状态与可恢复**：节点不保存归档状态。所有归档动作（分类、打标、移动）在执行前必须先写入 WAL 日志，通过 CID（内容寻址）定位实体文件。宕机重启时，只需重放 WAL 即可恢复归档现场。
3. **串行后处理**：归档操作发生在 V7.5 架构的“串行后处理”阶段，避免多线程并发写盘导致的 I/O 冲突和锁竞争。

---

### 二、 自动归档系统流水线设计

归档流水线分为五个核心阶段，全部在串行队列中执行：

#### 阶段 1：CID 生成与去重 (内容寻址)
*   **动作**：API返回结果入队后，串行处理器提取内容，计算其哈希值（如 SHA-256）作为 CID。
*   **作用**：相同内容天然去重。后续的标签、目录关系均通过 CID 指向内容实体，而非直接存储内容。

#### 阶段 2：熵值评估与自动打标 (避坑：API超时控制)
*   **动作**：调用轻量级模型对内容进行分类和打标。**【避坑执行】**：此处必须根据任务类型预设合理 timeout。如果是 B模型turbo 处理，设置 300秒 超时；如果是 A模型 深度处理，设置 600秒 超时。超时直接熔断并标记为 `ARCHIVE_TIMEOUT`。
*   **标签维度**：
    *   `entropy_level`：high（高熵/高价值） / low（低熵/冗余）
    *   `domain`：业务领域（如 tech, finance, ops）
    *   `task_type`：任务类型（如 code_gen, data_analysis）

#### 阶段 3：WAL 预写日志 (无状态保证)
*   **动作**：在真正写入文件系统前，将归档意图写入 WAL。
    *   日志格式：`[TXN_ID] [CID] [TAG:domain=tech, entropy=high] [ACTION:MOVE_TO:/archive/tech/]`
*   **作用**：此时文件尚未移动，但系统状态已持久化。若此时宕机，重启后扫描 WAL 未提交的事务即可重做，无需遍历文件系统排查“断点”。

#### 阶段 4：目录路由与实体落盘
*   **动作**：根据标签执行物理落盘。
    *   **高熵内容**：存入 `/active_pool/` 目录，同时触发「30分钟新认知注入定时器」，等待下一批次任务刷新时使用。
    *   **低熵内容**：存入 `/cold_archive/` 目录，或直接标记为可清理。
*   **验证**：落盘成功后，更新 WAL 状态为 `COMMITTED`。

#### 阶段 5：缓存刷新与认知淘汰 (认知锚定执行)
*   **动作**：系统维护一个全局任务计数器。每完成 10 个任务的归档，触发以下机制：
    1.  **刷新缓存**：清理当前的临时上下文缓存。
    2.  **淘汰低价值**：扫描 `/active_pool/`，根据评分算法淘汰排名靠后的低价值认知块，确保 800万 token/天 的高效转化率不被注水。

---

### 三、 避坑机制落地与配置管理

针对历史失败经验，本系统做以下硬性约束：

#### 1. 配置修改生效与验证机制（严防“配置未生效”）
归档系统的目录映射规则、高/低熵判定阈值、API超时时间均由配置中心管理。
*   **设计**：新增配置（如新增一个归档目录 `bio-tech`）时，必须同步修改**「读取点字典」**。
*   **强制验证**：修改配置后，系统自动拦截下一个真实任务，使用 Mock 数据执行一次 Dry-Run（空跑），并打印实际读取到的配置值。若与预期不符，自动回滚配置并告警，绝不将带病配置放入生产线。

#### 2. API 超时与降级机制（严防“调用超时卡死”）
*   **设计**：熵值评估 API 调用强制携带动态 timeout 参数。
    *   B模型turbo：`timeout = 300s`
    *   A模型：`timeout = 600s`
*   **降级策略**：若发生超时，系统不卡死，而是将该任务内容直接打上 `entropy=unknown` 标签，存入 `/quarantine/`（隔离区）目录，等待人工定期复核，保证主归档流水线不阻塞。

---

### 四、 系统运行时序图（文字版）

1. **多线程生产**：Worker 1~N 并发调用 API，结果放入 `Result_Queue`。
2. **串行消费**：`Archive_Worker` 从队列取出 Result。
3. **CID 生成**：计算 Hash，确认是否已归档。
4. **评估打标**：调用评估 API（严格执行 300s/600s 超时控制）。
5. **WAL 预写**：记录 `[CID -> 标签 -> 目标目录]`。
6. **物理落盘**：写入对应目录，高熵内容进入认知池预备态。
7. **WAL 提交**：标记日志为完成。
8. **周期校验**：每10个任务检查计数器，触发缓存刷新与认知池淘汰，注入30分钟内的新认知。

通过上述设计，归档系统不仅完美融入 V7.5 的 WAL+CID 无状态架构，还通过严格的熵值过滤与周期刷新，保护了“800万token/天”的核心认知带宽，同时用硬性探针机制彻底杜绝了配置不生效和API超时的坑。
