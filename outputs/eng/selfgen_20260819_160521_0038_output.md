# 任务类型: eng

# 三方同步自动化设计：Gitee / Feishu / Supabase

## 一、总体架构

```text
Gitee push / Feishu upload / Supabase storage change
                  │
                  ▼
        Webhook / 轮询 → sync_inbox
                  │
                  ▼
        ① 锚点校验（ID / Token / Endpoint / 路径）
                  │
                  ▼
        ② 重大变更过滤
                  │
                  ▼
        ③ 计算内容 Hash → 生成幂等 Job ID
                  │
                  ▼
        ④ 获取文件锁（按 path 加锁）
                  │
                  ▼
        ⑤ 冲突检测
                  │
                  ▼
        ⑥ 同步执行：Gitee commit / Feishu upload / Supabase upsert
                  │
                  ▼
        ⑦ 回读校验 Hash
                  │
                  ▼
        ⑧ 更新 sync_manifest 和 sync_jobs
```

核心原则：

- **锚点校验优先于链路优化**
- **幂等键基于内容 Hash，而不是事件 ID**
- **冲突时引擎只做隔离、备份、通知，不替人做最终决策**

---

## 二、锚点校验（防坑前置）

每次同步前，必须用最小成本校验以下锚点，任何一个失败就直接终止，不进入同步链路：

| 系统 | 必校验锚点 |
|---|---|
| Gitee | repo_id、branch、webhook secret、API base URL、access token 权限 |
| Feishu | app_id / app_secret、folder_token、drive API endpoint、事件订阅验证 |
| Supabase | project_ref、service_role_key、bucket_id、storage API endpoint |
| 任务本身 | source_event_id、path、content_hash、sync_policy_version |

校验失败时，记录错误并告警，不要继续执行。

---

## 三、触发与“重大变更”过滤

所有事件先进入 `sync_inbox`，再被同步引擎消费。

“重大变更”规则建议做成配置：

```json
{
  "gitee": {
    "trigger": "tag:v* OR commit_message_contains:[sync] OR path_prefix:/release/"
  },
  "feishu": {
    "trigger": "folder_token:release_folder OR file_name_prefix:v"
  },
  "supabase": {
    "trigger": "bucket:release-assets AND metadata.major==true"
  }
}
```

不满足规则的事件只记录，不触发同步。

## 四、幂等性设计

### 1. 幂等键生成

```text
job_id = sha256(source + "|" + path + "|" + content_hash + "|" + sync_policy_version)
```

- `content_hash` 是文件内容的 SHA-256
- 不使用 `event_id` 作为唯一幂等键，因为同一内容可能被多个不同事件重复投递
- `sync_policy_version` 用于同步规则升级后，避免旧 job_id 屏蔽新逻辑

### 2. 写入前检查目标状态

每个目标系统写入前，先读取当前文件/对象 Hash：

- 如果目标 Hash 已等于期望 Hash，跳过写入
- 如果目标不存在，则创建
- 如果目标存在且 Hash 不同，进入冲突检测

### 3. 数据库唯一约束

```sql
sync_jobs(
  id text primary key,
  source text,
  source_event_id text unique,
  path text,
  content_hash text,
  status text,
  ...
)
```

- `source_event_id` 唯一：防止同一个 webhook 事件重复消费
- `id` 是内容级幂等键：同一内容重复触发时直接返回

## 五、冲突处理方案

使用 `sync_manifest` 记录每个文件的同步状态：

```text
path: docs/release.md
base_hash: H0          -- 上次三方都一致的内容 Hash
gitee_hash: H0
feishu_hash: H0
supabase_hash: H0
version: 12
last_sync_source: gitee
```

### 1. 正常同步

- Gitee 内容变为 H1
- Feishu 和 Supabase 仍为 H0
- 不存在冲突，直接把 H1 同步到 Feishu 和 Supabase

### 2. 冲突判定

如果同一路径下：

- Gitee 是 H1
- Feishu 是 H2
- Supabase 是 H0
- 且 H1 ≠ H2 ≠ H0

则视为三方分叉冲突。

### 3. 冲突自动处理策略

| 文件类型 | 策略 |
|---|---|
| 文本/代码文件 | 尝试三方合并：`merge3(base=H0, source=H1, target=H2)`，合并成功则同步合并结果；合并失败则创建冲突副本 |
| 二进制文件 / 图片 / 压缩包 | 不自动合并，保留双方为冲突副本，通知人工 |
| 有明确 canonical source 的文件 | 例如代码以 Gitee 为准，则 Gitee 变更可自动覆盖其他端，但被覆盖前先备份为 `*.conflict-{timestamp}` |

### 4. 冲突副本命名

```text
path.conflict-20250620103000.ext
```

同时发送通知到飞书群，附上：

- 冲突文件路径
- 两个版本的来源
- 内容 Hash
- 人工处理入口

## 六、同步执行细节

### Gitee 代码提交

- 更新文件前先 GET 文件信息，拿到 `sha`
- 如果 `sha` 不存在，则创建文件
- 如果 `sha` 与预期不匹配，说明 Gitee 侧有并发修改，重新拉取后走冲突检测
- commit message 格式：

```text
sync(job_id): docs/release.md
```

### Feishu 文件上传

- 先按 `folder_token + file_name` 查找同名文件
- 如果存在且 Hash 相同，跳过
- 如果存在且 Hash 不同，尝试上传新版本；若无覆盖能力，则上传为新文件并标记版本关系
- 冲突时上传为 `*.conflict-{timestamp}`

### Supabase 存储同步

- 使用 Storage `upsert=true` 覆盖写入
- 写入前读取现有对象元数据中的 `content_hash`
- 若为冲突，先将原对象复制为 `path.conflict-{timestamp}`，再覆盖

## 七、配置管理防坑

配置统一存 `sync_config` 表：

```text
key: sync_rules
value: { ... }
version: 42
```

引擎每次执行任务前：

1. 读取 `sync_config` 的 `version`
2. 如果与本地缓存不同，触发 reload
3. reload 后必须做一次 dry-run 验证

避免“配置改了但读取点没改”的问题。

## 八、超时、重试与告警

### 超时预设

| 场景 | 超时 |
|---|---|
| 普通同步任务（不含模型调用） | 120s |
| 含 B 模型 / turbo 的同步判断 | 300s |
| 含 A 模型 / 复杂冲突合并 | 600s |
| Gitee API 单次调用 | 60s |
| Feishu API 单次调用 | 120s |
| Supabase Storage 单次调用 | 120s |

所有外部调用必须携带 `context`，超时后立即取消，不悬挂。

### 重试

```text
指数退避：1s -> 5s -> 30s -> 60s
最多 5 次
```

重试仍失败，进入 `sync_dead_letter` 表，并触发飞书告警。

## 九、关键伪代码

```python
def handle_event(event):
    # 1. 锚点校验
    validate_anchors(event)

    # 2. 路径映射 + 重大变更过滤
    path = map_path(event)
    if not is_major_change(event):
        return

    # 3. 内容 Hash + 幂等键
    content = await fetch_content(event)
    content_hash = sha256(content)
    job_id = make_job_id(event.source, path, content_hash, config.sync_policy_version)

    # 4. 文件锁
    with lock(f"sync:{path}"):

        # 5. 幂等检查
        if job_exists_success(job_id):
            return

        job = create_job(job_id, event, path, content_hash)

        # 6. 冲突检测
        manifest = get_manifest(path)
        if is_conflict(manifest, event.source, content_hash):
            resolve_conflict(manifest, event, content)
            return

        # 7. 同步到三端
        sync_to_gitee(path, content)
        sync_to_feishu(path, content)
        sync_to_supabase(path, content)

        # 8. 回读校验
        verify_all_targets(path, content_hash)

        # 9. 更新 manifest
        update_manifest(path, content_hash, event.source, job_id)
        mark_job_success(job_id)
```
