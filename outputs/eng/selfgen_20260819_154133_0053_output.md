# 任务类型: eng

## 设计引擎三方同步自动化方案

> 核心不是“把三个 API 接在一起”，而是以 **change_id + 内容哈希** 为纽带，形成“先验证、再分工、后沉淀规范”的有机同步链。  
> 以下方案同时覆盖：Gitee 代码提交、飞书文件上传、Supabase 存储同步、重大变更自动触发、幂等性、冲突处理、冷却重试。

---

## 1. 总体架构

```
设计引擎发布 major 变更
        │
        ▼
生成 ChangeManifest（change_id + 文件清单 + SHA256）
        │
        ▼
编排器 Orchestrator
        │
        ├── GiteeConnector     → 代码提交
        ├── FeishuConnector    → 文件上传
        └── SupabaseConnector  → 存储同步
        │
        ▼
每个连接器执行后立即 verify（读回目标端内容比对哈希）
        │
        ▼
全部成功 → 更新 ledger，重置冷却
部分失败 → 进入冷却，保留失败状态，幂等重试
```

### ChangeManifest 示例

```json
{
  "change_id": "v7.5.0-20250601-3f2a",
  "version": "7.5.0",
  "trigger": "design_engine.major_release",
  "source_commit": "3f2a9c...",
  "artifacts": [
    {
      "logical_path": "code/generated.py",
      "sha256": "abc123...",
      "size": 1024
    },
    {
      "logical_path": "docs/spec.md",
      "sha256": "def456...",
      "size": 2048
    }
  ]
}
```

## 2. 自动触发规则

### 触发源

1. **设计引擎发布事件**  
   - 设计引擎完成重大变更后，发送 `design.major_change` 事件。
   - 事件体包含 `change_id`、`version`、`artifacts`。

2. **Gitee Tag 推送**  
   - Webhook 监听 `push` 事件，当 tag 匹配 `v*` 时触发。
   - 忽略 `.sync/` 和 `ledger/` 相关提交，避免循环触发。

3. **定时兜底扫描**  
   - 每小时扫描一次 Gitee 新 tag，对比本地 ledger，发现漏同步则补跑。

### “重大变更”定义

- 版本号跃迁，如 `v7.2 → v7.5`
- 配置 schema 变更
- 生成的 API 契约/代码结构变化
- 设计引擎显式标记 `major: true`

## 3. 幂等性设计

每个连接器都使用**目标端原生标记**来判断是否已执行，不依赖中心状态表作为唯一事实。

### 3.1 Gitee 代码提交

- 提交信息固定包含 `sync: {change_id}`。
- 提交前检查：
  - 远端分支是否已包含相同 `change_id` 的提交；
  - 提交树（tree hash）是否一致。
- 如果内容无变化，不产生空提交。
- Push 使用 `--force-with-lease`，避免覆盖远端未知提交。
- 打 Tag 时：
  - 如果 tag 已存在且指向相同 commit，则跳过；
  - 如果 tag 已存在但指向不同 commit，判定为冲突，停止并告警。

### 3.2 飞书文件上传

- 飞书侧目录结构：

```
设计产出/
  20250601-v7.5.0-3f2a/
    manifest.json
    spec-3f2a.md
    generated-3f2a.py
```

- 上传前检查目录是否存在。
- 文件名携带 `change_id` 或哈希前缀：
  - `spec-3f2a.md`
  - `generated-3f2a.py`
- 如果目录中已存在同名同哈希文件，跳过。
- 不使用个人扫码绑定，改用飞书应用凭证获取 `tenant_access_token`，避免“扫码绑定失败”类问题。

### 3.3 Supabase 存储同步

- Bucket：`design-engine`
- 对象 Key 采用内容寻址：

```
by-hash/{sha256}/{filename}
```

- 同时维护一个“最新指针”：

```
latest/{change_id}/manifest.json
```

- 上传前调用 `HEAD` 检查对象：
  - 存在且 `metadata.sha256 == 期望值` → 跳过；
  - 不存在 → 上传；
  - 存在但哈希不同 → 走冲突处理。

## 4. 冲突处理方案

### 4.1 冲突类型

| 类型 | 示例 |
|---|---|
| 重复触发 | 同一 `change_id` 被事件和定时扫描同时触发 |
| 内容漂移 | 目标端文件被手动修改，哈希与 manifest 不一致 |
| 远端领先 | Gitee 远端出现本地没有的新提交 |
| 并发冲突 | 两个不同 `change_id` 同时执行同步 |
| 部分成功 | Gitee 成功、飞书失败，重试时不能重复提交 |

### 4.2 处理矩阵

| 场景 | Gitee | 飞书 | Supabase |
|---|---|---|---|
| 目标端无此文件 | 新建提交 | 上传 | 上传 |
| 目标端存在且哈希一致 | 跳过 | 跳过 | 跳过 |
| 目标端存在但哈希不一致，且无 generated 标记 | 不覆盖，备份到 `_conflicts/` 后告警 | 不覆盖，上传新哈希版本并告警 | 不覆盖，备份到 `_conflicts/` 后告警 |
| 目标端存在但哈希不一致，但有 generated 标记 | 覆盖，旧版本留在 git 历史 | 上传新哈希文件，更新 manifest | 覆盖，旧对象移入 `_conflicts/` |
| 远端领先 | `--force-with-lease` 失败，停止并告警 | 不适用 | 不适用 |
| 并发两个 change_id | 全局串行锁 | 全局串行锁 | 全局串行锁 |

### 4.3 串行与锁

- 默认使用**全局串行执行**，同一时间只处理一个 `change_id`。
- 锁可以使用本地文件锁 + Supabase 数据库锁双保险。
- 锁的 key 为 `sync:global`，owner 为 `change_id`，带过期时间。
- 获取锁失败则等待重试，避免并发覆盖。

## 5. 验证、冷却与重试

### 5.1 验证原则

> 状态标签只是“基因型”，目标端真实内容才是“表观状态”。

- 每个连接器执行完，必须从目标端**读回文件**，计算 SHA256。
- 与 manifest 中哈希比对一致，才标记成功。
- 不能只读自己的状态表就认为成功。

### 5.2 冷却重置机制

- 成功验证后，将冷却时间重置为 0。
- 失败后保留冷却时间，进入指数退避：

```
1 分钟 → 5 分钟 → 30 分钟 → 2 小时
```

- 冷却期内不自动重试同一个 `change_id`。
- 人工介入后可手动解除冷却。

### 5.3 超时设置

- 普通 API 调用必须设置 timeout：
  - Gitee API：30s
  - 飞书 API：60s
  - Supabase API：60s
- 如果同步前需要模型生成提交说明/版本摘要：
  - B 模型 turbo：300 秒
  - A 模型：600 秒
- 禁止无界等待。

## 6. 配置修改的“三点同步”

新增任何配置项时，必须同时修改：

1. 配置定义文件：`config.schema.json`
2. 配置加载器：`config_loader.py`
3. 配置读取点：API / UI / 实际使用该配置的代码

否则会出现“配置改了但没生效”的问题。

编排器启动时执行配置自检：

- 加载 `config.schema.json`
- 对比实际读取到的配置值
- 如果存在缺失或类型不匹配，直接 fail-fast

---

## 7. 连接器健康检查

每次同步前检查三个连接器：

| 连接器 | 检查方式 |
|---|---|
| Gitee | `GET /user`，验证 token 权限 |
| 飞书 | `GET /auth/v3/tenant_access_token/verify` |
| Supabase | `HEAD /storage/v1/object/...`，验证 service role key |

连接失败不重试，直接进入冷却，避免无效噪音。

---

## 8. 演进方向

这套方案不是机械地把三个 API 并联，而是让三方以 `change_id` 为纽带、以哈希为信任、以验证为闭环，形成可自我修正的同步社群。

后续可以继续演进：

- 增加语义级冲突检测
- 支持多分支并行同步
- 将冲突策略做成可插拔规则
- 最终走向“可演化性的演化”

---

**一句话总结：**  
用 `change_id` 保证幂等，用 `SHA256` 验证事实，用 `冷却重置` 防止噪音，用 `冲突矩阵` 守住安全边界。
