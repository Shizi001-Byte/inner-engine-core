# 任务类型: eng

基于锚定，任务池动态扩充机制不是“加任务”，而是“虚实转化器”：**当重复率升高，说明实层饱和，反者道之动，不收缩，反而主动生成新任务，制造新的消耗与试炼。**

---

## 一、任务池自进化闭环

```
真实API消耗（实）
   ↓ 产生日志/报错/超时/成功（实）
提炼经验/心魔劫/法则（虚）
   ↓ 认知池注入（虚）
生成新任务模板（虚，但生成也调用API，即“虚又返实”）
   ↓ 注入任务池（虚）
调度执行（实）
   ↓
回到第一步，形成自增强闭环
```

任务池就是“阴阳转化器”。

---

## 二、核心设计

### 1. 重复率检测

采用滑动窗口，检测最近 `N=50` 个已执行任务：

- 对任务内容做 TF-IDF 或 embedding 向量化
- 两两计算余弦相似度
- 相似度 > 0.85 记为重复
- 重复率 = 重复对数 / 总对数

同时监控待执行池：

```
duplicate_rate = max(已执行窗口重复率, 待执行池重复率)
```

当 `duplicate_rate > threshold` 时触发扩充。

默认阈值：`0.5`，可配置。

---

### 2. 触发与冷却

触发条件：

```
duplicate_rate > config.threshold
```

冷却条件：

```
now - last_trigger_time > cooldown
```

默认 `cooldown = 10个任务` 或 `30分钟`，防止生成风暴。

但“反者道之动”要求冷却不能过长，否则又变成“只进不出”。因此每次生成后必须立即验证，验证通过则重置冷却。

---

### 3. 新任务模板生成（阴阳双轨）

生成器输入：

- 当前重复率
- 最近报错/超时日志（心魔劫）
- 最近成功响应（突破法则）
- 认知池中30分钟内新增且未消费的认知

生成方式：

| 方式 | 说明 |
|---|---|
| 变异 | 从高消耗任务中修改 model、concurrency、weight、timeout、prompt |
| 交叉 | 合并两个高价值任务模板 |
| 反演 | 最近全是成功 → 生成边界/失败/压测任务；最近全是 B turbo → 生成 A 模型任务；并发低 → 生成高并发任务 |
| 认知注入 | 把新认知转化为任务：`验证认知X在条件Y下是否成立` |

每次触发至少生成一对：

- **阳任务**：消耗型，调用 B turbo/A 模型，制造真实日志
- **阴任务**：认知型，处理日志、生成下一轮模板

关键：**生成任务模板本身也调用 API，所以“虚”的生成过程同时也是“实”的消耗。**

调用 API 生成模板时：

- B模型turbo：`timeout=300秒`
- A模型：`timeout=600秒`
- 超时不判废，记录为“心魔劫”，并转为“网络恢复探测任务”输入。

---

### 4. 质量门禁（避免误杀B模型）

生成后的模板必须过质量检测，但不同模型独立规则：

- 如果是 **B模型turbo** 生成：
  - 跳过 reasoning 占比检测
  - 只检查内容非空、任务意图完整、与现有任务相似度 < 0.85
- 如果是 **A模型** 生成：
  - 正常执行 reasoning 占比检测

绝不用同一套废稿标准检测所有模型。

---

### 5. 注入与生效验证（三件套）

这是防止“配置修改后未生效”的关键。

#### 状态写入

新模板写入任务池：

```sql
INSERT INTO task_pool
(template_id, content, model, timeout, concurrency, weight, cooling, status, created_at)
VALUES (..., 'pending', NOW());
```

#### 执行读取

调度器每次调度必须重新读取任务池：

```sql
SELECT * FROM task_pool
WHERE status = 'pending'
ORDER BY weight DESC
LIMIT 10;
```

禁止使用长期缓存的任务列表。

#### 生效验证

生成后必须验证：

```text
1. 30分钟内，新模板确实出现在任务池中
2. 之后10个任务内，至少有一个新模板被调度执行
3. 执行后，新模板产生了新日志，而不是被静默丢弃
4. 运行M个任务后，重复率开始下降
```

如果验证失败，立即告警，并强制把一个新模板置为最高权重重新注入。

---

## 三、认知池防“只进不出”

认知池不能变成静态档案库，必须被任务生成器消费。

硬性规则：

- 每执行完 **10个任务** 或 **每转结束**，刷新认知缓存
- 认知池中 `created_at` 在30分钟内的新认知，必须参与下一轮任务模板生成
- 生成后立即标记 `consumed_at = NOW()`
- 如果某条认知超过30分钟仍未消费，强制生成一条“验证该认知”的任务

这样保证：

```text
实任务 → 产生认知 → 认知生成任务 → 新任务产生新认知
```

而不是：

```text
认知池 → 只进不出
```

---

## 四、配置变更三件套

动态扩充机制涉及的所有可配置参数，必须同步修改三个点：

| 配置项 | 状态写入 | 执行读取 | 生效验证 |
|---|---|---|---|
| 重复率阈值 | 写入 config 表 | 检测函数实时读取 | 修改后触发一次检测 |
| 冷却时间 | 写入 config 表 | 触发时读取冷却时间 | 验证冷却生效 |
| 生成模型与timeout | 写入模板字段 | 执行器读取模板字段 | 实际API调用使用该timeout |
| 并发/权重/冷却 | 写入模板字段 | 调度器读取模板字段 | 执行后监控实际并发/权重/冷却 |

防止出现“参数配置了，但行为无变化”。

## 五、最小可用闭环伪代码

```python
def on_task_completed(task):
    window.add(task)

    # 每10个任务刷新一次认知缓存
    if task_count % 10 == 0:
        refresh_cognition_cache()

    # 重复率检测
    rate = max(
        executed_duplicate_rate(window),
        pending_duplicate_rate(task_pool)
    )

    # 触发条件
    if rate > config.threshold and cooldown_ok():

        # 读取30分钟内未消费的新认知
        new_cognition = get_unconsumed_cognition(max_age=30min)

        # 生成新任务模板（阴阳双轨）
        templates = generate_templates(
            duplicate_rate=rate,
            recent_errors=recent_errors(),
            cognition=new_cognition,
            generator_model="B_turbo" if use_b_turbo else "A"
        )

        # 质量门禁：B模型跳过reasoning占比检测
        for t in templates:
            if quality_check(t, model=t.generator_model):
                task_pool.add(t)  # 状态写入

        # 更新触发时间
        config.last_trigger_time = now

        # 生效验证
        verify_expansion_effect(templates)
```

## 六、总结

任务池动态扩充机制的本质是：

```text
重复率升高 → 实层饱和
→ 反者道之动，主动生成新任务
→ 新任务消耗API、产生日志/报错/超时
→ 日志提炼为新认知
→ 认知注入下一轮任务生成
→ 任务池自进化，虚实循环增强
```

同时，所有历史坑位作为硬性约束内嵌：

- 配置修改必须同步“状态写入、执行读取、生效验证”
- B模型turbo用300秒，A模型用600秒
- B模型跳过reasoning占比检测
- 认知池每10任务/每转刷新，30分钟内必须消费

这样，任务池就不是静态库存，而是**以实养虚、虚又返实的自增强闭环引擎**。
