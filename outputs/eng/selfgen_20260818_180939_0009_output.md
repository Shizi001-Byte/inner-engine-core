# Supabase 记忆脑增量同步方案（推演）

## 推演结论

基于已有锚定，方案核心是：

- **同步单位是 block，不是 file**  
  文件只是「有序 block id 列表」的索引。
- **远端只存不可变 DAG 顶点**  
  不存同步任务记录，只存 `block / index / tombstone` 顶点。
- **流程固定为 Detect → Diff → Commit，每节点三转，共九转。**
- **每次提交前校验哈希、结构、来源。**
- **超时或冲突时停止写入，熔断保护记忆脑不被混乱固化。**

## 一、远端数据模型

```sql
-- 通用顶点表：block / index / tombstone 都是 DAG 顶点
create table vertices (
  id text primary key,
  type text not null check (type in ('block','index','tombstone')),
  created_at timestamptz not null default now()
);

-- 不可变块：内容寻址
create table block_vertices (
  id text primary key references vertices(id),
  content text not null,
  content_hash text not null,
  producer_model text,          -- A / B-turbo，用于质量规则分流
  created_at timestamptz not null default now()
);

-- 不可变文件版本：文件 = 有序 block id 列表
create table index_vertices (
  id text primary key references vertices(id),
  file_path text not null,
  block_ids text[] not null,    -- 有序 block ids
  created_at timestamptz not null default now()
);

-- 不可变墓碑：表示文件删除
create table tombstone_vertices (
  id text primary key references vertices(id),
  file_path text not null,
  created_at timestamptz not null default now()
);

-- DAG 边：index/tombstone 之间的父子关系
create table vertex_edges (
  parent_id text references vertices(id),
  child_id text references vertices(id),
  primary key (parent_id, child_id)
);

-- 读指针：memory brain 只通过它读最新状态
create table sync_heads (
  file_path text primary key,
  head_id text references vertices(id),
  head_type text check (head_type in ('index','tombstone')),
  updated_at timestamptz not null default now()
);

-- 同步配置 + 读取点
create table sync_config (
  key text primary key,
  value jsonb not null,
  version bigint not null
);

create table runtime_state (
  key text primary key,
  value text not null
);
```

ID 规则：

```text
block_id      = sha256('block\0' + canonical_content)
index_id      = sha256('index\0' + file_path + '\0' + block_ids.join('\0'))
tombstone_id  = sha256('tombstone\0' + file_path + '\0' + parent_id)
```

## 二、九转流水线

### Detect 节点：三转

1. **本地扫描**  
   watch + 定时全量扫描。  
   对每个文件做 block split，计算 block ids 和 file hash。  
   只对变化的文件做重切分，未变化文件直接使用缓存。

2. **远端读头**  
   查询 `sync_heads`，拿到每个文件当前 `head_id`。  
   如果 head 是 index，取它的 `block_ids`；如果是 tombstone，表示远端已删除。

3. **变更分类**  
   对比本地快照和远端 head，分类为：

   - 无变化
   - 仅本地变化 → push
   - 仅远端变化 → pull
   - 两边都变 → 进入三方合并/冲突
   - 删除 vs 修改 → 冲突
   - 两边都删除 → no-op

---

### Diff 节点：三转

1. **基线定位**  
   从本地 `local_state` 找到上次同步的 head。  
   通过 `vertex_edges` 找到本地 head 与远端 head 的最近公共祖先 LCA。  
   如果是首次同步且本地远端都有内容，视为无共同祖先，进入人工冲突。

2. **块级 diff3**  
   对每个文件做：

   ```text
   base   = 上次同步的 block_ids
   local  = 当前本地 block_ids
   remote = 当前远端 block_ids
   ```

   用 diff3 比较三个序列。  
   只有同一位置、同一 block 被两边不同修改时才叫冲突。  
   不同 block 的修改可以自动合并。

3. **生成 DAG 计划**  
   生成提交负载：

   ```json
   {
     "new_blocks": [],
     "new_indexes": [],
     "new_edges": [],
     "new_tombstones": [],
     "heads": [],
     "config_updates": [],
     "config_version": 43
   }
   ```

   如果有冲突，计划是 `STOP`，不生成任何写入。

---

### Commit 节点：三转

1. **预检**  
   - **哈希校验**：重新计算每个 block/index/tombstone id，必须匹配。  
   - **结构校验**：index 的 `block_ids` 不能有 null，顺序必须保留，所有 block id 必须存在或同时提交。  
   - **来源校验**：`file_path` 必须是规范化绝对路径，且与本地源文件匹配。  
   - **质量门禁**：按 `producer_model` 分流规则，B-turbo 跳过 reasoning 占比检测。

2. **事务写库**  
   调用 Supabase RPC `sync_commit(payload)`，在单个 Postgres 事务内：

   - `insert into vertices ... on conflict do nothing`
   - `insert into block_vertices ... on conflict do nothing`
   - `insert into index_vertices ... on conflict do nothing`
   - `insert into tombstone_vertices ... on conflict do nothing`
   - `insert into vertex_edges ... on conflict do nothing`
   - upsert `sync_heads`
   - 更新 `sync_config`，并同步更新 `runtime_state.config_version` 读取点

   这样即使重复提交，也是幂等的。

3. **读回验证**  
   提交后立刻读回 `sync_heads` 和对应顶点，核对哈希和结构。  
   更新本地 `local_state`。  
   验证失败则打开熔断，不再重试。

## 三、冲突处理

冲突处理遵循一个原则：

> 不能确定如何写，就不写。

### 自动合并

本地和远端都修改了同一文件，但改的是不同 block：

```text
base:   [A, B, C, D]
local:  [A, B', C, D]
remote: [A, B, C, D']

merged: [A, B', C, D']
```

只上传 `B'` 和 `D'`，`A`、`C` 不动。  
新 index 的 `parent_id` 同时指向 local head 和 remote head，形成 DAG 合并节点。

### 必须停止的冲突

- 两边改了同一个 block，且修改结果不同
- 一边删除文件，另一边修改文件
- 首次同步时本地和远端都有该文件，且无共同祖先
- 结构校验或来源校验失败

停止后：

- 不写入任何 block/index/tombstone
- 打开熔断
- 生成冲突报告到 `.sync/conflicts/`
- 人工解决后，用 `--resolve` 显式提交，index 的 parents 包含 local head 和 remote head

## 四、防坑与熔断

### 1. 配置修改必须同步读取点

`sync_config` 不能只更新值，必须在同一事务内更新：

```text
runtime_state.config_version = new_version
```

所有读取方必须通过 `get_config()` 读取，先检查 `config_version`。  
提交后立即读回验证，确保新配置生效。

### 2. 超时按模型预设

- B-turbo 模型调用：**300 秒**
- A 模型调用：**600 秒**
- 普通 DB 操作：默认 60 秒

超时后打开熔断，停止写入。  
超时熔断是防止「把混乱固化进记忆脑」的保险丝。

### 3. B-turbo 跳过 reasoning 占比检测

质量检测规则必须按模型独立配置：

```json
{
  "model": "A",
  "enabled": ["reasoning_ratio", "structure", "source"]
}
```

```json
{
  "model": "B-turbo",
  "enabled": ["structure", "source"],
  "disabled": ["reasoning_ratio"]
}
```

因为 B-turbo 的 reasoning 占比 70%–82% 是正常特性，不能误判为废稿。

## 五、一次完整同步示例

假设本地修改了 `memory.md` 的 B block，远端有人修改了 D block。

1. **Detect**  
   本地发现 `memory.md` 变化；远端 `sync_heads` 也变化。  
   判定为「两边都变」。

2. **Diff**  
   找到 LCA 后 diff3：

   ```text
   base:   [A, B, C, D]
   local:  [A, B', C, D]
   remote: [A, B, C, D']
   ```

   非冲突，生成计划：上传 `B'`、`D'`，生成新 index `[A, B', C, D']`。

3. **Commit**  
   预检通过后，事务写入两个新 block、一个新 index、两条 DAG 边，更新 `sync_heads`。  
   读回验证通过，本地状态更新。

最终效果：

- 没有上传整个文件
- 没有覆盖任何旧 block
- 远端多了一个新的不可变 index 顶点
- 记忆脑通过 `sync_heads` 读到最新一致状态
