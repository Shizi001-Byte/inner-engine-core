# 任务类型: eng

基于【已有认知锚定】与【避坑提醒】，直接推演并设计「设计引擎产出的自动归档系统」。我们将严格贯彻**“先校准锚点再优化链路”**原则，运用**“精气神三元迁移框架”**（神/脑-决策、气-链路、精-执行）构建“决策串行、执行并发”的架构，彻底解决L4成品类型断流与后处理阻塞问题。

以下是「设计引擎产出的自动归档系统」的架构推演与落地方案：

### 一、 系统三元框架映射与核心机制

自动归档系统的核心任务是：任务自动分类、打标签、存入对应目录。系统分为三层映射：

*   **神（决策层 / 主线程 / 串行）：负责锚点校准与类型闭环**
    *   **职责：** 串行接收执行层返回的结果，强制校准L4成品的类型锚点，确保SOP、Code、Checklist三种类型的完整性，不完整则打回重试或降级处理。处理完成后，串行执行目录分配与归档指令下发。
*   **气（链路层 / 状态机 / 队列）：防断流与流转控制**
    *   **职责：** 连接并发执行层与串行决策层。通过高吞吐消息队列（如Disruptor或BlockingQueue）暂存并发产出的结果，确保主线程串行后处理时不会因为某个子任务耗时过长而“断流”。
*   **精（执行层 / 工作线程 / 并发）：标签生成与特征提取**
    *   **职责：** 多线程并发调用大模型API，执行文本摘要提取、标签生成、分类匹配等耗时操作。

---

### 二、 自动归档系统执行流与防坑设计

#### 1. 阶段一：并发执行层（精）—— 大模型API调用与标签生成
设计引擎产出原始内容后，立即拆分为多个独立的元数据处理任务（如：提取业务域标签、生成内容摘要、匹配L4类型特征），投入线程池并发执行。

*   **【避坑：API调用超时】**
    *   **预设合理Timeout：** 在线程池发起Callable任务时，严格根据模型类型设定超时时间。针对B模型turbo设定硬超时**300秒**，针对A模型设定硬超时**600秒**。
    *   **超时熔断机制：** 一旦超时，该并发任务立即返回`TimeoutFallback`标记，丢入队列，绝不阻塞线程池或卡死后处理流程。

#### 2. 阶段二：链路流转层（气）—— 状态机防断流
并发任务完成后，结果统一写入`ArchivePendingQueue`。

*   **【防主线程串行后处理断流】**
    *   **异步解耦：** 主线程不直接等待并发任务，而是以固定速率（或基于事件驱动）从Queue中拉取已就绪的归档包。
    *   **状态隔离：** 每个归档包带有全局唯一的`TaskID`和`Status`（READY/INCOMPLETE/FAILED）。即使某个L4成品的某个并发标签任务失败，主线程仍能处理其他READY状态的任务，避免全局停滞。

#### 3. 阶段三：串行决策层（神/脑）—— 锚点校准、类型闭环与归档
主线程串行消费Queue中的结果，执行以下决策动作：

*   **【先校准锚点：解决L4成品转化仅sop类型的问题】**
    *   **类型闭环校验：** 主线程获取到标签结果后，**必须**强制校验该产出物的L4类型锚点是否完整。若类型为SOP，直接放行；若判定为Code或Checklist，但特征提取不全（如Code缺少运行环境标签，Checklist缺少校验步骤），则触发“类型未实现”异常。
    *   **纠正机制：** 对于未实现的Code/Checklist，主线程串行将其降级为SOP类型，或打上`TODO_L4_TYPE_INCOMPLETE`标签暂存于临时目录，确保归档系统的类型闭环与数据一致性。
*   **【避坑：配置修改后未生效】**
    *   **配置热加载与校验点同步：** 归档目录规则（如SOP存入`/docs/sop/`，Code存入`/repo/code/`）若发生修改，主线程在读取归档路径配置时，必须强制走统一的`ConfigCenter.getConfig()`接口。
    *   **修改即验证：** 新增或修改归档目录配置后，在主线程串行流程中加入`assertConfigValid()`断点，确保配置在第一个归档任务下发前立即生效，路径读取点与配置点绝对同步。

### 三、 归档系统主线程伪代码逻辑推演

```java
// ==================== 精：并发执行层 (工作线程) ====================
ExecutorService executor = Executors.newFixedThreadPool(10);
List<Future<ArchiveMeta>> futures = new ArrayList<>();

for (DesignArtifact artifact : designEngineOutputs) {
    futures.add(executor.submit(() -> {
        // 1. 调用大模型打标签 (严格遵循Timeout避坑规则)
        // B模型turbo用300秒，A模型用600秒
        int timeout = artifact.getModelType() == ModelType.TURBO ? 300 : 600;
        ArchiveMeta meta = callLLMWithTimeout(artifact, timeout); 
        
        // 2. 提取L4类型特征 (SOP / Code / Checklist)
        meta.setL4Type(extractL4Type(meta.getSummary()));
        return meta;
    }));
}

// 将结果投入队列 (气：链路层防断流)
for (Future<ArchiveMeta> future : futures) {
    try {
        ArchiveMeta meta = future.get(); // 可设置整体等待上限
        pendingQueue.offer(meta);
    } catch (Exception e) {
        pendingQueue.offer(new ArchiveMeta(STATUS.FAILED)); // 保证不断流
    }
}

// ==================== 神/脑：串行决策层 (主线程) ====================
while (true) {
    ArchiveMeta meta = pendingQueue.poll();
    if (meta == null) continue;

    // 步骤1：先校准锚点 —— 强制校验L4类型闭环
    if (meta.getL4Type() != L4Type.SOP) {
        // 处理 code/checklist 未实现或提取异常的问题
        if (!isL4TypeComplete(meta)) {
            log.warn("L4类型未实现完整闭环，降级处理: {}", meta.getId());
            meta.setL4Type(L4Type.SOP); // 降级为SOP保证流转
            meta.addTag("DOWNGRADED_L4_INCOMPLETE");
        }
    }

    // 步骤2：配置同步与校验 (避坑：配置修改未生效)
    // 必须实时读取，且修改后立即在当前串行点验证
    ArchiveConfig config = ConfigCenter.getLatestConfig(); 
    String targetDir = config.getDirectoryByType(meta.getL4Type());
    assertDirectoryValid(targetDir); // 立即验证配置生效

    // 步骤3：执行归档动作
    archiveToFileSystem(meta, targetDir);
    log.info("归档完成: {} -> 类型: {} -> 目录: {}", meta.getId(), meta.getL4Type(), targetDir);
}
```

### 四、 核心总结
该自动归档系统通过**“决策串行（主线程把控L4类型闭环与配置生效）、执行并发（线程池调模型打标签）”**的分层设计，将大模型调用的不确定性（超时风险）隔离在执行层，通过链路层队列防断流，最终确保主线程能够100%串行、稳定地完成“校准锚点-校验类型-读取配置-目录归档”的闭环动作。从根本上杜绝了类型转化单一、配置未生效及后处理断流的问题。
