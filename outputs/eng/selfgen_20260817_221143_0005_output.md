# 任务类型: eng

针对V7.5方舟效能引擎在“多线程API调用后串行后处理”场景下产生的推演状态一致性问题，其核心竞态条件在于：**并发API产生的副作用（状态变更指令）在进入串行后处理队列时，由于缺乏全序关系保障，导致指令交错或状态读写不一致。**

为了彻底解决这一问题，同时兼顾V75引擎的“效能”特性，以下给出基于**“意图分离 + 命令模式 + 双重缓冲”**的完整锁机制与架构方案。

---

### 一、 竞态条件根因分析

1. **读写撕裂**：多线程API同时读写全局推演状态，导致后处理引擎读取到半更新的状态。
2. **指令交错**：API A和API B本应按顺序执行，但在多线程下其内部产生的多个子状态变更指令在入队时发生交叉。
3. **可见性延迟**：多线程API提交状态修改后，串行后处理线程未能及时观测到内存可见性，导致基于旧状态进行推演。

---

### 二、 完整锁机制方案设计

为了避免全局大锁导致引擎效能下降，方案采用**三级锁机制**，将“API调用”与“状态应用”解耦。

#### 1. 架构设计：Command Queue + Double Buffering
* **API层**：多线程API不直接修改推演状态，而是生成不可变的状态变更指令。
* **队列层**：使用无锁队列或多生产者锁，将指令安全送入串行队列。
* **后处理层**：串行线程从队列拉取指令，应用到状态缓冲区。采用Front/Back双缓冲机制，实现读写分离。

#### 2. 三级锁机制明细

| 锁级别 | 锁类型 | 保护对象 | 适用场景 | 目的 |
| :--- | :--- | :--- | :--- | :--- |
| **L1 锁** | 互斥锁 | 指令入队操作| 多线程API提交变更指令 | 保证指令入队的原子性和全序性 |
| **L2 锁** | 读写锁 | 状态缓冲区指针 | 后处理线程交换Buffer时 | 允许多读单写，极度降低读锁竞争 |
| **L3 锁** | 自旋锁| 线程局部状态缓存 | 极高频的只读API查询 | 减少跨核缓存一致性总线流量 |

---

### 三、 方案落地伪代码与锁实现

#### 1. 数据结构与锁定义

```cpp
// 1. 状态变更指令
struct StateMutationCommand {
    uint64_t api_seq;         // API调用时序号
    EntityID target;          // 作用实体
    StateDelta delta;         // 不可变的状态增量
};

// 2. 双缓冲状态区
struct StateBuffer {
    GameState current_state;  // 用于对外提供查询
    GameState next_state;     // 用于串行后处理写入
};

class ArkEngineV75 {
private:
    // L1: 指令队列锁 (也可以使用成熟的无锁MPMC队列替代)
    std::mutex queue_mutex_;
    std::vector<StateMutationCommand> command_queue_;
    
    // L2: 状态指针读写锁
    std::shared_mutex buffer_rw_lock_;
    StateBuffer* front_buffer_; // 对外读
    StateBuffer* back_buffer_;  // 对内写
    
    // L3: 自旋锁 (用于高频轻量级状态查询)
    std::atomic<bool> tick_spinlock_{false}; 

public:
    // 多线程API调用入口
    void CallApiThreadSafe(const ApiRequest& req);
    
    // 串行后处理主循环
    void PostProcessTick();
};
```

#### 2. 多线程API调用处理 (L1锁)

API线程不修改状态，仅生成不可变的`StateMutationCommand`并加锁入队。为了减少锁竞争，可以使用局部缓冲+批量入队。

```cpp
void ArkEngineV75::CallApiThreadSafe(const ApiRequest& req) {
    // 1. 解析API，生成不可变的状态增量 (无需加锁)
    StateMutationCommand cmd;
    cmd.api_seq = GlobalSeqGenerator::next();
    cmd.target = req.target;
    cmd.delta = CalculateDelta(req); // 纯函数计算，无副作用

    // 2. 加L1锁，安全入队
    {
        std::lock_guard<std::mutex> lock(queue_mutex_);
        command_queue_.push_back(cmd);
    }
    
    // 3. 唤醒后处理线程
    process_semaphore_.release();
}
```

#### 3. 串行后处理引擎处理 (L2锁)

后处理线程是**唯一的写者**，它拥有`back_buffer_`的独占写权，无需加锁。处理完一个Tick后，进行指针交换。

```cpp
void ArkEngineV75::PostProcessTick() {
    std::vector<StateMutationCommand> local_commands;
    
    // 1. 加L1锁，批量取出指令并清空队列
    {
        std::lock_guard<std::mutex> lock(queue_mutex_);
        local_commands.swap(command_queue_);
    }

    // 2. 按序串行应用指令到 back_buffer_ (无需加L1锁，因为是单线程写)
    // 为了保证逻辑全序，可按 cmd.api_seq 排序
    std::sort(local_commands.begin(), local_commands.end(), 
              [](const auto& a, const auto& b){ return a.api_seq < b.api_seq; });

    for (const auto& cmd : local_commands) {
        ApplyMutationToBuffer(back_buffer_, cmd);
    }
    
    // 3. 推演演化逻辑 (物理、AI等串行逻辑)
    EvolveState(back_buffer_);

    // 4. 加L2写锁，交换双缓冲指针
    {
        std::unique_lock<std::shared_mutex> lock(buffer_rw_lock_);
        std::swap(front_buffer_, back_buffer_);
    }
}
```

#### 4. 高频只读API查询 (L3锁 / L2读锁)

外部系统查询推演状态时，获取L2读锁。如果读操作极高频且耗时极短，可降级使用L3自旋锁避免线程挂起开销。

```cpp
GameState ArkEngineV75::GetEntityState(EntityID id) {
    // 加L2读锁，允许多个查询线程并发读
    std::shared_lock<std::shared_mutex> lock(buffer_rw_lock_);
    return front_buffer_->current_state.GetEntity(id);
}
```

### 四、 死锁防范与性能优化策略

为了保障V7.5方舟引擎在极端并发下不崩溃、不卡死，需遵循以下原则：

1. **锁顺序严格定级**：
   任何线程获取锁的顺序必须是 `L1 -> L2 -> L3`。绝对不允许在持有L2锁的情况下去获取L1锁。
   
2. **临界区零阻塞原则**：
   * 在L1锁（队列锁）内部，严禁执行磁盘I/O、网络RPC或复杂的逻辑计算，只做`push_back`或`swap`操作。
   * API计算`CalculateDelta`必须在锁外完成。

3. **避免锁饥饿**：
   如果串行后处理Tick过长，导致`command_queue_`堆积，API线程在L1锁上竞争加剧。
   * **优化**：API端引入**Thread-Local Batch（线程局部批次缓存）**，API先写入本地无锁队列，积攒满32个或超过5ms后，一次性批量获取L1锁提交入队。

4. **防止后处理线程饿死**：
   使用带有超时的信号量（`try_acquire_for`），若后处理线程长时间未等到指令，应主动触发一次空Tick以交换缓冲，刷新对外可见性状态。

---

### 五、 方案总结

此完整锁机制方案通过**“多线程生成意图 + 单线程演化状态”**的架构，将多线程并发问题降维为简单的生产者-消费者模型。

* **彻底消除状态撕裂**：对外状态`front_buffer_`始终是完整的、一致的Tick快照。
* **消除指令交错竞态**：通过L1队列锁与单调递增`api_seq`，保证串行后处理的全序性。
* **极致效能**：读写分离避免了读写锁互斥，批量入队避免了多线程队列锁自旋空耗，完全契合V7.5方舟效能引擎的高吞吐、低延迟诉求。
