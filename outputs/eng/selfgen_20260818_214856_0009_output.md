# 任务类型: eng

基于【已有认知锚定】与【避坑提醒】，在推演Supabase记忆脑的增量同步方案时，我们严格贯彻**“先校准锚点再优化链路”**原则，运用**精气神三元迁移框架**进行推演。

当前同步链路断流的本质在于：“精”（底层实体/锚点）的文件状态与类型定义未闭环，导致“气”（增量同步链路）在多线程并发检测与主线程串行写入时发生冲突或资源错配。为避免“在错误的锚点上优化链路”，推演方案如下：

### 修改点 A：校准同步状态锚点（精 - 底层实体定义）

在推演增量同步前，必须先校准本地与Supabase双端的锚点字段，确保枚举完整性与读取点一致性（防范避坑提醒1：配置修改未生效）。

1. **类型枚举闭环**：`file_type` 锚点必须覆盖 `sop`、`code`、`checklist`，确保L4成品转化链路不再仅限sop类型。
2. **同步状态锚点**：新增/校准 `sync_status` 枚举（`UNSYNCED`, `SYNCING`, `SYNCED`, `CONFLICT`）。
3. **版本与哈希锚点**：引入 `content_hash`（MD5/SHA256，用于增量检测）与 `version`（整数递增，用于冲突检测）。
4. **立即验证**：锚点修改后，立刻在本地读取点与Supabase查询点验证字段映射生效。

---

### 增量同步链路推演（气 - 链路流转设计）

基于校准后的锚点，推演“检测变化 -> 增量同步 -> 冲突处理”的链路流转。

#### 1. 本地文件变化检测（多线程并发轮询）
*   **机制**：采用文件系统Watcher（如Watchdog）或定时多线程哈希计算任务。
*   **流程**：
    *   线程池并发读取本地文件，计算 `content_hash`。
    *   与本地SQLite/状态文件中的历史 `content_hash` 对比。
    *   若不一致，标记该文件 `sync_status = UNSYNCED`，推入待同步队列。
*   **避坑防范（超时处理）**：若文件变更触发了L4成品转化（需调用大模型API），该任务派发至独立线程。必须根据模型类型预设timeout：**B模型turbo用300秒，A模型用600秒**，防止线程被阻塞导致检测链路假死。

#### 2. 只同步变更部分（主线程串行后处理与Upsert）
*   **机制**：主线程从待同步队列消费，仅提取 `UNSYNCED` 的文件数据。
*   **流程**：
    *   主线程组装增量Payload（仅包含变更的文件内容、新的hash、版本号）。
    *   调用Supabase的 `upsert` 接口，带上 `version` 作为乐观锁条件：
        `UPDATE memory_brain SET content = $1, hash = $2, version = version + 1 WHERE id = $3 AND version = $4`
    *   同步成功后，本地 `sync_status` 置为 `SYNCED`。

#### 3. 废稿检测与L4转化（坑库预警防范）
*   **场景**：文件变更触发L4成品转化，生成 `code` 或 `checklist` 类型，需调用大模型。
*   **避坑执行**：在主线程串行后处理的L4转化质量检测环节，必须根据模型类型分发检测规则。**B模型(turbo)跳过reasoning占比检测**，防止其70-82%的reasoning特性被误杀导致无限重试，进而引发API超时与同步链路断流。

---

### 冲突处理机制（神 - 业务自洽与闭环）

当本地与Supabase的 `version` 不匹配时，触发冲突状态（`CONFLICT`）。

1. **冲突检测点**：Supabase的upsert返回行数为0（说明云端version已被其他端修改，大于本地提交的version）。
2. **处理策略（三选一，根据业务锚点决定）**：
    *   **云端为准**：拉取云端最新数据，覆盖本地变更（适用于只读客户端或弱权限端）。
    *   **本地为准**：强制拉取云端数据并合并本地变更，基于云端最新version再次提交。
    *   **人工介入/双版本留存**：将本地变更存入 `conflict_branch` 表，标记 `sync_status = CONFLICT`，等待业务层在UI上提示用户手动解决（推荐用于code/checklist等高价值L4成品）。

### 总结
通过先校准 `file_type`（补全code/checklist）、`sync_status`、`version` 与 `hash` 锚点，我们防范了配置不生效的风险；在多线程检测与主线程串行同步的链路中，通过模型专属超时设置与B模型废稿规则豁免，避免了链路假死与误杀。最终实现Supabase记忆脑的高效、无损增量同步。
