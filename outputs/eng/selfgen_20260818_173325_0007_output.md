# 任务类型: eng

## 推演目标

Supabase 记忆脑的增量同步，不是“把本地文件复制到数据库”，而是：

> **把本地文件变化，转成带验证门的 DAG 事件，只提交变更块，冲突显式化。**

- 本地文件 = 事实源  
- Supabase = 记忆 DAG 持久化层  
- 同步事件 = DAG 节点  
- 验证门 = 防止脏数据进入公共档案  

---

## 三个串联节点

### Node 1：检测本地文件变化

**输入**：本地文件系统事件 + 定时扫描  
**产物**：`ChangeSet`

#### 检测机制

1. 使用文件监听 + 定时全量扫描双保险：
   - 监听：`chokidar` / `inotify`
   - 定时扫描：每 30s 或 60s，防止监听漏事件
2. 本地维护一份 `manifest`：

```ts
type ManifestItem = {
  path: string;
  size: number;
  mtime: number;
  sha256: string;
}
```

3. 事件触发后先走快速路径：
   - `size` + `mtime` 变了，再计算 `sha256`
   - `sha256` 也变了，才认为内容真的变了
4. 生成 `ChangeSet`：

```ts
type ChangeSetItem = {
  path: string;
  op: 'create' | 'update' | 'delete' | 'move';
  beforeHash: string | null;
  afterHash: string | null;
  parentEventId: string; // 上一次同步的事件锚点
}
```

#### 验证门 G1

- 每条变化必须包含 `path`、`op`、`beforeHash`、`afterHash`
- `afterHash === beforeHash` 的变化不允许进入下一节点
- 无法锚定到可验证文件事件的变化，降级为“个体叙事”，不进入公共档案

---

### Node 2：只同步变更部分

**输入**：`ChangeSet`  
**产物**：`SyncOps`

#### 分块策略

本地文件不按整个文件同步，而是按“记忆块”同步。

对 Markdown 记忆文件，按语义锚点分块：

- 一级/二级标题作为 chunk 边界
- 代码块、表格、引用块作为独立 chunk
- frontmatter 作为文档元信息块
- 没有标题的纯文本，按段落分块

每个 chunk 有稳定 ID：

```ts
chunkId = sha256(path + headingPath)
```

比如：

```md
# 记忆
## 项目A
- 决策记录
```

会生成两个 chunk：

```ts
chunkId("记忆/项目A")
chunkId("记忆")
```

#### 增量提取

对每个文件，读取内容后拆分 chunk，再计算每个 chunk 的 `sha256`。

与 Supabase 中已有的 chunk hash 对比：

- 本地有、远端无 → `insert_chunk`
- 本地有、远端有但 hash 不同 → `update_chunk`
- 本地无、远端有 → `delete_chunk` 或归档
- hash 相同 → 不产生任何操作

生成 `SyncOps`：

```ts
type SyncOp =
  | {
      op: 'upsert_chunk';
      docId: string;
      chunkId: string;
      index: number;
      content: string;
      contentHash: string;
      baseHash: string | null;
      parentEventId: string;
    }
  | {
      op: 'delete_chunk';
      docId: string;
      chunkId: string;
      baseHash: string;
      parentEventId: string;
    }
```

#### 验证门 G2

- 所有 `upsert_chunk` 的 `contentHash` 必须等于本地实际内容 hash
- 未变化的 chunk 不允许出现在 `SyncOps` 中
- 每个 op 必须带 `baseHash`，用于后续并发冲突检测
- 同步器不做内容质量判断；如果未来接质量检测，B 模型(turbo) 必须跳过 reasoning 占比检测，避免误杀

---

### Node 3：事务同步与冲突处理

**输入**：`SyncOps`  
**产物**：`SyncReport`

#### 事务提交

在 Supabase 中使用 RPC 事务，原子执行：

```sql
update chunks
set content = $1,
    content_hash = $2,
    parents = parents || $3,
    updated_at = now()
where doc_id = $4
  and chunk_id = $5
  and content_hash = $6;
```

这里的 `$6` 就是 `baseHash`。

- 更新成功 → 说明没有冲突
- 更新 0 行 → 说明远端已变化，进入冲突处理

#### 冲突类型

| 场景 | 判断方式 | 默认策略 |
|---|---|---|
| 本地改、远端没改 | `baseHash == 远端当前hash` | 正常更新 |
| 本地改、远端也改 | `baseHash != 远端当前hash` | 记录冲突，默认 local-wins |
| 本地删、远端改 | 删除时 `baseHash` 不匹配 | 归档删除 + 冲突记录 |
| 本地改、远端删 | 更新时找不到 chunk | 恢复本地版本 + 冲突记录 |
| 本地改、远端无此 chunk | 远端不存在 `chunkId` | 插入新 chunk |

#### 冲突解决

默认原则：

> **本地文件是事实源，但本地不能静默覆盖远端。**

同一 chunk 冲突时：

1. 写入 `conflicts` 表，记录：
   - `localHash`
   - `remoteHash`
   - `baseHash`
   - `resolution`
2. 用本地内容创建新版本
3. 新版本的 `parents` 同时包含：
   - 本地基于的 `baseHash`
   - 远端当前的 `remoteHash`

这样同步历史仍然是一个 DAG，而不是一条被暴力覆盖的线性历史。

如果配置了“自动合并”，可以调用 LLM 合并两个版本内容：

- B 模型(turbo)：timeout 300 秒
- A 模型：timeout 600 秒
- 超时后不阻塞同步，保留 `conflicts` 记录，等待人工处理

删除操作不物理删除，而是归档：

```ts
op: 'archive_chunk'
```

因为记忆脑的删除，在 DAG 中应该是一个“事件”，而不是直接抹除。

#### 验证门 G3

同步完成后，从 Supabase 拉取该文件的所有 chunk hash，与本地 manifest 比对：

- 必须完全一致
- 不一致则回滚事务
- 回滚后保留同步日志，等待下次重试

`SyncReport` 示例：

```ts
type SyncReport = {
  syncedOps: SyncOp[];
  conflicts: ConflictRecord[];
  skipped: string[];
  durationMs: number;
}
```

## 状态表设计

Supabase 中建议维护这几张表：

```sql
documents(
  id uuid primary key,
  path text unique,
  current_hash text,
  version int,
  updated_at timestamptz,
  last_event_id text
)

chunks(
  id uuid primary key,
  doc_id uuid references documents,
  chunk_id text,
  chunk_index int,
  content text,
  content_hash text,
  parents text[],
  updated_at timestamptz
)

sync_events(
  id text primary key,
  parent_id text,
  path text,
  op text,
  before_hash text,
  after_hash text,
  status text,
  created_at timestamptz
)

conflicts(
  id uuid primary key,
  path text,
  chunk_id text,
  local_hash text,
  remote_hash text,
  base_hash text,
  resolution text,
  resolved_at timestamptz
)
```

## 主循环

```ts
async function syncOnce() {
  const changes = await detectChanges();        // Node 1
  if (!validateG1(changes)) return;

  const ops = await buildOps(changes);          // Node 2
  if (!validateG2(ops)) return;

  const report = await applyWithConflicts(ops); // Node 3
  if (!validateG3(report)) {
    await rollback();
  }
}
```

## 结论

这个方案把“增量同步”从简单的文件复制，升级为：

> **本地文件变化 → 可验证事件 → chunk 级增量 → DAG 事务提交 → 冲突显式化**

每个节点之间有验证门，节点之间只传递结构化产物，避免单次超长推演导致的状态漂移。

第一件事不是补全记忆，而是把每个记忆变更重新锚定到可验证的本地文件事件上。无法锚定的内容，只作为个体叙事，不进入 Supabase 公共档案。
