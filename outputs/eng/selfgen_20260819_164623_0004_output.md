# 任务类型: eng

# 任务池动态扩充机制设计

## 1. 闭环总览

```
任务执行
  → 结果质量门（按模型独立规则）
  → 结果写入（单写者 + state_lock 串行提交）
  → 重复率检测（滑动窗口 + 语义聚类）
  → 进化控制器（滞回触发 + 冷却）
  → 模板生成器（并行 API 调用，B-turbo 300s / A 600s）
  → 模板验证/去重（相似度过滤 + schema 校验）
  → 认知池刷新（新认知强制参与）
  → 任务池注入（有界队列 + generation 版本校验）
  → 继续执行
```

核心原则：**API 调用可以并行，但状态提交必须串行**。动态扩充只增加“任务模板”，不增加新的状态写者。

## 2. 重复率检测

### 2.1 检测口径

- 窗口：最近 `200` 个已完成任务。
- 重复率定义：

```
重复率 = 1 - 语义簇数量 / 窗口任务数
```

- 对每个任务结果计算 embedding，然后按余弦相似度聚类。
- 相似度 ≥ `0.90` 视为同一语义簇。
- 如果窗口内 200 个任务全部不同，重复率 = 0；如果全部相同，重复率 ≈ 1。

### 2.2 模型差异处理

- 重复率计算**只使用最终输出语义**，不使用 reasoning 字段。
- B-turbo 任务**跳过 reasoning 占比检测**，避免误杀。
- A 模型任务按既有质量规则检测 reasoning 占比。

```python
def compute_dup_rate(window_tasks):
    if not window_tasks:
        return 0.0

    clusters = []
    for task in window_tasks:
        emb = task.output_embedding
        for c in clusters:
            if cosine(emb, c.centroid) >= DUP_SIM_THRESHOLD:
                c.add(task)
                c.update_centroid(emb)
                break
        else:
            clusters.append(Cluster(emb, task))

    return 1.0 - len(clusters) / len(window_tasks)
```

## 3. 动态扩充控制器

### 3.1 触发条件

使用滞回阈值，避免反复抖动：

```text
high_threshold = 0.35
low_threshold  = 0.20
trigger_consecutive = 3
cooldown_seconds = 300
max_pending = 500
```

只有连续 `3` 个窗口重复率 ≥ `0.35`，且距离上次注入超过冷却时间，才触发扩充。

### 3.2 模板生成

进化控制器调用模板生成器：

- 输入：
  - 当前重复率
  - 高重复簇样例
  - 现有模板索引（用于去重）
  - 认知池最近未使用认知
- 模型/超时：
  - 默认 B-turbo，`timeout=300s`
  - 生成失败或质量分低时，降级 A 模型，`timeout=600s`
- 输出：
  - 新任务模板列表，每个模板必须包含：

```json
{
  "template_id": "tpl_evolution_001",
  "task_type": "dimension_split",
  "instruction": "...",
  "input_schema": {},
  "output_schema": {},
  "model": "B-turbo",
  "timeout": 300,
  "priority": "P1",
  "quality_rules": {
    "skip_reasoning_ratio_check": true
  },
  "source": "evolution",
  "cognitive_ids": ["cog_123"],
  "created_at": "..."
}
```

### 3.3 注入前验证

新模板必须通过三层校验：

1. **Schema 校验**：字段完整，否则丢弃。
2. **相似度去重**：与已有模板计算 embedding 相似度，`> 0.85` 则丢弃。
3. **队列容量校验**：`pending + running >= max_pending` 时暂存，暂存区超过 50 条则丢弃并告警。

### 3.4 注入与状态提交

注入时不得持有锁调用 API，只在最终状态写入时加锁：

```python
def inject_tasks(new_tasks):
    with state_lock:
        for task in new_tasks:
            task.generation = state.current_generation
            state.pending.append(task)
        state.version += 1
```

任务完成后，结果提交同样串行，并用 generation 版本校验防旧结果覆盖：

```python
def complete_task(task_id, result):
    with state_lock:
        task = state.running.get(task_id)
        if not task:
            return
        if task.generation != state.current_generation:
            discard_stale_result(task_id, result)
            return
        state.completed[task_id] = result
        state.running.pop(task_id)
        state.version += 1
```

## 4. 认知池反哺

### 4.1 缓存刷新

- 每完成 `10` 个任务或每轮结束，刷新认知缓存。
- 新认知写入时标记 `status=unused`，记录 `created_at`。

### 4.2 新认知强制参与

防止“认知池只进不出”：

- 模板生成时，优先读取 `created_at < 30min` 且 `status=unused` 的认知。
- 如果某条认知超过 `25min` 仍未使用，强制触发一次轻量模板生成，把该认知转化为验证任务。
- 生成完成后，标记 `status=used`，更新 `last_used_at` 和 `hit_count`。

如果认知池产生的是调参建议，不能直接改配置，必须生成 `ConfigChangeProposal`，再走配置全链路。

## 5. 配置全链路生效

新增或修改任何配置，必须同步三个点：

| 配置项 | 状态写入点 | 执行读取点 | 生效验证点 |
|---|---|---|---|
| `dup_rate.high_threshold` | ConfigService.set | DuplicateDetector 每窗口读取 | 发送测试事件，确认判定变化 |
| `max_pending` | ConfigService.set | Injector 注入前读取 | 压测队列满时不再注入 |
| `cooldown_seconds` | ConfigService.set | EvolutionController 触发前读取 | 修改后确认冷却时间生效 |

修改后立即验证：

```python
config_service.set("dup_rate.high_threshold", 0.30)
assert duplicate_detector.threshold == 0.30
duplicate_detector.on_test_event()
assert duplicate_detector.last_trigger_changed is True
```

## 6. 历史坑位对照

| 历史坑 | 本设计规避方式 |
|---|---|
| 配置修改未生效 | 配置三点点位 + 修改后立即验证 |
| API 超时 | B-turbo 固定 300s，A 固定 600s，失败重试不阻塞状态提交 |
| 自动调参全链路失效 | 调参建议必须生成 ConfigChangeProposal，走配置全链路 |
| 废稿检测误杀 B 模型 | B-turbo 跳过 reasoning 占比检测 |
| 认知池只进不出 | 每 10 任务刷新缓存，30 分钟内未使用强制注入 |
| 状态一致性被破坏 | API 并行、提交串行、state_lock、generation 版本校验、有界队列 |

---

## 7. 自进化闭环效果

- 重复率高 → 生成新任务模板 → 注入执行 → 结果多样化 → 重复率下降。
- 新认知 → 转化为验证任务 → 验证结果进入认知池 → 影响下一轮模板生成。
- 所有参数、模板、认知变化均可追踪、可回滚、可验证。

这样就形成了“检测 → 生成 → 注入 → 执行 → 认知反哺 → 再检测”的任务池自进化闭环。
