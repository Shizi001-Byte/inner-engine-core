# 任务类型: eng

# Supabase 记忆脑：增量同步方案推演

## 0. 从已知锚点推出的设计约束

- **同步粒度是块，不是整个文件**：文件只是“块的有序索引”，同步时只上传缺失/变化的块。
- **归档对象本体是 DAG 顶点，不是进程实例**：远端不存“同步任务”记录，而是存不可变的 `block / index / tombstone` 顶点。
- **流程结构是三个串联 DAG 节点，每节点三转，共九转**：`Detect -> Diff -> Commit`，每节点内部固定三步。
- **核心目标是事实边界 + 校验机制**：每个块是一个事实单元；每次提交前校验哈希、结构、来源。
- **超时熔断是负熵输入机制的保险丝**：同步是为了给记忆脑增加秩序，超时/冲突时必须停止写入，不能把混乱固化。

---

## 1. 总体架构

```
本地文件系统
   │
   ▼
Detect 节点（D1-D3）
   │
   ▼
Diff 节点（B1-B3）
   │
   ▼
Commit 节点（C1-C3）
   │
   ▼
Supabase 归档 DAG
```

执行流固定为三节点九转：

| 节点 | 转 | 动作 | 产物 |
|---|---|---|---|
| Detect | D1 | 扫描本地文件 path/size/mtime | 候选文件集 |
| Detect | D2 | 计算文件哈希，对比本地 manifest | 变更文件集 |
| Detect | D3 | 对变更文件做块切分，计算块哈希 | 本地块序列 |
| Diff | B1 | 读取本地 cursor 与远端 current vertex | base / remote 状态 |
| Diff | B2 | 做块集合差 + 文件索引 diff | 新增块、索引变更 |
| Diff | B3 | 生成同步计划或冲突记录 | SyncPlan / Conflict |
| Commit | C1 | 校验事实边界：哈希、结构、模型规则 | 合法载荷 |
| Commit | C2 | 事务写入 Supabase DAG | 新 DAG 顶点 + files 指针 |
| Commit | C3 | 读回确认，更新 cursor | 同步完成 |

## 2. Supabase 数据模型

核心表：

```sql
-- DAG 顶点：block / index / tombstone
create table dag_vertices (
  id uuid primary key,
  type text not null check (type in ('block','index','tombstone')),
  hash text not null,
  payload jsonb not null,
  meta jsonb not null default '{}',
  created_at timestamptz not null default now(),
  unique (type, hash)
);

-- DAG 边：不可变血缘
create table dag_edges (
  parent_id uuid not null references dag_vertices(id),
  child_id uuid not null references dag_vertices(id),
  primary key (parent_id, child_id)
);

-- 文件当前状态
create table files (
  path text primary key,
  current_index_id uuid references dag_vertices(id),
  status text not null default 'active',
  updated_at timestamptz not null default now()
);

-- 同步游标：只记录进度，不作为归档对象
create table sync_cursors (
  path text primary key,
  local_manifest_hash text not null,
  remote_index_id uuid references dag_vertices(id),
  last_sync_at timestamptz not null default now()
);

-- 冲突记录
create table conflicts (
  id uuid primary key default gen_random_uuid(),
  path text not null,
  base_index_id uuid references dag_vertices(id),
  local_index_id uuid references dag_vertices(id),
  remote_index_id uuid references dag_vertices(id),
  status text not null default 'pending',
  resolution_index_id uuid references dag_vertices(id),
  created_at timestamptz not null default now()
);
```

**归档对象本体是 DAG 顶点，不是进程实例**：  
每次同步成功产生的是新的 `block` 或 `index` 顶点；同步进程本身不写入归档。

## 3. 本地变化检测

### 3.1 事件驱动 + 定时兜底

- 使用 `chokidar` / `inotify` 监听本地目录。
- 同时每 60 秒做一次全量扫描，防止 watcher 漏事件。

### 3.2 manifest 机制

本地维护一份 manifest：

```json
{
  "version": 1,
  "files": {
    "docs/abc.md": {
      "size": 12345,
      "mtime": 1710000000,
      "file_hash": "blake3:...",
      "blocks": ["blake3:...", "blake3:..."]
    }
  }
}
```

检测逻辑：

1. 文件事件触发后，先 stat 文件。
2. 计算文件级哈希。
3. 与 manifest 中哈希一致 → 忽略。
4. 不一致 → 标记为变更文件。
5. 对变更文件做块切分。

### 3.3 块切分策略

块边界必须尽量稳定，避免小改动导致整个文件所有块都变化。

| 文件类型 | 切分方式 |
|---|---|
| Markdown | 按标题分块，每个标题区块为一个块 |
| JSONL | 每行一个块 |
| 纯文本 | 按语义段落分块，或使用 CDC 滚动哈希 |
| 其他 | 内容定义分块（CDC），平均块大小可配 |

块哈希统一使用 `BLAKE3(content)`。

## 4. 只同步变更部分

### 4.1 远端状态获取

Diff 节点 B1/B2：

```
base_remote_index = sync_cursors.remote_index_id
current_remote_index = files.current_index_id
```

从 `dag_vertices` 读取当前 index payload：

```json
{
  "path": "docs/abc.md",
  "blocks": ["blake3:blockA", "blake3:blockB", "blake3:blockC"]
}
```

### 4.2 块集合差

本地块哈希集合为 `L`，远端当前块哈希集合为 `R`：

```
new_blocks = L - R
```

只有 `new_blocks` 需要上传。

### 4.3 索引变更

如果本地块序列与远端块序列不同，则生成一个新的 `index` 顶点：

```json
{
  "path": "docs/abc.md",
  "blocks": ["blake3:blockA", "blake3:blockB_new", "blake3:blockC"]
}
```

索引顶点很小，同步成本低。

## 5. 提交节点：事务写入

Commit 节点 C2 使用 Supabase RPC 原子提交：

```sql
create or replace function sync_commit(
  p_path text,
  p_base_index_id uuid,
  p_new_blocks jsonb,
  p_new_index jsonb,
  p_new_index_hash text
) returns jsonb
language plpgsql
security definer
as $$
declare
  v_current uuid;
  v_new_index_id uuid;
begin
  select current_index_id into v_current
  from files
  where path = p_path
  for update;

  if v_current is distinct from p_base_index_id then
    return jsonb_build_object(
      'ok', false,
      'reason', 'conflict',
      'remote_index_id', v_current
    );
  end if;

  -- 插入新块
  insert into dag_vertices (id, type, hash, payload)
  select
    gen_random_uuid(),
    'block',
    b ->> 'hash',
    b
  from jsonb_array_elements(p_new_blocks) b
  on conflict (type, hash) do nothing;

  -- 插入新 index
  insert into dag_vertices (id, type, hash, payload)
  values (gen_random_uuid(), 'index', p_new_index_hash, p_new_index)
  on conflict (type, hash) do nothing;

  select id into v_new_index_id
  from dag_vertices
  where type = 'index' and hash = p_new_index_hash;

  -- DAG 边：base -> new index
  insert into dag_edges (parent_id, child_id)
  values (p_base_index_id, v_new_index_id);

  -- 更新文件指针
  update files
  set current_index_id = v_new_index_id,
      updated_at = now()
  where path = p_path;

  return jsonb_build_object('ok', true, 'index_id', v_new_index_id);
end;
$$;
```

C3 读回确认：

```
SELECT current_index_id
FROM files
WHERE path = $path;
```

确认与本地期望的 `new_index_id` 一致后，再更新 `sync_cursors`。

## 6. 冲突处理

### 6.1 冲突检测

提交时 `base_index_id` 与远端 `current_index_id` 不一致，即冲突。

### 6.2 三路合并

```
base:     [A, B, C]
local:    [A, B', C]
remote:   [A, B, C']
```

使用 diff3 对块哈希序列做合并。

- 非重叠修改 → 自动合并为 `[A, B', C']`
- 重叠修改 → 产生冲突标记，进入人工/AI 解决流程。

### 6.3 冲突解决原则

冲突解决不是“覆盖”，而是生成新的 DAG 合并顶点：

```
merged_index parents = [local_index, remote_index]
```

AI 解决时遵守事实边界：

- 不允许 AI 发明新事实。
- 只能选择已有块、重新排序已有块、或请求用户确认。
- 如果两个块是互补事实，可以同时保留。
- 如果两个块互相矛盾，必须标记为待用户决策。

## 7. 超时熔断

### 7.1 超时配置

| 场景 | 超时 |
|---|---|
| 本地文件扫描 / 哈希 | 30s |
| Supabase 查询 / 事务 | 30s |
| B 模型 turbo 调用 | 300s |
| A 模型调用 | 600s |

### 7.2 熔断规则

- 任何一转超时，不提交，不重试。
- 保留本地 manifest 和远端 DAG 原状。
- 记录 `sync_state = timeout`。
- 连续 3 次超时，打开熔断器，停止自动同步，等待人工介入。

同步是给记忆脑输入负熵；超时熔断是保险丝，防止混乱状态被写入记忆。

## 8. 模型相关避坑

### 8.1 B 模型 turbo 跳过 reasoning 占比检测

B 模型 turbo 的 reasoning 占比在 70%–82% 是正常特性，不是废稿。

因此在质量校验中：

```python
def quality_check(payload, model):
    if model == "B-turbo":
        # B 模型跳过 reasoning 占比检测
        return True

    # A 模型可以保留该规则
    if payload.reasoning_ratio > 0.82:
        return False
```

### 8.2 配置修改后必须同步修改读取点

所有配置项统一从 ConfigProvider 读取：

```python
timeout = Config.get("sync.b_model_timeout_seconds", 300)
```

修改配置后立即验证：

```python
Config.set("sync.b_model_timeout_seconds", 300)
assert Config.get("sync.b_model_timeout_seconds") == 300
```

新增配置项时，必须同步修改读取点，否则会出现“配置改了但行为没变”。

## 9. 总结

这个增量同步方案的本质是：

1. **本地文件变化检测**：watcher + manifest + 文件哈希。
2. **只同步变更部分**：块级去重，只上传新增块和新的索引顶点。
3. **冲突处理**：DAG 分支 + diff3 合并 + 人工/AI 裁决。
4. **事实边界 + 校验机制**：所有写入 DAG 的顶点都经过哈希校验和结构校验。
5. **超时熔断**：B 模型 300 秒，A 模型 600 秒，超时不写入。

同步结果不是“进程记录”，而是不可变的 DAG 顶点。  
这才是 Supabase 记忆脑该有的增量同步方式。
