# 任务类型: eng

# 自动归档系统设计（决策串行 · 执行并发）

## 1. 总体架构

```
任务提交
   │
   ▼
┌─────────────────────── 决策引擎（脑，串行） ───────────────────────┐
│  事件循环：从事件日志中读取事件，恢复任务状态，执行纯决策函数      │
│  输出：执行命令 / 新事件 / 状态流转                                │
└─────────────────────────────────────────────────────────────────────┘
   │ 命令（Command）                                      ▲ 结果事件（Event）
   ▼                                                      │
┌─────────────────────── 执行器（体，并发） ────────────────────────┐
│  Worker Pool：并发执行分类 API、打标 API、文件归档操作           │
│  不读取业务配置，不做路由判断，不推进状态机                       │
└─────────────────────────────────────────────────────────────────────┘
   │
   ▼
分类 / 打标签 / 文件移动 / 元数据写入
```

核心原则：  
**引擎只做决策，执行器只做动作。**  
所有状态变化都通过事件追加到事件日志，可重放、可校验。

---

## 2. 状态机设计

每个归档任务由引擎以显式状态机推进：

| 状态 | 触发事件 | 引擎决策 | 执行器动作 |
|---|---|---|---|
| `SUBMITTED` | 任务提交 | 固定 `config_version`，生成分类命令 | 无 |
| `CLASSIFYING` | 分类命令已发送 | 记录等待 | 调用分类 API，返回原始结果 |
| `CLASSIFIED` | 分类成功 | 解析、校验分类结果；决定打标策略 | 若需模型打标，则调用打标 API |
| `TAGGED` | 打标成功 | 根据分类/标签/目录映射计算目标路径 | 无 |
| `ROUTED` | 路由已决定 | 生成归档命令 | 移动/复制文件，写 sidecar 元数据 |
| `ARCHIVING` | 归档命令已发送 | 记录等待 | 执行文件操作 |
| `ARCHIVED` | 归档成功 | 进入终态 | 无 |
| `FAILED` | 任一步骤失败 | 决定重试 / 降级 / 人工介入 | 无 |

关键点：  
- 执行器永远不直接产生“下一步该干什么”的决策。  
- 分类 API 返回的只是原始结果；是否采用、如何归类、是否重试，全部由引擎决定。

## 3. 命令与事件示例

### 命令（引擎 → 执行器）

```json
{
  "command_id": "cmd_20250601_001",
  "task_id": "task_001",
  "type": "classify",
  "params": {
    "source": "/inbox/report.pdf",
    "model": "B_turbo"
  },
  "timeout_ms": 300000
}
```

归档命令示例：

```json
{
  "command_id": "cmd_20250601_002",
  "task_id": "task_001",
  "type": "archive_file",
  "params": {
    "src": "/inbox/report.pdf",
    "dest": "/archive/invoice/2025/06/task_001_report.pdf",
    "tags": ["invoice", "2025", "finance"]
  },
  "timeout_ms": 60000
}
```

### 事件（执行器 → 引擎）

```json
{
  "event_id": "evt_20250601_001",
  "task_id": "task_001",
  "seq": 4,
  "type": "ClassificationSucceeded",
  "data": {
    "category": "invoice",
    "confidence": 0.97,
    "raw_response": "..."
  },
  "config_version": 12,
  "created_at": "2025-06-01T10:00:04Z"
}
```

事件是事实记录，命令是待执行指令。  
重放事件日志即可恢复任务状态。

## 4. 配置管理：防止“配置修改后不生效”

### 4.1 配置必须版本化

每个任务在 `SUBMITTED` 时固定 `config_version`。  
事件中记录该版本，配置中心保留历史版本，重放时按当时版本读取。

### 4.2 引擎是唯一配置读取方

执行器禁止读取业务配置，尤其禁止读取目录映射、分类规则、标签规则。  
所有配置读取点集中在引擎决策函数中：

| 配置项 | 读取点 |
|---|---|
| 分类模型、API endpoint、timeout | 生成分类命令时 |
| 打标规则、标签字典 | 生成打标命令时 |
| 目录映射规则 | 计算目标路径时 |
| 归档并发数、staging 目录 | 生成归档命令时 |

### 4.3 配置变更后立即验证

配置发布流程：

1. 配置中心发布新版本 `config_version = 13`。
2. 引擎收到 `ConfigPublished` 事件。
3. 引擎自动执行 `smoke_test`：用样例任务走完整决策链，但不实际归档。
4. 输出 `category/tags/dest_path`，与预期比对。
5. 通过后，新任务才允许使用新配置；未通过则自动回滚到上一版本。

这样保证“新增配置必须同步修改读取点”且“修改后立即验证生效”。

## 5. API 超时与失败处理

### 5.1 超时配置

根据任务类型和模型类型预设 timeout：

```yaml
model_timeout:
  B_turbo: 300s
  A: 600s

classify:
  default_model: B_turbo
  long_doc_model: A
```

执行器发起调用时必须使用命令中的 `timeout_ms`：

- `B_turbo` 模型调用超时 300 秒；
- `A` 模型调用超时 600 秒；
- 超时后执行器返回 `ExecutionTimeout` 事件，不抛未捕获异常。

### 5.2 超时后的引擎决策

引擎收到 `ExecutionTimeout` 后，根据策略决定：

- 分类超时：可降级到规则分类，或重试一次；
- 打标超时：可跳过非关键标签，仅保留规则标签；
- 归档超时：重试一次；仍失败则进入 `FAILED`，转人工处理。

所有重试和降级都必须由引擎显式决策，不能由执行器自行重试。

## 6. 执行器并发模型

执行器使用 Worker Pool：

- 文件归档操作：线程池/协程池并发执行；
- 分类 API 调用：每个调用独立协程/线程，互不影响；
- 每个命令都带 `command_id`，执行器做幂等去重；
- 命令完成后发送结果事件，由事件队列统一回到引擎。

示例：

```yaml
executor:
  workers: 8
  queue_size: 100
  archive_staging_dir: /tmp/archive_staging
```

执行器不保存任务状态，不缓存决策结果。  
所有状态和进度都只存在于事件日志和引擎投影中。

## 7. 归档目录规则

目标路径由引擎根据分类结果和标签计算，例如：

```
<archive_root>/<category>/<primary_tag>/<yyyy>/<mm>/<task_id>_<filename>
```

示例：

```
/archive/invoice/2025/06/task_001_report.pdf
```

多个标签时，主标签用于目录路径，其余标签写入 sidecar 元数据：

```json
{
  "task_id": "task_001",
  "category": "invoice",
  "tags": ["invoice", "2025", "finance"],
  "source": "/inbox/report.pdf",
  "dest": "/archive/invoice/2025/06/task_001_report.pdf",
  "archived_at": "2025-06-01T10:01:00Z"
}
```

文件写入使用“临时文件 + 原子改名”，避免归档中断产生半成品。

## 8. 为什么这个设计不破坏“脑体分离”

- 所有路由判断、状态流转、重试策略、目录计算，都在引擎内完成；
- 执行器只是“手脚”，接收明确命令并返回结果；
- 没有把决策逻辑下沉到并发执行层，因此不会出现“隐式状态机”；
- 事件日志完整记录每次决策输入和输出，可重放、可审计。

后续如果要做性能优化，优先优化执行器的并发能力、API 调用效率、文件操作速度，而不是把决策逻辑搬到执行器。

## 9. 落地检查清单

- [ ] 新增配置项时，必须同步修改对应引擎读取点；
- [ ] 配置发布后，自动执行 smoke test；
- [ ] 每个任务固定 `config_version`，事件中记录版本；
- [ ] 执行器不读取业务配置、不做路由判断；
- [ ] 所有 API 调用带 `timeout_ms`；
- [ ] 所有命令带 `command_id`，执行器幂等；
- [ ] 所有状态变化写入事件日志，可重放。

这样即可实现一个稳定、可维护、可重放的自动归档系统。
