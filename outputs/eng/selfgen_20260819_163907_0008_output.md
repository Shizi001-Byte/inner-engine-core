# 任务类型: eng

## 结论先行

Supabase 记忆脑的增量同步，不能做成“定时全量覆盖”，而要设计成：

> **事件触发 + 块级 diff + CAS 条件更新 + 三向合并 + 写后验证**

并且同步器本身**不占用 3 路执行并发**，它作为独立后台任务运行，只在算力预算内处理变更。

同步完成的定义不是“写进了 Supabase”，而是：

> **Supabase 写入成功 + 本地/远端状态一致 + 读取点已刷新 + 验证查询通过**

---

## 1. 目标与约束

### 目标

- 本地文件变化能快速被感知；
- 只同步变更部分，不做全量扫描/全量上传；
- 多端/多任务并发修改时，不静默丢数据；
- 不突破“稳定 3 路并发”物理上限；
- 不因同步任务导致引擎空转或 API 超时。

### 约束

- 算力非零成本：能增量就增量，能事件驱动就不轮询；
- Supabase API 有超时风险：必须预设 timeout；
- 不同模型必须用独立质量规则：B 模型(turbo) 跳过 reasoning 占比检测；
- 配置/内容同步后必须立即刷新读取点，否则“看起来没生效”。

---

## 2. 总体架构

```
本地记忆目录
   │
   ├── FS Watcher 事件
   ├── 启动/周期扫描
   ├── 本地 manifest
   └── base 镜像（用于三向合并）
          │
          ▼
    同步执行器（后台，低优先级）
          │
          ▼
  Supabase
   ├── memory_files
   ├── memory_chunks
   ├── memory_tombstones
   └── RPC：sync_upsert_file / sync_delete_file
          │
          ▼
  写后验证 + 读取点刷新 + 索引/向量更新
```

同步器与 3 路 worker 分离：

- worker 负责执行任务；
- 同步器负责记忆脑数据管道；
- 只有冲突合并需要调用模型时，才向模型调度器申请槽位；
- 模型槽位不足时，不强制合并，先标记冲突，等待空闲。

## 3. 检测本地文件变化

### 3.1 三层检测机制

| 层级 | 方式 | 作用 |
|---|---|---|
| 第一层 | FS Watcher | 实时感知增删改 |
| 第二层 | 事件去抖 | 合并短时间连续写入 |
| 第三层 | hash 确认 | 避免 mtime/size 误判 |

### 3.2 本地状态文件

在记忆根目录维护：

```text
.memory-brain/
  manifest.json
  base/          # 上次同步成功的内容快照，用于冲突合并
  conflicts/     # 冲突现场备份
```

`manifest.json` 结构：

```json
{
  "files": {
    "notes/idea.md": {
      "local_hash": "abc123",
      "base_hash": "abc123",
      "base_version": 12,
      "mtime": 1710000000,
      "size": 2048,
      "status": "synced"
    }
  }
}
```

- `local_hash`：当前本地文件 hash；
- `base_hash`：上次同步成功时的内容 hash；
- `base_version`：上次同步成功时 Supabase 中的 version。

### 3.3 变化判定逻辑

```text
1. watcher 收到事件后，等待 2s 去抖；
2. 对路径做 stat + sha256；
3. 与 manifest.local_hash 比较；
4. 不同则进入 pending_changes；
5. 相同则忽略，避免误触发。
```

### 3.4 远程变化检测

- 优先使用 Supabase Realtime 订阅 `memory_files` 的 insert/update/delete；
- 如果没有 Realtime，则按 `updated_at > last_seen_at` 增量轮询；
- 轮询间隔建议 60s，避免空转。

## 4. 只同步变更部分

### 4.1 三级增量粒度

| 粒度 | 说明 |
|---|---|
| 文件级 | 只同步本地有变化的文件 |
| 块级 | 大文件只上传变化的 chunk |
| 索引级 | 只刷新变化 chunk 对应的向量/缓存 |

### 4.2 块级切分策略

- 小文件（默认 < 64KB）：整个文件作为一个 chunk；
- 大文件：使用内容定义切块（CDC），平均 chunk 大小 16KB；
- 每个 chunk 计算 `sha256`；
- 只上传 hash 变化的 chunk；
- 如果变化 chunk 比例超过 60%，则整文件替换，避免大量小请求反而更贵。

### 4.3 Supabase 表结构

```sql
create table memory_files (
  path text primary key,
  version bigint not null,
  content_hash text not null,
  updated_at timestamptz not null default now()
);

create table memory_chunks (
  path text not null,
  chunk_index int not null,
  chunk_hash text not null,
  content text not null,
  primary key (path, chunk_index)
);

create table memory_tombstones (
  path text primary key,
  deleted_at timestamptz not null default now()
);
```

### 4.4 原子写入 RPC

不能先写 chunk 再写 file，否则读取方可能读到半新半旧内容。  
用 Postgres 函数包在事务里：

```sql
create or replace function sync_upsert_file(
  p_path text,
  p_expected_version bigint,
  p_new_version bigint,
  p_content_hash text,
  p_chunks jsonb
) returns boolean
language plpgsql
security definer
as $$
declare
  affected int;
begin
  -- 同一路径串行化，防止多实例并发覆盖
  perform pg_advisory_xact_lock(hashtext(p_path)::bigint);

  update memory_files
     set version = p_new_version,
         content_hash = p_content_hash,
         updated_at = now()
   where path = p_path
     and version = p_expected_version;

  get diagnostics affected = row_count;

  if affected = 0 then
    return false;
  end if;

  delete from memory_chunks
   where path = p_path
     and chunk_index not in (
       select (x->>'chunk_index')::int
       from jsonb_array_elements(p_chunks) x
     );

  insert into memory_chunks(path, chunk_index, chunk_hash, content)
  select p_path,
         (x->>'chunk_index')::int,
         x->>'chunk_hash',
         x->>'content'
    from jsonb_array_elements(p_chunks) x
  on conflict (path, chunk_index)
  do update set chunk_hash = excluded.chunk_hash,
                content = excluded.content;

  return true;
end;
$$;
```

这里的 `p_expected_version` 是“我上次看到的版本”。  
如果版本不匹配，说明远端已被别人改过，需要走冲突处理。

## 5. 冲突处理

### 5.1 冲突判定矩阵

以 `base_hash` 为基准：

| 本地相对 base | 远端相对 base | 动作 |
|---|---|---|
| 未变 | 未变 | 跳过 |
| 变了 | 未变 | push |
| 未变 | 变了 | pull |
| 变了 | 变了 | 冲突 |
| 删除 | 未变 | push 删除 |
| 未变 | 删除 | pull 删除 |
| 删除 | 变了 | 冲突 |
| 变了 | 删除 | 冲突 |

### 5.2 三向合并

要合并，必须有 base 内容。  
所以同步成功后，会把内容快照写入：

```text
.memory-brain/base/<path>
```

冲突时读取三份内容：

- base
- local
- remote

执行 diff3 合并：

- 如果 local 和 remote 改的是不同段落，自动合并；
- 如果改的是同一段落，进入冲突标记或模型辅助合并。

### 5.3 自动合并规则

默认策略：

1. 非结构化文件：按时间戳选新版本，旧版本备份到 `.memory-brain/conflicts/`；
2. 结构化文本/Markdown：diff3 三向合并；
3. 重叠冲突：如果模型槽位允许，调用模型辅助合并；
4. 模型不可用或合并失败：标记 `conflict`，不覆盖任何一方，等待人工/后续处理。

### 5.4 模型合并的坑位规避

- 不同模型必须使用独立质量门；
- **B 模型(turbo) 的 reasoning 占比 70%-82% 是正常特性，不能因此判定合并结果不合格，跳过 reasoning 占比检测；**
- A 模型可沿用更严格质量门；
- 模型调用超时：

| 模型 | 超时 |
|---|---|
| B 模型(turbo) | 300 秒 |
| A 模型 | 600 秒 |

质量门示例：

```python
def pass_quality_gate(model, output):
    if model == "B-turbo":
        # B 模型高 reasoning 占比是正常特性，只做基本空输出校验
        return output.strip() != ""
    else:
        # A 模型按既有标准检测
        return reasoning_ratio(output) <= threshold
```

## 6. 执行器与预算控制

### 6.1 不占用 3 路并发

- 同步器是独立后台任务；
- 它本身不占用 worker 执行槽；
- 但如果冲突合并需要调用模型，则必须向模型调度器申请槽位；
- 一次最多申请 1 个模型槽位，避免冲突合并挤占多个执行通道。

### 6.2 每轮预算

```text
MAX_FILES_PER_CYCLE = 50
MAX_CHUNKS_PER_CYCLE = 200
MAX_MODEL_CALLS_PER_CYCLE = 1
```

每轮同步只处理预算内的变更，剩余变更保留到下一轮。  
这样可以避免同步任务长时间抢占 CPU/网络。

### 6.3 超时与重试

| 调用类型 | 超时 |
|---|---|
| Supabase 单次读写 | 30 秒 |
| Supabase 批量写入 | 300 秒 |
| B 模型(turbo) 合并 | 300 秒 |
| A 模型合并 | 600 秒 |

超时后不无限重试：

- 最多重试 3 次；
- 退避间隔：1s、5s、30s；
- 仍然失败则进入 pending 队列，等下一轮。

### 6.4 避免空转

- 没有事件时，同步器进入等待状态，不轮询；
- 远程轮询间隔 60s；
- 冲突文件设置冷却时间，例如 5 分钟内不重复自动重试。

## 7. 写后验证与读取点刷新

### 7.1 验证写入生效

每次 push/pull 完成后，不能只看 RPC 返回成功，还要从读取路径验证一次：

```text
select content_hash, version
from memory_files
where path = :path;
```

如果返回的 `content_hash` 与本地期望 hash 不一致，则视为同步失败，触发重试或告警。

### 7.2 同步修改读取点

这是历史踩坑点：

> 配置/内容修改后未生效，往往是因为只改了存储，没有刷新读取点。

所以同步成功后的最后一步必须是：

```text
refresh_reader(path)
```

如果记忆脑有向量索引，则只对变化 chunk 重新生成 embedding，并 upsert；  
如果记忆脑有缓存，则失效对应 path 的缓存；  
如果记忆脑有模板库，则更新对应模板版本。

### 7.3 删除的读取点刷新

删除文件时，也要同步删除：

- 本地缓存；
- 向量索引；
- 模板缓存；
- 相关 embedding。

## 8. 固化与监控

### 8.1 配置模板

```yaml
sync:
  root: ./memory
  chunk_size: 16384
  debounce_ms: 2000
  max_files_per_cycle: 50
  max_chunks_per_cycle: 200
  max_model_calls_per_cycle: 1
  timeout:
    supabase_single_op: 30s
    supabase_batch_op: 300s
    model_b_turbo: 300s
    model_a: 600s
  conflict:
    strategy: auto_merge_then_mark
    archive_dir: .memory-brain/conflicts
  verify:
    enabled: true
    read_back: true
    refresh_reader: true
```

### 8.2 监控指标

至少采集：

```text
sync_pending_count
sync_conflict_count
sync_chunks_uploaded
sync_verify_failure_count
sync_timeout_count
sync_last_success_time
```

如果 `sync_last_success_time` 超过 10 分钟没有更新，则告警。

## 9. 总结

这套增量同步方案的核心是：

1. **事件驱动**，避免全量扫描和空转；
2. **块级 diff**，只同步真正变化的内容；
3. **CAS + 事务 RPC**，防止并发覆盖；
4. **三向合并 + 模型辅助**，不静默丢数据；
5. **写后验证 + 读取点刷新**，确保同步真正生效；
6. **独立后台执行器**，不突破 3 路并发物理上限。

这样，Supabase 记忆脑才能成为“自进化闭环”的可靠底座：  
重复率检测读到的是最新记忆，模板生成不会重复，任务池注入不会过期。
