# 任务类型: eng

设计一个支持3-5轮递进推演、带有链式依赖和断点续跑能力的引擎任务机制，本质上是在设计一个**有向无环图（DAG）工作流**与**状态机**的结合体。

以下是从架构设计、数据结构、断点续跑机制到具体实现的完整方案：

---

### 一、 核心概念定义

在开始设计前，我们需要明确几个核心概念：
1. **推演会话**：一个核心议题的完整生命周期（包含3-5轮推演）。
2. **轮次节点**：每一轮的推演任务（如：Round 1 破题、Round 2 深挖、Round 3 总结）。
3. **上下文**：上一轮的输出结果，作为下一轮的输入。
4. **检查点**：每一轮执行完成后的状态和输出快照。

---

### 二、 任务依赖图设计

对于3-5轮的线性递进推演，依赖图是一条纯粹的线性链。但在实际引擎中，为了保证稳定性，每一轮内部通常会包含“执行”与“校验”两个子节点。

#### 1. 依赖图拓扑结构
采用**线性链式 DAG (Directed Acyclic Graph)**：

```text
[议题输入] 
   │
   ▼
[Round 1: 执行节点] ──(输出校验)──> [Round 1: 存储检查点]
   │ (上下文传递)
   ▼
[Round 2: 执行节点] ──(输出校验)──> [Round 2: 存储检查点]
   │ (上下文传递)
   ▼
[Round 3: 执行节点] ──(输出校验)──> [Round 3: 存储检查点]
   │
   ▼
[推演结束，生成最终报告]
```

#### 2. 数据上下文流转设计
不要简单地把“上一轮的原始输出”丢给下一轮，因为这会导致上下文爆炸或信息丢失。应采用**增量累积上下文**机制：

*   **轮次输入** = `全局议题` + `历史关键摘要` + `上一轮原始输出`
*   **全局状态**：维护一个 JSON，记录每一轮的状态和核心产出。

#### 3. 任务节点数据结构定义
每个轮次节点在引擎中应定义为如下结构：

```json
{
  "session_id": "topic_12345",
  "round_id": 2,
  "task_type": "DEDUCTION",
  "dependencies": ["topic_12345_round_1"],
  "input_context": {
    "topic": "如何提升大模型在垂直领域的准确率",
    "previous_outputs": ["Round 1 的输出结果..."]
  },
  "status": "PENDING", 
  "checkpoint": null
}
```

### 三、 断点续跑机制设计

断点续跑的核心在于：**幂等性**、**状态持久化** 和 **失败恢复策略**。

#### 1. 节点状态机设计
每个轮次节点必须具备以下状态，且只能单向流转：

*   `PENDING` (待执行)：任务已入队，等待调度。
*   `RUNNING` (执行中)：引擎正在处理该轮次。
*   `SUCCESS` (成功)：执行完成，输出已存入检查点。
*   `FAILED` (失败)：执行失败，等待重试或人工介入。
*   `SKIPPED` (跳过)：断点续跑时，发现已成功执行，直接跳过。

#### 2. 检查点机制
在每一轮执行完成时，必须将以下数据持久化到数据库（如 PostgreSQL 或 MongoDB）或缓存（如 Redis）中：

*   **轮次 ID** 与 **状态 (SUCCESS)**
*   **输出结果**
*   **引擎元数据**（消耗的 Token、执行时间、使用的模型版本等，用于复现）

#### 3. 断点续跑触发逻辑
当引擎重启或任务异常中断后重新拉起时，执行以下恢复算法：

1.  **加载会话**：根据 `session_id` 从数据库加载所有的轮次任务记录。
2.  **状态扫描**：遍历 3-5 轮的任务。
3.  **跳过成功节点**：对于状态为 `SUCCESS` 的节点，直接从检查点读取输出，作为下一轮的输入。
4.  **重置中断节点**：对于状态为 `RUNNING` 的节点（说明是宕机中断的），将其状态重置为 `PENDING`。
5.  **处理失败节点**：对于状态为 `FAILED` 的节点，检查重试次数，若未超过阈值则重置为 `PENDING`，否则触发告警。
6.  **重建依赖图**：将未完成的 `PENDING` 节点重新推入任务队列（如 Celery / RabbitMQ），并注入前置节点的检查点数据。

    def start_or_resume_session(self, topic):
        """启动或恢复推演"""
        # 1. 初始化或加载 3-5 轮任务图
        tasks = self.db.get_tasks(self.session_id)
        if not tasks:
            tasks = self._init_task_graph(topic) # 创建 Round 1-5 的依赖图
        
        # 2. 断点续跑检查
        context_accumulator = {}
        for task in tasks:
            if task.status == "SUCCESS":
                # 跳过已完成的，提取检查点数据供下一次使用
                context_accumulator[task.round_id] = task.checkpoint.output
                continue
            
            elif task.status == "RUNNING":
                # 宕机恢复：重置为 PENDING
                task.status = "PENDING"
                self.db.update_task(task)
            
            # 3. 执行未完成的任务

### 五、 进阶设计考量（提升系统鲁棒性）

1. **软隔离与超时机制**：
   某一轮推演如果涉及大模型调用，可能会因为网络抖动卡死。必须为 `execute_round` 设置硬超时（如 60秒），超时后直接判定为 `FAILED`，触发断点续跑，防止整个链路挂起。

2. **部分失败的微调重试**：
   如果 Round 3 失败了，重试时不一定要完全重新跑 Round 3。可以记录 Round 3 的失败原因（如“输出格式不符”），在重试时将“错误提示”附加到 Round 3 的 Prompt 中，让模型自我修正。

3. **人工介入节点**：
   在某些严肃的推演链路中，Round 3 (比如关键决策点) 完成后，可能需要人工审核。可以引入 `WAITING_FOR_HUMAN_REVIEW` 状态。断点续跑时，遇到此状态则暂停调度，等待外部 API 调用将其改为 `SUCCESS` 后继续往下推演。

### 总结
这套机制通过 **线性 DAG 定义链路** + **检查点持久化上下文** + **状态机驱动恢复** ，能够完美支撑3-5轮甚至更长链路的引擎推演。无论是遇到服务器重启、模型超时还是业务异常，只要数据库还在，就能在下一次拉起时从断点处丝滑续跑。
