# 任务类型: eng

## 推演：Supabase 记忆脑增量同步方案

### 0. 核心认知

增量同步的本质不是“少传文件”，而是：

> **以 `(file_path, chunk_id, revision)` 为锚点，做状态对齐。**

- `file_path`：归一化后的本地文件相对路径
- `chunk_id`：稳定逻辑 ID，不是内容 hash，也不是行号/序号
- `revision`：该 chunk 内容 + 元数据的版本指纹

同步不是比较“文件是否变了”，而是比较三份状态：

1. `baseline`：上次成功同步后的锚点集合，存在本地 manifest
2. `local`：当前本地文件解析出的期望锚点集合
3. `remote`：Supabase 当前实际锚点集合

增量同步就是让这三者收敛，并且只对差异部分做 API 和 DB 操作。

---

### 1. 本地变更检测

#### 1.1 文件级指纹

维护 manifest：

```json
{
  "file_path": "docs/a.md",
  "mtime_ns": 1710000000000000000,
  "size": 12345,
  "file_hash": "sha256(...)"
}
```

检测逻辑：

```text
if mtime 和 size 都没变：
    skip
else：
    重新计算 file_hash
    if file_hash 没变：
        只更新 mtime/size，skip
    else：
        进入 chunk 级 diff
```

这样避免“touch 一下文件就全量重刷”。

#### 1.2 chunk_id 的稳定性

`chunk_id` 不能是：

- 文件内的序号
- 纯内容 hash
- 行号

否则文件插入一段后，后续所有 chunk 都会“漂移”，导致全量重新 embedding。

推荐做法：

- 首次出现的新 chunk，生成 UUID v4 作为 `chunk_id`
- 后续文件变更时，用 diff 匹配旧 chunk 和新 chunk，尽量复用 `chunk_id`
- 匹配优先级：

```text
1. content_hash 完全相同 → 直接复用
2. 同一 heading_path 下，相似度 >= 0.8，且是一对一替换 → 复用
3. 否则：旧 chunk 标记删除，新 chunk 生成新 ID
```

这样：

```text
文件插入一个新段落
→ 未变化的段落 chunk_id 不变
→ 只有新段落需要 embedding 和 upsert
→ 不会退化成全量同步
```

#### 1.3 文件重命名

如果旧文件消失，新文件出现，但 `file_hash` 相同，应识别为 rename：

- 更新 manifest 中的 `file_path`
- 更新 Supabase 中对应 chunk 的 `file_path`
- 不需要重新 embedding

### 2. 三态 diff

每次同步一个文件时，取三类锚点：

```text
baseline: {chunk_id: revision}
local:    {chunk_id: revision}
remote:   {chunk_id: revision, is_deleted}
```

diff 逻辑：

```text
for chunk_id in union(baseline, local, remote):
    b = baseline.get(chunk_id)
    l = local.get(chunk_id)
    r = remote.get(chunk_id)

    # 幂等修复：远端已经等于本地，只是 manifest 没更新
    if l and r and l.revision == r.revision:
        baseline[chunk_id] = l.revision
        continue

    lb_changed = l and (not b or l.revision != b.revision)
    rb_changed = r and (not b or r.revision != b.revision)

    if not lb_changed and not rb_changed:
        noop
    elif lb_changed and not rb_changed:
        upsert local
    elif not lb_changed and rb_changed:
        pull/merge remote
    else:
        conflict
```

关键点：

- `revision` 必须包含内容和关键元数据指纹，例如：

```text
content_hash = sha256(normalized_text)
metadata_hash = sha256(canonical_json(metadata))
revision = sha256(content_hash + metadata_hash)
```

- 远端查询只查锚点和元数据，不查 embedding：

```sql
select
  chunk_id,
  revision,
  content_hash,
  is_deleted,
  metadata,
  updated_at
from memory_chunks
where file_path = any($1);
```

### 3. 冲突处理

冲突判断不能靠时间戳，必须靠 `revision`。

默认策略建议：

| 场景 | 默认行为 |
|---|---|
| 本地内容变，远端内容没变 | 推送本地，重新生成 embedding |
| 本地内容没变，远端派生字段变 | 保留远端派生字段，如 summary/tags |
| 本地内容变，远端派生字段变 | 内容按本地，派生字段合并，同键冲突写日志 |
| 本地内容变，远端内容也变 | **local-wins + 备份远端到 conflict_log** |
| 本地删除，远端没变 | 软删除远端 |
| 本地删除，远端内容已变 | **远端保留，写 conflict_log**，避免数据丢失 |
| 本地更新，远端已删除 | **本地恢复，写 conflict_log** |

示例：

```text
baseline: chunk_1 = rev_a
local:    chunk_1 = rev_b
remote:   chunk_1 = rev_c

→ 冲突
→ 默认 local-wins
→ 先把 remote 的 rev_c 内容写入 conflict_log
→ 再用 rev_b 覆盖远端
```

删除不要硬删，而是 tombstone：

```text
is_deleted = true
revision = sha256("tombstone:" + chunk_id + deleted_at)
```

本地也维护一个 `graveyard`：

```text
content_hash -> chunk_id
```

这样如果同一段内容未来重新出现，可以复活同一个 `chunk_id`，而不是生成新 chunk 导致重复。

### 4. 只同步变更部分

只有以下情况才需要调用 API：

- 新增 chunk
- 本地内容变更导致 `content_hash` 变化
- embedding 缺失或模型版本变化

以下情况不需要 API：

- chunk 内容没变
- 只改了 metadata
- 远端派生字段变更

这样能保证：

```text
一个 1000 个 chunk 的文件，只改了 1 个 chunk
→ 只 embedding 1 个 chunk
→ 只 upsert 1 个 chunk
→ 其余 999 个 chunk 零 API 调用、零 DB 写入
```

### 5. 并发与 API 后处理

#### 5.1 并发 API 调用

API 调用本身可以多线程并发，但要注意：

> 问题不在 API 调用，而在 API 返回后的共享状态写入。

错误示范：

```python
def on_api_done(result):
    shared_state.update(result)  # 多个线程同时写，交错
```

正确架构：

```text
API Worker Pool
    ↓ 每个 worker 只负责 HTTP 调用
结果队列 Queue
    ↓ 唯一 Writer 线程
质量检测 → 冲突解决 → Supabase 写入 → manifest 更新
```

原则：

- API worker 只产生结果对象
- Writer 是唯一允许写 DB 和 manifest 的线程
- 所有“后处理”串行执行

#### 5.2 超时与质量门禁

按模型配置超时：

```text
B 模型(turbo)：300 秒
A 模型：600 秒
```

质量检测按模型路由：

- B 模型(turbo)：**跳过 reasoning 占比检测**
- B 模型 reasoning 占比 70%–82% 是正常特性，不能判为废稿重试
- A 模型按自己的 reasoning 阈值检测

失败处理：

```text
超时/质量失败 → 有限次重试
仍失败 → 进入 quarantine 表，不阻塞整个同步
```

### 6. Supabase 表结构

```sql
create table memory_chunks (
  chunk_id uuid primary key,
  file_path text not null,
  revision text not null,
  content_hash text not null,
  content text,
  embedding vector(1536),
  metadata jsonb not null default '{}',
  is_deleted boolean not null default false,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index idx_memory_chunks_file
  on memory_chunks(file_path, is_deleted);

create index idx_memory_chunks_updated
  on memory_chunks(updated_at);

create table conflict_log (
  id bigserial primary key,
  chunk_id uuid,
  file_path text,
  baseline_revision text,
  local_revision text,
  remote_revision text,
  local_content text,
  remote_content text,
  resolution text not null,
  created_at timestamptz not null default now()
);
```

写入时建议带乐观锁：

```sql
update memory_chunks
set
  revision = $new_rev,
  content = $content,
  content_hash = $hash,
  metadata = $metadata,
  updated_at = now()
where
  chunk_id = $chunk_id
  and revision = $expected_rev;
```

如果影响行数为 0，说明远端已被其他客户端修改，需要重新 diff。

### 7. 同步主流程

```text
1. 文件 watcher / 轮询
   ↓
2. 检测 dirty 文件
   ↓
3. 解析 chunk，计算 local anchors
   ↓
4. 拉取 remote anchors
   ↓
5. 和 baseline 做三态 diff
   ↓
6. 解决冲突
   ↓
7. 只对变化 chunk 调 API
   ↓
8. 单 Writer 写入 Supabase
   ↓
9. 原子更新本地 manifest
```

第一次同步或 manifest 丢失时：

- 不要直接全量覆盖
- 先拉远端 anchors
- 按 `content_hash` 匹配本地 chunk，复用远端 `chunk_id` 和 embedding
- 建立 baseline 后再走增量流程

---

### 8. 防坑清单

- 没有稳定 `chunk_id` → 必然退化成全量同步
- 没有 `revision` → 冲突处理就是猜
- 新增配置必须同步修改读取点，改完立即验证
- B 模型(turbo) 不检测 reasoning 占比
- B 模型用 300 秒超时，A 模型用 600 秒超时
- API 返回后必须进单一队列，由单一 Writer 处理后写库
- 删除必须 tombstone，不能硬删，否则远端删除会被本地重新上传复活
- manifest 更新必须原子化，否则崩溃后需要幂等修复

最终记住：

> 增量同步不是“少传文件”，而是用 `(file_path, chunk_id, revision)` 把本地状态和远端状态对齐。对齐之后，只处理差异部分，才是真正的增量。
