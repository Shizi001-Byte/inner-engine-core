# 任务类型: eng

基于你给出的锚点，直接推演设计如下。不重复论证“为什么”，只给出“怎么做”。

---

## 一、核心锚点

自动归档系统的唯一锚点是：

> **TaskArchiveContract（任务归档契约）**

所有任务必须先被决策层转成契约，执行层只认契约，不认原始任务。

```json
{
  "contract_version": "1.0",
  "task_id": "task_20250101_001",
  "category": "财务/报销",
  "tags": ["报销", "发票", "紧急"],
  "target_dir": "/archive/finance/reimbursement",
  "archive_action": "move",
  "metadata": {
    "source": "ding_talk",
    "created_at": "2025-01-01T10:00:00Z",
    "owner": "user_a"
  }
}
```

这个契约就是归档系统的“列契约”。

---

## 二、系统链路

### 1. 决策层：严格串行

链路必须固定为：

```text
schema 定义
    ↓
任务分类
    ↓
标签生成
    ↓
目录映射
    ↓
契约评审
    ↓
输出归档契约
```

不允许跳跃，不允许并行，不允许在执行层补决策。

每一步都只做一件事：

| 步骤 | 输入 | 输出 |
|---|---|---|
| schema 定义 | 配置中心 | 字段契约、分类枚举、标签字典、目录映射表 |
| 任务分类 | 原始任务 | `category` |
| 标签生成 | 原始任务 + `category` | `tags` |
| 目录映射 | `category` | `target_dir` |
| 契约评审 | 完整契约 | 通过 / 打回决策层 |
| 输出契约 | 评审通过的契约 | 进入执行队列 |

关键约束：

- `category` 必须来自配置中心的分枚举，不能自由生成。
- `tags` 必须受控，不能脱离标签字典。
- `target_dir` 必须来自目录映射表，不能由执行层猜。
- 契约缺字段，直接打回，不能补。

---

### 2. 执行层：允许并发，禁止简化

执行层可以有多个 worker 并发处理不同任务。

但每个 worker 拿到的必须是完整契约，不能拿原始任务。

```python
def execute(contract):
    validate_contract(contract)          # 缺少字段直接失败

    target = Path(contract.target_dir)
    if not target.exists():
        raise Exception("target_dir 不存在")

    archive_task(contract.task_id, target)
    write_metadata(contract)             # 写 .archive.json
    verify_archive(contract)             # 归档后校验

    return {"status": "done", "task_id": contract.task_id}
```

执行层禁止做的事：

- 禁止根据任务标题重新猜分类。
- 禁止自己补标签。
- 禁止自己决定目录。
- 禁止只归档文件，不写元数据。
- 禁止“简化版归档脚本”。

## 三、配置变更机制

历史坑点：

> 配置修改后未生效，行为无变化。

所以自动归档系统必须统一配置中心，并且所有读取点都从配置中心读，不能散落硬编码。

### 配置中心必须管理的内容

- 分类枚举
- 标签字典
- 目录映射表
- 模型超时时间
- 归档动作类型（copy / move）
- 元数据字段定义

### 配置变更后必须立即验证

新增一个分类时，必须同步修改：

1. 分类枚举
2. 目录映射表
3. 标签字典
4. 评审规则
5. 索引/检索逻辑

修改完成后，必须自动跑一次冒烟验证：

```text
构造一条测试任务
→ 走决策层
→ 生成契约
→ 评审
→ 执行 dry-run
→ 确认归档结果符合预期
```

冒烟通过，配置才标记为“生效”。

## 四、超时与模型调用

历史坑点：

> API 调用超时，任务未在规定时间内返回。

自动归档系统在决策层会调用分类/打标模型，因此必须预设超时：

| 模型 | 默认超时 |
|---|---|
| A 模型 | 600 秒 |
| B 模型 turbo | 300 秒 |

超时后不允许无限等待，必须快速失败并进入重试/告警链路。

同时，决策层串行调用多个模型时，必须给整条决策链路设总超时，避免单个任务拖死整个队列。

## 五、风险控制

| 历史失败点 | 自动归档系统对应机制 |
|---|---|
| 简化版 SQL 导致列不匹配 | 所有任务必须生成完整 TaskArchiveContract，执行层禁止缺字段 |
| 配置修改后未生效 | 配置中心统一读取，变更后强制冒烟验证 |
| API 调用超时 | A 模型 600 秒，B 模型 turbo 300 秒，超时快速失败 |
| 执行层自行简化 | 执行层只认契约，不认原始任务，缺少信息直接失败 |
| 决策层不明确列映射 | 目录映射、标签映射、分类映射全部在决策层完成 |

---

## 六、实施顺序

先校准锚点，再优化链路。

1. 先用历史任务样本跑通决策层，产出契约。
2. 人工检查契约里的 `category`、`tags`、`target_dir` 是否稳定合理。
3. 校准 schema、分类枚举、标签字典、目录映射表。
4. 锚点稳定后，再放开执行层并发。
5. 最后接入配置中心和冒烟验证机制。

顺序反了，就会变成：执行层并发越快，错误归档越多。

---

## 七、最终验收标准

- 100% 任务在执行前都有完整契约。
- 0 个任务由执行层自行补字段。
- 分类、标签、目录映射全部来自配置中心。
- 配置修改后，冒烟验证自动执行，不通过不生效。
- 模型调用超时受控，不会无限等待。
- 归档完成后，契约元数据可被检索系统正确读取。

这样，自动归档系统才能做到：任务自动分类、自动打标签、自动存入对应目录，同时不丢锚点、不靠执行层猜。
