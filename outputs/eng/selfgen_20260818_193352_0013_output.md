# 任务类型: eng

## 推演：竞态条件在哪

多线程 API 调用本身没问题，问题出在**API 返回后**：

- 线程 A 和线程 B 同时拿到 chunk 1、chunk 2 的响应。
- 两者同时进入“后处理”临界区。
- 两者同时读到 `completed_chunks = 0`。
- A 写 `completed_chunks = 1`，B 也写 `completed_chunks = 1`。
- 最终 `completed_chunks` 应该等于 2，但实际是 1，或者被交错覆盖。

这就是典型的 **共享状态读改写交错**。

后处理必须串行化，并且落库时要靠数据库行锁和唯一锚点做最终兜底。

---

## 完整锁机制方案

### 核心设计

```
API 线程池（N 个线程，并发调用方舟 API）
          │
          ▼
响应到达 → 校验 content 非空
          │
          ▼
PostProcessGate（单消费者队列 / 串行后处理）
          │
          ▼
后处理：解析 → 校验 revision → 写 memory_blocks → 原子推进 completed_chunks
```

要点：

1. **API 调用不加锁**，保持并发。
2. **后处理必须串行**，用“单消费者队列 + Condition”实现全局临界区。
3. **数据库层再加行锁**，防止多进程/多实例部署时仍然交错。
4. **记忆块写入用 `(file_path, chunk_id, revision)` 作为唯一锚点**，天然幂等。

### 1. 串行后处理器：PostProcessGate

等价于一把全局锁，但比裸 `Lock` 更公平、更可控。

```python
import threading
from collections import deque
from concurrent.futures import Future

class PostProcessGate:
    """所有后处理任务必须通过这个 Gate 串行执行。"""

    def __init__(self):
        self._cond = threading.Condition()
        self._queue = deque()
        self._worker = threading.Thread(target=self._run, daemon=True)
        self._worker.start()

    def submit(self, job):
        """提交一个后处理任务，返回 Future。"""
        future = Future()
        with self._cond:
            self._queue.append((job, future))
            self._cond.notify()
        return future

    def _run(self):
        while True:
            with self._cond:
                while not self._queue:
                    self._cond.wait()
                job, future = self._queue.popleft()

            try:
                result = self._process(job)
                future.set_result(result)
            except Exception as e:
                future.set_exception(e)

    def _process(self, job):
        # 这里只能做后处理，不能再调外部大模型 API
        return post_process_chunk(job)
```

API 线程调用方式：

```python
def api_worker(chunk):
```

### 2. 方舟 API 调用：urllib 直连 + 超时

根据坑库，不用 `requests`，用 `urllib` 并禁用全局代理。

```python
import json
import urllib.request

ARK_TIMEOUT = {
    "B": 300,   # B 模型 turbo
    "A": 600,   # A 模型
}

def call_ark_api(payload, model_type):
    timeout = ARK_TIMEOUT.get(model_type, 300)

    opener = urllib.request.build_opener(
        urllib.request.ProxyHandler({})   # 显式禁用代理
    )

    req = urllib.request.Request(
        ARK_ENDPOINT,
        data=json.dumps(payload).encode("utf-8"),
        headers={
            "Content-Type": "application/json",
            "Authorization": f"Bearer {ARK_API_KEY}",
        },
        method="POST",
    )

    with opener.open(req, timeout=timeout) as resp:
        return json.loads(resp.read().decode("utf-8"))
```

### 3. 校验 Responses API 的 content 非空

B 模型如果用 Responses API，`output_tokens` 可能全耗在 reasoning 上，导致正式 `content` 为空。

```python
class EmptyContentError(Exception):
    pass

def extract_content(response):
    if not isinstance(response, dict):
        raise EmptyContentError("response 格式异常")

    # 优先取 Responses API 的 output_text
    content = response.get("output_text")

    # 兼容旧版 chat.completions
    if not content:
        try:
            content = response["choices"][0]["message"]["content"]
        except (KeyError, IndexError, TypeError):
            pass

    if not content:
        raise EmptyContentError(
            "content 为空：可能 reasoning 消耗了全部 output_tokens"
        )

    return content
```

### 4. 数据库层：锁 + 锚点 + 原子推进

即使 `PostProcessGate` 保证了单进程串行，多实例部署时仍可能跨进程竞争。  
所以必须在数据库层做事务和行锁。

#### 表结构

```sql
-- 文件同步状态
CREATE TABLE file_sync_state (
    file_path        text PRIMARY KEY,
    current_revision text NOT NULL,
    status           text NOT NULL DEFAULT 'pending', -- pending / processing / completed
    total_chunks     integer NOT NULL DEFAULT 0,
    completed_chunks integer NOT NULL DEFAULT 0,
    updated_at       timestamptz NOT NULL DEFAULT now()
);

-- 记忆块表，锚点就是主键
CREATE TABLE memory_blocks (
    file_path  text NOT NULL,
    chunk_id   integer NOT NULL,
    revision   text NOT NULL,
    content    text NOT NULL,
    embedding  vector(1024),
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (file_path, chunk_id, revision)
);
```

#### 原子后处理函数

用一个 Postgres 函数完成：

- 锁定 `file_sync_state` 对应行。
- 校验 revision 是否仍是当前 revision。
- 写入 `memory_blocks`。
- 原子推进 `completed_chunks`。
- 最后一个 chunk 完成后推进状态为 `completed`。

```sql
CREATE OR REPLACE FUNCTION process_chunk(
    p_file_path   text,
    p_chunk_id    integer,
    p_revision    text,
    p_content     text,
    p_embedding   vector
) RETURNS json
LANGUAGE plpgsql
AS $$
DECLARE
    v_current_revision text;
    v_status           text;
    v_total            integer;
    v_completed        integer;
BEGIN
    -- 行锁：同一文件同一时刻只有一个后处理事务能改状态
    SELECT current_revision, status, total_chunks
    INTO v_current_revision, v_status, v_total
    FROM file_sync_state
    WHERE file_path = p_file_path
    FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'file_sync_state not found: %', p_file_path;
    END IF;

    -- 旧 revision 的迟到结果直接丢弃，防止旧块污染当前状态
    IF v_current_revision <> p_revision THEN
        RETURN json_build_object(
            'status', 'stale',
            'completed', NULL,
            'total', NULL
        );
    END IF;

    -- 幂等写入记忆块
    INSERT INTO memory_blocks (
        file_path, chunk_id, revision, content, embedding
    )
    VALUES (
        p_file_path, p_chunk_id, p_revision, p_content, p_embedding
    )
    ON CONFLICT (file_path, chunk_id, revision)
    DO UPDATE SET
        content   = EXCLUDED.content,
        embedding = EXCLUDED.embedding;

    -- 如果文件已经 completed，说明是重复响应，不再重复计数
    IF v_status = 'completed' THEN
        RETURN json_build_object(
            'status', 'completed',
            'completed', v_total,
            'total', v_total
        );
    END IF;

    -- 原子推进完成计数
    UPDATE file_sync_state
    SET completed_chunks = completed_chunks + 1,
        updated_at = now()
    WHERE file_path = p_file_path
      AND current_revision = p_revision
      AND status = 'processing'
    RETURNING total_chunks, completed_chunks
    INTO v_total, v_completed;

    -- 如果是最后一个 chunk，标记 completed
    IF v_completed >= v_total THEN
        UPDATE file_sync_state
        SET status = 'completed',
            updated_at = now()
        WHERE file_path = p_file_path
          AND current_revision = p_revision
          AND status = 'processing';

        RETURN json_build_object(
            'status', 'completed',
            'completed', v_completed,
            'total', v_total
        );
    END IF;

    RETURN json_build_object(
        'status', 'processing',
        'completed', v_completed,
        'total', v_total
    );
END;
$$;
```

后处理代码里直接调用这个函数：

```python
def post_process_chunk(job):
    chunk, content = job

    # 如果 embedding 也是模型返回的，这里同样要先校验非空
    embedding = chunk.embedding

    return supabase.rpc(
        "process_chunk",
        {
            "p_file_path": chunk.file_path,
            "p_chunk_id": chunk.chunk_id,
            "p_revision": chunk.revision,
            "p_content": content,
            "p_embedding": embedding,
        }
    ).execute()
```

## 锁机制总结

| 层 | 机制 | 作用 |
|---|---|---|
| API 调用层 | 无锁，线程池并发 | 提高吞吐 |
| 后处理层 | `PostProcessGate` 单消费者队列 + Condition | 保证单进程内后处理严格串行 |
| 数据库层 | `SELECT ... FOR UPDATE` 行锁 | 保证跨进程/多实例状态一致 |
| 记忆块层 | `PRIMARY KEY (file_path, chunk_id, revision)` | 保证锚点幂等，重复写入不产生脏数据 |

## 避坑落地检查

1. **方舟 API 必须用 urllib 直连**，禁用代理：`ProxyHandler({})`。
2. **B 模型超时 300 秒，A 模型超时 600 秒**，写在调用参数里。
3. **Responses API 返回后先单测 `content` 非空**，再接入主流程。
4. **后处理函数内不能再调外部 API**，否则会阻塞串行队列。
5. **同一个 revision 重复执行，`completed_chunks` 不会超数**，因为数据库函数已处理 `completed` 状态。

最终效果：  
**多线程只负责并发拿 API 结果，后处理串行落库，数据库行锁兜底，锚点保证幂等。**  
这样 `completed_chunks` 永远等于 `memory_blocks` 中当前 revision 的实际块数，状态一致。
