# 任务类型: eng

基于提供的核心认知与避坑经验，设计引擎产出的“自动归档系统”将严格遵循**脑体分离架构**，并落实**显式声明、幂等可校验**的原则。以下是系统的推演与设计方案：

### 一、 架构边界划分（脑体分离）
根据认知锚定3与4，系统的边界必须清晰切分：

*   **脑（决策层/全局顺序）：** 负责任务分类、打标签、计算目标目录，并生成不可变的全局顺序归档事件。不包含任何文件系统写入或DB状态修改操作。
*   **体（执行层/同步层）：** 订阅决策事件，负责物理文件移动、元数据持久化、目录创建。严格幂等，不可自行决定分类或标签。

---

### 二、 决策引擎设计（脑）
决策引擎接收原始任务，调用AI模型进行分类与标签提取，输出归档指令事件。

**1. 模型调用与超时控制（避坑：API调用超时）**
*   预设严格timeout，分类打标签若调用 **B模型turbo**，强制设置 `timeout=300`秒；若调用 **A模型**，强制设置 `timeout=600`秒。
*   超时直接熔断当前任务，标记为 `DECISION_TIMEOUT`，进入死信队列等待重试，绝不阻塞全局顺序。

**2. 决策事件输出**
决策引擎产出的事件结构（不可变，显式声明）：
```json
{
  "event_id": "evt_20231025_001", // 全局顺序唯一标识
  "task_id": "task_12345",
  "decided_category": "财务报销",
  "decided_tags": ["Q3", "差旅", "已审核"],
  "target_directory": "/archive/finance/2023/Q3/",
  "decision_timestamp": 1698200000
}
```

---

### 三、 执行与同步层设计（体）
执行层消费决策事件，进行物理归档操作。

**1. 基建脚本与数据同步（避坑：简化版SQL与列错位）**
根据认知锚定1、2、5，坚决禁用简化版SQL，建表与同步必须显式声明：

*   **建表DDL（显式列名与类型）：**
    ```sql
    CREATE TABLE IF NOT EXISTS task_archive_records (
        id BIGSERIAL PRIMARY KEY,
        task_id VARCHAR(64) NOT NULL,
        category VARCHAR(128) NOT NULL,
        tags JSONB NOT NULL,
        file_path TEXT NOT NULL,
        archive_time TIMESTAMPTZ NOT NULL DEFAULT NOW(),
        event_id VARCHAR(64) UNIQUE NOT NULL -- 幂等校验核心
    );
    ```
*   **同步DML（禁止 `SELECT *` 或隐式插入）：**
    ```sql
    INSERT INTO task_archive_records 
        (task_id, category, tags, file_path, event_id) 
    VALUES 
        ('task_12345', '财务报销', '["Q3","差旅","已审核"]', '/archive/finance/2023/Q3/task_12345.pdf', 'evt_20231025_001')
    ON CONFLICT (event_id) DO NOTHING; -- 严格幂等
    ```

**2. 物理文件落盘校验**
执行文件移动后，立即执行脚本校验：目标路径文件是否存在、源路径文件是否已删除/标记转移。校验失败则触发回滚。

---

### 四、 配置中心与生效验证（避坑：配置修改未生效）
根据避坑提醒1，分类规则和目录映射配置的修改必须闭环验证。

**1. 配置读取点统一**
*   严禁在多个服务节点散落硬编码的目录映射规则。所有读取点必须指向统一的 `ArchiveConfigService`。

**2. 配置修改后的立即验证机制**
当修改了某类任务的归档目录（例如将“差旅”从 `/finance/` 改为 `/travel/`）后，系统强制执行以下流水：
*   **Step 1:** 配置中心发布新版本配置。
*   **Step 2:** 触发一个 `配置生效探针任务`（假任务）。
*   **Step 3:** 决策引擎读取配置，生成探针事件。
*   **Step 4:** 执行层接收探针事件，校验输出的 `target_directory` 是否与修改后的配置一致。
*   **Step 5:** 只有探针校验通过，配置版本才标记为 `Active`，否则回滚配置并告警。

---

### 五、 系统可重放与可校验设计
根据认知锚定2与4，整个归档过程必须可重放。

1.  **事件日志驱动：** 物理文件移动和DB同步完全由 `event_id` 驱动。若发生异常，只需重放事件队列，由于 `ON CONFLICT DO NOTHING` 和文件覆盖策略，最终状态必然一致。
2.  **全链路对账脚本：** 定时运行校验脚本，断言：
    *   DB中的 `task_id` 对应的物理文件是否存在。
    *   DB中的 `category` 和 `tags` 是否与决策引擎事件日志中的记录严格一致（而非靠执行层中间态猜测）。

**总结：** 该自动归档系统将“分类打标签”的智能决策与“文件移动入库”的机械执行彻底解耦。通过强制显式的DDL/DML、严格的超时控制、以及配置变更的探针验证，规避了SQL列错位、API阻塞、配置失效等历史坑点，确保归档过程确定、幂等、可校验。
