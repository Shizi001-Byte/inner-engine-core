# 任务类型: eng

基于已有认知锚定，不再重复推导熵增定律。以下方案直接把这些结论转成设计约束：**自动归档系统就是引擎的“负熵输入”**，目标是降低引擎整体的功能熵；同时归档系统自身也必须具备抗退化、可纠偏、可验证的闭环。

---

## 一、设计目标

| 目标 | 对应低功能熵表现 |
|---|---|
| 任务自动分类准确 | 归档目录与任务真实类型一致 |
| 打标签完整、可检索 | 标签覆盖关键维度，不丢失元信息 |
| 存入对应目录 | 目录命中率高，不产生“乱堆区” |
| 配置变更可验证 | 修改后立即生效，不出现“改了没反应” |
| 模型调用不拖死归档 | 超时自动降级，不无限阻塞 |

---

## 二、总体架构

```
引擎任务产出
   ↓
采集器：监听任务结束事件，收集输出文件/日志/指标/manifest
   ↓
归一化：统一路径、时间、格式，提取结构化元数据
   ↓
分类器：规则优先 + 模型兜底
   ↓
打标签：多标签生成，写入 sidecar 元数据文件
   ↓
目录映射：分类 + 标签 → 目标目录
   ↓
归档执行：安全校验 → 原子写入 → 建立索引
   ↓
反馈闭环：人工纠偏 → 规则/模型更新 → 自检 → 生效
```

核心原则：**能用结构化元数据就不调用模型，能走规则就不走大模型，避免把简单归档变成高延迟、高失败率任务。**

## 三、任务分类体系

按锚定 4，AI 引擎的自然退化发生在四个层级。因此归档系统的一级分类直接对齐这四层：

| 一级分类 | 含义 | 典型任务类型 |
|---|---|---|
| `compute` | 物理算力/资源层 | 资源监控、算力调度、成本核算、容量规划 |
| `model` | 模型参数/训练层 | 训练、微调、量化、评估、checkpoint 管理 |
| `service` | 服务链路层 | 在线推理、批量推理、API trace、故障、压测 |
| `alignment` | 价值对齐层 | red team、人类反馈、安全评估、合规审计、政策检查 |

二级分类由任务类型决定，例如：

```
model.training
model.evaluation
service.inference
service.incident
alignment.safety_eval
compute.resource_usage
```

分类优先级：

1. 引擎任务自带 `task_manifest.json`，直接读取 `layer`、`task_type`；
2. 没有 manifest 时，用规则匹配文件路径、日志关键字、任务名；
3. 规则仍无法确定时，调用模型分类。

## 四、打标签体系

标签是归档系统的“信息负熵”，必须足够覆盖检索需要。

### 系统自动标签

- 层级：`layer:compute/model/service/alignment`
- 任务类型：`task_type:training/evaluation/inference/...`
- 状态：`status:success/failed/timeout/degraded/blocked`
- 模型版本：`model:qwen2.5-72b`
- 数据版本：`data:2025-01-01`
- 超时配置：`timeout:300` / `timeout:600`

### 内容标签

- 由模型或规则从产出内容中抽取：
  - `anomaly`
  - `retry`
  - `value_alignment_risk`
  - `latency_p99`
  - `oom`
  - `human_feedback`

### 控制标签

- `confidence:0.95`
- `needs_review:true`
- `source:auto_archive`
- `verified:false`

所有标签写入与产出物同名的 `.meta.json` 文件：

```
{
  "run_id": "20250601-abc123",
  "layer": "model",
  "task_type": "training",
  "status": "success",
  "tags": ["layer:model", "task_type:training", "status:success"],
  "confidence": 0.98,
  "archived_at": "2025-06-01T12:00:00Z"
}
```

## 五、目录设计

目录由一级分类 + 二级任务类型 + 日期构成：

```
/engine-outputs/
  _pending/          # 等待分类
  _review/           # 低置信度/模型超时/需人工确认
  _failed/           # 归档流程本身失败
  compute/
    resource_usage/2025-06-01/
    capacity/2025-06-01/
  model/
    training/2025-06-01/
    evaluation/2025-06-01/
  service/
    inference/2025-06-01/
    incident/2025-06-01/
  alignment/
    safety_eval/2025-06-01/
    human_feedback/2025-06-01/
```

文件名格式：

```
{run_id}_{timestamp}_{task_type}_{status}.{ext}
```

例如：

```
20250601-abc123_20250601T120000Z_training_success.json
```

如果任务状态为 `failed`，仍然按对应任务类型归档，只是标签不同，避免把失败任务单独丢弃。

## 六、配置管理：防止“改了没生效”

历史教训 1 必须内置为强制机制。

### 原则

- **所有配置只存一处**：配置中心 `ArchiveConfig`。
- **所有模块从统一读取点获取配置**，禁止代码中散落硬编码默认值。
- **新增配置项时，必须同步检查读取点**：新增目录映射、标签规则、模型超时，必须能在同一处被看到。

### 配置项

```yaml
archive:
  rules:
    - pattern: "train_*.log"
      layer: model
      task_type: training
    - pattern: "infer_*.json"
      layer: service
      task_type: inference
  model_router:
    fast:
      model: B-turbo
      timeout: 300
    deep:
      model: A
      timeout: 600
  directory_mapping:
    model.training: /engine-outputs/model/training
    service.inference: /engine-outputs/service/inference
```

### 配置生效验证流程

1. 修改配置中心，版本号 +1；
2. 系统读取新版本配置；
3. 自动运行自检样本集：
   - 输入 20 条已标注历史任务；
   - 断言分类结果、标签、目标目录与预期一致；
4. 自检通过后切换 active 配置；
5. 上线后监控配置命中率、目录命中率；
6. 一旦发现异常，自动回滚到上一版本。

这样就不会出现“配置改了，行为没变”。

## 七、API 超时处理：防止任务卡死

历史教训 2 直接落地为模型路由策略。

### 调用规则

| 场景 | 模型 | 超时 |
|---|---|---|
| 常规分类 | B 模型 turbo | 300 秒 |
| 复杂任务/低置信度二次分类 | A 模型 | 600 秒 |

### 处理流程

```
需要模型分类
   ↓
调用 B-turbo，timeout=300s
   ↓
成功且置信度 ≥ 0.9 → 直接归档
   ↓
超时 或 置信度 < 0.9
   ↓
调用 A 模型，timeout=600s
   ↓
成功 → 归档
   ↓
仍失败/超时 → 规则兜底分类 + 放入 _review
```

关键点：

- 每次 API 调用必须显式设置 timeout，不允许默认无限等待；
- 超时不重试到天荒地老，最多降级到规则 + 人工复核；
- 归档主流程不被模型调用阻塞：模型调用在 worker 中异步执行，队列消费失败自动重试 3 次，仍失败进 `_failed`。

## 八、归档系统自身的抗退化设计

锚定 4 说 AI 引擎会在四个层级自然退化。归档系统也一样，必须有针对性防护。

| 层级 | 退化表现 | 防护机制 |
|---|---|---|
| 算力层 | 磁盘满、归档节点故障 | 容量监控、归档队列长度告警 |
| 模型层 | 分类模型漂移、规则过时 | 定期用人工纠偏数据重训/更新规则 |
| 服务链路层 | 管道超时、队列积压 | 超时控制、失败重试、降级路径 |
| 价值对齐层 | 分类标准偏离用户真实意图 | 人工反馈闭环，宏观价值原则优先 |

---

## 九、反馈闭环：负熵输入

锚定 5 在归档系统中的体现是：

- **宏观价值主体性**：人类定义分类原则、价值边界、归档规范；
- **分布式功能主体性**：每个自动分类器、规则引擎、归档 worker 自治执行；
- **互利共生**：人工纠偏数据反哺规则和模型，自动系统减少人工重复劳动。

### 反馈路径

```
人工在 _review 中修正分类/标签
   ↓
修正结果进入纠偏样本库
   ↓
定期增量训练分类模型 / 更新规则表
   ↓
配置中心生成新版本
   ↓
自检通过后发布
   ↓
归档系统功能熵下降
```

这样，归档系统不是一次性静态程序，而是持续从外部吸收“负熵”的耗散结构。

---

## 十、最终效果

- 引擎产出一旦生成，自动进入归档流程；
- 分类、打标签、目录存储全部自动化；
- 低置信度任务自动转入人工复核，不阻塞主流程；
- 配置修改可验证、可回滚；
- 模型调用有超时兜底，不拖垮归档；
- 人工纠偏持续降低系统功能熵，防止归档体系自然退化。

一句话总结：**自动归档系统是引擎的负熵输入，它的职责不是简单“存文件”，而是让引擎产出从“无序堆积”变成“有序可检索的知识资产”。**
