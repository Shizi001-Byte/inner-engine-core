# 任务类型: eng

针对V7.5方舟效能引擎在“多线程API调用后串行后处理”场景下的推演状态一致性问题，核心矛盾在于：**并发产生的推演事件（或结果）在进入串行化处理阶段时，由于时序不确定性、缓存可见性延迟以及状态读改写（RMW）的非原子性，导致最终引擎状态机紊乱。**

以下是为V7.5方舟效能引擎量身定制的完整锁机制与并发控制方案。

---

### 一、 竞态条件根因分析

在V7.5架构中，竞态主要发生在以下三个环节：
1. **结果提交竞态**：多个API工作线程同时完成计算，试图将推演结果写入待处理队列。
2. **状态读改写（RMW）竞态**：串行后处理线程在根据API结果更新引擎全局状态（如资源池、实体坐标、任务进度）时，若混入其他读操作，可能导致状态丢失或脏读。
3. **可见性延迟**：多核CPU缓存导致工作线程看到的引擎状态非最新，基于过期状态进行的推演产生错误结果。

---

### 二、 核心架构设计：生产者-消费者与状态隔离

为保证“多线程调用”与“串行后处理”的无缝衔接，采用**事件驱动+状态快照隔离**架构：

*   **API工作线程（生产者）**：执行无状态或基于只读快照的推演逻辑，生成包含上下文的 `EventContext` 对象，推入无锁/细粒度锁队列。
*   **后处理线程（消费者，单线程）**：从队列拉取 `EventContext`，串行执行状态变更。
*   **状态读写控制**：工作线程读取状态使用读写锁（`Shared Lock`），后处理线程更新状态使用排他锁（`Exclusive Lock`）。

---

### 三、 完整锁机制方案

#### 1. 提交阶段：无锁队列与CAS（解决提交竞态）
使用基于CAS（Compare-And-Swap）的无锁环形缓冲区替代传统的互斥锁队列，消除线程切换开销。

```cpp
// 伪代码：无锁环形队列提交
class LockFreeRingBuffer {
    std::atomic<int> head;
    std::atomic<int> tail;
    EventContext buffer[CAPACITY];

public:
    bool Push(const EventContext& event) {
        int current_tail = tail.load(std::memory_order_relaxed);
        int next_tail = (current_tail + 1) % CAPACITY;
        
        if (next_tail == head.load(std::memory_order_acquire)) {
            return false; // 队列满，工作线程执行退避或丢弃策略
        }
        
        // 尝试占用槽位
        while (!tail.compare_exchange_weak(current_tail, next_tail, 
                                          std::memory_order_acq_rel)) {
            current_tail = tail.load(std::memory_order_relaxed);
            next_tail = (current_tail + 1) % CAPACITY;
            if (next_tail == head.load(std::memory_order_acquire)) return false;
        }
        
        buffer[current_tail] = event; // 写入数据
        // 此时对消费者可见
        return true;
    }
};
```

#### 2. 排序阶段：序列号与等待锁（解决严格串行化）
如果V7.5要求API结果必须严格按照发起顺序进行后处理，则需引入序列号机制与条件变量。

```cpp
class SequencedProcessor {
    std::atomic<uint64_t> global_seq{0};
    std::unordered_map<uint64_t, EventContext> pending_results;
    std::mutex seq_mutex;
    std::condition_variable seq_cv;
    uint64_t expected_seq{0};

public:
    uint64_t GetSeq() {
        return global_seq.fetch_add(1, std::memory_order_relaxed);
    }

    void SubmitResult(uint64_t seq, EventContext&& result) {
        std::lock_guard<std::mutex> lock(seq_mutex);
        pending_results[seq] = std::move(result);
        seq_cv.notify_one(); // 唤醒消费线程
    }

    void ProcessLoop() {
        while (true) {
            std::unique_lock<std::mutex> lock(seq_mutex);
            seq_cv.wait(lock, [this]{ return pending_results.count(expected_seq); });
            
            EventContext event = std::move(pending_results[expected_seq]);
            pending_results.erase(expected_seq++);
            lock.unlock(); // 解锁后再进行耗时的状态更新
            
            ApplyStateChange(event); // 串行执行，无并发冲突
        }
    }
};
```

#### 3. 状态更新阶段：读写锁与状态分片（解决RMW竞态）
串行后处理线程更新状态时，可能与其他正在并发读取状态的API线程冲突。采用 `std::shared_mutex` 并结合状态分片降低锁粒度。

```cpp
// 状态分片管理器
class ShardStateMutex {
    static constexpr int SHARD_COUNT = 64;
    std::shared_mutex shard_mutexes[SHARD_COUNT];

public:
    std::shared_mutex& GetMutexForEntity(uint64_t entity_id) {
        return shard_mutexes[entity_id % SHARD_COUNT];
    }
};

// API工作线程：读取状态（共享锁）
EventContext ReadStateForAPI(ShardStateMutex& sm, uint64_t entity_id) {
    std::shared_lock<std::shared_mutex> lock(sm.GetMutexForEntity(entity_id));
    // 读取当前引擎状态
    return GenerateContext(entity_id, current_state);
}

// 串行后处理线程：更新状态（排他锁）
void ApplyStateChange(ShardStateMutex& sm, const EventContext& event) {
    std::unique_lock<std::shared_mutex> lock(sm.GetMutexForEntity(event.entity_id));
    // 执行状态变更逻辑
    current_state.update(event);
}
```

### 四、 针对V7.5引擎的高级优化策略

#### 1. 批处理与双缓冲机制
如果后处理逻辑极轻量但调用极频繁，单次加锁解锁开销过大。可采用双缓冲：
*   API线程写入 `Buffer A`（带自旋锁）。
*   当 `Buffer A` 满或达到时间片（如16ms）时，原子交换指针，API线程改写 `Buffer B`。
*   后处理线程锁住并清空 `Buffer A` 进行批量串行处理。这大幅减少了锁征用。

#### 2. 避免死锁的严格规范
*   **锁获取顺序**：如果在后处理中需要同时修改多个实体的状态，必须严格按照 `entity_id` 升序获取分片锁。
*   **锁不跨网络/IO**：在 `ApplyStateChange` 中，只做纯内存状态计算，任何需要写数据库或RPC调用的操作必须异步化，绝不能持有状态锁时进行网络等待。

#### 3. 内存序严格控制
在C++等底层语言中，必须明确内存序以防止指令重排导致的竞态：
*   生产者写入事件数据后，更新 `tail` 指针必须使用 `memory_order_release`。
*   消费者读取 `tail` 指针后，读取事件数据必须使用 `memory_order_acquire`。
*   保证数据写入对消费者绝对可见，防止后处理线程读到空指针或脏内存。

### 五、 方案总结与实施路径

| 场景 | 推荐机制 | 解决的问题 | 性能影响 |
| :--- | :--- | :--- | :--- |
| **高频结果提交** | 无锁环形队列 (CAS) | 消除互斥锁上下文切换开销 | 极低，适用于多线程高并发 |
| **严格时序依赖** | 序列号+条件变量 | 保证推演结果按API发起顺序处理 | 中，存在等待间隙 |
| **状态并发读/独占写** | 读写锁+状态分片 | 解决RMW竞态，避免读线程阻塞 | 低，分片降低碰撞概率 |
| **超高吞吐场景** | 双缓冲+批量后处理 | 减少锁获取频率，压榨CPU缓存 | 会有微小延迟（微秒级） |

**实施建议**：
1. 首先剥离V7.5后处理逻辑中的副作用，确保其变为纯内存状态计算。
2. 引入无锁队列替代原有的 `std::mutex` 保护队列。
3. 对引擎全局状态进行拆分，使用分片读写锁替换全局大锁。
4. 通过压测工具（如模拟1000线程并发API调用）验证状态一致性，确保无死锁及状态丢失。
