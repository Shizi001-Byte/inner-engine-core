# 任务类型: eng

基于你的锚点，推演出的自动归档系统设计如下：

## 一句话结论

**自动归档系统 = 决策层生成“归档契约”，执行层只做契约的机械执行。**  
“任务自动分类、打标签、存入对应目录”不是执行层自己发挥出来的，而是决策层先定好的一张“列契约表”。

---

## 1. 先校准锚点：定义归档契约

这是整个系统的“列”，所有任务都必须按这张表走：

| task_type | required_metadata | tags | target_dir |
|---|---|---|---|
| invoice | amount, vendor | finance/invoice | `/archive/finance/invoice` |
| ticket | priority, owner | support/{priority} | `/archive/support/{priority}` |
| unknown | - | needs_review | `/archive/_manual/` |

执行层看到任务后，不能自己写 `if title contains "发票": 归到 finance`。  
因为那就是“简化版 SQL”，等于把列映射推给执行层去猜，必然出现列不匹配。

---

## 2. 决策串行：schema → 评审 → 脚本

- **schema**：先明确任务有哪些字段，哪些字段参与分类、打标签、目录映射。
- **评审**：检查映射是否完整，例如：
  - 每个 `task_type` 是否有非空 `target_dir`
  - 每个 `target_dir` 是否依赖了必填字段
  - 是否存在无法判断的默认路径
- **脚本**：根据评审后的契约，生成唯一可执行的归档脚本。

只有决策层完成这三步，执行层才能开始。

---

## 3. 执行并发：不自行简化

各任务可以并行跑，但必须遵守：

- 所有 worker 使用同一个生成的脚本
- 不允许 worker 本地改写规则
- 不允许跳过 `required_metadata`
- 不允许把未知类型默认丢进 `other`

如果任务缺少字段，或者类型不在契约表中，就直接进入 `needs_review`，而不是由执行层猜一个目录。

---

## 4. 配置修改后必须立即生效

防止“配置改了，行为没变化”。

设计方式：

- 所有分类规则、标签规则、目录映射都放在配置表里
- 配置更新时，必须**原子切换配置读取点**
- 切换后立即跑一个 `smoke_task` 验证：

```text
输入样例任务
→ 断言分类是否正确
→ 断言标签是否正确
→ 断言目录是否正确
→ 失败则自动回滚
```

这样每次配置变更，都会有一个“立即验证”动作，而不是等线上任务跑出来才发现没生效。

---

## 5. API 超时：按模型分档

自动分类/打标签如果依赖外部模型，需要设置合理 timeout：

- B 模型 turbo：300 秒
- A 模型：600 秒

任务总 deadline 不能等于 API timeout，必须留出写盘、日志、异常处理时间。

超时后的任务不能丢弃，应该进入：

```text
/archive/_manual/timeout/
```

并打上标签：

```text
api_timeout
```

这样超时是可观测、可重试、可人工处理的，而不是静默失败。

---

## 6. 验证闭环：先校准锚点，再优化链路

- 批处理前：用样本任务跑一遍契约，确认分类/标签/目录都正确
- 批处理后：核对各目录文件数、标签分布是否符合预期
- 如果链路性能不够，先看契约是否足够清晰，再谈并发优化

---

所以，设计引擎产出的自动归档系统，最终交付的不应该是一堆“移动文件”的脚本，而是一套：

```text
契约表 + 评审规则 + 生成的归档脚本 + 配置生效验证 + 超时兜底
```

任务自动分类、打标签、存入对应目录，只是这套契约机制的执行结果。
