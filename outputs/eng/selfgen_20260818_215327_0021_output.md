# 任务类型: eng

基于【已有认知锚定】与【避坑提醒】，针对V7.5方舟效能引擎中“多线程API调用后串行后处理”的架构，我们将严格贯彻**“先校准锚点再优化链路”**原则，运用**“精气神三元迁移框架”**，推演Supabase记忆脑的增量同步方案。

在“决策串行、执行并发”的架构下，Supabase记忆脑的增量同步（本地文件变化检测、只同步变更部分、处理冲突）必须解决**“并发执行层的无序变更产生” vs “串行决策层的锚点校验与状态闭环”**这一核心矛盾。以下是推演方案：

### 第一阶段：先校准锚点（同步前安全校验）
在触发任何Supabase同步动作前，主线程必须先完成锚点校准，彻底规避历史踩坑经验：
1. **配置锚点校验**：确认Supabase的`Table`与`Schema`读写点配置一致，避免“配置修改后未生效”的致命坑。
2. **质量检测锚点校验**：对多线程API回调的产物进行分类校验。**B模型(turbo)跳过reasoning占比检测**（允许70-82%直接放行），A模型执行严格检测。防止废稿误杀导致记忆脑写入空数据或错误重试。
3. **超时锚点校验**：确认生成产物是否在规定时间内返回（B模型turbo 300秒，A模型 600秒），超时数据不进入同步队列。

---

### 第二阶段：精气神三元增量同步方案推演

#### 1. 【精】本地状态感知层（执行层 / 并发 / 精）：文件变化检测与差分提取
**核心目标**：在并发无序的文件写入中，精准捕获“变更部分”，避免全量同步导致的性能开销与超时。
* **变更检测机制（基于Hash与时间戳）**：
  * 并发线程写入L4成品库（sop/code/checklist）时，附带生成`content_hash`（如MD5）与`updated_at`。
  * 检测器定时或事件触发扫描，将本地文件的`content_hash`与Supabase记忆脑中维护的`last_sync_hash`对比。不一致即为“变更部分”。
* **差分队列生成**：
  * 将变更的文件封装为`Sync_Item`，推入`Sync_Queue`。
  * **防断流设计**：严格标记`item_type`（sop/code/checklist），防止L4成品转化仅同步sop类型而导致code/checklist断流。

#### 2. 【气】增量流控传输层（传输层 / 异步 / 气）：只同步变更部分
**核心目标**：高效传输，避免因大批量数据交互导致API调用超时（规避坑库预警）。
* **增量Upsert流控**：
  * 从`Sync_Queue`取出`Sync_Item`，只将变更的JSON payload发送至Supabase的Edge Function或直接Upsert至表。
  * **超时隔离**：同步Supabase的网络请求timeout独立于模型API（模型B用300s/A用600s），Supabase同步timeout预设为30秒。若同步超时，该`Sync_Item`重回队列重试，不阻塞主线程。
* **分片提交**：若并发回调产生大量变更，按10条/批进行分片Upsert，防止Supabase连接池打满。

#### 3. 【神】Supabase记忆脑状态闭环（决策层 / 主线程 / 串行 / 神）：冲突处理与状态写竞态
**核心目标**：解决“状态写竞态”与“锚点校准失败”，确保多线程回调不会越权修改全局状态。
* **竞态现象预防（串行写入锁）**：
  * 并发线程检测到本地文件变化后，**绝对禁止直接调用Supabase API写入**。
  * 必须由主线程（神）串行地消费`Sync_Queue`。主线程加锁（`is_syncing`状态位），依次处理sop、code、checklist的同步。
* **冲突处理机制（乐观锁与版本号）**：
  * Supabase表中为每条记忆增加`version`字段。
  * 本地提交同步时，携带`expected_version`。Supabase通过Postgres的`UPDATE ... WHERE version = expected_version`进行原子操作。
  * **冲突触发场景**：若多线程导致同一份sop被两次修改，或本地与云端版本不一致，Supabase返回受影响行数为0。
  * **冲突解决策略**：
    1. 主线程捕获冲突，暂停该条目的同步。
    2. 拉取云端最新版本，与本地版本进行三向合并（基础版、本地版、云端版）。
    3. 若无法自动合并（如code逻辑冲突），标记为`conflict_pending`，抛出人工或更高优先级决策层处理，确保L4成品库的绝对一致性。

### 总结闭环
通过**【精】的Hash差分检测**过滤了无变化的文件，通过**【气】的分片增量Upsert**避免了同步超时，最终所有变更汇聚到**【神】的主线程串行队列**中加锁执行。主线程严格把控sop/code/checklist的类型定义与版本号冲突处理，彻底解决了“并发执行层无序返回”导致的“状态写竞态与L4断流”问题。
