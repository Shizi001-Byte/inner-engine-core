# 任务类型: eng

针对Supabase作为“记忆脑”后端的增量同步方案，核心挑战在于**本地与云端的双向一致性**。由于记忆脑通常包含大量碎片化文件（如Markdown笔记、JSON向量数据），全量同步不仅效率低下，还会消耗大量带宽和API请求。

以下是为您推演的增量同步方案，包含数据模型、变化检测、增量传输、冲突处理的完整算法与伪代码。

---

### 一、 数据结构与状态模型

为了支持增量同步，我们需要在本地维护一个**同步状态表**，并在Supabase建立对应的元数据字段。

#### 1. Supabase 数据表设计 (`memories`)
```sql
CREATE TABLE memories (
  id UUID PRIMARY KEY,
  user_id UUID REFERENCES auth.users,
  file_path TEXT NOT NULL,         -- 逻辑路径，如 "folder/note.md"
  content TEXT,                   -- 实际内容
  content_hash TEXT NOT NULL,     -- 内容的SHA-256哈希值
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  is_deleted BOOLEAN DEFAULT FALSE, -- 软删除标志
  version INTEGER DEFAULT 1       -- 乐观锁版本号
);
```

#### 2. 本地状态追踪 (Local Manifest - SQLite/JSON)
本地需维护一个清单，记录每个文件的最后已知云端状态：
```json
{
  "folder/note.md": {
    "local_hash": "a1b2c3...",
    "remote_hash": "a1b2c3...",
    "remote_version": 5,
    "last_sync": "2023-10-27T10:00:00Z"
  }
}
```

---

### 二、 变更检测算法

检测本地变化不用扫描文件内容，而是依赖**文件系统属性**与**哈希比对**。

**算法逻辑：**
1. 遍历本地记忆库目录。
2. 获取文件的 `mtime`（修改时间）。
3. 若 `mtime` 大于本地 Manifest 记录的 `last_sync`，或本地 Manifest 中无此文件，则计算文件内容的 SHA-256 哈希值。
4. 比较新计算的哈希值与 Manifest 中的 `local_hash`。若不同，则标记为 **LOCAL_MODIFIED**。
5. 本地存在但 Manifest 中不存在的文件，标记为 **LOCAL_CREATED**。
6. Manifest 中存在但本地文件系统中不存在的文件，标记为 **LOCAL_DELETED**。

---

### 三、 冲突处理策略

采用**乐观锁与 Last-Write-Wins (LWW) 结合**的策略，辅以冲突备份。

**冲突场景**：本地准备推送修改时，发现 Supabase 中的 `version` 已经被其他设备修改（即 `remote_version` 不匹配）。
**处理方案**：
1. 触发冲突解决机制。
2. 比较 `updated_at` 时间戳。时间较晚的一方获胜。
3. **不丢弃数据**：将失败的一方内容另存为新文件（如 `note (conflict copy 20231027).md`），并将其标记为待同步状态。

---

### 四、 核心伪代码实现

以下是同步引擎的完整伪代码（TypeScript 风格）：

```typescript
// 全局变量
const LOCAL_DIR = "/path/to/memory_brain";
const LOCAL_MANIFEST = loadLocalManifest(); // 读取本地状态

// --- 1. 同步主流程 ---
async function syncMemoryBrain() {
    // 第一步：拉取远程变更并应用到本地
    await pullRemoteChanges();
    
    // 第二步：检测本地变更
    const localChanges = detectLocalChanges();
    
    // 第三步：推送本地变更到 Supabase
    await pushLocalChanges(localChanges);
    
    // 第四步：保存最新状态
    saveLocalManifest(LOCAL_MANIFEST);
}

// --- 2. 本地变更检测 ---
function detectLocalChanges() {
    const changes = [];
    const currentFiles = scanFileSystem(LOCAL_DIR); // 返回 {path, mtime, content}
    
    // 检测新建和修改
    for (const file of currentFiles) {
        const manifestRecord = LOCAL_MANIFEST[file.path];
        
        // 优化：mtime未变则跳过哈希计算
        if (manifestRecord && manifestRecord.last_sync > file.mtime) {
            continue;
        }
        
        const currentHash = sha256(file.content);
        
        if (!manifestRecord) {
            changes.push({ path: file.path, content: file.content, hash: currentHash, action: "CREATE" });
        } else if (manifestRecord.local_hash !== currentHash) {
            changes.push({ path: file.path, content: file.content, hash: currentHash, action: "UPDATE" });
        }
    }
    
    // 检测删除
    for (const path in LOCAL_MANIFEST) {
        if (!currentFiles[path]) {
            changes.push({ path: path, action: "DELETE" });
        }
    }
    
    return changes;
}

// --- 3. 拉取远程变更 ---
async function pullRemoteChanges() {
    // 获取本地最大的 last_sync 时间
    const lastSyncTime = getMaxLastSyncTime(LOCAL_MANIFEST);
    
    // 查询 Supabase 中该时间之后更新的记录
    const { data: remoteUpdates } = await supabase
        .from('memories')
        .select('*')
        .gt('updated_at', lastSyncTime);
        
    for (const remote of remoteUpdates) {
        const local = LOCAL_MANIFEST[remote.file_path];
        
        if (remote.is_deleted) {
            // 远程已删除，删除本地文件
            deleteLocalFile(remote.file_path);
            delete LOCAL_MANIFEST[remote.file_path];
        } else {
            // 远程有更新
            if (!local || local.remote_hash !== remote.content_hash) {
                writeLocalFile(remote.file_path, remote.content);
                // 更新本地 Manifest
                LOCAL_MANIFEST[remote.file_path] = {
                    local_hash: remote.content_hash, // 拉取后本地与远程一致
                    remote_hash: remote.content_hash,
                    remote_version: remote.version,
                    last_sync: getCurrentTime()
                };
            }
        }
    }
}

// --- 4. 推送本地变更 (含冲突处理) ---
async function pushLocalChanges(changes) {
    for (const change of changes) {
        if (change.action === "DELETE") {
            // 软删除：更新 Supabase 状态
            await supabase.from('memories')
                .update({ is_deleted: true, updated_at: getCurrentTime(), version: supabase.rpc('increment_version') })
                .eq('file_path', change.path);
            delete LOCAL_MANIFEST[change.path];
            continue;
        }
        
        // CREATE 或 UPDATE
        const manifestRecord = LOCAL_MANIFEST[change.path];
        const expectedVersion = manifestRecord ? manifestRecord.remote_version : 0;
        
        // 尝试 Upsert，带上乐观锁条件 (expected_version)
        const { data, error } = await supabase.rpc('upsert_memory', {
            p_path: change.path,
            p_content: change.content,
            p_hash: change.hash,
            p_expected_version: expectedVersion
        });
        
        if (error && error.code === 'CONFLICT_DETECTED') {
            // 触发冲突解决
            await handleConflict(change);
        } else if (data) {
            // 推送成功，更新本地 Manifest
            LOCAL_MANIFEST[change.path] = {
                local_hash: change.hash,
                remote_hash: change.hash,
                remote_version: data.new_version,
                last_sync: getCurrentTime()
            };
        }
    }
}

// --- 5. 冲突解决机制 ---
async function handleConflict(localChange) {
    // 1. 获取最新的远程数据
    const { data: remote } = await supabase.from('memories')
        .select('*').eq('file_path', localChange.path).single();
        
    // 2. 策略：保留双方内容，将本地内容重命名为冲突文件
    const conflictPath = `${localChange.path}.conflict.${Date.now()}`;
    writeLocalFile(conflictPath, localChange.content);
    
    // 3. 强制将本地原路径文件同步为远程最新状态
    writeLocalFile(localChange.path, remote.content);
    
    // 4. 更新本地 Manifest 为远程状态
    LOCAL_MANIFEST[localChange.path] = {
        local_hash: remote.content_hash,
        remote_hash: remote.content_hash,
        remote_version: remote.version,
        last_sync: getCurrentTime()
    };
    
    // 5. 将新生成的冲突文件加入待同步队列（下一轮循环会将其作为新文件上传）
    // 这样既不丢失用户的本地修改，又保证了主路径的一致性
}
```

### 五、 Supabase 端配合 (PostgreSQL RPC)

为了实现乐观锁和原子性操作，建议在 Supabase 创建一个 RPC 函数：

```sql
CREATE OR REPLACE FUNCTION upsert_memory(
  p_path TEXT,
  p_content TEXT,
  p_hash TEXT,
  p_expected_version INT
)
RETURNS TABLE(new_version INT) AS $$
DECLARE
  current_version INT;
  new_ver INT;
BEGIN
  -- 获取当前版本号
  SELECT version INTO current_version FROM memories WHERE file_path = p_path;
  
  -- 乐观锁检查：如果记录已存在且版本号不匹配，则抛出冲突
  IF current_version IS NOT NULL AND current_version != p_expected_version THEN
    RAISE EXCEPTION 'CONFLICT_DETECTED';
  END IF;
  
  -- 执行 Upsert
  INSERT INTO memories (file_path, content, content_hash, version, updated_at, is_deleted)
  VALUES (p_path, p_content, p_hash, COALESCE(current_version, 0) + 1, NOW(), FALSE)
  ON CONFLICT (file_path) DO UPDATE
  SET content = EXCLUDED.content,
      content_hash = EXCLUDED.content_hash,
      version = EXCLUDED.version,
      updated_at = EXCLUDED.updated_at,
      is_deleted = FALSE
  RETURNING version INTO new_ver;
  
  RETURN QUERY SELECT new_ver;
END;
$$ LANGUAGE plpgsql;
```

### 六、 方案优化点总结

1. **mtime 优化**：遍历本地文件时，优先比对文件修改时间，避免频繁读取大文件并计算 Hash。
2. **软删除机制**：不执行物理删除，通过 `is_deleted = true` 标记，避免其他设备同步时出现“删除操作复活文件”的问题。
3. **冲突不阻断**：遇到冲突时，不直接报错终止同步，而是将冲突内容另存为新文件，保证整个同步流程顺利结束，由用户后续决定如何合并冲突文件。
4. **向量数据兼容**：如果“记忆脑”包含向量化数据，可将 RAG 向量也存入 `memories` 表或关联表中。当拉取到新文本内容时，触发 Supabase Edge Function 重新计算 embedding，实现增量向量化。
