# 任务类型: eng

基于已有锚定，不重复论证；直接给出可落地的三方同步自动化设计。

---

## 0. 设计定位

把一次“重大变更”视为一次**广域分布式状态机跃迁**：

- `Gitee`：代码/配置的事实源投影
- `飞书`：人工可读文档/文件投影
- `Supabase`：运行时认知池/对象存储投影

三方同步不是三个独立上传脚本，而是同一个状态机在三个投影面上的幂等收敛。

同时补上“8月欠账”的根因：**同步缺失、不可验证**。  
所以本方案强制要求：每次同步后必须回读验证，配置修改后必须 `sync --check` 验证生效。

---

## 1. 总体架构

```text
引擎/CI 检测到重大变更
        │
        ▼
生成 manifest.json（唯一事实源）
        │
        ▼
写入 outbox 事件表
        │
        ▼
Sync Orchestrator 消费事件
        │
        ├──→ Gitee Worker：代码提交
        ├──→ 飞书 Worker：文件上传
        └──→ Supabase Worker：对象存储 + 认知池指针更新
        │
        ▼
Verify：三方回读校验
        │
        ▼
更新 sync_state 账本
```

事件投递是 **at-least-once**，所以所有写操作必须幂等。

## 2. 数据契约

### manifest.json

```json
{
  "artifact_id": "uuid",
  "version": "1.4.0",
  "type": "code | doc | knowledge",
  "content_hash": "sha256",
  "parent_artifact_id": "上一个 artifact_id",
  "changed_paths": [],
  "schema_hash": "schema migration 的哈希",
  "timestamp": "2026-04-17T00:00:00Z"
}
```

### sync_state 表

```sql
create table if not exists sync_state (
  idempotency_key text primary key,
  artifact_id text not null,
  sink text not null,           -- gitee / feishu / supabase
  sink_ref text,                -- commit sha / file_token / object path
  content_hash text not null,
  status text not null,         -- pending / success / failed / conflict
  last_error text,
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);
```

每次执行前查 `sync_state`：

```text
if exists(idempotency_key, sink, status='success'):
    return  // 已经做过，直接跳过
```

## 3. Gitee 代码提交

### 3.1 流程

1. 拉取远端最新状态：
   ```bash
   git fetch origin
   git ls-remote origin refs/heads/main
   ```
2. 检查远端是否已经包含本次 `artifact_id`：
   - 如果 `sync_state` 已有该 `artifact_id` 的 Gitee success 记录，直接返回。
   - 如果远端 commit message 中包含该 `artifact_id`，直接复用。
3. 否则：
   - 基于当前 `main` 创建分支 `release/{version}`
   - 应用变更
   - 提交，commit message 固定格式：
     ```text
     chore(engine): sync {artifact_id} {version} hash={content_hash}
     ```
4. 推送到 Gitee：
   ```bash
   git push origin release/{version}
   ```
5. 如果需要，自动创建 PR 到 `main`。

### 3.2 幂等性

- `idempotency_key = gitee:{artifact_id}`
- 通过 `sync_state` 判断是否已提交
- 通过 commit message 中的 `artifact_id` 防止重复提交
- 通过 `git merge-base --is-ancestor` 判断 commit 是否已在远端

### 3.3 冲突处理

- 如果远端 `main` 已经前移，且不是 fast-forward：
  - 不要强推。
  - 自动 rebase；
  - rebase 冲突则放弃自动合并，保留本地分支，标记 `conflict`，通知人工处理。
- 如果 Gitee 上有其他开发者提交：
  - 自动创建 PR，而不是直接写 `main`。

## 4. 飞书文件上传

### 4.1 流程

1. 获取 `tenant_access_token`，不依赖扫码。
2. 根据 `manifest.type` 确定目标文件夹 token。
3. 搜索目标文件夹内是否已有同名文件：
   - 文件名规则：
     ```text
     {type}-{version}-{hash8}.{ext}
     ```
   - 例如：
     ```text
     knowledge-report-1.4.0-a1b2c3d4.md
     ```
4. 如果不存在：上传新文件。
5. 如果存在且 `sync_state` 中 `content_hash` 一致：跳过。
6. 如果存在但 hash 不同：
   - 检查飞书文件 `modified_time` 是否晚于上次同步时间；
   - 若未被人工修改：上传新版本文件；
   - 若已被人工修改：**不覆盖**，上传为 `{type}-{version}-conflict-{timestamp}.{ext}`，并告警。

### 4.2 幂等性

- `idempotency_key = feishu:{artifact_id}`
- 文件名中带 `content_hash` 短哈希，天然避免重复上传
- `sync_state` 中记录 `file_token`，下次直接校验

### 4.3 冲突处理

- 飞书文件可被人工编辑，因此飞书**不是事实源**，只是投影。
- 人工修改与引擎产出冲突时：
  - 不自动覆盖人工版本；
  - 生成冲突副本；
  - 通过飞书消息或任务通知管理员处理。

> 避坑：若将来接飞书连接器扫码，绑定前先确认客户端是最新版本、页面放大到最大、豆包账号已登录；自动化环境尽量用应用凭据，避免扫码。

## 5. Supabase 存储同步

### 5.1 对象存储布局

```text
engine/{type}/{artifact_id}/{filename}      -- 不可变对象
engine/{type}/latest.json                   -- 可变指针（或使用 Postgres 表）
```

不可变对象路径中包含 `artifact_id`，因此同一个 artifact 永远不会重复写入。

### 5.2 认知池指针

Supabase 存储本身没有 CAS，所以用 Postgres 表做指针：

```sql
create table if not exists sync_pointer (
  type text primary key,
  current_artifact_id text,
  current_version text,
  content_hash text,
  updated_at timestamptz default now()
);

create table if not exists artifact_versions (
  artifact_id text primary key,
  version text,
  type text,
  parent_artifact_id text,
  content_hash text,
  created_at timestamptz default now()
);
```

同步步骤：

1. 上传不可变对象：
   ```http
   POST /storage/v1/object/engine/{type}/{artifact_id}/{filename}
   x-upsert: false
   ```
2. 如果返回 `Duplicate`，说明已经上传过，跳过。
3. 写入 `artifact_versions`：
   ```sql
   insert into artifact_versions (...)
   values (...)
   on conflict (artifact_id) do nothing;
   ```
4. 更新指针，只允许向前移动：

```sql
update sync_pointer
set current_artifact_id = :artifact_id,
    current_version = :version,
    content_hash = :content_hash,
    updated_at = now()
where type = :type
  and (
    current_artifact_id is null
    or current_artifact_id = :parent_artifact_id
    or current_version < :version
  );
```

如果 `update` 影响行数为 0，说明该 artifact 不是当前指针的后继，也不是更高版本，则标记冲突，不覆盖当前认知池。

### 5.3 幂等性

- `idempotency_key = supabase:{artifact_id}`
- 不可变对象以 `artifact_id` 为路径，天然幂等
- Postgres 表用主键去重
- 指针更新通过条件 `where` 保证不会回退

### 5.4 冲突处理

- 两个并发 artifact 都声称是 `latest` 时：
  - 两者都保存为不可变对象；
  - 指针不被错误更新；
  - `sync_state` 中记录 `conflict`；
  - 等待合并后的新 artifact 来推进指针。

## 6. 三方同步的顺序与失败恢复

推荐顺序：

```text
Gitee → 飞书 → Supabase
```

原因：

- Gitee 是代码事实源，先提交，后续失败可追溯；
- 飞书是人工投影，成功后便于告警；
- Supabase 是最终认知池，最后更新指针，避免“对象上传了但代码还没提交”的中间态。

失败恢复：

- 如果 Gitee 成功、飞书失败：不重推 Gitee，只重试飞书。
- 如果飞书成功、Supabase 失败：不重传飞书，只重试 Supabase。
- 每次重试使用同一个 `idempotency_key`。
- 重试 3 次仍失败：标记 `failed`，发飞书告警。

---

## 7. 幂等性总表

| 操作 | 幂等键 | 重复执行结果 | 冲突处理 |
|---|---|---|---|
| Gitee 提交 | `gitee:{artifact_id}` | 跳过，或复用已有 commit | rebase/PR，不覆盖远端 |
| 飞书上传 | `feishu:{artifact_id}` | 跳过，或复用已有 file_token | 不覆盖人工修改，生成 conflict 副本 |
| Supabase 对象上传 | `supabase:{artifact_id}:{path}` | 返回 Duplicate，跳过 | 不覆盖不可变对象 |
| Supabase 指针更新 | `supabase:{artifact_id}:pointer` | 条件更新不满足则跳过 | 保留旧指针，标记 conflict |

## 8. 验证机制（防“配置修改后未生效”）

每次同步完成后必须执行 `verify`：

| 目标 | 验证方式 |
|---|---|
| Gitee | `git fetch && git rev-parse origin/main` 是否等于期望 commit |
| 飞书 | 通过 file_token 拉取文件元数据，比对名称/修改时间/大小 |
| Supabase | 查询 `sync_pointer` 和 `artifact_versions`，比对 content_hash |

验证不通过：

- `sync_state.status = failed`
- 自动重试
- 重试仍失败则告警

配置管理：

- 所有目标分支、飞书文件夹、Supabase bucket、超时配置统一放在 `sync.config.json`
- 每次修改配置后必须跑：
  ```bash
  sync --check
  ```
- 不通过不允许发布。

---

## 9. 超时规范

根据避坑要求，显式预设超时：

| 场景 | 超时 |
|---|---|
| Gitee API / git push | 30s |
| 飞书普通上传 | 300s |
| 飞书大文件分片上传 | 600s |
| Supabase 对象上传 | 600s |
| 同步链路中若有模型调用（摘要/提交说明生成） | B 系列 turbo 300s，A 系列 600s |

超时不靠“无限等”，而是进入重试队列；重试超过 3 次直接失败告警。

---

## 10. 最终效果

- 每次重大变更后，Gitee、飞书、Supabase 自动收敛到同一个 `manifest` 状态；
- 重复触发不会产生重复提交、重复文件、重复对象；
- 人工修改不会被自动覆盖；
- 同步结果可验证，配置修改可立即验证生效；
- 不消耗日供给 400 万 Token 的语义算力做无意义的同步动作；若确需模型参与，严格按 300s/600s 超时控制。
