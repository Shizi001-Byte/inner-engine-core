# 任务类型: eng

## 推演结论

增量同步的本质不是“少传文件”，而是：**以 `(file_path, chunk_id, revision)` 为锚点，做状态对齐**。  
所以顺序必须是：

> **先校准锚点，再优化链路。**

没有稳定锚点，增量同步一定会退化成全量同步；没有 revision，冲突处理就是猜。

---

## 一、先定义契约锚点

### 1. 远端表结构

Supabase 中一张表负责存记忆块：

```sql
create table if not exists memory_chunks (
  file_path text not null,
  chunk_id text not null,
  chunk_index int not null,
  content text not null,
  content_hash text not null,
  metadata jsonb not null default '{}'::jsonb,
  embedding vector(1536),
  revision bigint not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  primary key (file_path, chunk_id)
);
```

这里的唯一键就是锚点：

```text
(file_path, chunk_id)
```

`revision` 是远端版本号，本地每次同步时记录自己上次同步到的版本，作为冲突检测依据。

### 2. 本地 manifest

本地维护一份同步清单，例如 `.membrain/manifest.json`：

```json
{
  "files": {
    "project.md": {
      "content_hash": "sha256:...",
      "chunks": [
        {
          "chunk_id": "project.md::目标",
          "content_hash": "sha256:...",
          "base_revision": 2
        }
      ]
    }
  }
}
```

`base_revision` 就是“上次同步时，远端这个 chunk 的 revision”。

## 二、检测本地文件变化

### 1. 文件监听 + 周期扫描

- 使用 `chokidar` 监听本地文件变化。
- 忽略临时文件：`.tmp`、`.swp`、`.DS_Store`、`.membrain/`。
- 文件事件触发后，做 1~2 秒 debounce，避免文件写入过程中被读取。
- 同时每 5 分钟做一次全量扫描，防止监听事件丢失。

### 2. 用 hash 判断变化，不要只信 mtime

mtime 可能因为 `git checkout`、`touch` 等原因变化，但内容没变。

所以：

```text
mtime 变化 -> 进入待检查队列
content_hash 变化 -> 才认为是真正变化
```

### 3. 生成变更集

对本地文件与 manifest 做 diff：

- 新增文件 → 所有 chunk 为 `upsert`
- 删除文件 → 所有 chunk 为 `delete`
- 修改文件 → 只 diff 出内容变化的 chunk
- 同一 chunk 内容 hash 没变 → 跳过

## 三、只同步变更部分

### 1. 变更集结构

```ts
type Change =
  | {
      op: 'upsert';
      filePath: string;
      chunkId: string;
      chunkIndex: number;
      content: string;
      contentHash: string;
      metadata: Record<string, unknown>;
      baseRevision: number;
    }
  | {
      op: 'delete';
      filePath: string;
      chunkId: string;
      baseRevision: number;
    };
```

只有这些变更项会进入执行阶段。

### 2. 只重算变更 chunk 的 embedding

- 内容没变的 chunk，不调用 embedding API。
- 内容变化的 chunk，才重新生成 embedding。
- 如果只是 metadata 变化，内容没变，则只更新 metadata，不重算 embedding。

### 3. 严格按契约写 Supabase

不要在执行层拼接简化 SQL，否则会重蹈“列不匹配”的坑。

应该把写操作收敛到唯一 RPC 或 repository 层，例如：

```sql
sync_upsert_chunk(
  p_file_path text,
  p_chunk_id text,
  p_chunk_index int,
  p_content text,
  p_content_hash text,
  p_embedding vector,
  p_metadata jsonb,
  p_base_revision bigint
)
```

逻辑：

```text
1. select revision from memory_chunks where file_path=? and chunk_id=? for update;
2. if row 不存在:
     insert
3. else if revision == p_base_revision:
     update，revision = revision + 1
4. else:
     返回冲突
```

删除类似：

```sql
sync_delete_chunk(
  p_file_path text,
  p_chunk_id text,
  p_base_revision bigint
)
```

执行阶段可以并发，但**每个任务都不得自己猜列映射**。

## 四、处理冲突

### 1. 冲突定义

本地 manifest 中记录的 `base_revision`，与远端当前 `revision` 不一致，就是冲突。

例如：

- 本地改了某个 chunk，base_revision = 2
- 远端当前 revision = 3
- 说明有其他端改过这个 chunk

### 2. 冲突策略

| 策略 | 行为 | 适用场景 |
|---|---|---|
| `local-wins` | 本地覆盖远端；先把远端版本归档到 `.membrain/conflicts/` | 本地是权威 |
| `remote-wins` | 远端覆盖本地；用远端内容更新本地文件，并更新 manifest | 远端/团队是权威 |
| `manual` | 不自动覆盖；写冲突文件和审计记录，等待人工处理 | 默认/高风险记忆 |

### 3. 防止同步死循环

`remote-wins` 时，必须做两件事：

1. 把远端内容写回本地文件
2. 更新 manifest 的 `content_hash` 和 `base_revision`

否则下一轮扫描会发现本地文件又与 manifest 不一致，导致反复冲突。

`manual` 时，在 manifest 中标记该 chunk 为 `conflict`，同步引擎跳过它，直到人工处理完成。

## 五、决策串行，执行并发

```text
决策层（串行）：
  扫描文件 -> diff -> 生成变更集 -> 生成 sync task

执行层（并发）：
  每个 task 独立执行 upsert/delete
```

这样能保证：

- 列映射、chunk_id、base_revision 在决策层一次性确定
- 执行层只负责按契约执行，不允许自行简化

## 六、避坑落地

### 1. 配置修改后必须立即生效

每次同步周期都重新读取配置，不能启动时缓存。

新增配置项时，必须同步修改读取点。修改配置后，执行一次：

```bash
sync --verify --dry-run
```

确认实际生效的配置符合预期。

### 2. API 超时按任务类型设置

不要用全局默认 timeout。

- B 模型 turbo 任务：300 秒
- A 模型任务：600 秒
- embedding API：30 秒
- Supabase 写操作：30 秒

超时后做指数退避重试，但不要无限重试。

### 3. B 模型质量检测独立

B 模型 turbo 的 reasoning 占比 70%～82% 是正常特性，不能判定为废稿。

所以：

- B 模型跳过 reasoning 占比检测
- 改用输出结构校验、必填字段校验
- 不要用 A 模型的废稿阈值去套 B 模型

## 七、整体同步伪代码

```ts
async function syncMemoryBrain() {
  const config = await loadConfig();          // 每次重新读取
  const manifest = await loadManifest();

  const currentFiles = await scanLocalFiles(config);

  // 决策串行
  const changes = diffLocalToManifest(currentFiles, manifest, config);

  if (changes.length === 0) return;

  // 生成任务，仍然串行
  const tasks = await planTasks(changes, config);

  // 执行并发
  await runTasks(tasks, {
    concurrency: config.syncConcurrency ?? 5,
    onSuccess: (task, result) => {
      updateManifest(manifest, task, result.newRevision);
    },
    onConflict: (task, remote) => {
      resolveConflict(task, remote, config.conflictPolicy);
    }
  });

  await saveManifest(manifest);
}
```

## 最后

这套方案的核心不是“增量算法”，而是：

> **锚点先定死，增量才可信。**

只要 `(file_path, chunk_id, revision)` 这个锚点一致，列映射不丢，冲突能检测，那么增量同步就是稳定的。  
在此基础上，再优化监听效率、并发数、API timeout，才有意义。
