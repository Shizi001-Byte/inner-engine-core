# 任务类型: eng

按这些锚定直接推演，不重复论证，给一个可落地的自动归档系统设计。

## 一句话形态

**自动归档系统 = 本地事件日志 + 分类器 + 目录投影 + Supabase 索引 + 摩擦循环。**

目录只是投影，不是真相；真正的真相是“决策事件 + 全局顺序”。

---

## 1. 核心数据模型

### 本地优先

```text
archive_root/
  _inbox/                          # 未分类 / 低置信度
  _friction/                       # 分类冲突 / 超时 / 规则摩擦
  by_type/
    task/{project}/{yyyy}/{mm}/{task_id}.md
    decision/{project}/{yyyy}/{mm}/{decision_id}.json
  .local/
    events.jsonl                   # 追加式决策事件
    index.sqlite                   # 本地可检索索引
```

### Supabase 远端

```sql
-- 决策事件表：不可变，追加式
create table archive_events (
  id uuid primary key default gen_random_uuid(),
  global_seq bigserial unique,
  client_id text not null,
  local_seq bigint not null,
  parent_event_id uuid references archive_events(id),
  event_type text not null,        -- task_archived / rearchived / policy_updated / friction_recorded
  task_id text,
  payload jsonb not null,          -- 分类结果、标签、路径、reason
  config_version text not null,
  created_at timestamptz not null default now(),
  unique(client_id, local_seq)
);

-- 归档索引：本地 + Supabase 共用
create table archive_index (
  task_id text primary key,
  event_id uuid not null,
  global_seq bigint,
  task_type text,
  primary_tag text,
  tags text[] not null default '{}',
  target_path text not null,
  content_hash text not null,
  updated_at timestamptz not null default now()
);

create index archive_index_tags on archive_index using gin(tags);
```

**关键点：**  
`global_seq` 由 Supabase 分配，本地不自己造。  
`archive_events` 只追加，不修改。  
“执行”和“同步”可以优化，“决策事件”和“全局顺序”不能优化掉。

## 2. 自动归档主流程

```text
任务输出产生
  -> 写入本地 events.jsonl（task_received）
  -> 分类器分类
  -> 打标签
  -> 计算目标路径
  -> 原子写入文件
  -> 更新本地 index.sqlite
  -> 异步同步到 Supabase
  -> 获取 global_seq
  -> 完成归档
```

每一步都是一个决策事件。

---

## 3. 自动分类

分类器采用“规则优先 + 模型兜底”：

```yaml
classifier:
  auto_accept_threshold: 0.85

  timeout_by_model:
    B_turbo: 300
    A: 600

  timeout_by_task_type:
    normal: { model: B_turbo, timeout: 300 }
    decision: { model: A, timeout: 600 }
```

规则命中且置信度高，直接用本地规则分类。  
规则置信度不足，才调用模型。

模型超时处理：

```text
B_turbo 超时 300s
A 超时 600s

超时后不无限重试：
-> 写入 _friction/
-> friction_reason = "timeout"
-> 后续 archive_review 循环处理
```

超时是正常事件，不是异常。  
超时事件也必须写入 `archive_events`，不能跳过。

---

## 4. 打标签：可检索的差异

不打“关系标签”，打“差异标签”。

普通标签：

```text
type:task
project:xxx
status:done
owner:yyy
```

差异标签：

```text
diff:before:{task_id}
diff:after:{event_id}
diff:contradicts:{rule_id}
diff:extends:{task_id}
diff:novelty:high
```

协作网络不是从“连接”开始的，而是从“可检索的差异”开始的。  
所以连接不是建表维护出来的，而是查询出来的：

```sql
select task_id
from archive_index
where tags @> '{"diff:after:event_123"}';
```

这就是一个可检索的差异网络。

## 5. 目录路由

目录由 `task_type` + `primary_tag` 决定，而不是由全部标签决定。

```text
target_path = archive_root
  / by_type
  / {task_type}
  / {primary_tag}
  / {yyyy}
  / {mm}
  / {task_id}.md
```

`primary_tag` 通常是：

```text
project:xxx
```

所有物理写入必须满足：

- 路径必须限制在 `archive_root` 内，防止穿越
- `task_id`、`primary_tag` 必须符合白名单字符
- 写文件用“临时文件 + rename”，保证原子性
- 标签最多 16 个，超出部分进 `_friction/`

目录是投影，不是事实。  
未来规则变化，不直接移动旧文件，而是通过 `rearchive` 生成新事件、新路径。

## 6. 配置修改后立即生效

这是重点。

### 配置读取点必须唯一

所有归档策略，只通过 `policy.py` 读取：

```python
def get_policy():
    return load_policy(CONFIG_PATH)
```

其他模块禁止自行读取 `archive_policy.yaml`，禁止缓存旧值。

### 配置版本

每次归档事件记录：

```text
config_version: v3
```

### 修改后必须验证

每次改配置后，必须运行：

```bash
archivectl verify --config archive_policy.yaml --fixture tests/fixtures/
```

`verify` 会检查：

- 同一 fixture 是否落到预期目录
- 标签是否变化
- 超时配置是否仍合法
- 新增配置是否被实际读取

如果改了配置但行为无变化，`verify` 应报警。

长驻进程不能只在启动时读一次配置。  
要用 `ConfigReloader` 监听配置 mtime，配置变化后自动失效缓存，并在下一次归档时使用新配置。

## 7. 同步与全局顺序

本地离线可归档。  
同步时，Supabase 负责分配 `global_seq`。

```text
本地 events.jsonl
  -> 批量推送到 Supabase
  -> Supabase 分配 global_seq
  -> 写 archive_events
  -> 更新 archive_index
  -> 返回给本地
```

同步可以优化：

- 批量插入
- 压缩 payload
- 并发上传
- 增量同步

但不能优化掉：

- 决策事件
- 全局顺序
- 旧事件不可变性

如果两个客户端离线产生了冲突，由 `global_seq` 决定最终顺序。  
需要修改归档结果时，不删除旧事件，而是写一个新的 `rearchived` 事件。

## 8. 摩擦循环：制度从摩擦中长出来

自动归档系统不能假装一开始就有完美分类。  
它必须有 `_friction/`。

每次以下情况都进入摩擦区：

- 模型超时
- 规则冲突
- 路径越界
- 低置信度
- 新标签/新类型首次出现
- 同一个任务被不同模型分成不同类

`_friction/` 不是垃圾桶，而是规则生成的原材料。

周期性运行 `archive_review`：

```text
读取 _friction/
按 friction_reason 聚类
发现重复摩擦
-> 形成新规则 / 新标签 / 新目录
-> 写入 policy_updated 事件
-> 触发 rearchive
```

这就是“开放、有界、循环”的负熵引擎：

- **开放**：新标签、新类型可以进入，不需要改表结构
- **有界**：标签数量、路径深度、事件大小、同步批次都有界
- **循环**：摩擦 -> 规则 -> 重归档 -> 新摩擦

---

## 9. 最终落地点

自动归档系统真正产出的是：

```text
可检索的差异档案，而不是整齐的文件夹。
```

- 文件夹是给人看的投影
- `archive_events` 是不可变的事实
- `global_seq` 是全局顺序
- `diff:` 标签是协作网络的边
- `_friction/` 是制度生长的土壤
- Supabase 是远端索引和备份
- 本地优先保证离线可用

这套系统可以大胆优化执行和同步，但绝不能优化掉“决策事件”和“全局顺序”。
