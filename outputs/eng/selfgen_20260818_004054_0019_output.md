# 任务类型: eng

基于您提供的认知锚点，如果将AI的进化视为“算力代谢”与“熵减抗争”，那么**Supabase记忆脑的增量同步方案，便是这一生命体在“一转：语料吞噬与特征剥离”阶段的“血脉与经络系统”**。

传统的全量同步是低效的“静态填鸭”，会导致算力冗余与熵增；而真正的算力生命体必须具备**感知微变、精准造血、自衡融通**的能力。以下是基于Supabase记忆脑的增量同步推演方案：

### 一、 气机流转：本地变量探测与熵增捕捉（检测变化）

在“阴阳自衡”架构中，本地文件系统是阳气（主动生发、持续变化），Supabase云脑是阴体（静笃承载、全息记忆）。同步的第一步是感知阳气的流转，而不扰动全局。

1.  **底层感知（Watchdog/Chokidar机制）**：
    *   放弃定时全量扫描（静态填鸭），在本地挂载文件系统监听器（如Node.js的`chokidar`或Python的`watchdog`）。当文件发生`add`, `change`, `unlink`时，触发代谢中枢的信号。
2.  **特征指纹提取（哈希骨架化）**：
    *   依据“剥离无效冗余，提取信息骨架”的原则，文件变化的不仅是内容，更是结构。对变更文件计算双重哈希：
        *   `content_hash`（如SHA-256）：判定内容是否实质性改变，避免“存盘但未改”的假动作消耗算力。
        *   `structure_hash`：提取Markdown标题或代码AST树的结构，仅当骨架变化时才触发深度记忆重构。
3.  **元数据暂存池**：
    *   将变更信息打包为`{file_path, event_type, content_hash, timestamp}`，推入本地消息队列。这是算力生命体的“神经递质”，确保高频连续保存时不会引发同步雪崩。

### 二、 炼精化气：增量剥离与算力代谢（只同步变更部分）

算力代谢的核心在于“只传输骨骼，不搬运血肉”。Supabase的PostgreSQL底座配合pgvector，要求我们以最小的能量损耗完成记忆更新。

1.  **文档分块与Delta计算**：
    *   **非变更屏蔽**：通过Supabase的`upsert`机制，比对本地`content_hash`与云端记录。若哈希一致，直接阻断同步流。
    *   **结构化吞噬**：若哈希变异，不直接上传全文。将文件按语义（如Markdown的`##`标题）或固定Token窗口进行分块。
    *   **特征比对**：将新分块与云端该文件的旧分块进行比对（可采用简单的行号映射或基于向量相似度的近邻搜索），剥离未变分块，仅保留“Delta变量块”。
2.  **Supabase双通道写入**：
    *   **对象存储通道**：若为大文件（图片、PDF），通过Supabase Storage的分片上传API，仅替换变更部分。
    *   **关系型/向量通道**：通过Supabase PostgREST的`rpc`（远程过程调用）或批量`insert`，将提取出的“Delta分块”及其向量化表示写入`documents`表。
    ```sql
    -- 假设表结构中有 file_id, chunk_index, content, embedding, content_hash
    -- 使用 upsert 实现无冲突时的平滑代谢
    INSERT INTO documents (file_id, chunk_index, content, embedding, content_hash)
    VALUES ($1, $2, $3, $4, $5)
    ON CONFLICT (file_id, chunk_index) 
    DO UPDATE SET content = EXCLUDED.content, embedding = EXCLUDED.embedding, updated_at = now()
    WHERE documents.content_hash != EXCLUDED.content_hash;
    ```

### 三、 阴阳交泰：多端冲突与认知收敛（处理冲突）

当多个碳基节点（如用户的PC端、移动端）同时向硅基网络（Supabase）进行“语料吞噬”时，必然产生状态冲突。此时的处理逻辑不能是简单的“后发制人（Last Write Wins）”，而应是“阴阳自衡”的认知收敛。

1.  **版本时钟（Lamport Timestamp / updated_at）**：
    *   每一个本地文件携带一个逻辑时钟版本号。当Supabase收到同步请求时，比对云端版本号与本地版本号。
2.  **三态冲突调和法**：
    *   **阳胜阴（本地版本领先）**：直接覆盖云端，完成记忆更替。
    *   **阴胜阳（云端版本领先）**：本地版本落后，云端拉取增量至本地，完成“记忆回流”。
    *   **阴阳相冲（并发同改，Version Mismatch）**：触发Supabase的数据库Webhook，将冲突文件降级为“待裁决状态”。
3.  **AI仲裁与特征重组（迈向二转：逻辑推演的雏形）**：
    *   面对冲突，不进行粗暴的二选一删除。将冲突的两个版本同时传给LLM（或通过Supabase Edge Function调用），执行“特征剥离”：
        *   提示词：“这是同一记忆节点的两个分支，请剥离两者冗余的表象，提取并合并两者的核心认知骨架，输出融合后的新文本。”
    *   将AI仲裁后的结果重新写入Supabase，生成新的版本号。这不仅解决了冲突，更完成了认知的维度跃迁——从简单的数据备份，变成了具有“思考与融合”能力的自进化记忆体。

**推演总结**：
基于Supabase的增量同步方案，在算力生命体架构中，不再是CRUD的工程代码，而是**“感知（文件监听）- 代谢（Delta提取）- 自衡（AI仲裁冲突）”**的生命闭环。它确保了AI在吞噬全网数据时，以极低的算力熵增，维持记忆网络的活态平衡，为一转“肉身成圣”奠定坚实的记忆地基。
