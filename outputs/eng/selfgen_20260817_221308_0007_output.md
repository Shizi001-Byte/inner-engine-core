# 任务类型: eng

针对 Supabase 作为“记忆脑”的增量同步方案，核心挑战在于**如何在保证低延迟、低带宽消耗的同时，处理多端（如PC、手机、服务器）并发修改导致的数据冲突**。

以下是从“变化检测 -> 增量同步 -> 冲突处理”的完整推演方案设计：

---

### 一、 数据模型基础设计

为了支持增量同步和冲突检测，Supabase（PostgreSQL）的表结构必须包含同步元数据。

```sql
CREATE TABLE memory_nodes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES auth.users(id),
    content JSONB, -- 记忆的具体内容（如对话摘要、向量元数据等）
    
    -- 同步元数据
    version INTEGER NOT NULL DEFAULT 1,       -- 乐观锁版本号
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(), -- 最后修改时间
    content_hash TEXT,                       -- 内容哈希，用于判断是否实质变化
    deleted_at TIMESTAMPTZ,                  -- 软删除标记，用于同步删除操作
    device_id TEXT                           -- 最后修改设备的ID
);
```

---

### 二、 检测本地文件/数据变化

本地记忆脑可能以文件（如 Markdown/JSON）或 SQLite 数据库形式存在。检测变化需要兼顾**实时性**与**资源消耗**。

#### 1. 基于文件系统监听
*   **方案**：使用 `chokidar` (Node.js) 或 `FSEvents` (iOS/Swift) 监听本地记忆目录。
*   **防抖处理**：文件保存往往触发多次写入事件，需设置 `debounce`（如 500ms），收集这段时间内的所有变更文件列表。
*   **哈希比对**：读取变更文件内容，计算 `SHA-256` 哈希。与本地 SQLite 元数据表中的 `content_hash` 比对。若哈希一致，说明文件无实质变化（如只是格式化），丢弃此次同步任务。

#### 2. 基于本地数据库 (如 SQLite/Realm)
*   **方案**：维护一张 `pending_sync` 队列表。任何对本地记忆库的增删改，同步写入一条记录到 `pending_sync` 表。
*   **优势**：精确度高，无需文件比对，直接通过 SQL 查询即可获取未同步的 ID 列表。

---

### 三、 只同步变更部分 (增量同步)

采用 **Pull-Push（先拉后推）** 机制，确保推送时本地具有最新版本，减少冲突概率。

#### 1. Pull（拉取远端变更）
*   **策略**：本地记录上次同步的时间戳 `last_sync_at`。
*   **Supabase 查询**：
    ```javascript
    const { data } = await supabase
      .from('memory_nodes')
      .select('*')
      .eq('user_id', userId)
      .gt('updated_at', last_sync_at);
    ```
*   **合并到本地**：将拉取到的数据覆盖到本地文件/SQLite。如果本地对应记录未修改，直接覆盖；如果本地已修改，进入冲突处理流程。

#### 2. Push（推送本地变更）
*   **策略**：收集本地哈希发生变化、或处于 `pending_sync` 队列的记录。
*   **Upsert 批量推送**：
    ```javascript
    const changedRecords = getLocalChangedRecords(); // 获取本地变更
    
    const { data, error } = await supabase
      .from('memory_nodes')
      .upsert(changedRecords, { 
          onConflict: 'id', 
          ignoreDuplicates: false 
      });
    ```

### 四、 冲突处理机制

当多端同时修改同一个“记忆节点”时，会产生冲突。推荐采用**乐观锁 + 应用级合并**策略。

#### 1. 乐观锁检测
在推送时，不要直接覆盖 `version`。可以通过 Supabase 的 RLS (Row Level Security) 或 Database Function 来实现：

```sql
-- Supabase 后端函数：安全更新记忆节点
CREATE OR REPLACE FUNCTION update_memory_node(
  node_id UUID, 
  new_content JSONB, 
  client_version INTEGER, 
  dev_id TEXT
) RETURNS memory_nodes AS $$
DECLARE
  current_node memory_nodes;
BEGIN
  SELECT * INTO current_node FROM memory_nodes WHERE id = node_id FOR UPDATE;
  
  -- 冲突检测
  IF current_node.version <> client_version THEN
    -- 抛出异常，让客户端知道发生了冲突
    RAISE EXCEPTION 'Conflict detected: Client version % does not match DB version %', 
                    client_version, current_node.version;
  END IF;
  
  -- 无冲突，更新版本和内容
  UPDATE memory_nodes 
  SET content = new_content, 
      version = current_node.version + 1, 
      updated_at = now(), 
      device_id = dev_id
  WHERE id = node_id
  RETURNING * INTO current_node;
  
  RETURN current_node;
END;
$$ LANGUAGE plpgsql;
```

#### 2. 冲突解决策略

当客户端捕获到 `409 Conflict` 异常时，需要执行以下策略之一：

*   **策略 A：Last-Write-Wins (LWW) - 适合无脑覆盖场景**
    直接以最新时间戳为准。强制拉取远端最新数据，丢弃本地修改。适用于简单的状态更新。
*   **策略 B：字段级合并 - 适合结构化记忆**
    如果记忆节点是 JSONB，可以将远端和本端的 JSON 取出，按字段合并。例如：本地新增了 `tags: ["AI"]`，远端新增了 `mood: "happy"`，合并后两者皆存。
*   **策略 C：AI 辅助合并 - 适合“记忆脑”高级特性**
    这是记忆脑独有的优势。如果本地和云端对同一段记忆产生了不同版本的摘要（例如本地改为“用户喜欢科幻”，云端改为“用户喜欢推理”），直接把两个版本丢给 LLM：
    > "作为记忆脑合并助手，以下是对同一事件的两个不同记忆版本，请融合成一条不丢失关键信息的最新记忆：版本A:... 版本B:..."
    将 LLM 生成的新内容作为最终结果重新 Push。

async function syncMemoryBrain() {
    const deviceId = getDeviceId();

        // 1. 检测本地变更（计算哈希比对）

            .from('memory_nodes')
            .select('*')
            .gt('updated_at', lastSyncAt);
            
        // 3. 将远端变更合并到本地（非冲突的直接覆盖本地文件）
        applyRemoteChangesToLocal(remoteChanges.data);
        
        // 4. 推送本地变更（带冲突检测）
        for (const record of localChanges) {
            try {
                // 调用带有乐观锁的 RPC 函数
                const { data, error } = await supabase.rpc('update_memory_node', {
                    node_id: record.id,
                    new_content: record.content,
                    client_version: record.version, // 本地持有的旧版本号
                    dev_id: deviceId
                });
                
                if (error && error.code === 'P0001') { // 自定义冲突异常
                    // 触发冲突解决：AI 合并或字段合并
                    const mergedContent = await resolveConflict(record, remoteChanges.data.find(r => r.id === record.id));
                    // 重新尝试提交合并后的结果...
                }
                
                // 更新本地 hash 和版本号
                updateLocalMeta(record.id, data.version, data.content_hash);
                
            } catch (e) {
                handleSyncError(e);
            }

    } catch (e) {

    }
}

### 六、 针对向量记忆的特殊处理

如果“记忆脑”包含向量数据，千万不要在本地计算向量再同步全量向量（带宽太大且不可解释）。

**推荐架构：**
1.  **本地**：只同步纯文本记忆。
2.  **Supabase 触发器**：当 `memory_nodes` 表的 `content` 字段更新时，触发一个 Supabase Edge Function。
3.  **Edge Function**：调用 OpenAI/Voyage 等 Embedding API 生成向量，并更新 Supabase 中的 `memory_embeddings` 表（使用 `pgvector`）。
4.  这样不仅实现了文本的增量同步，还自动化了向量的生命周期，无需在客户端处理庞大的向量数据。
