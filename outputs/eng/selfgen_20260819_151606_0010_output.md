# 任务类型: eng

## 设计：引擎产出三方同步自动化

### 一、核心策略

以 **“不可变产物 + 同步状态机 + 序号仲裁”** 规避幂等与冲突问题：

- 每次重大变更生成唯一 `sync_id`，例如：`maj_20250601_8f3a2c`
- 每次变更带单调递增序号 `seq`，用于判断新旧，不依赖服务器时间
- 每个产物计算 `sha256` 内容哈希，作为内容指纹
- 三方存储都使用 `sync_id` / `hash` 作为不可变 key，天然避免重复写入
- 只有“最新指针”需要更新，指针冲突统一按 `seq` 大者胜

---

### 二、触发机制

#### 1. 事件源

| 事件源 | 说明 |
|---|---|
| 引擎生成完成 | 引擎产出稳定版本后，发出 `major_change` 事件 |
| 人工标记 | 在管理后台/API 手动触发同步 |
| 定时补偿 | 定时扫描未完成或状态不一致的同步任务 |
| Gitee 代码变更 | 如果引擎本身由 Gitee 代码驱动，可监听 push 事件 |

#### 2. 重大变更判定

优先使用引擎自带的 `change_type`：

- `major`：触发三方同步
- `minor` / `patch`：只更新本地状态，不触发三方同步

若引擎未提供该字段，则通过规则判定：

- 命中核心路径：`src/`、`docs/api/`、`schema.sql`、`config/*.yaml`
- 变更文件数量超过阈值，例如 5 个
- diff 行数占比超过 30%
- 语义化版本号 major/minor 变化

#### 3. 配置生效验证

为避免“配置修改后未生效”：

- 所有触发规则统一存于 `trigger_config` 表
- 同步任务每次从数据库读取配置，不设长缓存
- 修改配置后必须立即发送 `probe` 测试事件
- 若 10 秒内未收到 worker 消费日志，则回滚配置

---

### 三、三方同步流程

#### 状态表

```sql
create table sync_outbox (
  id bigserial primary key,
  sync_id text unique not null,
  seq bigint not null,
  artifact_name text not null,
  content bytea not null,
  content_hash text not null,
  status text not null default 'pending',
  attempts int not null default 0,
  last_error jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table sync_state (
  sync_id text primary key,
  seq bigint not null,
  gitee_commit_id text,
  gitee_status text,
  feishu_file_token text,
  feishu_status text,
  supabase_object_key text,
  supabase_status text,
  sync_status text not null default 'pending',
  updated_at timestamptz not null default now()
);
```

#### 1. Gitee 代码提交

文件布局：

```text
artifacts/<sync_id>/<artifact_name>
artifacts/latest.json
```

`latest.json` 内容：

```json
{
  "sync_id": "maj_20250601_8f3a2c",
  "seq": 42,
  "hash": "sha256:...",
  "path": "artifacts/maj_20250601_8f3a2c/xxx"
}
```

同步流程：

1. 拉取最新 `origin/main`
2. 检查远端是否已有 `sync-id=<sync_id>` 的 commit，若有则跳过
3. 写入 `artifacts/<sync_id>/` 下所有文件
4. 更新 `latest.json`，仅当新 `seq` 大于当前 `seq` 时更新
5. commit message 固定包含：
   ```text
   chore(engine): sync <sync_id> [sync-id=<sync_id>] [sha256=<hash>]
   ```
6. push 到 `origin/main`

幂等点：

- 相同 `sync_id` 的 commit 只提交一次
- 相同 `sync_id` 的目录已存在则跳过
- push 失败后重试前先查询远端 commit，避免重复提交

冲突处理：

- `artifacts/<sync_id>/` 是独立目录，天然无冲突
- `latest.json` 冲突时，按 `seq` 大者胜
- 若 rebase 冲突发生在业务文件，不自动 merge，标记 `conflict` 并触发引擎基于最新代码重新生成

#### 2. 飞书文件上传

目录结构：

```text
引擎产出/版本文件/
```

文件名格式：

```text
<artifact_name>.<sync_id>.<content_hash>.<ext>
```

例如：

```text
设计文档.maj_20250601_8f3a2c.a1b2c3d4.md
```

流程：

1. 使用飞书云空间 API 上传文件到指定文件夹
2. 上传前按文件名查询是否已存在
3. 若存在且 `sync_id` 与 `hash` 一致，跳过
4. 若存在但 `hash` 不同，说明是不同内容，上传新版本文件
5. 上传成功后记录 `file_token`

幂等点：

- 文件名本身包含 `sync_id` 和 `hash`
- 同一 `sync_id` 同一 `hash` 不会重复上传
- 飞书侧不覆盖文件，只新增版本，避免并发覆盖冲突

冲突处理：

- 飞书文件对象不可变，无冲突
- 若需要“最新版”索引，在飞书知识库维护一个索引页
- 索引页更新使用飞书文档 revision 乐观锁，冲突后重新读取，再按 `seq` 判断是否更新

#### 3. Supabase 存储同步

Bucket：

```text
engine-artifacts
```

对象路径：

```text
artifacts/<sync_id>/<content_hash>/<artifact_name>
```

流程：

1. 使用 `storage.from('engine-artifacts').upload(path, content, { upsert: false })`
2. 若对象已存在，则检查 metadata 中的 `hash`
3. 若 hash 一致，跳过
4. 若 hash 不一致，说明 `sync_id` 冲突，立即告警

最新指针表：

```sql
create table latest_artifacts (
  artifact_name text primary key,
  sync_id text not null,
  seq bigint not null,
  object_key text not null,
  content_hash text not null,
  updated_at timestamptz not null default now()
);
```

更新逻辑：

```sql
insert into latest_artifacts(artifact_name, sync_id, seq, object_key, content_hash)
values (:name, :sync_id, :seq, :key, :hash)
on conflict (artifact_name) do update
set sync_id = excluded.sync_id,
    object_key = excluded.object_key,
    content_hash = excluded.content_hash,
    seq = excluded.seq,
    updated_at = now()
where excluded.seq > latest_artifacts.seq;
```

幂等点：

- 对象 key 含 `sync_id` 与 `hash`，相同内容不会重复写
- 最新指针使用条件更新，只有 `seq` 更大时才覆盖

冲突处理：

- 内容对象无冲突
- 最新指针冲突由 `seq` 仲裁
- 若两个并发任务同时写，后写且 `seq` 小的会被 SQL 条件挡住

---

### 四、幂等性总览

| 目标 | 幂等键 | 判断方式 | 重复操作结果 |
|---|---|---|---|
| Gitee | `sync-id=<sync_id>` | 查 commit message / 查目录 | 跳过 |
| 飞书 | 文件名含 `sync_id` + `hash` | 按文件名查询 | 跳过 |
| Supabase Storage | 对象路径含 `sync_id` + `hash` | 查对象是否存在 | 跳过 |
| 最新指针 | `artifact_name` | `seq` 条件更新 | 旧 seq 不覆盖新 seq |

所有外部操作在重试前，都先查询目标是否已有该 `sync_id` 的痕迹，确认后再决定是否执行。

---

### 五、冲突处理方案

#### 1. 内容冲突

三方存储内容均使用不可变 key：

```text
artifacts/<sync_id>/<hash>/...
```

因此同一内容不可能冲突；不同内容不可能写到同一 key。

#### 2. 最新指针冲突

统一仲裁规则：

```text
seq 大者胜
若 seq 相同，则 sync_id 字典序大者胜
```

Gitee 的 `latest.json`、飞书索引页、Supabase `latest_artifacts` 都遵循该规则。

#### 3. Gitee rebase 冲突

- 新文件不会冲突
- `latest.json` 冲突时，使用合并脚本读取两个版本，取 `seq` 较大的内容
- 业务代码冲突时不自动解决，标记 `conflict`，通知引擎基于最新代码重新生成

#### 4. 并发触发

- 所有同步任务先写入 `sync_outbox`
- worker 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 取任务
- 同一 `sync_id` 不会被两个 worker 同时处理

### 六、超时与重试

| 操作 | 超时时间 | 重试策略 |
|---|---|---|
| Gitee push | 60s | 3 次指数退避 |
| 飞书上传 | 300s | 3 次指数退避 |
| Supabase 上传 | 60s | 3 次指数退避 |
| AI 重大变更判定（B-turbo） | 300s | 1 次重试 |
| AI 重大变更判定（A 模型） | 600s | 1 次重试 |

每次超时/重试都记录到 `sync_state.last_error`，作为“心魔劫”反馈日志。

---

### 七、历史坑位规避

- 配置修改后立即验证：配置读取点统一，修改后发送 `probe` 事件，确认 worker 消费后再正式生效
- API 超时：所有外部调用设置明确 timeout，AI 模型按 B-turbo 300s / A 模型 600s
- 飞书连接器：优先使用飞书开放平台应用凭证，不依赖扫码连接器；若必须使用连接器，先升级客户端、放大页面、确认豆包账号已登录，失败自动告警

---

### 八、闭环说明

本设计不刻意回避“消耗”：每次重大变更都会真实触发 Gitee 提交、飞书上传、Supabase 写入，以及可能的冲突重试与日志产出。这些消耗是“实层动作”；同步状态收敛与冲突反馈则形成“虚层反馈”。

通过 `sync_id` 保证消耗是收敛的，不因重试产生脏数据，从而形成可持续的虚实自增强闭环。
