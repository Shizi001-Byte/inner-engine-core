## 一、认知质检 SOP：3 条可复用铁律

### 铁律 1：配置即代码，改配置必须同步改读取点，且立即验证

- **预防**：所有配置集中加载，禁止在业务代码里散落默认值；新增配置项时必须全局搜索读取点，确保同一个 key 被消费。
- **验证方法**：修改一个配置项后，跑 `sync --dry-run --verbose`，观察行为是否变化；或写一条测试断言“配置 key 被实际消费”。

```ts
// 所有读取点都从 config 取，禁止硬编码默认值
const chunkSize = syncConfig.chunkSize;
const conflictPolicy = syncConfig.conflictPolicy;
```

---

### 铁律 2：所有外部调用必须显式设置 timeout，超时即失败，不许卡死任务

- **预防**：模型调用、Supabase RPC、embedding 调用全部包一层 `withTimeout`。  
  - B 模型（turbo）：300 秒  
  - A 模型：600 秒  
  - Supabase RPC：建议 10~30 秒，按网络情况配置
- **验证方法**：mock 一个永不返回的请求，断言任务在 timeout 后抛错，而不是无限挂起。

```ts
function withTimeout<T>(p: Promise<T>, ms: number, label: string): Promise<T> {
  let timer: NodeJS.Timeout;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error(`${label} timeout ${ms}ms`)), ms);
  });
  return Promise.race([p, timeout]).finally(() => clearTimeout(timer!));
}

// 模型调用
const timeoutMs = model === 'B' ? 300_000 : 600_000;
await withTimeout(modelClient.call(...), timeoutMs, `model:${model}`);

// Supabase RPC
await withTimeout(supabase.rpc('sync_document', params), 30_000, 'sync_document');
```

---

### 铁律 3：模型质检规则必须按模型隔离，禁止全局统一阈值

- **预防**：质量检测函数必须接收 `model` 参数。  
  - A 模型：保留 reasoning 占比检测  
  - B 模型（turbo）：跳过 reasoning 占比检测，因为 70%~82% reasoning 占比是 B 模型正常特性，不是废稿
- **验证方法**：用 B 模型 reasoning=80% 的 fixture 跑检测，必须通过；用 A 模型同样 fixture 跑检测，必须失败。

```ts
function isQualityOk(result: GenerationResult, model: ModelId): boolean {
  if (model === 'B') return true; // B turbo 70-82% reasoning 是正常特性
  if (model === 'A') return result.reasoningRatio <= 0.5;
  return true;
}
```

# 二、Supabase 记忆脑增量同步方案

## 1. 总体思路

- 本地记忆文件是 **source of truth**，Supabase 是持久化副本。
- 用 `hash` 检测文件级变更，用 `content-addressed chunk` 定位变更粒度。
- 每次 sync 都是一个“突变”：通过 `sync_batches` 记录；通过验证后更新本地状态，失败则回滚，相当于“净化选择”。

## 2. 数据模型

```sql
-- 文档级元数据
create table documents (
  path text primary key,          -- 本地相对路径
  version bigint not null,        -- 每次同步 +1，用于冲突检测
  content_hash text not null,     -- 整个文件的 sha256
  updated_at timestamptz not null default now()
);

-- 全局内容寻址 chunk，不可变，避免重复 embedding
create table chunks (
  chunk_id text primary key,      -- sha256(chunk content)
  content text not null,
  embedding vector(1536),         -- 可选，按你的 embedding 维度调整
  created_at timestamptz not null default now()
);

-- 文档到 chunk 的有序映射
create table document_chunks (
  doc_path text references documents(path) on delete cascade,
  chunk_index int not null,
  chunk_id text references chunks(chunk_id),
  primary key (doc_path, chunk_index)
);

-- 同步批次，用于审计和回滚
create table sync_batches (
  id uuid primary key default gen_random_uuid(),
  status text not null,           -- pending / committed / rolled_back
  changes jsonb not null,
  created_at timestamptz not null default now()
);

-- 冲突记录
create table conflicts (
  id uuid primary key default gen_random_uuid(),
  path text not null,
  base_version bigint,
  local_version bigint,
  remote_version bigint,
  resolution text not null,       -- local_wins / remote_wins / merged / manual
  detail jsonb,
  created_at timestamptz not null default now()
);
```

本地状态文件 `.sync/state.json`：

```json
{
  "files": {
    "notes/foo.md": {
      "hash": "sha256:...",
      "version": 3,
      "mtime": 1234567890,
      "chunk_ids": ["chunk1", "chunk2", "chunk3"]
    }
  }
}
```

## 3. 检测本地文件变化

- 快速路径：先比 `mtime + size`，没变就跳过。
- 最终以 `sha256` 为准：`mtime` 变了但内容没变，不触发同步。
- 扫描结果分三类：
  - 新增文件：本地有，state 无
  - 修改文件：hash 变了
  - 删除文件：state 有，本地无

```ts
type FileChange =
  | { kind: 'create'; path: string; hash: string; chunks: Chunk[] }
  | { kind: 'update'; path: string; oldChunkIds: string[]; hash: string; chunks: Chunk[] }
  | { kind: 'delete'; path: string; version: number };
```

## 4. 只同步变更部分

核心：按 `chunk_id` 比较，而不是按整个文件覆盖。

- 对文件分块，例如按 Markdown 标题、段落、句子切分，超长再按固定窗口切。
- 每个 chunk 的 `chunk_id = sha256(chunk content)`。
- 对比旧 chunk_ids 和新 chunk_ids：

```ts
const oldIds = state.files[path].chunk_ids;
const newIds = newChunks.map(c => c.id);

const addedIds = newIds.filter(id => !oldIds.includes(id));
const removedIds = oldIds.filter(id => !newIds.includes(id));
// unchangedIds = oldIds ∩ newIds，不需要重新 embedding
```

同步时：

1. 只对 `addedIds` 生成 embedding，只插入新 chunk 到 `chunks` 表。
2. 重建 `document_chunks` 映射，记录新的顺序。
3. 删除 `removedIds` 对应的 `document_chunks` 行。
4. 更新 `documents.content_hash` 和 `version + 1`。

因为 `chunks` 是全局内容寻址的，unchanged chunk 不重算 embedding，不重传 content。`document_chunks` 是轻量映射，全量重建成本低，同时避免插入/删除导致 chunk_index 大面积冲突。

## 5. 冲突处理

### 冲突判断

同步前检查远端版本：

```ts
remote = getRemoteDocument(path);

if (remote == null) {
  // 远端已删除，本地还在 -> 冲突或重新创建
} else if (remote.version === state.files[path].version) {
  // 无冲突，正常同步
} else if (localHash === state.files[path].hash) {
  // 本地没改，远端改了 -> 直接拉取远端，不叫冲突
} else {
  // 本地也改了，远端也改了 -> 冲突
}
```

### 冲突策略

| 策略 | 行为 |
|---|---|
| `local-wins` | 用本地覆盖远端，记录 conflict |
| `remote-wins` | 用远端覆盖本地，记录 conflict |
| `merge` | 尝试 chunk 级三路合并；重叠冲突则转 manual |
| `manual` | 跳过该文件，生成冲突文件，等待人工处理 |

### chunk 级三路合并

- base = 本地 state 里的旧 `chunk_ids`
- local = 当前本地文件 chunk_ids
- remote = Supabase 当前 chunk_ids

用 diff 算法比较：

- `base -> local` 的变更
- `base -> remote` 的变更

如果两个 diff 没有触碰同一个 chunk_index，则自动合并；如果触碰同一个位置且内容不同，标记为冲突，写入 `.sync/conflicts/` 目录，并插入 `conflicts` 表。

## 6. 关键 RPC：事务性写入

Supabase 不能用 REST 安全地做“检查版本 + 重建 document_chunks”，所以用 RPC 函数包事务。

```sql
create or replace function sync_document(
  p_path text,
  p_expected_version bigint,
  p_content_hash text,
  p_chunk_ids text[],
  p_chunk_contents jsonb -- 新增 chunk 的 {chunk_id: content}
)
returns bigint
language plpgsql
as $$
declare
  v_doc documents%rowtype;
  v_new_version bigint;
  c record;
begin
  select * into v_doc from documents where path = p_path for update;

  if not found then
    if p_expected_version <> 0 then
      raise exception 'conflict: expected 0, remote missing';
    end if;
    insert into documents(path, version, content_hash, updated_at)
    values (p_path, 1, p_content_hash, now())
    returning * into v_doc;
    v_new_version := 1;
  else
    if v_doc.version <> p_expected_version then
      raise exception 'conflict: expected %, remote %', p_expected_version, v_doc.version;
    end if;
    v_new_version := v_doc.version + 1;
    update documents
    set version = v_new_version,
        content_hash = p_content_hash,
        updated_at = now()
    where path = p_path;
  end if;

  -- 新增全局 chunks，已存在则跳过
  for c in select * from jsonb_each(p_chunk_contents)
  loop
    insert into chunks(chunk_id, content)
    values (c.key, c.value)
    on conflict (chunk_id) do nothing;
  end loop;

  -- 重建文档 chunk 映射
  delete from document_chunks where doc_path = p_path;

  for i in 1..array_length(p_chunk_ids, 1)
  loop
    insert into document_chunks(doc_path, chunk_index, chunk_id)
    values (p_path, i - 1, p_chunk_ids[i]);
  end loop;

  return v_new_version;
end;
$$;
```

同步批次完成后：

- 原子更新本地 `.sync/state.json`
- 标记 `sync_batches.status = 'committed'`
- 如果后续校验失败，用 `sync_batches.changes` 里的旧快照回滚远端和本地状态

## 7. 验证清单

- [ ] 修改本地文件后，第二次 sync 只更新变更 chunk，unchanged chunk 不重新 embedding
- [ ] 连续跑两次 sync，第二次无任何变更（幂等）
- [ ] 模拟远端 version 大于本地，触发冲突，按策略处理并生成 conflict 记录
- [ ] 配置 `conflictPolicy` 后，行为立即变化
- [ ] 模型 timeout 改成 1ms 后，任务在 1ms 内报错，不卡死
- [ ] B 模型 reasoning=80% 的输出通过质检；A 模型同样输出被拒

这套方案把“本地文件变化检测、chunk 级增量、冲突处理”统一到同一个事务模型里，并且把历史踩过的坑收敛成了可执行的 SOP 铁律。
