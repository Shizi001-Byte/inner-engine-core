# 任务类型: eng

基于您提供的核心结论与避坑提醒，我将为您设计一套严格遵循“脑体分离架构”边界的**自动归档系统**。该系统将显式定义决策与执行的边界，确保所有操作可重放、可校验、且配置严格生效。

以下是系统设计方案：

### 一、 架构边界定义（遵循认知锚定3、4）
基于“脑体分离架构的边界，就是‘决策事件/全局顺序’与‘执行/同步’的边界”这一核心结论，系统划分为两层：

*   **脑（决策中心）：** 负责任务分类、打标签、计算目标目录。**绝不触碰实际文件系统或数据库写入**。它只产出带有全局顺序号的“归档决策事件”。
*   **体（执行中心）：** 订阅决策事件，负责物理文件移动、元数据入库。严格按照决策事件的全局顺序执行同步操作，自身不做任何路径推演。

---

### 二、 基础设施与数据层设计（遵循认知锚定1、5，避坑提醒1）
为防止列不匹配及配置不生效问题，基建层必须遵循以下硬性约束：

#### 1. 显式DDL与列映射（禁用简化版）
```sql
-- 禁止使用 CREATE TABLE ... AS SELECT 或隐式建表
-- 必须显式声明列名、列顺序、列类型，且与源表/下游预期严格对齐
CREATE TABLE IF NOT EXISTS `archive_metadata` (
  `event_id` BIGINT NOT NULL COMMENT '全局顺序事件ID',
  `task_id` VARCHAR(64) NOT NULL COMMENT '任务ID',
  `source_path` VARCHAR(512) NOT NULL COMMENT '源文件路径',
  `target_path` VARCHAR(512) NOT NULL COMMENT '目标归档路径(决策产出)',
  `task_tags` JSON NOT NULL COMMENT '任务标签(决策产出)',
  `task_category` VARCHAR(128) NOT NULL COMMENT '任务分类(决策产出)',
  `archive_status` TINYINT NOT NULL DEFAULT 0 COMMENT '执行状态:0待执行 1成功 2失败',
  `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  `updated_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`event_id`),
  UNIQUE KEY `uk_task_id` (`task_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

#### 2. 配置热更新与强校验（避坑提醒1）
*   **配置中心：** 存储分类规则、标签字典、目录映射策略。
*   **强校验机制：** 新增配置项时，基建脚本必须包含对读取点（如 `ConfigReader.get("archive_root_path")`）的单元测试。
*   **生效验证：** 配置修改后，CI/CD流水线立即触发一个“Dry-Run”任务，读取该配置并输出预期路径，若读取点未同步修改或读取为空，则流水线阻断。

---

### 三、 决策中心设计（脑）

#### 1. 分类与打标签引擎（遵循认知锚定2：显式、可重放）
*   决策中心接收到任务后，调用AI模型或规则引擎进行分类和打标签。
*   **显式声明：** 禁止使用隐式上下文。每一次决策必须包含完整的任务特征输入。
*   **API超时控制（避坑提醒2）：**
    *   如果调用 **B模型(turbo)** 进行轻量级标签提取，预设 `timeout = 300` 秒。
    *   如果调用 **A模型** 进行复杂的文档摘要与深度分类，预设 `timeout = 600` 秒。
*   **可重放设计：** 决策结果不直接落库，而是生成标准的决策事件：
    ```json
    {
      "event_id": "20231024100000-001", // 全局顺序号
      "task_id": "task-98765",
      "decision_type": "ARCHIVE_ROUTING",
      "payload": {
        "category": "financial_report",
        "tags": ["Q3", "2023", "raw_data"],
        "target_directory": "/archive/financial/2023/Q3/"
      },
      "decision_hash": "a1b2c3d4..." // 基于输入特征与规则版本生成的哈希，供重放校验
    }
    ```

---

### 四、 执行中心设计（体）

#### 1. 事件消费与同步执行
执行中心读取 `archive_metadata` 表中 `archive_status=0` 的记录，严格按照 `event_id` 的字典序（全局顺序）执行。

#### 2. 幂等与可校验脚本（遵循认知锚定1）
执行脚本必须满足：
*   **幂等性：** 重复执行同一条事件，最终状态一致。移动文件前先校验目标路径是否存在且MD5一致，若一致则直接标记成功。
*   **可校验性：** 执行完成后，反向校验源文件是否消失、目标文件是否存在、数据库元数据的 `target_path` 是否与物理路径完全一致。

---

### 五、 避坑与校验流程总结

1.  **配置防坑流程：**
    修改分类规则配置 -> 同步修改决策中心对应的读取类 -> 运行单元测试验证读取点不为空 -> 触发Dry-Run验证分类行为变化 -> 放行。
2.  **API调用防坑流程：**
    根据任务路由判断模型类型 -> B模型强制注入300s timeout，A模型注入600s timeout -> 捕获TimeoutException -> 写入重试队列并降级到规则引擎兜底分类。
3.  **数据防错位流程：**
    执行物理归档 -> 读取物理文件实际信息 -> 显式更新 `archive_metadata` 表（明确写出列名，不使用 `SELECT *` 或简写） -> 校验DB与物理世界一致 -> 标记 `archive_status=1`。

该设计严格遵循了您提供的认知锚定，所有决策可重放，所有执行可校验，且脑体边界极其清晰，能够有效避免历史踩过的坑。
