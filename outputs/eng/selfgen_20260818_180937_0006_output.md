# 任务类型: eng

基于已有认知锚定，不重复论证，直接推演 Supabase 记忆脑的增量同步方案。

## 一、核心数据模型：只有 DAG 顶点，没有同步任务表

远端不存 `sync_jobs` 表，只存不可变顶点：

- `block`：内容寻址的事实单元，`hash = sha256(content)`
- `index`：文件的有序块索引，一个 DAG 顶点
- `tombstone`：删除标记顶点
- `sync_heads`：只是当前 head 指针，可更新，不是归档本体

```sql
create table blocks (
  hash text primary key,
  size int not null,
  content bytea not null,
  created_at timestamptz not null default now()
);

create table file_index (
  index_hash text primary key,
  file_id uuid not null,
  block_hashes text[] not null,
  parent_index_hash text references file_index(index_hash),
  created_at timestamptz not null default now()
);

create table tombstones (
  tombstone_hash text primary key,
  file_id uuid not null,
  index_hash text not null references file_index(index_hash),
  block_hash text null,
  created_at timestamptz not null default now()
);

create table sync_heads (
  file_id uuid primary key,
  head_index_hash text not null references file_index(index_hash),
  updated_at timestamptz not null default now()
);

create table conflict_vertices (
  conflict_id uuid primary key default gen_random_uuid(),
  file_id uuid not null,
  base_index_hash text,
  local_index_hash text,
  remote_index_hash text,
  status text not null default 'open',
  resolution_index_hash text,
  created_at timestamptz not null default now()
);
```

文件不是被整文件复制，而是由 `index.block_hashes` 按顺序组装出来的视图。同步只上传缺失块、写入新 index/tombstone、更新 head。

## 二、流程结构：Detect -> Diff -> Commit，每节点三转，共九转

### 1. Detect：检测本地文件变化

| 转 | 动作 |
|---|---|
| D1 | 监听本地文件变更：inotify/FSEvents + 周期性全量扫描 |
| D2 | 对变更文件分块并计算哈希：Markdown 按语义块切，超大块用 CDC；块哈希 `sha256(content)` |
| D3 | 与本地 manifest 比对，标记新增块、修改块、删除块 |

只把变化的块放入候选集，未变化的块不参与后续上传。

### 2. Diff：计算远端差异

| 转 | 动作 |
|---|---|
| F1 | 拉取远端 `sync_heads` 对应 `file_index`，获取远端块哈希序列 |
| F2 | 对本地块哈希序列和远端块哈希序列做 LCS/Myers diff，计算最小编辑脚本 |
| F3 | 生成变更计划：`upload_blocks`、`download_blocks`、`new_block_hashes`、`parent_index_hash`、`tombstones` |

关键点：

- 内容相同的块不重复上传。
- 顺序变化只更新 index，不重传内容。
- 远端有而本地没有的块，只下载缺失块。

### 3. Commit：校验并写入 DAG

| 转 | 动作 |
|---|---|
| C1 | 校验：parent index 仍是 head；每个块 content hash 与 hash 一致；index 引用的块全部存在；剩余时间预算足够 |
| C2 | 写入：先写 blocks，再写 file_index，再写 tombstones，最后乐观更新 sync_heads |
| C3 | 确认：更新本地 manifest；如果是远端拉取，则用新 block_hashes 组装本地文件；发生冲突则写 conflict_vertices，不更新 head |

Commit 必须用事务或 RPC 原子完成，不能客户端分步写。

## 三、Supabase 提交函数示例

生产环境建议 block 内容走 Supabase Storage，RPC 只传哈希；这里用 `bytea[]` 表达事务原子性。

```sql
create or replace function commit_sync(
  p_file_id uuid,
  p_parent_index_hash text,
  p_block_hashes text[],
  p_block_contents bytea[],
  p_deleted_block_hashes text[] default '{}'
)
returns text
language plpgsql
security definer
set statement_timeout = '10s'
as $$
declare
  v_new_index_hash text;
  v_dummy uuid;
begin
  -- 1. 写入缺失 block
  insert into blocks(hash, content)
  select encode(sha256(content), 'hex'), content
  from unnest(p_block_contents) as content
  on conflict (hash) do nothing;

  -- 2. 校验 index 中所有块都存在
  if exists (
    select 1 from unnest(p_block_hashes) h
    left join blocks b on b.hash = h
    where b.hash is null
  ) then
    raise exception 'BLOCK_MISSING';
  end if;

  -- 3. 计算新 index 顶点 hash
  v_new_index_hash := encode(sha256(convert_to(
    p_file_id::text || '|' || coalesce(p_parent_index_hash, '') || '|' || array_to_string(p_block_hashes, ',')
  , 'UTF8')), 'hex');

  -- 4. 写入 index 顶点
  insert into file_index(index_hash, file_id, block_hashes, parent_index_hash)
  values (v_new_index_hash, p_file_id, p_block_hashes, p_parent_index_hash)
  on conflict do nothing;

  -- 5. 写入 tombstone
  insert into tombstones(tombstone_hash, file_id, index_hash, block_hash)
  select encode(sha256(convert_to(
    p_file_id::text || '|' || v_new_index_hash || '|' || coalesce(block_hash, '')
  , 'UTF8')), 'hex'), p_file_id, v_new_index_hash, block_hash
  from unnest(p_deleted_block_hashes) as block_hash;

  -- 6. 乐观更新 head
  insert into sync_heads as sh (file_id, head_index_hash)
  values (p_file_id, v_new_index_hash)
  on conflict (file_id) do update
  set head_index_hash = excluded.head_index_hash
  where sh.head_index_hash = p_parent_index_hash
  returning file_id into v_dummy;

  if not found then
    raise exception 'SYNC_CONFLICT';
  end if;

  return v_new_index_hash;
end;
$$;
```

如果 `SYNC_CONFLICT`，事务回滚，不写坏数据。

## 四、冲突处理

冲突在 Commit 阶段通过乐观锁发现：

- 提交时发现 `sync_heads.head_index_hash != p_parent_index_hash`
- 说明远端已经前进，本地基于旧 base 提交

处理策略：

1. **自动合并**
   - 本地和远端改动的块集合不相交：自动合并，生成新 index 顶点。
   - 两边都删同一个块：无冲突。
   - 两边改同一个块但结果哈希相同：无冲突。

2. **真冲突**
   - 同一个块被改成不同内容。
   - 一边删除、一边修改。
   - 顺序变化产生歧义。

真冲突时：

- 写 `conflict_vertices` 记录 base/local/remote。
- 不更新 `sync_heads`。
- 阻塞该文件后续自动写入，直到人工或 LLM 解决。
- 解决后写一个新的 index 顶点，并更新 head。

核心原则：**同步是为了给记忆脑增加秩序，冲突/超时时必须停止写入，不能把混乱固化。**

## 五、避坑清单

### 1. 配置修改必须同步读取点

所有配置只从统一 `get_config()` 读取，不允许在多个模块硬编码默认值。

新增配置后必须同步修改读取点，并立即执行 `sync --verify` 验证生效。

特别注意：**修改分块大小/分块策略后，必须全量重新分块**，否则旧 manifest 会产生虚假 diff。

### 2. API 超时按模型预设

如果 Commit 阶段需要调用 LLM 做冲突合并或摘要：

- B 模型（turbo）：300 秒
- A 模型：600 秒

不要用统一短超时。超时后直接熔断，不写入任何顶点。

### 3. 质量检测规则必须按模型隔离

B 模型（turbo）的 reasoning 占比 70%–82% 是正常特性，不能被废稿检测误杀并自动重试。

必须为不同模型设置独立规则：

```ts
const qualityRules = {
  'A':       { maxReasoningRatio: 0.85 },
  'B-turbo': { skipReasoningRatio: true },
};
```

否则 B 模型会被误判为废稿，导致无意义重试，浪费预算和同步时间。

### 4. 不建同步任务表

Supabase 远端不存 `sync_jobs` 表。同步历史由 DAG 顶点推导：

- 每个 block 是不可变事实。
- 每个 index 是不可变快照。
- 每个 tombstone 是不可变删除记录。
- `sync_heads` 只是头指针。

这样增量同步天然可审计、可回滚、可去重。
