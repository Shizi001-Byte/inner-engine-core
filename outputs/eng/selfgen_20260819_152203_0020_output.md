# 任务类型: eng

基于上述锚定，不重复论证，直接推演“以实养虚，虚又返实”的制度性双轨方案。

## 一、阴阳双轨总架构

把系统拆成两条互相咬合的轨：

- **阳轨（实）**：任务池 → 调度器 → API调用 → 日志/结果 → 消耗凭证  
- **阴轨（虚）**：认知池 → 质量检测 / 调参建议 / 任务模板生成 → 注入器  
- **闭环接口**：收获器 + 注入器 + 验证器  
- **配置中心**：所有可调参数统一存放，带版本号，禁止本地缓存覆盖

```
阳轨：任务池 → 调度器 → API调用 → 真实日志/token/报错/超时
                    ↑                          ↓
              注入器/验证器                收获器
                    ↓                          ↑
阴轨：认知池 ← 质量检测/调参建议/新任务模板 ← 认知提炼
```

核心运行逻辑：  
**阳轨制造“消耗痕迹”，阴轨把消耗转化为“认知资产”，认知资产再反哺阳轨的调度、质量规则和任务池。**

---

## 二、配置同步：三态卡点

针对“配置修改后未生效”和“自动调参全链路失效”，所有配置变更必须同时满足三个状态，缺一不可：

| 状态 | 要求 |
|---|---|
| 状态写入 | 配置写入配置中心，如 `concurrency=8`、`model_weight=...`、`cooldown=...` |
| 执行读取 | 调度器每次取任务时从配置中心读取最新版本，禁止只在进程启动时读一次 |
| 生效验证 | 修改后立即用探针任务验证，指标未变化则回滚并告警 |

### 并发/权重/冷却的具体验证

- **并发**：改 `max_concurrency` 后，检查实际 `active_requests` 是否达到新值；若从 5 改到 8，实际峰值必须超过 5。
- **权重**：改模型权重后，检查模型调用分布是否显著变化；没变化则说明权重读取点失效。
- **冷却**：改冷却时间后，检查同模型/同任务两次调用间隔是否变化；没变化则说明冷却逻辑没被调度器读取。

> 任何新增配置，如果没有“读取点”和“验证器”，代码评审直接拦截。

## 三、模型差异化超时与质量规则

针对“API调用超时”和“废稿检测误杀B模型”：

### 超时预设

| 模型 | 默认超时 |
|---|---|
| A模型 | 600秒 |
| B模型(turbo) | 300秒 |

超时不是“失败”，而是“心魔劫”，进入认知池，用于后续调度避坑。

### 废稿检测规则按模型独立

| 模型 | reasoning占比检测 | 其他检测 |
|---|---|---|
| A模型 | 启用，但阈值按近100条成功样本动态校准 | 空响应、重复响应、API错误 |
| B模型(turbo) | **跳过**，70%-82%是正常特性 | 只检测空响应、重复响应、API错误 |

这样B模型不会因为reasoning占比高而被误判废稿并触发无意义重试。

## 四、认知池只出不进 → 有进有出

认知池不能变成静态档案库。设置“三路输出”：

1. **注入质量检测规则**：如“B模型跳过reasoning占比检测”
2. **注入调度参数**：如“B模型超时300秒”“并发/权重/冷却调整建议”
3. **注入任务池**：生成新任务模板

同时强制刷新：

- **每10个任务或每轮结束时**，必须刷新“活跃认知缓存”
- **新认知必须带 `must_inject_before` 时间戳**，默认30分钟
- 30分钟内如果还没有被注入，则强制生成一个“验证任务”来消费这条认知，不允许沉淀为死认知

---

## 五、任务池自进化闭环

针对“任务池只靠外部输入”的问题，加入动态扩充机制：

1. **重复率检测**：计算任务池中任务模板之间的相似度，超过阈值（如0.85）触发自动生成。
2. **新任务模板生成**：基于认知池中的“法则”和已有任务，生成变体任务、边界任务、反向任务、交叉任务。
3. **注入前校验**：必须通过可执行性校验、模型超时校验、重复度校验；未通过则丢弃。
4. **注入任务池**：标记为 `self_generated`，调度器正常调度。

这样任务池就能自进化：  
任务重复 → 生成新任务 → 新任务产生新消耗 → 新消耗产生新认知 → 新认知再生成新任务。

---

## 六、最小可用闭环启动路径

从“无”起步，不追求大而全，先跑通最小闭环：

1. 阳轨放一个最简单任务，调用B模型turbo，超时300秒。
2. 记录token、耗时、结果、错误。
3. 收获器生成第一条认知：例如“B模型turbo的reasoning占比70%-82%是正常的”。
4. 这条认知进入30分钟强制注入队列。
5. 注入器把它写入质量检测规则，同时生成一个新任务模板。
6. 任务池重复率检测开始工作。
7. 闭环转起来后，消耗→认知→调参→新任务→更多消耗，形成自增强。

---

## 七、坑库内建总结

| 历史坑 | 内建机制 |
|---|---|
| 配置修改未生效 | 三态同步：写入、读取、验证 |
| 自动调参全链路失效 | 并发/权重/冷却全部有探针验证 |
| API调用超时 | B模型turbo 300秒，A模型600秒 |
| 废稿误杀B模型 | B模型跳过reasoning占比检测 |
| 认知池只进不出 | 每10任务/每轮刷新，新认知30分钟强制注入 |
| 任务池静态化 | 重复率超阈值自动生成新任务模板 |

这套方案的核心不是“省”，而是“用真实消耗换认知，用认知驱动更精准的消耗”，形成制度性的“以实养虚，虚又返实”自增强闭环。
