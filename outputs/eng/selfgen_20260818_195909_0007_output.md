# 任务类型: eng

## 推演结论

用 **本地指纹状态 + 内容寻址块 + 乐观锁版本号 + 三方冲突仲裁 + 软删除/归档** 实现 Supabase 记忆脑的增量同步。

---

## 1. 整体架构

```
本地文件变化
   │
   ├─ Watchdog/Chokidar 监听，防抖 500ms
   │
   ├─ 计算指纹：sha256(file_content)
   │     ↓
   │ 与本地状态文件 .memory-sync/state.json 对比
   │     ↓
   │ 有变化则进入同步队列
   │
   ├─ 读取 Supabase 远端状态：version / content_hash / updated_at
   │     ↓
   ├─ 判定：push / pull / conflict / delete / archive
   │     ↓
   └─ 同步后更新本地状态，写 sync_ops 日志
```

---

## 2. 数据模型

```sql
-- 文件级元数据
create table memory_files (
  path text primary key,
  content_hash text not null,
  version bigint not null default 0,
  updated_at timestamptz default now(),
  deleted boolean default false,
  status text default 'active',  -- active / archived
  last_accessed_at timestamptz default now()
);

-- 内容寻址块
create table memory_blocks (
  hash text primary key,
  content text not null,
  ref_count int not null default 0
);

-- 文件与块的映射
create table file_blocks (
  path text not null references memory_files(path),
  block_index int not null,
  block_hash text not null references memory_blocks(hash),
  primary key (path, block_index)
);

-- 同步操作日志
create table sync_ops (
  id bigserial primary key,
  path text not null,
  op text not null,  -- push / pull / conflict / delete / archive
  from_hash text,
  to_hash text,
  version bigint,
  created_at timestamptz default now()
);
```

---

## 3. 检测本地文件变化

- 使用 `chokidar` / `watchdog` 监听本地记忆目录。
- 忽略 `.memory-sync/`、`.git/`、临时文件。
- 事件防抖 300–500ms，合并原子写入产生的多次事件。
- 不只看 `mtime`，必须计算 `sha256(content)`，因为 `mtime` 变化不代表内容变化。

本地状态文件示例：

```json
{
  "memory/foo.md": {
    "local_hash": "sha256:...",
    "remote_hash": "sha256:...",
    "version": 12,
    "last_sync_at": "2025-01-01T00:00:00Z"
  }
}
```

## 4. 只同步变更部分

### 4.1 文件级增量

小文件直接按文件同步；大文件按块同步。

### 4.2 块级增量

将文件切成块：

- 默认按行/语义块切分。
- 若文件频繁插入内容，推荐使用滚动哈希切块，避免中间插入导致后续所有块 hash 变化。

同步时：

1. 本地切块得到 `local_manifest = [hash1, hash2, hash3]`
2. 从远端读取该文件已有的 `remote_manifest = [hash1, hash2]`
3. 只上传本地有、远端没有的块
4. 只删除远端有、本地没有的块
5. 更新 `file_blocks` 映射

伪代码：

```python
def push(path, local_hash, remote):
    local_blocks = split_into_blocks(path)
    remote_blocks = get_remote_manifest(path)

    to_upload = {
        h: content
        for h, content in local_blocks
        if h not in remote_blocks
    }
    to_delete = remote_blocks - set(local_blocks)

    supabase.rpc("sync_push", {
        "path": path,
        "expected_version": remote.version,
        "to_upload": to_upload,
        "new_manifest": [h for h, _ in local_blocks],
        "to_delete": list(to_delete)
    })
```

`sync_push` 在 Postgres 事务内完成：

- 对 `memory_files` 加行锁
- 校验 `version == expected_version`
- 插入新块，维护 `ref_count`
- 删除不再引用的块
- 更新 `content_hash`、`version = version + 1`
- 写 `sync_ops`

这样保证不会出现半同步状态。

## 5. 冲突处理

用「三方比较」判断冲突：

```python
base = state.remote_hash   # 上次成功同步时远端的 hash
local = current_local_hash
remote = fetch_remote(path).content_hash

if remote == base and local != base:
    push(local)
elif local == base and remote != base:
    pull(remote)
elif local != base and remote != base:
    resolve_conflict(path, local, remote)
else:
    noop()
```

### 5.1 冲突策略

| 策略 | 行为 |
|---|---|
| `lww` | 按 `local_mtime` 和 `remote.updated_at` 比较，新的赢，旧的备份到 `.conflicts/` |
| `merge` | 行级/JSON 合并；无法自动合并时生成冲突文件 |
| `manual` | 只标记 `conflict`，不自动覆盖，等人工处理 |

### 5.2 乐观锁防覆盖

所有更新都带 `expected_version`：

```sql
update memory_files
set content_hash = $new_hash,
    version = version + 1,
    updated_at = now()
where path = $path
  and version = $expected_version;
```

如果影响行数为 0，说明远端已被别人改过，立即进入冲突处理。

## 6. 删除与淘汰同步

这是防止“认知池只进不出”的关键。

### 6.1 本地删除

- 本地文件删除后，不能只删本地。
- 调用 `sync_delete(path, expected_version)`，远端设置 `deleted = true`。
- 保留软删除状态一段时间，确认无其他端需要恢复后再物理清理。

### 6.2 本地归档

- 对超过生命周期、长期未访问的认知，本地标记 `archived`。
- 同步时作为普通更新推送到远端。
- 远端查询必须带 `where status = 'active'`，否则归档不生效。

### 6.3 远端删除/归档

- 如果远端删除而本地未改，则把本地移到 `.trash/`。
- 如果远端删除而本地已改，则按冲突处理，不能直接删。

## 7. 避坑映射

| 历史坑 | 本方案对策 |
|---|---|
| 配置修改后未生效 | 新增配置必须同步修改读取点；同步后执行一次测试同步断言行为 |
| API 调用超时 | Supabase REST 调用设 30s 超时 + 指数退避重试；LLM 合并时按模型分级：B 模型 turbo 300s，A 模型 600s |
| 废稿检测误杀 B 模型 | 冲突合并结果质量检测不通用“reasoning 占比”；B 模型 turbo 跳过 reasoning 占比检测，只校验结构、字段、长度 |
| 认知池只进不出 | 同步方案强制支持删除/归档/降权，监控活跃条目数应出现周期性下降或稳定波动，而非单调递增 |

---

## 8. 验证方案

1. 修改一个本地文件，确认只上传变更块，不触发全量上传。
2. 本地和远端同时修改同一文件，确认进入冲突流程，不互相覆盖。
3. 本地删除文件，确认远端软删除，活跃计数下降。
4. 查看 `sync_ops` 表，确认每次操作都有记录。
5. 监控 `memory_files` 中 `status='active'` 的数量，确认存在淘汰波动，而不是只增不减。

这样，Supabase 记忆脑的增量同步既能高效传输变更，又能正确处理冲突，同时避免历史踩过的坑。
