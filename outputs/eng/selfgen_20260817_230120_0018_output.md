# 任务类型: eng

推演一套基于 Supabase 的“记忆脑”（通常指 RAG 知识库或个人 AI 记忆系统）增量同步方案，核心目标是**高效、无感、避免冲突**。

这套方案分为三大模块：**本地变化检测**、**增量同步策略**、**冲突处理机制**。

---

### 一、 核心架构设计

在推演具体逻辑前，我们需要明确本地与 Supabase 的数据结构映射。

*   **本地状态库：** 使用 SQLite 或简单的 JSON 文件，记录本地文件的元数据。
*   **Supabase 数据表：**
    *   `documents` 表：存储文档元数据（id, file_path, content_hash, version, updated_at）。
    *   `document_chunks` 表：存储切片数据（id, document_id, chunk_hash, content, embedding向量）。
*   **Supabase Storage：** 存储原始文件的备份（可选，用于多端共享原始文件）。

---

### 二、 检测本地文件变化

全量扫描极其消耗资源，我们需要一套机制来精准捕获“增量”。

#### 1. 变化检测机制组合
*   **实时监听（事件驱动）：** 使用 `watchdog` (Python) 或 `chokidar` (Node.js) 监听文件系统事件（创建、修改、删除、重命名）。当文件保存时，立即触发预计算。
*   **哈希比对（内容驱动）：** 文件系统的事件可能会被多次触发（如连续保存）。收到事件后，计算文件的 SHA-256 哈希值。如果哈希值与本地状态库中记录的哈希值一致，则忽略（防止伪变更）。
*   **兜底全量扫描（定时补偿）：** 每天定时执行一次全量扫描，对比文件哈希与本地状态库，修复因程序未运行时产生的遗漏变更。

#### 2. 本地状态库结构设计
```json
// local_state.json 或 local_sqlite
{
  "file_path": "/notes/ai_architecture.md",
  "content_hash": "a1b2c3d4...",  // 文件内容哈希
  "local_version": 5,            // 本地版本号
  "last_synced_at": "2023-10-27T10:00:00Z",
  "status": "PENDING_SYNC"       // PENDING_SYNC, SYNCED, CONFLICT
}
```

### 三、 增量同步策略

只同步变更部分，避免重新生成整个知识库的 Embedding。

#### 1. 变更类型识别与处理
当检测到本地文件变化后，根据哈希比对结果执行不同操作：

*   **新增：** 本地无记录，Supabase 无记录。
    *   操作：切片 -> 本地生成 Embedding -> 插入 Supabase `documents` 和 `document_chunks` 表。
*   **修改：** 哈希值改变。
    *   操作：**Chunk 级别的 Diff（核心优化）**。
    *   不要重新 Embedding 整个文档。将新文档切片后，计算每个 Chunk 的哈希。
    *   与 Supabase `document_chunks` 表中该文档的旧 Chunk 哈希对比：
        *   哈希不变：跳过。
        *   哈希改变：删除旧 Chunk 向量，插入新 Chunk 向量。
        *   新增 Chunk：插入新向量。
*   **删除：** 本地文件被删。
    *   操作：调用 Supabase API，通过 `document_id` 级联删除 `documents` 表和 `document_chunks` 表中的相关数据。
*   **重命名/移动：** 路径改变但哈希不变。
    *   操作：仅更新 Supabase `documents` 表中的 `file_path` 字段，不触碰向量表。

#### 2. 同步队列与去抖
由于 AI 记忆脑的 Embedding 生成较慢，同步不能阻塞主线程。
*   引入消息队列（如本地轻量级的 Celery / BullMQ）。
*   **去抖处理：** 文件连续修改时，取消之前的 Embedding 任务，只执行最后一次。

### 四、 冲突处理机制

当多端（如 PC、Mac、手机）同时修改同一个记忆文件并同步到 Supabase 时，会产生冲突。我们采用 **乐观并发控制**。

#### 1. 版本号机制
每个文档在 Supabase 中有一个 `version` 字段。
*   客户端拉取文档时，记录当前 `version` (例如 V1)。
*   客户端本地修改后，推送更新时附带条件：`UPDATE documents SET content=..., version=2 WHERE id=... AND version=1`。
*   如果受影响行数返回 0，说明文档已被其他端修改，触发冲突。

#### 2. 冲突解决策略
根据“记忆脑”的特性，提供三种解决策略（可配置）：

*   **策略 A：最后写入获胜** - 适合纯笔记同步。
    *   强制覆盖：使用 `updated_at` 时间戳判断，时间晚的覆盖早的。丢失早期数据。
*   **策略 B：分支合并获胜（推荐）** - 适合 AI 记忆库。
    *   检测到冲突后，将后提交的版本作为“新分支”存入 Supabase。
    *   在 Supabase 中生成一个冲突副本：`file_path = "notes/ai.md (conflict copy)"`。
    *   通知客户端拉取冲突副本，由用户或 AI 在本地决定如何合并（例如让大模型读取两个版本的 Chunk，生成融合后的新文本，再重新同步）。
*   **策略 C：基于 Chunk 的细粒度合并** - 最复杂但最无损。
    *   如果两个端修改的是文档的不同段落（不同 Chunk 哈希），可以在 Supabase 侧直接合并：保留两端的 Chunk 哈希，只删除双方都不再拥有的旧 Chunk。

#### 3. Supabase RPC 处理冲突
可以通过 Supabase 的 Postgres RPC (Remote Procedure Call) 将冲突判断逻辑放在数据库端执行，保证原子性。

```sql
-- supabase/functions/_sync_document.sql
CREATE OR REPLACE FUNCTION sync_document(
  p_doc_id UUID,
  p_expected_version INT,
  p_new_hash TEXT,
  p_chunks JSONB -- 包含变更的 chunks
)
RETURNS BOOLEAN AS $$
DECLARE
  current_version INT;
BEGIN
  SELECT version INTO current_version FROM documents WHERE id = p_doc_id FOR UPDATE;
  
  IF current_version = p_expected_version THEN
    -- 无冲突，执行更新
    UPDATE documents SET content_hash = p_new_hash, version = current_version + 1 WHERE id = p_doc_id;
    -- 处理 chunks 的 upsert/delete...
    RETURN TRUE;
  ELSE
    -- 发生冲突
    RETURN FALSE;
  END IF;
END;
$$ LANGUAGE plpgsql;
```

### 五、 完整同步推演流程

假设场景：用户在 PC 端修改了 `memory.md`，新增了一段话。

1.  **本地监听：** `watchdog` 捕获到 `memory.md` 的 `modified` 事件。
2.  **去抖与哈希：** 等待 2 秒无后续修改，计算文件 `content_hash = "xyz789"`。
3.  **状态比对：** 本地状态库记录的哈希是 `"abc123"`，判定为“已修改”，状态置为 `PENDING_SYNC`。
4.  **切片与 Diff：**
    *   将 `memory.md` 切分为 10 个 Chunks。
    *   计算 Chunk 哈希，发现只有第 5 个和第 6 个 Chunk 的哈希变了。
5.  **生成 Embedding：** 仅对第 5、6 个 Chunk 调用 Embedding 模型生成向量。
6.  **请求 Supabase：**
    *   读取 Supabase 中该文档的 `version` 为 `3`。
    *   调用 RPC `sync_document(p_doc_id, p_expected_version=3, p_new_hash="xyz789", p_chunks=[...])`。
7.  **Supabase 响应：**
    *   **成功：** 数据库版本更新为 4。客户端更新本地状态库版本为 4，状态置为 `SYNCED`。
    *   **失败（冲突）：** 返回当前数据库版本 5。
8.  **处理冲突（若失败）：**
    *   客户端拉取远端最新版本 (V5) 的内容。
    *   执行策略 B：将本地修改保存为 `memory (local_conflict).md` 并提示用户，或者调用大模型进行语义合并后重新提交。

### 六、 性能优化补充

1.  **离线支持：** 如果断网，本地状态库的 `PENDING_SYNC` 记录会堆积。网络恢复后，按时间顺序批量执行上述同步逻辑。
2.  **Supabase Edge Functions：** 如果让客户端直接操作 Supabase 数据库和 pgvector 表，安全性较低。更好的架构是：客户端将变更的 Chunk 上传给 Supabase Edge Function，由 Function 负责 Embedding 生成、版本比对和数据库写入。这能减轻客户端负担，并保护数据库直连安全。
