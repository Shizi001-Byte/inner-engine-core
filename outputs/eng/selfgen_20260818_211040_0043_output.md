# 任务类型: eng

基于【已有认知锚定】中的 CONST-1（精气神三元迁移框架）与 A0 锚定，针对 V7.5 方舟效能引擎中“多线程 API 调用后串行后处理”的场景，直接推演状态一致性方案与完整锁机制。

---

### 一、 竞态条件推演与核心解法

在多线程并发调用大模型 API，随后由主线程进行串行后处理的架构中，核心矛盾在于**生产者（并发线程）与消费者（后处理线程）的速度差与内存可见性差**。

1. **写写覆盖（线程 A/B 竞态）**：若多线程向同一个共享变量（如全局结果列表或字典）追加结果，不施加互斥锁会导致底层数据结构指针错乱，线程 B 的写操作覆盖线程 A 的写操作。
2. **读写脏读（生产/后处理竞态）**：若后处理线程在读取结果时，某 API 线程正在写入“半成品”数据（例如：已写入 `task_id`，但还未写入 `response_content`），后处理线程将读到空值或部分结果。
3. **状态错位（旧结果滞留）**：配置修改后未生效，或线程复用导致旧请求结果混入新批次。

**核心解法**：采用 **“线程局部变量隔离 + 全局互斥锁批量快照写入 + 条件变量同步后处理”** 的机制。

### 二、 V7.5 完整锁机制方案

#### 1. 数据结构定义与隔离策略
避免多线程直接操作全局共享内存，采用“攒批快照”策略。

*   **局部结果集**：每个 API 调用线程内部维护 `local_result`，包含 `task_id`, `content`, `status`, `config_version`。数据不落盘全局。
*   **全局结果汇聚区**：`global_result_map = {}`，仅由主互斥锁保护。
*   **同步信号**：`threading.Condition()`，用于唤醒串行后处理线程。

#### 2. 核心锁机制工作流

**【生产端：多线程 API 调用】**
1.  **请求前置校验**：发起 API 前，先校验配置版本（防止配置修改未生效坑），并根据模型类型设定强制超时（B模型turbo:300s，A模型:600s）。同时显式关闭代理（`proxies=None` 或 urllib 直连，防止 ProxyError）。
2.  **执行 API 调用**：获取响应后，立即验证 `content` 非空（防止 Responses API 空耗 reasoning 导致空回复）。
3.  **加锁写入（临界区）**：
    ```python
    with global_lock:
        # 原子性写入，确保 task_id 和 content 同时落盘，杜绝“部分结果”脏读
        global_result_map[task_id] = {
            "content": local_content,
            "config_ver": current_ver,
            "status": "completed"
        }
        completed_count += 1
        # 如果全部完成，唤醒后处理线程
        if completed_count == total_tasks:
            condition.notify_all()
    ```

**【消费端：串行后处理线程】**
1.  **阻塞等待**：
    ```python
    with global_lock:
        while completed_count < total_tasks:
            condition.wait() # 释放锁并等待生产者唤醒
        # 此时所有生产者已完成，安全获取快照
        snapshot_results = global_result_map.copy()
    ```
2.  **无锁串行后处理**：后处理线程在锁外遍历 `snapshot_results`，执行解析、入库等耗时操作，避免长时间持锁导致 API 线程阻塞。

### 三、 结合历史踩坑经验的工程级实现规范

在上述锁机制方案的落地过程中，必须将历史坑点内化为代码级防御：

| 防御维度 | 坑点来源 | 锁机制及业务流防范落地 |
| :--- | :--- | :--- |
| **网络代理** | ProxyError导致线程崩溃死锁 | 网络层统一用 `urllib` 直连；如用 `requests`，必须在 API 请求函数入口显式写死 `proxies={"http": None, "https": None}`。防止某线程因代理报错抛出未捕获异常，导致 `completed_count` 永远不达标，后处理线程永久 `wait()` 死锁。 |
| **超时控制** | API无超时导致任务挂起死锁 | 针对模型预设合理 timeout。必须在并发任务启动前将超时参数传入，**B模型turbo强制 300 秒，A模型强制 600 秒**。超时抛出异常时，在 `finally` 块中加锁写入 `status="timeout"`，确保计数器累加。 |
| **内容空值** | content为空污染后处理流 | API 返回后、加锁写入前，插入单测级断言：`if not content or content.strip() == "": raise EmptyContentError`。捕获该错误后，在锁内写入错误占位符，防止空耗 reasoning 的无效数据进入后处理流程。 |
| **配置版本** | 配置修改后未生效 | 引入 `config_version` 字段。每次修改配置后版本+1，API 调用线程读取配置时比对版本，不一致则拒绝请求并重载配置。写入全局 Map 时记录 `config_ver`，后处理时校验版本一致性。 |

### 四、 异常兜底与状态恢复机制

针对多线程死锁或异常退出的极端情况，锁机制需提供兜底：

1. **超时唤醒机制**：后处理线程的 `condition.wait(timeout=650)`，最大等待时间略大于 A 模型最长超时（600s）。若超时唤醒，则遍历 `global_result_map`，将未标记 `completed` 的任务强制标记为 `status="lost"`，继续执行串行后处理，避免引擎永久挂起。
2. **写锁粒度控制**：临界区（`with global_lock` 内）**严禁包含 I/O 操作**（如网络请求、文件读写）。仅允许内存字典赋值和计数器自增，确保锁的持有时间在微秒级，彻底消除写写覆盖与读写阻塞。
