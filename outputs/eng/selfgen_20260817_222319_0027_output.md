# 任务类型: eng

推演一个基于 Supabase 的“记忆脑”（AI 记忆系统）增量同步方案，核心挑战在于**保持本地状态与云端数据库的一致性**，同时**降低网络开销**和**处理多端/多智能体并发修改带来的冲突**。

以下是完整的增量同步方案推演，分为四个核心模块：

---

### 一、 整体架构设计

**核心思路：本地 SQLite（或 JSON 索引）作为影子库，Supabase Postgres 作为中央事实源。**

*   **本地端：** 监听文件系统变化，维护本地索引（记录文件 Hash、最后修改时间、同步状态）。
*   **云端：** Supabase 存储实际记忆数据（结构化表 + 向量列）。
*   **同步层：** 基于“时间戳 + 逻辑时钟”的增量拉推机制。

#### 1. Supabase 数据表设计
```sql
-- 记忆脑核心表
CREATE TABLE memories (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    user_id UUID REFERENCES auth.users(id),
    -- 内容与元数据
    content TEXT,
    embedding VECTOR(1536), -- 向量列
    source_path TEXT,      -- 对应的本地文件路径
    file_hash TEXT,        -- 文件内容的 Hash 值
    -- 同步与冲突处理字段
    created_at TIMESTAMPTZ DEFAULT now(),
    updated_at TIMESTAMPTZ DEFAULT now(),
    deleted_at TIMESTAMPTZ, -- 软删除标记
    version INTEGER DEFAULT 1 -- 乐观锁/版本号
);

-- 索引优化
CREATE INDEX idx_memories_user_updated ON memories(user_id, updated_at);
CREATE INDEX idx_memories_source_path ON memories(source_path);
```

---

### 二、 检测本地文件变化

为了实现真正的“增量”，不能每次都全量扫描文件内容。

#### 1. 监听机制
*   **主动监听（实时性高）：** 使用 Node.js 的 `chokidar` 或 Python 的 `watchdog` 监听文件系统事件（`add`, `change`, `unlink`）。
*   **轮询扫描（兜底策略）：** 定时遍历目录，对比文件状态。

#### 2. 本地状态追踪
在本地维护一个 SQLite 数据库 `local_memory_index.db`：
```sql
CREATE TABLE local_memories (
    source_path TEXT PRIMARY KEY,
    file_hash TEXT,        -- md5 或 sha256
    local_mtime INTEGER,  -- 本地修改时间戳
    sync_state TEXT,      -- 'synced', 'pending_push', 'pending_pull', 'conflict'
    remote_version INTEGER-- 记录云端当前的 version
);
```

#### 3. 变更判定算法
当监听到文件变化时：
1.  **计算 Hash：** 读取文件内容计算 `file_hash`。
2.  **对比本地索引：**
    *   若 Hash 未变 -> 忽略（只是 touch 修改了时间）。
    *   若 Hash 变化 -> 更新本地索引 `sync_state = 'pending_push'`。
    *   若文件删除 -> 标记 `sync_state = 'pending_push'` 且逻辑删除。

---

### 三、 只同步变更部分

同步分为 Push（本地推云端）和 Pull（云端拉本地）。

#### 1. Push（本地变更推送到 Supabase）
收集所有 `sync_state = 'pending_push'` 的记录，批量处理：

*   **新增/修改文件：**
    1.  提取记忆内容。
    2.  **本地计算 Embedding**（或调用 Supabase Edge Function / OpenAI API 计算）。
    3.  通过 Supabase JS Client 执行 `upsert` 操作：
        ```javascript
        // 批量 upsert 示例
        const { data, error } = await supabase
          .from('memories')
          .upsert(batchData.map(item => ({
              source_path: item.path,
              content: item.content,
              embedding: item.embedding,
              file_hash: item.file_hash,
              updated_at: new Date().toISOString(),
              version: item.remote_version + 1 // 递增版本号
          })), { onConflict: 'source_path' });
        ```
*   **删除文件：**
    将云端对应记录的 `deleted_at` 设置为当前时间（软删除）。

#### 2. Pull（云端变更拉取到本地）
拉取自上次同步以来的云端变更。
1.  记录本地最后同步时间 `last_sync_time`。
2.  调用 Supabase RPC（远程过程调用）或直接查询：
    ```javascript
    const { data } = await supabase
      .from('memories')
      .select('*')
      .gt('updated_at', last_sync_time)
      .order('updated_at', { ascending: true });
    ```
3.  遍历 `data`，根据 `deleted_at` 决定本地是否删除文件/索引，根据 `updated_at` 决定是否覆盖本地内容。

### 四、 处理冲突

当本地文件被修改（`pending_push`），同时云端也被修改（Pull 时发现 `updated_at` 大于本地记录时间），即发生冲突。

#### 冲突检测机制：乐观锁 + 时间戳
1.  本地准备 Push 时，检查本地 `remote_version` 是否与云端匹配。
2.  如果云端 `version` 大于本地 `remote_version`，说明云端已被其他端修改，触发冲突。

#### 冲突解决策略
针对“记忆脑”场景，推荐以下策略：

**策略 A：云端优先 + 追加合并（推荐用于 AI 记忆）**
AI 记忆通常允许冗余。如果发生冲突，不覆盖任何一方，而是将本地的修改作为一条**新的记忆片段**插入云端。
*   *逻辑：* 本地文件 A 修改了，云端记忆 A 也修改了。Push 时检测到冲突 -> 放弃 Update，改为 Insert 一条 `source_path = A_v2` 的新记忆。

**策略 B：Last-Write-Wins (LWW) 严格覆盖**
如果记忆必须与文件严格绑定。
1.  **时间戳比较：** 比较本地文件 `local_mtime` 与云端 `updated_at`。
2.  若本地较新，强制 Push（携带最新的 `version` 进行 upsert）。
3.  若云端较新，放弃本地 Push，将云端内容覆盖回本地文件。

**策略 C：保留分叉**
在 Supabase 中增加一张 `memory_history` 表。发生冲突时，将旧版本移入历史表，主表记录最新版本，并在元数据中标记 `had_conflict: true`，等待用户或后续 AI Agent 进行合并。

#### 冲突处理代码推演：
```javascript
async function pushMemory(localItem) {
    // 1. 尝试查询云端当前状态
    const { data: remote } = await supabase
        .from('memories')
        .select('version, updated_at, file_hash')
        .eq('source_path', localItem.source_path)
        .single();

    if (remote) {
        // 2. 冲突检测：版本号不匹配 且 hash 不同
        if (remote.version > localItem.remote_version && remote.file_hash !== localItem.file_hash) {
            console.log(`Conflict detected on ${localItem.source_path}`);
            
            // 策略 A: 追加为新记忆 (生成新ID，不绑定原文件)
            await supabase.from('memories').insert({
                content: localItem.content,
                embedding: localItem.embedding,
                source_path: `${localItem.source_path}_conflict_${Date.now()}`,
                file_hash: localItem.file_hash,
                version: 1
            });
            
            // 拉取云端最新内容覆盖本地，解决本地状态
            await pullAndOverwriteLocal(localItem.source_path, remote);
            return;
        }
    }

    // 3. 无冲突，正常 upsert
    await supabase.from('memories').upsert({
        source_path: localItem.source_path,
        content: localItem.content,
        embedding: localItem.embedding,
        file_hash: localItem.file_hash,
        version: (remote?.version || 0) + 1
    }, { onConflict: 'source_path' });
}
```

### 五、 关键优化点

1.  **Embedding 计算降本增效：**
    检测到文件变化后，不要对整个文件重新向量化。利用 LangChain/LlamaIndex 的文本分割器，只对文件中**变化的 Chunk** 计算 Embedding。这需要在本地索引中细化到 `Chunk` 级别，而不是 `File` 级别。
2.  **Supabase Realtime 旁路监听：**
    可以利用 Supabase Realtime (WebSocket) 订阅 `memories` 表的变更。当其他设备/后端 Agent 修改了云端记忆时，本地能立刻收到推送触发 Pull，而不必依赖定时轮询。
3.  **网络中断恢复：**
    本地 `sync_state` 机制天然支持断点续传。网络恢复后，只要扫描 `sync_state != 'synced'` 的记录继续 Push 即可。
