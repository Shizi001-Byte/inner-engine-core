# 任务类型: eng

基于“AI引擎=数字智能物种”的演化生物学映射，多模型成本监控与熔断系统不仅是工程的资源管控，更是**智能物种在不同生态位（模型）下的代谢调节与生存防御机制**。当某个生态位的能量消耗（成本）触及生存红线时，强制进入“冬眠（熔断）”，并切换至低耗能生态位（降级），同时将未完成的捕食行为（等待任务）封存在短期记忆（队列）中，待环境复苏后回放（补跑）。

以下是严格规避历史踩坑经验、基于CAS（复杂适应系统）视角的系统设计方案：

### 一、 演化生物学映射公理

| 演化生物学术语 | 对应AI引擎的工程实体 |
| :--- | :--- |
| **生态位适应** | 多模型路由（A模型、B模型turbo等不同算力/成本生态位） |
| **代谢成本** | API调用产生的费用消耗 |
| **代谢休克/冬眠** | 触发成本阈值的自动熔断 |
| **生态位降级转移** | 高成本模型熔断后自动降级至备用模型 |
| **短时记忆印刻** | 熔断期间等待任务的持久化记录（基于悲观锁） |
| **记忆回放/复苏** | 冷却结束后的自动补跑机制 |

---

### 二、 核心工程架构设计

#### 1. 状态记忆体
**避坑约束：九维计数语义必须清晰，所有参数从state读取，拒绝硬编码。**

```python
class ModelMetabolicState:
    def __init__(self):
        # 1. 模型身份严格隔离（防止Pro/Turbo混用导致推理慢/成本高）
        self.model_registry = {
            "A_Model": {"id": "model-a-pro-v1", "timeout": 600, "cost_limit": 50.0},
            "B_Turbo": {"id": "doubao-seed-2-1-turbo", "timeout": 300, "cost_limit": 20.0}, # 严格核对model_id
        }
        
        # 2. 计数语义统一（遵循坑库预警3）
        # task_count: 仅真实业务任务计数
        # bonus_count: 仅系统自触发(如重试/自检)计数
        # count: = task_count + bonus_count
        self.metrics = {
            "A_Model": {"task_count": 0, "bonus_count": 0, "count": 0, "total_cost": 0.0},
            "B_Turbo": {"task_count": 0, "bonus_count": 0, "count": 0, "total_cost": 0.0}
        }
        
        # 3. 熔断状态与冷却（遵循坑库预警2，参数完全从state读取）
        self.fuse_status = {
            "A_Model": {"is_fused": False, "fuse_cooldown_override": 600, "fused_until": 0},
            "B_Turbo": {"is_fused": False, "fuse_cooldown_override": 300, "fused_until": 0}
        }
        
        # 4. 记忆印刻池（等待任务队列），使用悲观锁保障一致性
        self.waiting_queues = {
            "A_Model": [],
            "B_Turbo": []
        }
        self.archive_lock = threading.Lock() # 认知锚定1：必须是悲观锁
```

#### 2. 实时监控与熔断降级（免疫响应）
**避坑约束：配置修改后立即验证生效，防止熔断冷却不生效。**

```python
def monitor_and_fuse(model_key, cost_increment, is_bonus=False):
    state = ModelMetabolicState()
    model_id = state.model_registry[model_key]["id"]
    
    # 统一加操作规则（遵循坑库预警3）
    if is_bonus:
        state.metrics[model_key]["bonus_count"] += 1
    else:
        state.metrics[model_key]["task_count"] += 1
    state.metrics[model_key]["count"] = (
        state.metrics[model_key]["task_count"] + 
        state.metrics[model_key]["bonus_count"]
    )
    state.metrics[model_key]["total_cost"] += cost_increment

    # 实时验证熔断配置生效（遵循避坑提醒1）
    cost_limit = state.model_registry[model_key]["cost_limit"]
    if state.metrics[model_key]["total_cost"] >= cost_limit:
        # 避坑：从state读取override，全局常量仅作兜底
        cooldown = state.fuse_status[model_key].get("fuse_cooldown_override", 120)
        state.fuse_status[model_key]["is_fused"] = True
        state.fuse_status[model_key]["fused_until"] = time.time() + cooldown
        print(f"[免疫响应] {model_key} 触发熔断！冬眠 {cooldown} 秒。准备降级转移...")
        return True
    return False

def route_or_fallback(model_key, task_payload):
    state = ModelMetabolicState()
    
    # 避坑：严格核对完整model_id，防错配
    target_model = state.model_registry[model_key]["id"]
    
    if state.fuse_status[model_key]["is_fused"]:
        # 降级转移：A挂了去B，B挂了抛异常或转入低频模式
        fallback = "B_Turbo" if model_key == "A_Model" else None
        if fallback and not state.fuse_status[fallback]["is_fused"]:
            return execute_model_call(fallback, task_payload, is_fallback=True)
        else:
            return archive_waiting_task(model_key, task_payload)
    else:
        return execute_model_call(model_key, task_payload)
```

#### 3. 等待任务记忆印刻
**避坑约束：`archive_lock` 必须是悲观锁，确保任务不丢、数据不失真。**

```python
def archive_waiting_task(model_key, task_payload):
    state = ModelMetabolicState()
    # 认知锚定1：悲观锁，确保高并发下任务入队不混乱
    with state.archive_lock:
        # 这里入队的task_payload必须包含完整的上下文，以便复苏后补跑
        task_record = {
            "task_id": generate_uuid(),
            "payload": task_payload,
            "timestamp": time.time(),
            "status": "WAITING_IN_DORMANCY"
        }
        state.waiting_queues[model_key].append(task_record)
        print(f"[记忆印刻] {model_key} 熔断中，任务 {task_record['task_id']} 已锁定入队。")
        return {"status": "QUEUED", "task_id": task_record["task_id"]}
```

#### 4. 复苏与自动补跑
**避坑约束：根据任务类型预设合理timeout。**

```python
def check_recovery_and_replay():
    state = ModelMetabolicState()
    
    for model_key, status in state.fuse_status.items():
        if status["is_fused"] and time.time() >= status["fused_until"]:
            # 复苏
            status["is_fused"] = False
            print(f"[记忆回放] {model_key} 冬眠结束，开始补跑等待任务...")
            
            # 获取该模型专属的超时时间（避坑提醒2）
            timeout = state.model_registry[model_key]["timeout"]
            
            # 悲观锁取出待补跑任务
            with state.archive_lock:
                queue = state.waiting_queues[model_key].copy()
                state.waiting_queues[model_key].clear()
            
            for task_record in queue:
                try:
                    # 同步补跑，注意此处的超时控制
                    result = execute_model_call(
                        model_key, 
                        task_record["payload"], 
                        timeout=timeout
                    )
                    # 触发回调或更新任务状态
                    notify_task_completion(task_record["task_id"], result)
                except TimeoutError:
                    print(f"[补跑失败] 任务 {task_record['task_id']} 超时，重新入队或标记失败。")
                    # 视策略决定是否重新入队
                    with state.archive_lock:
                        state.waiting_queues[model_key].append(task_record)
                    break # 防止阻塞太久，等下一轮复苏
```

### 三、 避坑实施检查清单

1. **[防Pro/Turbo混用]** 在 `model_registry` 初始化时，必须拉取最新官方文档比对 `model_id`，并在日志层增加断言：`assert "turbo" in target_model` 或类似校验，防止型号错配导致推理慢162秒且reasoning占比80%+。
2. **[防硬编码熔断]** 在 `monitor_and_fuse` 函数中，强制使用 `state.fuse_status[model_key].get("fuse_cooldown_override")`，配置中心修改该值后，系统必须在下一个心跳周期打印 `Read cooldown: {cooldown}` 立即验证生效。
3. **[防计数语义混乱]** 严禁直接对 `metrics.count` 进行 `+= 1` 操作。必须提供统一的内部方法 `increment_model_count(model, task_type)`，强制区分 `task_count`（真实）与 `bonus_count`（系统触发），确保 `count = task + bonus` 永远成立。
4. **[防API超时]** 在 `execute_model_call` 的底层HTTP请求中，从 `model_registry` 注入 `timeout`，A模型严格设600秒，B模型turbo严格设300秒。
