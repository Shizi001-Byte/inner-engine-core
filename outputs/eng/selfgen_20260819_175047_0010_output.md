# 任务类型: eng

# 引擎任务链式推演机制

## 1. 机制总览

把“核心议题”看作状态机初始态 `S0`。每一轮 `R_i` 都是一次状态跃迁：

- 输入：上一轮已通过验证的状态 `S_{i-1}`
- 输出：本轮新状态 `S_i`
- 门禁：`S_i` 必须通过验证 `V_i`，才能成为下一轮输入

所以依赖关系是：

```text
S0
 │
 ▼
R1 ──> S1 ──> V1 ──(pass)──> R2 ──> S2 ──> V2 ──(pass)──> R3
                                │
                                └──(fail)──> R2 或 R1（受控回退）
```

标准情况下使用 5 轮：定义 → 分析 → 方案 → 验证 → 落地。  
简单议题可折叠为 3 轮：定义+分析 → 方案 → 验证+落地。  
复杂议题最多 5 轮，超过 5 轮说明拆解粒度不对，应回到 `R1` 重新定义。

---

## 2. 标准 5 轮定义与任务依赖

| 轮次 | 核心任务 | 输入 | 输出 | 验证门禁 |
|---|---|---|---|---|
| `R1` 定义 | 明确真实问题、成功指标、约束、可自动化边界 | 核心议题 `S0` | `S1`：问题定义、指标、约束、风险清单 | 指标可量化？约束无冲突？不是伪议题？ |
| `R2` 分析 | 找根因、瓶颈、可干预点 | `S1` | `S2`：根因链、瓶颈清单、杠杆点 | 每个瓶颈有数据或逻辑支撑？ |
| `R3` 方案 | 生成候选方案，选择推荐方案，设计执行依赖 | `S2` | `S3`：候选方案、推荐方案、执行依赖图、资源预算 | 方案覆盖根因？资源/超时可行？依赖无环？ |
| `R4` 验证 | 小规模试点/模拟，验证方案有效性和配置变更 | `S3` | `S4`：试点结果、证据、配置变更清单 | 指标达标？配置已 `sync --check`？行为变化已验证？ |
| `R5` 落地 | 部署上线、监控、回读验证 | `S4` | `S5`：上线报告、监控数据、回滚方案 | 线上指标回读？双实例状态一致？ |

关键规则：

- `R2` 的输入是 `R1` 的输出，`R3` 的输入是 `R2` 的输出，以此类推。
- 每一轮输出必须是结构化 artifact，不能只是“讨论记录”。
- 每一轮输出未通过验证时，不能进入下一轮。

## 4. 状态同步与回读验证

### 4.1 每次同步后必须回读验证

每一轮 `R_i` 产生 `S_i` 后，不能直接信任写入成功，必须：

```text
写入 S_i → 执行 sync --check → 从实际读取点读回 S_i → 比对一致 → 标记完成
```

如果读回内容不一致，本轮不算完成，需要重新同步。

### 4.2 配置修改后必须 sync --check 验证生效

历史教训：配置修改后未生效，行为无变化。

所以本机制强制要求：

- 新增配置必须同步修改“读取点”；
- 修改配置后立即执行 `sync --check`；
- 确认实际读取到的值等于期望值；
- 再跑一条冒烟用例，确认行为真的变化；
- 之后才允许进入下一轮。

示例：

```text
R4 修改了派单策略参数
→ 写入新配置
→ 同步修改 R5 实际读取配置的代码/路径
→ 执行 sync --check，确认读取到新参数
→ 跑一条冒烟样例，确认行为变化
→ 才允许 R5 开始
```

### 4.3 高可用执行底座

按已验证认知：至少 2 个引擎实例，但不需要 systemd / supervisor / k8s 这类外部守护进程。

落地方式：

- 两个引擎实例通过内部心跳互相发现、互相接管；
- 状态 `S_i` 在实例之间互相复制；
- active 实例故障时，standby 从最近一个已通过验证的状态继续，不重跑整条链；
- 不引入外部守护进程。

## 5. 超时与失败处理

历史教训：API 调用超时，任务未在规定时间内返回。

因此每个任务启动前必须按模型类型预设 timeout：

| 模型 | 单次 API 调用超时 |
|---|---|
| B-turbo | 300 秒 |
| A | 600 秒 |

处理规则：

- 超时后本轮输出作废；
- 不无限重试；
- 将当前轮拆成更小的子任务，例如 `R3-a`、`R3-b`、`R3-c`；
- 子任务之间继续使用相同依赖规则；
- 若一轮内多次超时，重新检查拆解粒度，而不是盲目增加 timeout。

## 6. 内置历史经验与认知锚定

本机制直接固化以下原则：

- **实践碾压学历**：每一轮只做“最小可验证产物”，不要求先学完整理论再动手。
- **真实痛点驱动**：`R1` 必须验证议题来自真实、重复、低效、可自动化的场景，否则终止。
- **高频迭代反馈闭环**：验证门禁就是反馈闭环，失败快速回退修正。
- **算力极限利用**：`R3` 必须给出模型选择与 token 预算，优先用 B-turbo 做快速迭代，A 做深度决策。
- **状态机升维**：每一轮的有效调用都是状态跃迁样本；成功和失败都沉淀到状态样本库，后续相似议题可以从某个 `S_i` 起步，而不是每次从 `S0` 开始。

## 7. 示例：外卖骑手调度 AI 引擎优化

- `S0`：午高峰订单延误率高
- `R1` 输出 `S1`：延误率降低 30%，预算 ≤ 800 万 token/日，覆盖区域 A/B
- `R2` 输出 `S2`：根因是“天气+出餐慢 → 预测不准 → 派单集中 → 骑手路线绕路”
- `R3` 输出 `S3`：方案 = 动态运力调度 + 路线推荐 + 订单分配；依赖图 = 天气数据接入 → 预测模型 → 派单策略 → 路线引擎
- `R4` 输出 `S4`：用历史数据模拟；修改派单策略配置后 `sync --check` 确认读取点已更新；试点延误率下降 28%，未达 30%，回退到 `R3` 调整策略；再试点达标
- `R5` 输出 `S5`：部署到 2 个引擎实例，互相发现/接管，无外部守护进程；上线后回读线上指标，确认生效

这样，整个任务链既有清晰的依赖图，又能保证“上一轮输出驱动下一轮输入”，同时把配置生效验证和超时控制变成强制门禁，避免历史踩坑。
