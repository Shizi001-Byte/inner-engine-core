# 任务类型: eng

# 多模型成本实时监控与自动熔断系统设计

## 0. 设计基线（基于已有认知锚定）

- **模型维度独立**：每个模型独立计数、独立熔断、独立降级链；不搞“全局熔断”。
- **状态必须原子**：所有计数与熔断状态切换走 Redis Lua 脚本；跨实例用分布式锁。
- **幂等保护**：任务级用 `task_id` 幂等；调用级用 `call_id` 防重。
- **配置动态生效**：所有可配置参数从 `state -> 配置中心 -> 全局默认值` 读取；全局常量只做兜底，禁止硬编码。
- **阴阳双轨**：
  - **阳轨**：在线实时路由、成本监控、熔断降级；
  - **阴轨**：等待任务记录、恢复后自动补跑、配置生效校验、对账自愈。  
  两条轨不互相替代，而是通过状态存储与 `task_id` 对账实现自衡。

## 1. 总体架构

```text
                     +-------------------+
                     |   配置中心/模型注册表  |
                     +---------+---------+
                               |
  Task ──> Router ──> CircuitBreaker ──> ModelAdapter ──> Model API
              │              │                  │
              │              v                  v
              │        State Store         Cost Monitor
              │        (Redis)           (滑动窗口成本)
              │              ^
              └──> Waiting Queue / Replay Scheduler
```

核心组件：

- **Router**：路由、降级、幂等检查、熔断前预检。
- **Cost Monitor**：按模型统计 token、成本、错误率、超时率、慢请求率。
- **CircuitBreaker**：每个模型独立状态机：`CLOSED / OPEN / HALF_OPEN`。
- **ModelAdapter**：真正调用模型 API，带正确 `model_id` 与超时。
- **Waiting Queue / Replay Scheduler**：熔断期间记录等待任务，恢复后自动补跑。
- **State Store**：Redis，保存计数、熔断状态、等待任务、配置覆盖项。

## 2. 模型注册与配置

### 2.1 模型注册表

必须使用官方文档完整 `model_id`，禁止简写、别名、混用。

示例：

| model_id | 系列 | 定位 | 超时 |
|---|---|---|---|
| `doubao-seed-2-1-pro` | A | pro | 600s |
| `doubao-seed-2-1-turbo` | B | turbo | 300s |
| `doubao-seed-2-1-light` | B | light | 120s |

- 配置里出现 `doubao-seed-2-1` 这种无后缀别名，启动直接失败。
- 接入新模型前必须核对官方文档的完整 `model_id` 与价格表。
- 请求与响应中的 `model_id` 必须一致；如果响应返回了不同 `model_id`，计入 `model_mismatch_count` 并触发告警/熔断。
- 如果模型支持 `reasoning_tokens`，且 `reasoning_tokens / output_tokens` 异常高（例如 >80%），可能是 pro 被当成 turbo 使用，需要告警。

### 2.2 动态配置读取

所有运行时参数必须通过统一函数读取：

```text
effective_config = state.get(model_id, key)
                  ?? config_center.get(model_id, key)
                  ?? DEFAULT_CONSTANTS.get(key)
```

例如：

```text
fuse_cooldown = state.get("model:doubao-seed-2-1-turbo:fuse.cooldown_override")
                ?? config_center.get("model.doubao-seed-2-1-turbo.fuse_cooldown")
                ?? DEFAULT_FUSE_COOLDOWN
```

禁止在业务代码里直接写：

```python
cooldown = 120  # 错误：这会覆盖 state 配置
```

配置变更后必须立即验证生效：

1. 更新配置。
2. 自增 `config_version`。
3. 所有实例 watch 到新版本。
4. 系统发起一个 `bonus_count` 的配置验证探针，读取实际生效配置并回传。
5. 与期望值不一致则告警并回滚。

## 3. 计数语义与状态存储

### 3.1 计数语义

统一规则：

- `task_count`：仅真实任务触发的模型 API 调用次数。
- `bonus_count`：仅系统自触发的模型 API 调用次数，例如探活、预热、配置验证。
- `count = task_count + bonus_count`，是派生值。
- `tasks_completed`：真实任务成功完成数，按 `task_id` 去重。
- `task_count` 不是 `tasks_completed`，两者不能互相替代。

| 指标 | 含义 | 更新时机 |
|---|---|---|
| `task_count` | 真实任务 API 调用次数 | 真实任务发起 HTTP 请求前 +1 |
| `bonus_count` | 系统自触发 API 调用次数 | 系统探针/预热发起请求前 +1 |
| `total_count` | 派生值 = task_count + bonus_count | 禁止直接累加 |
| `tasks_completed` | 真实任务成功完成数 | 成功响应后按 task_id 去重 +1 |
| `tasks_failed` | 真实任务最终失败数 | 任务重试耗尽后 +1 |
| `tasks_timeout` | 超时 API 调用次数 | 超时后 +1 |
| `tasks_slow` | 慢请求 API 调用次数 | 耗时 > slow_threshold 后 +1 |
| `error_count` | 所有 API 错误次数 | 任何 API 错误后 +1 |
| `model_mismatch_count` | 模型 ID 错配次数 | 响应 model_id 与请求不一致时 +1 |
| `cost_total` | 实际费用 | 根据 usage 与价格计算后累加 |

### 3.2 原子更新与幂等

普通计数必须通过原子脚本：

```lua
-- incr_by_type.lua
-- KEYS[1] = idem_key, KEYS[2] = model:{model_id}:counters
-- ARGV[1] = field, ARGV[2] = delta, ARGV[3] = ttl
if redis.call("SET", KEYS[1], 1, "NX", "EX", ARGV[3]) then
    redis.call("HINCRBY", KEYS[2], ARGV[1], ARGV[2])
    return 1
end
return 0
```

- 每次 API 调用生成 `call_id`，用 `call_id` 做计数幂等。
- 每个业务任务有 `task_id`，用 `task_id` 做任务状态幂等。
- 禁止直接 `INCR total_count`，必须走统一入口。

## 4. 熔断器状态机

每个模型独立状态：

```text
CLOSED --触发阈值--> OPEN
OPEN --冷却时间到--> HALF_OPEN
HALF_OPEN --探针成功--> CLOSED
HALF_OPEN --探针失败--> OPEN（冷却时间加倍）
```

### 4.1 触发条件

任一模型满足以下任一条件即熔断：

- 最近 1 分钟 / 1 小时 / 1 天成本超限。
- 最近 5 分钟错误率超过阈值。
- 最近 5 分钟超时率超过阈值。
- 最近 5 分钟慢请求率超过阈值。
- `model_mismatch_count` 超过阈值。

### 4.2 冷却时间

冷却时间必须从 state 读取：

```text
cooldown_until = now + cooldown * (2 ^ fuse_attempts)
```

- 如果熔断原因是成本超日限额，则 `cooldown_until` 应该是次日零点，而不是固定秒数。
- 如果 state 中配置了 `fuse_cooldown_override=300`，就必须用 300 秒，不允许用硬编码 120 秒。

## 5. 实时成本监控

### 5.1 成本计算

每个模型独立计价：

```text
cost = input_tokens * input_price
     + output_tokens * output_price
     + cache_read_tokens * cache_price
```

- 价格必须来自模型注册表。
- 禁止拿 pro 的价格算 turbo，也禁止拿 turbo 的价格算 pro。
- 如果响应没有返回 usage，不估算，记 `cost_unknown_count` 并告警。

### 5.2 滑动窗口

用 Redis ZSET 保存每个模型的成本窗口：

```text
model:{model_id}:cost:1m
model:{model_id}:cost:1h
model:{model_id}:cost:1d
```

每次调用完成后：

1. 用 `call_id` 做成员。
2. `ZADD` 写入当前时间戳与 cost。
3. 删除窗口外数据。
4. 在 Lua 中求和。
5. 如果超过阈值，触发熔断。

### 5.3 发送前成本预检

调用模型前，先检查：

```text
current_cost + worst_case_cost > cost_limit
```

如果已经会超限，则直接熔断，不再发起本次调用。

## 6. 降级链

每个模型独立配置降级链：

```text
model:doubao-seed-2-1-pro.degrade_chain = [
    "doubao-seed-2-1-turbo",
    "doubao-seed-2-1-light",
    "queue"
]
```

Router 逻辑：

```text
if 原模型 CLOSED:
    调用原模型
else if 任务允许降级:
    按降级链找第一个 CLOSED 模型并调用
else:
    进入等待队列
```

注意：

- 降级后，计数器按**实际调用模型**累加。
- 任务状态记录 `preferred_model` 和 `actual_model`。
- 降级链上的模型也必须是注册表中的完整 `model_id`。

## 7. 熔断期间等待任务与恢复补跑

### 7.1 等待队列

熔断期间，不能降级或不允许降级的任务进入等待队列：

```text
pending:{model_id}
```

使用 Redis Stream 或 List，任务内容包括：

```text
task_id
payload
preferred_model
allow_degrade
enqueue_time
attempts
```

同时设置：

```text
task:{task_id}:status = waiting
task:{task_id}:wait_model = model_id
```

### 7.2 恢复补跑

冷却时间到期后，进入 `HALF_OPEN`：

1. 系统发送探针任务，探针计入 `bonus_count`。
2. 探针成功：状态变为 `CLOSED`。
3. 探针失败：重新变为 `OPEN`，冷却时间翻倍。
4. 只有 `CLOSED` 后，Replay Scheduler 才开始消费等待队列。

Replay 时：

- 根据 `task_id` 检查任务状态。
- 如果已经是 `completed` 或 `failed`，跳过。
- 如果原模型仍然不是 `CLOSED`，重新放回队列，等待下次重试。
- 如果重试次数超过 `max_attempts`，标记为 `failed` 并告警。

## 8. 关键流程

### 8.1 正常调用

```text
Task 进入 Router
→ 检查 task_id 幂等
→ 读取配置
→ 检查熔断状态
→ 成本预检
→ task_count +1
→ 调用模型（带正确 model_id 和 timeout）
→ 记录 usage / cost
→ tasks_completed +1
```

### 8.2 熔断降级

```text
Task 进入 Router
→ 原模型 OPEN
→ 如果允许降级，按降级链找可用模型
→ 调用降级模型
→ 如果降级链全不可用，进入 pending 等待队列
```

### 8.3 恢复补跑

```text
冷却时间到
→ HALF_OPEN
→ 系统探针成功
→ CLOSED
→ Replay Scheduler 消费 pending 队列
→ 对每个 task_id 做幂等检查
→ 调用原模型补跑
```

## 9. 落地检查表

| 历史坑 | 本系统预防措施 |
|---|---|
| 配置修改后未生效 | 统一配置读取入口；配置变更后跑配置验证探针；不一致则回滚 |
| API 调用超时 | 按模型配置 timeout：B turbo 300s，A pro 600s；HTTP client 必须使用 context deadline |
| B 模型型号错配 | 模型注册表使用完整 model_id；响应 model_id 校验；reasoning_tokens 占比异常告警 |
| 熔断冷却配置不生效 | 冷却时间从 state 读取；`fuse_cooldown_override` 必须生效；全局常量只兜底 |
| 九维计数语义混乱 | 禁止裸 `count`；`task_count`、`bonus_count`、`tasks_completed` 严格区分；`count=task+bonus` 为派生值 |
| 并发竞态 | 计数用 Lua 原子脚本；熔断状态切换用分布式锁；API 调用期间不持锁 |
| 重复执行/重复计数 | `task_id` 做任务幂等；`call_id` 做调用计数幂等 |

---

这套系统以“每个模型独立自治”为边界，以“阴阳双轨”处理在线降级与离线补跑之间的矛盾，最终实现：

- 成本实时可控；
- 单模型故障不影响全局；
- 熔断期间不丢任务；
- 恢复后自动补跑；
- 所有计数、配置、状态都可审计、可对账、可回滚。
