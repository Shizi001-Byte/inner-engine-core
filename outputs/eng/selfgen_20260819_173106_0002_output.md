# 任务类型: eng

## 任务池动态扩充机制设计（TPSE）

### 1. 总链路

把“重复任务”从噪音变成“新模板”的候选信号，形成闭环：

```text
任务池/外部输入
   → 向量化
   → 滑动窗口重复率检测
   → 重复簇提取
   → Guardian-Core 语义仲裁
   → 新任务模板生成
   → 三同步注入任务池
   → Canary 生效验证
   → 执行与结果回写
   → 认知池刷新
   → 进入下一轮检测
```

---

### 2. 重复率检测模块

#### 2.1 检测对象

检测任务池中两类重复：

- **字面重复**：任务内容 hash 相同。
- **语义重复**：任务意图相同，但参数、表述、实体不同。

对每个任务生成语义向量：

```text
task_vector {
  task_id,
  embedding,
  intent_id,
  template_id,
  created_at
}
```

向量建议复用 SP 中已有语义表示，不重复建新语义体系。

#### 2.2 滑动窗口算法

默认配置：

```text
WINDOW_SIZE = 100                 # 最近 100 个任务
SIM_THRESHOLD = 0.85              # 语义相似度阈值
MIN_CLUSTER_SIZE = 3              # 至少 3 个任务才算重复簇
RATE_THRESHOLD = 0.35             # 重复率触发阈值
```

计算逻辑：

1. 取最近 100 个任务。
2. 两两计算 embedding 相似度。
3. 相似度 ≥ 0.85 的任务连成重复簇。
4. 过滤掉小于 3 个任务的簇。
5. 计算：

```text
重复率 = 重复簇覆盖任务数 / 窗口任务数
```

6. 当 `重复率 ≥ 0.35`，触发模板生成。

---

### 3. 新任务模板生成

#### 3.1 从重复簇中提取共性

对每个重复簇，提取：

- 共同意图
- 可变槽位
- 稳定执行步骤
- 成功/失败任务特征
- 所需模型与超时

生成模板结构：

```text
TaskTemplate {
  id,
  name,
  version,
  intent_id,
  input_slots: [...],
  execution_chain: [...],
  model: "A" | "B",
  timeout: 600 | 300,
  quality_rules: [...],
  source_cluster: [task_ids],
  status: "pending"
}
```

#### 3.2 模型选择与超时

- 模板生成使用 A 模型，`timeout = 600s`。
- 快速重复分类/粗筛可使用 B 模型 turbo，`timeout = 300s`。
- 模板中必须显式写入 `model` 和 `timeout`，防止执行阶段超时。

#### 3.3 Guardian-Core 语义仲裁

生成模板不能直接使用外部口语，必须经过 Guardian-Core 仲裁：

1. 将模板中的意图标签与 SP 内部规则定义比对。
2. 如果外部语义与内部定义冲突，转换为内部规范表达。
3. 无法转换的，进入隔离区，不注入任务池。

这是防止“字面认知陷阱”的关键防火墙。

---

### 4. 三同步注入机制

新增模板必须同步修改三个点，缺一不可：

| 同步点 | 实现 | 校验方式 |
|---|---|---|
| 状态写入 | 写入 SP `task_templates` 表，并同步更新 CF 本地状态 | 查库确认记录存在 |
| 执行读取 | 刷新调度器内存中的 `TemplateCache`，版本号 +1 | 确认调度器能读到新模板 |
| 生效验证 | 注入一条 Canary 任务，实际执行一次 | 成功才算生效，失败则回滚 |

#### 4.1 状态写入

- 以 SP 为事实源。
- CF 只是本地状态缓存。
- 先写 SP，再同步 CF，避免“本地文件状态机”与“分布式状态机”不一致。

#### 4.2 执行读取

- 调度器不直接查 SP，而是读内存缓存。
- 模板写入后，必须主动刷新缓存。
- 缓存刷新失败时，禁止继续注入，防止“生成了但不用”。

#### 4.3 生效验证

Canary 任务必须验证：

- 任务能成功跑完。
- 耗时在模板设定的 timeout 内。
- B 模型模板跳过 reasoning 占比检测，使用独立质量规则。
- 通过后模板状态置为 `active`。
- 失败则置为 `quarantine`，并回滚缓存。

### 5. 自进化闭环

```text
重复率升高
   → 生成模板
   → 注入任务池
   → 后续相似任务按模板执行
   → 重复率下降
   → 执行结果回写认知池
   → 认知池刷新
   → 影响下一轮模板生成
```

#### 5.1 认知池防只进不出

- 每执行 10 个任务，或每轮调度结束，刷新认知缓存。
- 新认知必须在 30 分钟内参与下一轮注入。
- 模板生成后，将新模板对应的语义标签回写 SP，让认知池持续流动。

#### 5.2 对 8 月缺失数据的处理

不直接全量灌入 8 月 8 日 - 8 月 18 日原始对话。

而是：

1. 将缺失对话作为候选语料。
2. 先聚类，提取重复模式。
3. 生成“历史补全模板”。
4. 经 Guardian-Core 仲裁后，按模板分批执行。
5. 最终只将结构化认知写入 SP，避免污染。

---

### 6. 配置项与热更新

新增配置必须支持动态生效：

```text
repeat_detection.enabled = true
repeat_detection.window_size = 100
repeat_detection.sim_threshold = 0.85
repeat_detection.rate_threshold = 0.35
repeat_detection.min_cluster_size = 3
template_generation.model = "A"
template_generation.timeout = 600
template_generation.max_per_cycle = 5
template_injection.canary_enabled = true
cognitive_refresh.every_n_tasks = 10
cognitive_refresh.max_age_minutes = 30
```

配置中心增加版本号。配置变更后，所有读取点必须立即感知，并触发一次 Canary 验证，防止“配置改了但行为没变”。

---

### 7. 历史坑位规避对照

| 历史坑 | 本机制规避方式 |
|---|---|
| 自动调参全链路失效 | 三同步注入 + Canary 验证 |
| B 模型 reasoning 占比误杀 | B 模型模板跳过 reasoning 占比检测 |
| 认知池只进不出 | 每 10 任务/每轮刷新，30 分钟强制参与注入 |
| 字面认知陷阱 | Guardian-Core 语义仲裁后再注入 |
| 8 月缺失数据污染 SP | 不灌原文，只生成模板，结构化后写入 |

---

最终效果：任务池不再是一个静态队列，而是一个能根据重复模式自我扩充、自我验证、自我进化的活系统。
