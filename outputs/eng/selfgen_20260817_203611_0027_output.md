# 任务类型: eng

针对Supabase作为“记忆脑”（Memory Brain，通常用于AI Agent的长期记忆存储、知识库或笔记系统）的场景，增量同步是解决多端数据一致性、降低带宽和数据库负载的核心。

以下将推演一套完整的增量同步方案，包含本地文件变化检测、增量同步算法以及冲突处理机制，并附带伪代码。

---

### 一、 核心架构与数据模型

在Supabase中，我们需要两张表来支撑记忆文件的同步：

1.  **`memory_files` (文件元数据表)**：记录文件路径、版本号、哈希值、更新时间。
2.  **`memory_chunks` (文件内容块表)**：将大文件切片存储，或直接存储完整文本/向量。

#### Supabase 表结构设计 (伪 SQL)
```sql
-- 文件元数据表
CREATE TABLE memory_files (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES auth.users(id),
    file_path TEXT NOT NULL,
    content_hash TEXT NOT NULL,      -- 文件内容的SHA-256哈希
    version INT DEFAULT 1,          -- 乐观锁版本号
    updated_at TIMESTAMPTZ DEFAULT now(),
    is_deleted BOOLEAN DEFAULT false,
    UNIQUE(user_id, file_path)
);

-- 启用 RLS (Row Level Security)
ALTER TABLE memory_files ENABLE ROW LEVEL SECURITY;
```

### 二、 如何检测本地文件变化？

检测本地变化不能仅依赖文件的修改时间（`mtime`），因为有时内容没变但时间变了。应采用 **“修改时间初筛 + 内容哈希精准比对”** 的策略。

#### 算法：本地状态扫描
1.  遍历本地记忆目录。
2.  读取本地状态清单（`local_manifest.json`，记录上次同步的 `{path, mtime, hash}`）。
3.  如果文件不在清单中 -> 标记为 `Added`。
4.  如果文件在清单中，但 `mtime` 大于清单记录 -> 计算当前文件哈希：
    *   若哈希与清单不同 -> 标记为 `Modified`。
    *   若哈希相同 -> 标记为 `Unchanged`（仅更新本地 mtime 缓存）。
5.  清单中存在，但本地磁盘没有的文件 -> 标记为 `Deleted`。

#### 伪代码
```typescript
interface FileMeta { path: string; mtime: number; hash: string; }
interface LocalManifest { [path: string]: FileMeta }

interface ChangeSet {
    added: string[];
    modified: string[];
    deleted: string[];
}

function detectLocalChanges(localDir: string, lastManifest: LocalManifest): ChangeSet {
    const changes: ChangeSet = { added: [], modified: [], deleted: [] };
    const currentFiles = scanDirectory(localDir); // 返回所有当前文件的路径和mtime

    // 1. 检测新增和修改
    for (const file of currentFiles) {
        const lastMeta = lastManifest[file.path];
        if (!lastMeta) {
            changes.added.push(file.path);
        } else if (file.mtime > lastMeta.mtime) {
            const currentHash = calculateSHA256(file.path);
            if (currentHash !== lastMeta.hash) {
                changes.modified.push(file.path);
            }
            // 无论是否修改，更新本地mtime缓存以备下次比对
            lastManifest[file.path].mtime = file.mtime; 
        }
    }

    // 2. 检测删除
    for (const path in lastManifest) {
        if (!currentFiles.has(path)) {
            changes.deleted.push(path);
        }
    }

    return changes;
}
```

### 三、 如何只同步变更部分？

对于文本/Markdown等记忆文件，如果仅改了几个字，上传整个文件和重新生成所有向量是浪费的。可采用 **基于“行”或“块”的 Diff 算法**，或者为了系统简洁，采用 **基于“文件级哈希”的增量覆盖**。

考虑到 Supabase 的特性，推荐 **文件级增量（整体替换） + 懒加载向量更新** 的方案：
只把发生 `Added` 和 `Modified` 的文件内容上传到 Supabase Storage，并更新 `memory_files` 表的元数据。向量表 `memory_chunks` 可通过 Supabase Edge Functions 监听 `memory_files` 变更后异步更新。

#### 算法：增量同步推送
1.  从 Supabase 拉取远程 `memory_files` 最新元数据列表。
2.  遍历本地的 `ChangeSet`：
    *   **Added/Modified**: 比对本地哈希与远程哈希。若不同，上传文件内容到 Supabase Storage，并 Upsert 元数据。
    *   **Deleted**: 请求 Supabase 软删除该记录。
3.  拉取远程有但本地没有的变更（其他设备修改的）。

#### 伪代码
```typescript
async function pushChanges(changes: ChangeSet, localManifest: LocalManifest) {
    const remoteFiles = await supabase.from('memory_files').select('*');
    const remoteMap = new Map(remoteFiles.map(f => [f.file_path, f]));

    // 处理新增和修改
    for (const path of [...changes.added, ...changes.modified]) {
        const localHash = localManifest[path].hash;
        const remoteMeta = remoteMap.get(path);

        // 增量核心：只有远程不存在，或哈希不一致时才上传
        if (!remoteMeta || remoteMeta.content_hash !== localHash) {
            // 1. 上传实际内容到 Supabase Storage
            const fileContent = readFileContent(path);
            await supabase.storage.from('memory-brain').upload(path, fileContent, { upsert: true });

            // 2. 更新元数据表
            await supabase.from('memory_files').upsert({
                file_path: path,
                content_hash: localHash,
                updated_at: new Date().toISOString(),
                is_deleted: false
                // 注意：version 由数据库或冲突处理逻辑控制
            });
        }
    }

    // 处理删除
    for (const path of changes.deleted) {
        await supabase.from('memory_files')
            .update({ is_deleted: true, updated_at: new Date().toISOString() })
            .eq('file_path', path);
    }
}
```

### 四、 如何处理冲突？

**场景**：设备 A 和设备 B 同时修改了同一个记忆文件 `memory_1.md`，并尝试同步到 Supabase。

**解决方案：乐观锁 + 三分合并**

在 `memory_files` 表中利用 `version` 字段。客户端提交时必须带上它读取时的 `version`。

#### 算法：冲突检测与解决
1.  客户端 A 提交更新，附带 `expected_version = 1`。
2.  数据库当前 `current_version = 1`，更新成功，数据库 `version` 自增为 `2`。
3.  客户端 B 提交更新，附带 `expected_version = 1`。
4.  数据库当前 `current_version = 2`，版本不匹配，发生冲突。
5.  **冲突解决策略**：
    *   获取远程最新版本 (v2)、远程基座版本 (v1)、本地新版本。
    *   执行三方合并（例如使用 `diff-match-patch` 库针对文本进行合并）。
    *   若无冲突行：自动合并生成新文件，提交为 v3。
    *   若有冲突行：保留双方内容（如 `<<<<<<<` 和 `>>>>>>>` 标记），以远程版本为基座保存为 v3，并通知用户/Agent手动解决。

#### 伪代码
```typescript
async function syncWithConflictResolution(filePath: string, localContent: string) {
    const localMeta = localManifest[filePath];
    const expected_version = localMeta.version || 1;

    // 尝试使用乐观锁更新
    const { data, error } = await supabase.rpc('attempt_update_memory', {
        p_path: filePath,
        p_hash: localMeta.hash,
        p_expected_version: expected_version
    });

    if (error) {
        // 乐观锁失败，说明版本落后，触发冲突解决流程
        if (error.code === 'VERSION_CONFLICT') {
            await resolveConflict(filePath, localContent);
        }
    }
}

async function resolveConflict(filePath: string, localContent: string) {
    // 1. 拉取远程最新数据和远程基座（本地修改前的版本）
    const remoteLatest = await fetchRemoteFile(filePath); // 包含 v2 内容
    const baseContent = localMeta.baseContent; // 本地保存的 v1 内容

    // 2. 执行三方合并
    const mergedContent = threeWayMerge(baseContent, localContent, remoteLatest.content);

    // 3. 判断合并是否包含冲突标记
    const hasConflict = mergedContent.includes('<<<<<<<');

    // 4. 强制以新版本上传 (不带乐观锁条件，或带远程最新的 version)
    const newVersion = remoteLatest.version + 1;
    await supabase.storage.from('memory-brain').upload(filePath, mergedContent, { upsert: true });
    await supabase.from('memory_files').update({
        content_hash: calculateSHA256(mergedContent),
        version: newVersion,
        updated_at: new Date().toISOString()
    }).eq('file_path', filePath);

    if (hasConflict) {
        notifyAgentOrUser(filePath, "存在合并冲突，已生成合并文件，请检查。");
    }
}
```

*附：Supabase 端处理乐观锁的 PL/pgSQL 函数（部署在数据库中）：*
```sql
CREATE OR REPLACE FUNCTION attempt_update_memory(p_path TEXT, p_hash TEXT, p_expected_version INT)
RETURNS VOID AS $$
BEGIN
    UPDATE memory_files
    SET content_hash = p_hash, version = version + 1, updated_at = now()
    WHERE file_path = p_path AND version = p_expected_version;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'VERSION_CONFLICT';
    END IF;
END;
$$ LANGUAGE plpgsql;
```

### 五、 拉取远程变更（反向同步）

除了推送到云端，客户端还需要拉取其他设备的变更：

1.  客户端记录上次同步的时间戳 `last_sync_at`。
2.  查询 Supabase：`SELECT * FROM memory_files WHERE updated_at > last_sync_at`。
3.  遍历结果：
    *   如果 `is_deleted = true` -> 删除本地文件。
    *   如果本地不存在或哈希不同 -> 从 Storage 下载文件覆盖本地。
4.  更新 `last_sync_at` 为当前时间。

### 总结

这套方案的优点在于：
1. **低开销**：通过 `mtime` 初筛避免大量无用的哈希计算。
2. **细粒度增量**：通过比对哈希值，跳过未修改文件的上传。
3. **高可靠**：通过数据库层面的 `version` 字段实现乐观锁，结合文本三方合并解决多端编辑冲突，保障记忆脑的数据一致性。
