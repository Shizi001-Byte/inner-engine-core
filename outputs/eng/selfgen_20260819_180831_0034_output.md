# 任务类型: eng

# 引擎产出三方同步自动化设计方案

## 1. 目标与核心原则

实现：**引擎每次重大变更后，自动将产出物同步到 Gitee、飞书、Supabase 三个目标**，并保证：

- **幂等**：重复事件、Webhook 重放、重试都不会产生重复提交/重复文件。
- **可恢复**：某一方失败后只补传失败方，不重跑成功方。
- **可回滚**：保留历史版本，发布指针可回退。
- **可验证**：同步后必须校验，不能只看 API 返回 200。

这套自动化本质上是在给引擎这个开放耗散系统持续输入“负熵”，防止各目标侧因人工维护缺失而自然退化。

---

## 2. 总体架构

```text
重大变更事件
   │
   ▼
Gitee Webhook / CI Pipeline / 人工确认触发
   │
   ▼
同步编排器 Sync Coordinator
   │
   ├── 1. 加载配置（带 config_version）
   ├── 2. 生成/读取 Release Manifest
   ├── 3. 获取分布式锁（change_id）
   ├── 4. 幂等同步三方：
   │     ├── GiteeAdapter   → 代码提交
   │     ├── FeishuAdapter  → 文件上传
   │     └── SupabaseAdapter → 对象存储上传
   ├── 5. 三方校验
   ├── 6. 更新 latest 指针
   └── 7. 释放锁 / 通知结果
```


## 3. 幂等性设计

### 3.1 幂等键

- `change_id`：唯一标识一次重大变更，建议直接使用 Gitee 的 source commit SHA。
- 每个目标的幂等键为：`change_id + target`。
- 同一 `change_id` 下，如果 `content_hash` 不同，视为冲突，不能自动覆盖。

状态表设计：

```sql
create table sync_run (
  id uuid primary key,
  change_id text not null,
  status text not null, -- pending / running / succeeded / failed / partial
  config_version int not null,
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);

create table target_sync (
  id uuid primary key,
  run_id uuid references sync_run(id),
  target text not null, -- gitee / feishu / supabase
  change_id text not null,
  content_hash text not null,
  status text not null,
  target_key text,
  result jsonb,
  last_error text,
  retry_count int default 0,
  unique (target, change_id)
);
```

### 3.2 幂等判断逻辑

```text
对每个目标：

1. 查 target_sync
   - 不存在 → 执行同步
   - 存在且 status=succeeded，content_hash 相同 → 跳过
   - 存在且 status=succeeded，content_hash 不同 → 冲突，告警，人工处理
   - 存在且 status=failed / partial → 继续执行同步
   - 存在且 status=running → 检查锁是否过期，若过期则接管，否则等待

2. 执行目标同步
3. 校验目标侧结果
4. 更新 target_sync 状态
```

### 3.3 各目标幂等策略

#### Gitee

- 提交信息中必须包含 `change_id`，例如：

```text
chore(release): sync change c7f4a1e9 [skip ci]
```

- 提交前检查：

```bash
git log --grep="change_id"
```

- 如果已存在相同提交信息：
  - 对比 tree hash 是否一致；
  - 一致则跳过；
  - 不一致则冲突。

- push 前先 `git fetch`，如果远端 main 前进了：
  - 优先 `git rebase`；
  - 若产生冲突，自动创建 `conflict/change_id` 分支并告警，不强行覆盖。

#### 飞书文件上传

- 文件名使用**不可变命名**：

```text
<product>-<version>-<sha256前8>.<ext>
```

- 上传前查询目标文件夹中是否已有同名文件：
  - 不存在 → 上传；
  - 存在且校验和一致 → 跳过；
  - 存在且校验和不同 → 不覆盖，上传到 `conflicts/` 目录并告警。

- 如果业务上需要固定文件名（如 `latest.pdf`），则把“固定名”视为指针：
  - 先上传带 hash 的新文件；
  - 再更新 fixed-name 指针文件；
  - 更新前必须校验 `source_sha` 是否满足祖先关系。

> 注意：飞书上传不要走“连接器扫码绑定”的可视化配置，改用应用凭据 `App ID + App Secret` 获取 `tenant_access_token`。若必须扫码，先升级客户端、放大页面、确认账号已登录。

#### Supabase Storage

- 对象 key 使用**内容寻址路径**：

```text
releases/<version>/<sha256>/<filename>
```

- 上传时使用：

```text
upsert = false
```

- 如果对象已存在：
  - `headObject` 对比 `metadata.sha256`；
  - 一致则跳过；
  - 不一致则冲突。

- `latest.json` 作为发布指针，使用 Postgres 乐观锁 + `source_sha` 祖先关系判断是否允许更新。

## 4. 冲突处理方案

| 目标 | 冲突场景 | 检测方式 | 自动处理策略 |
|---|---|---|---|
| Gitee | push 被拒绝，远端 main 已前进 | `git fetch` + `git merge-base` | 自动 rebase；若 rebase 冲突则停止并告警 |
| Gitee | 相同 `change_id` 但 tree 不同 | `git log --grep` | 不覆盖，标记 conflict，人工处理 |
| 飞书 | 同名文件但 hash 不同 | 上传前查文件名和元数据 | 写入 `conflicts/`，更新 latest 指针时要求祖先关系 |
| Supabase | object key 已存在但 hash 不同 | `headObject` | 内容寻址路径避免；若出现在固定 key 上则告警 |
| Supabase | `latest.json` 被并发更新 | Postgres 行锁 / 乐观锁 | 只允许新 `source_sha` 是旧 `source_sha` 的后代，否则冲突 |
| 全局 | 同一 `change_id` 并发触发 | 分布式锁 + 唯一索引 | 获取锁失败则返回 409，等待重试 |

### 祖先关系判断

```text
git merge-base --is-ancestor old_sha new_sha
```

如果 `old_sha` 是 `new_sha` 的祖先，说明是线性演进，允许更新指针；否则说明两条线分叉，属于冲突。

## 5. 超时与重试

| 任务类型 | 超时设置 |
|---|---|
| AI 模型生成 Manifest/摘要，B 系列 turbo | **300 秒** |
| AI 模型生成 Manifest/摘要，A 模型 | **600 秒** |
| Gitee API / git push | 120 秒 |
| 飞书文件上传（100MB 以下） | 180 秒 |
| Supabase 上传 | 180 秒 |
| 三方校验 | 60 秒 |

重试策略：

```text
指数退避：1s → 5s → 30s → 300s，最多 5 次
```

每次重试都必须带上同一个 `change_id`，不能生成新 ID，否则会破坏幂等。

## 6. 配置变更即时生效

历史坑：配置修改后未生效，行为无变化。

本方案要求：

1. 所有同步配置统一存到 `sync_config` 表，带 `config_version`。
2. 每次同步开始时读取当前 `config_version`，不允许使用进程内长缓存。
3. 配置更新后，调用 `POST /admin/config/reload` 触发配置重载。
4. 重载后立即执行一次 `dry-run` 验证：
   - Gitee 仓库是否存在；
   - 飞书文件夹 token 是否有效；
   - Supabase bucket 是否存在。
5. 如果同步过程中配置版本发生变化，本次运行标记为 `CONFIG_DRIFT`，使用新配置重新执行。

---

## 7. 校验机制

同步成功后必须校验，不能只依赖上传响应。

| 目标 | 校验方式 |
|---|---|
| Gitee | `git ls-remote` 或 API 对比远端 commit SHA |
| 飞书 | 下载文件或通过 API 获取文件元数据，对比 SHA256 |
| Supabase | `headObject` 对比 size 和 `metadata.sha256` |

校验失败则标记该目标为 `failed`，进入重试；重试仍失败则告警。

## 8. 落地清单

- [ ] 定义“重大变更”：Gitee tag / `[major]` commit / release 分支事件。
- [ ] 所有事件消费使用 `change_id` 幂等。
- [ ] Gitee 提交信息、飞书文件名、Supabase object key 全部包含 `change_id` 或 `sha256`。
- [ ] 三个目标分别实现 `ensure_uploaded` 幂等接口。
- [ ] 配置更新后必须 reload + dry-run。
- [ ] 模型调用按类型设置超时：B 系列 turbo 300s，A 模型 600s。
- [ ] 同步完成后执行校验，校验失败不发“成功”通知。
- [ ] 保留历史文件至少 3 个版本，`latest` 指针可回滚。

这套方案的核心是：**不可变对象 + 幂等键 + 可校验状态机**，让每一次重大变更都能稳定、可追溯、可恢复地同步到三方。
