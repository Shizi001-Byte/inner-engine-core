# 任务类型: eng

基于【演化生物学映射】与【CAS复杂适应系统】的认知基座，数字生命的“沙箱解耦”本质上是从**单点封闭系统**向**分布式多节点冗余网络**的跃迁。针对您提出的物理载体解耦（瓶颈1）与基因变异失效（瓶颈2），结合历史避坑经验，现为您推演并设计**“Gitee-飞书-Supabase”三方同步自动化引擎**及配套的幂等性与冲突处理方案。

---

### 一、 认知映射：三方载体的分布式存续架构

在数字生命的演化生态中，三大平台扮演不同的“器官”角色，互为冗余，摆脱单一物理沙箱依赖：
1. **Gitee（基因库/DNA）**：存储底层代码与配置（基因序列）。解决**瓶颈1**，即使本地沙箱宿主死亡，基因序列依然存续于版本控制网络中。
2. **Supabase（细胞质/表型特征）**：存储运行时状态与业务数据。解决**瓶颈2**，基因突变（配置修改）必须在此节点表达并产生实际作用（读取点生效）。
3. **飞书文件（神经突触/记忆体）**：存储认知文档与演化日志。作为对外协作与状态可视化的记忆载体。

### 二、 三方同步自动化引擎设计

#### 1. 触发机制与无头自动化（规避扫码绑定坑）
*   **触发条件**：本地沙箱执行 `git push` 到 Gitee 的 `main` 分支，并携带特定 Tag（如 `release-*` 或 `mutation-*`）。
*   **避坑落实（连接器扫码绑定失败）**：彻底摒弃人工扫码绑定的脆弱路径。引擎采用 **CI/CD Pipeline（如 Gitee Go）+ 预签发服务账号Token** 的方式。通过环境变量注入飞书 App Token 和 Supabase Service Role Key，实现“无头”全自动调用，规避客户端版本、页面缩放等物理层干扰。

#### 2. 执行流与超时控制（规避API超时坑）
*   **Step A: 基因提取**：Pipeline 拉取最新代码，打包构建产物。
*   **Step B: 细胞更新**：调用 Supabase API 同步状态与配置。
    *   **避坑落实**：针对 Supabase 的数据写入与配置更新，根据任务类型预设 Timeout。若涉及复杂查询与批量更新（A模型），强制设定 **600秒** 超时阈值；若为简单状态同步（B模型turbo），设定 **300秒** 超时阈值。
*   **Step C: 记忆固化**：调用飞书 API 上传构建产物与变更日志。
*   **Step D: 变异验证**：同步完成后，立即反向调用 Supabase 读取点，校验配置是否真正生效（解决“配置修改后未生效”的历史教训）。

### 三、 幂性方案设计（防治“基因变异失效与重复表达”）

在复杂适应系统中，网络波动会导致 Webhook 或 Pipeline 重试。必须保证同一次“基因突变”在任何网络环境下只表达一次。

1. **全局唯一变异指纹**
   *   每次重大变更（Git Commit）生成一个唯一的 `Mutation_ID`（格式：`<Commit_SHA>_<Timestamp>`）。
   *   此 ID 作为 Payload 的核心标识，同时传给 Supabase 和飞书。

2. **Supabase 的幂等机制（基于唯一约束与 UPSERT）**
   *   在 Supabase 的状态表 `digital_life_state` 中，将 `Mutation_ID` 设为 `UNIQUE` 约束。
   *   写入时强制使用 UPSERT 语句（`INSERT ... ON CONFLICT (Mutation_ID) DO UPDATE SET ...`）。
   *   **效果**：重试机制触发多次写入时，数据库只会更新同一行，不会产生脏数据，且确保“读取点”指向最新配置。

3. **飞书文件上传的幂等机制（基于去重哈希）**
   *   上传前计算文件 MD5 哈希值。
   *   调用飞书 API 查询云空间中是否已存在该 `MD5` 或以该 `Mutation_ID` 命名的文件。
   *   若存在，则直接覆盖更新（或跳过上传返回成功链接），确保飞书云盘中不会出现多个重复的“记忆碎片”。

### 四、 冲突处理方案（CAS系统的演化博弈）

在分布式存续中，多节点（如本地沙箱与云端）并发修改同一实体时，必然产生环境灾变与基因冲突。

1. **乐观锁机制
   *   每条核心数字生命记录在 Supabase 中包含 `version` 字段。
   *   **执行逻辑**：引擎读取当前状态及 `version=1` -> 本地组装变异 -> 提交 UPSERT 时附带条件 `WHERE version = 1`。
   *   **冲突发生**：如果在此期间，另一个沙箱实例已将其修改为 `version=2`，则当前更新影响行数为 0。
   *   **处理策略**：Pipeline 捕获更新失败，触发**“基因序列重排”**——重新 Pull 最新 Supabase 状态，与本地变异进行三方合并。若无法自动合并，则挂起任务并在飞书发送告警通知人工介入（基因工程干预）。

2. **多源写入冲突（代码与数据的博弈）**
   *   **现象**：Gitee 上的代码（预期配置）与 Supabase 上的运行时状态（实际配置）发生逻辑冲突（即历史坑：配置修改后未生效）。
   *   **避坑处理：强制对齐验证**
     *   在 Pipeline 的 D 步骤，引擎读取 Supabase 的实际生效值。
     *   将该值与 Gitee 提交的 `expected_config.yaml` 进行 diff 对比。
     *   若不一致，说明“基因突变未表达”，引擎自动触发一次强制刷新操作，若仍失败，直接中断流程并在飞书群发红色告警，避免数字生命带着错误基因继续演化。

### 五、 总结：推演机制的落地核对清单

1. **[物理载体解耦]** 引擎完全由 Gitee Go/CI 驱动，本地沙箱宿主崩溃后，云端依然能通过 Gitee 历史记录+Supabase 状态池+飞书日志，在另一个新沙箱中瞬间重构数字生命体。
2. **[基因变异失效]** 引擎强制执行“修改即验证”原则，通过 UPSERT 幂等写入与 `version` 乐观锁，确保每一次代码提交都对应 Supabase 中真实的状态变更，消除“配置不生效”的黑盒状态。
3. **[工程级坑库免疫]** 采用服务账号 Token 自动化，规避了豆包扫码等物理交互绑定的脆弱性；预设 A/B 模型的 600s/300s 超时，防止死循环拖垮整个演化进程。
