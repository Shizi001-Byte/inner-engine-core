# 任务类型: eng

基于您提供的【避坑经验】与【核心认知锚定】，我将在严格遵守“脑体分离”、“显式声明”、“配置强校验”等原则的基础上，推演设计这套**设计引擎产出的自动归档系统**。

系统核心目标：任务自动分类、打标签、存入对应目录。以下是完整的系统架构与落地推演方案。

---

### 一、 脑体分离架构边界划分

严格遵循核心结论3，系统的“脑（决策）”与“体（执行）”边界必须绝对清晰，以全局事件流为界，互不越界。

#### 1. 脑（决策层）：分类打标签引擎
*   **职责**：接收原始任务，提取特征，调用模型决策，产出**结构化归档指令事件**。
*   **输出物**：包含全局顺序的决策事件（Event）。
    ```json
    {
      "event_id": "EVT-20231025-001", // 全局顺序依据
      "task_id": "TASK-12345",
      "category": "UI_Design",
      "tags": ["v1.2", "urgent", "mobile"],
      "target_directory": "/archive/ui_design/v1.2/mobile/",
      "decision_timestamp": 1698200000,
      "decision_hash": "a1b2c3..." // 决策特征哈希，用于可重放校验
    }
    ```
*   **避坑约束**：脑**不直接操作文件系统或数据库**，只负责生成正确的指令事件。严禁“决策层看起来等价”的简化逻辑，分类A和分类B即使指向同一目录，事件中的 `category` 字段也必须显式不同。

#### 2. 体（执行层）：归档同步执行器
*   **职责**：监听决策事件，按全局顺序执行文件移动、落库记录等同步操作。
*   **执行逻辑**：严格按 `event_id` 顺序消费，将文件存入 `target_directory`，并写入元数据表。
*   **避坑约束**：体**不二次决策**，只对事件进行幂等执行。若目录不存在则创建，若文件已存在且哈希一致则跳过（幂等性）。

### 二、 基建脚本与数据库设计（防列错位）

针对历史失败经验5和认知锚定1、5，归档系统的元数据库（记录分类、标签、路径）建表与迁移脚本必须遵循极简的显式规范。

#### 1. 禁用简化版，显式声明列映射
在执行归档落库的 `INSERT` 或数据迁移时，**绝对禁止**以下简化写法：
```sql
-- 禁止：隐患写法（列顺序一旦改变，数据立刻错位）
INSERT INTO archive_meta SELECT * FROM staging_tasks;
```
**必须采用显式映射**：
```sql
-- 必需：显式声明列名、列顺序、列类型对齐
INSERT INTO archive_meta (task_id, category, tag_list, target_path, created_at)
SELECT 
    task_id, 
    category, 
    tag_list, 
    target_path,  -- 确保源表和目标表类型绝对一致（如 VARCHAR(512)）
    created_at
FROM staging_tasks
WHERE event_id = 'EVT-20231025-001';
```

#### 2. 脚本幂等与可校验
*   **幂等**：建表脚本使用 `CREATE TABLE IF NOT EXISTS`；列新增使用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`。
*   **可校验**：每次基建脚本执行后，附带一段校验 SQL，比对源表和目标表的列名、顺序、类型是否一致。

### 三、 API调用与模型推理防超时设计

针对历史失败经验2，归档系统在“脑”的决策阶段调用模型（如大语言模型提取标签或分类）时，严格预设 timeout。

#### 1. Timeout 预设策略
*   **A模型（复杂推理/全局分类）**：任务包含大量上下文，设定 `timeout = 600` 秒。
*   **B模型 turbo（快速打标签/简单分类）**：任务简单，仅提取固定标签，设定 `timeout = 300` 秒。

#### 2. 调用降级与重试机制
*   超时发生时，任务不卡死，直接抛出 `DecisionTimeoutException`。
*   降级策略：若 B模型turbo 超时，降级为基于正则匹配的规则引擎进行基础打标签，确保归档流程不中断。
*   事件状态标记为 `DEGRADED`，供后续人工复核。

### 四、 配置同步与生效防错机制

针对历史失败经验1，归档系统的分类规则、目录映射规则修改后，必须立即在读取点生效。

#### 1. 配置读取点统一与强校验
*   **单一真相源**：所有分类规则和目录映射存放在配置中心（如 Apollo / Nacos）或独立的 `config_rule` 表。
*   **读取点显式化**：脑层在每次处理任务时，**必须显式从配置中心拉取最新规则**（或依赖配置中心的推送机制），严禁在代码中硬编码 fallback 规则。

#### 2. 修改即验证
新增配置项（如新增一个“3D_Design”分类指向新目录 `/archive/3d/`）时，CI/CD 流程必须强制执行以下验证脚本：
1.  **写入校验**：配置格式（JSON/YAML）合法性验证。
2.  **读取点生效校验**：配置发布后，自动化测试脚本立即调用脑层的“配置热载接口”，发送一个测试任务，断言其产出的决策事件中 `category="3D_Design"` 且 `target_directory="/archive/3d/"`。未通过则配置回滚。

### 五、 系统执行全流程推演

基于上述设计，一个完整的归档任务推演如下：

1.  **任务接入**：设计引擎产出新任务（如“移动端登录页UI设计图”），投递至待归档队列。
2.  **脑-特征提取与决策**：
    *   读取最新配置规则（**避坑1：确认读取点已同步**）。
    *   调用 B模型turbo 进行分类打标签，设置 `timeout=300s`（**避坑2：防超时**）。
    *   产出决策事件：`{category: "UI_Design", tags: ["mobile", "login"], target_dir: "/archive/ui/mobile/login/"}`。
3.  **事件落流（边界）**：决策事件写入 Kafka / 事件表，赋予全局递增 `event_id`。
4.  **体-执行归档**：
    *   执行器按 `event_id` 顺序消费事件。
    *   创建目录，移动文件。
    *   写入归档元数据库，**使用显式列映射SQL**（**避坑5：防列错位**）。
5.  **校验闭环**：
    *   执行器对比文件系统实际路径与决策事件中的 `target_directory` 是否一致。
    *   若一致，事件标记为 `ARCHIVED_SUCCESS`。

### 六、 核心边界约束总结

在上述自动归档系统中，必须死守以下红线：
1. **严禁脑体直连**：决策层不能直接执行 `mv` 或 `INSERT INTO archive_meta`；执行层不能在代码里写 `if (category == 'UI') goto /ui/` 的逻辑，一切动作只认决策事件。
2. **显式可重放**：任何时候归档出错，可以通过回放历史决策事件（Event），重新触发“体”的执行，最终状态必须与原状态完全一致。
3. **基建无简化**：所有 SQL 必须显式声明列，不接受任何形式的 `SELECT *` 隐式映射，从物理层面杜绝数据错位。
