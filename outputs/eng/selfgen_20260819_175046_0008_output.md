# 任务类型: eng

## 方案：基于“状态机 + 内容寻址”的三方同步自动化

核心思路：**把一次同步建模为一次状态跃迁**。本地引擎产出为唯一事实源；Gitee、飞书、Supabase 都只保存同一份 `manifest.json` 和带内容哈希的产物。同步不是“上传文件”，而是“让三端 manifest 收敛到一致”。

---

### 1. 触发：什么时候同步

“重大变更”用规则判定，避免噪音触发：

- `VERSION` 或 `CHANGELOG.md` 中标记 `major` / `breaking`
- 输出目录内容哈希变化，且变化文件属于 `api/`、`config/`、`schema/` 等关键路径
- 提交信息包含 `[sync]` 或 `[release]`
- 配置变更后必须执行 `sync --check` 验证生效，再触发同步

触发后先做防抖：**30 秒内多次触发合并为一次**。

---

### 2. 同步状态机

```
IDLE → PREFLIGHT → SYNCING → VERIFYING → DONE
                    ↓            ↓
                CONFLICT      FAILED
```

- `PREFLIGHT`：执行 `sync --check`，检查三端凭据、网络、远端状态
- `SYNCING`：按 Gitee → 飞书 → Supabase 顺序推送
- `VERIFYING`：推送后立即回读远端哈希，必须与本地一致
- 每次状态跃迁都记录到 `sync_events` 表，作为后续优化冲突策略的样本

---

### 3. 幂等性设计

所有产物使用 **内容哈希 `sha256` 作为幂等键**。

每个产物在三端的存储路径都带哈希，例如：

- Gitee：`output/{artifact}/{version}/{hash}/file`
- 飞书：`{artifact}.{hash}.pdf`
- Supabase：`artifacts/{artifact}/{hash}/file`

同步前先比较三端 `manifest.json`：

- 若远端 manifest 与本地完全一致 → 跳过
- 若某个哈希不存在 → 上传
- 若某个哈希已存在且相同 → 视为成功，不重复写入

这样重复执行同步不会产生重复提交、重复上传或重复文件。

---

### 4. 三端具体策略

#### Gitee 代码提交

- 使用 Gitee Contents API，提交时携带当前远端文件 `sha`
- 若远端 `sha` 与本地预期一致，则提交成功
- 若远端 `sha` 已变化，说明发生并发修改，进入冲突处理
- 提交信息固定为 `sync: {hash}`，同一个哈希不会重复提交
- 不做 force push，冲突时新建“解决冲突”提交，保留历史

#### 飞书文件上传

- 使用飞书自建应用凭据获取 `tenant_access_token`，不依赖个人扫码连接器
- 若产品必须走连接器：先升级飞书客户端、放大页面、确认豆包账号已登录；失败后自动降级到 Open API
- 上传前按文件名搜索文件夹；同名同哈希直接跳过
- 同名不同哈希 = 外部修改，进入冲突处理
- 上传后回读文件 token，并更新 `manifest.json`

#### Supabase 存储同步

- 使用 Storage API，路径带哈希，天然不可变
- 用 `upsert=false` 做“不存在才创建”，重复创建会触发唯一约束，捕获后比对哈希
- 维护 `current.json` 指针，指向当前生效的哈希
- 若 `current.json` 被外部修改，且指向的哈希不是本地期望值，则判定为冲突

---

### 5. 冲突处理方案

冲突定义：**远端哈希既不是本地期望哈希，也不是上一次同步记录中的哈希**。

| 策略 | 行为 |
|---|---|
| `source-wins` | 以引擎输出为准，覆盖远端；覆盖前先把远端旧文件备份到 `backup/{timestamp}/` |
| `remote-wins` | 不覆盖，记录冲突，跳过本次同步并告警 |
| `manual` | 暂停该产物同步，生成冲突报告，等待人工处理 |

默认策略：

- 生成类产物（代码、文档、模型输出）使用 `source-wins`
- 配置类、密钥类文件使用 `manual`，绝不自动覆盖

所有冲突都写入 `sync_conflicts` 表，字段包含：产物 ID、目标端、本地哈希、远端哈希、策略、解决人、解决时间。

---

### 6. 回读验证与超时

- 每次上传后立即回读远端哈希，最多重试 3 次
- 重试间隔：1s / 2s / 4s + 随机抖动
- 超时设置：
  - Gitee API：30s
  - 飞书上传：120s
  - Supabase Storage：30s
  - 若用 AI 模型判断“是否重大变更”：B 模型 turbo 用 300s，A 模型用 600s
- 回读不一致时，标记 `verify_failed`，不更新 `sync_events` 为成功，等待下次同步修复

---

### 7. 高可用与自愈

- 两个引擎实例通过 Supabase 的 advisory lock / lease 互斥，同一时间只有一个实例执行同步
- 若同步中途崩溃，状态表留下 `pending` 记录；另一个实例在租约过期后接管，从失败目标端继续
- 不需要 systemd / supervisor / k8s 额外守护进程
- 配置修改后立即重新读取配置，禁止使用旧缓存；修改后先 `sync --check` 再同步，避免“配置没生效”

---

### 8. 落地检查清单

- [ ] 所有产物路径包含 `sha256`
- [ ] 三端都有 `manifest.json`
- [ ] 同步前执行 `sync --check`
- [ ] 同步后执行回读验证
- [ ] 配置变更后重新加载配置
- [ ] 飞书使用应用凭据，不依赖扫码绑定
- [ ] 每个 API 调用都有 timeout 和重试上限
- [ ] 冲突记录可查询、可回放、可手动解决

这套方案把三方同步从“文件复制”升级为“状态收敛”，天然具备幂等性，遇到外部修改能安全处理，并且每次同步都在为系统积累状态跃迁样本，后续可以基于历史冲突数据自动优化冲突策略。
