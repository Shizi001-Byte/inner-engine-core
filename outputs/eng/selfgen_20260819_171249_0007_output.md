# 任务类型: eng

# 任务池自进化闭环设计

基于已有架构锚定：Guardian-Core 双进程、WAL+Snapshot、单向同步与幂等优先。本方案不重复论证底层，只落地“任务池动态扩充 + 自进化闭环”。

核心思路：**以实养虚，虚又返实**  
- **实**：真实任务执行、API 调用、Token 消耗、重复率、成功率  
- **虚**：任务模板、认知池、调度策略、ChainTask 链式定义  
- **返实**：新模板注入任务池后，被调度器真实执行，产生新的真实执行数据，形成闭环  

---

## 1. 重复率检测

### 1.1 检测窗口

使用最近 N 个已完成任务作为滑动窗口：

- 默认 `N = 100`
- 每次任务完成时，写入窗口并移除过期记录
- 窗口数据放入 `metrics_store`，底层用 WAL 记录，避免丢失

### 1.2 重复判定

任务指纹：

- 精确指纹：`sha256(规范化目标 + 输入Schema + ChainTask结构)`
- 语义指纹：`embedding(任务目标 + 约束条件)`

重复判定条件：

- 精确指纹相同，或
- 语义向量余弦相似度 >= `0.92`

重复率计算：

- 将窗口内任务构建为相似度图
- 节点：任务
- 边：两个任务判定为重复
- 连通分量数量记为 `C`
- 重复率 = `1 - C / N`

> 如果产品语境中“重复率”指完全相同的模板重复，可将语义相似度阈值调到 `0.99` 或只使用精确指纹。

### 1.3 ChainTask 链级重复挖掘

ChainTask 是引擎中的链式任务类型，因此重复检测要支持“子步骤序列”级别：

- 每条 ChainTask 执行记录保存 `subtask_sequence`
- 使用 PrefixSpan 挖掘频繁子序列
- 如果某个子序列出现次数 >= `min_support`，且占窗口任务比例超过阈值，则视为一个重复簇

例如：

```text
parse_log -> aggregate_metric -> format_output
```

在多个任务中重复出现，就触发新 ChainTask 模板生成。

### 1.4 防误判：B 模型独立规则

重复率计算只使用：

- 任务目标
- 输入 Schema
- 链式结构
- 输出契约

**不读取、不统计模型 reasoning 占比**。  
B 模型（turbo）reasoning 占比高是正常特性，不能作为废稿或重复特征。

## 2. 自进化触发

### 2.1 触发条件

同时满足以下条件才触发自动扩充：

```text
repetition_rate > repeat_threshold
and now - last_expansion_at > expansion_cooldown
and auto_expand_enabled == true
and not exists evolution_id
```

默认值：

- `repeat_threshold = 0.4`
- `expansion_cooldown = 100 个任务` 或 `30 分钟`
- `auto_expand_enabled = true`

### 2.2 幂等键

生成新模板前，先计算：

```text
evolution_id = sha256(sorted(cluster_ids) + config_version)
```

如果 `evolution_id` 已存在，说明该重复簇已生成过模板，直接跳过。  
这保证同一重复模式不会被反复生成，符合幂等优先原则。

## 3. 新任务模板生成

### 3.1 证据包

生成器必须基于真实执行数据，而不是凭空编造模板。证据包包括：

- 重复簇列表
- 每个簇的代表任务
- 每个簇的 Token 消耗、成功率、延迟
- 当前认知池缓存
- 当前已存在的任务模板，避免重复生成

### 3.2 生成模型调用

生成模板时：

- 如果使用 B 模型 turbo：`timeout = 300s`
- 如果使用 A 模型：`timeout = 600s`

超时后走降级路径：用规则组合认知池已有模板，不能阻塞闭环。

### 3.3 生成的模板结构

```yaml
task_template:
  template_id: tpl_log_analyzer_chain
  name: log_analyzer_chain
  type: ChainTask
  evolution_id: "sha256(...)"
  status: CANDIDATE
  input_schema:
    log_path: string
    metric_type: enum[error_code, latency, top_n]
    output_format: enum[text, json]
  chain_definition:
    nodes:
      - node_id: parse
        type: log_parser
      - node_id: aggregate
        type: metric_aggregator
      - node_id: format
        type: output_formatter
    edges:
      - from: parse
        to: aggregate
      - from: aggregate
        to: format
  quality_rules:
    model_specific:
      B-turbo:
        timeout: 300
        skip_reasoning_ratio_check: true
      A:
        timeout: 600
        reasoning_ratio_check: true
  timeout:
    default: 300
    model_overrides:
      B-turbo: 300
      A: 600
```

### 3.4 生成后校验

生成模板不能直接注入，必须通过校验：

1. JSON Schema 合法
2. ChainTask 为 DAG，无环
3. 与现有模板语义相似度 < `0.90`
4. 覆盖测试：用新模板匹配重复簇样本，至少覆盖一个重复簇
5. 反重复验证：如果新模板不能降低重复率，拒绝注入

---

## 4. 注入任务池与闭环

### 4.1 模板状态机

```text
CANDIDATE -> VALIDATING -> ACTIVE
CANDIDATE -> REJECTED
ACTIVE -> DISABLED
DISABLED -> ARCHIVED
```

### 4.2 注入动作

- 将新模板写入 `task_templates` 表
- 写入 WAL 事件：`TaskTemplateGenerated`
- 发布 `TaskPoolChanged` 事件
- 调度器收到事件后，立即刷新模板缓存，不能使用静态缓存

### 4.3 生效验证

注入后执行一次探针任务：

- 用新模板生成一个最小实例
- 按模板质量规则执行
- 如果失败或超时，将模板置为 `DISABLED`
- 如果通过，置为 `ACTIVE`

### 4.4 反馈指标

每个自进化模板都要跟踪：

- `matched_task_count`
- `success_rate`
- `avg_tokens_per_task`
- `repetition_rate_before / after`
- `coverage`

每轮结束评估：

- 如果重复率下降 >= 10%，且质量通过率 >= 95%，保留并提高调度权重
- 如果未达标，禁用模板，并自动调高 `repeat_threshold`，降低生成速度，防止自进化失控

## 5. 认知池联动

认知池不能只进不出。

- 每 10 个任务或每轮结束，强制刷新认知缓存
- 新认知条目设置 `fresh_until = now + 30min`
- 30 分钟内必须参与一次任务注入或模板生成
- 如果自然任务没有命中，则创建低成本的 `CognitionProbeTask` 来消费该认知
- 长期未命中且效用分低的认知条目，降权或淘汰

这样保证：

```text
认知池 -> 参与注入 -> 影响真实调度 -> 产生新认知 -> 回到认知池
```

## 6. 防坑落地：配置三点同步

本设计所有新增可配置参数，必须同步修改三个点：

| 配置项 | 状态写入 | 执行读取 | 生效验证 |
|---|---|---|---|
| `repeat_threshold` | 配置中心写入 + WAL | 重复率检测器每次评估时读取 | 修改后立即 `verify_config`，确认读取值等于写入值 |
| `auto_expand_enabled` | 配置中心写入 | 进化引擎生成前检查 | dry-run 触发一次，确认开关生效 |
| `max_templates_per_round` | 配置中心写入 | 生成器批量上限 | 测试注入 2 个模板，确认上限生效 |
| `cognitive_refresh_interval` | 配置中心写入 | 缓存管理器定时读取 | 观察刷新事件，确认周期变化 |

关键原则：

```text
新增配置必须同步修改：
1. 状态写入
2. 执行读取
3. 生效验证
```

缺一不可。

## 7. 闭环伪代码

```text
on_task_completed(rec):
    metrics_store.add(rec)

    if ++task_count_since_refresh >= 10 or round_end:
        refresh_cognitive_cache()

    rate = repetition_monitor.add_and_get(rec)

    if rate > cfg.repeat_threshold and cooldown_ok():
        clusters = repetition_monitor.top_clusters()

        evolution_id = sha256(sorted(cluster_ids) + cfg.config_version)

        if not exists(evolution_id):
            templates = evolution_engine.generate(
                evidence=clusters,
                cognitive_cache=cognitive_cache
            )

            for t in templates:
                if validate(t):
                    inject(t)
                    verify_injection(t)

            set_cooldown()
```

## 8. 总结

这个设计形成完整闭环：

```text
真实执行数据
    -> 重复率检测
    -> 认知池与执行证据驱动生成
    -> 新 ChainTask 模板校验注入
    -> 调度器真实执行
    -> 新执行数据再次回流
```

同时避开了历史坑：

- 配置修改后立即验证生效，避免“改了没反应”
- B 模型跳过 reasoning 占比检测，避免误杀
- 认知池每 10 任务/轮末刷新，新认知 30 分钟内参与注入，避免只进不出
- 生成调用按模型设置超时：B-turbo 300s，A 模型 600s
- 模板生成和注入使用幂等键，避免重复扩充导致任务池膨胀

任务池不再是静态档案库，而是会根据真实执行数据持续自进化的动态任务生态。
