# 任务类型: eng

基于你给的锚定，推演出的自动归档系统如下：  
**不是“把 Gitee、飞书、Supabase 三个 API 接在一起”，而是用 `change_id + content_hash` 把一次引擎产出固化成唯一事实，再做“先验证、再分工、后沉淀规范”的同步链。**

## 1. 核心模型

### 唯一键
每个归档记录必须携带：

```json
{
  "change_id": "c_001",
  "content_hash": "sha256:xxxx",
  "parent_change_id": null,
  "engine_version": "v7.5",
  "task_type": "code_fix",
  "output": "..."
}
```

- `change_id`：引擎生成，表示“一次意图变更”。
- `content_hash`：对产出内容做规范化后哈希，用于幂等、去重、冲突判断。
- 两者共同作为所有后端的关联键。

### 归档目录

```
/archive/
  code/
    fix/
      c_001__a1b2c3d4/
        manifest.json
        payload.diff
        tags.json
        source.json
    feat/
  doc/
    decision/
    design/
  meta/
    evolution/
    reflection/
  _journal/
    archive-wal.jsonl
  _quarantine/
```

目录由分类结果决定：

```text
target_dir = /archive/{class_path}/{change_id}__{content_hash[0:12]}/
```

## 2. 归档流水线

```text
RECEIVED
  -> VERIFIED
  -> CLASSIFIED
  -> TAGGED
  -> ARCHIVED_LOCAL
  -> SYNCED_BACKENDS
  -> RULE_PRECIPITATED
  -> COMPLETED
```

任何一步失败都进入 `RETRY_WAIT`，超过最大次数进入 `QUARANTINE`。

### 第一步：先验证

写任何后端之前，先校验：

- 产出内容是否完整
- `change_id` 是否存在
- `content_hash` 是否匹配
- 是否已有相同 `change_id + content_hash`

```python
def verify(task):
    h = sha256(canonicalize(task.output))
    assert task.change_id
    assert h == task.content_hash
    # 幂等
    if exists(task.change_id, h):
        return "DONE"
    # 冲突
    if exists(task.change_id, other_h):
        return "CONFLICT"
    return "VERIFIED"
```

### 第二步：再分工

验证通过后，才做两件事：

1. **自动分类**
2. **分发到三条后端链路**

分类规则优先，模型兜底：

```yaml
classifier:
  fast:
    model: B-model-turbo
    timeout: 300
  deep:
    model: A-model
    timeout: 600
  fallback: rule-only
```

分类结果示例：

```text
class = code/fix
tags  = [action:fix, module:archive, severity:minor]
```

然后“分工”：

| 后端 | 职责 | 写入键 |
|---|---|---|
| Supabase | 结构化索引、查询、状态 | `change_id + content_hash` |
| Gitee | 不可变提交历史、规则沉淀 | commit message 包含 `change_id + content_hash` |
| 飞书 | 面向人阅读的文件、通知 | 文件名包含 `change_id + content_hash` |

```python
# Supabase
supabase.from_("archives").upsert({
    "change_id": change_id,
    "content_hash": content_hash,
    "class": cls,
    "tags": tags,
    "target_dir": target_dir,
}, on_conflict="change_id,content_hash")

# Gitee
GiteeConnector.commit(
    repo="archive",
    path=target_dir,
    message=f"archive(change_id={change_id}, hash={content_hash[:8]}) {cls}"
)

# 飞书
feishu.upload_file(
    folder=f"归档/{cls}",
    filename=f"{change_id}__{content_hash[:8]}.md",
    dedupe_by=content_hash
)
```

### 第三步：后沉淀规范

归档成功后，不是结束，而是把这次分类/标签变成下一次可复用的规则：

```text
归档完成
  -> 生成规则提案 _rules/proposals/{change_id}.yaml
  -> 合并进 taxonomy.yaml / mapping.yaml
  -> RuleService.reload(version)
  -> 用探针任务验证新规则生效
```

注意避坑：  
**只更新规则文件不算生效，必须更新读取点。**  
所以每次规则合并后必须执行：

```python
RuleService.reload(version="2026-04-01")
assert probe_archive().class == "code/fix"
```

## 3. 冲突处理

同一个 `change_id` 出现不同 `content_hash`：

- 这不是错误，而是引擎演化了。
- 不覆盖旧记录。
- 作为新 revision 归档，并记录 `supersedes`。

```text
/archive/code/fix/c_001__newhash/
  manifest.json   # supersedes: old_hash
```

同时触发冲突通知，避免静默覆盖。

## 4. 重大变更自动触发

如果分类结果包含：

```text
class = meta/evolution
severity = major
tags 包含 breaking
```

则自动触发：

- Gitee 提交 `CHANGELOG.md`
- 飞书推送重大变更通知
- Supabase 写入 `major_changes` 表
- 生成一条新的 `change_id` 作为本次演化的决策记录

## 5. 崩溃中重建

沙箱不稳定是默认方向，所以归档器必须不依赖内存态。

实现方式是：

- 每次状态变更前写 WAL
- 每次写文件先写临时文件再原子 rename
- 每次外部调用都幂等
- 启动时从 WAL 恢复：

```text
recover_from_wal():
  如果 local_done 不存在 -> 重做本地写入
  如果 synced 不存在    -> 重做后端同步
  如果 rules_merged 不存在 -> 重做规则沉淀
```

这样即使进程被杀、状态丢失、网络中断，只要 WAL 在，就能从上次断点继续。

## 6. 冷却重试与超时

```yaml
retry:
  max_attempts: 5
  base_delay: 2s
  max_delay: 120s
  jitter: 0.3

timeout:
  classify_fast_model: 300s   # B-model-turbo
  classify_deep_model: 600s   # A-model
  gitee_commit: 30s
  feishu_upload: 120s
  supabase_upsert: 30s
```

超时后不立即重试，进入冷却；冷却耗尽后降级：

```text
完整模式
  -> 规则分类模式
  -> 最小归档模式
  -> 隔离区
```

## 结论

这套自动归档系统的本质是：

```text
change_id + content_hash = 唯一事实
先验证 = 写入前防脏数据
再分工 = 分类 + 三条后端投影
后沉淀规范 = 让归档系统自己进化
```

它不追求“更稳定”，而是把“崩溃后重建”内建到每一步。
