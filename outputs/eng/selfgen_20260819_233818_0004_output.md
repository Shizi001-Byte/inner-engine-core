# 任务类型: eng

# L4成品转化支持 code/checklist 类型 — 修复方案

## 一、问题拆解（基于已知问题反推结构）

「L4成品转化仅sop类型，code/checklist未实现」意味着在L4转化分派逻辑里只接通了SOP这一条分支。结合多目标优化锚点，需要避免：只把"加case"当成完成，却忽略了类型分支注册、读取点同步、超时差异化、并发下隐性崩溃等次生问题。

## 二、具体修改点（按调用链自顶向下）

### 修改点 1：分派器（dispatcher）注册补全
**文件假设**：`l4_converter/dispatcher.py`

```python
# 现状（伪代码）
_TYPE_REGISTRY = {
    "sop": SOPConverter,
    # code / checklist 缺失
}

# 修改为
from .converters.sop_converter import SOPConverter
from .converters.code_converter import CodeConverter
from .converters.checklist_converter import ChecklistConverter

_TYPE_REGISTRY = {
    "sop": SOPConverter,
    "code": CodeConverter,
    "checklist": ChecklistConverter,
}

# 启动期断言：所有配置中的目标类型必须有注册converter
def assert_type_coverage(configured_types):
    missing = set(configured_types) - set(_TYPE_REGISTRY)
    if missing:
        raise RuntimeError(f"L4 converter未注册类型: {missing}")
```
**对应避坑1**：新增类型后立即在启动入口断言覆盖，避免"配了但读不到"。

### 修改点 2：补全 CodeConverter / ChecklistConverter
若两类converter完全缺失，按SOPConverter的接口签名实现最小可用版本：
- 输入：task_payload + context
- 输出：标准化L4 product对象（type字段必须填`code`/`checklist`）
- 内部模板与prompt按类型差异化

### 修改点 3：超时差异化配置（对应避坑2）
**文件**：`l4_converter/timeout_policy.py`

```python
L4_TIMEOUT_BY_TYPE = {
    "sop":       300,   # B-turbo默认
    "code":      600,   # A模型，复杂生成
    "checklist": 300,   # 结构简单，B-turbo即可
}

def get_timeout(task_type, model_tier):
    base = L4_TIMEOUT_BY_TYPE.get(task_type, 300)
    if model_tier == "A":
        base = max(base, 600)
    return base
```
**关键**：超时常量既要在调度处读取，也要在监控埋点读取，避免出现"调度用了新值、监控还用旧值"的读取点漂移。

### 修改点 4：并发反馈游标扩展（呼应多目标优化锚点）
**文件**：`l4_converter/concurrency_governor.py`

不再只看"单任务失败率"，把崩溃频率纳入游标：
```python
metrics = {
    "task_fail_rate": ...,          # 既有
    "crash_retry_rate": ...,        # 新增：OOM/死锁/连接重置等瞬断
    "effective_output_ratio": ...,  # 新增：有效产出 / 总算力
}
# 当 crash_retry_rate > 阈值 或 effective_output_ratio 下降时，
# 即使 task_fail_rate 正常也触发回退并发
```

## 三、验证方法

### 1. 单元验证（即时生效性）
- 对3种type分别构造最小payload，断言返回对象的`type`字段与请求一致。
- 断言`_TYPE_REGISTRY`的key集合 ⊇ 配置文件中的目标类型集合（启动断言触发）。

### 2. 配置生效验证（对应避坑1）
- 修改配置把`target_type=code`，调用一次L4转化，确认实际走的是CodeConverter（日志打type分支）。
- 故意配置一个未注册的`target_type=foo`，断言启动断言能抛错。

### 3. 超时验证（对应避坑2）
- 用一个故意慢返的mock模型，验证code类型的超时边界=600s，checklist=300s。
- 同时验证监控埋点读取到的超时值与调度一致。

### 4. 并发多目标验证（对应核心认知锚点）
- 5路并发混合sop/code/checklist执行一轮，采集：
  - 单任务失败率（应不劣化）
  - crash_retry_rate（应低于回退阈值）
  - effective_output_ratio（应 ≥ 3路稳定基线）
- 任一指标恶化即回退到3路，而不是只看失败率。

### 5. 回归验证
- 跑一轮纯sop的L4转化，确认既有行为零变化（无全量扫描、无标准化强制要求）。

## 四、风险评级与边界

- **风险等级：low** — 仅在分派表新增两个分支 + 新增两个独立converter类，未触碰既有SOP路径，未改动核心调度状态机。
- **不做的事**：不重写SOP converter、不修改任务记忆、不做全量历史回填、不强制类型标准化（严格遵守5项核心锚点）。
- **回滚预案**：如出现回归，仅需把`_TYPE_REGISTRY`中code/checklist两行注释掉即可恢复原状，启动断言会因配置覆盖触发显式报错而非静默降级。

## 五、一句话总结

补齐L4分派器的类型注册 + 启动断言 + 差异化超时 + 多指标并发游标，验证覆盖"配置生效、超时边界、并发隐性崩溃"三条线，即可在不触碰既有SOP路径的前提下把code/checklist接通。
