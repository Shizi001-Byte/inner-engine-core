# 任务类型: eng

# Supabase 记忆脑增量同步方案

基于锚定，不重复论证，直接推演：

> 同步单位是 **block**，不是 file；  
> file 只是「有序 block id 列表」的 index；  
> Supabase 只存 **block / index / tombstone** 顶点；  
> 流程固定为 **Detect → Diff → Commit**，每节点三转，共九转。

---

## 1. 数据模型：只有三类顶点

### 1.1 block：内容顶点

```sql
create table blocks (
  id uuid primary key default gen_random_uuid(),
  content text not null,
  content_hash text not null,   -- 用于识别相同内容
  created_at timestamptz not null default now()
);

create index blocks_content_hash_idx on blocks(content_hash);
```

block 不可变：内容变了，就生成新 block id。  
所以文件局部修改，只会产生新 block，不会重传整个文件。

### 1.2 index：文件索引顶点

```sql
create table file_index (
  file_id uuid not null,
  rev bigint not null,
  block_ids uuid[] not null,
  parent_rev bigint,
  updated_at timestamptz not null default now(),
  primary key (file_id, rev),
  foreign key (file_id, parent_rev) references file_index(file_id, rev)
);

create index file_index_current_idx on file_index (file_id, rev desc);
```

文件当前内容 = 该 file_id 下 `rev` 最大的 `block_ids`。

### 1.3 tombstone：删除顶点

```sql
create table tombstones (
  kind text not null check (kind in ('block', 'file')),
  target_id uuid not null,
  created_at timestamptz not null default now(),
  primary key (kind, target_id)
);
```

- `kind='block'`：block 已删除，禁止再被新 index 引用。
- `kind='file'`：file 已删除，用于防止旧设备把已删除文件重新同步回来。

不建 `sync_jobs`，不建 `sync_logs`。

## 2. Detect：检测本地变化

每节点三转：

### 第一转：本地扫描

本地维护一个轻量 manifest，不是同步任务记录，只是本地游标：

```json
{
  "files": {
    "file-uuid-1": {
      "path": "docs/note.md",
      "last_rev": 3,
      "block_ids": ["block-uuid-a", "block-uuid-b"],
      "mtime": 1690000000,
      "size": 1024
    }
  }
}
```

扫描规则：

- `mtime + size` 没变：跳过。
- 文件新增、修改、删除：进入解析。
- 解析时按稳定切块策略切 block，例如 Markdown 段落 / 代码块 / 空行分隔。
- 对比旧 block 的 `content_hash`：
  - 相同内容：复用旧 block id；
  - 不同内容：生成新 block id；
  - 消失的 block id：记录为删除。

### 第二转：远端拉取

对变更的 file_id，从 Supabase 拉取：

1. 当前最新 `file_index`；
2. 该 file 是否存在 `tombstone`；
3. 涉及 block 是否有 `tombstone`。

得到：

- `L`：本地当前 block id 列表；
- `R`：远端当前 block id 列表；
- `B`：本地 manifest 中 `last_rev` 对应的远端 index 作为 base。

### 第三转：变化分类

- `L == R`：无变化，跳过。
- 仅 `L` 变：push。
- 仅 `R` 变：pull。
- 都变：进入 Diff 做三路合并。
- 本地存在但远端 file 已 tombstone：冲突。

---

## 3. Diff：只同步变更部分

每节点三转：

### 第一转：本地 Diff

对 block id 序列做 diff，得到操作集：

```text
insert(pos, block_id)
delete(pos, block_id)
replace(pos, old_block_id, new_block_id)
```

例如：

```text
B = [A, B, C]
L = [A, B2, C]
D_L = replace(pos=1, B -> B2)
```

### 第二转：远端 Diff

同样方式：

```text
R = [A, B, D, C]
D_R = insert(pos=2, D)
```

### 第三转：合并裁决

基于 `B` 做三路合并，生成目标 `M`：

| 情况 | 结果 |
|---|---|
| 非重叠 hunk | 自动合并 |
| 双方都插入同一个 block id | 保留一份 |
| 双方都删除同一个 block id | 保留删除 |
| 一方修改、另一方未动 | 取修改 |
| 同一位置修改成不同 block | 冲突 |
| 一方修改、另一方删除 | 冲突 |
| 本地引用已 tombstone 的 block | tombstone 优先，剔除该 block |

冲突时按配置：

- `local_wins`：本地版本胜出；
- `remote_wins`：远端版本胜出；
- `marker`：在冲突位置插入一个「冲突标记 block」，内容为：

```text
<<<<<<< local
...
=======
...
>>>>>>> remote
```

这个冲突标记 block 也是普通 block，不存任务记录。  
后续人工或模型消解后，下一次 sync 会自然替换它。

---

## 4. Commit：提交变更

每节点三转：

### 第一转：本地落盘

- 按 `M` 渲染最新文件内容；
- 写临时文件后原子 rename；
- 更新本地 manifest 的 `last_rev` 和 `block_ids`。

### 第二转：Supabase 事务提交

一个事务内完成：

```sql
begin;

-- 1. 新 block 入库
insert into blocks (id, content, content_hash)
values (...)
on conflict (id) do nothing;

-- 2. 写新 index 顶点，乐观锁 rev = old_rev + 1
insert into file_index (file_id, rev, block_ids, parent_rev)
values ($file_id, $old_rev + 1, $M, $old_rev);

-- 3. 死 block 写 tombstone
insert into tombstones (kind, target_id)
select 'block', b.id
from blocks b
where b.id = any($old_block_ids)
  and not exists (
    select 1
    from file_index fi
    where b.id = any(fi.block_ids)
      and fi.rev = (
        select max(rev)
        from file_index fi2
        where fi2.file_id = fi.file_id
      )
  );

-- 4. 文件删除时写 file tombstone
insert into tombstones (kind, target_id)
values ('file', $file_id)
on conflict do nothing;

commit;
```

如果 `rev` 冲突，说明 Detect 之后又有远端提交，整个事务回滚，回到 Detect 重新走九转。

### 第三转：验证

- 读回 Supabase 最新 `file_index`；
- 确认 `block_ids == M`；
- 确认 `M` 中每个 block 都有内容且未被 tombstone；
- 确认本地渲染文件 hash 与预期一致。

验证失败不写失败任务表；下一次 Detect 会自然覆盖。

## 5. 避坑配置

### 5.1 配置读取点必须唯一

新增配置时必须同步修改读取点，例如：

- `block_size`
- `conflict_mode`
- `timeout`
- `quality_rule`

否则会出现「配置改了但行为没变」。  
修改后立即跑一次自检：用测试文件触发同步，确认行为变化。

### 5.2 模型调用 timeout

如果 Diff / 冲突消解 / block 生成会调用模型：

- B 类 turbo 模型：**300 秒**
- A 类模型：**600 秒**

超时和废稿要分开处理，不能混在一起重试。

### 5.3 废稿检测不能误杀 B 模型

B 类 turbo 模型的 reasoning 占比 70%-82% 是正常特性，不是废稿。  
质量检测规则必须按模型独立：

- B 类 turbo：跳过 reasoning 占比废稿检测；
- 只有 A 类模型才做 reasoning 占比异常检测。

---

## 6. 结论

这套方案下：

- 文件改动只会同步变化的 block；
- 文件顺序变化只改 index 顶点；
- 删除只产生 tombstone 顶点；
- 冲突靠三路合并收敛到 block 级；
- Supabase 里没有同步任务记录，只有 `block / index / tombstone` 三类状态顶点。

流程始终是：

```text
Detect → Diff → Commit
  三转    三转    三转   = 共九转
```
