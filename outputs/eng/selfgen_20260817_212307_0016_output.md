# 任务类型: eng

针对V7.5方舟效能引擎在“多线程API调用后串行后处理”阶段出现的状态一致性问题和竞态条件，其核心矛盾在于：**高并发的无状态API执行与带状态的串行后处理之间的过渡地带缺乏隔离与同步保障**。

为了彻底解决这一问题，同时兼顾V7.5引擎的高效能需求，以下给出一套**“架构级解耦 + 多层次锁机制”**的完整方案。

---

### 一、 竞态条件推演分析

在V7.5方舟效能引擎中，典型的竞态条件通常发生在以下场景：
1. **读写撕裂**：线程A在读取共享状态进行后处理计算时，线程B正在修改该状态，导致A读取到半更新的脏数据。
2. **丢失更新**：线程A和线程B同时基于同一初始状态`S0`计算得出结果`S1`和`S2`，串行提交时，`S2`覆盖了`S1`，导致A的更新丢失。
3. **死锁/饿死**：后处理逻辑中锁粒度过大或锁顺序不一致（如锁A->锁B vs 锁B->锁A），导致多线程在后处理阶段相互等待，引擎效能急剧下降。

---

### 二、 完整锁机制方案：分层同步架构

为了兼顾“效能”与“一致”，我们不能简单地使用单一全局互斥锁，而是采用**三层锁机制与无锁队列结合**的方案。

#### 第一层：架构级解耦 —— 无锁任务队列 (规避多线程锁竞争)
**核心思想**：将“多线程API调用”与“串行后处理”在物理上彻底隔离。API线程只负责生产结果，不直接操作最终状态。

*   **机制**：采用 MPSC（多生产者单消费者）无锁环形队列。
*   **操作**：
    *   多个API线程在完成计算后，将后处理所需的上下文封装成`PostProcessTask`对象。
    *   使用**CAS（Compare-And-Swap）无锁算法**将Task推入队列。
*   **收益**：彻底消除了多线程在后处理阶段的锁竞争，API线程永远不会因为后处理而阻塞。

#### 第二层：状态级同步 —— 分片读写锁 (保障串行后处理的一致性)
如果后处理逻辑必须在API线程内立即执行且涉及共享状态修改，则采用**分片读写锁**。

*   **机制**：将引擎全局状态按实体ID（如PlayerID或EntityID）哈希分片到N个桶中，每个桶配一把`SharedMutex`（读写锁）。
*   **操作**：
    *   **读状态（API并行阶段）**：获取共享锁（`SharedLock`），允许多个线程同时读取同一分片的状态。
    *   **写状态（串行后处理阶段）**：获取排他锁（`UniqueLock`），保证同一时刻只有一个线程能修改该分片的状态。
*   **收益**：将全局锁的冲突概率降低至 `1/N`，大幅提升并发吞吐量。

#### 第三层：数据级保障 —— 乐观并发控制 (OCC / MVCC) (解决丢失更新)
针对状态计算的耗时操作，避免长时间持有排他锁。

*   **机制**：状态对象引入版本号`Version`。
*   **操作**：
    1. API线程读取状态 `State(Version=N)`，不加锁。
    2. 线程在本地内存中基于 `Version=N` 执行后处理计算，生成 `NewState`。
    3. 提交时，获取短暂排他锁，检查当前内存中的 `Version` 是否仍为 `N`。
    4. 若是，则写入 `NewState(Version=N+1)`；若否，说明被其他线程抢先修改，放弃当前锁，重试或丢弃。

### 三、 具体代码落地结构设计 (C++ 伪代码示例)

#### 1. 无锁队列方案（推荐，最契合“串行后处理”描述）

```cpp
// 定义后处理任务结构
struct PostProcessTask {
    uint64_t entity_id;
    StateDelta delta;
    // ...
};

// V7.5方舟效能引擎 专属无锁队列
class ArkEnginePostProcessor {
private:
    // MPSC 无锁队列
    LockFreeQueue<PostProcessTask> task_queue_;
    std::atomic<bool> runner_active_{false};
    std::thread serial_worker_;

    // 串行处理状态
    EngineGlobalState global_state_;

public:
    // 1. API多线程调用此接口（无锁/极短CAS）
    void SubmitPostProcess(PostProcessTask&& task) {
        // CAS 操作将任务推入队列，不阻塞API线程
        task_queue_.Enqueue(std::move(task)); 
    }

    // 2. 后台专有线程串行消费（彻底解决竞态）
    void StartSerialWorker() {
        runner_active_ = true;
        serial_worker_ = std::thread([this]() {
            while (runner_active_) {
                PostProcessTask task;
                if (task_queue_.Dequeue(task)) {
                    // 因为只有一个消费者线程在修改 global_state_，所以无需加锁
                    // 天然保证状态一致性
                    ApplyToGlobalState(task); 
                } else {
                    // 队列空时休眠或让出CPU时间片
                    std::this_thread::yield(); 
                }
            }
        });
    }

private:
    void ApplyToGlobalState(const PostProcessTask& task) {
        // 安全的串行状态修改
        global_state_.ApplyDelta(task.entity_id, task.delta);
    }
};
```

#### 2. 细粒度分片锁方案（若必须在API线程内完成状态修改）

```cpp
class ShardedStateLockManager {
private:
    static constexpr size_t SHARD_COUNT = 64;
    struct Shard {
        std::shared_mutex rw_lock;
        EntityState state;
    };
    std::array<Shard, SHARD_COUNT> shards_;

    Shard& GetShard(uint64_t entity_id) {
        return shards_[entity_id % SHARD_COUNT];
    }

public:
    // 并行API调用时的读取
    EntityState ReadState(uint64_t entity_id) {
        auto& shard = GetShard(entity_id);
        std::shared_lock<std::shared_mutex> lock(shard.rw_lock); // 共享锁
        return shard.state;
    }

    // 串行后处理时的写入
    void ApplyPostProcess(uint64_t entity_id, const StateDelta& delta) {
        auto& shard = GetShard(entity_id);
        std::unique_lock<std::shared_mutex> lock(shard.rw_lock); // 排他锁
        shard.state.Apply(delta);
    }
};
```

### 四、 死锁预防与引擎效能保障策略

在V7.5引擎中引入锁机制，必须防止死锁和性能倒退：

1. **严格锁层级**：
   如果后处理必须同时操作多个实体（如实体A向实体B转账），必须严格按照 `EntityID` 升序获取锁，杜绝循环等待。
   ```cpp
   // 正确的加锁顺序
   auto ids = std::sort({id_a, id_b}); 
   LockManager::Acquire(ids[0]);
   LockManager::Acquire(ids[1]);
   ```
2. **锁超时与降级机制**：
   设定锁等待超时（如5ms）。若超时未能获取排他锁，API不应阻塞挂死，而是将任务转入第一层的无锁队列，交由后台线程异步处理，保障API线程的响应时间。
3. **避免持锁I/O**：
   绝对禁止在持有排他锁（`unique_lock`）期间进行网络调用、磁盘读写或长耗时计算。应采用“计算 -> 获取锁 -> 更新内存 -> 释放锁”的极短临界区模式。

### 五、 总结

针对V7.5方舟效能引擎的竞态条件，最佳方案是：**用无锁队列将“多线程并发”强行转化为“单线程串行”**。

*   对于**高吞吐、可异步**的后处理：采用 `MPSC无锁队列 + 单一后台消费线程`，从物理上消灭竞态条件，引擎性能最优。
*   对于**强实时、必须同步**的后处理：采用 `实体分片 + 读写锁 + 乐观版本控制`，将锁冲突降低到理论极限。

这套方案既保证了V7.5引擎对高性能的严苛要求，又从架构和微观两个层面彻底封死了状态不一致的竞态漏洞。
