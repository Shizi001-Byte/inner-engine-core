# 任务类型: eng

# 三方同步自动化设计方案

## 一、设计原则锚定（继承认知基线）

| 原则 | 在本任务中的工程映射 |
|---|---|
| 无记忆修改 | 工作流节点不依赖本地持久态，所有中间状态写入 Supabase `sync_log` 表 |
| 无全量扫描 | 路由用哈希索引（change_id），禁止遍历比对 |
| 异构自适应 | 三方 API 客户端做能力探测 + 降级（飞书 OpenAPI/SDK/Webhook 多通道） |
| 多目标优化 | 时延、幂等强度、回滚成本三目标加权 |

## 二、总体架构

```
┌─────────────────────────────────────────────────────────────┐
│  触发源 (重大变更)                                            │
│  ├─ Gitee push to main / tag create                          │
│  ├─ 飞书文档手动标记「同步」                                   │
│  └─ Supabase cron 周期校验                                    │

│  Orchestrator (无状态 Worker)                                │
│  1. 计算 change_id = sha256(commit_sha + path + content)     │
│  2. 查询 Supabase.sync_log[change_id] → 命中即返回            │
│  3. 未命中 → 三方并行下发                                      │
└──────┬──────────────┬──────────────┬──────────────────────┘
       │              │              │
       ▼              ▼              ▼
   Gitee API     Feishu API    Supabase API

       │              │              │
       └──────┬───────┴──────┬───────┘
              ▼              ▼
       结果回写 Supabase.sync_log
              │
              ▼
       Validate 阶段（立即验证生效——防坑1）
```

## 三、幂等性设计（核心）

### 3.1 幂等键构造

```python
change_id = sha256(
    f"{git_commit_sha}:{file_path}:{content_hash}:{operation}"
    .encode()
).hexdigest()[:32]
```

- `operation` ∈ {`create`, `update`, `delete`}
- 内容哈希采用 SHA-256，避免 MD5 碰撞
- `change_id` 作为三方的**唯一业务键**：
  - Gitee：commit message 末尾追加 `[change_id:xxxx]`
  - 飞书：文件名前缀 `cid_xxxx_` 或自定义属性 `x-change-id`
  - Supabase：`storage.objects` 的 `metadata.change_id`

### 3.2 sync_log 表结构（Supabase）

```sql
CREATE TABLE sync_log (
  change_id        TEXT PRIMARY KEY,
  git_commit_sha   TEXT NOT NULL,
  source           TEXT NOT NULL,  -- gitee | feishu | supabase | manual
  operation        TEXT NOT NULL,
  content_hash     TEXT NOT NULL,
  gitee_status     TEXT DEFAULT 'pending',  -- pending|success|failed|skipped
  feishu_status    TEXT DEFAULT 'pending',
  supabase_status  TEXT DEFAULT 'pending',
  gitee_ref        TEXT,   -- commit url / file_key / object_path
  feishu_ref       TEXT,
  supabase_ref     TEXT,
  created_at       TIMESTAMPTZ DEFAULT now(),
  updated_at       TIMESTAMPTZ DEFAULT now(),
  retry_count      INT DEFAULT 0,
  conflict_flag    BOOLEAN DEFAULT FALSE
);
CREATE INDEX idx_sync_log_content ON sync_log(content_hash);
```

### 3.3 幂等执行流程

```
┌─ 接收变更事件
│
├─ 1. 计算 change_id
│
├─ 2. SELECT * FROM sync_log WHERE change_id = ?
│   ├─ 命中且三方 status=success → 直接返回，跳过（防坑1：避免重复执行）
│   ├─ 命中但有 pending/failed → 进入断点续传，只补齐未成功方
│   └─ 未命中 → INSERT，进入下发
│
├─ 3. 三方并行下发（携带 change_id 作为幂等键）
│   ├─ Gitee: 检查 commit message 是否已含 change_id → 已含则跳过
│   ├─ 飞书: 查询同名文件或自定义属性 → 已存在则跳过
│   └─ Supabase: upsert by (bucket, path) + metadata.change_id → 已匹配则跳过
│
└─ 4. 全部 success → 标记 completed；否则按退避重试
```

## 四、冲突处理

### 4.1 冲突定义

同一 `content_hash` 但不同 `change_id` 同时存在，或同一目标路径被多个 change_id 写入。

### 4.2 冲突检测

```python
# 路径级冲突检测（O(1) 索引查询，非全量扫描）
def detect_conflict(target_path: str, new_change_id: str) -> bool:
    row = supabase.table("sync_log") \
        .select("change_id, content_hash, updated_at") \
        .eq("supabase_ref", target_path) \
        .neq("change_id", new_change_id) \
        .order("updated_at", desc=True) \
        .limit(1) \
        .execute()
    return len(row.data) > 0
```

### 4.3 冲突解决策略

| 冲突类型 | 策略 | 说明 |
|---|---|---|
| Git ↔ 飞书 内容哈希不一致 | Git 优先（Source of Truth） | 飞书侧文件被人工编辑 → 用 Git 版本覆盖并标记 `conflict_flag=true` |
| 飞书 ↔ Supabase 不一致 | 时间戳 LWW + 版本保留 | 旧版本归档到 `storage.objects.archive/{change_id}` |
| 同 change_id 多次触发 | 幂等跳过 | change_id 主键约束 |
| 跨节点并发同路径写入 | CAS 乐观锁 | `UPDATE ... WHERE updated_at = ?` 影响行数=0 即冲突 |

### 4.4 冲突告警

`conflict_flag=true` 时：
- 飞书机器人推送告警卡片（含 change_id、双方 content_hash 前 8 位、diff 链接）
- Supabase 中保留双版本，待人工裁定或规则裁定后归档

## 五、超时与重试（防坑2）

| 阶段 | API | timeout | 重试次数 | 退避策略 |
|---|---|---|---|---|
| Gitee commit | `POST /repos/{owner}/{repo}/git/commits` | 60s | 3 | 指数 2s/4s/8s |
| 飞书文件上传 | `POST /open-apis/drive/v1/files/{token}/upload` | **120s** | 3 | 指数 5s/10s/20s |
| 飞书大文件分片 | `POST /upload_prepare / upload_part / upload_finish` | 300s | 2 | 固定 30s |
| Supabase Storage upsert | `POST /storage/v1/object/{bucket}/{path}` | 30s | 5 | 指数 1s/2s/4s/8s/16s |
| 整体工作流 | — | **600s**（A 模型基线） | — | 超时即标记 partial，进入修复流程 |

> 飞书 API 用 **300s**（参考 B 模型 turbo 基线）以应对大文件分片场景。

## 六、立即验证机制（防坑1落地）

每次配置修改或同步执行后，强制进入 validate 阶段：

```python
def validate_sync(change_id: str) -> dict:
    result = {"gitee": False, "feishu": False, "supabase": False}
    
    # Gitee: 查询 commit 是否存在且 message 含 change_id
    commit = gitee_api.get_commit(repo, commit_sha)
    result["gitee"] = change_id in commit.message
    
    # 飞书: 查询文件 metadata.change_id
    meta = feishu_api.get_file_metadata(file_token)
    result["feishu"] = meta.get("x-change-id") == change_id
    
    # Supabase: 查询 object metadata
    obj = supabase.storage.from_(bucket).list(path_prefix)
    result["supabase"] = any(
        o.metadata.get("change_id") == change_id for o in obj
    )
    
    # 任一未验证通过 → 标记 failed 触发重试
    if not all(result.values()):
        supabase.table("sync_log").update({
            **{f"{k}_status": "failed" if not v else "success" for k, v in result.items()},
            "updated_at": "now()"
        }).eq("change_id", change_id).execute()
    
    return result
```

**关键：validate 失败必须改变 sync_log 状态，否则下次触发会幂等跳过 → 这是历史踩坑的直接映射。**

## 七、异构环境自适应（防坑3）

### 7.1 飞书多通道降级

```
飞书同步通道优先级：
1. OpenAPI（首选，需 app_token）
2. SDK（次选，需扫码绑定 —— 注意防坑：客户端版本 + 页面缩放 + 账号登录态）
3. Webhook 回调（仅通知，不传内容 —— 兜底）
```

> ⚠️ 连接器扫码绑定历史坑：绑定前确认客户端最新版；页面缩放到最大查按钮；失败先检查账号登录态。**生产环境优先用 OpenAPI + app_token，规避扫码路径。**

### 7.2 代理与配额自适应

```python
class SyncClient:
    def __init__(self):
        self.rate_limit = {"gitee": 60, "feishu": 100, "supabase": 200}  # req/min
        self.proxy_pool = detect_proxy_env()  # 自动探测 HTTP_PROXY/HTTPS_PROXY
    
    def call(self, api: str, **kwargs):
        # 配额检测 → 选择可用代理 → 设置 timeout → 执行 → 验证
        if self.rate_limit[api] <= 0:
            wait_until_reset(api)
        client = select_client_by_proxy(api)
        resp = client.request(timeout=self.timeout[api], **kwargs)
        assert self.validate(api, resp)  # 立即验证生效
        return resp
```

## 八、失败回滚

```
三方同步失败处理：
├─ 单方失败 → 仅重试该方（基于 sync_log 状态字段断点续传）
├─ 双方失败 → 重试 3 次后告警，保留已成功方结果
├─ 三方全失败 → 标记 change_id 为 aborted，等待人工介入
└─ 冲突导致覆盖 → 旧版本归档到 archive，可一键回滚
```

回滚操作同样基于 change_id 幂等：
```sql
-- 回滚 = 将 archive 版本重新作为新 change_id 推送
INSERT INTO sync_log (change_id, ...) VALUES (new_change_id, ...);
-- 不修改历史记录，符合「无记忆修改」原则（只追加，不就地改）
```

## 九、完整工作流伪代码

```python
def sync_workflow(event):
    change_id = compute_change_id(event)
    
    # 1. 幂等检查
    existing = supabase.table("sync_log").select("*").eq("change_id", change_id).execute()
    if existing.data and all_done(existing.data[0]):
        return {"status": "skipped", "change_id": change_id}
    
    if not existing.data:
        supabase.table("sync_log").insert({
            "change_id": change_id,
            "git_commit_sha": event.commit_sha,
            "source": event.source,
            "operation": event.op,
            "content_hash": event.content_hash,
        }).execute()
    
    # 2. 冲突检测
    if detect_conflict(event.target_path, change_id):
        supabase.table("sync_log").update({"conflict_flag": True}).eq("change_id", change_id).execute()
        notify_conflict(change_id)
        # 仍继续，按 LWW 策略覆盖
    
    # 3. 三方并行下发（各自独立 timeout、重试、降级）
    results = parallel_execute(
        gitee_push(event, change_id, timeout=60),
        feishu_upload(event, change_id, timeout=300),
        supabase_upsert(event, change_id, timeout=30),
    )
    
    # 4. 立即验证（防坑1）
    validation = validate_sync(change_id)
    
    # 5. 回写状态
    supabase.table("sync_log").update({
        "gitee_status": "success" if validation["gitee"] else "failed",
        "feishu_status": "success" if validation["feishu"] else "failed",
        "supabase_status": "success" if validation["supabase"] else "failed",
        "giteo_ref": results["gitee"].ref,
        "feishu_ref": results["feishu"].ref,
        "supabase_ref": results["supabase"].ref,
        "updated_at": "now()",
    }).eq("change_id", change_id).execute()
    
    # 6. 失败重试或告警
    if not all(validation.values()):
        schedule_retry(change_id, max_retries=3)
    
    return {"status": "completed", "change_id": change_id, "validation": validation}
```

## 十、防坑清单（映射历史经验）

| 历史坑 | 本方案对应措施 |
|---|---|
| 配置修改后未生效 | validate 阶段强制执行，失败即改状态触发重试，不静默跳过 |
| API 超时 | 分 API 设 timeout：Gitee 60s / 飞书 300s / Supabase 30s / 整体 600s |
| 飞书扫码绑定失败 | 优先 OpenAPI+app_token，规避扫码；降级时附绑定 checklist |
| 无记忆约束冲突 | sync_log 只追加不就地改，回滚用新 change_id |
| 全量扫描 | 所有查询走 change_id / content_hash 索引，O(1) |
| 异构环境 | 多通道降级 + 代理探测 + 配额自适应 |

---

**核心结论**：通过 `change_id` 作为贯穿三方的幂等键 + `sync_log` 作为唯一状态真相源 + 强制 validate 阶段，实现「无记忆修改」约束下的可靠三方同步。冲突采用 Git 优先 + LWW + 版本归档策略，超时按 API 类型分级预设，全程规避历史踩坑点。
