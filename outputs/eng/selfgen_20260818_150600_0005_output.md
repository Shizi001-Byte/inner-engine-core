# 任务类型: eng

基于锚定，直接推演。

## 核心模型

- 本地文件系统 = **写入源**，Supabase = **记忆脑 / 查询面**。
- 默认单向同步：本地 → Supabase；反向恢复可作为可选项。
- 同步粒度：**文件级 manifest + 语义块级 delta**。
- 一致性：最终一致，通过 `version` 乐观锁避免并发覆盖。

---

## 1. 检测本地文件变化

### 监听 + 扫描兜底

- 用文件监听器监听目录（如 `chokidar`/`notify`）。
- 启动时全量扫描一次；之后每 10 分钟增量扫描一次，兜底监听器漏掉的事件。
- 忽略临时文件/目录：`.git`、`node_modules`、`*.tmp`、`*.swp`、`*.DS_Store`。

### 快速判断变化

先比 `size + mtime`，不一致再算 `sha256`：

```
size + mtime 变了？
  是 → 计算 sha256
       sha256 与 manifest 一致 → 跳过
       不一致 → 进入同步队列
  否 → 跳过
```

### 事件去抖

文件写入过程中可能产生多次事件。设置 settle 窗口，比如 1 秒：

- 窗口内文件再次变化，则重新计时。
- 窗口结束后才真正读取文件，避免读到半截内容。

### 删除与重命名

- 删除：manifest 里有、本地没有 → 写 tombstone，软删 Supabase 数据。
- 重命名：旧路径删 + 新路径增；如果 `sha256` 相同，可以只改 `file_path`，保留 chunks。

## 2. 只同步变更部分

文件级判断只能知道“哪个文件变了”，真正增量要到 **chunk 级**。

### 分块策略

- Markdown/文本：优先按标题层级切 section。
- section 太大时，再用滚动哈希（buzhash）继续切块，避免插入/删除导致后续块全部变化。
- 每块用 `content_hash` 作为稳定 ID：内容变了，hash 就变，等价于旧块删、新块加。

### 增量同步算法

```
new = split(local_content)
old = supabase.get_chunks(file_path)

old_by_hash = { c.content_hash: c for c in old }

to_insert = new 中 content_hash 不在 old_by_hash 的块
to_delete = old 中 content_hash 不在 new 的块
to_keep   = new 中 content_hash 已在 old_by_hash 的块

只对 to_insert 生成 embedding
to_keep 的 embedding 完全不动
```

这样只有真正变化的块会更新，未变化块不会重新 embedding，节省时间和费用。

### 原子提交

用 Postgres 函数在一个事务里完成：

1. 校验 manifest 版本；
2. 删除 `to_delete`；
3. upsert `to_insert`；
4. 更新文件的 `sha256`、`version + 1`。

## 3. 处理冲突

冲突不等到写入时才处理，而是通过 `version` 乐观锁 + chunk 级三方对比。

### 冲突来源

- 同步过程中，本地文件又被修改。
- 同步过程中，Supabase 远端已被其他端修改。
- 双向同步时，本地和远端同时改了同一个块。

### 冲突检测

`sync_manifest` 中保存：

- `sha256`：上次同步成功的文件哈希。
- `version`：每次同步 +1。

同步开始时记录 `expected_version`。提交前：

- 复查本地文件 hash，如果又变了 → 放弃本次，重新入队。
- 用 `expected_version` 做条件更新，如果远端 version 不匹配 → 冲突。

### chunk 级三方对比

记录上次同步成功的 chunk 集合为 `base`。

- `local == base`，`remote == base` → 无变化；
- `local != base`，`remote == base` → 本地胜出；
- `local == base`，`remote != base` → 远端胜出；
- `local != base`，`remote != base` → 冲突。

### 解决策略

- 默认 **local-wins**：引擎产物以本地为准，但把远端旧版写入 `sync_conflicts`，避免丢知识。
- 可选 **remote-wins**：手工维护的记忆条目以 Supabase 为准。
- 可选 **merge**：不同 chunk 互不影响；同一 chunk 两边都改，则保留本地，并把冲突副本追加到 `sync_conflicts`。

---

## 4. 阴轨：可靠性护栏

- **配置校验**：启动时校验 Supabase URL/Key、目录白名单、分块参数、模型路由；新增配置必须同步修改读取点，修改后立即 `--dry-run` 验证。
- **超时**：外部模型调用按模型预设 timeout：B模型turbo 300秒，A模型600秒；超时进入重试队列。
- **重试**：指数退避，最多 5 次；超过后写 `sync_ledger` 并告警。
- **目录自愈**：启动时创建缺失目录；Supabase bucket/表缺失时自动补建。
- **质量门禁**：如果同步中引入质量检测，B模型turbo 跳过 reasoning 占比检测；不同模型必须独立规则，避免误杀重试。

## 5. 落地表结构

```sql
create table sync_manifest (
  path text primary key,
  sha256 text not null,
  size bigint not null default 0,
  mtime timestamptz not null,
  version bigint not null default 0,
  deleted boolean not null default false,
  last_synced_at timestamptz not null default now()
);

create table document_chunks (
  id text primary key,            -- sha256(file_path + content)
  file_path text not null references sync_manifest(path) on delete cascade,
  chunk_index int not null,
  content text not null,
  content_hash text not null,
  embedding vector(1536),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique(file_path, chunk_index)
);

create table sync_conflicts (
  id bigserial primary key,
  file_path text not null,
  chunk_id text,
  base_content text,
  local_content text,
  remote_content text,
  resolution text not null default 'pending',
  created_at timestamptz not null default now()
);

create table sync_ledger (
  id bigserial primary key,
  file_path text not null,
  operation text not null,
  status text not null,
  details jsonb,
  created_at timestamptz not null default now()
);
```

## 6. 原子提交函数

```sql
create or replace function sync_file_chunks(
  p_path text,
  p_chunks jsonb,
  p_new_sha256 text,
  p_expected_version bigint
) returns boolean language plpgsql security definer as $$
declare
  v_version bigint;
begin
  select version into v_version from sync_manifest where path = p_path for update;

  if v_version is null then
    insert into sync_manifest(path, sha256, version, last_synced_at)
    values (p_path, p_new_sha256, 1, now());
  elsif v_version <> p_expected_version then
    return false;
  else
    update sync_manifest
       set sha256 = p_new_sha256,
           version = version + 1,
           last_synced_at = now()
     where path = p_path;
  end if;

  delete from document_chunks
   where file_path = p_path
     and id not in (select (c->>'id') from jsonb_array_elements(p_chunks) c);

  insert into document_chunks(id, file_path, chunk_index, content, content_hash, embedding)
  select c->>'id', p_path, (c->>'chunk_index')::int, c->>'content', c->>'content_hash',
         nullif(c->>'embedding', '')::vector
    from jsonb_array_elements(p_chunks) c
  on conflict (id) do update
     set content = excluded.content,
         content_hash = excluded.content_hash,
         embedding = excluded.embedding,
         updated_at = now();

  return true;
end $$;
```

这个函数保证：

- 只更新变化块；
- 未变化块不重新 embedding；
- 版本冲突时返回 `false`，由上层决定走 `local-wins` 还是 `sync_conflicts`。

## 7. 检索侧

同步完成后，Supabase 作为记忆脑提供检索：

```sql
select file_path, chunk_index, content
from document_chunks
order by embedding <=> $query_embedding
limit 5;
```

增量同步不需要每次重建向量索引；chunk upsert 后索引自动更新即可。
