# 任务类型: eng

## 结论先行

不要在“API 调用线程”里直接加锁做后处理。

正确做法是：

> **并发调用 API → 结果进入队列 → 单写者（或按 key 分片的单写者）串行后处理 → 状态存储用版本号 CAS 提交**

锁仍然要，但只保护“状态存储”的短临界区，不保护“后处理业务逻辑”，更不能跨 API 调用持锁。

---

## 1. 问题模型

V7.5 方舟效能引擎中，假设：

- 有 `N` 个线程并发调用外部 API；
- 每个线程拿到结果后，需要更新共享状态；
- 后处理逻辑要求串行执行，至少要求**同一个业务 key 内串行**。

竞态条件主要有四类：

| 竞态类型 | 现象 |
|---|---|
| 写-写竞态 | 两个线程同时 `read-modify-write`，后写覆盖先写，丢更新 |
| 读-写竞态 | 后处理读到另一个线程写入一半的中间状态 |
| 顺序竞态 | 线程 A 先完成但后获得锁，导致最终状态顺序颠倒 |
| 锁跨 IO | 持锁调用 API，超时、阻塞、死锁，拖垮引擎 |

根因是：

> **后处理逻辑虽然写着“串行”，但没有被收口到唯一的执行流里。**

---

## 2. 设计原则

1. **锁不跨 IO**：API 调用期间绝不持锁。
2. **单写者原则**：同一个状态 key，同一时刻只允许一个后处理任务写。
3. **按 key 分片**：避免全局锁导致无关任务互相阻塞。
4. **版本号 CAS**：用乐观锁兜底，防止丢失更新。
5. **幂等 + 序号**：每个后处理任务带唯一 `seq`，重复执行不产生副作用。
6. **有界等待**：所有锁获取必须有 timeout，避免死锁。

---

## 3. 总体架构

```
Thread 1 ──> API ──┐
Thread 2 ──> API ──┤
Thread 3 ──> API ──┼──> PostTask Queue ──> PostProcessor（单写者/按key分片）
Thread 4 ──> API ──┘                              │
                                                   │ 获取状态写锁
                                                   v
                                            StateStore（版本号 CAS）
```

核心思想：

- API 调用线程只负责调用 API 和生成 `PostTask`；
- `PostProcessor` 是唯一允许写状态的地方；
- 如果必须全局串行，就用 1 个队列、1 个消费者；
- 如果不同 key 可以并行，就按 `key` 哈希分片，每个分片一个队列、一个消费者。

## 4. 锁机制详细设计

### 4.1 锁层级

| 层级 | 锁 | 作用 |
|---|---|---|
| L0 | 进程单例锁 | 防止同一台机器启动多个引擎实例 |
| L1 | 分布式锁 | 多实例部署时，防止跨进程并发写 |
| L2 | 分片状态锁 | 保护本地状态存储，按 key 分片 |
| L3 | 版本号 CAS | 乐观锁，防止更新丢失 |

锁的获取顺序：

```
L0 进程单例锁
  -> L1 分布式锁（仅多实例时）
    -> L2 分片状态锁
      -> L3 版本号 CAS
```

禁止逆序获取。

---

### 4.2 状态记录结构

```python
class StateRecord:
    def __init__(self, key, data):
        self.key = key
        self.data = data
        self.version = 0
        self.last_applied_seq = -1   # 已应用的最后任务序号
        self.updated_at = None
```

关键点：

- `version` 每次成功写入 +1；
- `last_applied_seq` 用于幂等；
- 写入时必须校验 `version`，不匹配则说明存在冲突。

### 4.3 状态存储：锁 + CAS

```python
import threading
import time
import copy
from zlib import crc32


class StateStore:
    def __init__(self, shard_count=256):
        self.shard_count = shard_count
        self._locks = [threading.RLock() for _ in range(shard_count)]
        self._records = {}
        self._seq_lock = threading.Lock()
        self._seq = 0

    def _shard(self, key):
        return crc32(key.encode("utf-8")) % self.shard_count

    def next_seq(self):
        with self._seq_lock:
            self._seq += 1
            return self._seq

    def read(self, key):
        with self._locks[self._shard(key)]:
            rec = self._records.get(key)
            return copy.deepcopy(rec) if rec else None

    def cas(self, key, expected_version, new_data, seq):
        with self._locks[self._shard(key)]:
            rec = self._records.setdefault(
                key, StateRecord(key, {})
            )

            # 版本不一致：有并发写者已经改了
            if rec.version != expected_version:
                raise ConflictError(
                    f"key={key} version conflict: "
                    f"expected={expected_version}, actual={rec.version}"
                )

            # 序号不大于已应用序号：重复任务，忽略
            if seq <= rec.last_applied_seq:
                return False

            rec.data = new_data
            rec.version += 1
            rec.last_applied_seq = seq
            rec.updated_at = time.time()
            return True
```

这里 `cas` 是原子的，因为整个操作在分片锁内完成。

### 4.4 后处理队列：串行化执行流

```python
from queue import Queue
from threading import Thread


class PostTask:
    def __init__(self, seq, key, result):
        self.seq = seq
        self.key = key
        self.result = result


class PostProcessor:
    def __init__(self, store, queue_count=4):
        self.store = store
        self.queue_count = queue_count
        self.queues = [Queue() for _ in range(queue_count)]
        self.threads = []

        for i in range(queue_count):
            t = Thread(target=self._run, args=(i,), daemon=True)
            self.threads.append(t)
            t.start()

    def submit(self, seq, key, result):
        q = self.queues[crc32(key.encode("utf-8")) % self.queue_count]
        q.put(PostTask(seq, key, result))

    def _run(self, idx):
        while True:
            task = self.queues[idx].get()
            try:
                self._process(task)
            except Exception:
                self._retry_or_dlq(task)
            finally:
                self.queues[idx].task_done()

    def _process(self, task):
        rec = self.store.read(task.key)

        # 幂等
        if rec and task.seq <= rec.last_applied_seq:
            return

        old_data = rec.data if rec else {}
        expected_version = rec.version if rec else 0

        # 业务状态机校验
        if not valid_transition(old_data, task.result):
            raise InvalidTransitionError(task)

        new_data = apply_result(old_data, task.result)

        # CAS 提交
        self.store.cas(
            task.key,
            expected_version,
            new_data,
            task.seq,
        )
```

说明：

- 如果 `queue_count = 1`，就是全局严格串行；
- 如果 `queue_count > 1`，同一个 key 永远进同一个队列，所以**同 key 严格串行，不同 key 可并行**；
- 后处理线程里不调用外部 API，只做纯内存/状态计算，锁持有时间极短。

## 5. 顺序一致性：要不要按请求顺序？

默认情况下，`PostTask` 进入队列的顺序是“API 返回完成的顺序”。

如果业务要求“最终状态必须按请求发起顺序”，则需要给任务分配单调递增的 `seq`，并在后处理器中做重排序：

```python
class OrderedPostProcessor:
    def __init__(self):
        self.cond = threading.Condition()
        self.pending = {}      # seq -> PostTask
        self.expected = 1      # 下一个期望处理的 seq

    def submit(self, task):
        with self.cond:
            if task.seq == self.expected:
                self._apply(task)
                self.expected += 1

                while self.expected in self.pending:
                    self._apply(self.pending.pop(self.expected))
                    self.expected += 1

            elif task.seq > self.expected:
                self.pending[task.seq] = task

            else:
                # seq 小于 expected，说明是重复或过期任务
                log_stale_task(task)

    def _apply(self, task):
        # 这里再进入 StateStore.cas
        pass
```

注意：

- 如果某个 `seq` 的请求超时或失败，必须立即提交一个“失败任务”补上缺口；
- 否则有序后处理会卡住等待缺失的 `seq`；
- 超时兜底：超过 `max_api_timeout + 安全余量` 后，自动跳过缺失序号。

## 6. 分布式锁：多实例部署时

如果 V7.5 引擎是多实例部署，本地锁不够，需要分布式锁。

Redis 分布式锁的推荐写法：

```python
import uuid
import redis


class RedisLock:
    def __init__(self, redis_client, lock_key, ttl=30000):
        self.redis = redis_client
        self.lock_key = lock_key
        self.token = uuid.uuid4().hex
        self.ttl = ttl

    def acquire(self, timeout=5):
        deadline = time.time() + timeout
        while time.time() < deadline:
            ok = self.redis.set(
                self.lock_key,
                self.token,
                nx=True,
                px=self.ttl,
            )
            if ok:
                return True
            time.sleep(0.05)
        return False

    def release(self):
        # 只有 token 匹配才删除，防止误删别人的锁
        lua = """
        if redis.call('get', KEYS[1]) == ARGV[1] then
            return redis.call('del', KEYS[1])
        else
            return 0
        end
        """
        self.redis.eval(lua, 1, self.lock_key, self.token)
```

更稳妥的做法是：

- 分布式锁只用于“防止多实例同时写”；
- 真正的一致性由 `StateStore.cas` 的版本号兜底；
- 如果要求更强一致，可以引入 fencing token：获取锁时递增全局 token，写入时校验 token 不小于当前记录的 token。

## 7. 引擎单例锁：避免 PID 文件竞态

不要用 PID 文件自检测，容易踩“自己刚写入 PID 就以为已有实例”的坑。

用文件锁：

```python
import fcntl


class EngineSingletonLock:
    def __enter__(self):
        self.fd = open("/var/lock/ark_engine.lock", "w")
        try:
            fcntl.flock(self.fd, fcntl.LOCK_EX | fcntl.LOCK_NB)
        except OSError:
            raise SystemExit("Engine already running")

    def __exit__(self, *args):
        fcntl.flock(self.fd, fcntl.LOCK_UN)
        self.fd.close()
```

## 8. API 调用层的配套避坑

锁机制只解决竞态，还要配合 API 调用的稳定性：

```python
import urllib.request
import json


def _direct_opener():
    # 直连，避免环境变量里的全局代理导致 ProxyError
    return urllib.request.build_opener(
        urllib.request.ProxyHandler({})
    )


def call_api(model, payload):
    # 按历史经验：B 模型 turbo 用 300 秒，A 模型用 600 秒
    timeout = 300 if model == "B-turbo" else 600

    req = urllib.request.Request(
        API_URL,
        data=json.dumps(payload).encode("utf-8"),
        headers={"Content-Type": "application/json"},
    )

    with _direct_opener().open(req, timeout=timeout) as resp:
        result = json.loads(resp.read().decode("utf-8"))

    # B 模型用 Responses API 时，必须校验 content 非空
    if model == "B-turbo" and not result.get("content"):
        raise EmptyContentError("B-turbo response content is empty")

    return result
```

API 调用异常时，不要静默丢弃：

```python
def api_worker(store, post_processor, model, params):
    seq = store.next_seq()

    try:
        result = call_api(model, params)
    except Exception as e:
        result = {"error": str(e)}

    post_processor.submit(seq, params["state_key"], result)
```

这样即使失败，也会进入后处理，按失败结果推进状态机，不会造成状态缺失。

## 9. 验证方案

至少需要四类测试：

| 测试 | 验证点 |
|---|---|
| 并发压力测试 | 100 个线程同时提交同一个 key 的后处理，最终 `version == 100`，数据无丢失 |
| 乱序测试 | 提交 `seq=3,1,2`，有序后处理最终按 `1,2,3` 应用 |
| 幂等测试 | 同一个 `seq` 重复提交，状态只更新一次 |
| 锁超时测试 | 故意长时间持锁，后处理任务超时后进入 DLQ，不 deadlock |

---

## 10. 结论

V7.5 方舟效能引擎的状态一致性，不能靠“后处理代码里加一把大锁”解决。

完整方案是：

> **并发 API 调用 + 有序结果队列 + 单写者后处理 + 分片锁 + 版本号 CAS + 幂等序号**

这套机制把“并发无序性”限制在无共享状态的 API 调用阶段，把“后处理阶段”变成确定性的串行执行流，相当于持续向引擎注入负熵，抑制功能熵增，避免系统自然退化。
