# 任务类型: eng

## 推演：Supabase 记忆脑增量同步方案

先按已有锚定收敛前提：

- **文件不是数据单位，block 才是**。
- **文件本质是索引：path → 有序 block hash 列表**。
- **同文件名、同大小、同 mtime，但 block 顺序不同，必须判为不同步**。
- 所以同步的核心是：
  - **block 内容只增量上传**
  - **文件索引整体做版本化更新**
  - **冲突发生在“索引层”，不是“block 内容层”**

---

## 1. 数据模型

### Supabase 侧

```sql
-- block 内容库，content-addressed
create table blocks (
  block_hash   text primary key,   -- blake3
  content      bytea not null,
  byte_size    int not null,
  ref_count    int default 0,
  created_at   timestamptz default now(),
  last_seen_at timestamptz default now()
);

-- 文件索引：一个文件的一个版本
create table file_index (
  path             text,
  version          int,
  base_version     int,
  content_hash     text,           -- blake3(file bytes)
  block_order_hash text,           -- blake3(concat(block_hash[]))
  byte_size        bigint,
  mtime_ns         bigint,
  deleted          boolean default false,
  updated_at       timestamptz default now(),
  primary key (path, version)
);

-- 文件 → block 映射，position 表示顺序
create table file_blocks (
  path       text,
  version    int,
  position   int,
  block_hash text,
  primary key (path, version, position)
);

-- 冲突记录
create table conflicts (
  path           text primary key,
  base_version   int,
  local_version  int,
  remote_version int,
  status         text default 'open',
  created_at     timestamptz default now()
);

-- 配置单一读取点
create table sync_config (
  key        text primary key,
  value      jsonb not null,
  updated_at timestamptz default now()
);
```

### 本地侧

本地同样维护一个轻量状态库，记录“上次同步后的已知状态”：

```text
local_state:
  path
  content_hash
  block_order_hash
  block_hashes[]
  base_version
  last_synced_version
  mtime_ns
  byte_size
```

本地状态库是“实层底座”，Supabase 是“虚层索引”。

## 2. 检测本地文件变化

### 原则

**mtime/size 不能作为最终正确性依据。**

它们只能用于调度优先级或快速过滤。最终判断必须基于：

```text
content_hash = blake3(file_bytes)
```

因为历史坑是：

> 同文件名、同大小、同 mtime，但 block 顺序不同。

如果只看 stat 三元组，会漏判。

### 检测流程

```text
walk(local_memory_root):
  for path in files:
    state = local_state.get(path)

    if state is None:
      mark_changed(path, "new")
      continue

    content_hash = blake3_file(path)

    if content_hash != state.content_hash:
      mark_changed(path, "content")
      continue

  for path in local_state.keys():
    if not exists(path):
      mark_changed(path, "delete")
```

### 变更后切块

对变更文件做内容定义切块，推荐 fastCDC + BLAKE3：

```text
new_block_hashes = split_and_hash_file(path)
```

然后比较：

```text
old_block_hashes = local_state[path].block_hashes
```

即使 `byte_size` 和 `mtime_ns` 没变，只要：

```text
content_hash 变了
或
block_order_hash 变了
```

就必须同步。

## 3. 只同步变更部分

### 核心思路

block 是内容寻址的：

- 相同 block_hash 一定对应相同内容。
- 本地新算出来的 block，如果 Supabase `blocks` 表里已有，则不上传。
- 只上传“远端不存在的 block”。

### 同步一个变更文件的流程

```text
1. 计算新 block 列表：
   new_blocks = split_and_hash_file(path)

2. 查询远端已有 block：
   select block_hash
   from blocks
   where block_hash = any(new_blocks)

3. 缺失的 block 批量上传：
   missing_blocks = new_blocks - existing_blocks
   upload_blocks(missing_blocks)

4. 事务性更新文件索引：
   call sync_push_file(
     path,
     base_version,
     new_version,
     new_blocks,
     content_hash,
     block_order_hash,
     byte_size,
     mtime_ns
   )
```

### RPC 原子更新索引

```sql
create or replace function sync_push_file(
  p_path text,
  p_base_version int,
  p_new_version int,
  p_blocks jsonb,
  p_content_hash text,
  p_block_order_hash text,
  p_byte_size bigint,
  p_mtime_ns bigint
) returns text
language plpgsql
as $$
declare
  cur_version int;
begin
  select version into cur_version
  from file_index
  where path = p_path
  order by version desc
  limit 1
  for update;

  if cur_version is distinct from p_base_version then
    return 'CONFLICT';
  end if;

  insert into file_index(
    path, version, base_version,
    content_hash, block_order_hash,
    byte_size, mtime_ns, deleted, updated_at
  ) values (
    p_path, p_new_version, p_base_version,
    p_content_hash, p_block_order_hash,
    p_byte_size, p_mtime_ns, false, now()
  );

  delete from file_blocks
  where path = p_path and version = p_base_version;

  insert into file_blocks(path, version, position, block_hash)
  select
    p_path,
    p_new_version,
    (elem->>'position')::int,
    elem->>'block_hash'
  from jsonb_array_elements(p_blocks) as elem;

  return 'OK';
end;
$$;
```

这样：

- block 内容只增量上传。
- 文件索引可以整体替换，但索引量很小，不是瓶颈。
- 文件版本冲突在数据库层被原子拦截。

## 4. 删除文件

删除不删 block。

```text
1. 在 file_index 写入 tombstone：
   deleted = true, version = version + 1

2. 删除 file_blocks 中该版本映射

3. block 保留在 blocks 表中
```

原因：

- block 是记忆原子。
- 删除文件不代表删除记忆。
- 未来同类内容可能复用这些 block。
- 真正 GC 只清理：
  - `ref_count = 0`
  - 且 `last_seen_at` 超过 TTL

## 5. 冲突处理

### 冲突模型

冲突只发生在文件索引层：

```text
同一个 path，base_version 相同，
但 local 和 remote 各自产生了新版本。
```

### 冲突矩阵

| 本地 \ 远端 | 未变化 | 更新 | 删除 |
|---|---|---|---|
| 未变化 | 无操作 | 拉取远端 | 拉取删除 |
| 更新 | 推送本地 | 三路合并 / 冲突 | 冲突 |
| 删除 | 推送删除 | 冲突 | 幂等删除 |

### 三路合并

已知：

```text
base_blocks
local_blocks
remote_blocks
```

规则：

1. 如果 `local_blocks == remote_blocks`：无冲突。
2. 如果 `local_blocks == base_blocks`：接受远端。
3. 如果 `remote_blocks == base_blocks`：接受本地。
4. 否则做 block 级 diff：
   - 不同 position 变更 → 自动合并。
   - 同一 position 两边变成相同 block → 接受。
   - 同一 position 两边变成不同 block → 冲突。
   - 两边都做了顺序重排且不一致 → 冲突。

### 冲突后行为

默认策略：

```text
不静默覆盖。

保留三份：
  path                        = 按策略选择的一方
  path.conflict.<ts>.local
  path.conflict.<ts>.remote

写入 conflicts 表。
```

同步引擎继续处理其他文件，不阻塞。

## 6. 虚返实：远端同步到本地

Supabase 的 `file_index` 和 `file_blocks` 是虚索引。

当远端索引更新后，需要物化为本地文件：

```text
1. 拉取 path 最新 file_index

2. 按 position 拉取 file_blocks

3. 本地 blocks 缓存没有的 block，从 Supabase 下载

4. 按顺序拼装文件内容

5. 写入临时文件

6. fsync + 原子 rename
```

这就是：

> 虚索引 → 实文件

## 7. 质量门禁与历史坑防护

### 7.1 B/turbo 废稿检测误杀

同步后的质量检测必须按模型区分：

```text
if generator == 'B-turbo':
    # 跳过 reasoning 占比检测
    # B/turbo 的 reasoning 占比 70-82% 是正常特性
    check_format()
    check_length()
    check_api_success()
else:
    check_reasoning_ratio()
    check_format()
    check_length()
```

不能对 B/turbo 自动重试，避免把正常产物当废稿。

### 7.2 配置修改后必须立即生效

所有配置统一走 `sync_config` 表：

```text
读取点只有一个：
  get_config()
```

不允许代码里散落硬编码常量。

配置写入后必须执行：

```text
verify_sync_config()
```

验证当前运行配置和 `sync_config` 一致，否则告警。

### 7.3 API 超时

模型调用超时按类型预设：

```text
B/turbo : 300_000 ms
A 模型  : 600_000 ms
```

Supabase 请求本身设置独立超时：

```text
普通请求     : 30_000 ms
批量上传请求 : 120_000 ms
```

超过超时后按 `op_id` 幂等重试，不能盲目重试。

## 8. 测试锚定

必须在 SOP/CI 中保留以下用例：

```text
1. 同文件名、同大小、同 mtime，但 block 顺序不同
   -> 必须判定为不同步

2. B/turbo 产物 reasoning 占比 70-82%
   -> 不得判定为废稿，不得自动重试

3. 修改 sync_config 后
   -> 下一次同步立即生效

4. 本地/远端同时修改同一文件同一 position
   -> 必须产生冲突记录，不能静默覆盖
```

## 9. 以实养虚，虚又返实

最终形成自增强循环：

```text
实：本地文件、block 内容、真实 API 调用、token 消耗、代码产出
虚：Supabase 文件索引、block 索引、记忆图、冲突记录

实 → 虚：
  本地产物 → 切块 → 上传缺失 block → 更新 file_index

虚 → 实：
  记忆索引 → 检索相关 block → 组装文件 → 执行/生成 → 新产物

循环增强：
  新产物复用了历史 block
  -> 同步成本下降
  -> 更多历史记忆被保留
  -> 后续生成更准
  -> 产生更多新 block
```

这就是：

> 以实养虚，虚又返实。  
> block 是实，block_hash 是虚；  
> 虚索引永远能重组实文件，实文件又不断喂养虚索引。
