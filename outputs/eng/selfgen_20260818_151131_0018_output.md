# 任务类型: eng

沿用锚定：把「Supabase 记忆脑」设计为 **本地优先 + Supabase 做远端存储与索引**。增量同步就是“阳轨：变更泵 + 阴轨：自愈网”。

## 1. 总体状态机

每个文件在同步系统中只有一个状态：

| 状态 | 含义 |
|---|---|
| `SYNCED` | 本地内容与远端 manifest 一致 |
| `LOCAL_DIRTY` | 本地已变更，未推送到远端 |
| `REMOTE_DIRTY` | 远端已变更，未拉取到本地 |
| `CONFLICT` | 本地和远端都变了，需仲裁 |
| `SYNCING` | 正在上传/下载 |
| `DELETED_LOCAL` / `DELETED_REMOTE` | 单侧删除，待同步删除 |

同步引擎维护一张本地状态表：

```text
file_state(
  path,
  local_checksum,
  base_checksum,        -- 上次同步时本地内容
  remote_checksum,      -- 上次同步时远端内容
  base_remote_version,  -- 上次同步时远端版本号
  dirty_local,
  dirty_remote,
  conflict_pending
)
```

所有判断都基于这张表，而不是直接比较文件时间戳。

## 2. 检测本地文件变化

### 2.1 双通道检测

- **实时通道**：监听本地目录，使用 `inotify` / `FSEvents` / Watchman 等。  
  事件：`add`、`change`、`unlink`、`rename`。
- **兜底通道**：定时全量扫描，例如每 30 秒比对 `path + size + mtime_ns`。  
  防止 watcher 漏掉网络盘、休眠唤醒后的批量修改。

### 2.2 防抖与指纹计算

文件写入不是原子的，必须防抖：

```text
事件进入 ChangeQueue
→ 同一路径 1.5s 内无新事件
→ 读取文件 stat
→ 计算 SHA-256 或 chunk 指纹
→ 与 base_checksum 比较
→ 产生 LocalChangeOp
```

### 2.3 变更操作类型

```text
UPSERT：新增或修改
DELETE：删除
RENAME：路径变化，但文件内容可能没变
```

如果文件内容 hash 没变、只是路径变了，则不重新上传 chunk，只更新 manifest 中的 path。

## 3. 只同步变更部分

采用三层增量：

```text
操作级增量：只推送 sync_ops 中的变更记录
文件级增量：只处理 dirty 文件
块级增量：只上传/下载变更的 chunk
```

### 3.1 内容分块

对超过阈值的大文件，使用 **内容定义分块（CDC）**，例如 FastCDC：

```text
min chunk: 64KB
avg chunk: 128KB
max chunk: 256KB
```

每个 chunk 用 SHA-256 寻址，存储在 Supabase Storage：

```text
memory_brain/chunks/{sha256}
```

因为地址是内容 hash，天然去重。  
小文件（< 256KB）直接整体上传，不切块。

### 3.2 增量上传

本地文件变更后：

1. 重新分块，得到新的 chunk hash 列表。
2. 和远端 manifest 中该文件的旧 chunk 列表对比。
3. 只上传缺失或变化的 chunk。
4. 最后调用一个事务性 RPC：

```sql
select sync_push_file(
  p_path,
  p_file_id,
  p_checksum,
  p_chunk_hashes,
  p_source_replica,
  p_base_remote_version,
  p_op_id
);
```

该 RPC 内部完成：

- 检查 `base_remote_version` 是否等于远端当前版本；
- 不相等则返回 `conflict`；
- 相等则更新 `file_manifest`，写入 `file_chunks`，追加一条 `sync_ops`；
- `op_id` 唯一，重试时幂等跳过。

### 3.3 增量拉取

远端变更通过轮询 `sync_ops` 或 Supabase Realtime 获得：

```text
拉取 sync_ops where id > last_cursor and source_replica != local
→ 对每个 op：
    → 检查本地是否 dirty
    → 如果没有本地冲突：
        → 下载缺失 chunk
        → 写入临时文件
        → 原子 rename 覆盖本地文件
        → 更新 file_state
    → 如果本地也 dirty：
        → 进入冲突处理
```

下载时也只下载本地缺失的 chunk，而不是整个文件。

## 4. 冲突处理

### 4.1 冲突判定

满足以下条件判定冲突：

```text
本地文件自上次同步后发生变化
且
远端 manifest 自上次同步后也发生变化
```

### 4.2 仲裁模式

| 模式 | 行为 |
|---|---|
| `local-wins` | 保留本地，覆盖远端；覆盖前把远端版本存入 `conflicts/` |
| `remote-wins` | 保留远端，覆盖本地；覆盖前把本地版本存入 `.memory/conflicts/` |
| `manual` | 两端都不覆盖，生成冲突副本，由用户/元控制器决策 |

默认推荐 `local-wins + conflict copy`，保证不丢数据。

### 4.3 冲突副本位置

```text
本地：.memory/conflicts/{path}.{timestamp}.local.md
远端：memory_brain/conflicts/{path}.{timestamp}.remote.md
```

同时写入冲突表：

```sql
sync_conflicts(
  path,
  local_hash,
  remote_hash,
  local_version,
  remote_version,
  resolved,
  resolution
);
```

未解决前，该文件不进入后续同步。

## 5. Supabase 核心表设计

```sql
-- 文件 manifest
create table file_manifest (
  path text primary key,
  file_id uuid,
  checksum text,
  version_remote bigint default 0,
  updated_at timestamptz,
  deleted boolean default false,
  source_replica text
);

-- 内容寻址 chunk
create table chunk_objects (
  hash text primary key,
  size bigint,
  storage_path text,
  ref_count bigint default 0
);

-- 文件与 chunk 的映射
create table file_chunks (
  file_id uuid,
  chunk_hash text,
  chunk_index int,
  primary key (file_id, chunk_index)
);

-- 同步操作日志
create table sync_ops (
  id bigserial primary key,
  op_id uuid unique,
  source_replica text,
  path text,
  op text,              -- upsert / delete
  file_id uuid,
  checksum text,
  chunk_hashes text[],
  version bigint,
  created_at timestamptz
);

-- 各副本拉取游标
create table sync_cursors (
  replica_id text primary key,
  last_op_id bigint
);
```

## 6. 阴轨：自愈与避坑

### 6.1 配置读取点单一化

所有模块必须从同一个 `SyncConfig` 对象读取配置：

```yaml
sync:
  watch_paths: [./memory]
  ignore: ["*.tmp", ".DS_Store", ".memory/conflicts/**"]
  chunk_size: { min: 64KB, avg: 128KB, max: 256KB }
  small_file_threshold: 256KB
  conflict_mode: local-wins
  timeout:
    storage: 30s
    ai_model_turbo: 300s   # B 模型
    ai_model_standard: 600s # A 模型
```

如果新增配置项，必须同步修改所有读取点：

- watcher 过滤规则
- 手动扫描过滤规则
- chunker 参数
- uploader / downloader
- 冲突仲裁器
- 自愈巡检

修改配置后立即重新加载并做一次配置校验，不能只改一处。

### 6.2 超时兜底

所有外部调用必须显式设置 timeout：

- Supabase Storage 上传/下载：30s
- Postgres RPC：30s
- 同步过程中如果调用 AI 做摘要/标签：B 模型 turbo 用 300s，A 模型用 600s

超时后进入重试队列，而不是直接失败。

### 6.3 失败重试

```text
sync_retry_queue(
  op_id,
  op_type,
  payload,
  attempts,
  next_retry_at,
  last_error
)
```

- 上传 chunk 是幂等的，可以无限重试；
- `sync_push_file` 带 `op_id`，重复执行不会产生重复操作；
- 指数退避 + 抖动；
- 超过最大重试次数后告警，而不是静默丢弃。

### 6.4 目录自愈

每次同步周期开始前检查：

- 本地目录不存在 → 从远端 manifest 重建；
- Supabase bucket 不存在 → 自动创建；
- `file_manifest` 表不存在 → 自动跑 migration；
- 远端 manifest 引用了 chunk，但 chunk 对象丢失 → 从本地或其他副本补传；
- 本地指纹库损坏 → 全量扫描重建。

### 6.5 模型差异质检

如果同步后接入 AI 质量检测，必须按模型区分规则：

- B 模型（turbo）的 `reasoning_ratio` 在 70%–82% 是正常特性；
- 不能因为 reasoning 占比高就判定为废稿并自动重试；
- B 模型跳过 reasoning 占比检测，只做内容完整性检测。

## 7. 同步循环总览

```text
阳轨：
本地文件事件
  → 防抖 + 指纹计算
  → 生成变更操作
  → 增量上传/下载
  → 更新 manifest
  → 更新索引

阴轨：
配置校验
  → 超时控制
  → 失败重试
  → 目录自愈
  → 冲突备份
  → 模型差异质检
```

整个系统形成闭环：本地无序的文件变更，通过增量同步变成 Supabase 中有序、可检索、可复用的记忆资产。
