# Supabase 记忆脑增量同步方案推演

## 0. 总体架构

```
┌─────────────┐      ┌──────────────────┐      ┌────────────────┐
│ 本地文件树   │ ──> │ 变更检测层        │ ──> │ 同步队列(SQLite)│
│ (.md/.json) │      │ FSEvents+轮询    │      │ outbox 表      │
└─────────────┘      └──────────────────┘      └───────┬────────┘
                                                       │
                          ┌────────────────────────────┘
                          ▼
                ┌──────────────────┐      ┌───────────────────┐
                │ 增量计算 / diff   │ ──> │ Supabase RPC       │
                │ hash + patch     │      │ (RLS + 乐观锁)    │
                └──────────────────┘      └─────────┬─────────┘
                                                    │
                          ┌─────────────────────────┘
                          ▼
                ┌──────────────────┐      ┌───────────────────┐
                │ Realtime 广播     │ ──> │ 其他端订阅 → 落盘   │
                │ memory_events     │      │                  │
                └──────────────────┘      └───────────────────┘
```

核心三层：**变更检测 → 增量传输 → 冲突协调**。下面分别推演。

## 1. 本地文件变化检测

### 1.1 三种方案对比

| 方案 | 延迟 | CPU/IO | 可靠性 | 复杂度 |
|------|------|--------|--------|--------|
| **轮询 stat** | 秒级 | O(n) 线性 | 高（兜底） | 低 |
| **FSEvents 监听** | 毫秒级 | O(1) 事件驱动 | 中（漏事件） | 中 |
| **混合（推荐）** | 毫秒级 + 兜底 | 低 | 高 | 中 |

### 1.2 推荐：混合方案

**A. 实时层：FSEvents**
- Node: `chokidar`；Python: `watchdog`；Rust: `notify`
- 监听事件：`add` / `change` / `unlink` / `rename`
- **防抖**：500ms~2s 合并（编辑器原子写会触发多次）
- **忽略模式**：`.git/`、`node_modules/`、临时文件 `*.swp`、`4913`

**B. 兜底层：定时轮询**
- 每 30s 全量 `stat` 一次
- 比对 `mtime + size`，差异项入队
- 处理 FSEvents 漏报（如网络挂载、容器内）

**C. 启动 reconciliation**
- 进程启动时全量扫描 → 与本地元数据表 diff → 补齐遗漏

### 1.3 本地元数据表（SQLite）

```sql
CREATE TABLE file_meta (
  path         TEXT PRIMARY KEY,
  content_hash TEXT,             -- sha256(normalized content)
  size         INTEGER,
  mtime_ms     INTEGER,
  remote_version INTEGER,        -- 远端乐观锁版本号
  local_state  TEXT,             -- 'synced' | 'pending' | 'conflict'
  pending_op   TEXT,             -- 'upsert' | 'delete'
  last_synced_at INTEGER
);

CREATE TABLE sync_outbox (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  path TEXT, op TEXT, content_hash TEXT,
  base_version INTEGER, attempts INTEGER DEFAULT 0,
  created_at INTEGER
);

CREATE INDEX idx_outbox_pending ON sync_outbox(created_at);
```

### 1.4 内容哈希策略
- **规范化**：先统一行尾、去除 BOM、压缩连续空白，避免无意义变更
- **大文件分块**：>1MB 用 rolling hash（rsync 风格），定位变动块
- **向量缓存复用**：hash 不变 → 直接复用嵌入，不调 embedding API

## 2. 只同步变更部分

### 2.1 表结构（Supabase Postgres）

```sql
-- 主表：当前快照
CREATE TABLE memory_nodes (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      UUID NOT NULL REFERENCES auth.users(id),
  path         TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  content      TEXT,                 -- 小文件直存；大文件存 storage URL
  storage_url  TEXT,                 -- 大文件走 Supabase Storage
  size         BIGINT,
  version      BIGINT NOT NULL DEFAULT 1,
  updated_at   TIMESTAMPTZ DEFAULT now(),
  deleted_at   TIMESTAMPTZ,
  UNIQUE(user_id, path)
);

-- 版本历史（用于三方合并、回滚）
CREATE TABLE memory_node_versions (
  node_id   UUID NOT NULL REFERENCES memory_nodes(id) ON DELETE CASCADE,
  version   BIGINT NOT NULL,
  content_hash TEXT,
  content   TEXT,
  author    TEXT,                    -- 'client_id'
  created_at TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (node_id, version)
);

-- 事件日志（下行同步源）
CREATE TABLE memory_events (
  id         BIGSERIAL PRIMARY KEY,
  user_id    UUID NOT NULL,
  node_id    UUID NOT NULL,
  path       TEXT NOT NULL,
  op         TEXT NOT NULL,          -- 'upsert' | 'delete'
  new_version BIGINT,
  content_hash TEXT,
  created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_events_user ON memory_events(user_id, id);

-- RLS
ALTER TABLE memory_nodes ENABLE ROW LEVEL SECURITY;
ALTER TABLE memory_events ENABLE ROW LEVEL SECURITY;
ALTER TABLE memory_node_versions ENABLE ROW LEVEL SECURITY;

CREATE POLICY user_own ON memory_nodes
  FOR ALL USING (user_id = auth.uid());

CREATE POLICY user_own ON memory_events
  FOR SELECT USING (user_id = auth.uid());
```

### 2.2 上行同步 RPC

```sql
CREATE OR REPLACE FUNCTION sync_upsert_batch(
  items jsonb
) RETURNS jsonb AS $$
DECLARE
  item jsonb;
  results jsonb := '[]'::jsonb;
  v_id UUID; v_ver BIGINT;
BEGIN
  FOR item IN SELECT * FROM jsonb_array_elements(items)
  LOOP
    SELECT id, version INTO v_id, v_ver
      FROM memory_nodes
     WHERE user_id = auth.uid() AND path = item->>'path';
     
    IF v_id IS NULL THEN
      -- 新增
      INSERT INTO memory_nodes(user_id, path, content_hash, content, size, version)
      VALUES (auth.uid(), item->>'path', item->>'hash', item->>'content',
              (item->>'size')::bigint, 1)
      RETURNING id INTO v_id;
      
      INSERT INTO memory_node_versions(node_id, version, content_hash, content, author)
      VALUES (v_id, 1, item->>'hash', item->>'content', item->>'client_id');
      
      INSERT INTO memory_events(user_id, node_id, path, op, new_version, content_hash)
      VALUES (auth.uid(), v_id, item->>'path', 'upsert', 1, item->>'hash');
      
      results := results || jsonb_build_object('path', item->>'path', 'status', 'ok', 'version', 1);
      
    ELSIF (item->>'base_version')::bigint = v_ver THEN
      -- 乐观锁通过，更新
      UPDATE memory_nodes
         SET content_hash = item->>'hash',
             content = item->>'content',
             size = (item->>'size')::bigint,
             version = v_ver + 1,
             updated_at = now(),
             deleted_at = NULL
       WHERE id = v_id;
       
      INSERT INTO memory_node_versions(node_id, version, content_hash, content, author)
      VALUES (v_id, v_ver + 1, item->>'hash', item->>'content', item->>'client_id');
      
      INSERT INTO memory_events(user_id, node_id, path, op, new_version, content_hash)
      VALUES (auth.uid(), v_id, item->>'path', 'upsert', v_ver + 1, item->>'hash');
      
      results := results || jsonb_build_object('path', item->>'path', 'status', 'ok', 'version', v_ver + 1);
      
    ELSE
      -- 版本冲突
      results := results || jsonb_build_object(
        'path', item->>'path',
        'status', 'conflict',
        'server_version', v_ver,
        'server_hash', (SELECT content_hash FROM memory_nodes WHERE id = v_id)
      );
    END IF;
  END LOOP;
  RETURN results;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

### 2.3 文件内增量（diff patch）

对大文本/JSON 记忆文件：
- 客户端本地保留 `base_content`
- 修改后生成 `diff-match-patch` 或 `fast-json-patch`
- RPC 接收 `patch` 而非完整内容
- 服务端：`base_hash` 校验 → 应用 patch → 存新版本

```ts
// 客户端伪代码
const patch = dmp.patch_make(baseContent, newContent);
await rpc('sync_patch', {
  path, base_hash: baseHash, patch, base_version: remoteVersion
});
```

### 2.4 向量数据增量

记忆脑通常含向量化索引：

```
文件 → chunk → embedding → 向量表
```

**增量策略**：
1. 文件 hash 不变 → 跳过（向量全复用）
2. 文件 hash 变化：
   - 按 chunk 边界（段落/markdown heading）切分
   - 计算 chunk 级 hash
   - 仅对变更 chunk 调 embedding API
   - 删除旧 chunk 向量，插入新向量

```sql
CREATE TABLE memory_chunks (
  id UUID PRIMARY KEY,
  node_id UUID REFERENCES memory_nodes(id) ON DELETE CASCADE,
  chunk_index INT,
  chunk_hash TEXT,
  content TEXT,
  embedding VECTOR(1536),
  UNIQUE(node_id, chunk_index)
);
```

### 2.5 下行同步

**A. Pull 模式（启动 / 重连）**
```ts
const { data } = await supabase.rpc('pull_events', {
  since_id: lastEventId,
  limit: 500
});
// 顺序应用 events → 本地文件
```

**B. Push 模式（实时）**
```ts
supabase.channel('memory-sync')
  .on('postgres_changes',
    { event: 'INSERT', schema: 'public', table: 'memory_events', filter: `user_id=eq.${uid}` },
    payload => applyEventToLocal(payload.new)
  )
  .subscribe();
```

**应用事件到本地文件**：
- `upsert`：写文件，更新 `file_meta`（remote_version = new_version, local_state='synced'）
- `delete`：删本地文件 + 元数据
- **回环防护**：服务端事件回写到本地时，要 short-circuit（避免自己触发的事件再进入 outbox）

### 2.6 大文件与二进制
- > 1MB 或非文本：直接走 Supabase Storage
- DB 仅存 `storage_url + content_hash + size`
- 上传用 `Content-Addressed`：object key = `user_id/hash`，天然去重
- 多部分上传 / 续传

### 2.7 批量与节流
- RPC 批量数组（≤ 50 项/批）
- 客户端 worker 队列，并发 4
- 指数退避重试（2s, 4s, 8s... 上限 60s）

## 3. 冲突处理

### 3.1 冲突类型

| 类型 | 触发条件 | 严重度 |
|------|----------|--------|
| 编辑冲突 | 两端基于同 base_version 修改 | 中 |
| 删除/修改冲突 | 一端删一端改 | 高 |
| 重命名/移动冲突 | 两端 rename 到不同路径 | 中 |
| 时钟漂移 | updated_at 不可靠 | 低 |

### 3.2 检测机制

**乐观锁（核心）**：
- 每次提交带 `base_version`
- `base_version == server.version` → 通过，`version += 1`
- 否则 → 返回 `conflict` + 当前 server 内容

**客户端回退**：
- 比对 `local_hash` vs `server_hash`，相同则视为无冲突（已同步）

### 3.3 解决策略矩阵

| 策略 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| **LWW** (Last-Write-Wins) | 个人低频同步 | 简单 | 数据丢失 |
| **字段级 LWW** | 结构化元数据 | 精细 | 需 schema 设计 |
| **3-way merge** | 文本/JSON | 自动合并 | 失败需人工 |
| **CRDT (Yjs/Automerge)** | 协作编辑 | 无冲突 | 存储膨胀，文本不适用 |
| **Union (集合并集)** | 标签、链接 | 自然 | 无法删除 |

### 3.4 推荐组合策略

针对记忆脑的混合方案：

```
字段类型          解决策略
─────────────────────────────
元数据（title, tags）  字段级 LWW
正文内容              3-way merge (diff3) + 冲突标记
标签集合              Union + tombstone
向量索引              重建（无冲突，跟随正文版本）
```

### 3.5 三方合并流程

冲突时客户端执行：

```ts
async function resolveConflict(path, localContent, serverContent) {
  const baseContent = await fetchVersion(path, localBaseVersion);
  
  // 1. 尝试文本 3-way merge
  const merged = diff3Merge(baseContent, localContent, serverContent);
  
  if (merged.conflicts.length === 0) {
    // 自动合并成功，重新提交
    await sync_upsert(path, merged.result, base_version: serverVersion);
  } else {
    // 2. 生成冲突标记文件，留待用户解决
    await fs.writeFile(
      `${path}.conflict.md`,
      renderConflictMarkers(merged)
    );
    await notifyUser(path, 'conflict_detected');
  }
}
```

冲突标记（git 风格）：
```markdown
<<<<<<< local
我刚才修改的内容
=======
服务端的版本
>>>>>>> remote
```

### 3.6 删除/修改冲突

- 服务端：删除即 `deleted_at` 设置；后续 upsert 检测到 `deleted_at != NULL` 但 client 提交 `upsert` → 返回特殊冲突码 `delete_modify_conflict`
- 默认策略：**修改优先**（恢复节点，version 续接）
- 用户可选"确认删除"

### 3.7 历史版本辅助

`memory_node_versions` 表保留最近 N=20 版本：
- 三方合并需要 base
- 用户回滚
- 审计 / 时间机器

定期清理：保留最近 N 版 + 每天首版（保留 90 天）。

## 4. 可靠性保障

### 4.1 At-least-once 投递
- 本地 `sync_outbox` 持久化
- RPC 成功 → 删除 outbox 项
- 失败 → 重试，**幂等键**用 `content_hash`（重复提交同 hash → 直接返回 ok）

### 4.2 幂等设计
```sql
-- 同 path + 同 hash + 同 base_version → 视为重复
-- RPC 内判断：
IF content_hash = (SELECT content_hash FROM memory_nodes WHERE ...)
   AND base_version = server_version THEN
   RETURN jsonb_build_object('status', 'ok', 'version', server_version);
END IF;
```

### 4.3 网络恢复
- 重连 → 拉取 `last_event_id` 之后所有事件 → 顺序应用
- 兜底全量 reconcile：
  ```ts
  const remoteList = await rpc('list_all_nodes'); // 含 path + hash
  const localList = scanLocalFiles();
  // 计算 diff → 双向补齐
  ```

### 4.4 一致性边界
- 客户端时钟不可信 → 全用 `server_updated_at`
- 事件 ID 单调递增（BIGSERIAL）→ 下行同步 watermark 可靠
- 跨设备 client_id（UUID v4，本地生成）→ 用于冲突来源标识

## 5. 性能优化要点

| 维度 | 优化 |
|------|------|
| **批量** | RPC 数组入参，事务内处理；50 项/批 |
| **去重** | Storage 用 content-hash 作 key，相同内容共享对象 |
| **压缩** | 大文本 gzip（Supabase Storage 自动支持 br） |
| **索引** | `(user_id, path)`, `(user_id, updated_at)`, `events(user_id, id)` |
| **分区** | 事件表按月分区（量大时），保留 90 天后归档 |
| **缓存** | 客户端 LRU 缓存 base_version（最近访问 100 文件） |
| **节流** | 防抖 + worker pool 并发 4 |
| **Realtime** | 用 Server-Sent filter 减少 fanout（仅自己 user_id） |

## 6. 落地路线（MVP → 完整）

### MVP（1-2 周）

## 7. 关键决策清单

1. **检测层**：FSEvents（实时）+ 30s 轮询（兜底）+ 启动全量 reconcile
2. **同步粒度**：文件级为主，大文件降级为 chunk/patch
3. **冲突策略**：乐观锁检测 + 3-way merge 自动 + 冲突标记文件人工兜底
4. **传输通道**：DB RPC（小） + Storage（大） + Realtime（下行 push）
5. **可靠性**：outbox 持久化 + 幂等 + since_event_id 增量恢复
6. **向量增量**：chunk 级 hash 复用，仅变更 chunk 重嵌

这个方案在保证数据一致性的前提下，把同步成本压缩到"变更量级"而非"全量级"，并通过版本历史 + 三方合并把人工干预降至最低。
