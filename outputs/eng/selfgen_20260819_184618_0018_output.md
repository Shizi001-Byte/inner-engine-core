# 任务类型: eng

## 任务池动态扩充机制设计

### 一、机制定位

本机制服务于「生态型 / 轻边际成本供给主体」的 AI 调度/运营引擎。

设计优先级遵循已有认知：

1. **省时间**：所有扩充动作不能阻塞主调度，必须设置超时与降级路径。
2. **保进化**：不能空转，必须形成「检测 → 生成 → 注入 → 验证 → 反馈」闭环。
3. **不追求省 Token**：允许一定生成成本，换取任务池长期多样性和进化能力。

核心思路：

> 任务池如果不加干预，会自发走向同质化，即重复率上升。  
> 重复率就是任务池的“熵增”代理指标。  
> 自动生成新任务模板并注入，就是给系统注入“负熵”，打破封闭循环。

---

### 二、总体闭环

```text
任务池/执行日志
      ↓
重复率检测器
      ↓ 超过阈值
模板生成器 ←—— 认知池（30分钟内强制参与）
      ↓
候选过滤（按模型差异化）
      ↓
注入器（写状态 + 刷新缓存 + 通知调度器）
      ↓
生效验证（canary 任务）
      ↓
反馈调参 / 认知沉淀 / 任务池淘汰
      ↑___________________________|
```

---

### 三、核心模块设计

#### 1. 重复率检测器

- 使用滑动窗口，例如最近 200 个已执行任务。
- 对任务文本做语义向量化，用 embedding 计算相似度。
- 将相似度高于阈值的任务聚成一个语义簇。
- 重复率公式：

```text
重复率 R = (N - C) / N
```

其中：

- N = 窗口内任务总数
- C = 语义簇数量，即有效任务类型数

当 `R > 重复率阈值` 时，触发扩充。

默认阈值可设为：

```text
重复率阈值：0.4
语义相似度阈值：0.85
滑动窗口：200
```

这些参数必须可配置，不能硬编码。

---

#### 2. 模板生成器

生成新任务模板时，不能只靠随机生成，必须基于高重复簇作为种子。

##### 种子选择

- 从重复率最高的语义簇中抽取典型任务作为种子。
- 这些种子代表当前“卡住”的同质化方向。
- 生成器要打破这个方向，而不是继续产出同类任务。

##### 生成方式

采用两种方式结合：

1. **LLM 生成**
   - Prompt 中包含：
     - 种子任务模板
     - 当前任务池高频主题
     - 最新认知池内容
     - 要求：改变场景、目标、约束、格式、难度中至少两个维度
   - 生成 3～5 个候选模板。

2. **规则变异降级**
   - 如果 LLM 调用超时，则走规则变异：
     - 实体替换：把“城市 A”换成“城市 B”
     - 目标反转：从“提升点击率”反转为“提升留存但降低点击率”
     - 格式迁移：从“写文案”迁移为“写短视频脚本”
     - 约束增减：增加字数、资源限制或时间限制
     - 难度递进：从单步任务变为多步任务

##### 超时控制

调用生成模型时必须设置超时：

```text
B模型(turbo)：300秒
A模型：600秒
```

超时后不能阻塞，直接降级到规则变异路径。

---

#### 3. 候选过滤

过滤条件必须按模型差异化，不能一刀切。

##### 通用过滤

- 语义去重：与现有任务池相似度超过阈值，则丢弃。
- 可执行性检查：字段完整、参数明确、调度器可识别。
- 安全过滤：不包含违规内容。

##### 模型差异化过滤

历史坑：B 模型 reasoning 占比 70%～82% 是正常特性，不能被判为废稿。

因此：

```text
B模型(turbo)：跳过 reasoning 占比检测，只看输出完整性、可执行性、语义新颖性。
A模型：可以保留 reasoning 占比检测，但阈值要重新校准，不能直接套用旧规则。
```

---

#### 4. 注入器

注入不是简单写库，必须同步三个点：

```text
状态写入：把新任务模板写入任务池存储。
执行读取：立刻更新调度器正在读取的任务池缓存，并广播变更事件。
生效验证：调度器能实际读取到新模板，并成功生成一个 canary 任务。
```

伪代码：

```python
def inject_and_verify(template):
    template_id = task_pool_store.insert(template)       # 状态写入
    task_pool_cache.refresh([template])                  # 执行读取
    scheduler.notify(TaskPoolChanged(template_id))       # 执行读取

    result = scheduler.run_canary(template_id)           # 生效验证
    if not result.ok:
        task_pool_store.deactivate(template_id)
        task_pool_cache.refresh([template_id])
        log_failure(result)
```

只有 canary 任务成功执行，新模板才算真正生效。

---

#### 5. 认知池联动

历史坑：认知池只进不出，变成静态档案库。

因此：

- 每处理 10 个任务，或每一轮调度结束，主动刷新认知缓存。
- 新认知必须在 30 分钟内参与一次任务模板生成。
- 生成模板前，检查认知池缓存新鲜度；如果超过 30 分钟未刷新，先刷新再生成。
- 认知池要有淘汰机制：长期未命中、未参与生成的认知降权或归档。

---

#### 6. 反馈与自进化

每次扩充后，记录指标：

```text
重复率是否下降
新模板 canary 通过率
新模板实际执行成功率
平均响应时间
认知命中率
```

如果连续 3 次扩充后重复率仍未下降，自动调整：

- 提高生成变异强度
- 扩大生成 batch_size
- 降低重复率触发阈值
- 强制刷新认知池

如果 canary 通过率过低，说明生成方向错误，则：

- 回滚新模板
- 降低变异强度
- 把失败原因沉淀回认知池

### 四、避坑对照表

| 历史坑 | 本机制应对 |
|---|---|
| 配置修改后未生效 | 所有参数统一配置中心；新增配置必须同步“状态写入、执行读取、生效验证”；修改后立即读回校验 |
| API 调用超时 | 生成调用按模型设置超时：B模型(turbo) 300秒，A模型 600秒；超时走规则变异降级 |
| 废稿检测误杀 B 模型 | B模型(turbo) 跳过 reasoning 占比检测；不同模型使用独立质量规则 |
| 认知池只进不出 | 每 10 任务或每轮结束刷新认知缓存；新认知 30 分钟内必须参与生成注入；旧认知降权/归档 |
| 自动调参全链路失效 | 调参后必须通过 debug/read 接口确认生效，并用一次 canary 触发验证行为变化 |

---

### 五、结论

这个机制形成的是真正的闭环：

```text
重复率升高 → 自动感知 → 生成新模板 → 过滤 → 注入 → 验证 → 反馈 → 重复率下降
```

同时满足：

- 不因扩充阻塞主流程
- 不因配置不同步导致假生效
- 不因模型差异误杀 B 模型
- 不让认知池变成死库
- 不让任务池无限膨胀

最终，任务池不再是一个静态队列，而是一个能自我更新的活系统。
