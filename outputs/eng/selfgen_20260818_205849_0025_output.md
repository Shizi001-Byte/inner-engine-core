# 任务类型: eng

推演结论：**把本地文件当作“实”，Supabase 当作“虚”**。同步单位不是整个文件，而是**内容块 chunk**。用“版本号 + 内容哈希”作为唯一真值，mtime 只用来触发扫描，不用来判冲突。

---

## 一、总体架构：阴阳双轨运行

```
本地文件系统（阳/实）
      │
      │ ① 文件变化检测（watcher + 轮询）
      │ ② 内容哈希 + chunk 分块
      ▼
同步引擎（太极/自衡）
      │
      │ ③ push：只把变更 chunk 写入 Supabase
      │ ④ pull：把远端变化写回本地
      ▼
Supabase 记忆脑（阴/虚）
   files / chunks / file_chunks / conflicts
```

**以实养虚**：本地修改 → 分块 → 向量化 → 写入 Supabase，记忆检索变强。  
**虚又返实**：Supabase 里 AI 生成/远端修改的记忆 → 拉回本地文件，成为新的“实”。

## 二、数据模型

```sql
-- 文件版本表
create table files (
  path text primary key,
  version bigint not null default 0,
  content_hash text not null,
  updated_at timestamptz not null default now()
);

-- 内容块表，content_hash 唯一，避免重复向量化
create table chunks (
  id uuid primary key default gen_random_uuid(),
  content_hash text unique not null,
  content text not null,
  embedding vector(1536),
  created_at timestamptz not null default now()
);

-- 文件与 chunk 的映射
create table file_chunks (
  file_path text references files(path) on delete cascade,
  chunk_id uuid references chunks(id),
  chunk_index int not null,
  content_hash text not null,
  primary key (file_path, chunk_index)
);

-- 同步日志
create table sync_log (
  id bigserial primary key,
  file_path text,
  operation text,        -- push / pull / conflict / merge
  chunk_hash text,
  status text,           -- ok / failed / skipped
  detail jsonb,
  created_at timestamptz default now()
);

-- 冲突表
create table conflicts (
  id uuid primary key default gen_random_uuid(),
  file_path text,
  local_hash text,
  remote_hash text,
  local_version bigint,
  remote_version bigint,
  resolution text,       -- pending / merged / manual
  created_at timestamptz default now()
);
```

## 三、检测本地文件变化

1. 用 `chokidar` / `inotify` 监听本地文件事件，同时保留**周期性全量扫描**作为兜底，防止事件丢失。
2. 对每个文件先算快速指纹 `(size, mtimeMs)`。
3. 如果快速指纹变了，再算完整哈希 `blake3`。
4. 和本地 manifest 比对：

```json
{
  "files": {
    "notes/foo.md": {
      "hash": "blake3...",
      "chunks": ["hash1", "hash2", "hash3"],
      "version": 7
    }
  }
}
```

5. 如果哈希没变，只更新 mtime；如果哈希变了，进入同步队列。
6. 对文件写入做 debounce，例如 `500ms`，避免编辑中途被同步。

## 四、只同步变更部分

### 1. 分块策略

推荐用**语义分块**：

- Markdown 按标题分块；
- 标题下过长则按段落分块；
- 避免用固定长度硬切，否则插入一段会导致后续 chunk 全部变化。

每个 chunk 计算 `content_hash = blake3(content)`。  
只要内容不变，哈希就不变；插入新段不会影响旧 chunk。

### 2. 增量同步算法

```text
old_chunks = manifest[path].chunks
new_chunks = split(file_content)

old_hashes = set(old_chunks)
new_hashes = [hash(c) for c in new_chunks]

to_insert = [c for c in new_chunks if hash(c) not in old_hashes]
to_remove = old_hashes - new_hashes
```

同步时：

- 只对 `to_insert` 做 embedding 并写入 `chunks`；
- 如果 `content_hash` 在 Supabase 已存在，直接复用，不重复向量化；
- 更新 `file_chunks` 映射；
- 删除只在 `file_chunks` 中移除映射，不物理删除 `chunks`，因为可能被其他文件共享。

### 3. 伪代码

```python
def push_file(path):
    content = read(path)
    new_chunks = chunk_markdown(content)
    new_hashes = [blake3(c) for c in new_chunks]

    existing = fetch_existing_hashes(new_hashes)
    missing = [c for c in new_chunks if hash(c) not in existing]

    embed_and_insert(missing)  # 只处理真正新增/变更的 chunk

    upsert_file_chunks(path, new_hashes)
    increment_file_version(path)

    manifest[path] = {
        "hash": blake3(content),
        "chunks": new_hashes,
        "version": get_remote_version(path)
    }
```

这样，一个 100 段的文件只改 1 段，就只同步 1 段，而不是整个文件。

## 五、处理冲突

### 1. 冲突判断

以 `files.version` 为权威，不信任 mtime：

| 本地 | 远端 | 动作 |
|---|---|---|
| 未变 | 未变 | 无操作 |
| 变了 | 未变 | push 本地 |
| 未变 | 变了 | pull 远端 |
| 变了 | 变了 | 进入冲突处理 |

### 2. 三向合并

保留上一版 chunk 列表作为 base：

```text
base = manifest[path].chunks
local = 当前本地 chunk 列表
remote = Supabase 当前 chunk 列表
```

用 diff3 比较：

- 如果本地和远端改的是**不同 chunk**，自动合并；
- 如果改的是**同一个 chunk**，进入 LLM 合并或人工冲突。

### 3. LLM 合并

合并提示词：

```text
合并以下同一记忆块的两种修改：
- base：原始内容
- local：本地修改
- remote：远端修改

要求：
1. 保留双方新增事实；
2. 删除矛盾/过期内容；
3. 输出纯 Markdown。
```

调用模型时，必须使用独立超时：

```python
timeout_map = {
    "B/turbo": 300,
    "A": 600
}
```

质量门禁也要按模型区分：

```python
def quality_ok(model, result):
    if model == "B/turbo":
        # 关键：B/turbo 的 reasoning 占比 70%-82% 是正常特性
        # 不要检查 reasoning_ratio，不要误判为废稿
        return (
            result.is_valid_markdown() and
            result.contains_both_sides() and
            len(result.content) > 0
        )

    if model == "A":
        return (
            result.is_valid_markdown() and
            result.contains_both_sides() and
            0.3 <= result.reasoning_ratio <= 0.9
        )
```

如果 LLM 合并失败，或超过对应模型 timeout，不无限重试，而是：

- 写入 `file.conflict.md`，用冲突标记保留双方内容；
- 写入 `conflicts` 表；
- 等待人工解决后，再同步回 Supabase。

## 六、防坑配置

```yaml
sync:
  debounce_ms: 500
  chunk_size: 1500

  # 模型超时必须按模型独立配置
  llm_timeout:
    "B/turbo": 300
    "A": 600

  # B/turbo 不检测 reasoning 占比
  quality:
    "B/turbo":
      skip: ["reasoning_ratio"]
      check: ["valid_markdown", "contains_both_sides"]
    "A":
      check: ["valid_markdown", "contains_both_sides", "reasoning_ratio"]

  # 按目录配置同步方向
  direction:
    "notes/**": push          # 本地为源
    "memories/ai/**": pull    # Supabase 为源
    "shared/**": bidirectional
```

### 避坑一：配置修改后必须立即验证生效

不能只改配置文件，必须保证所有读取点都读取同一个 Config 对象。

- watcher 要重新加载 ignore 规则；
- chunker 要重新加载 `chunk_size`；
- syncer 要重新加载 `direction`；
- 修改配置后执行：

```bash
sync --dry-run
sync --validate-config
```

确认行为变化后再进入正式同步。

### 避坑二：API 调用超时

- 普通 Supabase REST 请求：建议 `30s`，重试 3 次；
- 冲突合并用 `B/turbo`：`300s`；
- 冲突合并用 `A` 模型：`600s`；
- 超过 timeout 后，不能简单重试，要降级或标记人工处理。

### 避坑三：B/turbo 废稿误杀

B/turbo 的 reasoning 占比高是正常现象，不能作为废稿判断标准。  
在增量同步的 LLM 合并质量检测中，**B/turbo 跳过 reasoning 占比检测**，只看输出是否有效、是否包含双方关键信息。

## 七、自愈与验证

每次同步后必须验证：

- push 后：

```sql
select count(*) from file_chunks where file_path = '目标文件';
```

对比本地 chunk 数量，一致才算成功。

- pull 后：

```text
本地文件 hash == 远端 content_hash
```

一致才算成功。

- 每次配置变更后，运行 `sync --dry-run`，确认“该同步的同步、该忽略的忽略”。

## 八、九转玄功映射

| 转 | 能力 | 对应机制 |
|---|---|---|
| 一转 | 感知变化 | watcher + 轮询扫描 |
| 二转 | 版本刻印 | blake3 + version + manifest |
| 三转 | 分形炼化 | 语义分块 + content hash |
| 四转 | 阴阳推拉 | push/pull 双轨同步 |
| 五转 | 冲突渡劫 | diff3 + LLM 合并 |
| 六转 | 自愈回环 | 同步日志 + 重试 + 验证 |
| 七转 | 不漏不重 | 幂等 upsert + 共享 chunk |
| 八转 | 外魔不侵 | 模型独立 timeout 和质量门禁 |
| 九转 | 时空收敛 | 多端最终一致 |

最终效果：**本地每次修改，Supabase 记忆脑只吸收变化的部分；远端每次变化，本地也能安全收回；两边同时改，不丢内容，不无限重试，不误杀 B/turbo。**
