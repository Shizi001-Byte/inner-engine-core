# 任务类型: eng

# Supabase 记忆脑增量同步方案推演

## 0. 推演基线

基于已有锚定：缺失区间不是「认知池空了」，而是**溯源链断了**。  
所以增量同步的核心不是「全量对齐」，而是：

> **最小变更 + 溯源链连续 + 冲突可解释**

不能把本地文件直接整段覆盖到 Supabase，否则会继续制造「无法回溯的静态档案」。

---

## 1. 整体流程

```text
本地记忆文件
   ↓  watcher + 定期哈希扫描
检测变更
   ↓  按 chunk 做 diff
只同步变更部分
   ↓  模型处理 / 质量门禁 / 超时控制
写入 Supabase（事务）
   ↓  同步修改读取点
验证生效
```

同时支持反向：Supabase 远端变更通过 Realtime / 轮询拉回本地，形成双向同步。

---

## 2. 检测本地文件变化

### 2.1 实时监听 + 全量兜底

- 使用 `chokidar` / `inotify` / `watchdog` 监听本地文件事件。
- 监听事件包括：`add`、`change`、`delete`、`rename`。
- 事件需要做 **debounce**，避免编辑器原子写入触发多次重复同步。
- 同时每 10 分钟做一次全量哈希扫描，兜底处理 watcher 漏掉的变更，例如休眠唤醒、网络盘文件被外部改动。

### 2.2 维护文件清单

本地与 Supabase 都维护一份 `sync_manifest`：

```sql
sync_manifest(
  file_id text primary key,
  path text,
  content_hash text,
  chunk_count int,
  version bigint,
  last_write_id text,
  synced_at timestamptz
)
```

- `content_hash` 使用 `sha256(file_content)`。
- 只有内容哈希变化才进入同步管道。
- 仅 mtime / 文件权限变化不触发同步。

### 2.3 远端变更检测

- 订阅 Supabase Realtime：`postgres_changes` on `memory_chunks`。
- 收到事件后检查 `writer_id`：
  - 如果是本地自己写入的，直接忽略，避免回环。
  - 如果是其他端写入的，拉取变更并合并到本地文件。

伪代码：

```ts
on('change', filePath => {
  const h = sha256(filePath)
  if (h !== manifest[filePath].content_hash) {
    enqueue(filePath)
  }
})

every(10min, () => {
  for (const filePath of scanAllFiles()) {
    const h = sha256(filePath)
    if (h !== manifest[filePath].content_hash) {
      enqueue(filePath)
    }
  }
})
```

## 3. 只同步变更部分

### 3.1 按 chunk 切分，而不是整文件同步

本地文件不能按「整个文件」作为同步单位，必须按**语义 chunk** 切分。

推荐：

- 每个记忆条目使用 frontmatter 中的稳定 `id`。
- 按标题 / 段落 / 列表块切分。
- 每个 chunk 有稳定 `chunk_id`。

例如：

```md
---
id: memory-20240818-001
---

这里是记忆正文。
```

### 3.2 对比 chunk 哈希

同步时，对每个文件：

```text
旧 manifest chunk 哈希集合：
  C1: hash1
  C2: hash2

新文件 chunk 集合：
  C1: hash1'  → MODIFY
  C2: hash2   → NOOP
  C3: hash3   → ADD
```

变更类型：

- `ADD`
- `MODIFY`
- `DELETE`
- `MOVE`：内容哈希相同，但文件路径 / 顺序变化，只更新元数据。

### 3.3 只处理变更 chunk

- 只有 `ADD` / `MODIFY` 的 chunk 需要重新 embedding。
- `NOOP` 不调用模型。
- `DELETE` 不直接物理删除，先 tombstone，再进入冲突判断。
- `MOVE` 只更新 `file_id` / `chunk_order`，不重新生成 embedding。

### 3.4 写入 Supabase 必须是事务

```sql
BEGIN;

UPDATE memory_chunks SET content = $1, embedding = $2, version = version + 1
WHERE chunk_id = $3 AND version = $4;

UPDATE sync_manifest SET content_hash = $5, chunk_count = $6, version = version + 1
WHERE file_id = $7;

COMMIT;
```

这样写入和 manifest 更新是原子的，避免「Supabase 有数据但 manifest 没更新」的脏状态。

## 4. 冲突处理

### 4.1 冲突来源

同一 chunk 在本地和远端同时被修改，或者本地删除但远端修改。

### 4.2 乐观锁

每个 chunk 带 `version` 字段。

写入时：

```sql
UPDATE memory_chunks
SET content = $1, version = version + 1
WHERE chunk_id = $2 AND version = $3;
```

如果影响行数为 0，说明远端 version 已经变化，进入冲突处理。

### 4.3 冲突分类处理

| 场景 | 处理方式 |
|---|---|
| 只有本地变更 | 直接写入 |
| 只有远端变更 | 拉取并更新本地 |
| 两边变更但内容一致 | 视为 no-op |
| 两边都修改 | 三路合并 |
| 本地删除，远端修改 | 不静默删除，进入冲突队列 |
| 远端删除，本地修改 | 保留本地，标记冲突 |

### 4.4 三路合并

- `base`：上次同步时的 chunk 内容。
- `local`：当前本地内容。
- `remote`：当前 Supabase 内容。

优先使用 `diff3` 做文本级三路合并：

- 合并成功 → 生成 `merged` 版本，写入 `memory_chunks`，version + 1。
- 合并失败 → 不自动覆盖，写入 `conflict_log`。

### 4.5 冲突队列

```sql
conflict_log(
  chunk_id text,
  base_content text,
  local_content text,
  remote_content text,
  status text,        -- pending / resolved / manual
  resolution text,
  created_at timestamptz
)
```

可选：用 LLM 辅助合并。但必须遵守：

- 使用 B 模型（turbo）：超时 300 秒。
- 使用 A 模型：超时 600 秒。
- B 模型跳过 reasoning 占比检测，不能把 70-82% 的 reasoning 当成废稿。
- A 模型走完整质量检测。

### 4.6 溯源链断裂区间的冲突

如果冲突发生在 `traceability_status = 'broken'` 的 chunk 上，不能自动合并。

必须走：

> **双锚点-三源交叉-分段重建**

1. 找到断裂区间前后的已知锚点。
2. 使用三个来源交叉验证：本地文件、Supabase、Git 历史 / 备份。
3. 分段重建，每段都验证锚点连续性。
4. 绝不一次性补全整个断裂区间，避免单次调用超时。

## 5. 配置修改必须同步修改读取点

历史坑：配置修改后未生效。

所以：

- 所有同步配置必须有版本号，例如 `sync_config_version`。
- 如果修改了 chunk 切分方式、embedding 模型、同步规则，必须同步修改 Supabase 中的读取点：

```text
memory_chunks 写入格式变了
       ↓
search_memory / get_memory_chunk / 相关视图 必须同步更新
       ↓
否则写入新格式，读取点还在读旧格式，表现就是“配置修改后未生效”
```

### 验证方法

每次配置变更后，执行 canary 验证：

```sql
-- 读取点验证
SELECT * FROM search_memory('某个已知记忆片段')
WHERE chunk_id = 'expected-chunk-id';
```

如果读不到预期结果，则回滚配置，不能继续同步。

## 6. 质量门禁与模型独立规则

### 6.1 超时控制

- B 模型（turbo）：300 秒。
- A 模型：600 秒。
- 超时后指数退避重试，最多 2 次。
- 仍然失败则标记该 chunk 失败，不阻塞整个同步批次。

### 6.2 废稿检测

不同模型必须有独立的质量检测规则：

- A 模型：按原有规则检测。
- B 模型（turbo）：**跳过 reasoning 占比检测**。
- B 模型 reasoning 占比 70-82% 是正常特性，不能判定为废稿，也不能自动重试。

### 6.3 溯源链写入

每个 chunk 写入时维护：

```text
source_anchor_before
source_anchor_after
traceability_status
```

读取点在查询时默认过滤：

```sql
WHERE traceability_status = 'ok'
```

防止断链认知被注入下游任务。

---

## 7. 推演结论

增量同步方案可行，但必须满足：

1. 以 chunk 为最小同步单位，不能整文件覆盖。
2. 检测层使用 watcher + 哈希扫描双保险。
3. 写入层使用事务 + 乐观锁。
4. 冲突层使用三路合并 + 冲突队列，不用简单 LWW。
5. 溯源链断裂区间必须走双锚点-三源交叉-分段重建。
6. 配置修改必须同步修改读取点，并立即验证。
7. 模型调用按 B turbo 300 秒 / A 600 秒设置超时。
8. B 模型跳过 reasoning 占比废稿检测。

这样才能避免「配置不生效、超时、废稿误杀、断链注入下游」这些历史坑。
