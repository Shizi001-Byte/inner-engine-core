# 任务类型: eng

以下为设计引擎产出的**自动归档系统方案**。直接基于已锚定的五条核心结论推演，不再重复论证。

## 1. 系统目标

自动完成：

- 任务自动分类
- 自动打标签
- 存入对应目录
- 并形成**可校验、可纠偏、可低熵维护**的闭环

## 2. 总体架构

```
任务入口
   │
   ▼
输入归一化
   │
   ▼
分类引擎 ──► 打标签引擎 ──► 归档执行器 ──► 校验器
   ▲                              │
   │                              ▼
   └────────── 反馈 / 纠偏 ◄─── 索引/审计
```

控制流：任务状态推进  
数据流：任务内容与元数据流转  
两者通过事件总线解耦，可独立扩展。

## 3. 核心模块设计

### 3.1 任务接入层

- 接收任务原始数据
- 统一为 `Task` 对象
- 写入待归档队列
- 所有外部 API 调用**必须配置 timeout**

配置示例：

```yaml
timeout_budget:
  B_turbo: 300   # B模型turbo，适合快速分类
  A: 600         # A模型，适合复杂任务分析
```

如果超时，不能无限等待，直接走兜底策略：

- 分类失败 → 标记为 `needs_review`
- 打标签失败 → 返回空标签 + 失败原因
- 归档失败 → 进入重试队列，最多 3 次

### 3.2 自动分类引擎

分类逻辑：

1. 先走规则分类器，快速识别已知任务类型
2. 规则置信度低时，调用模型分类
3. 模型选择按任务类型和复杂度路由

```yaml
classification_route:
  simple_task:
    model: B_turbo
    timeout: 300
  complex_task:
    model: A
    timeout: 600
```

输出：

```json
{
  "task_id": "task_123",
  "category": "finance",
  "confidence": 0.96,
  "model_used": "B_turbo",
  "needs_review": false
}
```

### 3.3 自动打标签引擎

标签来源：

- 规则标签：根据任务字段自动生成
- 模型标签：由分类模型抽取关键词
- 系统标签：`needs_review`、`timeout`、`high_priority`

标签约束：

- 统一小写
- 不允许包含 `/`
- 必须来自标签字典
- 新标签需要注册后才能进入正式标签库

输出：

```json
{
  "task_id": "task_123",
  "tags": ["invoice", "urgent", "vendor"],
  "tag_version": "2025-06-01"
}
```

### 3.4 归档执行器

目录结构：

```
/archive/{category}/{yyyy}/{mm}/{task_id}/
├── content.json
├── metadata.json
└── tags.json
```

标签索引目录：

```
/archive/_tags/{tag}/{task_id} -> ../../{category}/{yyyy}/{mm}/{task_id}
```

归档要求：

- 写入使用临时目录 + `rename`，保证原子性
- 同一 `task_id` 重复写入时，幂等处理
- 写入完成后必须校验文件存在、元数据完整

## 4. 配置中心：避免“配置修改后未生效”

所有配置统一存放在配置中心，模块不读本地散落配置。

### 4.1 配置注册表

每条配置必须登记：

- 配置 key
- 读取点代码位置
- 消费模块
- 校验规则

```yaml
config_registry:
  - key: archive.root_path
    read_point: "src/archiver/path_builder.py#L42"
    consumers: [archiver]
    validation: absolute_path

  - key: classification.model_route
    read_point: "src/classifier/router.py#L18"
    consumers: [classifier]
    validation: enum[simple_task, complex_task]
```

新增配置时，**必须同步修改读取点**，否则视为无效配置。

### 4.2 配置生效验证

配置变更后，立即执行“配置冒烟测试”：

1. 构造一条已知测试任务
2. 走完整归档链路
3. 断言分类结果、标签、目标目录符合预期
4. 不符合则自动回滚配置

例如修改了分类目录映射后，冒烟测试必须验证：

- 新任务进入新目录
- 旧任务不受影响
- 配置版本号正确写入 metadata

## 5. 闭环不是“建好就自转”，而是持续对抗熵增

系统内置三类熵减任务：

### 5.1 每日一致性巡检

- 对比实际目录与索引
- 缺失文件 → 重新归档
- 多余文件 → 隔离区
- 标签索引失效 → 重建 symlink

### 5.2 分类质量抽样

- 每天抽样已归档任务
- 人工/规则复核分类结果
- 准确率低于阈值 → 触发模型重训或配置调整
- 反馈结果重新进入归档闭环

### 5.3 低熵运维操作

- 清理临时文件、过期锁、失效 symlink
- 压缩冗余标签
- 清理不再使用的分类目录
- 定期检查 timeout 预算是否仍合理

## 6. 严格解耦：进化稳定策略

模块间不共享数据库，只通过事件通信。

```
TaskCreated -> TaskClassified -> TaskTagged -> TaskArchived -> TaskVerified
```

每个事件有 schema 版本：

```json
{
  "event_type": "TaskArchived",
  "schema_version": 1,
  "payload": {
    "task_id": "task_123",
    "path": "/archive/finance/2025/06/task_123",
    "tags": ["invoice", "urgent"]
  }
}
```

这样各模块可以独立升级、替换、扩展，不会互相锁死。

## 7. 控制流与数据流的扩展

- 控制流：任务状态机可以水平扩展
- 数据流：按 `task_id` 或 `category` 分区
- 目录存储可扩展为对象存储，但归档语义不变

系统整体是：

> **控制流推进任务状态，数据流承载任务内容与元数据，两者通过事件解耦，形成可持续扩展的归档闭环。**

## 8. 总结

这个自动归档系统不是一次性交付物，而是一个需要持续运维的低熵系统。

关键点：

- 配置修改必须带读取点同步和立即验证
- 所有模型调用必须带 timeout 兜底
- 归档后必须校验
- 分类错误必须反馈
- 目录/标签/索引必须每日巡检
- 模块之间严格解耦

最终效果：

> 任务自动分类、自动打标签、自动存入对应目录，并在持续对抗熵增中保持稳定。
