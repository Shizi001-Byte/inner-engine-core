# 任务类型: eng

# 设计引擎三方同步自动化方案

## 0. 设计原则（锚定）

- 每次重大变更对应一个不可变事件，事件 ID 作为全局幂等键。
- 三方同步 = Gitee / Feishu / Supabase 三个目标通道，各自独立状态、独立熔断、独立降级链。
- 所有状态变更必须走 **分布式锁 + 原子状态更新 + 幂等保护**。
- 以 `task_id` 作为唯一幂等标识，重复触发/重试不产生重复数据。
- 自动同步是“快轨”，对账与冲突仲裁是“慢轨”，双轨并行，形成“阴阳自衡”的负反馈机制。
- AI 负责分布式执行、冲突预判、合并建议；人类负责最终价值仲裁。

---

## 1. 总体架构

```text
设计引擎
   │  发布重大变更
   ▼
Event Bus
   │  生成 task_id
   ▼
Sync Orchestrator（分布式锁 + 状态机）
   ├─ Gitee Worker    → Gitee 代码提交
   ├─ Feishu Worker   → 飞书文件上传
   └─ Supabase Worker → Supabase 存储同步
   │
   ▼
状态与审计存储：Supabase Postgres
  ├─ sync_tasks
  ├─ target_state
  ├─ artifact_manifest
  └─ sync_ledger
   │
   ▼
Reconcile Service（慢轨：对账/冲突检测）
   │
   ▼
Conflict Queue → 人工仲裁 → 生成新任务
```

Supabase 承担双重角色：

- 作为三方同步目标之一，存储产物文件。
- 作为同步编排的状态中心，保存任务状态、锁、幂等记录、审计日志。

## 2. 重大变更触发与 `task_id`

### 2.1 触发条件

满足任一条件即视为“重大变更”：

- 设计引擎产物版本号 `major` 或 `minor` 变化。
- 变更类型为 `feature` / `refactor` / `release` / `breaking`。
- 提交信息或事件消息包含 `[sync]` 标记。
- 人工通过控制台触发并填写变更原因。

### 2.2 事件载荷

```json
{
  "artifact_id": "design/order-service",
  "version": "2.1.0",
  "change_type": "major",
  "source_ref": "design-engine/job/12345",
  "files": [
    {
      "path": "docs/order-service.md",
      "content_hash": "sha256:...",
      "content": "..."
    }
  ],
  "metadata": {
    "author": "design-engine",
    "triggered_at": "2026-01-01T00:00:00Z"
  }
}
```

### 2.3 `task_id` 生成规则

```text
task_id = SHA256(tenant_id + artifact_id + version + change_type)
```

相同产物、相同版本、相同变更类型重复发布时，`task_id` 相同，天然幂等。

## 3. 幂等性设计

### 3.1 全局状态机

`sync_tasks` 表状态：

```text
pending → running → success
                  → partial
                  → failed
                  → conflict
```

领取任务必须使用原子更新：

```sql
UPDATE sync_tasks
SET status = 'running',
    worker_id = :worker_id,
    started_at = now()
WHERE task_id = :task_id
  AND status = 'pending'
RETURNING *;
```

如果 `UPDATE` 返回 0 行，说明任务已被处理或正在处理，直接跳过。

### 3.2 分布式锁

每个 `task_id` 加分布式锁：

```text
SET lock:sync:{task_id} = token NX PX 300000
```

锁过期后由状态机中的 `running` 超时机制接管，防止 Worker 宕机导致任务卡死。

### 3.3 各目标幂等

#### Gitee 幂等

- 每次 commit 的 message 尾部追加：

```text
Sync-Task: <task_id>
```

- 提交前检查目标分支是否已存在包含相同 `Sync-Task` 的 commit。
- 同时检查 `git ls-tree <branch> <path>` 的 blob SHA 是否与本次文件内容 hash 一致。
- 如果已存在且 hash 一致，直接跳过。
- 推送时使用分支锁，避免并发 push 冲突。

#### Feishu 幂等

- 使用飞书自建应用 API，不使用扫码绑定连接器。
- 上传前先按文件夹 + 文件名查找已有 `file_token`。
- 如果已有文件且内容 hash 相同，跳过。
- 如果已有文件但内容不同，通过 `file_token` 更新，而不是新建文件。
- 每次成功上传后，将 `file_token` 写入 `target_state.external_ref`。

#### Supabase 幂等

- 存储桶对象路径固定为：

```text
artifacts/{artifact_id}/{relative_path}
```

- 上传前读取对象 metadata 中的 `content_hash`。
- 如果 hash 相同，跳过。
- 如果 hash 不同，使用 `upsert=true` 覆盖，并更新 metadata。
- 同时在 `sync_artifacts` 表执行：

```sql
INSERT INTO sync_artifacts (task_id, path, content_hash, object_key, version)
VALUES (:task_id, :path, :hash, :key, :version)
ON CONFLICT (task_id) DO UPDATE
SET content_hash = EXCLUDED.content_hash,
    object_key = EXCLUDED.object_key,
    version = EXCLUDED.version,
    updated_at = now()
WHERE sync_artifacts.content_hash IS DISTINCT FROM EXCLUDED.content_hash;
```

## 4. 冲突处理方案

### 4.1 冲突类型

| 冲突场景 | 示例 |
|---|---|
| 版本冲突 | 三方中某一方已被人工修改，且版本比当前同步源新 |
| 内容冲突 | 相同版本号但内容 hash 不同 |
| 并发冲突 | 两个任务同时修改同一个文件 |
| 状态不一致 | Gitee 成功、Feishu 失败，或目标端被外部改动 |

### 4.2 版本向量规则

为每个 artifact 维护：

```text
source_version = 设计引擎产物版本
target_version = 目标端当前版本
base_version  = 上次成功同步时的版本
```

决策规则：

| 条件 | 动作 |
|---|---|
| `source_version > target_version` | 自动覆盖 |
| `source_version == target_version` 且 hash 相同 | 跳过 |
| `source_version == target_version` 且 hash 不同 | 冲突，升级人工 |
| `source_version < target_version` | 目标端更新，不覆盖，升级人工 |
| `force_sync=true` 且人工审批通过 | 强制覆盖 |

### 4.3 三方自动合并

对于文本类文件（`.md`、`.json`、`.yaml`、代码等）：

- 以上次同步内容为 base。
- 使用 `diff3` / `git merge-file` 做三方合并。
- 合并无冲突：生成新的合并产物，以新的 `task_id` 重新同步三方。
- 合并有冲突：进入 `conflict_queue`，由人工仲裁。

对于二进制文件：

- 不自动合并。
- 按版本规则处理；若目标端更新，则必须人工决策。

### 4.4 双轨制：快轨 + 慢轨

- **快轨**：自动同步、自动重试、自动熔断，追求效率。
- **慢轨**：对账、冲突检测、审计、人工仲裁，追求可靠。

两轨并行，互不阻塞：

- 快轨产生 `sync_ledger` 日志。
- 慢轨消费日志并检测漂移。
- 当慢轨发现冲突时，暂停快轨对该 artifact 的自动覆盖，直到人工裁决。

这就是“阴阳自衡”：不消除速度与质量的矛盾，而是将其制度化为双轨运行。

## 5. 独立熔断、降级链与超时

### 5.1 每目标独立熔断

Gitee、Feishu、Supabase 各自维护：

```text
failure_count
circuit_state: closed / open / half_open
```

- 连续失败达到阈值（例如 5 次），熔断打开。
- 熔断期间不再调用该目标，其他目标不受影响。
- 熔断打开后定时半开探测，成功后关闭。

### 5.2 降级链

| 目标 | 降级链 |
|---|---|
| Gitee | API → git CLI → 本地暂存 + 定时重试 |
| Feishu | OpenAPI → 飞书机器人通知 → 人工上传队列 |
| Supabase | DB upsert → 消息队列 → 死信队列 + 告警 |

### 5.3 超时预设

外部 API 调用必须设置合理超时，避免任务卡死：

| 调用类型 | 连接超时 | 读超时 | 写超时 |
|---|---|---|---|
| Gitee | 10s | 30s | 60s |
| Feishu | 10s | 60s | 300s |
| Supabase | 10s | 30s | 600s |

AI 摘要/说明生成任务：

- B 模型 / turbo：`300s` 超时。
- A 模型：`600s` 超时。
- 超时后不阻塞主链路，降级为模板摘要继续同步。

每个 AI 模型独立计数、独立熔断、独立降级链，避免一个模型故障拖垮整条同步链路。

## 6. 配置生效与验证

### 6.1 配置集中化

所有同步配置统一存放在 `sync_config` 表中，例如：

- Gitee 仓库、分支、Token。
- Feishu 自建应用凭证、文件夹 token。
- Supabase 项目地址、Bucket、Service Key。
- 超时、重试、熔断阈值。

Worker 每次任务执行前重新读取配置，不允许长期缓存静态配置。

### 6.2 修改后立即验证

新增或修改配置后，必须执行：

```bash
sync_ctl verify --target all
```

验证内容：

- 配置能否被正确读取。
- Gitee Token 是否有权限。
- Feishu `tenant_access_token` 是否有效。
- Supabase Bucket 是否可读写。
- 实际执行一次 `.health` 文件写入并删除。

如果验证失败，则配置变更不生效，避免“配置修改后未生效、行为无变化”的问题。

### 6.3 飞书连接器避坑

- 新方案一律使用飞书自建应用 OpenAPI，不使用扫码绑定连接器。
- 如果历史遗留必须使用扫码绑定：
  1. 确认客户端是最新版本。
  2. 页面缩放到最大，查找“添加连接器”按钮。
  3. 绑定前确认豆包/飞书账号已登录。
  4. 绑定动作必须可重试，失败后自动重试并告警。

## 7. 对账与审计

### 7.1 定期对账

Reconcile Service 定期执行：

- 对比设计引擎最新产物 manifest。
- 对比 Gitee 文件 blob SHA。
- 对比 Feishu 文件 token 对应内容 hash。
- 对比 Supabase 对象 metadata。

发现漂移后：

- 若来源版本更新，重新触发同步。
- 若目标端被外部修改，进入冲突处理流程。

### 7.2 审计日志

所有操作写入 `sync_ledger`：

```text
task_id
target
action
request_hash
response_hash
status
created_at
```

日志只追加、不修改，作为审计和冲突追溯依据。

## 总结

这套方案以 `task_id` 为幂等根，以分布式锁和原子状态机为一致性底座，以独立熔断和超时保护为稳定性保障，以“快轨自动同步 + 慢轨对账仲裁”双轨机制处理冲突。既保留 AI 的分布式执行能力，又确保人类对最终价值和冲突裁决的主体性。
