# 任务类型: eng

基于【演化生物学映射】与【CAS复杂适应系统】框架，将Gitee（基因库/DNA）、Supabase（记忆脑/中枢神经系统）与飞书（表型/物理交互界面）视为一个完整的信息流演化生态。在此基础上，推演并设计三方同步自动化引擎。

在此系统中，**Gitee的每一次重大变更（Commit/Merge）相当于基因突变**，**Supabase负责记录突变特征并协调表达**，**飞书则是将高维代码沉淀翻译为人类可读的低维物理文档（表型表达）**。

以下是自动化引擎设计方案及幂等性、冲突处理推演：

---

### 一、 三方同步自动化引擎工作流

每次Gitee发生重大变更（如Tag推送、Master分支Merge）时，触发Webhook，引擎按以下链路执行：

1. **刺激接收与基因解码**
   - Gitee Webhook触发自动化任务。
   - 引擎提取`commit_hash`（基因序列号）和变更文件列表。
2. **记忆校验与中枢调度**
   - 引擎向Supabase查询该`commit_hash`是否存在。
   - **[避坑落实-配置同步]** 读取Supabase中的`sync_config`表获取目标飞书文件夹Token。每次读取后立即通过API拉取最新配置并比对，确保配置修改实时生效。
3. **表型翻译与物理投射**
   - 将代码库中的Markdown/文档提取，调用飞书API上传或更新文件。
   - **[避坑落实-超时预设]** 根据历史坑库预警，为API调用设置严格超时：飞书文件上传（视作B模型turbo任务）预设**300秒**timeout；若涉及大批量代码仓库Clone与编译（视作A模型任务）预设**600秒**timeout。
   - **[避坑落实-连接器认证]** 上传前校验飞书`tenant_access_token`有效性，模拟“客户端最新版本”逻辑，确保不会因Token过期导致绑定/上传失败。
4. **记忆固化**
   - 上传成功后，将`commit_hash`、飞书文件`document_id`、时间戳写入Supabase，完成神经记忆闭环。

---

### 二、 幂等性设计方案

在CAS框架下，幂等性意味着**相同的基因输入，无论中枢神经系统如何重复处理，最终只能产生唯一的表型输出**。

#### 1. 基于基因序列号的全局唯一锁
- **机制**：以Gitee的 `commit_hash` 作为唯一主键。在执行飞书上传前，先向Supabase的 `sync_tasks` 表执行 `INSERT ... ON CONFLICT (commit_hash) DO NOTHING`。
- **效果**：如果Webhook因网络抖动重试，相同`commit_hash`无法二次插入，直接返回“已处理”状态，从源头杜绝重复上传。

#### 2. 表型投射的幂等更新
- **机制**：飞书API调用采用“查找或创建”策略。Supabase中维护 `gitee_file_path` 与 `feishu_document_id`的映射表。
- **效果**：若任务重试，引擎查询Supabase发现已有对应的 `feishu_document_id`，则调用飞书的**更新**接口而非创建接口，确保不会在飞书云文档中生成重复文件。

---

### 三、 冲突处理方案

演化过程中必然存在基因竞争与表达冲突。引擎采用**“DNA绝对权威 + 中枢神经系统纠错”**策略处理冲突：

#### 1. 基因与表型不一致
- **现象**：飞书文档被人工手动篡改，与Gitee源码不一致。
- **处理（DNA主导原则）**：Gitee作为DNA底座，拥有最高权威。每次同步执行时，若发现飞书文档内容与Gitee最新提交不一致，直接以Gitee内容覆盖飞书文档（强制覆写）。若飞书文档被删除，则在Supabase中查到原`document_id`失效后，重新创建新文档并更新映射。
- **扩展**：若需保留人工修改，可在飞书文档首页注入只读警告：“本文件由Gitee自动同步，人工修改将在下次同步时被覆盖”。

#### 2. 并发演化冲突
- **现象**：短时间内多个Gitee Commit涌入，导致多个同步任务并发争抢飞书API，或Supabase状态混乱。
- **处理（中枢神经排队）**：
  - 利用Supabase的行级锁（`SELECT ... FOR UPDATE`）对同一文件路径的变更进行串行化处理。
  - 引入版本号机制，只有`commit_timestamp`晚于Supabase记录的最后同步时间的任务才会执行。早到的迟到任务将被丢弃（视为已被更高阶演化覆盖）。

#### 3. API调用超时与网络中断
- **现象**：飞书文件上传超时（>300s），或Supabase写入失败。
- **处理（断点续传与状态机）**：
  - 任务状态在Supabase中分为：`PENDING`（已入队）, `PROCESSING`（飞书上传中）, `SUCCESS`（完成）, `FAILED`（超时/报错）。
  - 若状态停留在`PROCESSING`超过600秒（A模型超时阈值），判定为僵尸任务。
  - 触发补偿机制：通过Gitee API反向校验该Commit是否存在，若存在则重置状态为`PENDING`等待下一轮定时巡检任务拉起，利用幂等性确保安全重试。

### 四、 工程映射总结表

| 已有锚定 (演化生物学/CAS) | 在本模块中的工程映射 (Gitee/飞书/Supabase) |
| :--- | :--- |
| **基因库** | Gitee代码仓库，`commit_hash`是DNA序列，Master分支是纯系血统。 |
| **记忆脑/中枢神经系统** | Supabase的`sync_tasks`与`sync_config`表，行级锁与唯一约束负责神经递质的精确传递。 |
| **表型/物理交互界面** | 飞书云文档，将代码变更翻译为团队可读的API文档/设计文档。 |
| **环境选择压力** | API超时限制（300s/600s）与人工篡改检测，不适应的表型（错误文档）将被淘汰并重写。 |
