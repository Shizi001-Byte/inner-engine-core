# 任务类型: eng

设计引擎产出的自动归档系统，核心目标是实现**“任务结束即归档，数据可检索，文件有条理”**。这需要一套结合了事件驱动、规则引擎、元数据管理和文件系统操作的综合机制。

以下是该自动归档系统的完整设计方案：

---

### 一、 系统核心工作流

整个归档过程可分为四个阶段：**事件触发 ➔ 元数据提取 ➔ 智能分类与打标 ➔ 物理存储与记录**。

1. **事件触发**：设计引擎完成任务（成功或失败）后，向消息队列（如 Kafka/RabbitMQ）发送一条带有 `Task ID` 的事件。
2. **元数据提取**：归档系统消费该事件，从数据库或任务上下文中提取关键信息（设计类型、发起人、输入参数、耗时、引擎版本等）。
3. **智能分类与打标**：根据预设规则或 AI 模型，计算该任务的归档目录和标签集合。
4. **物理存储与记录**：将产出文件移动/复制到目标存储路径，重命名，并在数据库中写入归档记录，供后续检索。

---

### 二、 详细模块设计

#### 1. 自动分类策略
分类决定了文件存入哪个物理目录。建议采用**多维度交叉分类**，以业务线或设计类型为主维度。

*   **基于规则的分类（主路径）**：
    *   **按设计类型**：`/Brand_Logos/`, `/UI_Mockups/`, `/Marketing_Posters/`
    *   **按项目/业务线**：`/ProjectA/Banners/`, `/ProjectB/Avatars/`
    *   **按时间维度**：`/2023/10/DesignType/`（适合海量且时间敏感的产出）
    *   **按状态分类**：`/Approved/`（已通过）, `/Draft/`（草稿）, `/Failed/`（引擎报错产出）
*   **基于内容的智能分类（辅助路径）**：
    *   如果任务上下文缺失，调用图像识别 API（如 CLIP 模型或云服务），分析产出图的特征（如：主色调、是否含人物、风格是扁平还是3D），自动归入对应风格目录。

#### 2. 自动打标机制
标签是检索文件的关键。标签分为系统标签和语义标签，通常存储在数据库中与文件路径关联，或写入文件的 XMP/EXIF 元数据中。

*   **系统标签（自动提取）**：
    *   基础信息：`Task_ID`, `Engine_Version` (如 SDXL-1.0), `Creator_ID`
    *   质量指标：`Resolution:4K`, `Has_Alpha:True`
    *   时间标签：`Q4_2023`, `October`
*   **语义标签（从输入提取或生成）**：
    *   **Prompt 提取**：从设计引擎的输入提示词中提取高频实体词。例如输入 "A cyberpunk cat wearing sunglasses"，提取标签：`Cyberpunk`, `Cat`, `Sunglasses`。
    *   **风格标签**：根据使用的模型或 Lora 自动打标，如 `Anime_Style`, `Photorealistic`。
    *   **反向打标**：如果产出无文本描述，可使用图像打标模型（如 WD14 Tagger）自动生成描述性标签。

#### 3. 目录结构与命名规范
为了避免单目录文件数量爆炸（影响文件系统性能），建议采用**日期+哈希分桶**的目录结构，并通过软链接或数据库提供逻辑分类视图。

**物理存储结构（推荐）**：
```text
/Archive_Root/
└── 2023/
    └── 10/
        └── 25/
            └── TaskID_ab12cd34/                  # 以任务ID为文件夹
                ├── origin_0.png                  # 原始产出
                ├── origin_1.png
                ├── thumbnail_webp/               # 缩略图
                └── meta.json                     # 归档元数据与标签快照
```

**文件命名规范**：
自动重命名文件，使其脱离数据库也具备一定可读性：
`[Date]_[DesignType]_[TaskID-short].png`
例如：`20231025_Logo_8f3a.png`

### 三、 技术实现架构

#### 核心组件：
1. **归档调度器**：监听引擎完成事件，执行归档编排逻辑。
2. **规则引擎**：使用 Drools 或简单的 Python 规则字典，根据上下文决定目标路径。
3. **打标服务**：
    *   文本提取：NLP 分词 + 实体识别（如 spaCy）。
    *   图像打标：CLIP / BLIP / WD14 等轻量级模型推理服务。
4. **存储适配器**：适配本地磁盘、NAS、对象存储（AWS S3, 阿里云 OSS）。
5. **元数据库**：PostgreSQL（存储结构化元数据和标签） + Elasticsearch（支持全文和标签检索）。

#### 伪代码示例（Python）：

```python
def handle_task_completed_event(task_id):
    # 1. 获取任务上下文
    task_data = db.get_task(task_id)
    assets = storage.get_temp_assets(task_data['output_paths'])
    
    # 2. 智能分类 (计算目录)
    design_type = task_data.get('type', 'Unknown')
    date_str = datetime.now().strftime("%Y/%m/%d")
    target_dir = f"/archive/{date_str}/{design_type}/{task_id}/"
    
    # 3. 自动打标
    tags = set()
    tags.update(extract_tags_from_prompt(task_data['prompt'])) # 语义提取
    tags.update(extract_system_tags(task_data, assets))        # 系统提取
    ai_tags = image_tagging_service.get_tags(assets[0].path)   # 图像识别
    tags.update(ai_tags)
    
    # 4. 物理归档与重命名
    archived_assets = []
    for index, asset in enumerate(assets):
        new_filename = f"{datetime.now().strftime('%Y%m%d')}_{design_type}_{task_id[:8]}_{index}.png"
        new_path = os.path.join(target_dir, new_filename)
        storage.move_file(asset.path, new_path)
        archived_assets.append(new_path)
        
        # 写入 XMP 元数据 (可选，提升跨平台可用性)
        write_metadata_to_file(new_path, tags)
        
    # 5. 数据库记录
    db.insert_archive_record({
        "task_id": task_id,
        "paths": archived_assets,
        "tags": list(tags),
        "category": design_type,
        "status": "ARCHIVED"
    })
    
    # 6. 推送到搜索引擎
    es_index.index({
        "task_id": task_id,
        "tags": list(tags),
        "path": archived_assets[0],
        "prompt": task_data['prompt']
    })
```

### 四、 高级特性与优化建议

1. **生命周期管理**：
   *   **冷热分层**：近 30 天的产出存在高频 SSD 缓存中，方便快速预览；超 30 天自动迁移到低成本对象存储（如 S3 Glacier），数据库中只保留路径指针。
2. **去重与相似度归档**：
   *   计算每个产出文件的感知哈希。如果新归档文件与已有文件哈希一致，不重复占用物理空间，仅在数据库中新增一条记录指向旧文件。
3. **版本控制**：
   *   如果一个任务经历多次重跑，通过 `Parent_Task_ID` 关联，在目录下保留历史版本，并打上 `Deprecated` 标签。
4. **权限与安全隔离**：
   *   在元数据中记录 `Project_ID`，在检索和访问资产时，通过项目 ID 进行 RBAC（基于角色的访问控制）校验，防止敏感设计稿泄露。

### 五、 总结
这套系统的精髓在于**“物理存储扁平化（日期+任务ID分桶），逻辑检索多维化（标签+分类数据库）”**。不要试图把所有的分类逻辑都映射成实际的文件夹层级，这不仅会导致目录极深，还会在分类规则变更时面临海量文件迁移的灾难。依靠强大的元数据库和标签体系，才能让设计引擎的归档系统兼具灵活性与高性能。
