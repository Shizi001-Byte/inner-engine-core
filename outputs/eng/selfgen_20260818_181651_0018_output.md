# 任务类型: eng

# Supabase 记忆脑增量同步方案（block 级）

## 0. 从锚点推出的三条门禁

1. **同步、差异分析、回滚判定，一律以 `block_id` 有序列表为最小核对单位。**  
   `file` 只是索引，不是传输单位。

2. **`mtime` / `size` / 文件整体 hash 只能做“是否要重新解析”的 dirty 标志，不能做同步判定。**  
   所以必须保留“同文件名、同大小、同 mtime，但 block 顺序不同”的样本，跑 SOP 时必须判为不同步。

3. **所有远端读取点必须实时读 Supabase，不能读本地缓存的远端状态。**  
   新增配置后必须立即验证生效，否则会出现“配置改了但行为没变”。

---

## 1. 数据模型

### Supabase 侧

```sql
-- 记忆块：内容寻址，不可变
create table blocks (
  id text primary key,          -- sha256(block_type || content)
  content text not null,
  embedding vector(1536),       -- 可选，如果做向量记忆
  created_at timestamptz not null default now()
);

-- 文件索引：文件 = 有序 block id 列表
create table files (
  path text primary key,
  block_ids text[] not null,
  version bigint not null default 0,
  updated_at timestamptz not null default now()
);

-- 冲突归档：避免静默丢数据
create table sync_conflicts (
  id uuid primary key default gen_random_uuid(),
  path text not null,
  conflict_type text not null,
  archived_block_ids text[] not null,
  created_at timestamptz not null default now()
);
```

### 本地侧

本地需要记录“上次索引到的 block 列表”和“上次同步成功的远端 base 状态”：

```sql
create table local_sync_meta (
  path text primary key,
  mtime timestamptz,
  size bigint,
  last_indexed_block_ids text[] not null,
  base_block_ids text[] not null,
  base_version bigint not null
);
```

## 2. 检测本地文件变化

流程：

1. 文件 watcher 触发，或定时 deep scan 触发。
2. 读取 `mtime` / `size`。
   - 如果没变化，可以先跳过。
   - 但不能只靠这个下结论；需要定期 deep scan 强制重新解析，防止“同 mtime、同 size、block 顺序被改”漏检。
3. 解析文件为 blocks：
   - Markdown：按标题 / 段落 / 代码块切分。
   - 长文：用 content-defined chunking（CDC），避免中间插入内容导致后续所有 block 都变化。
4. 计算每个 block：
   ```text
   block_id = sha256(block_type + content)
   ```
5. 得到本地有序 `local_block_ids`。
6. 与 `last_indexed_block_ids` 比较：
   - 相同：不处理。
   - 不同：进入增量同步流程。

---

## 3. 只同步变更部分

### 3.1 差异计算

用 block id 序列做 diff，而不是文件内容 diff：

```text
diff(remote.block_ids, local.block_ids)
=> insert / delete / move / replace(old_id, new_id)
```

注意：`block_ids` 是有序数组，允许重复，不能用集合比较。

### 3.2 只上传新 block

```text
new_blocks = 本地 blocks 中，remote 不存在的 block
```

如果远端已经有相同 `block_id`，说明内容相同，只需要更新文件索引引用，不需要重新上传内容。

### 3.3 原子更新

通过一个 Postgres Function 完成：

```sql
create or replace function sync_file(
  p_path text,
  p_block_ids text[],
  p_new_blocks jsonb,
  p_base_version bigint
) returns jsonb
language plpgsql
as $$
declare
  v_version bigint;
  v_current_block_ids text[];
  v_new_version bigint;
begin
  -- 实时读远端，并锁行
  select version, block_ids
    into v_version, v_current_block_ids
  from files
  where path = p_path
  for update;

  if not found then
    v_version := 0;
    v_current_block_ids := '{}';
  end if;

  -- 乐观锁：版本不对说明有并发冲突
  if v_version <> p_base_version then
    return jsonb_build_object(
      'status', 'conflict',
      'current_version', v_version,
      'current_block_ids', v_current_block_ids
    );
  end if;

  -- 插入新 block；内容寻址，幂等
  insert into blocks(id, content)
  select id, content
  from jsonb_to_recordset(p_new_blocks) as x(id text, content text)
  on conflict (id) do update set content = excluded.content;

  -- 更新文件索引
  if v_version = 0 then
    insert into files(path, block_ids, version)
    values (p_path, p_block_ids, 1)
    returning version into v_new_version;
  else
    update files
    set block_ids = p_block_ids,
        version = version + 1,
        updated_at = now()
    where path = p_path
    returning version into v_new_version;
  end if;

  -- 清理无引用 block，但保留冲突归档里的 block
  delete from blocks b
  where not exists (
    select 1 from files f where b.id = any(f.block_ids)
  )
  and not exists (
    select 1 from sync_conflicts c where b.id = any(c.archived_block_ids)
  );

  return jsonb_build_object('status', 'ok', 'new_version', v_new_version);
end;
$$;
```

这样：

- 修改一个 block 内容时，只上传这个新 block；
- 其他 block 不动；
- 文件索引更新为新的 `block_ids` 数组；
- 不会全量重传文件。

## 4. 冲突处理

### 4.1 冲突判定

本地保存了上次同步成功时的：

```text
base_block_ids
base_version
```

同步时读取远端：

```text
remote.block_ids
remote.version
```

如果：

```text
remote.version == base_version
```

说明远端没有变化，直接推送本地 diff。

如果：

```text
remote.version != base_version
```

说明本地和远端都改过，进入 3-way merge：

```text
Base   = base_block_ids
Local  = 本地当前 block_ids
Remote = 远端当前 block_ids
```

判断：

- `Local == Remote`：两端结果一致，更新 base 即可。
- `Local == Base`：只有远端改，拉取远端。
- `Remote == Base`：只有本地改，推送本地。
- 否则：两端都改了，做 3-way merge。

### 4.2 3-way merge 规则

用 block id 序列 diff：

```text
diff(Base, Local)
diff(Base, Remote)
```

- 两端操作互不重叠：合并后推送。
- 两端同时触碰同一个 block id：
  - 例如本地把 `B` 改成 `B_local`，远端把 `B` 改成 `B_remote`
  - 这是冲突。

默认策略：

- **LWW（Last-Write-Wins）**：比较本地 `mtime` 和远端 `updated_at`，谁新听谁的。
- 被覆盖的一方写入 `sync_conflicts` 归档，不静默丢弃。

可选策略：

- `local-wins`：本地永远优先。
- `remote-wins`：远端永远优先。
- `duplicate`：把两个冲突版本都保留，插入到原位置，并加冲突标记。

### 4.3 回滚

回滚也基于 block id 列表：

```text
把 files.block_ids 更新为目标版本的 block_ids
```

缺失的 block 从 `blocks` 表补齐；不缺失的不动。

## 5. 模型 / 超时 / 质量门禁

如果同步链路里涉及 LLM 生成 embedding 或记忆块：

- 普通 `sync_file` RPC 超时建议短一些：30s 内。
- 模型生成 / embedding 任务按模型类型预设超时：
  - B 模型（turbo）：300s
  - A 模型：600s
- B 模型（turbo）的 reasoning 占比在 70%–82% 是正常特性，不要判定为废稿，不要自动重试。
- A 模型需要独立质量检测规则，不要用同一套阈值。

## 6. 必须验收的样本

### 样本 1：同 file 名、同 size、同 mtime，但 block 顺序不同

```text
本地 block_ids = [A, B, C]
远端 block_ids = [A, C, B]
```

预期：

- 必须判定为“不同步”。
- 只更新 `files.block_ids` 顺序。
- 不上传任何 block 内容。

### 样本 2：修改一个 block 的内容 / ID

```text
原来 [A, B, C]
改成 [A, B', C]
```

预期：

- diff 只出现 `B -> B'`。
- 传输日志里只出现 `B'` 这个 block。
- 不能出现整个文件全量重传。

### 样本 3：并发冲突

本地和远端同时改了同一个文件，但改的是不同 block。

预期：

- 3-way merge 成功，两个 block 的修改都保留。
- 如果改同一个 block，则走 LWW 或 duplicate，且失败一方进入 `sync_conflicts`。

---

这套方案的本质就是：**文件不是同步单位，block id 列表才是。**  
所有检测、传输、冲突、回滚都围绕 block id 列表展开，才能在 Supabase 记忆脑上做到真正的增量同步。
