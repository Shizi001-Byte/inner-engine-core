# 任务类型: eng

在已锚定的九转流程上，直接推演锁机制。结论先行：

> **竞态根因不是“后处理不够快”，而是“锁作用域与 API 调用生命周期不匹配”。**  
> 所以不能只靠一个全局锁，也不能靠后处理队列本身。需要的是：  
> **per-block 租约锁 + CAS 状态迁移 + per-file index 短事务锁 + 代际 token 拒绝迟到响应。**

---

## 1. 锁模型总览

同步单位是 block，所以锁的默认粒度是 **block_vertex**；文件只是有序 block id 列表，所以 commit 时还需要锁 **index_vertex**；tombstone 作为特殊 vertex，复用 block 级锁。

```
block_vertex 增加：
  state             -- idle/detecting/detected/diffing/diffed/committing/synced
  lock_owner        -- 持有者标识
  lock_token        -- 随机 token，CAS 用
  lock_expires_at   -- 租约过期时间
  phase_gen         -- 代际，拒绝迟到响应
  op_id             -- 外部 API 幂等键

index_vertex 增加：
  sync_phase        -- detect/diff/commit（可选，批处理屏障用）
  phase_gen         -- 阶段代际
  pending_count     -- 当前阶段未完成数
```

**不建 sync_task 表**。锁状态直接挂在 vertex 上，和业务状态同库同事务。

---

## 2. 九转状态机与锁的关系

每个大节点正好三转：申请锁、成功提交、失败回退。三个节点共九转。

| 节点 | 申请锁（进入） | 成功 | 失败/超时 |
|---|---|---|---|
| Detect | `idle -> detecting` | `detected` | `idle` |
| Diff | `detected -> diffing` | `diffed` | `detected` |
| Commit | `diffed -> committing` | `synced` | `diffed` |

锁不是额外加的，而是**状态迁移本身必须是原子 CAS**。

---

## 3. 获取租约锁：API 调用前

API 调用可能长达 300s/600s，所以不能持有数据库行锁跨网络调用；但必须防止同一个 block 被并发调度。因此用「租约锁」。

```sql
UPDATE block_vertex
SET state = 'detecting',
    lock_owner = :worker_id,
    lock_token = gen_random_uuid(),
    lock_expires_at = now() + make_interval(secs => :lease_secs),
    phase_gen = :phase_gen,
    op_id = gen_random_uuid()
WHERE block_id = :block_id
  AND state = 'idle'
  AND (lock_owner IS NULL OR lock_expires_at < now())
RETURNING lock_token;
```

- 返回 0 行：该 block 已被别的线程持有，不能调用 API。
- `lease_secs` 必须大于 API timeout：
  - B 模型 turbo：API timeout 300s，lease 建议 330s
  - A 模型：API timeout 600s，lease 建议 660s
- `op_id` 作为外部 API 幂等键；重试时若还在同一节点，复用同一个 `op_id`。

---

## 4. 完成回调：后处理 CAS

API 返回后，进入串行后处理。后处理可以串行，但**不能用“先查再改”**，必须用带 token 的 CAS。

```sql
UPDATE block_vertex
SET state = 'detected',
    lock_owner = NULL,
    lock_token = NULL,
    lock_expires_at = NULL,
    version = version + 1
WHERE block_id = :block_id
  AND lock_token = :token
  AND phase_gen = :phase_gen
RETURNING version;
```

如果返回 0 行，说明是：

- 重复回调；
- 迟到响应；
- 锁已被 reaper 回收；
- 该 block 已经进入下一阶段。

此时直接丢弃，不能覆盖新状态。

### 失败/超时回退

```sql
UPDATE block_vertex
SET state = 'idle',
    lock_owner = NULL,
    lock_token = NULL,
    lock_expires_at = NULL
WHERE block_id = :block_id
  AND lock_token = :token;
```

如果 `content` 为空（Responses API 的坑），也按失败回退，不能进入 `detected/diffed`。

---

## 5. Commit 阶段：index 锁

commit 不只是改 block 状态，还会改 `index_vertex.ordered_block_ids`。所以这里需要短事务行锁。

```sql
BEGIN;

-- 1. 锁住 file index
SELECT * FROM index_vertex
WHERE file_id = :file_id
FOR UPDATE;

-- 2. 校验版本，防止基于旧 index 提交
UPDATE index_vertex
SET ordered_block_ids = :new_ordered_block_ids,
    version = version + 1
WHERE file_id = :file_id
  AND version = :expected_version;

-- 3. 同一事务里释放 block 锁，推进状态
UPDATE block_vertex
SET state = 'synced',
    lock_owner = NULL,
    lock_token = NULL,
    lock_expires_at = NULL
WHERE block_id = :block_id
  AND lock_token = :token;

COMMIT;
```

如果第 2 步更新 0 行，说明 index 版本已变化，必须回滚，并把 block 回退到 `diffed`，重新 Diff/Commit。

这个机制同时解决 tombstone 和 update 的竞争：两者都要改同一个 index，后者会因为版本不匹配而失败。

---

## 6. 批处理屏障：Detect 全部完成再 Diff

如果你要求“Detect → Diff → Commit”是整批推进，而不是 block 独立推进，则需要在 `index_vertex` 上加一个轻量屏障。

```sql
-- 阶段开始
UPDATE index_vertex
SET sync_phase = 'detect',
    phase_gen = phase_gen + 1,
    pending_count = :block_count
WHERE file_id = :file_id;

-- 每个 completion 后处理完
UPDATE index_vertex
SET pending_count = pending_count - 1
WHERE file_id = :file_id
  AND phase_gen = :phase_gen
RETURNING pending_count;
```

当 `pending_count = 0`，才允许进入下一阶段：

```sql
UPDATE index_vertex
SET sync_phase = 'diff',
    phase_gen = phase_gen + 1
WHERE file_id = :file_id
  AND sync_phase = 'detect'
  AND phase_gen = :phase_gen;
```

迟到的旧阶段响应会带着旧 `phase_gen`，在 block CAS 和 index pending_count 更新时都会被拒绝。

---

## 7. 死锁避免与崩溃恢复

### 锁顺序

- 永远先锁 `index_vertex`，再锁 `block_vertex`；
- 永远不要反过来；
- 永远不要在持有 `index_vertex` 行锁时调用外部 API；
- 所有租约锁都有过期时间，不会无限等待。

### Reaper 回收过期锁

```sql
UPDATE block_vertex
SET state = CASE state
      WHEN 'detecting'  THEN 'idle'
      WHEN 'diffing'    THEN 'detected'
      WHEN 'committing' THEN 'diffed'
    END,
    lock_owner = NULL,
    lock_token = NULL,
    lock_expires_at = NULL
WHERE lock_expires_at < now()
  AND state IN ('detecting', 'diffing', 'committing')
RETURNING block_id, state;
```

如果是批处理模式，reaper 还要把对应 `pending_count` 减掉，避免屏障永远卡住。

---

## 8. 落地约定

- API 调用统一用 `urllib`，显式 `ProxyHandler({})`，避免全局代理导致 ProxyError；
- 不引入 `requests`；如果必须用，显式 `proxies=None`；
- API timeout 按模型预设：B turbo 300s，A 600s；
- lock lease 必须大于 API timeout，否则 API 没回来锁先过期；
- Responses API 先单测 `content` 非空再接主流程；
- 锁状态和业务状态放在 Supabase/Postgres 同库，不用 Redis 分布式锁。

这套机制下，多线程 API 调用可以并发，串行后处理只负责“按顺序应用 CAS”，不会出现重复调度、乱序覆盖、index 撕裂或 tombstone 被复活。
