# 任务类型: eng

推演结论：**增量同步不要做成“文件级 diff”，要做成“chunk 级事件同步”**。  
本地文件只是“记忆契约的实例”，`memory_chunks` 表才是同步的核心锚点。

---

## 0. 先校准锚点，再谈增量

增量同步的前提不是“能算出差异”，而是“差异能映射到稳定的列契约”。

启动时先做三件事：

1. **契约检查**：确认 `memory_files`、`memory_chunks`、`memory_versions`、`sync_events` 的列结构完全符合预期。
   - 特别是 `version`、`base_version`、`content_hash`、`last_writer`、`schema_version`。
   - 不允许在同步 SQL 里“顺手简化列”，否则必然出现列不匹配。
2. **锚点校准**：把本地 `.sync-state` 里的 `last_synced_version` 与 Supabase 中的 `memory_files.version` 对齐。
   - 如果对不齐，先做一次 `reconcile`，用哈希比对产出第一批增量事件。
   - 锚点不校准，后面的增量同步全是猜。
3. **配置生效检查**：新增配置必须同步修改读取点。
   - 例如新增 `ignore_patterns`，必须在配置加载处读取并传给 watcher。
   - 改完配置后，跑一次 `dry-run`，并故意改一个文件验证事件产生。

## 1. 核心表结构

```sql
create extension if not exists vector;

create table memory_files (
  path text primary key,
  content_hash text not null,
  version bigint not null default 0,
  updated_at timestamptz not null default now(),
  schema_version int not null default 1
);

create table memory_chunks (
  path text not null,
  chunk_id text not null,
  chunk_index int not null,
  content text not null,
  content_hash text not null,
  embedding vector(1536),
  version bigint not null,
  last_writer text not null default 'unknown',
  updated_at timestamptz not null default now(),
  primary key (path, chunk_id)
);

create table memory_versions (
  path text not null,
  version bigint not null,
  parent_version bigint,
  source text not null,
  chunks jsonb not null,
  created_at timestamptz not null default now(),
  primary key (path, version)
);

create table sync_events (
  id bigserial primary key,
  path text not null,
  event_type text not null,
  base_version bigint not null,
  target_version bigint,
  delta jsonb,
  status text not null default 'pending',
  owner text not null,
  created_at timestamptz not null default now()
);

create table memory_conflicts (
  id bigserial primary key,
  path text not null,
  chunk_id text not null,
  base_version bigint not null,
  base_content text,
  local_content text,
  remote_content text,
  status text not null default 'open',
  resolver_model text,
  created_at timestamptz not null default now()
);
```

关键点：  
`memory_chunks.chunk_id` 是稳定锚点，不是内容哈希。建议用 `path#标题路径` 或 `path#block-id`。  
这样内容修改时，chunk_id 不变，才能做增量更新和冲突合并。

## 2. 检测本地文件变化

### 2.1 实时监听 + 兜底扫描

- 用文件监听，如 Chokidar：
  - `add` / `change` / `unlink`
  - 500ms debounce，防止编辑器临时文件抖动。
- 同时保留定时全量扫描：
  - 每 5 分钟遍历一次本地文件。
  - 先比 `mtime + size`，变了再算 SHA-256。
  - 防止 watcher 漏事件，尤其是网络盘、IDE 原子保存。

### 2.2 变化后生成 delta

对每个变化文件：

1. 读取文件内容。
2. 按契约切分为 chunks。
3. 用 `chunk_id` 对比本地状态里的旧 chunks。
4. 生成增量事件：

```json
{
  "base_version": 3,
  "target_version": 4,
  "changed_chunks": [
    {
      "chunk_id": "memory/foo.md#section-a",
      "op": "upsert",
      "content": "新内容",
      "content_hash": "sha256..."
    }
  ],
  "deleted_chunks": [
    {
      "chunk_id": "memory/foo.md#old-section",
      "op": "delete"
    }
  ]
}
```

这个 delta 就是“执行层唯一允许使用的同步契约”。

---

## 3. 只同步变更部分

同步时不允许直接上传整个文件。

### 3.1 传输层

- 只 upsert 变化的 chunk。
- 只 delete 消失的 chunk。
- 更新 `memory_files.content_hash` 和 `version`。
- 所有操作放在一个 Postgres 事务里，避免半同步状态。

### 3.2 向量增量

如果记忆脑使用 embedding：

- 只对 `changed_chunks` 重新生成 embedding。
- 未变化 chunk 的 embedding 不动。
- 如果 embedding 模型切换了，不要偷偷混用；必须走一次 `schema_version` 升级，全量重算。

### 3.3 执行并发

- 不同文件的同步任务可以并行。
- 同一个文件必须串行，通过 `sync_events` 的 per-path 锁保证。
- 决策层串行决定“这个 delta 能不能应用”，执行层并发写入。

## 4. 冲突处理

冲突的本质不是“两边都改了”，而是 **base_version 对不上**。

### 4.1 检测冲突

每次 push 时用乐观锁：

```sql
update memory_files
set version = version + 1,
    content_hash = $new_hash
where path = $path
  and version = $base_version;
```

如果影响行数为 0，说明远端版本已经前进，进入冲突流程。

### 4.2 三方合并

使用 base / local / remote 三份内容：

- base：`memory_versions[path, base_version]`
- local：本地当前 chunks
- remote：Supabase 当前 `memory_chunks`

逐 chunk 判断：

- local = base，remote = base → 不变。
- local ≠ base，remote = base → 取 local。
- local = base，remote ≠ base → 取 remote。
- local ≠ base，remote ≠ base：
  - local == remote → 取任意一份。
  - 否则 → 冲突 chunk。

### 4.3 冲突不阻塞全部

- 非冲突 chunk 先合并，写入新版本。
- 冲突 chunk 写入 `memory_conflicts`。
- 文件状态标记为 `conflicted`，等 resolver 处理。

### 4.4 冲突解决

冲突解决可以人工，也可以用模型。

如果走模型：

- 把 base / local / remote 三份内容给模型。
- 要求模型输出合并后的 chunk 内容，必须保持原有事实，不要丢信息。
- 输出必须符合 JSON schema，且 `content_hash` 匹配。
- 合并结果写回本地文件和远端，然后关闭 conflict。

#### 模型选择与超时

- 简单冲突：B 模型 turbo，timeout 300 秒。
- 复杂冲突：A 模型，timeout 600 秒。
- 不同任务类型必须配置独立 timeout，不能统一默认值。

#### B 模型废稿检测避坑

- 如果 resolver 使用 B 模型，**禁止用 reasoning 占比作为废稿判据**。
- B 模型正常输出可能 70-82% 是 reasoning，这是它的正常特性。
- 质量检测规则按模型独立配置：
  - B 模型：校验 JSON schema + content_hash。
  - A 模型：校验 JSON schema + content_hash + 语义连贯性。
- 不要用同一套废稿检测逻辑套所有模型。

## 5. 同步链路总览

```text
本地文件变化
   ↓
watcher / 定时扫描
   ↓
解析 chunks，生成 delta
   ↓
写入 sync_events（决策层，串行）
   ↓
执行层并发 apply_delta
   ↓
更新 memory_files / memory_chunks / memory_versions
   ↓
生成/更新 embedding
   ↓
校验 content_hash
```

远端变化同理：

```text
Supabase Realtime 事件
   ↓
忽略自己写入的事件
   ↓
对比本地 last_synced_version
   ↓
无冲突 → 应用远端 delta 到本地文件
有冲突 → 进入三方合并
```

---

## 6. 最终避坑清单

- 不要写简化版同步 SQL；必须带上 `version`、`base_version`、`content_hash`。
- 先校准锚点，再优化链路。
- 配置修改后必须同步修改读取点，并立即验证。
- B 模型 turbo 不套 reasoning 废稿检测。
- B 模型 turbo 用 300 秒 timeout，A 模型用 600 秒。
- 只同步变更 chunk，不同步整个文件。
- 同一个文件串行决策，不同文件并行执行。

这样推演出来的增量同步方案，才是“有契约、有锚点、可冲突恢复”的方案，而不是“本地文件变了就整篇上传”的简化版。
