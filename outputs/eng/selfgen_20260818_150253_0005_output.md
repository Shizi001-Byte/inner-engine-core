# 任务类型: eng

基于已有认知锚定，推演归档系统设计如下，不重复论证。

## 一、系统定位

自动归档系统不是“事后整理工具”，而是感知层第 4 轮闭环的“负熵引擎”：

> 把引擎产出的瞬时数据（无），转化为可复用、可检索、可溯源的资产（有）。

归档系统由「脑」掌握控制权，用**阴阳双轨**打破单线执行的死局：

- **阳轨**：产出 → 捕获 → 分类 → 打标 → 归档 → 确认
- **阴轨**：扫描 → 校验 → 修复 → 学习 → 规则更新

阳轨保证产出不被归档阻塞；阴轨保证归档结果持续有序。

## 二、总体架构

```text
引擎产出
   │
   ▼
事件总线 / 文件监听 / API 回调
   │
   ▼
┌─────────────────────────────┐
│        脑（元控制器）         │
│  规则库 · 标签库 · 目录映射   │
│  配置版本 · 状态机 · 稳态校验  │
└─────────────────────────────┘
   │
   ▼
┌──────────── 阳轨 ────────────┐
│ 捕获 → 预分类 → 语义分类     │
│ → 标签归一化 → 目录计算      │
│ → 原子归档 → 索引更新        │
└─────────────────────────────┘
   │
   ▼
┌──────────── 阴轨 ────────────┐
│ 定时一致性扫描 → 差异修复     │
│ 低置信度复核 → 规则学习       │
└─────────────────────────────┘
```

## 三、自动分类机制

分类不是单一模型，而是“规则 + 模型 + 脑裁决”三层递进：

### 1. 规则预分类

从任务元数据中直接抽取候选标签：

- 来源模块
- 文件名模式
- 任务参数
- 输出格式
- 调用方标识

例如：

```text
engine_type=report_generator
output_format=pdf
domain_field=finance
```

→ 候选标签：

```text
task_type:report
domain:finance
format:pdf
```

### 2. 语义模型分类

对非结构化内容，调用分类模型补充语义标签。

模型调用必须配置超时：

| 模型 | 超时 |
|---|---|
| B 模型 turbo | 300 秒 |
| A 模型 | 600 秒 |

超时后不阻塞，降级为规则分类结果，并标记：

```text
confidence: low
need_review: true
```

### 3. 脑裁决

- 分类结果冲突时，由脑按优先级裁决。
- 新标签必须进入标签白名单，经脑批准后才能生效。
- 低置信度任务进入阴轨复核队列，不直接污染归档目录。

## 四、打标体系

标签统一使用命名空间，避免歧义：

```text
task_type:report
task_type:code
task_type:dataset
task_type:analysis

domain:finance
domain:medical
domain:legal
domain:education

security:public
security:internal
security:confidential

time_scope:realtime
time_scope:daily
time_scope:weekly
```

打标时做归一化：

- `财务报告` → `domain:finance`
- `财报` → `domain:finance`
- `report` → `task_type:report`

归一化规则由脑维护，版本化存储。

## 五、目录映射算法

归档目录由标签组合计算，避免手工维护大量路径。

```text
/archive
  /{year}
    /{month}
      /{domain}
        /{task_type}
          /{task_id}/
            manifest.json
            output_files...
```

示例：

```text
/archive/2025/04/finance/report/T20250415-001/
    manifest.json
    output.pdf
    raw_payload.json
```

目录映射表由脑统一管理：

| 标签组合 | 目录模板 |
|---|---|
| domain:finance + task_type:report | `{root}/{year}/{month}/finance/report/{task_id}/` |
| domain:medical + task_type:dataset | `{root}/{year}/{month}/medical/dataset/{task_id}/` |
| security:confidential 前缀 | `{secure_root}/{year}/{month}/...` |

## 六、归档执行流程

归档采用“先写临时区，再原子提交”的方式：

```text
1. 引擎产出完成
2. 写入暂存区 /tmp/archive_staging/{task_id}/
3. 生成 manifest.json
4. 计算目标目录
5. 移动/复制到目标目录
6. 校验文件数量、大小、校验和
7. 写入索引库
8. 返回归档确认
```

任一环节失败：

- 不删源文件
- 标记归档失败
- 进入阴轨重试队列
- 重试 3 次仍失败，进入死信区人工处理

## 七、脑的稳态机制

### 1. 配置版本化

所有规则、标签、目录映射、模型超时均存放在版本化配置中。

每次任务归档时，manifest 记录当时的配置版本：

```json
{
  "task_id": "T20250415-001",
  "config_version": "2025.04.15-r3",
  "classifier": "rule+semantic",
  "labels": ["domain:finance", "task_type:report"],
  "target_dir": "/archive/2025/04/finance/report/T20250415-001/"
}
```

### 2. 配置修改同步读取点

历史教训：配置改了没生效，是因为读取点没同步。

本系统所有读取点必须统一接入配置中心：

- 规则预分类器
- 标签归一化器
- 目录映射计算器
- 模型超时配置
- 归档执行器

配置变更后，脑立即执行一次“金丝雀验证”：

```text
用一条样本任务跑通：
捕获 → 分类 → 打标 → 归档 → 校验
```

验证通过，配置版本正式生效；验证失败，自动回滚。

### 3. 阴轨一致性校验

每天扫描归档目录，检查：

- 是否有孤儿文件
- 是否有缺失 manifest
- 标签是否与目录一致
- 索引库是否与实际目录一致

发现差异后，由阴轨自动修复或生成补偿任务。

### 4. 循环学习

归档系统定期统计：

- 分类置信度分布
- 规则命中率
- 模型超时率
- 人工复核结果

反馈给脑，持续更新规则库和标签库。

---

## 八、避坑策略映射

| 历史失败 | 本系统对策 |
|---|---|
| 配置修改后未生效 | 配置版本化；所有读取点统一从配置中心读取；变更后立即金丝雀验证 |
| API 调用超时 | B 模型 turbo 超时 300 秒；A 模型超时 600 秒；超时降级为规则分类并标记复核 |

---

## 九、阴阳双轨闭环

整个系统最终形成一个活局：

- **阳轨**让产出有序归档，支撑当前任务。
- **阴轨**让归档系统自我修复、自我进化。
- **脑**掌握控制权，维护开放、有界、循环的稳态。

归档不再是“任务终点”，而是下一次任务的起点。

> 反者道之动：归档产生的索引和知识，反过来赋能引擎，让数字生命在感知层不断从无序走向有序，从“无”生出“有”。
