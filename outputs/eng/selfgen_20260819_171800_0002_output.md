# 任务类型: eng

# 多模型成本实时监控与自动熔断系统设计

本方案直接建立在 **Guardian-Core 双进程、WAL+Snapshot、单向同步、幂等优先** 的锚定之上，不重复论证底层自恢复；只推演增量同步链上的闭环：

> 本地文件（实）→ 变化检测（虚/策略）→ 只传差异（实）→ 冲突处理（虚/策略）→ Supabase 认知池（实）→ 同步指标（实）→ 策略调优（虚）→ 更高效的下一轮同步（返实）

---

## 1. 总体架构

```
业务进程                         监控进程
┌──────────────┐               ┌──────────────────────────────┐
│  Gateway     │   usage event  │  UsageEventConsumer         │
│  CostGuard   │ ───────────────▶│  CounterStore / BreakerState│
│  准入/降级    │               │  WaitingQueue / ReplayWorker │
└──────┬───────┘               └──────────────┬───────────────┘
       │                                      │ WAL + Snapshot
       ▼                                      ▼
     LLM API                          Supabase 认知池
                                      (model_usage_events,
                                       model_counters_snapshot,
                                       breaker_events)
```

- **业务进程**：拦截每一次模型调用，先做成本准入，再放行/降级/入队。
- **监控进程**：消费 usage event，更新每模型计数与熔断状态，写 WAL，定时快照，增量同步 Supabase，驱动补跑。
- **幂等优先**：所有事件带 `event_id`，所有任务带 `task_id + attempt_id`，重复事件不重复计数。

## 2. 配置与模型注册

### 2.1 配置必须从 state 读取

所有可配置参数统一收敛到 `state.cost_control`，全局常量只做默认值兜底。

```ts
const DEFAULTS = {
  fuseCooldownSeconds: 120, // 仅兜底，不是默认生效值
  hardCapUsd: 1000,
  softCapUsd: 800,
  taskCostCapUsd: 5,
  errorRateThreshold: 0.1,
  maxReplayBatch: 10,
  replayQps: 2,
};

function getCostConfig(modelId: string) {
  const stateCfg =
    state.cost_control.models[modelId] ??
    state.cost_control.default ??
    {};
  return { ...DEFAULTS, ...stateCfg, modelId };
}
```

关键点：

- `fuse_cooldown_override` 必须从 state 读取，禁止硬编码 120。
- 配置修改后必须触发 `reload_config()`，并在日志中打印 `config_hash`。
- 每次熔断判定都带上 `config_hash`，便于验证“配置是否真的生效”。

### 2.2 model_id 必须精确匹配官方文档

接入新模型前必须核对官方完整 model_id，`pro/turbo/light` 不可混用。

```ts
modelRegistry = {
  "doubao-seed-2-1-turbo": {
    timeoutSeconds: 300,
    pricing: { inputPer1k: 0.3, outputPer1k: 0.6 },
  },
  "doubao-seed-2-1-pro": {
    timeoutSeconds: 600,
    pricing: { inputPer1k: 0.8, outputPer1k: 1.2 },
  },
};
```

- 计数器 key、熔断 key、日志 key 全部使用完整 `model_id`。
- 未注册的 model_id 直接拒绝调用，防止“把 pro 当 turbo 用”导致成本和耗时失控。

## 3. 计数语义：九维计数器

统一规则：

> **task_count 仅真实任务；bonus_count 仅系统自触发；count = task_count + bonus_count。**

| 维度 | 字段 | 更新时机 |
|---|---|---|
| 1 | `task_count` | 非 bonus 的真实任务，每次调用 +1，含成功/失败/超时 |
| 2 | `bonus_count` | 系统自触发调用，每次 +1 |
| 3 | `count` | 每次调用 +1，必须等于 task_count + bonus_count |
| 4 | `task_success_count` | 真实任务成功时 +1 |
| 5 | `task_failed_count` | 真实任务失败/超时时 +1 |
| 6 | `cost_task_usd` | 真实任务成本累加 |
| 7 | `cost_bonus_usd` | 系统自触发成本累加 |
| 8 | `cost_total_usd` | 总成本累加，= cost_task + cost_bonus |
| 9 | `token_total` | prompt + completion tokens 累加 |

任何加操作必须原子更新：

```ts
if (event.isBonus) {
  bonusCount += 1;
  costBonusUsd += event.costUsd;
} else {
  taskCount += 1;
  costTaskUsd += event.costUsd;
  if (event.status === "success") taskSuccessCount += 1;
  else taskFailedCount += 1;
}
count += 1;
costTotalUsd += event.costUsd;
tokenTotal += event.promptTokens + event.completionTokens;
```

Supabase 表上加约束：

```sql
CHECK (count = task_count + bonus_count)
CHECK (task_success_count + task_failed_count <= task_count)
```

每 10 分钟跑一次审计，发现 `count != task_count + bonus_count` 立即告警并暂停熔断判定，防止错误数据导致误熔断。

## 4. 熔断状态机与降级

### 4.1 阈值类型

每个模型独立计数，独立判定：

- `hard_cap_usd`：周期内总成本硬上限，超过即熔断。
- `soft_cap_usd`：接近上限时告警，不熔断。
- `task_cost_cap_usd`：单任务累计成本上限，超过则暂停该任务。
- `max_tokens_per_period`：周期内 token 上限。
- `error_rate_threshold`：滑动窗口内错误率，如最近 100 次调用中超时/5xx/限流占比 > 10%。

### 4.2 状态机

```
CLOSED ──阈值超限──▶ OPEN
OPEN   ──冷却到期──▶ HALF_OPEN
HALF_OPEN ──探针成功──▶ CLOSED
HALF_OPEN ──探针失败──▶ OPEN（冷却翻倍）
```

- **CLOSED**：正常放行，调用后结算并更新计数。
- **OPEN**：不再向该模型发送新请求。
- **HALF_OPEN**：只放行少量探针任务，验证模型已恢复。
- **CLOSED 后**：自动补跑等待队列。

### 4.3 熔断期间记录等待任务

模型 `M` 熔断后，每个原本要发给 `M` 的任务都先持久化到 `waiting_task`：

```ts
type WaitingTask = {
  waitingId: string;
  taskId: string;
  attemptId: string;
  modelId: string;        // 原始模型
  inputSnapshot: object;
  params: object;
  priority: number;
  status:
    | "waiting"    // 等待原模型恢复
    | "degraded"   // 已用 fallback 执行，不再补跑
    | "replaying"  // 正在补跑
    | "done"
    | "failed";
  createdAt: string;
};
```

降级策略：

- `queue_only`：只排队，不降级，恢复后补跑。
- `fallback_then_queue`：优先切到 fallback 模型；fallback 也失败则留在等待队列。
- 如果任务被 fallback 成功执行，`waiting_task.status = "degraded"`，恢复后**不补跑**。
- 只有 `status = "waiting"` 的任务在恢复后自动补跑。

### 4.4 冷却时间必须读 state

```ts
const cooldown =
  cfg.fuseCooldownOverride ??
  cfg.fuseCooldownSeconds ??
  DEFAULTS.fuseCooldownSeconds;

cooldownUntil = openedAt + cooldown * 1000;
```

`fuse_cooldown_override = 300` 就必须生效，禁止 fallback 到硬编码 120。

### 4.5 恢复与补跑

- 冷却到期后进入 `HALF_OPEN`。
- 从等待队列中选 1 个任务作为探针，发给原模型。
- 探针成功 → `CLOSED`，启动 ReplayWorker。
- 探针失败 → 回到 `OPEN`，冷却时间翻倍，等待队列保留。
- ReplayWorker 按 `priority DESC, createdAt ASC` 拉取 `waiting` 任务，限制并发和 QPS，避免恢复后瞬间打爆成本。

## 5. 关键流程伪代码

### 5.1 请求准入

```ts
function shouldAllow(modelId, task) {
  const cfg = getCostConfig(modelId);
  const breaker = getBreaker(modelId);

  // 熔断中
  if (breaker.state === "OPEN") {
    enqueueWaitingTask(modelId, task);
    if (cfg.degradeStrategy === "fallback_then_queue") {
      const fb = cfg.fallbackModelId;
      if (fb && getBreaker(fb).state === "CLOSED") {
        return { allow: true, targetModelId: fb, degraded: true };
      }
    }
    return { allow: false, queued: true };
  }

  if (breaker.state === "HALF_OPEN") {
    if (breaker.probeCount < cfg.probeMax) {
      return { allow: true, targetModelId: modelId, probe: true };
    }
    enqueueWaitingTask(modelId, task);
    return { allow: false, queued: true };
  }

  // CLOSED：调用前用预估成本做准入
  const projectedCost = estimateCost(modelId, task);
  const remaining = cfg.hardCapUsd - getCounter(modelId).costTotalUsd;

  if (projectedCost > remaining) {
    enqueueWaitingTask(modelId, task);
    return { allow: false, queued: true, reason: "hard_cap_projected" };
  }

  if (getTaskCost(task.taskId) + projectedCost > cfg.taskCostCapUsd) {
    enqueueWaitingTask(modelId, task);
    return { allow: false, queued: true, reason: "task_cost_cap" };
  }

  return { allow: true, targetModelId: modelId };
}
```

### 5.2 调用后结算

```ts
function onUsageEvent(event) {
  // 幂等：同一 event_id 只处理一次
  if (existsEvent(event.eventId)) return;

  appendWAL(event);                 // 先写 WAL
  applyCounter(event);              // 再更新内存计数
  updateErrorWindow(event);         // 超时/5xx/限流计入错误率

  const breaker = getBreaker(event.modelId);

  if (breaker.state === "CLOSED") {
    const reason = checkThresholds(event.modelId);
    if (reason) openBreaker(event.modelId, reason);
  }

  if (breaker.state === "HALF_OPEN") {
    if (event.status === "success") {
      closeBreaker(event.modelId);
      startReplay(event.modelId);
    } else {
      openBreaker(event.modelId, "probe_failed");
    }
  }

  syncToSupabase(event);            // 增量同步
}
```

### 5.3 补跑 worker

```ts
async function replay(modelId) {
  const cfg = getCostConfig(modelId);
  const tasks = loadWaitingTasks(modelId, cfg.maxReplayBatch);

  for (const task of tasks) {
    task.status = "replaying";
    task.attemptId = newAttemptId();

    const result = await callModel(modelId, task.inputSnapshot, {
      timeout: getModel(modelId).timeoutSeconds,
    });

    if (result.success) {
      task.status = "done";
      onUsageEvent(result.usageEvent);
    } else if (task.retryCount < cfg.maxRetries) {
      task.status = "waiting";
      task.retryCount += 1;
    } else {
      task.status = "failed";
      alert(task.taskId);
    }

    saveWaitingTask(task);
    sleep(1000 / cfg.replayQps);
  }
}
```

## 6. 幂等、WAL、快照、Supabase 同步

### 6.1 幂等

- `usage_event.event_id` 全局唯一，重复事件直接忽略。
- `task_id + attempt_id` 唯一，重试时生成新的 `attempt_id`，不会重复计数。
- 补跑时如果任务已 `degraded`，跳过。

### 6.2 WAL + Snapshot

- 每次 usage event 先追加 WAL，再更新内存计数器。
- 每 10 分钟或每 1 万条事件做一次 Snapshot。
- 重启时：加载最新 Snapshot + 重放 WAL 中未快照的事件，恢复计数器和等待队列。

### 6.3 增量同步到 Supabase 认知池

- 同步器记录 `last_sync_seq`，只传新增事件，即“只传差异”。
- 使用 `event_id` 作为幂等键：

```sql
INSERT INTO model_usage_events (...)
VALUES (...)
ON CONFLICT (event_id) DO NOTHING;
```

- 冲突处理：本地 WAL 是唯一事实源，Supabase 以本地为准。
- 同步指标包括：`last_sync_seq`、`sync_lag_ms`、`events_synced`、`model_counters_snapshot`。

### 6.4 策略调优闭环

- 策略调优模块每 30 分钟读取 Supabase 认知池中的成本/熔断/等待队列指标。
- 产出规则：调整某模型 `hardCapUsd`、`fuseCooldownSeconds`、`fallbackModelId`。
- 规则写回 `state.cost_control`，下一轮同步自动使用新配置。

## 7. 历史坑位对照表

| 历史坑 | 本设计防线 |
|---|---|
| 配置修改后未生效 | 配置统一从 state 读取，`config_hash` 参与每次判定，修改后 reload 并验证 |
| API 调用超时 | 每模型配置 timeout：turbo 300s，pro 600s；超时计入错误率并可能触发熔断 |
| B 模型型号错配 | 使用完整 `model_id`，未注册模型拒绝调用，pro/turbo/light 不可混用 |
| 熔断冷却配置不生效 | `fuse_cooldown_override` 从 state 读取，全局常量只做兜底 |
| 九维计数语义混乱 | `count = task_count + bonus_count`，`task_success_count` 单独统计，数据库加 CHECK 约束 |

---

该设计将“成本实时监控、自动熔断、等待队列、恢复补跑”全部纳入 Guardian-Core 的 WAL+Snapshot 体系，同时保持每模型独立、配置可热更新、计数语义可审计，避免历史踩坑点再次发生。
