# 任务类型: eng

设计和推演一个基于 Supabase 的“记忆脑”（通常指代 AI Agent 的长期记忆库或向量知识库）的增量同步方案，核心目标是**高效、低延迟、避免全量扫描、且在多端/多 Agent 环境下具备冲突容错能力**。

因为“记忆脑”的文件通常包含文本、向量或 JSON 结构化数据，我们可以借鉴 Git 的版本控制思想，结合 Supabase 的 Postgres 数据库和 Storage 能力来实现。

以下是完整的推演方案，包含具体算法和伪代码。

---

### 架构概览

*   **本地端：** 本地文件系统 + 本地状态数据库（如 SQLite/LevelDB，记录文件哈希和版本号）。
*   **Supabase 端：**
    *   `Storage`：存储实际的记忆文件内容（或分块）。
    *   `Postgres Table`：存储文件元数据（路径、哈希、版本号、更新时间）。
    *   `Realtime`：用于监听远端变更，触发即时同步。

---

### 一、 如何检测本地文件变化

**核心思想：基于内容哈希的快照对比，而非依赖文件系统的 Modify Time（易被篡改且时区敏感）。**

**算法逻辑：**
1. 遍历本地记忆目录。
2. 读取文件内容，计算 SHA-256 哈希值。
3. 将计算出的哈希与本地状态库中记录的哈希进行对比。
4. 如果哈希不一致，则判定文件发生变更（Added 或 Modified）。
5. 对比本地文件列表和状态库列表，找出被删除的文件。

**伪代码：**

```javascript
// 本地状态库结构: { filePath: String, hash: String, version: Int, lastSync: Timestamp }

function detectLocalChanges(localMemDir, localStateDB) {
    const currentFiles = scanDirectory(localMemDir); // 获取当前所有文件路径
    const changes = { added: [], modified: [], deleted: [] };
    
    const currentFileMap = new Map();

    for (const filePath of currentFiles) {
        const content = readFile(filePath);
        const currentHash = sha256(content);
        currentFileMap.set(filePath, true);
        
        const stateRecord = localStateDB.get(filePath);

        if (!stateRecord) {
            // 状态库中没有，新增文件
            changes.added.push({ filePath, content, hash: currentHash });
        } else if (stateRecord.hash !== currentHash) {
            // 哈希不同，文件被修改
            changes.modified.push({ filePath, content, hash: currentHash, oldVersion: stateRecord.version });
        }
    }

    // 检测删除：状态库中有，但当前文件系统中没有
    for (const stateRecord of localStateDB.getAll()) {
        if (!currentFileMap.has(stateRecord.filePath)) {
            changes.deleted.push({ filePath: stateRecord.filePath, oldVersion: stateRecord.version });
        }
    }

    return changes;
}
```

### 二、 如何只同步变更部分

**核心思想：仅将 `added` 和 `modified` 的文件推送到 Supabase，并更新元数据表；对于 `deleted`，执行软删除。**

**算法逻辑：**
1. 将检测到的变更文件列表上传至 Supabase Storage。
2. 在 Supabase Postgres 中开启事务，更新 `memory_metadata` 表。
3. 使用乐观锁更新版本号。

**伪代码：**

```javascript
async function syncChangesToSupabase(localChanges) {
    const supabaseClient = getSupabaseClient();
    
    // 1. 处理新增和修改
    for (const file of [...localChanges.added, ...localChanges.modified]) {
        // 上传文件内容到 Supabase Storage (覆盖同名文件)
        await supabaseClient.storage.from('memory-brain')
            .upload(file.filePath, file.content, { upsert: true });
            
        // 更新元数据表
        await supabaseClient.from('memory_metadata').upsert({
            path: file.filePath,
            hash: file.hash,
            // version 由数据库触发器或代码逻辑控制自增
            updated_at: new Date().toISOString()
        }, { onConflict: 'path' });
    }

    // 2. 处理删除
    for (const file of localChanges.deleted) {
        // Storage 中删除文件
        await supabaseClient.storage.from('memory-brain').remove([file.filePath]);
        // 数据库中软删除
        await supabaseClient.from('memory_metadata')
            .update({ is_deleted: true, updated_at: new Date().toISOString() })
            .eq('path', file.filePath);
    }
}
```

### 三、 如何处理冲突

**核心思想：基于版本号的乐观锁 + Last-Write-Wins (LWW) / 分支合并策略。**

在多 Agent 并发写入同一个记忆文件时，会产生冲突。我们通过 Supabase 的 `version` 字段来处理。

**冲突检测与解决算法：**
1. 客户端在上传前，携带本地的基础版本号 `base_version` 发起同步请求。
2. Supabase 端通过 Postgres 函数或 RLS 策略检查当前数据库中该文件的 `current_version`。
3. 如果 `base_version == current_version`，无冲突，允许更新，`version + 1`。
4. 如果 `base_version < current_version`，**发生冲突**。
5. **解决策略**：对于 AI 记忆脑，通常采用“保留双方记忆”的策略，而不是直接覆盖。将远端最新版本拉取下来，合并后作为新版本提交。

**伪代码：**

```javascript
async function syncFileWithConflictResolution(file) {
    const supabaseClient = getSupabaseClient();
    
    // 假设 file 包含: { filePath, content, hash, base_version }
    
    // 1. 尝试获取远端当前状态
    const { data: remoteRecord } = await supabaseClient.from('memory_metadata')
        .select('version, hash')
        .eq('path', file.filePath)
        .single();

    if (!remoteRecord) {
        // 远端不存在，直接新增
        await pushToSupabase(file, 1);
        return;
    }

    // 2. 冲突检测
    if (file.base_version === remoteRecord.version) {
        // 无冲突，正常更新，版本号+1
        await pushToSupabase(file, remoteRecord.version + 1);
    } else {
        // 3. 发生冲突 (file.base_version < remoteRecord.version)
        console.log(`Conflict detected on ${file.filePath}. Resolving...`);
        
        // 拉取远端最新版本内容
        const { data: remoteContent } = await supabaseClient.storage.from('memory-brain')
            .download(file.filePath);
            
        // 记忆脑特有冲突解决：不覆盖，而是合并内容 (如：追加修改记录，或者由 LLM 总结合并)
        const mergedContent = await aiMergeMemory(remoteContent, file.content);
        const mergedHash = sha256(mergedContent);
        
        // 将合并后的内容作为新版本提交，基于远端的最新 version
        await pushToSupabase({
            filePath: file.filePath,
            content: mergedContent,
            hash: mergedHash,
            base_version: remoteRecord.version // 基于远端最新版本
        }, remoteRecord.version + 1);
        
        // 更新本地状态为合并后的状态
        updateLocalState(file.filePath, mergedHash, remoteRecord.version + 1);
    }
}

// 辅助函数：推送到 Supabase 并更新数据库 (需要原子操作)
async function pushToSupabase(file, newVersion) {
    // 上传 Storage
    await supabaseClient.storage.from('memory-brain')
        .upload(file.filePath, file.content, { upsert: true });
        
    // 更新 DB (使用乐观锁条件：WHERE version = file.base_version)
    const { error } = await supabaseClient.from('memory_metadata')
        .update({ 
            hash: file.hash, 
            version: newVersion, 
            updated_at: new Date().toISOString() 
        })
        .eq('path', file.filePath)
        .eq('version', file.base_version); // 防止在更新过程中又被其他端修改
        
    if (error) {
        // 极小概率发生并发竞争，递归重试冲突解决
        return syncFileWithConflictResolution(file);
    }
    
    updateLocalState(file.filePath, file.hash, newVersion);
}
```

### 四、 补充：Supabase 端的协同配置

为了让上述方案高效运行，Supabase 端需要如下配置：

1. **元数据表结构：**
   ```sql
   CREATE TABLE memory_metadata (
       id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
       path TEXT UNIQUE NOT NULL,
       hash TEXT NOT NULL,
       version INT NOT NULL DEFAULT 1,
       is_deleted BOOLEAN DEFAULT FALSE,
       updated_at TIMESTAMPTZ DEFAULT now()
   );
   ```

2. **触发自增 (可选，如果不想在客户端算 Version)：**
   可以在 Postgres 创建一个 Trigger，在 `UPDATE` 时自动将 `version = version + 1`，这样客户端只需传内容，由数据库保证版本严格单调递增。

3. **Realtime 监听（拉取远端变更）：**
   本地 Agent 需要订阅 Supabase Realtime，当 `memory_metadata` 表发生变更时，反向拉取最新的文件内容更新到本地，从而实现双向增量同步。
   ```javascript
   supabaseClient.channel('memory-changes')
     .on('postgres_changes', { event: '*', schema: 'public', table: 'memory_metadata' }, payload => {
         downloadRemoteChanges(payload.new); // 拉取变更的文件覆盖本地
     })
     .subscribe();
   ```

### 方案总结

1. **变化检测：** 抛弃文件 mtime，采用 SHA-256 全量哈希遍历对比，绝对可靠且支持离线。
2. **增量同步：** 仅上传 `hash` 发生变化的文件到 Storage，并更新 Postgres 中的元数据。
3. **冲突处理：** 使用 `version` 字段作为乐观锁。发生冲突时，不采取粗暴的 LWW（后者覆盖前者），而是拉取远端内容，通过 AI 或逻辑合并后，生成新版本提交，确保记忆脑的数据不丢失。
