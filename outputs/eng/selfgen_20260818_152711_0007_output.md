# 任务类型: eng

## 结论先行

V7.5 的锁机制不能只做“给后处理加一把大锁”。  
真正的锁要锁在**决策事件追加**和**投影更新**上；API 调用本身不持锁。

竞态条件来源于两个点：

1. **丢失更新**：多个线程基于同一个旧状态读取、调用 API，后处理时互相覆盖。
2. **乱序提交**：API 返回顺序和发起顺序不一致，后处理如果按“完成顺序”执行，会破坏全局顺序。

所以完整方案是：

> **全局序号 + 版本校验 + 有序提交队列 + 超时补位**

---

## 一、竞态推演

假设共享状态 `S = 0`：

```text
线程 A：读 S=0 -> 调用 API_A -> 后处理 S=S+1 => S=1
线程 B：读 S=0 -> 调用 API_B -> 后处理 S=S+1 => S=1
```

如果后处理不加锁或版本校验，最终 `S=1`，但两个成功事件都应该生效，正确值应为 `S=2`。

更隐蔽的是乱序提交：

```text
A 的 API 先发起，seq=10
B 的 API 后发起，seq=11

但 B 先返回，A 后返回。

如果按“完成顺序”后处理：
先执行 B(seq=11)，再执行 A(seq=10)
```

虽然后处理是串行的，但**全局顺序反了**。  
后续任何基于 `S` 的决策都可能错误。

## 二、锁机制总体设计

| 锁/原语 | 保护对象 | 获取时机 | 持有时间 |
|---|---|---|---|
| `SeqLock` | 全局序号分配 | 发起 API 前 | 微秒级 |
| `StateRWLock.read` | 读取状态版本/投影 | 发起 API 前 | 微秒级 |
| `StateRWLock.write` | 事件追加/投影更新 | 后处理提交时 | 毫秒级，不含 API 调用 |
| `Pending Cond` | 待提交队列、`next_commit` | 入队/出队/等待 | 微秒级 |
| `Watchdog` | 超时任务、seq 空洞 | 定时巡检 | 独立 |

核心原则：

- API 调用全程不持有任何锁。
- 锁只保护“决策事件落盘”和“投影更新”。
- 所有后处理任务必须携带 `seq` 和 `base_version`。
- 后处理严格按 `seq` 顺序提交，而不是按完成顺序提交。

## 三、完整锁机制伪码

```python
class PostTask:
    seq: int
    key: str
    base_version: int
    base_key_version: int
    response: object
    error: object = None
    idempotency_key: str = ""


class OrderedPostProcessor:
    def __init__(self, state):
        self.state = state

        # 全局序号锁
        self.seq_lock = threading.Lock()
        self.next_seq = 1

        # 状态读写锁
        self.state.rw_lock = RWLock()

        # 待提交队列
        self.cond = threading.Condition()
        self.pending = []          # 小顶堆，按 seq 排序
        self.next_commit = 1

        # 在途 API 任务
        self.inflight_lock = threading.Lock()
        self.inflight = {}         # seq -> (ctx, deadline)

        # 启动后处理线程
        threading.Thread(target=self._loop, daemon=True).start()
        threading.Thread(target=self._watchdog, daemon=True).start()

    # 1. 发起 API 前：分配 seq，读取版本
    def begin_api(self, key):
        with self.seq_lock:
            seq = self.next_seq
            self.next_seq += 1

        with self.state.rw_lock.rlock():
            base_version = self.state.version
            base_key_version = self.state.key_versions[key]

        ctx = APIContext(
            seq=seq,
            key=key,
            base_version=base_version,
            base_key_version=base_key_version,
        )

        with self.inflight_lock:
            # API_TIMEOUT 按模型设置：
            # B 系列 turbo 用 300 秒，A 系列用 600 秒
            self.inflight[seq] = (ctx, time.monotonic() + API_TIMEOUT)

        return ctx

    # 2. API 返回后：提交后处理任务
    def finish_api(self, ctx, response=None, error=None):
        with self.inflight_lock:
            self.inflight.pop(ctx.seq, None)

        task = PostTask(
            seq=ctx.seq,
            key=ctx.key,
            base_version=ctx.base_version,
            base_key_version=ctx.base_key_version,
            response=response,
            error=error,
        )

        with self.cond:
            heapq.heappush(self.pending, (task.seq, task))
            self.cond.notify_all()

    # 3. 后处理线程：严格按 seq 顺序提交
    def _loop(self):
        while True:
            with self.cond:
                while not (
                    self.pending
                    and self.pending[0][0] == self.next_commit
                ):
                    self.cond.wait()

                _, task = heapq.heappop(self.pending)

            # 注意：这里已经释放 cond，再获取状态写锁
            self._commit(task)

            with self.cond:
                self.next_commit += 1
                self.cond.notify_all()

    # 4. 提交决策事件 + 更新投影
    def _commit(self, task):
        rerun = False

        with self.state.rw_lock.wlock():

            # 幂等保护：同一 idempotency_key 只处理一次
            if task.idempotency_key and task.idempotency_key in self.state.event_index:
                return

            # API 失败也必须有事件，否则 seq 会空洞
            if task.error:
                self._append_event(task, event_type="api_failed")
                return

            # 版本校验：防止基于过期状态做更新
            if task.base_key_version != self.state.key_versions[task.key]:
                policy = self.state.policy(task.key)

                if policy == "abort":
                    self._append_event(task, event_type="aborted")

                elif policy == "merge":
                    self._append_event(task, event_type="merged")
                    self._apply_merge(task)

                elif policy == "rerun":
                    self._append_event(task, event_type="superseded")
                    rerun = True

                return

            # 正常提交
            self._append_event(task, event_type="decision")
            self._apply_projection(task)

        # 锁外重试，避免持有状态锁调用 API
        if rerun:
            self._rerun(task)

    # 5. 超时补位，防止 seq 空洞导致后续任务永久等待
    def _watchdog(self):
        while True:
            time.sleep(1)
            now = time.monotonic()
            expired = []

            with self.inflight_lock:
                for seq, (ctx, deadline) in self.inflight.items():
                    if now > deadline:
                        expired.append(ctx)

            for ctx in expired:
                self.finish_api(ctx, error=TimeoutError("api timeout"))
```

## 四、冲突处理策略

当 `base_key_version` 不等于当前 `key_versions[key]` 时，说明这个 API 调用基于的状态已经过期。

| 策略 | 行为 | 适用场景 |
|---|---|---|
| `abort` | 丢弃该次更新，追加 `aborted` 事件 | 强一致性要求高，不能接受过期覆盖 |
| `merge` | 使用合并函数，将响应合并进当前投影 | 更新可交换、可合并 |
| `rerun` | 释放锁后，用最新状态重新发起 API 调用 | 业务允许重试，且 API 幂等 |

注意：

- `rerun` 必须在锁外执行。
- `rerun` 会分配新的 `seq`，旧任务已经追加 `superseded` 事件，不会阻塞后续任务。
- 要限制重试次数，防止活锁。

## 五、死锁与性能避坑

1. **API 调用永远不持锁。**
2. **后处理线程在 `cond` 下拿到任务后，先释放 `cond`，再获取 `StateRWLock.write`。**
3. **`rerun` 不能持锁执行，必须通过标志位在锁外处理。**
4. **锁的顺序是：短锁、不嵌套。**
5. **如果单线程后处理成为瓶颈，可以按 key 分片：同一个 key 的任务严格按 seq 提交，不同 key 可并行。**
6. **跨进程/多实例时，本地锁不够，Supabase 侧必须用事务和唯一约束。**

## 六、Supabase 远端一致性补充

V7.5 是“本地优先 + Supabase 远端存储与索引”，本地锁只能解决单机多线程竞态。

跨实例时：

- `decision_events` 表必须有 `seq` 和 `idempotency_key` 唯一约束。
- 同步时使用 Postgres 事务：
  ```sql
  INSERT INTO decision_events (seq, key, base_version, payload, idempotency_key)
  VALUES (...)
  ON CONFLICT (idempotency_key) DO NOTHING;
  ```
- 投影表使用乐观锁：
  ```sql
  UPDATE projections
  SET value = ...,
      version = version + 1
  WHERE key = ?
    AND version = ?;
  ```

这样本地锁保证线程安全，Supabase 唯一约束保证跨实例幂等和最终一致。

## 七、验证方式

1. **并发丢失更新测试**：两个线程同时调用同一 key 的 API，断言最终状态等于两个成功事件的总和。
2. **乱序返回测试**：让后发起的 API 先返回，断言事件日志中的 `seq` 依然连续且有序。
3. **超时补位测试**：模拟一个 API 永不返回，断言 watchdog 会插入 `api_failed` 事件，后续任务不阻塞。
4. **幂等测试**：同一 `idempotency_key` 重复提交，断言只产生一条决策事件。
5. **Supabase 多实例测试**：两个实例同时同步事件，断言无重复、无主键冲突。
