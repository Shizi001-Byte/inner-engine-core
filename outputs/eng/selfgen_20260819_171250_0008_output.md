# 任务类型: eng

以下方案直接建立在 **Guardian-Core 双进程、WAL+Snapshot、单向同步与幂等优先** 的锚定之上，不重复论证底层自恢复；只推演“增量同步”这条 **ChainTask** 链。

核心链式推演：

> 本地文件（实）→ 变化检测（虚/策略）→ 只传差异（实）→ 冲突处理（虚/策略）→ Supabase 认知池（实）→ 同步指标（实）→ 策略调优（虚）→ 更高效的下一轮同步（返实）

---

## 1. 总体架构

```
本地记忆文件
   │
   ▼
Guardian 进程（文件监听 + WAL 写入）
   │
   ▼
本地 WAL + Manifest Snapshot
   │
   ▼
Core 进程（ChainTask 执行器）
   │  detect → diff → upload → commit → conflict-resolve
   ▼
Supabase
   ├── Storage：原始文件/大块对象
   ├── Postgres：memory_files / memory_chunks / sync_ops
   └── pgvector：embedding 向量检索
```

Guardian 负责“看”，Core 负责“算”。Guardian 检测到文件变化后只写 WAL，不直接同步；Core 消费 WAL 生成 ChainTask，执行增量同步。

## 2. 本地文件变化检测

### 2.1 监听方式

- 首选 OS 级监听：`inotify` / `FSEvents` / `chokidar` / `watchdog`
- 兜底轮询：每 N 秒扫描一次，比较 `mtime + size + sha256`
- 不能只信 `mtime`，因为 `touch` 会改 mtime 但内容没变；最终以 hash 为准

### 2.2 本地 WAL + Snapshot

Guardian 每次收到事件，追加一条 WAL：

```json
{
  "op": "upsert",
  "path": "notes/idea.md",
  "mtime": 1710000000,
  "size": 1234,
  "sha256": "abc...",
  "event_id": "uuid"
}
```

- WAL 是追加日志，崩溃后可重放
- 定期生成 `manifest.snapshot.json`，记录每个文件的 `path / version / hash / chunks`
- Snapshot 成功后才截断旧 WAL
- 启动时：加载 Snapshot → 重放 WAL → 全量扫描兜底

### 2.3 防抖与合并

同一文件 2 秒内多次变化，合并为一次同步。防止编辑器频繁保存触发大量 ChainTask。

## 3. 只同步变更部分

### 3.1 分块策略

- 小文件（< 64KB）：整个文件作为一个块
- 文本记忆文件（Markdown / JSON）：按行或段落分块，做行级 diff
- 大文件 / 二进制：使用内容定义分块（CDC，如 FastCDC），避免文件中间插入内容导致后续所有块 hash 变化

每个块计算 `sha256`，形成 chunk 级指纹。

### 3.2 差异比较

本地 Manifest 与 Supabase 远程 Manifest 对比：

- 本地有、远程没有 → 新增块
- 两边 hash 不同 → 修改块
- 本地没有、远程有 → 删除块或标记 tombstone
- hash 相同 → 跳过

只上传“新增/修改”的块，这就是“只同步变更部分”。

### 3.3 Supabase 写入

Storage 对象 key：

```
memory/{user_id}/{file_hash}/{version}/{chunk_index}
```

因为 `version + chunk_index` 不可变，重试上传同一个 key 是幂等的。

Postgres 同步：

- `memory_files` 记录文件级版本、hash、chunk 数量
- `memory_chunks` 记录 chunk 内容、hash、embedding
- 只对变更 chunk 重新生成 embedding，未变更 chunk 的向量保留

这样真实 token 消耗只花在变化部分，也就是“以实养虚”里的“实”。

## 4. 冲突处理

### 4.1 版本锚点

本地 Manifest 为每个文件记录：

```json
{
  "path": "notes/idea.md",
  "base_version": 3,
  "local_version": 4,
  "base_hash": "old-hash",
  "local_hash": "new-hash"
}
```

Supabase 的 `memory_files` 表记录远程 `version` 和 `content_hash`。

### 4.2 冲突判定

同步前先比较：

- 远程 version == base_version，且本地有变化 → 无冲突，直接提交
- 远程 version > base_version，且本地也有变化 → 冲突

### 4.3 冲突解决策略

默认采用“单向同步 + 幂等优先”：

- 本地是权威：`local_wins`
- 远程有未同步变更时，先拉取并记录到 `sync_conflicts`，再以本地内容覆盖远程
- 所有写操作带 `op_id`，重复执行只生效一次

如果需要双向同步，则启用更细粒度策略：

| 策略 | 适用场景 |
|---|---|
| `local_wins` | 本地是唯一事实源 |
| `remote_wins` | 远程被人工/其他设备修改，本地可丢弃 |
| `3-way merge` | 文本文件，基于共同祖先自动合并 |
| `LLM semantic merge` | 语义冲突，自动合并无法处理时 |
| `manual` | 高风险冲突，留待人工处理 |

3-way merge 原则：

- base = 上次同步时的共同快照
- local_diff = base → 本地
- remote_diff = base → 远程
- 两个 diff 不重叠 → 自动合并
- 重叠 → 冲突标记，或交给 LLM 合并

### 4.4 幂等提交

Supabase 提供 RPC `apply_sync`：

```sql
begin;
  -- 检查 op_id 是否已存在
  if exists (select 1 from sync_ops where op_id = p_op_id) then
    return true;
  end if;

  -- 乐观锁检查版本
  update memory_files
     set version = p_new_version,
         content_hash = p_new_hash
   where path = p_path
     and version = p_expected_version;

  if not found then
    return false; -- 冲突
  end if;

  insert into sync_ops (op_id, file_path, ...) values (...);
commit;
```

这样网络重试、进程重启、重复执行都不会产生重复数据。

## 5. ChainTask 落地

每次增量同步实例化为一个 ChainTask：

```
detect → diff → upload → commit → ack
```

- `detect`：从 WAL 和 Snapshot 得到变更文件列表
- `diff`：比较本地/远程 chunk hash，生成变更块列表
- `upload`：上传变更块到 Supabase Storage
- `commit`：RPC 原子更新 `memory_files / memory_chunks / sync_ops`
- `ack`：更新本地 base_version，写 sync_metrics

每个步骤都幂等。某一步失败，只从该步重试，不重新执行已完成步骤。

## 6. 以实养虚，虚又返实

每次同步后写 `sync_metrics`：

```json
{
  "op_id": "uuid",
  "file_path": "notes/idea.md",
  "duration_ms": 320,
  "changed_chunks": 3,
  "skipped_chunks": 120,
  "uploaded_bytes": 2048,
  "conflict_count": 1,
  "merge_method": "3way",
  "embedding_tokens": 512,
  "config_version": "2025-01-01-v3"
}
```

这些真实指标用于调优“虚”的策略：

- chunk 太大 → 浪费上传；chunk 太小 → 开销高，调 chunk_size
- local_wins 导致远程数据频繁丢失 → 改 merge 策略
- embedding token 消耗过高 → 换更便宜的模型或更优分块
- 同步耗时过长 → 调整并发度、timeout、重试策略

调优后的策略又驱动下一次同步，这就是“虚又返实”的自增强闭环。

## 7. 避坑落实

### 7.1 配置修改必须立即验证生效

所有同步参数集中在 `sync_config` 表/文件中，读取点只有 `getSyncConfig()`。

新增配置字段后，必须同步修改读取点，否则配置不会生效。

修改配置后执行：

```bash
syncctl verify --probe
```

用一个小文件走完整条链，并检查 `sync_metrics.config_version` 已变成新值。

### 7.2 预设合理超时

Supabase 普通请求：

- 默认 30 秒
- 重试 3 次，指数退避
- 大文件上传按块并发，单块超时 120 秒

LLM 辅助冲突合并：

- B 模型 turbo：300 秒
- A 模型：600 秒
- 超时不无限重试，降级为 `local_wins` 或写入 `sync_conflicts` 等人工处理

### 7.3 废稿检测不能误杀 B 模型

如果 LLM 合并流程中自带“废稿检测/自动重试”逻辑，必须按模型区分：

- B 模型 turbo：跳过 reasoning 占比检测
- B 模型 reasoning 占比 70%-82% 是正常特性，不能判定为废稿

否则每次 LLM 合并都会被误杀并重试，最终超时。

## 8. 总结

这个增量同步方案是一条完整的链：

- 本地文件变化是“实”
- 差异检测与合并策略是“虚”
- 只传变更块是“实”
- 冲突处理是“虚”
- Supabase 认知池是“实”
- metrics 回流调优是“虚又返实”

整条链由 ChainTask 串起，Guardian-Core 双进程保证存活，WAL+Snapshot 保证可恢复，op_id + version 保证幂等和冲突可解。
