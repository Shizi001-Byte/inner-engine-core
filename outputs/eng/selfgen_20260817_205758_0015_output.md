# V7.4 九维闭环引擎 —— 多线程API调用串行后处理竞态推演与锁机制方案

---

## 一、架构假设与竞态场景建模

### 1.1 九维状态空间定义

```
D1: 输入态       D2: 校验态       D3: 处理态
D4: 聚合态       D5: 反馈态       D6: 补偿态
D7: 版本态       D8: 生命周期态    D9: 一致性快照态
```

每个维度独立维护状态字段，维度间存在**有向依赖**：

```
D1 → D2 → D3 → D4 → D5
                ↓      ↑
    D6 ← ← ← ←       |
    D7(版本贯穿) → D9(快照) ← D8
```

### 1.2 并发拓扑

```
                    ┌── Thread-1: API调用 → 写D1,D3 → 入队后处理
Thread Pool ────────┼── Thread-2: API调用 → 写D1,D3 → 入队后处理
                    ├── Thread-3: API调用 → 写D1,D3 → 入队后处理
                    └── Thread-N: ...

                    Serial Post-Processor (单线程消费):
                    ┌── 读D1,D3 → 写D4,D5 → 更新D7,D9 ──┐
                    └──────────── 循环 ←─────────────────┘
```

## 二、竞态推演（9类竞态）

### 竞态 R1：写-写覆盖（D1/D3 维度）

```
时间线：
  T1: API-1 读D1.state → S_old → 写 D1.state = S_a
  T2: API-2 读D1.state → S_old → 写 D1.state = S_b   // 覆盖S_a
  T3: 后处理读 D1.state → S_b（丢失S_a）

后果：S_a对应的业务数据在后处理中永远不会被处理，产生"静默丢弃"
```

**根因**：读-改-写非原子。

### 竞态 R2：读-写撕裂（D4 聚合态）

```
后处理线程正在执行 D4 = aggregate(D1, D3)：
  Step1: 读 D1 = S_a          ← 时刻t1
  ---- API线程在此处写 D3 = S_new ----
  Step2: 读 D3 = S_new        ← 时刻t2
  Result: D4 = aggregate(S_a, S_new)  ← 跨版本聚合，语义非法
```

**根因**：跨维度读取无快照隔离。

### 竞态 R3：版本号乱序（D7 维度）

```
  Thread-1: version=7, payload=A
  Thread-2: version=8, payload=B

后处理队列（无序到达）:
  消费 version=8 (B) → 写D7=8
  消费 version=7 (A) → 写D7=7   ← 版本回退！

后果：D8(生命周期态)基于D7做状态机迁移时，
      v8→v7的回退会触发非法迁移路径
```

### 竞态 R4：后处理队列入队竞态

```
  Thread-1: enqueue(task_A)
  Thread-2: enqueue(task_B)

若队列底层结构在enqueue时未同步：
  - 链表: next指针丢失
  - 环形Buffer: writePos覆盖
  - 产生: 任务丢失或重复消费
```

### 竞态 R5：ABA 问题（D9 快照态）

```
  D9.snapshot = ref(X)
  
  Thread-1: CAS(D9.snapshot, X, X_new) → 失败
  Thread-2: D9.snapshot = X → Y → X   // A→B→A
  Thread-1: CAS(D9.snapshot, X, X_new) → 成功（但语义错误，X已被改过）
```

### 竞态 R6：指令重排导致的可见性陷阱

```java
// API线程
state.payload = payload;      // Step1: 普通写
state.ready = true;           // Step2: 标志位

// 后处理线程
if (state.ready) {             // Step3
    process(state.payload);    // Step4: 可能读到null!
}
```

**根因**：Step1和Step2无happens-before关系，CPU/编译器可能重排。

### 竞态 R7：锁粒度不当导致的死锁

```
  Thread-1: lock(D1) → 请求 lock(D3)
  Thread-2: lock(D3) → 请求 lock(D1)
  
  经典交叉死锁
```

### 竞态 R8：补偿态与处理态的竞态窗口

```
  后处理: 处理task_A → 失败 → 标记D6(补偿) → 准备重试
  
  在标记D6之前，API线程读取D3发现task_A已"处理"，
  返回成功给调用方 → 但实际后处理失败
  
  窗口: [后处理开始标记] → [D6补偿标记] 之间的时间差
```

### 竞态 R9：快照态与实际状态的最终一致漂移

```
  D1~D8 各维度独立更新成功
  D9 快照更新失败（或延迟）
  
  后处理下次循环读D9快照 → 获取到旧状态集
  → 基于旧快照做聚合 → 产生脏数据
  
  长期后果：D9与D1~D8持续漂移，最终一致性无法收敛
```

## 三、完整锁机制方案

### 3.1 锁分层架构

```
┌─────────────────────────────────────────────────────┐
│                 L0: 进程级屏障                        │
│          (Memory Barrier / volatile语义)             │
├─────────────┬───────────┬───────────┬───────────────┤
│  L1: 维度锁  │ L2: 序列锁 │ L3: 队列锁 │ L4: 快照锁    │
│  (DimLock)  │ (SeqLock) │(QueueLock)│(SnapLock)     │
├─────────────┴───────────┴───────────┴───────────────┤
│              L5: 版本乐观锁                            │
│              (VersionCAS / OCC)                       │
├──────────────────────────────────────────────────────┤
│              L6: 分布式锁                               │
│              (Redlock / ZK, 仅多实例时)                 │
└──────────────────────────────────────────────────────┘
```

### 3.2 L1 —— 分段维度锁（解决 R1, R2, R7）

**设计原则**：按维度分段，避免全局锁；固定锁序防死锁。

```java
public enum DimLockOrder {
    // 严格按此顺序加锁，禁止逆序
    D1_INPUT,    // 0
    D2_VALIDATE, // 1
    D3_PROCESS,  // 2
    D4_AGGREGATE,// 3
    D5_FEEDBACK, // 4
    D6_COMPENSATE,// 5
    D7_VERSION,  // 6
    D8_LIFECYCLE,// 7
    D9_SNAPSHOT  // 8
}

public class DimLockManager {
    // 每维度内部再按entityId分段
    private final Striped<ReentrantReadWriteLock> dimLocks;
    // stripeCount = 256, 每个维度独立池
    
    private final ReentrantReadWriteLock[] locks 
        = new ReentrantReadWriteLock[9];
    
    public AutoCloseableLock acquire(DimLockOrder... order) {
        // 按枚举序号升序加锁，防死锁
        Arrays.sort(order);
        for (DimLockOrder d : order) {
            locks[d.ordinal()].writeLock().lock();
        }
        return () -> {
            // 逆序释放
            for (int i = order.length - 1; i >= 0; i--) {
                locks[order[i].ordinal()].writeLock().unlock();
            }
        };
    }
}
```

**API线程写入路径**：
```java
public void onApiCall(String entityId, Payload payload) {
    try (var lock = dimLockManager.acquire(D1_INPUT, D3_PROCESS)) {
        // 原子地读取-修改-写入D1和D3
        state.setD1(entityId, payload);
        state.setD3(entityId, ProcessState.PENDING);
    }
    // 锁释放后再入队，避免持锁阻塞队列
    postProcessQueue.offer(new Task(entityId, payload.version));
}
```

### 3.3 L2 —— 序列号锁（解决 R3 版本乱序）

```java
public class VersionSequencer {
    private final AtomicLong globalSeq = new AtomicLong(0);
    
    // 每个entityId维护一个单调递增版本号
    private final ConcurrentSkipListMap<Long, Task> pendingTasks 
        = new ConcurrentSkipListMap<>();
    
    public long nextVersion(String entityId) {
        // entityId级别原子递增
        return entityVersionMap
            .computeIfAbsent(entityId, k -> new AtomicLong(0))
            .incrementAndGet();
    }
    
    public void enqueueOrdered(Task task) {
        long seq = globalSeq.incrementAndGet();
        task.setGlobalSeq(seq);
        pendingTasks.put(seq, task);
    }
    
    public Task pollNext() {
        // 严格按全局序列号消费
        Map.Entry<Long, Task> entry = pendingTasks.pollFirstEntry();
        return entry != null ? entry.getValue() : null;
    }
}
```

```
入队: Thread-1 seq=7, Thread-2 seq=8
消费: 永远先消费seq=7，再消费seq=8
     即使Thread-2先到达队列，也会排在seq=7之后
```

### 3.4 L3 —— 后处理队列锁（解决 R4 入队竞态）

```java
public class PostProcessQueue {
    // 方案A: 使用无锁队列 (MpscArrayQueue, 多生产者单消费者)
    private final MpscArrayQueue<Task> queue;
    
    // 方案B: 有锁队列 + 双缓冲
    private final Object writeBufferLock = new Object();
    private Task[] writeBuffer = new Task[CAPACITY];
    private int writeIndex = 0;
    private volatile boolean bufferReady = false;
    
    // 生产者（API多线程）
    public void offer(Task task) {
        // 方案A: 无锁入队
        while (!queue.offer(task)) {
            Thread.yield(); // 背压
        }
    }
    
    // 消费者（后处理单线程）
    public Task poll() {
        return queue.poll(); // Mpsc保证单消费者安全
    }
    
    // 批量消费，减少锁竞争
    public int drainTo(List<Task> batch, int max) {
        return queue.drain(batch::add, max);
    }
}
```

**选用 MpscArrayQueue 的理由**：

| 特性 | MpscArrayQueue | LinkedBlockingQueue | ConcurrentLinkedQueue |
|------|---------------|--------------------|-----------------------|
| 多生产者 | ✅ 无锁CAS | ✅ 加锁 | ✅ CAS |
| 单消费者 | ✅ 简单读 | ✅ 加锁 | ✅ CAS |
| 有界背压 | ✅ | ✅ | ❌ |
| 性能 | 最高 | 中 | 高(但无界) |

### 3.5 L4 —— 快照锁 + Copy-on-Write（解决 R2, R5, R9）

```java
public class SnapshotManager {
    private final ReentrantReadWriteLock snapLock = new ReentrantReadWriteLock();
    
    // 不可变快照对象
    public static final class EngineSnapshot {
        final Map<String, DimState> dims;  // 不可变Map
        final long version;
        final long timestamp;
        
        EngineSnapshot(Map<String, DimState> dims, long version) {
            this.dims = Map.copyOf(dims);  // 防御性拷贝
            this.version = version;
            this.timestamp = System.nanoTime();
        }
    }
    
    private volatile EngineSnapshot current;
    
    // API线程：读快照（读锁，允许并发读）
    public EngineSnapshot readSnapshot() {
        snapLock.readLock().lock();
        try {
            return current;  // volatile读，保证可见性
        } finally {
            snapLock.readLock().unlock();
        }
    }
    
    // 后处理线程：写快照（写锁，独占）
    public void commitSnapshot(Map<String, DimState> newDims, long version) {
        snapLock.writeLock().lock();
        try {
            // 版本号单调校验
            if (current != null && version <= current.version) {
                throw new IllegalStateException(
                    "版本回退: " + version + " <= " + current.version);
            }
            current = new EngineSnapshot(newDims, version);
        } finally {
            snapLock.writeLock().unlock();
        }
    }
}
```

**快照隔离保证后处理读取一致性**：
```
后处理读取快照 S_v8:
  D1=v8, D3=v8, D4=v8 ... (全部同一版本)
  
即使API线程在此期间写入了D1=v9，
后处理本次循环仍然基于v8快照处理，不受影响
```

### 3.6 L5 —— 版本乐观锁 CAS（解决 R1, R5 ABA）

```java
public class VersionedState {
    private final AtomicStampedReference<DimState> ref;
    // 使用StampedReference而非普通AtomicReference，解决ABA
    
    public boolean cas(DimState expect, DimState update, int expectStamp) {
        return ref.compareAndSet(expect, update, expectStamp, expectStamp + 1);
    }
    
    public DimState get(long[] stampHolder) {
        return ref.get(stampHolder);
    }
}
```

**ABA问题解决**：
```
Thread-1: 读 D9 = X(stamp=1)
Thread-2: D9: X(stamp=1) → Y(stamp=2) → X(stamp=3)
Thread-1: CAS(X, X_new, stamp=1) → 失败！stamp不匹配

正确行为：Thread-1重试，读取最新状态
```

### 3.7 内存屏障方案（解决 R6 指令重排）

```java
public class StateVisibility {
    // 方案1: volatile字段（JMM保证happens-before）
    private volatile boolean ready = false;
    private Payload payload;           // 非volatile
    
    // 方案2: 使用VarHandle精确控制（JDK9+）
    private static final VarHandle PAYLOAD_HANDLE;
    private static final VarHandle READY_HANDLE;
    
    static {
        try {
            PAYLOAD_HANDLE = MethodHandles.lookup()
                .findVarHandle(StateVisibility.class, "payload", Payload.class);
            READY_HANDLE = MethodHandles.lookup()
                .findVarHandle(StateVisibility.class, "ready", boolean.class);
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }
    
    // 生产者：Release语义（保证payload写入对ready=true之前的读者可见）
    public void publish(Payload p) {
        PAYLOAD_HANDLE.setRelease(this, p);
        READY_HANDLE.setRelease(this, true);
    }
    
    // 消费者：Acquire语义
    public void consume() {
        if ((boolean) READY_HANDLE.getAcquire(this)) {
            Payload p = (Payload) PAYLOAD_HANDLE.getAcquire(this);
            process(p);  // 保证不为null
        }
    }
}
```

**内存屏障语义图**：
```
Producer (Release):
  payload = P;          ──┐ StoreStore屏障
  ready = true;          ──┘ 不允许重排到payload写之前

Consumer (Acquire):
  if (ready) {           ──┐ LoadLoad屏障  
  process(payload);     ──┘ 不允许重排到ready读之前
```

### 3.8 补偿态竞态窗口方案（解决 R8）

```java
public class CompensateGuard {
    // 处理状态标记必须原子地包含补偿预备态
    enum ProcessState {
        PENDING,      // 待处理
        PROCESSING,   // 处理中（后处理持有）
        COMPENSATING, // 补偿中
        DONE,         // 完成
        FAILED        // 最终失败
    }
    
    // 使用状态机CAS，消除窗口
    public boolean tryProcess(String entityId) {
        return stateMap.computeIfAbsent(entityId, 
            k -> new AtomicReference<>(ProcessState.PENDING))
            .compareAndSet(ProcessState.PENDING, ProcessState.PROCESSING);
    }
    
    public boolean tryCompensate(String entityId) {
        AtomicReference<ProcessState> state = stateMap.get(entityId);
        // PROCESSING → COMPENSATING 必须原子转换
        return state.compareAndSet(ProcessState.PROCESSING, ProcessState.COMPENSATING);
    }
    
    // API线程查询时，必须检查完整状态
    public boolean isTerminal(String entityId) {
        ProcessState s = stateMap.get(entityId).get();
        return s == ProcessState.DONE || s == ProcessState.FAILED;
    }
}
```
