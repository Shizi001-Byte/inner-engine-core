# 任务类型: eng

# 多模型成本实时监控与自动熔断系统设计

> 锚定前提：本方案直接建立在 **Guardian-Core 双进程、WAL+Snapshot、单向同步、幂等优先** 之上，不重复论证底层自恢复；只推演“增量同步”这条 **ChainTask** 链。

## 0. ChainTask 推演链

```text
本地文件（实）
  → 变化检测（虚/策略）：成本聚合 + 熔断判断
  → 只传差异（实）：WAL 增量事件同步
  → 冲突处理（虚/策略）：event_id 幂等，本地为准
  → Supabase 认知池（实）：usage/breaker/pending 历史
  → 同步指标（实）：sync_lag、unsynced_count、breaker_state
  → 策略调优（虚）：30 分钟滚动调阈值/冷却/fallback
  → 更高效的下一轮同步（返实）：自适应 batch 大小
```

---

## 1. 总体架构

```text
Executor 进程
├── Router：按 BreakerRegistry 路由/降级/入队
├── PendingQueue：熔断期间的等待任务
└── Replayer：熔断恢复后自动补跑

Monitor 进程
├── CounterStore：本地实时计数 + WAL
├── BreakerRegistry：每个 model_id 独立状态机
└── SyncWorker：增量同步到 Supabase
```

- 本地 `WAL + Snapshot` 是事实源，Supabase 只做认知池/报表/调优，不参与实时熔断。
- 所有阈值判断在本地完成，不因 Supabase 故障而阻塞。

### 2.2 避坑：配置修改后必须生效

- 所有可配置参数必须从 `state.config` 读取，禁止硬编码。
- 全局常量只做默认值兜底：

```python
cooldown = state.config.models[model_id].fuse.cooldown_seconds
if cooldown is None:
    cooldown = DEFAULT_FUSE_COOLDOWN_SECONDS  # 仅兜底
```

- 配置写入后立即执行 `apply_config()`，并做自检：

```python
def apply_config(new_config):
    validate_model_ids(new_config)
    validate_fallbacks(new_config)
    validate_timeouts(new_config)
    wal.append(config_change_event)
    state.config = new_config
    assert state.config.models["doubao-seed-2-1-turbo"].fuse.cooldown_seconds == 300
```

- 新增配置必须同步修改读取点；否则会出现“改了不生效”。

## 3. 计数模型：语义必须统一

### 3.1 两套计数器，禁止混用

```text
任务注册计数（语义层）
  task_count        = 真实任务数（去重）
  bonus_count       = 系统自触发任务数（去重）
  count             = task_count + bonus_count
  tasks_completed   = 真实任务完成数（去重）

模型用量计数（成本/熔断层）
  api_call_task     = 真实任务触发的 API 调用次数
  api_call_bonus    = 系统自触发 API 调用次数
  api_call_total    = api_call_task + api_call_bonus
  cost_usd          = 实际计费金额
  error_count       = 错误次数
  timeout_count     = 超时次数
```

### 3.2 关键规则

- **禁止裸 `count` 字段**。如果展示总量，必须带前缀：
  - `api_call_total`
  - `task_count + bonus_count`
- `task_count` 只算真实任务，`bonus_count` 只算系统自触发。
- `count = task_count + bonus_count` 是导出关系，不是独立累加字段。
- `tasks_completed` 只算真实任务成功数，不等于 `api_call_task`。
- 任何加操作必须通过同一个 `Incr()` 入口，先写 WAL，再更新内存。

```python
def add_api_call(counter, source):
    if source == "task":
        counter.api_call_task += 1
    elif source == "bonus":
        counter.api_call_bonus += 1
    else:
        raise ValueError("unknown source")
    counter.api_call_total = counter.api_call_task + counter.api_call_bonus
```

### 3.3 滑动窗口

- 熔断判断使用滑动窗口，不用累计全量：
  - 最近 5 分钟错误率/超时率
  - 最近 1 小时成本
  - 最近 1 天成本
  - 最近 1 分钟调用量

本地维护分钟级/小时级桶：

```text
cost_last_hour = sum(cost_minute_buckets[-60:])
error_rate_5m = error_count_5m / api_call_total_5m
```

## 4. 熔断状态机

每个 `model_id` 独立维护一个熔断器：

```text
CLOSED -> OPEN -> HALF_OPEN -> CLOSED
```

### 4.1 熔断条件

每次 API 返回后立即判断：

```python
def should_open(model_id):
    cfg = state.config.models[model_id].fuse
    c = state.counters[model_id]

    if c.cost_last_hour >= cfg.max_cost_per_hour:
        return True
    if c.cost_last_day >= cfg.max_cost_per_day:
        return True
    if c.api_call_last_minute >= cfg.max_calls_per_minute:
        return True
    if c.error_rate_5m >= cfg.max_error_rate_5m:
        return True
    if c.timeout_rate_5m >= cfg.max_timeout_rate_5m:
        return True
    return False
```

### 4.2 状态切换

```text
CLOSED:
  - 请求正常放行
  - 响应后检查 should_open()
  - 超过阈值 -> OPEN

OPEN:
  - 拒绝该模型的新请求
  - 进入降级或等待队列
  - cooldown_until = now + cooldown_seconds（从 state 读取）

HALF_OPEN:
  - 放行 1 个探测请求
  - 成功且未超阈值 -> CLOSED，触发 Replayer
  - 失败或超阈值 -> OPEN，冷却翻倍
```

### 4.3 冷却时间

```python
next_cooldown = min(
    cfg.fuse.cooldown_seconds * (2 ** consecutive_opens),
    cfg.fuse.max_cooldown_seconds
)
```

> 避坑：熔断冷却必须从 `state.config.models[model_id].fuse.cooldown_seconds` 读取，不能用硬编码 120 秒。

## 5. 降级与补跑

### 5.1 路由逻辑

```python
def dispatch(req):
    model_id = req.model_id

    if breaker[model_id].is_open():
        return degrade_or_queue(req)

    # 预检查：如果剩余预算不足，直接熔断，避免超限
    if should_open(model_id):
        breaker[model_id].open("pre-check")
        return degrade_or_queue(req)

    resp = call_model(model_id, req, timeout_for(req))

    if resp.error:
        record_failure(model_id, req.source, resp.error)
        if should_open(model_id):
            breaker[model_id].open(resp.error)
        return resp.error

    record_success(model_id, req.source, resp.usage)
    if should_open(model_id):
        breaker[model_id].open("cost-threshold")

    return resp
```

### 5.2 降级

```python
def degrade_or_queue(req):
    for fb in state.config.models[req.model_id].fallbacks:
        if not breaker[fb].is_open():
            resp = call_model(fb, req, timeout_for(fb))
            record_success(fb, req.source, resp.usage, degraded_from=req.model_id)
            return resp

    if req.async:
        return pending_queue.enqueue(req)
    else:
        return 503 ServiceUnavailable
```

### 5.3 等待任务队列

- 熔断期间，无法降级的任务进入 `PendingQueue`。
- 每个任务持久化到 WAL：

```json
{
  "event_id": "uuid",
  "type": "task_enqueue",
  "model_id": "doubao-seed-2-1-turbo",
  "task_id": "task_123",
  "idempotency_key": "task_123_attempt_1",
  "status": "waiting",
  "enqueued_at": "2026-01-01T00:00:00Z"
}
```

### 5.4 恢复后自动补跑

熔断器进入 `CLOSED` 时触发 Replayer：

```python
def replay(model_id):
    concurrency = cfg.queue.replay_initial_concurrency

    while True:
        if breaker[model_id].state != CLOSED:
            return

        tasks = pending_queue.list_waiting(model_id, limit=concurrency)
        if not tasks:
            return

        for task in tasks:
            go replay_one(model_id, task)

        concurrency = min(
            concurrency * 2,
            cfg.queue.replay_max_concurrency
        )
```

`replay_one` 必须幂等：

```python
def replay_one(model_id, task):
    if completed_tasks.exists(task.idempotency_key):
        return

    pending_queue.mark_running(task)
    resp = call_model(model_id, task.payload, timeout_for_task(task))

    if resp.error:
        if task.attempt >= cfg.queue.max_attempts:
            pending_queue.mark_failed(task)
        else:
            pending_queue.requeue_with_backoff(task)
        return

    record_success(model_id, "task", resp.usage)
    completed_tasks.mark(task.idempotency_key)
    pending_queue.mark_completed(task)
```

> 避坑：补跑不能重复执行业务逻辑；必须依赖 `idempotency_key` + `completed_tasks` 去重。

## 6. Supabase 增量同步

### 6.1 表结构

```sql
create table model_usage_events (
  event_id uuid primary key,
  model_id text not null,
  source text not null check (source in ('task','bonus')),
  task_id text,
  degraded_from text,
  status text not null,
  usage jsonb,
  cost_usd numeric,
  created_at timestamptz
);

create table model_breaker_events (
  event_id uuid primary key,
  model_id text not null,
  from_state text not null,
  to_state text not null,
  reason text,
  created_at timestamptz
);
```

### 6.2 只传差异

- SyncWorker 记录 `last_synced_event_id`。
- 每次只读取 WAL 中新增事件，批量写入 Supabase。
- 写入使用：

```sql
insert into model_usage_events (...)
values (...)
on conflict (event_id) do nothing;
```

- Supabase 不可用时不阻塞本地熔断，WAL 继续累积，恢复后追平。

## 7. 策略调优

每 30 分钟从 Supabase 认知池读取聚合指标：

```text
avg_cost_per_task
timeout_rate
error_rate
fallback_ratio
breaker_open_count
pending_queue_depth
```

调优器生成配置建议：

- 某模型频繁熔断 → 提高 `cooldown_seconds` 或降低 `max_cost_per_hour`
- 某模型成本高 → 提前切到 fallback
- 免费额度充足 → 适当放宽成本阈值
- fallback 成功率高 → 调整 fallback 顺序

调优结果必须走 `apply_config()`，写 WAL，并自检生效。

## 8. 验证与避坑对照

| 历史坑 | 本方案对策 |
|---|---|
| 配置修改后不生效 | 所有参数从 state 读取；`apply_config()` 后立即断言自检 |
| API 超时未返回 | 每个模型/任务类型配置独立 timeout；turbo 默认 300s，A 类默认 600s |
| B 模型型号错配 | 只允许官方完整 `model_id`；响应中 model 与请求不一致时失败 |
| 熔断冷却硬编码 | `cooldown_seconds` 从 state 读取，常量只兜底 |
| count/task/bonus 混乱 | 禁止裸 count；`task_count`、`bonus_count`、`api_call_total`、`tasks_completed` 各自独立，统一入口更新 |
