# 任务类型: eng

基于【已有认知锚定】与【历史避坑经验】，直接推演 Supabase 记忆脑的增量同步方案。本方案将严格规避配置未生效、API超时、废稿误杀及多线程竞态问题。

---

### Supabase 记忆脑增量同步方案

#### 一、 A0 锚定：状态一致性与数据基线
基于 `CONST-1: 精气神三元迁移框架`，记忆脑的同步需建立“本地态（精）- 同步引擎（气）- 远端态（神）”的一致性基线。

*   **A0 基线定义**：每条记忆片段必须具备 `memory_id`, `content_hash`, `updated_at`, `version` 四个核心字段。
*   **一致性前提**：本地与 Supabase 的初始状态必须对齐。启动同步前，以 Supabase 远端 `updated_at` 最大值为锚点，拉取全量 ID 列表构建本地索引基线，后续所有增量均基于此基线计算。

#### 二、 本地文件变化检测（防竞态版）
针对多线程 API 调用后接串行后处理导致的“线程覆盖”与“部分结果”问题，检测层做如下隔离：

1.  **原子化写入与快照读取**
    *   **避坑**：后处理线程读到“部分结果”。
    *   **对策**：本地文件写入采用“临时文件 -> 重命名”的原子操作。文件 Watcher（如 `watchdog`）仅监听 `on_modified` 且文件大小稳定 500ms 后的完整文件。
2.  **写入锁与版本号预分配**
    *   **避坑**：线程 A 写完结果，线程 B 覆盖了 A 的结果。
    *   **对策**：串行后处理队列写入本地文件前，需获取 `memory_id` 级别的分布式锁（或本地互斥锁）。写入时递增本地版本号，确保线程 B 的写入基于线程 A 的最新版本（Version >= Version_A + 1），若版本冲突则触发重试。

#### 三、 增量同步机制（只同步变更部分）
通过哈希比对与状态机控制，仅同步有效变更，同时规避 API 超时与废稿误杀。

1.  **变更计算**
    *   计算本地文件 `content_hash` (SHA-256)，与 Supabase 中对应 `memory_id` 的 hash 比对。不一致则判定为变更，进入同步队列。
2.  **同步前处理与 API 调用（严格防坑）**
    *   若同步涉及模型重写或摘要提取：
        *   **超时控制**：B模型(turbo) 设置 300秒 timeout，A模型 设置 600秒 timeout。
        *   **废稿检测隔离**：若使用 B模型(turbo) 生成记忆摘要，**强制跳过 reasoning 占比检测**。因为 B模型 reasoning 占比 70-82% 是正常特性，直接放行进入 Supabase 写入队列。
3.  **增量 Upsert 操作**
    *   使用 Supabase 的 `upsert` 功能，携带 `memory_id` 和最新 `version`。
    *   仅传输变更的字段（如 `content`, `embedding`, `metadata`），而非全量文档。

#### 四、 冲突处理策略
当本地版本与远端版本发生冲突（如多端同时修改同一记忆）：

1.  **乐观锁机制**
    *   在 Supabase 表结构中设置 `version` 字段。Upsert 时附带条件：`WHERE version = local_version - 1`。
2.  **冲突回退与合并**
    *   若更新行数为 0，说明远端已被其他端更新，触发冲突。
    *   **解决策略**：拉取远端最新数据，采用“最后写入胜出（LWW）”或针对特定字段进行三向合并（本地旧版、本地新版、远端版）。对于记忆脑，通常采用保留时间戳最新的版本，并将冲突版本存入 `conflict_log` 表供人工介入。

#### 五、 配置生效与验证机制（强制闭环）
针对“配置修改后未生效”的坑，实施严格的验证流：

1.  **配置中心化与读取点同步**
    *   新增同步配置（如 `SYNC_DEBOUNCE_MS`, `CONFLICT_STRATEGY`）必须同时更新：本地环境变量、Supabase `app_config` 表、以及同步引擎内的内存常量。
2.  **修改即验证**
    *   配置变更后，立即向 Supabase 发送一次测试 Ping（带最新配置标识），若远端未返回预期标识，则同步引擎熔断并告警。

---

### 方案执行流推演

1.  **监听触发**：本地多线程生成结果 -> 串行队列加锁写入本地文件 -> Watcher 检测到完整变更。
2.  **哈希计算**：比对本地 `content_hash` 与本地索引基线 -> 发现差异 -> 推入同步队列。
3.  **预处理**：若需 B 模型处理 -> 设 300s timeout -> 生成结果跳过 reasoning 占比检测 -> 生成最终 payload。
4.  **远端同步**：执行带版本号的 `upsert` -> 若成功，更新本地基线版本；若失败，触发冲突拉取与 LWW 裁决。
5.  **配置校验**：每次同步前读取配置，变更后立即自测验证生效性。
