# 任务类型: eng

设计一个链式推演机制的引擎，核心在于**状态机的闭环管理**与**数据的版本化持久化**。针对一个核心议题拆分为3-5轮递进任务，且要求上游输出作为下游输入，并支持断点续跑，以下是完整的架构设计方案。

---

### 一、 核心数据结构设计

要实现断点续跑，必须将任务执行的无状态过程转化为有状态的实体存储。我们需要定义三个核心模型：

#### 1. 推演会话
代表一次完整的议题推演生命周期。
```json
{
  "session_id": "sess_001",
  "topic": "如何评估AI大模型在金融风控领域的商业落地价值",
  "total_rounds": 4,
  "current_round": 2,
  "status": "RUNNING", // CREATED, RUNNING, PAUSED, FAILED, COMPLETED
  "created_at": "2023-10-27T10:00:00Z"
}
```

#### 2. 轮次任务节点
代表每一轮的具体执行任务。
```json
{
  "task_id": "task_002",
  "session_id": "sess_001",
  "round": 2,
  "status": "SUCCESS", // PENDING, RUNNING, SUCCESS, FAILED, SKIPPED
  "input_data_ref": "storage://sess_001/round_1/output.json", // 上一轮的输出引用
  "output_data_ref": "storage://sess_001/round_2/output.json",
  "error_msg": null,
  "retry_count": 0,
  "started_at": "2023-10-27T10:05:00Z",
  "finished_at": "2023-10-27T10:06:30Z"
}
```

---

### 二、 任务依赖图设计

虽然3-5轮是线性递进，但为了引擎的健壮性，应当采用**有向无环图（DAG）**的思想来设计依赖关系。我们将每一轮的输入输出通过“数据引用”进行解耦。

#### 1. 依赖图拓扑结构
对于3-5轮的递进任务，图结构表现为单向链表式DAG：
```text
[Round 1: 议题拆解] 
       │ (输出: 核心子问题列表)
       ▼
[Round 2: 维度扩展] 
       │ (输出: 各子问题的深度分析及数据支撑)
       ▼
[Round 3: 逻辑融合] 
       │ (输出: 冲突点排查与综合推演结论)
       ▼
[Round 4: 结论沉淀] 
         (输出: 最终结构化报告)
```

#### 2. 上下文传递机制
上一轮输出作为下一轮输入，有两种常见模式：
*   **严格透传模式**：Round 2 的完整 JSON 输出直接作为 Round 3 的 `input`。
*   **上下文累积模式**：Round 2 的输出不仅包含自身结果，还包装了 Round 1 的结果，形成滚动上下文。推荐此模式，因为LLM在推演时往往需要回顾全局。

**依赖解析逻辑**：
引擎在调度时，执行 Round N 的前置条件为：
1. `task_N.status == PENDING`
2. `task_{N-1}.status == SUCCESS`
3. `task_{N-1}.output_data_ref` 指向的存储对象存在且可读。

---

### 三、 断点续跑机制设计

断点续跑的核心逻辑是：**引擎重启或任务失败恢复时，能够从持久化存储中读取 Session 状态，并找到第一个断点任务继续执行。**

#### 1. 状态机流转设计
每个 Task 节点的状态流转必须严格遵循以下规则：
*   `PENDING` -> `RUNNING` (引擎接管，开始执行)
*   `RUNNING` -> `SUCCESS` (执行完毕，输出已落盘)
*   `RUNNING` -> `FAILED` (执行异常，记录 error_msg)
*   `FAILED` -> `RUNNING` (重试机制触发)

#### 2. 断点探测算法
当引擎启动或收到恢复指令时，执行以下逻辑：

```python
def resume_session(session_id):
    session = db.get_session(session_id)
    if session.status in ["COMPLETED", "RUNNING"]:
        return
        
    tasks = db.get_tasks_by_session(session_id)
    
    # 1. 清理脏数据：将上次崩溃时处于 RUNNING 状态的任务重置为 PENDING
    for task in tasks:
        if task.status == "RUNNING":
            task.status = "PENDING"
            db.update_task(task)
            
    # 2. 寻找断点：第一个未成功的任务
    breakpoint_task = None
    for task in sorted(tasks, key=lambda x: x.round):
        if task.status != "SUCCESS":
            breakpoint_task = task
            break
            
    if breakpoint_task:
        # 3. 校验输入依赖：确保上一轮的输出存在
        if breakpoint_task.round > 1:
            prev_task = get_task(session_id, breakpoint_task.round - 1)
            if not storage.exists(prev_task.output_data_ref):
                raise Exception("上一轮输出数据丢失，无法续跑")
                
        # 4. 重新投递断点任务
        engine.submit(breakpoint_task)
```

#### 3. 任务执行器的幂等性保证
为了安全地断点续跑，任务执行器（Executor）必须实现幂等性：
*   **输出隔离**：每次重试时，输出文件带版本号（如 `round_2_output_v1.json`），成功后才将最新版本的引用写回 Task 记录。避免读到写了一半的脏数据。
*   **资源预处理**：Executor 启动时，先检查本次任务的预期输出是否已经存在且完整，若完整则直接标记 SUCCESS，不重复执行（适用于超时导致的假死恢复）。

---

### 四、 引擎执行主循环

结合以上设计，引擎的核心工作流如下：

1.  **初始化**：接收核心议题，创建 Session 和 3-5 个 PENDING 状态的 Task 记录，配置好依赖图。
2.  **调度**：Scheduler 扫描 PENDING 任务，检查其前置依赖是否 SUCCESS。
3.  **执行**：
    *   将 Task 置为 RUNNING。
    *   从存储中拉取上一轮的 `output_data_ref`。
    *   调用推演模型（如 LLM API）。
    *   将推演结果写入存储，生成新的 `output_data_ref`。
    *   将 Task 置为 SUCCESS。
4.  **推进**：更新 Session 的 `current_round`，触发下一轮 PENDING 任务。
5.  **异常处理**：
    *   若 API 超时或报错，Task 置为 FAILED。
    *   触发重试策略（如指数退避，最多3次）。
    *   若重试耗尽，Session 状态置为 PAUSED，等待人工介入或断点续跑指令。
6.  **完成**：最后一轮 SUCCESS 后，Session 状态置为 COMPLETED。

### 五、 高级优化考量

1.  **分支推演支持**：在某些轮次（如第3轮逻辑融合），可能需要对比两种不同的推演路径。可以将依赖图设计为 1->2->(3a & 3b)->4。通过图结构可以轻松支持这种分叉与汇聚。
2.  **人工介入**：在断点续跑时，允许人工修改某一轮的 `output_data_ref`（人工修正大模型的幻觉），然后从该轮开始继续自动推演。这要求引擎提供一个 "Override and Resume" 的 API。
3.  **缓存与成本控制**：如果议题未变，重启时不希望重跑已经成功的轮次。基于状态机的设计天然支持这一点，只有 FAILED 或 PENDING 的任务才会被重新调度。

通过**“DAG依赖图 + 存储引用解耦 + 状态机断点探测 + 幂等执行器”**这一套组合拳，可以构建出一个高可用、可观测、且支持优雅断点续跑的链式推演引擎。
