# V7.5 方舟效能引擎：多线程 API 调用 → 串行后处理的锁机制方案

## 0. 结论先行

不能只用一把 Redis 锁，也不能只依赖数据库行锁。  
必须组合使用：

1. **任务级分布式锁**：保证同一 `task_id` 的后处理只有一个线程在跑  
2. **原子剩余计数器**：保证“所有 API 调用都完成”这个条件只被触发一次  
3. **数据库状态 CAS**：保证任务状态只能按状态机单向演进，且带 `lock_token` 防“锁过期后的旧线程污染”  
4. **幂等键**：保证同一回调、同一后处理、同一终态写入只生效一次  
5. **模型级原子熔断计数**：保证每个模型独立熔断、独立降级链，不因全局锁串扰

这正好对应“阴阳自衡”架构：  
**阳轨** = 多线程并发调 API，无锁推进；  
**阴轨** = 后处理串行收敛，严格状态演进；  
**锁** = 阴阳转换的制度闸门。

---

## 1. 问题模型：竞态到底在哪

多线程 API 调用完成后，多个线程可能同时进入后处理，产生竞态：

- 线程 A 和线程 B 都发现“所有 API 都完成了”
- 两个线程同时做后处理
- 后处理同时更新任务状态，可能造成：
  - 重复写结果
  - 旧结果覆盖新结果
  - 状态回退
  - 终态不一致

因此需要一套**“分布式锁 + 原子状态更新 + 幂等保护”**的完整机制。

---

## 2. 任务状态机

```
PENDING
   │ 提交
   ▼
RUNNING         ← 多线程并发调用 API
   │ 剩余调用数 DECR 到 0
   ▼
POST_RUNNING    ← 串行后处理中
   │ 后处理完成
   ▼
COMPLETED / PARTIAL / DEGRADED / FAILED
```

终态不可逆。  
重试必须使用新的 `task_id`，或显式走重试状态机，不能覆盖终态。

---

## 3. 锁体系总览

| 机制 | Key / 对象 | 作用 | 类型 |
|---|---|---|---|
| 任务后处理锁 | `lock:task:{task_id}:post` | 串行后处理互斥 | Redis `SET NX PX` |
| fencing token | `lock:token:seq` | 防止锁过期后旧线程继续写 | Redis `INCR` |
| 完成屏障 | `counter:task:{task_id}:remaining` | 判断所有 API 调用完成 | Redis `DECR` |
| 回调幂等 | `idem:call:{task_id}:{model_id}` | 防止重复/迟到回调 | Redis `SETNX` |
| 任务状态 CAS | `task_state` 表 | 状态权威 | DB `UPDATE ... WHERE` |
| 模型熔断计数 | `model:{model_id}:stats` | 独立熔断、独立降级 | Redis Lua 原子操作 |

## 4. 关键实现

### 4.1 任务级分布式锁 + fencing token

不能只用“唯一 owner”做锁，还要带 **fencing token**。  
否则锁过期后，旧线程还在跑，新线程拿到锁，旧线程最终写入时可能覆盖新线程。

```python
import redis
import uuid
import time
import random

r = redis.Redis(host="...", decode_responses=True)

LOCK_LEASE_MS = 30_000
LOCK_WAIT_MS = 5_000

def acquire_post_lock(task_id: str, owner: str, lease_ms: int = LOCK_LEASE_MS, wait_ms: int = LOCK_WAIT_MS):
    key = f"lock:task:{task_id}:post"
    deadline = time.monotonic() + wait_ms / 1000

    while time.monotonic() < deadline:
        token = r.incr("lock:token:seq")  # fencing token
        value = f"{owner}:{token}"

        if r.set(key, value, nx=True, px=lease_ms):
            return token

        time.sleep(0.02 + random.random() * 0.03)

    return None


def renew_post_lock(task_id: str, owner: str, token: int, lease_ms: int = LOCK_LEASE_MS):
    key = f"lock:task:{task_id}:post"
    value = f"{owner}:{token}"

    lua = """
    if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('PEXPIRE', KEYS[1], ARGV[2])
    else
        return 0
    end
    """
    return r.eval(lua, 1, key, value, lease_ms)


def release_post_lock(task_id: str, owner: str, token: int):
    key = f"lock:task:{task_id}:post"
    value = f"{owner}:{token}"

    lua = """
    if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('DEL', KEYS[1])
    else
        return 0
    end
    """
    return r.eval(lua, 1, key, value)
```

> 注意：`release_post_lock` 必须用 Lua 比较 value，不能直接 `DEL`，否则可能删掉新持有者的锁。

### 4.2 原子完成屏障

每个 API 调用线程完成后，必须做一次原子 `DECR`。

只有 `DECR` 返回 `0` 的那个线程，才有资格触发后处理。

```python
def on_call_finished(task_id: str, model_id: str, ok: bool, result: dict, degraded: bool = False):
    call_idem_key = f"idem:call:{task_id}:{model_id}"

    # 幂等：同一个模型回调只处理一次
    if not r.set(call_idem_key, "1", nx=True, ex=24 * 3600):
        return

    # 保存单个调用结果
    r.set(f"call_result:{task_id}:{model_id}", json.dumps(result), ex=24 * 3600)

    # 更新模型独立计数/熔断
    update_model_stats(model_id, ok)

    # 原子完成屏障
    counter_key = f"counter:task:{task_id}:remaining"
    remaining = r.decr(counter_key)

    if remaining == 0:
        maybe_post_process(task_id)
    elif remaining < 0:
        # 说明有迟到/重复回调，已经有人触发过后处理
        log_duplicate_late(task_id, model_id)
```

### 4.3 数据库状态 CAS

Redis 锁只是“闸门”，真正权威状态在数据库。  
后处理开始时，必须用 CAS 把状态从 `RUNNING` 改成 `POST_RUNNING`，并写入 `lock_owner` 和 `lock_token`。

```sql
UPDATE task_state
SET status = 'POST_RUNNING',
    lock_owner = %s,
    lock_token = %s,
    version = version + 1,
    updated_at = NOW()
WHERE task_id = %s
  AND status = 'RUNNING'
  AND lock_token IS NULL;
```

如果影响行数为 0，说明已有另一个线程开始了后处理，当前线程直接退出。

后处理完成时，必须再次用 CAS 写终态：

```sql
UPDATE task_state
SET status = %s,
    result = %s,
    lock_owner = NULL,
    lock_token = NULL,
    version = version + 1,
    updated_at = NOW()
WHERE task_id = %s
  AND status = 'POST_RUNNING'
  AND lock_owner = %s
  AND lock_token = %s;
```

只有 `lock_owner` 和 `lock_token` 都匹配，才能写终态。  
这样即使 Redis 锁过期、新线程接管，旧线程也无法覆盖状态。

### 4.4 后处理触发函数

```python
def maybe_post_process(task_id: str):
    owner = str(uuid.uuid4())

    token = acquire_post_lock(task_id, owner)

    if token is None:
        # 另一个线程正在后处理，或锁还没过期，交给持锁者/看护者
        return

    try:
        # 数据库 CAS：只有一个线程能真正开始后处理
        if not try_start_post_processing(task_id, owner, token):
            return

        # 如果后处理可能超过锁租期，必须启动续约
        stop_event = threading.Event()
        t = threading.Thread(target=renew_loop, args=(task_id, owner, token, stop_event), daemon=True)
        t.start()

        try:
            result = do_serial_post_processing(task_id)
            final_status = "COMPLETED" if not degraded else "DEGRADED"
            finalize_task(task_id, owner, token, final_status, result)
        finally:
            stop_event.set()
    finally:
        release_post_lock(task_id, owner, token)
```

### 4.5 模型级独立熔断与降级链

每个模型独立计数，独立熔断，独立降级链。  
用 Redis Lua 保证原子性，不需要跨模型锁。

```python
MODEL_TIMEOUT_SEC = {
    "b_turbo": 300,  # B模型turbo
    "a": 600,        # A模型
}

MODEL_DEGRADATION_CHAIN = {
    "a": ["b_turbo", "cache"],
    "b_turbo": ["cache"],
}

MODEL_STATS_LUA = """
local key = KEYS[1]
local ok = ARGV[1]
local now = tonumber(ARGV[2])
local threshold = tonumber(ARGV[3])
local cooldown = tonumber(ARGV[4])

redis.call('HINCRBY', key, 'total', 1)

if ok == '1' then
    redis.call('HINCRBY', key, 'success', 1)
    redis.call('HSET', key, 'consec_fail', 0)
else
    redis.call('HINCRBY', key, 'fail', 1)
    local cf = redis.call('HINCRBY', key, 'consec_fail', 1)
    local opened = tonumber(redis.call('HGET', key, 'opened_until') or '0')

    if cf >= threshold and opened < now then
        redis.call('HSET', key, 'opened_until', now + cooldown)
    end
end

return 1
"""
```

调用 API 前检查熔断：

```python
def is_circuit_open(model: str) -> bool:
    opened_until = r.hget(f"model:{model}:stats", "opened_until")
    return int(opened_until or 0) > time.time()
```

降级链：

```python
def call_with_degradation(task_id: str, primary_model: str, payload: dict):
    chain = [primary_model] + MODEL_DEGRADATION_CHAIN[primary_model]

    for model in chain:
        if model == "cache":
            result = get_cache_result(task_id)
            on_call_finished(task_id, primary_model, True, result, degraded=True)
            return

        if is_circuit_open(model):
            continue

        try:
            result = call_ark_api(model, payload, timeout=MODEL_TIMEOUT_SEC[model])
            validate_response(model, result)
            on_call_finished(task_id, primary_model, True, result, degraded=(model != primary_model))
            return
        except Exception as e:
            update_model_stats(model, False)
            log_error(model, e)

    on_call_finished(task_id, primary_model, False, {"error": "all models failed"})
```

### 4.6 API 调用直连，避免 ProxyError

历史坑：全局代理会导致 `requests` 调用火山引擎 API 报 `ProxyError`。  
统一用 `urllib` 直连，不引入 `requests`。

```python
import urllib.request
import json

def call_ark_api(model: str, payload: dict, timeout: int):
    url = ARK_API_URL[model]

    body = json.dumps(payload).encode("utf-8")
    req = urllib.request.Request(url, data=body, headers={"Content-Type": "application/json"})

    # 显式清空代理，避免环境变量全局代理
    opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))

    with opener.open(req, timeout=timeout) as resp:
        return json.loads(resp.read().decode("utf-8"))
```

> 如果某处必须用 `requests`，必须显式传 `proxies=None`。

### 4.7 B 模型 Responses API 空 content 校验

历史坑：B 模型用 Responses API 格式时，`output_tokens` 可能全耗在 reasoning 上，正式回复 `content` 为空。  
后处理前必须校验 `content` 非空，否则按失败处理，不能进入主流程。

```python
def validate_response(model: str, resp: dict):
    if model == "b_turbo":
        content = resp.get("content")
        if not content:
            raise EmptyResponseError(f"b_turbo response content empty: {resp}")
```

### 5.4 串行后处理

- 获取 Redis 后处理锁
- 数据库 CAS `RUNNING -> POST_RUNNING`
- 执行后处理
- 数据库 CAS `POST_RUNNING -> COMPLETED/DEGRADED/FAILED`
- 释放 Redis 后处理锁

### 5.5 看护者 Reaper

防止线程崩溃、锁过期、回调丢失：

```python
def reap_stale_tasks():
    rows = SELECT * FROM task_state
           WHERE status IN ('RUNNING', 'POST_RUNNING')
             AND timeout_at < NOW()

    for row in rows:
        # 不抢锁，直接 DB CAS 强制收敛
        UPDATE task_state
        SET status = 'FAILED',
            result = 'timeout',
            lock_owner = NULL,
            lock_token = NULL,
            version = version + 1
        WHERE task_id = %s
          AND status = row.status
          AND version = row.version
```

如果 `RUNNING` 状态但 `remaining <= 0`，Reaper 也要负责重新触发后处理：

```python
def reap_untriggered_post_processing():
    rows = SELECT * FROM task_state
           WHERE status = 'RUNNING'
             AND updated_at < NOW() - INTERVAL '5 seconds'

    for row in rows:
        remaining = r.get(f"counter:task:{row.task_id}:remaining")
        if remaining is not None and int(remaining) <= 0:
            maybe_post_process(row.task_id)
```

## 6. 锁参数与配置

| 配置项 | 建议值 | 说明 |
|---|---|---|
| B 模型 turbo 超时 | 300 秒 | API 调用硬超时 |
| A 模型超时 | 600 秒 | API 调用硬超时 |
| 后处理锁租期 | 30 秒 | 必须大于后处理最大耗时，否则续约 |
| 后处理锁等待时间 | 5 秒 | 获取不到就退出，由持锁者/Reaper 负责 |
| 任务总超时 | 模型超时 + 后处理超时 + 60 秒 | 防止整个任务悬挂 |
| 计数器 TTL | 任务总超时 + 60 秒 | 防止 Redis key 提前消失 |

> 配置修改后，必须同步修改所有读取点，并立即用单测验证生效。  
> 不要硬编码模型超时和锁租期。

## 7. 避坑清单

1. **不要用 requests 调方舟 API**  
   必须用 `urllib` 直连，显式清空代理。

2. **不要用 PID 文件做分布式锁**  
   PID 文件有竞态，历史教训：启动脚本刚写入 PID，引擎读到自己 PID 误判“已有实例”退出。  
   用 Redis/etcd 锁 + lease + fencing token。

3. **不要只依赖 Redis 锁**  
   Redis 锁会过期，必须配合数据库 CAS 和 `lock_token`，防止旧线程覆盖新状态。

4. **不要在后处理中调用外部 API**  
   后处理只做聚合、校验、落库。  
   否则锁长时间占用，容易租约过期，造成锁被接管。

5. **B 模型必须校验 content 非空**  
   不能因为 `output_tokens` 有值就认为成功。

## 8. 验证方案

### 单测：锁互斥

- 20 个线程同时 `acquire_post_lock`，同一时刻只有一个成功。
- 锁过期后，新线程能获取，旧线程 `release_post_lock` 失败。
- 旧线程数据库 CAS 写终态失败。

### 集成测试：多线程调用后处理

- 模拟 3 个 API 调用同时完成。
- 只有一次 `POST_RUNNING` 状态切换。
- 只有一次终态写入。
- 终态结果完整。

### 混沌测试：迟到回调

- 一个调用在剩余计数归零后才返回。
- 回调幂等键拦截，不重复进入后处理。
- 任务终态不被迟到结果覆盖。

---

这套方案把“多线程并发”和“串行后处理”的矛盾，升维为**制度性的阴阳双轨运行**：  
**阳轨无锁并行，阴轨串行收敛，锁是制度闸门，CAS 是法理，fencing token 是身份。**  
竞态没有被简单消除，而是被制度化成了有序的状态演进。
