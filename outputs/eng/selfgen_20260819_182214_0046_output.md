# 任务类型: eng

下面给出**引擎产出三方同步自动化**的设计方案，重点覆盖：**自动触发、幂等性、冲突处理、回读验证、失败避坑**。

---

## 0. 设计原则（来自已有锚点）

- **先潜水，后行动**：每次同步前先查 `sync_ledger` 和目标端现状，不直接写入。
- **用小测试换判断力**：正式全量同步前，先做连通性/权限/配置 hash 小验证。
- **负熵投入**：同步失败/冲突必须写入坑库，作为后续校准的变异来源。
- **配置修改后立即验证**：同步成功 ≠ 配置生效，必须回读验证。

---

## 1. 总体架构

### 1.1 触发源

引擎每次“重大变更”后，生成一个 **Change Manifest**，并写入 Supabase `outbox`：

```json
{
  "change_id": "c_20260607_001",
  "version": 42,
  "config_hash": "sha256:...",
  "artifacts": [
    {
      "path": "rules/engine_config.yaml",
      "generated": true,
      "content_sha256": "sha256:..."
    },
    {
      "path": "docs/engine_changelog.md",
      "generated": true,
      "content_sha256": "sha256:..."
    }
  ]
}
```

> 重大变更定义：版本号递增、`config_hash` 变化、知识库/坑库结构变化，或引擎显式标记 `sync: true`。

### 1.2 同步流程

```text
引擎变更
  -> 写 outbox 表
  -> 定时 poller 拉取
  -> Sync Orchestrator 处理
  -> 写 sync_ledger 状态 pending
  -> 三个 Adapter 同步：
       Gitee：提交代码 / 打 tag
       飞书：上传文件 / 创建文档
       Supabase：写入 Storage / 更新 DB
  -> 全部成功 -> 更新 latest 指针
  -> 回读验证
  -> 写 success / failed / conflict
```

## 2. 幂等性设计

### 2.1 幂等键

每个同步任务使用唯一幂等键：

```text
change_id + artifact_path + dest_type + content_sha256
```

在 `sync_ledger` 表中加唯一约束：

```sql
CREATE TABLE sync_ledger (
  sync_key TEXT PRIMARY KEY,
  change_id TEXT NOT NULL,
  version BIGINT NOT NULL,
  artifact_path TEXT NOT NULL,
  dest_type TEXT NOT NULL, -- gitee | feishu | supabase
  dest_ref TEXT,
  content_sha256 TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending',
  retry_count INT DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE(change_id, artifact_path, dest_type)
);
```

### 2.2 每个目标端的幂等策略

#### Gitee

- 每个变更生成固定 `Change-Id`。
- 提交信息中必须包含：

```text
sync(engine): v42 artifacts

Change-Id: I{c_20260607_001}
Artifact-Hash: sha256:...
```

- 推送前先检查：

```bash
git fetch origin main
git log --grep="Change-Id: I{c_20260607_001}" origin/main --oneline
```

如果已存在，则跳过提交。

- 版本化 tag：

```bash
git tag v{version}
git push origin v{version}
```

tag 不可变，已存在则直接跳过。

#### 飞书

- 上传文件名带版本号：

```text
{artifact_path}.v{version}{ext}
```

例如：

```text
engine_config.yaml.v42.yaml
```

- 上传前先查目标文件夹是否存在同名文件。
- 如果 `sync_ledger` 中已有 `feishu_file_token`，先验证 token 是否有效。
- 有效则复用；无效则重新上传。
- 如果飞书 API 支持 `request_id`，则每次上传都传：

```text
request_id: {sync_key}
```

#### Supabase

- Storage 对象路径使用不可变版本路径：

```text
artifacts/{version}/{artifact_path}
```

- 使用 Supabase Storage 的 `upsert` 模式，重复上传同一路径不会产生新对象。
- DB 层使用 `upsert`：

```sql
INSERT INTO sync_ledger (...)
VALUES (...)
ON CONFLICT (change_id, artifact_path, dest_type)
DO UPDATE SET
  status = EXCLUDED.status,
  dest_ref = EXCLUDED.dest_ref,
  updated_at = now()
WHERE sync_ledger.status <> 'success'
   OR sync_ledger.dest_ref IS DISTINCT FROM EXCLUDED.dest_ref;
```

## 3. 冲突处理方案

### 3.1 核心原则

**引擎 manifest 是权威来源，版本号单调递增。**

不允许“旧版本覆盖新版本”。

### 3.2 版本预检查

同步前必须做：

```sql
SELECT version, content_sha256, last_synced_at
FROM sync_state
WHERE artifact_path = :path;
```

判断逻辑：

| 情况 | 处理 |
|---|---|
| 目标版本 < 新版本 | 允许同步 |
| 目标版本 == 新版本，hash 相同 | 幂等跳过 |
| 目标版本 == 新版本，hash 不同 | 冲突，告警，不覆盖 |
| 目标版本 > 新版本 | 拒绝同步，版本回退 |

### 3.3 Gitee 冲突处理

- 推送 main 分支失败时，先 `fetch`。
- 如果远程有相同 `Change-Id`：跳过。
- 如果远程有手动提交，且没有碰本次产物文件：自动 merge 后推送。
- 如果远程手动提交碰了同一个文件：
  - `generated: true` 的产物：以引擎版本为准，但记录审计日志。
  - `generated: false` 的产物：**不自动覆盖**，创建冲突单。

```bash
git fetch origin main
git merge --ff-only origin/main
# 如果不能 ff-only，说明有分叉
# 检查冲突文件，按上述策略处理
```

### 3.4 飞书冲突处理

- 版本化文件名天然避免大部分冲突。
- 如果同名文件已存在但 `sync_ledger` 无记录：
  - 不覆盖。
  - 记录为 `conflict`，人工确认是重新上传还是沿用已有文件。
- 如果上传导入任务重复执行：
  - 通过 `task_id` 查询导入状态，幂等复用。

### 3.5 Supabase 冲突处理

使用乐观锁 CAS 更新 `latest` 指针：

```sql
UPDATE sync_state
SET version = :new_version,
    content_sha256 = :new_hash,
    last_synced_at = now()
WHERE artifact_path = :path
  AND (version < :new_version OR version IS NULL);
```

如果 `rowcount = 0`，说明版本冲突，拒绝写入。

## 4. 避免“同步成功但没生效”

这是历史最大坑：**配置改完，行为没变。**

所以每次同步后必须**回读验证**：

```text
Gitee：读取远程文件，计算 hash
飞书：读取文件 token 内容，计算 hash
Supabase：读取 Storage 对象 + DB 行，计算 hash
```

三者 hash 必须等于 manifest 中的 `content_sha256`。

如果不一致，则状态标记为：

```text
verification_failed
```

并触发告警，不能算“同步成功”。

> 注意：回读必须从真实读取路径读，不能读缓存。

## 5. 超时与重试

### 5.1 超时预设

| 调用类型 | 超时 |
|---|---|
| Gitee API | 30s |
| 飞书上传 | 120s |
| Supabase Storage | 60s |
| 模型辅助冲突分类：B 模型 turbo | 300s |
| 模型辅助冲突分类：A 模型深审 | 600s |

### 5.2 重试策略

- 指数退避：`1s -> 2s -> 4s`，最多 3 次。
- 重试仍然失败，进入死信队列，不无限重试。
- 每次失败写入坑库：

```sql
INSERT INTO pitfall_log(dest_type, error_code, detail, change_id)
VALUES (:dest_type, :error_code, :detail, :change_id);
```

---

## 6. 飞书连接器避坑

如果飞书上传依赖连接器：

1. 先确认飞书客户端是最新版本。
2. 页面缩放到最大，查找“添加连接器”按钮。
3. 绑定失败时，先检查豆包账号是否已登录。
4. 不要盲目重试，避免消耗配额和超时。

---

## 7. 最终状态机

```text
pending
  -> syncing
  -> success
  -> verification_failed
  -> conflict
  -> dead
```

- `success`：三个目标端都已写入，且回读验证通过。
- `verification_failed`：写入完成但回读 hash 不一致，需要立即处理。
- `conflict`：版本冲突或手动文件冲突，需要人工介入。
- `dead`：重试耗尽，进入死信队列。

---

这套方案的核心是：

> **用版本化写入保证幂等，用 CAS 指针更新保证不覆盖新版本，用回读验证保证配置真正生效。**
