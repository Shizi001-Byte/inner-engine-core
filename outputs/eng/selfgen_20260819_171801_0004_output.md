# 任务类型: eng

# 引擎产物三方同步自动化设计

## 0. 锚定

本设计建立在已确认的锚定之上：

- Guardian-Core 双进程架构：同步协程由守护进程托管，崩溃自动拉起。
- WAL + Snapshot：同步状态、产物清单都走 WAL，崩溃后从 Snapshot 恢复。
- 单向同步：引擎产物是唯一事实源，Gitee / Feishu / Supabase 都是派生目标端。
- 幂等优先：所有同步操作必须有确定性 `sync_id`，重复执行不产生重复提交或重复上传。

本方案只推演这条 ChainTask 链：

```text
本地文件（实）
  -> 变化检测（虚/策略）
  -> 只传差异（实）
  -> 冲突处理（虚/策略）
  -> Supabase 认知池（实）
  -> 同步指标（实）
  -> 策略调优（虚）
  -> 更高效的下一轮同步（返实）
```

---

## 1. 触发条件：重大变更判定

不是每次小改动都触发三方同步。只有满足以下条件才自动触发：

- 产物清单 `artifact_manifest.json` 中 `change_type` 为 `major` / `minor` / `breaking` / `release`；
- 或 `version` 发生主/次版本变化；
- 或显式标记 `important: true`。

触发后进入队列，消费者合并 30 秒内的连续事件为一个同步批次，避免抖动。每个重大变更都必须在最终批次中体现。

---

## 2. 同步总流程

```text
重大变更事件
  -> 读取 WAL 中已提交的产物记录
  -> 与 Snapshot 基线比较，生成 sync_manifest
  -> 计算 delta（只传差异）
  -> 按目标端 fan-out：
       Gitee   adapter
       Feishu  adapter
       Supabase adapter
  -> 每个 adapter 独立幂等执行
  -> 写 sync_state / sync_metrics
  -> 生成同步报告
  -> 更新同步策略
```

三个目标端不要求跨端原子事务，采用“最终一致”：

- 每个目标端独立收敛到同一 `version`；
- 某端失败只补该端；
- 不会因为 Feishu 失败而回滚已经成功的 Gitee 提交。

## 3. 幂等性设计

### 3.1 同步 ID

每个产物、每个目标端、每次变更，生成确定性的 `sync_id`：

```text
sync_id = sha256(artifact_key + ":" + action + ":" + content_hash)
```

删除操作：

```text
sync_id = sha256(artifact_key + ":delete:" + old_version)
```

只要 `sync_id` 相同，重复执行就是同一件事，必须被跳过或覆盖为同一结果。

### 3.2 同步状态表

统一用 Supabase Postgres 存同步状态：

```sql
create table public.sync_state (
  id bigint generated always as identity primary key,
  sync_id text not null,
  artifact_key text not null,
  dest_type text not null check (dest_type in ('gitee','feishu','supabase')),
  dest_key text not null,
  content_hash text not null,
  version text not null,
  action text not null default 'upsert',
  status text not null default 'pending',
  attempts int not null default 0,
  last_error text,
  remote_ref text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique(sync_id, dest_type, dest_key)
);
```

每次同步前：

1. 查 `sync_state`；
2. 如果 `status = success` 且 `content_hash` 一致，则跳过；
3. 如果远端已存在但状态丢失，则 `adopt` 登记，不重复上传；
4. 如果状态是 `failed`，走重试。

并发控制：

```sql
select pg_advisory_xact_lock(hashtext(sync_id));
```

防止同一产物同一目标端被并发同步。

## 4. 只传差异：Delta 计算

同步引擎不扫描全量文件，而是读取引擎输出的 `artifact_manifest.json`：

```json
{
  "version": "1.4.0",
  "change_type": "minor",
  "files": [
    {
      "path": "engine-output/app.zip",
      "sha256": "abc123...",
      "action": "upsert"
    },
    {
      "path": "engine-output/old.csv",
      "sha256": "def456...",
      "action": "delete"
    }
  ],
  "generated_paths": ["engine-output/", "src/generated/"]
}
```

Delta 计算规则：

- `sync_state` 无记录：`create`；
- `sync_state.content_hash` 与本地不一致：`update`；
- 新清单不再包含旧产物：`delete`；
- `sync_state` 已成功且 hash 一致：`skip`。

只有非 `skip` 的文件进入目标端 adapter。

## 5. Gitee 代码提交

### 5.1 策略

- 使用 Gitee token / SSH key，不用交互式登录。
- 只提交 delta 文件，不提交整个仓库。
- 禁止默认 `force push`。

### 5.2 幂等流程

1. `git fetch origin main`
2. 检查 `git log --grep="sync_id=..." origin/main`
   - 如果已存在该 `sync_id`，标记成功并结束。
3. 从 `origin/main` 创建临时分支：

```bash
git checkout -B sync/{sync_id} origin/main
```

4. 应用 delta 文件到工作区。
5. 提交：

```bash
git add {delta_files}
git commit -m "sync {artifact_key} v{version} [sync_id={sync_id}]"
```

6. 推送前再次 fetch，如果远端有更新，则 rebase：

```bash
git fetch origin
git rebase origin/main
```

7. push 到 `main`。

### 5.3 Gitee 冲突处理

| 冲突场景 | 处理方式 |
|---|---|
| 远端领先，但本地可 rebase | 自动 rebase 后推送 |
| rebase 冲突，且冲突文件在 `generated_paths` 内 | 自动取引擎产物版本，继续 rebase |
| rebase 冲突，且冲突文件不是生成文件 | 放弃本次 main 推送，创建 `sync-conflict/{sync_id}` 分支，推送分支，并飞书告警 |
| push 被拒绝（远端刚刚变化） | 重新 fetch + rebase，最多重试 3 次 |
| 同一 `sync_id` 已存在于远端历史 | 直接跳过，登记成功 |

## 6. 飞书文件上传

### 6.1 避坑

- 优先使用飞书服务端 API + `tenant_access_token`，不依赖“连接器扫码绑定”。
- 如果必须使用连接器，先检查飞书客户端是否最新版、账号是否已登录、页面是否缩放到最大。

### 6.2 目录与命名

飞书云空间目录结构：

```text
SyncRoot/
  {artifact_key}/
    {version}/
      {original_name}-{hash8}.{ext}
    latest/
      {original_name}.{ext}
```

- `{version}` 目录只写一次，天然幂等；
- 文件名带 `hash8`，同名即同内容，可快速判断；
- `latest` 是可选指针，用于给人工查看最新版本。

### 6.3 幂等流程

1. 查询 `sync_state`；
2. 如果状态成功且 hash 一致，跳过；
3. 检查飞书目标文件夹：
   - 目标 `{version}` 下已有同名文件且 hash 一致：登记 `file_token` 后跳过；
   - 目标 `{version}` 下已有同名文件但 hash 不一致：说明版本号未变但内容变了，属于冲突，上传到 `_conflicts/{artifact_key}/{timestamp}/`，并告警；
   - 目标不存在：上传。
4. 上传后调用飞书 API 校验 `file_token` 存在，再写 `sync_state`。

### 6.4 超时

- 飞书单文件上传超时：`300s`
- 上传超时后不盲目重试，先查飞书目标文件夹：
  - 如果文件已存在：标记成功；
  - 如果不存在：按退避重试。

## 7. Supabase 存储同步

### 7.1 路径设计

Supabase Storage Bucket 名称：`engine-output`

```text
{artifact_key}/{version}/{original_name}-{hash8}.{ext}
```

同样提供可选 `latest` 指针：

```text
{artifact_key}/latest/{original_name}.{ext}
```

### 7.2 幂等流程

1. 查询 `storage.objects`：

```sql
select metadata
from storage.objects
where bucket_id = 'engine-output'
  and name = '{object_path}';
```

2. 判断：

- 对象不存在：上传；
- 对象存在且 metadata 中 `content_hash` 或路径中 `hash8` 一致：跳过；
- 对象存在但 hash 不一致，且是 `{version}` 路径：不覆盖，上传到 `_conflicts/` 并告警；
- 对象存在但 hash 不一致，且是 `latest` 路径：如果 `sync_state` 显示该 `latest` 是引擎上次创建的，则备份旧对象后覆盖；否则不覆盖，保留人工文件并告警。

3. 上传时携带 metadata：

```json
{
  "sync_id": "...",
  "content_hash": "...",
  "version": "1.4.0"
}
```

4. 成功后写 `sync_state`，同时 upsert 到 `artifact_files` 表。

## 8. 冲突处理总矩阵

| 目标端 | 冲突类型 | 自动处理 | 人工兜底 |
|---|---|---|---|
| Gitee | 远端领先 | rebase | 创建 PR / 告警 |
| Gitee | 非生成文件冲突 | 不自动覆盖 | `sync-conflict` 分支 + 飞书通知 |
| Gitee | 生成文件冲突 | 取引擎版本 | 备份到 `_backup/` |
| Feishu | 同名文件 hash 不一致 | 不覆盖，上传到 `_conflicts/` | 飞书告警 |
| Feishu | `latest` 被人工修改 | 不覆盖 `latest` | 飞书告警 |
| Supabase | `{version}` 路径 hash 不一致 | 不覆盖，上传到 `_conflicts/` | 飞书告警 |
| Supabase | `latest` 被人工修改 | 不覆盖 | 飞书告警 |
| 任意端 | 状态 success 但远端缺失 | 自动重新同步 | 连续失败后告警 |

删除操作统一规则：

- 仅当远端当前文件 hash 等于引擎上次同步 hash 时才删除；
- 如果远端被人工修改过，不删除，移动到 `_conflicts/{artifact_key}/{timestamp}/`。

## 9. 重试与超时

### 9.1 重试策略

- 指数退避：`1min -> 5min -> 30min -> 2h`
- 最大重试次数：`5`
- 每次重试前必须重新执行幂等检查，不能盲目重试。

### 9.2 超时配置

| 环节 | 超时 |
|---|---|
| Gitee fetch / push | 60s |
| Gitee rebase | 120s |
| Feishu 单文件上传 | 300s |
| Supabase 单对象上传 | 120s |
| 整个同步任务 | 600s |
| AI 生成变更摘要（B 模型 turbo） | 300s |
| AI 生成变更摘要（A 模型） | 600s |

AI 摘要生成与同步主流程解耦，不阻塞三方同步。

## 10. 同步指标与策略调优

### 10.1 指标表

```sql
create table public.sync_metrics (
  id bigserial primary key,
  sync_id text not null,
  dest_type text not null,
  artifact_key text not null,
  duration_ms int not null,
  bytes int not null,
  retries int not null default 0,
  conflict_resolved boolean not null default false,
  strategy text not null,
  created_at timestamptz not null default now()
);
```

### 10.2 策略调优

每轮同步后写入 `sync_metrics`，策略调优模块读取：

- 如果 Gitee 频繁 rebase 冲突，则调整同步时段或改为 PR 模式；
- 如果 Feishu 上传频繁超时，则改为分片上传或提前压缩；
- 如果 Supabase `latest` 频繁被人工修改，则关闭 `latest` 自动覆盖，只保留版本目录。

策略配置存储在 `sync_config` 表，调优结果反馈到下一轮同步：

```json
{
  "gitee": {
    "conflict_policy": "rebase_generated_or_pr"
  },
  "feishu": {
    "timeout_ms": 300000,
    "versioned": true
  },
  "supabase": {
    "upsert_latest": true
  }
}
```

---

## 11. 配置修改后必须验证生效

为避免“配置改了但没生效”，所有同步策略统一读取 `sync_config` 表，禁止本地缓存残留。

配置变更后执行：

```text
verify_config()
```

校验内容：

1. 读取 `sync_config` 最新值；
2. 断言所有读取点都使用同一版本配置；
3. 执行一次 `dry_run` 同步；
4. 验证 dry_run 结果符合预期；
5. 返回成功后才允许正式触发下一轮同步。

---

## 12. 最终一致性确认

每轮同步结束后，生成 `sync_report`：

- 每个目标端成功/失败文件数；
- 每个目标端耗时；
- 冲突自动解决数；
- 人工处理项列表；
- 下一轮待补同步项。

该报告写入 Supabase 认知池，作为下一轮策略调优的输入。

这样，Gitee、Feishu、Supabase 三方最终会稳定收敛到同一个引擎产物版本，且不会因重复触发、超时重试或远端人工修改而产生重复提交或数据覆盖。
