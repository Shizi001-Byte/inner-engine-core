# 任务类型: eng

## 结论先行

多线程 API 调用本身可以并发；问题出在“后处理”对共享 state 的读-改-写。  
V7.5 的状态在 Redis/etcd 这类共享存储上，且两个引擎实例都可能执行后处理，所以必须用**分布式锁 + 原子状态更新 + 幂等保护**。

锁的覆盖范围必须严格控制：

- **外部 API 调用期间不持锁**，否则多线程退化为串行，且 300s/600s 超时会拖死锁。
- **锁只保护后处理临界区**：计数更新、熔断状态更新、降级链状态更新、结果状态写入。

---

## 1. 竞态推演

假设两个线程同时完成同一个 `model_id` 的 API 调用，进入后处理：

```
线程 A: read state -> task_count = 0
线程 B: read state -> task_count = 0
线程 A: write task_count = 1
线程 B: write task_count = 1
```

最终结果错误，丢失一次计数。

即使使用 Redis `HINCRBY` 解决单一计数，熔断、降级链、`count = task_count + bonus_count` 这类多字段状态仍会不一致：

```
线程 A: 更新 task_count 成功
线程 B: 更新 breaker 失败
→ state 处于中间状态
```

跨两个引擎实例时，单机锁无效，必须使用 Redis 分布式锁。

---

## 2. 锁粒度设计

### 2.1 按模型分片

V7.5 锚定结论：每个模型独立计数、独立熔断、独立降级链。

所以锁 key 设计为：

```
ark:engine:v7.5:lock:model:{official_model_id}
```

同一模型的“后处理”严格串行，不同模型可以并行。

### 2.2 多模型更新时必须排序加锁

如果一次后处理会同时更新多个模型状态，例如降级链从 B 模型切到 A 模型，则必须获取多个锁。

防死锁规则：

1. 将所有 lock key 排序；
2. 按排序顺序逐个加锁；
3. 任何一个锁失败，释放已获取锁，退避重试；
4. 释放时按逆序释放。

## 3. 完整锁机制

### 3.1 Redis 分布式锁

使用 Redis `SET NX PX` 实现租约锁，锁值使用 UUID，释放时用 Lua 校验。

```python
import time
import uuid
import threading


class RedisLock:
    def __init__(self, redis, key, ttl_ms=5000, wait_ms=3000):
        self.redis = redis
        self.key = key
        self.token = str(uuid.uuid4())
        self.ttl_ms = ttl_ms
        self.wait_ms = wait_ms
        self._stop = threading.Event()
        self._thread = None
        self._lost = False

    def acquire(self):
        deadline = time.time() + self.wait_ms / 1000

        while time.time() < deadline:
            ok = self.redis.set(
                self.key,
                self.token,
                nx=True,
                px=self.ttl_ms
            )
            if ok:
                self._lost = False
                self._start_watchdog()
                return True

            time.sleep(0.05)

        raise TimeoutError(f"lock acquire timeout: {self.key}")

    def _start_watchdog(self):
        self._stop.clear()
        self._thread = threading.Thread(target=self._renew, daemon=True)
        self._thread.start()

    def _renew(self):
        # 每 TTL/3 续约一次，防止后处理未完成锁就过期
        while not self._stop.wait(self.ttl_ms / 3 / 1000):
            ok = self.redis.eval(
                """
                if redis.call('get', KEYS[1]) == ARGV[1] then
                    return redis.call('pexpire', KEYS[1], ARGV[2])
                else
                    return 0
                end
                """,
                1,
                self.key,
                self.token,
                self.ttl_ms
            )

            if not ok:
                self._lost = True
                break

    def is_lost(self):
        return self._lost

    def release(self):
        self._stop.set()
        if self._thread:
            self._thread.join(timeout=1)

        self.redis.eval(
            """
            if redis.call('get', KEYS[1]) == ARGV[1] then
                return redis.call('del', KEYS[1])
            else
                return 0
            end
            """,
            1,
            self.key,
            self.token
        )
```

### 3.2 多锁顺序获取

```python
class MultiLock:
    def __init__(self, redis, keys, ttl_ms=5000, wait_ms=3000):
        self.redis = redis
        self.keys = sorted(set(keys))
        self.ttl_ms = ttl_ms
        self.wait_ms = wait_ms
        self.locks = []

    def __enter__(self):
        try:
            for key in self.keys:
                lock = RedisLock(
                    self.redis,
                    key,
                    self.ttl_ms,
                    self.wait_ms
                )
                lock.acquire()
                self.locks.append(lock)
        except Exception:
            self.__exit__(None, None, None)
            raise

        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        for lock in reversed(self.locks):
            lock.release()
        self.locks = []
```

## 4. 后处理临界区

### 4.1 外部 API 调用不持锁

```python
def run_task(task):
    # 外部 API 调用，无锁并发
    resp = call_api_with_timeout(task)

    # 只有后处理阶段持锁
    post_process(task, resp)
```

API 超时仍然按锚定配置：

- B 模型 turbo：300s
- A 模型 pro：600s

锁 TTL 与 API 超时无关，锁 TTL 只保护后处理本身。

### 4.2 后处理伪代码

```python
def post_process(task, resp):
    lock_keys = [
        f"ark:engine:v7.5:lock:model:{task.model_id}"
    ]

    # 如果一次后处理会影响多个模型，例如降级链切换
    for model_id in task.affected_model_ids:
        lock_keys.append(f"ark:engine:v7.5:lock:model:{model_id}")

    with MultiLock(redis, lock_keys, ttl_ms=5000, wait_ms=3000) as locks:
        # 锁续约失败时必须终止，不能继续写
        for lock in locks.locks:
            if lock.is_lost():
                raise LockLostError()

        state_key = f"ark:engine:v7.5:state:model:{task.model_id}"
        processed_key = f"ark:engine:v7.5:processed:{task.model_id}"

        state, version = read_state(state_key)
        next_state = compute_next_state(state, task, resp)

        result = redis.eval(
            """
            if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
                return 'duplicate'
            end

            if redis.call('HGET', KEYS[1], 'version') ~= ARGV[2] then
                return 'conflict'
            end

            redis.call('SADD', KEYS[2], ARGV[1])
            redis.call('HSET', KEYS[1], 'version', ARGV[3], 'data', ARGV[4])

            return 'ok'
            """,
            2,
            state_key,
            processed_key,
            task.task_id,
            version,
            version + 1,
            json.dumps(next_state)
        )

        if result == b'conflict':
            raise StateConflictError()

        if result == b'duplicate':
            return
```

## 5. 状态更新原子性

不能只靠锁，还必须用 Lua 脚本保证“读-改-写”原子性。原因：

- 锁可能因为 GC、网络抖动、Redis 卡顿而过期；
- 旧持锁者恢复后可能继续写；
- 状态版本 CAS 可以拦截这种“旧写者”。

核心要求：

- 所有计数器、熔断器、降级链字段必须一起更新；
- `count` 不冗余存储，读取时计算 `task_count + bonus_count`；
- 如果必须存储 `count`，必须在同一个 Lua 脚本里更新；
- `task_count` 只记真实任务调用；
- `bonus_count` 只记系统自触发调用。

## 6. 失败处理

### 6.1 锁获取失败

不能无限等待，也不能丢弃任务。

建议：

- 等待超时默认 3000ms；
- 超时后进入重试队列；
- 重试次数有限，超过后告警并人工介入。

### 6.2 锁续约失败

说明锁可能已经丢失，必须停止写状态，防止旧写者覆盖新状态。

### 6.3 状态版本冲突

说明有其他后处理已先写入，当前任务需要重新读取状态、重新计算后处理。

### 6.4 幂等

后处理可能因为重试而执行多次，所以必须按 `task_id` 做幂等。

`processed` 集合中的 `task_id` 保留时间至少大于任务最大重试窗口。

---

## 7. 监控与告警

至少上报以下指标：

- `postproc_lock_wait_ms`
- `postproc_lock_acquired_total`
- `postproc_lock_lost_total`
- `postproc_state_conflict_total`
- `postproc_duplicate_total`
- `postproc_duration_ms`

如果 `lock_lost` 或 `state_conflict` 大于 0，必须立即告警，因为说明已经有锁过期或状态异常。

## 8. 替代方案：Redis Stream 串行队列

如果希望彻底避免锁续约和死锁问题，可以采用 Redis Stream 做串行后处理：

1. API 完成后，不直接后处理；
2. 将完成事件写入 `ark:engine:v7.5:postproc:stream:{model_id}`；
3. 每个模型流由单消费者串行消费；
4. 消费时仍然用 Lua 做幂等和原子状态更新。

队列方案天然保证串行，但会引入 at-least-once 投递，所以幂等仍然是必须的。

锁方案和队列方案可以共存：

- 默认用分布式锁；
- 锁压力过大时，切换为 Stream 串行队列；
- 两者都依赖 Redis 作为唯一状态源。
