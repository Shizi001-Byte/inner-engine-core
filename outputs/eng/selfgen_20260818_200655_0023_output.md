# 任务类型: eng

# 自动归档系统设计（可落地）

## 0. 设计约束

- **并发边界**：只有 API 调用阶段允许并发；后处理必须单消费者。
- **状态变更**：所有 `task` 状态更新必须原子化，并带 `version` 做乐观锁仲裁。
- **结果与状态解耦**：API 调用方只写 `classification_results`，绝不直接改 `task.status`。
- **超时分级**：B 模型 turbo 用 300 秒，A 模型用 600 秒。
- **成本模型**：A 模型更贵不是因为它更快，而是因为它占用稀缺紧急调度资源；若计算更重，按 `γ_A` 提高基础价。

---

## 1. 总体架构

```text
任务进入
   │
   ▼
task(status=PENDING, version=1)
   │
   ▼
调度器（选择 A/B 模型）
   │
   ▼
API Caller Pool（可并发）
   │  只写 classification_results
   ▼
classification_results
   │
   ▼
归档消费者（单消费者）
   │  乐观锁 + 版本仲裁
   ▼
task 状态更新 / 文件归档到目录
```

---

## 2. 数据模型

### 2.1 `task`

```sql
CREATE TABLE task (
  task_id       UUID PRIMARY KEY,
  version       INT NOT NULL DEFAULT 1,
  status        TEXT NOT NULL DEFAULT 'PENDING',
  -- PENDING / ARCHIVING / ARCHIVED / FAILED
  source_uri    TEXT NOT NULL,
  archive_root  TEXT NOT NULL,
  category      TEXT,
  tags          JSONB,
  target_path   TEXT,
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`status` 只能由**归档消费者**修改，API 调用方不碰。

### 2.2 `classification_results`

```sql
CREATE TABLE classification_results (
  id          BIGSERIAL PRIMARY KEY,
  request_id  UUID NOT NULL UNIQUE,
  task_id     UUID NOT NULL,
  model_type  TEXT NOT NULL CHECK (model_type IN ('A','B')),
  status      TEXT NOT NULL CHECK (status IN ('SUCCEEDED','FAILED','TIMEOUT')),
  category    TEXT,
  tags        JSONB,
  confidence  NUMERIC,
  raw_payload JSONB,
  error       TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  processed_at TIMESTAMPTZ
);

CREATE INDEX idx_classification_results_task
  ON classification_results (task_id, created_at);
```

API 调用方只向这张表插入数据。

## 3. 核心流程

### 3.1 任务进入

- 插入 `task`，状态为 `PENDING`，`version=1`。
- 调度器根据任务优先级/配置选择 A 或 B 模型。
- 生成 `request_id`，投递到分类调用队列。

### 3.2 并发调用 API

API Caller Pool 可以水平扩容，但只做一件事：调 API，写结果。

- B 模型：客户端 timeout = **300 秒**
- A 模型：客户端 timeout = **600 秒**
- 每次调用使用唯一 `request_id`，超时重试时复用同一个 `request_id`，保证幂等。
- 成功：插入 `status='SUCCEEDED'`，写入 `category/tags/confidence/raw_payload`。
- 超时/失败：插入 `status='TIMEOUT'/'FAILED'`，写入 `error`。

**禁止**在 API 调用阶段修改 `task.status`。

### 3.3 单消费者后处理

归档消费者是唯一的后处理者。

#### 1. 选取结果

消费 `classification_results` 中 `processed_at IS NULL` 且 `status='SUCCEEDED'` 的记录。

仲裁策略：

- 默认优先采用 A 模型结果；
- A 失败则用 B；
- 同模型取 `confidence` 最高者。

如果全部失败，则用 CAS 将任务置为 `FAILED`。

#### 2. 计算目标目录

```text
target_path = archive_root / safe(category) / safe(primary_tag) / task_id.ext
```

完整 `tags` 写入 `task.tags` 和文件元数据。

#### 3. 原子化更新任务状态

先领取任务：

```sql
UPDATE task
SET status      = 'ARCHIVING',
    category    = :category,
    tags        = :tags,
    target_path = :target_path,
    version     = version + 1
WHERE task_id  = :task_id
  AND version  = :expected_version
  AND status   = 'PENDING';
```

如果影响行数为 0，说明版本冲突，必须重新加载任务并仲裁。

#### 4. 幂等写入目标目录

- 先写临时文件，再 `rename` 到目标路径；
- 如果目标文件已存在，且内容 hash 一致，则跳过；
- 如果内容不一致，先备份再覆盖。

这一步天然幂等，支持消费者崩溃后恢复重试。

#### 5. 完成归档

```sql
UPDATE task
SET status  = 'ARCHIVED',
    version = version + 1
WHERE task_id = :task_id
  AND version = :archiving_version
  AND status  = 'ARCHIVING';
```

最后将 `classification_results.processed_at` 置为当前时间。

---

## 4. 一致性保障

- **状态变更原子化**：所有 `task` 更新都使用单条 `UPDATE`，不是先查再改。
- **版本仲裁**：`WHERE version = :expected_version`，冲突就重试，不覆盖别人改动。
- **单消费者**：后处理逻辑只能有一个消费者；API 调用可以并发，但归档目录写入不能并发。
- **高可用**：如果单消费者进程崩溃，用 leader election 或 DB advisory lock 保证同一时刻仍只有一个归档消费者接管。

---

## 5. 超时与失败处理

| 模型 | timeout |
|---|---|
| B（turbo） | 300s |
| A（heavy） | 600s |

- 调用方必须设置 `context.WithTimeout`，不能无限等。
- 超时后记录 `TIMEOUT`，不直接改任务状态。
- 允许重试一次，复用原 `request_id`。
- 归档消费者遇到版本冲突，重新加载后重试；遇到文件写入失败，保留 `ARCHIVING` 状态，等待下一轮重试。

## 6. 配置管理

所有配置统一放在配置中心，代码中只通过 `ConfigReader` 读取，禁止散落硬编码。

配置项至少包括：

- A/B 模型选择规则；
- B 模型 timeout = 300s；
- A 模型 timeout = 600s；
- `archive_root`；
- 目录规则模板；
- 是否启用 tag 子目录；
- A 模型价格系数 `γ_A`。

### 防坑：配置修改后未生效

新增配置时，必须同步修改 `ConfigReader` 和所有读取点。修改后立即用一条 canary 任务验证，确认分类/归档行为发生变化；如果无变化，检查是否有配置读取点遗漏。

## 7. 成本/定价

```text
价格 = 基础价 × 模型系数
```

- B 模型系数：`γ_B`
- A 模型系数：`γ_A`

A 模型更贵不是因为它“更快”，而是因为它占用稀缺的紧急调度资源。如果 A 模型计算更重，则按 `γ_A` 提高基础价。
