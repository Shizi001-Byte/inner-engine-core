# 任务类型: eng

## 推演结论

Supabase 记忆脑的增量同步，本质不是“少传文件”，而是：

> 以 `(file_path, chunk_id, revision)` 为锚点，做本地状态和远端状态的对齐。

没有稳定 `chunk_id`，增量会退化成全量；没有 `revision`，冲突处理就是猜。  
所以方案必须建立在：**稳定 chunk_id + 数据库单调 revision + CAS 写入** 上。

---

## 1. 锚点与表结构

### Supabase 表：只负责存记忆块

```sql
create table memory_chunks (
  file_path   text not null,
  chunk_id    text not null,
  revision    bigint not null default 1,
  content     text not null,
  embedding   vector(1536),
  model       text not null,
  meta        jsonb not null default '{}',
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now(),
  deleted_at  timestamptz,

  primary key (file_path, chunk_id)
);

create index idx_memory_chunks_updated_at
  on memory_chunks(updated_at);
```

关键点：

- `revision` 是数据库侧的单调递增版本号。
- 删除用软删除：`deleted_at` 不为空。
- 删除时也要 `revision = revision + 1`，否则远端删除无法被增量感知。
- 查询记忆时统一 `where deleted_at is null`。

### 本地同步状态：`.sync_state.json`

本地必须保存每个 chunk 上次同步时的状态：

```json
{
  "client_id": "laptop-01",
  "last_pull_at": "2026-01-01T00:00:00Z",
  "chunks": {
    "notes/foo.md::c1": {
      "content_hash": "sha256:...",
      "base_revision": 3,
      "base_deleted": false,
      "local_mtime": 1710000000
    }
  }
}
```

这里的 `base_revision` 就是上次成功同步时远端 `memory_chunks.revision`。  
它是冲突检测的锚点。

---

## 2. 检测本地文件变化

### 2.1 扫描本地文件

- 用 `(mtime, size)` 做快速过滤。
- 文件没变，直接复用上次的 chunk 列表。
- 文件变了，才重新解析分块。

### 2.2 稳定 chunk_id

没有稳定 chunk_id，增量同步必死。

推荐：

1. 文件内显式写 chunk 标记：

```markdown
<!-- chunk_id: c1 -->
这里是第一块记忆。
```

2. 如果没有显式标记，用内容定义分块（CDC），不要用“第 N 段”这种位置型 ID。

### 2.3 计算本地 diff

对每个 chunk 计算 `content_hash = sha256(normalized_content)`，然后和本地 state 对比：

| 情况 | local_action |
|---|---|
| 本地有，state 没有 | `create` |
| 本地有，state 有，hash 不同 | `update` |
| state 有，本地没有 | `delete` |

这样就能做到：**只同步变更的 chunk，而不是整文件。**

---

## 3. 只同步变更部分：CAS 写入

所有写入 Supabase 的操作，必须走 CAS：

```sql
create or replace function sync_upsert_chunk(
  p_file_path text,
  p_chunk_id text,
  p_base_revision bigint,
  p_content text,
  p_embedding vector,
  p_model text,
  p_meta jsonb default '{}'
) returns text
language plpgsql
as $$
declare
  cur_rev bigint;
begin
  select revision into cur_rev
  from memory_chunks
  where file_path = p_file_path and chunk_id = p_chunk_id
  for update;

  -- 远端不存在
  if cur_rev is null then
    if p_base_revision is not null then
      return 'conflict';
    end if;

    insert into memory_chunks(
      file_path, chunk_id, revision, content, embedding, model, meta
    ) values (
      p_file_path, p_chunk_id, 1, p_content, p_embedding, p_model, p_meta
    );

    return 'ok';
  end if;

  -- 远端存在，且 base_revision 匹配，才允许更新
  if cur_rev = p_base_revision then
    update memory_chunks
       set revision = revision + 1,
           content = p_content,
           embedding = p_embedding,
           model = p_model,
           meta = p_meta,
           deleted_at = null,
           updated_at = now()
     where file_path = p_file_path and chunk_id = p_chunk_id;

    return 'ok';
  end if;

  return 'conflict';
end;
$$;
```

删除同理：

```sql
create or replace function sync_delete_chunk(
  p_file_path text,
  p_chunk_id text,
  p_base_revision bigint
) returns text
language plpgsql
as $$
declare
  cur_rev bigint;
  cur_deleted timestamptz;
begin
  select revision, deleted_at into cur_rev, cur_deleted
  from memory_chunks
  where file_path = p_file_path and chunk_id = p_chunk_id
  for update;

  if cur_rev is null then
    if p_base_revision is null then
      return 'ok';
    end if;
    return 'conflict';
  end if;

  if cur_rev = p_base_revision then
    if cur_deleted is null then
      update memory_chunks
         set revision = revision + 1,
             deleted_at = now(),
             updated_at = now()
       where file_path = p_file_path and chunk_id = p_chunk_id;
    end if;

    return 'ok';
  end if;

  return 'conflict';
end;
$$;
```

这样就不会出现“没有 revision，冲突处理靠猜”的问题。

## 4. 冲突检测与处理

### 4.1 先拉远端增量

每次同步先拉远端变更：

```sql
select file_path, chunk_id, revision, content, deleted_at, updated_at
from memory_chunks
where updated_at > ${last_pull_at};
```

游标 `last_pull_at` 使用 Supabase 时间，不要用本地时间。

### 4.2 合并本地 action 和远端 action

| 本地 | 远端 | 处理 |
|---|---|---|
| 无 | 无 | 跳过 |
| create/update | 无 | push 本地 |
| 无 | update | pull 远端 |
| delete | 无 | delete 远端 |
| delete | delete | 只更新状态 |
| update | update（hash 相同） | 只更新状态 |
| update | update（hash 不同） | 冲突 |
| delete | update | 冲突 |
| update | delete | 冲突 |

### 4.3 冲突策略

CAS 返回 `conflict` 后，不能直接覆盖。

推荐默认策略：

1. 先拉当前远端 chunk。
2. 如果远端内容和本地内容 hash 相同，说明只是 base_revision 过期，直接对齐状态。
3. 如果确实双方都改了：
   - 默认进入人工冲突区，写入 `.sync_conflicts/`，不自动覆盖。
   - 如果产品允许 `last-write-wins`，则比较 `local_mtime` 和远端 `updated_at`，赢家用当前远端 revision 作为 `base_revision` 再写一次。
   - 输家必须留档，不能静默丢失。

核心原则：

> 有 revision，LWW 才是明确策略；没有 revision，LWW 就是猜。

## 5. 并发控制：API 返回后是临界区

多线程调用 API 本身不是问题，问题在 API 返回后：

> 多个线程同时尝试进入“串行后处理”临界区，导致共享状态被交错读写。

所以：

- API 调用可以并发。
- API 返回后的 quality gate、CAS 写库、本地 state 更新必须串行。

实现方式：

```python
with ThreadPoolExecutor(max_workers=8) as pool:
    futures = [
        pool.submit(call_embedding_api, chunk)
        for chunk in changed_chunks
    ]

    for future in as_completed(futures):
        post_queue.put(future.result())

# 单线程消费后处理队列
while True:
    item = post_queue.get()
    with item.lock:
        if quality_gate(item):
            cas_write(item)
        update_local_state(item)
```

如果不想用队列，就按 `(file_path, chunk_id)` 加锁。  
**绝对不要在 API 回调里直接写 `sync_state`。**

## 6. 质量门禁与模型差异

### 6.1 不同模型必须有独立质量规则

```python
def quality_gate(item) -> bool:
    if not item.content.strip():
        return False

    if len(item.embedding) != EMBEDDING_DIM:
        return False

    # B 模型(turbo) 的 reasoning 占比 70-82% 是正常特性
    if item.model in config["quality_gate"]["skip_reasoning_ratio_for_models"]:
        return True

    # A 模型才检查 reasoning 占比
    if item.reasoning_ratio > config["quality_gate"]["max_reasoning_ratio_A"]:
        return False

    return True
```

配置示例：

```json
{
  "quality_gate": {
    "skip_reasoning_ratio_for_models": ["B-turbo"],
    "max_reasoning_ratio_A": 0.85
  }
}
```

这样就不会误杀 B 模型，也不会让 A 模型废稿反复重试。

### 6.2 超时按模型配置

```python
API_TIMEOUT = {
    "B-turbo": 300,
    "A": 600,
}

timeout = API_TIMEOUT[model]
```

不要用全局 timeout。  
否则 B 模型可能被误判超时，A 模型可能被过早掐断。

## 7. 配置修改后必须验证生效

历史坑：配置改了，但行为没变。

预防：

- 所有配置只从 `get_sync_config()` 读取。
- 新增配置时必须同步修改读取点。
- 修改后跑冒烟测试：

```python
def test_config_read_point():
    cfg = get_sync_config()
    assert cfg["quality_gate"]["skip_reasoning_ratio_for_models"] == ["B-turbo"]
    assert cfg["api_timeout"]["B-turbo"] == 300
    assert cfg["api_timeout"]["A"] == 600
```

## 8. 落地检查清单

- [ ] `memory_chunks` 表有 `revision` 和 `deleted_at`
- [ ] 所有写入走 RPC CAS，不是裸 `upsert`
- [ ] 本地 state 保存 `base_revision` 和 `content_hash`
- [ ] chunk_id 稳定，优先显式标记
- [ ] 本地 diff 只产生变更 chunk
- [ ] API 调用并发，后处理串行
- [ ] B-turbo 跳过 reasoning 占比检测
- [ ] A 模型超时 600s，B-turbo 超时 300s
- [ ] 配置读取点唯一，修改后立即验证

这套方案的核心就是一句话：

> 用 `(file_path, chunk_id, revision)` 做锚点，用 CAS 做写入，用本地 state 做 diff，只同步变更部分。
