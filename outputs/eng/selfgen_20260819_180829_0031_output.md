# 多模型成本实时监控与自动熔断系统设计

## 0. 避坑基线（先写死原则）

1. **官方 `model_id` 是唯一标识**  
   所有计数、成本、熔断、降级、超时配置，都挂在官方 `model_id` 上。  
   业务方只传 `model_alias`，由模型注册表解析成官方 `model_id`，禁止业务代码拼接模型名。

2. **所有可配置参数从 state 读取**  
   全局常量只做默认值兜底。  
   例如 `fuse_cooldown_override=300` 必须从 state 读，不能硬编码成 120。

3. **计数语义统一**  
   - `task_count`：真实业务任务产生的模型调用次数；补跑/重试也算一次真实调用。  
   - `bonus_count`：系统自触发调用次数，如健康检查、预热、熔断探测。  
   - `count = task_count + bonus_count`。  
   - `tasks_completed` 单独统计，不能与 `count` 混用。  
   - 所有计数加操作必须走统一 `IncrMetric`，禁止裸 `INCR count`。

4. **熔断恢复必须状态机驱动**  
   不能靠零散的 if-else 判断，必须显式维护 `CLOSED / OPEN / HALF_OPEN` 状态。

## 1. 总体架构

```
上游请求
   |
   v
[统一推理入口 / API Gateway]
   |
   v
[Cost Monitor 成本监控]  <---- Redis 实时成本计数
   |
   v
[Circuit Breaker Manager 熔断管理]
   |                     |
   | CLOSED              | OPEN / HALF_OPEN
   v                     v
[Model Client]      [Degradation Router 降级路由]
   |                     |-- fallback 模型
   |                     |-- 降级响应/缓存
   |                     `-- PendingTask Queue 等待队列
   v                          |
[Usage Reporter]         [Replay Scheduler 自动补跑]
   |                          |
   +-------- Redis/DB <-------+
```

核心组件：

| 组件 | 职责 |
|---|---|
| Model Registry | 维护 `model_alias -> official_model_id`、价格、超时时间、模型类型 |
| Cost Monitor | 实时统计每个模型的 token 成本、调用次数，做预算预检 |
| Circuit Breaker Manager | 每个模型独立状态机，阈值触发熔断 |
| Degradation Router | 熔断后选择 fallback 模型、降级响应，或进入等待队列 |
| PendingTask Queue | 记录熔断期间等待补跑的任务 |
| Replay Scheduler | 模型恢复后自动限速补跑等待任务 |
| Config/State Store | 存放所有动态配置和熔断状态 |

## 2. 模型注册表与配置

### Model Registry 字段

```json
{
  "alias": "b-turbo",
  "official_model_id": "doubao-seed-2-1-turbo",
  "model_type": "turbo",
  "provider": "doubao",
  "input_price_per_1k": 0.002,
  "output_price_per_1k": 0.008,
  "timeout_seconds": 300
}
```

另一个模型：

```json
{
  "alias": "a-model",
  "official_model_id": "a-model-2-1-pro",
  "model_type": "pro",
  "provider": "a-provider",
  "input_price_per_1k": 0.003,
  "output_price_per_1k": 0.009,
  "timeout_seconds": 600
}
```

> 避坑：`doubao-seed-2-1-pro` 不能当 `doubao-seed-2-1-turbo` 用。  
> 接入新模型前，必须核对官方文档完整 `model_id`，并在注册表里显式配置。

### 动态配置从 state 读取

例如：

```python
DEFAULT_FUSE_COOLDOWN = 120  # 仅兜底

def get_fuse_cooldown(model_id):
    return int(
        state.hget(f"config:{model_id}", "fuse_cooldown_override")
        or DEFAULT_FUSE_COOLDOWN
    )
```

配置项示例：

```
config:doubao-seed-2-1-turbo:
  cost_limit_per_window: 500
  cost_window_seconds: 3600
  fuse_cooldown_override: 300
  fallback_chain: ["doubao-seed-2-1-light"]
  probe_limit: 5
  probe_success_threshold: 3
  replay_rate_per_second: 10
  max_attempts: 3
```

> 避坑：配置修改后，下一次决策必须立即读到新值。  
> 不能只在启动时加载配置；如用本地缓存，必须订阅 state 变更并失效缓存。

## 3. 实时成本监控与计数

### 3.1 每个模型独立计数

所有 key 都以 `official_model_id` 为维度：

```text
metric:{model_id}:{minute_bucket}
  task_count
  bonus_count
  count
  task_cost
  bonus_cost
  total_cost
  error_count
  timeout_count
  circuit_open_count
```

`minute_bucket` 示例：`202506061430`

通过 Redis Hash 存储，按分钟聚合，查询时用 Lua 滑动窗口求和。

### 3.2 成本计算

```python
def calc_cost(model, usage):
    input_cost = usage.input_tokens / 1000 * model.input_price_per_1k
    output_cost = usage.output_tokens / 1000 * model.output_price_per_1k
    return input_cost + output_cost
```

### 3.3 预算预检 + 实际扣减

为了不让并发请求打穿成本阈值，采用两阶段：

1. **调用前预检**  
   根据请求的 `input_tokens + max_tokens` 估算最大成本 `estimated_cost`。  
   如果当前窗口成本 + 在途预留成本 + 估算成本 > 阈值，则直接拒绝或降级。

2. **调用后实际扣减**  
   拿到真实 usage 后计算实际成本，释放预留，并累加实际成本。

```python
def before_call(model, task):
    estimated_cost = estimate_max_cost(model, task)
    ok = redis.eval(reserve_budget_lua,
                    keys=[model.official_model_id],
                    args=[estimated_cost, cost_limit])
    if not ok:
        circuit_manager.open(model, "cost_limit_precheck")
        return degrade_or_queue(task, model)
    return call_model(task, model)


def after_call(model, task, usage):
    actual_cost = calc_cost(model, usage)
    release_reservation(model, task.estimated_cost, actual_cost)
    incr_metric(model, task_type=task.task_type, count=1, cost=actual_cost)

    if window_total_cost(model) > cost_limit:
        circuit_manager.open(model, "actual_cost_limit")
```

> 避坑：所有计数加操作必须在同一个原子脚本里完成，保证 `count = task_count + bonus_count`，不会出现 `count=666` 但 `tasks_completed=79` 的失真。

## 4. 熔断状态机

每个模型独立维护：

```text
CLOSED -> OPEN -> HALF_OPEN -> CLOSED
              ^                  |
              |------------------|
```

| 当前状态 | 触发条件 | 动作 |
|---|---|---|
| CLOSED | 成本超限 / 错误率超限 / 超时率超限 | 置为 OPEN，记录 `opened_at`、`reason`、`cooldown_until` |
| OPEN | 冷却时间到期 | 置为 HALF_OPEN，允许少量探测请求 |
| HALF_OPEN | 探测成功数达到阈值，且成本未超限 | 置为 CLOSED，启动自动补跑 |
| HALF_OPEN | 任意探测失败，或成本再次超限 | 重新置为 OPEN，重置冷却时间 |

### 熔断状态存储

```text
cb:{model_id}:
  state: CLOSED
  reason: ""
  opened_at: 0
  cooldown_until: 0
  probe_success: 0
  probe_fail: 0
  config_version: 12
```

冷却时间必须从 state 读取：

```python
def open_circuit(model, reason):
    cooldown = get_fuse_cooldown(model.official_model_id)
    cb.state = "OPEN"
    cb.opened_at = now
    cb.cooldown_until = now + cooldown
    cb.reason = reason
```

## 5. 降级策略

熔断期间，请求进入 Degradation Router：

### 5.1 同步降级

- 优先使用 fallback 模型。  
  fallback 链来自 state，例如：

  ```text
  fallback_chain: ["doubao-seed-2-1-light", "other-provider-model"]
  ```

- fallback 模型也有自己的独立熔断器和计数器。  
  如果 fallback 也熔断，继续尝试下一个。

- 如果业务允许，可以返回缓存结果或固定降级响应。

### 5.2 异步降级：进入等待队列

如果任务必须由原模型执行，或 fallback 全部不可用，则进入等待队列：

```text
pending_tasks:{model_id}
```

任务字段：

```json
{
  "task_id": "uuid",
  "idempotency_key": "business-key",
  "model_id": "doubao-seed-2-1-turbo",
  "payload": {},
  "trace_id": "xxx",
  "enqueue_time": 1710000000,
  "attempts": 0,
  "status": "PENDING"
}
```

等待队列必须持久化，不能放内存。  
可用 Redis Stream + AOF，或 Kafka/RocketMQ；强可靠场景建议 MySQL 事务写 outbox 再投递 MQ。

## 6. 恢复后自动补跑

### 6.1 触发时机

当熔断器从 `HALF_OPEN` 转为 `CLOSED` 时，启动 Replay Scheduler。

### 6.2 补跑流程

```python
def replay_pending_tasks(model_id):
    while True:
        if circuit_manager.is_open(model_id):
            break

        if not cost_monitor.reserve_budget(model_id):
            circuit_manager.open(model_id, "cost_limit_replay")
            break

        task = queue.claim(model_id, rate_limit=config.replay_rate)
        if task is None:
            break

        try:
            result = model_client.call(model_id, task)
            task.status = "COMPLETED"
            mark_completed(task, result)
        except Exception:
            task.attempts += 1
            if task.attempts >= max_attempts:
                task.status = "DLQ"
            else:
                task.status = "PENDING"
                task.next_retry_time = now + backoff(task.attempts)
```

### 6.3 防抖与幂等

- 补跑使用 `task_id` 做唯一键，避免重复执行。
- 如果补跑过程中再次触发熔断，立即停止，剩余任务继续留在队列。
- 补跑也要限速，避免恢复瞬间打爆模型成本。

> 注意：补跑是一次真实模型调用，所以会增加 `task_count` 和 `total_cost`；但 `tasks_completed` 只在任务成功时 +1。这不是计数 bug，是语义明确。

## 7. 实时监控与告警

监控面板至少包含：

- 每个模型的 `total_cost` 实时趋势
- 每个模型的 `task_count` / `bonus_count` / `count`
- 熔断状态 `CLOSED / OPEN / HALF_OPEN`
- 等待队列深度
- 补跑速度和成功率
- 错误率、超时率

告警规则：

- 成本达到阈值的 80% 时预警
- 熔断打开时立即告警
- 等待队列积压超过阈值时告警
- 补跑失败率过高时告警

## 8. 避坑检查清单

| 历史坑 | 本系统对策 |
|---|---|
| B 模型型号错配 | 业务只传 alias，注册表解析官方 `model_id`；CI 校验模型类型，pro/turbo/light 不可混用 |
| 熔断冷却配置不生效 | 所有冷却时间从 state 读，全局常量仅默认值；配置修改后立即验证 |
| 计数语义混乱 | `task_count`、`bonus_count`、`count` 分开维护，统一 `IncrMetric`，`count=task+bonus` |
| API 调用超时 | 每个模型在注册表里配置 `timeout_seconds`，B turbo 300 秒，A 模型 600 秒；超时计入错误率并可能触发熔断 |

---

## 9. 结语

这个系统本质上是一个“负熵输入”控制环：

- 实时感知成本熵增；
- 通过熔断、降级、队列、补跑，快速恢复系统有序性；
- 每个模型独立闭环，避免单一模型失控拖垮全局；
- 所有配置从 state 读取，避免“改不生效”的隐性熵增。

这样就能让多模型系统在成本、稳定性和服务质量之间保持低功能熵的稳定运行。
