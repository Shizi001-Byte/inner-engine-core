# 任务类型: eng

先给结论：**不要做整文件覆盖同步，也不要做纯文件级 diff；用“内容寻址块 + 版本 CAS + 回读校验”**。  
也就是把本地记忆文件切成语义块，每个块有内容哈希和版本号；同步只传变化的块；冲突用版本号检测，用“保留双方”兜底。

---

## 1. 同步模型：把记忆脑当成状态机

每个记忆块是一个状态：

```text
block_key -> chunk_id -> rev
```

- `block_key`：稳定语义标识，例如 `notes/project.md##Context`
- `chunk_id`：块内容的 SHA-256，内容变了 chunk_id 就变
- `rev`：版本号，每次成功更新 +1

本地维护一份 `.sync/manifest.json`，记录每个 block_key 最近同步时的 `base_rev`。  
云端 Supabase 是权威状态机，本地是工作副本。

---

## 2. 检测本地文件变化

本地需要一个轻量 daemon/CLI，例如 `memory-sync watch`：

- 启动时全量扫描 `~/memory-bank`
- 运行时用 `chokidar` / `fs.watch` / `watchdog` 监听
- 事件触发后 debounce 500ms，防止编辑器中间态
- 快速对比 `mtime + size`，变了才对文件重新哈希
- 和本地 manifest 比对，生成增量块：

```text
added/changed: { block_key, chunk_id, content, base_rev }
deleted:       { block_key, deleted: true, base_rev }
```

**避坑：新增记忆目录后，必须同步修改读取点并执行 `memory-sync sync --check`，否则 watcher 不会监听新目录。**

---

## 3. 只同步变更部分

### 切块规则

- Markdown：按 `##` 标题分块，`block_key = file_path#heading`
- JSON：按顶层 key 分块，`block_key = file_path#key`
- 不适合切块的文件：退化成整文件一块

### 上传增量

假设本地有一个块从旧内容变成新内容：

1. 计算新块的 `chunk_id = sha256(new_content)`
2. 写入内容表 `memory_chunks`：

```sql
insert into memory_chunks (chunk_id, content, content_hash)
values ($1, $2, $1)
on conflict (chunk_id) do nothing;
```

3. 更新映射表 `memory_blocks`，用 CAS 防止覆盖：

```sql
update memory_blocks
set chunk_id = $2,
    rev = rev + 1,
    updated_at = now(),
    updated_by = $3
where block_key = $1
  and rev = $4;   -- $4 是本地 base_rev
```

如果 `rowcount = 0`，说明云端版本已经不是本地基于的版本，进入冲突处理。

- 批量上传，每批 100 个块
- Supabase RPC 调用设置 timeout：**轻量 manifest 请求 60s，批量上传 300s**
- 同步完成后必须回读验证：查询云端 `content_hash` 和本地对比，不一致就重试

---

## 4. 冲突处理

冲突本质：

> 同一个 block_key，本地和云端从同一个 `base_rev` 各自发生了不同变化。

### 自动合并策略

按顺序处理：

1. 不同 block_key 的变化 → 直接都保留
2. 同一个 block_key，只有一侧变化 → 取变化侧
3. 同一个 block_key，两侧都变化：
   - Markdown：尝试 `git merge-file` 三路合并
   - JSON：不同 key 深合并；数组取并集；对象递归合并
   - 标量冲突：生成冲突记录，不覆盖

### 不能自动合并时

绝不静默丢弃任何一方：

- 云端版本保留为当前
- 本地版本写入 `.conflict-<device>-<timestamp>` 文件
- 同时在 `memory_conflicts` 表记录

如果冲突合并需要调用大模型：

- B 模型 turbo 设置 300s 超时
- A 模型设置 600s 超时
- 注意：**B 模型 reasoning 占比高是正常特性，不要把它当废稿重试**

---

## 5. 反向同步：云端 → 本地

订阅 Supabase Realtime 的 `memory_blocks` 变更：

- 收到远程变更后，根据 `block_key` 找到本地文件
- 如果本地对应块没有未同步修改，直接把远程 chunk_id 对应内容写回本地
- 如果本地也有未同步修改，走冲突处理

用 `updated_by = device_id` 忽略自己产生的变更，防止回环。

---

## 6. 核心表结构

```sql
create table memory_chunks (
  chunk_id text primary key,          -- sha256(content)
  content text not null,
  content_hash text not null,
  created_at timestamptz default now()
);

create table memory_blocks (
  block_key text primary key,         -- file_path#heading/key
  chunk_id text not null references memory_chunks(chunk_id),
  rev bigint not null default 0,
  updated_by text not null default '',
  deleted_at timestamptz,
  updated_at timestamptz default now()
);

create table memory_conflicts (
  id bigserial primary key,
  block_key text not null,
  base_chunk_id text,
  local_chunk_id text,
  remote_chunk_id text,
  status text default 'open',
  created_at timestamptz default now()
);
```

---

## 7. 强制验证

每次同步后必须执行：

```bash
memory-sync sync --check
```

检查内容：

- 本地配置的 watch 路径是否全部生效
- 本地 manifest 和远端 `memory_blocks` 是否一致
- 每个变更块的 `content_hash` 是否回读一致

这就是“同步后必须回读验证”的强制闭环。  
增量同步的核心不是技术炫技，而是：**只传播状态跃迁，不传全量状态；冲突时保留分歧，不丢失记忆。**
