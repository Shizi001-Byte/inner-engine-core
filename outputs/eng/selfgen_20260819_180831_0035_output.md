# 引擎产出自动归档系统设计

## 1. 系统定位

本系统对 AI 引擎产出的任务结果做**自动分类、自动打标签、自动存入对应目录**，把高熵的“产出流”转化为低熵的“有序资产”。

本质上，这是一个**负熵注入器**：它持续从外部吸收产出、配置、规则、人工反馈，维持归档链路的低功能熵；如果缺少这套系统，引擎产出会逐渐堆积、混乱、不可追踪，最终形成“引擎自然退化”的服务链路熵增。

---

## 2. 总体架构

```text
引擎任务完成
   │
   ▼
接入层（MQ / Webhook / SDK）
   │
   ▼
归档 Pipeline：
  清洗 → 分类 → 打标 → 目录映射 → 原子写入 → 索引/通知
   │
   ├── 规则引擎（优先）
   ├── 模型服务（兜底，B/A 模型分级超时）
   ├── 配置中心（单一事实源，热更新）
   ├── 人工复核队列（低置信度/失败）
   └── 观测告警（Metrics + Trace）
```

## 3. 核心流程

### 3.1 接入与幂等

- 引擎产出完成后发送事件，包含：
  - `task_id`
  - 产出内容 URI 或 body
  - 任务类型、业务域、来源、模型版本等元数据
- 归档服务以 `task_id` 做幂等去重，避免重复归档。

### 3.2 内容清洗

- 校验产出完整性。
- 剥离敏感信息、临时字段、内部日志。
- 提取正文/文件内容，供后续分类和打标。

### 3.3 自动分类

三级分类：

1. **规则层**：根据任务类型、来源、业务域、关键词等快速分类。
   - 例如：`task_type=code_generation` → `代码生成`
   - 例如：内容包含 `SQL`、`pandas` → `数据分析`
2. **模型层**：规则置信度低时，调用分类模型兜底。
3. **人工层**：规则和模型都无法确定时，进入人工复核队列。

### 3.4 自动打标签

标签分为四类：

| 标签类型 | 示例 |
|---|---|
| 系统标签 | `task_id`、`模型版本`、`引擎版本`、`耗时`、`状态` |
| 业务标签 | `业务域`、`产品线`、`场景` |
| 内容标签 | 关键词、实体、主题、语言、文件类型 |
| 安全标签 | `敏感`、`合规受限`、`公开` |

打标来源：

- 任务元数据直接映射。
- 对产出内容做关键词/实体抽取。
- 敏感内容识别后打安全标签，并归档到受限目录。

### 3.5 目录映射与存储

目录模板示例：

```text
/archive/{业务域}/{任务类型}/{yyyy}/{mm}/{dd}/{task_id}/
├── manifest.json      # 标签、元数据、分类结果
├── output.md          # 产出正文/文本
├── output.bin         # 二进制文件（如有）
└── meta.json          # 原始任务信息
```

- `task_id` 保证目录唯一，避免覆盖。
- `manifest.json` 写入所有标签和分类信息，便于检索和审计。

### 3.6 原子提交

- 先写临时目录，校验完整后 `rename` 到正式目录。
- 写入索引库（如 ES/数据库）后更新状态。
- 任一步失败，进入待复核队列，不阻塞主流程。

## 4. 避坑设计：已纳入历史失败经验

### 4.1 配置修改必须生效

**历史教训**：配置修改后未生效，行为无变化。

**本系统做法**：

- **单一配置源**：所有配置统一放在配置中心，代码中不复制配置值。
- **统一读取点**：所有模块通过 `ConfigClient` 读取同一个 key，不存在“多处维护”问题。
- **修改后立即自检**：配置发布后自动触发一次“自检任务”，用历史样本走通 分类→打标→目录映射→归档 全链路。
- **对比验证**：自检结果与预期目录/标签做 diff，不一致则告警并回滚。
- **版本对账**：定期检查运行实例实际生效的配置版本，防止“改了但没生效”。

### 4.2 API 调用超时

**历史教训**：API 调用超时，任务未在规定时间内返回。

**本系统做法**：

- 分类/打标模型调用超时按模型类型区分：
  - **B 模型 turbo：300 秒**
  - **A 模型：600 秒**
- 超时不无限等待，进入降级路径：
  - 优先用规则结果归档。
  - 如果规则也不足，进入人工复核队列。
- 重试策略：
  - 只重试网络抖动/5xx 等可重试错误。
  - 超时错误不重试。
  - 最多重试 2 次，退避 1s/5s。
- 所有模型调用传入 `task_id`，保证可追踪、可幂等。

## 5. 与“功能熵”和“耗散系统”的对应

| 引擎退化层级 | 自动归档系统的对抗方式 |
|---|---|
| 物理算力层 | 归档后清理临时文件，减少存储碎片和 IO 混乱 |
| 模型参数层 | 按模型版本、prompt 版本打标签，产出可归因 |
| 服务链路层 | 幂等、超时隔离、异步化，避免单个任务阻塞全链路 |
| 价值对齐层 | 安全标签 + 人工复核 + 规则反馈，保持与业务目标对齐 |

同时，归档系统自身也需要持续负熵输入：

- 新的分类规则
- 新的标签词典
- 模型阈值调整
- 人工复核反馈

否则，规则会老化，分类准确率会随业务漂移而下降。

## 6. 反馈闭环：人机共生

自动归档不是“机器完全替代人”，而是：

- 机器负责**规模化初分**：海量任务自动分类、打标、归档。
- 人负责**高价值判断**：处理低置信度、敏感内容、复杂边界。
- 人的修正结果回流到规则库/模型训练集，形成持续进化。

这正是“宏观价值主体性”与“分布式功能主体性”的互利共生：自动系统提供效率，人工系统提供价值校准，双方通过反馈形成协同进化。

---

## 7. 落地建议

1. 先接入 3～5 类高频任务，验证规则分类准确率。
2. 再开启模型兜底，逐步扩大覆盖面。
3. 配置中心、自检、超时分级必须优先完成，否则后续扩展会重复踩坑。
4. 上线后关注三个指标：
   - 归档成功率
   - 分类准确率
   - 标签覆盖率

最终效果：引擎产出从“完成任务即结束”变成“完成任务即沉淀”，自动形成有序、可检索、可治理、可审计的资产库。
