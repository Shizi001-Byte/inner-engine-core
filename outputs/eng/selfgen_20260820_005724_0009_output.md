### 一、 引擎层架构推演：约束调和与 V7.5 管线映射

要满足“节点无持久状态（无记忆修改）”且“恢复时不遍历所有节点”，引擎层必须采用 **WAL（预写式日志）+ 内容寻址（CID）** 机制。

1. **触发与日志生成（WAL意图持久化）**
   - **触发条件**：重大变更（如本地代码 Commit、构建产物生成、数据库导出完成）。
   - **动作**：引擎不生成任何本地节点树，而是直接将变更意图写入 WAL。例如：`TX_001: PUT_CID(QmXyZ) -> Gitee, Feishu, Supabase`。
2. **多线程API调用（并发执行）**
   - 按照避坑要求，针对不同平台预设合理 timeout。
   - **Gitee API**：代码推送/Commit（Timeout: 300s）。
   - **飞书 API**：大文件分片上传（Timeout: 600s，视作A模型处理，防止大文件超时）。
   - **Supabase API**：Storage对象插入/数据库记录更新（Timeout: 300s）。
3. **结果入队与串行后处理**
   - 三方调用的结果（成功/失败/CID回执）推入内存队列。
   - 串行后处理负责：比对返回的 CID、更新 WAL 状态为 `COMPLETED`、处理冲突。

### 二、 幂等性方案（基于内容寻址与回执校验）

由于节点“无记忆修改”，不能依赖本地时间戳或文件列表判断是否已同步，必须通过 **内容寻址（Content-ID, 类似Git SHA-1或文件MD5）** 结合远端状态校验来实现幂等。

#### 1. Gitee 代码提交幂等
- **CID 生成**：以本次变更的 Git Commit SHA 作为 CID。
- **幂等策略**：在 API 调用前，WAL 记录意图。多线程调用 Gitee API 推送 Commit 时，如果该 SHA 已存在于远端仓库（Gitee 会返回 `Everything up-to-date` 或非快进报错），引擎判定为**已同步**，直接标记 WAL 为成功，不重复创建新 Commit。
- **防超时重试**：若因网络超时未收到响应，重试时只需查询 Gitee 该 SHA 是否存在，存在则跳过。

#### 2. 飞书文件上传幂等
- **CID 生成**：文件内容的 MD5 Hash。
- **幂等策略**：飞书不支持同名覆盖，旧文件会保留。引擎在串行后处理时，将飞书文件的 `file_token` 与 CID 绑定。
  - 若因断电重启，WAL 重放，引擎向飞书发起上传前，先通过飞书 API 查询目标文件夹下是否有带 `[CID:xxxxx]` 后缀的文件。
  - 若有，则跳过上传，仅更新 Supabase 中的飞书 `file_token` 映射。

#### 3. Supabase 存储同步幂等
- **CID 生成**：数据记录的主键或 Storage 对象的 Content-MD5。
- **幂等策略**：利用 Supabase 的 Upsert 能力。API 调用时，将 CID 作为存储路径（如 `sync/gitee-commits/{SHA}.json`）或数据库主键。
  - 多线程调用 `upsert` 接口，即使重复调用，Supabase 底层会根据主键覆盖，实现天然幂等。

### 三、 冲突处理方案（串行后处理阶段）

三方网络状态不一致必然导致“部分成功部分失败”的冲突。串行后处理队列负责在 WAL 的保障下解决冲突。

#### 1. 跨系统状态分歧冲突
- **现象**：Gitee 提交成功，飞书超时失败，Supabase 成功。WAL 中该事务状态为 `PARTIAL_COMMITTED`。
- **处理方案**：
  - **不回滚**（满足无记忆修改，无法可靠反向遍历删除）。引擎将失败节点的重试任务重新入队。
  - 串行后处理检查 Supabase 中的“同步状态表”，发现 Gitee 和 Supabase 已有 CID，飞书缺失，则触发**飞书单边重试补偿**，而非整体重做。

#### 2. 并发写入冲突
- **现象**：两次重大变更几乎同时触发，TX_001 和 TX_002 并发执行。
- **处理方案**：
  - WAL 是严格追加的，TX_001 一定在 TX_002 之前。
  - 串行后处理按 WAL 顺序校验回执。如果发现 TX_002 在 Gitee 上先于 TX_001 合入（非正常变基情况），引擎将 TX_002 在 Gitee 的 Commit 强制 Revert，并生成 TX_003 重新提交，以对齐飞书和 Supabase 的顺序。

#### 3. 飞书同名文件冲突
- **现象**：同名文件内容变更，飞书生成了两个文件。
- **处理方案**：串行后处理在成功上传新文件后，调用飞书 API 将旧版本文件（通过 Supabase 记录的旧 `file_token`）移动至 `/_trash` 文件夹，并更新 Supabase 映射。

### 四、 避坑与约束落实清单

为确保该方案在工程落地时不重蹈覆辙，严格落实以下策略：

1. **配置生效与读取点验证（防配置失效坑）**
   - 新增三方同步配置（如 Gitee 仓库 Token、飞书 App ID）后，必须在 WAL 写入前、多线程调用前 **立即验证读取点**。若配置读取失败，直接阻断 TX 生成，防止无效 API 调用导致超时。
2. **超时控制硬编码级约束（防 API 超时坑）**
   - 飞书文件上传模块预设 600s Timeout（大模型/A模型级别）。
   - Gitee/Supabase API 预设 300s Timeout。
   - 超时后不阻塞管线，直接将结果标记为 `TIMEOUT` 入队，交由串行后处理决定是否重试。
3. **恢复时绝不遍历节点状态（满足硬约束）**
   - 节点重启后，引擎仅读取 WAL 中状态为 `PENDING` 或 `PARTIAL` 的事务，通过 API 精确查询对应的 CID 是否存在，而非拉取全量文件树比对。
4. **客户端/环境前置检查（防连接器坑）**
   - 在执行同步任务前，引擎自动进行环境自检：确认 Gitee Token 权限（push）、飞书会话有效性、Supabase RLS（行级安全）策略允许写入。若自检失败，直接抛出明确异常，不进入管线。
