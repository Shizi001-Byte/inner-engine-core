# 任务类型: eng

基于【演化生物学映射】与【CAS复杂适应系统】框架，Supabase作为“记忆脑/中枢神经系统”，其核心使命是记录状态流转，弥合高维代码（Gitee/DNA）与低维物理界面（飞书）之间的认知差。

针对“检测本地文件变化、只同步变更部分、处理冲突”的增量同步需求，现推演Supabase记忆脑的增量同步方案如下：

### 一、 CAS框架下的“记忆脑”增量同步架构映射

在CAS（复杂适应系统）中，系统通过“感知-反应-记忆”循环适应环境。Supabase在此过程中扮演**突触网络**，负责记录每一次神经元（节点）活动的状态，避免全量重算带来的系统能量过载。

| 演化生物学/CAS概念 | Supabase工程映射 | 作用与机制 |
| :--- | :--- | :--- |
| **突触电位变化** | 本地文件变化检测 | 监听本地文件系统，捕获“刺激信号” |
| **动作电位传递** | 增量差异计算与同步 | 仅提取并传输发生变化的“电位”，降低能耗 |
| **免疫排异反应** | 冲突检测与解决 | 识别多源修改造成的“基因冲突”，执行裁定 |

### 二、 核心机制推演与工程实现

#### 1. 检测本地文件变化（环境刺激感知机制）
**机制推演**：神经系统不会对静态环境持续放电，仅对“变化”产生动作电位。系统需通过哈希算法识别文件的“基因突变”。
**工程实现**：
- **感知层**：使用文件系统监听组件（如Node.js的 `chokidar` 或 Python的 `watchdog`）捕获 `add`, `change`, `unlink` 事件。
- **记忆比对**：计算本地文件的 SHA-256 哈希值，与 Supabase `file_memory` 表中记录的 `last_known_hash` 进行比对。若一致，则视为无突变，终止后续流程。
- **【避坑执行·配置同步】**：监听规则（如忽略 `node_modules`、`.git` 等）必须抽离为独立配置文件。**新增配置必须同步修改读取点，修改后立即通过单测验证生效**，防止因配置未加载导致全量误传或死循环。

#### 2. 只同步变更部分（轴向传输与能量最优）
**机制推演**：DNA复制采用半保留复制，仅合成新增碱基对。同步引擎也应仅传输变更的数据块，而非整个基因组。
**工程实现**：
- **差异提取**：对于代码文件（高维DNA），基于行级 diff 提取变更片段；对于二进制文件，直接覆盖文件实体但在元数据层记录版本。
- **状态更新**：将变更部分推送至飞书后，立即更新 Supabase 的 `file_memory` 表：
  - `file_path`: 文件路径
  - `current_hash`: 最新哈希值
  - `feishu_file_token`: 飞书对应的文件凭证
  - `last_sync_time`: 最后同步时间戳
- **【避坑执行·超时控制】**：如果在同步过程中需要调用大模型（如调用A/B模型生成代码变更摘要，用于飞书文档的更新说明），必须预设合理 timeout。**B模型turbo用300秒，A模型用600秒**。避免大文件处理导致中枢神经阻塞。

#### 3. 处理冲突（免疫排异与稳态调节）
**机制推演**：当本地环境（低维界面）与远端基因库（高维Gitee/飞书）发生不一致时，系统产生“免疫反应”。Supabase作为中枢神经，需提供冲突裁决依据。
**工程实现**：
- **冲突检测**：同步前，先查询 Supabase 中该文件的 `last_sync_time` 与 Gitee/飞书的实际更新时间。若远端时间 > Supabase记录时间，且本地有修改，则判定为“并发修改冲突”。
- **冲突裁决策略**：
  - *策略A（高维优先）*：Gitee作为DNA底座，优先级最高，本地拉取远端覆盖。
  - *策略B（时间戳优先）*：保留最新修改，记录历史版本到 `file_conflict_log` 表。
  - *策略C（AI辅助裁定）*：调用大模型对比两份代码逻辑，生成合并方案。
- **【坑库预警·大模型废稿误杀】**：若采用策略C调用大模型辅助裁定，**不同模型必须有独立的质量检测规则。B模型(turbo)跳过reasoning占比检测**。由于B模型reasoning占比70-82%为其正常特性，若强制套用常规废稿检测（如要求reasoning<30%），将导致大模型输出被误判为废稿而触发无限重试，最终引发同步引擎崩溃。

### 三、 Supabase 记忆脑表结构设计 (中枢神经系统数据模型)

为支撑上述增量同步与冲突处理，Supabase需建立以下核心表结构：

```sql
-- 记忆脑主表：记录文件当前认知状态
CREATE TABLE file_memory (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    file_path TEXT NOT NULL UNIQUE,
    content_hash TEXT NOT NULL,          -- 本地最新哈希
    gitee_sha TEXT,                      -- Gitee对应的commit SHA
    feishu_file_token TEXT,              -- 飞书文件token
    last_sync_time TIMESTAMPTZ DEFAULT NOW(),
    sync_status TEXT DEFAULT 'idle'      -- idle, syncing, conflict
);

-- 冲突免疫日志表：记录排异反应过程
CREATE TABLE file_conflict_log (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    file_path TEXT NOT NULL,
    local_hash TEXT NOT NULL,
    remote_hash TEXT NOT NULL,
    resolution_strategy TEXT,            -- 'gitee_overwrite', 'local_overwrite', 'ai_merged'
    ai_reasoning TEXT,                   -- 若调用AI，记录其推理过程
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

### 四、 验证矩阵（基于避坑经验）

| 机制 | 验证点 | 预期结果 |
| :--- | :--- | :--- |
| **配置生效验证** | 修改文件监听忽略规则 | 读取点同步更新，未忽略文件不再触发哈希计算 |
| **API超时验证** | 触发B模型生成代码摘要 | 300秒内返回正常结束；超时则自动熔断，不阻塞同步主线程 |
| **废稿检测验证** | B模型返回reasoning占比75% | 跳过占比检测，直接提取有效部分写入日志，**不触发自动重试** |

通过上述CAS框架下的增量同步设计，Supabase不仅能精准捕获“基因突变”，还能以最低能耗完成信息流转，并在冲突发生时维持系统稳态。
