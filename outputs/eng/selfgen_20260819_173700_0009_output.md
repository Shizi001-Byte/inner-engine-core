# 任务类型: eng

下面给出一个可直接落地的“多模型成本实时监控 + 自动熔断 + 降级 + 等待补跑”方案。  
这套方案会避开你给出的历史坑位：**model_id 错配、熔断冷却不生效、计数语义混乱**，同时保持与 `CF --> SP[Supabase 认知池 实]` 的分布式状态机升维一致。

---

## 1. 总体架构

```text
ChainTask 任务
    │
    ▼
模型路由 / API 网关
    │
    ├── 调用模型 A / B / C
    │
    ▼
Usage Event Bus（用量事件总线）
    │
    ▼
Counter Service（实时计数）
    │
    ▼
Circuit Breaker（熔断器）
    │
    ├── 正常：放行
    ├── 熔断：降级 / 进入等待队列
    └── 恢复：自动补跑等待任务
```

关键原则：

- **SP 是权威状态**：熔断状态、等待任务、计数事件最终都写入 SP。
- **CF 只是本地事件日志 / 投影**：不参与熔断仲裁，避免分布式状态分脑。
- **每个模型独立计数、独立熔断**：`model_id` 是唯一维度，禁止 pro/turbo/light 混用。

## 2. 数据模型

### 2.1 模型目录表 `model_catalog`

```sql
create table model_catalog (
  model_id          text primary key,          -- 官方完整 model_id
  alias             text unique not null,      -- 业务别名，例如 b_turbo
  provider          text not null,
  timeout_seconds   int not null,              -- B 模型 turbo 用 300s，A 模型用 600s
  cost_per_1k_input_tokens  numeric,
  cost_per_1k_output_tokens numeric,
  is_active         boolean default true
);
```

示例：

| alias | model_id | timeout_seconds |
|---|---|---|
| b_turbo | `doubao-seed-2-1-turbo` | 300 |
| a_pro | `doubao-seed-2-1-pro` | 600 |

> 计数、熔断、成本统计只认 `model_id`，不认 alias。

---

### 2.2 模型策略表 `model_policy`

所有阈值、冷却时间、降级链都从这里读取。

```sql
create table model_policy (
  model_id                  text primary key,
  cost_limit_per_minute     numeric,   -- 成本阈值
  cost_limit_per_hour       numeric,
  cost_limit_per_day        numeric,
  task_count_limit_per_minute int,     -- 请求量阈值
  error_rate_threshold      numeric,   -- 错误率阈值，例如 0.2
  fuse_cooldown_seconds     int,       -- 熔断冷却时间，必须从 state 读取
  fallback_chain            jsonb,     -- ["b_turbo", "b_light", ...]
  degrade_mode              text,      -- 'fallback' 或 'force_wait'
  probe_max                 int,       -- half-open 探测请求数
  probe_success_required    int,       -- half-open 连续成功次数
  updated_at                timestamptz
);
```

> **避坑**：代码中不允许出现 `const cooldown = 120`。  
> 必须这样写：  
> `const cooldown = policy.fuse_cooldown_seconds ?? DEFAULT_FUSE_COOLDOWN_SECONDS;`

---

### 2.3 熔断状态表 `circuit_state`

```sql
create table circuit_state (
  model_id        text primary key,
  state           text not null,  -- CLOSED / OPEN / HALF_OPEN
  tripped_at      timestamptz,
  cooldown_until  timestamptz,
  reason          text,
  updated_at      timestamptz
);
```

---

### 2.4 等待任务表 `waiting_task`

熔断期间无法执行的任务必须记录下来，恢复后补跑。

```sql
create table waiting_task (
  id                uuid primary key default gen_random_uuid(),
  chain_task_id     text not null,
  original_model_id text not null,
  fallback_chain    jsonb,
  status            text not null default 'waiting',  -- waiting/running/success/failed/canceled
  enqueued_at       timestamptz not null default now(),
  available_after   timestamptz not null default now(),
  attempts          int not null default 0,
  max_attempts      int not null default 10,
  idempotency_key   text unique,
  payload           jsonb
);
```

## 3. 实时计数与成本统计

### 3.1 计数维度

每个模型独立维护以下指标：

```text
usage:cost:{model_id}:{yyyyMMddHHmm}
usage:task:{model_id}:{yyyyMMddHHmm}
usage:bonus:{model_id}:{yyyyMMddHHmm}
usage:error:{model_id}:{yyyyMMddHHmm}
```

### 3.2 计数语义

严格区分：

- `task_count`：仅统计真实 ChainTask 任务。
- `bonus_count`：仅统计系统自触发任务。
- `total_count = task_count + bonus_count`
- `cost_amount`：成本，不是 count。

> **避坑**：不要用同一个 `count` 字段表示所有计数。  
> 任何加操作必须携带 `event_type`，且必须去重：

```sql
insert into model_usage_event (
  event_id, model_id, event_type, cost_amount, input_tokens, output_tokens, created_at
)
values (...)
on conflict do nothing;
```

---

### 3.3 原子累加

用 Redis Lua 原子操作，避免并发计数丢失：

```lua
local cost_key  = KEYS[1]
local task_key  = KEYS[2]
local bonus_key = KEYS[3]

redis.call('INCRBYFLOAT', cost_key, ARGV[1])

if ARGV[2] == 'task' then
  redis.call('INCRBY', task_key, 1)
elseif ARGV[2] == 'bonus' then
  redis.call('INCRBY', bonus_key, 1)
end

redis.call('EXPIRE', cost_key, 86400)
```

## 4. 熔断状态机

```text
CLOSED --(成本超限/错误率超标)--> OPEN
OPEN   --(冷却时间到)------------> HALF_OPEN
HALF_OPEN --(探测成功)----------> CLOSED
HALF_OPEN --(探测失败)----------> OPEN
```

### 4.1 熔断条件

满足任意一个即熔断：

```text
cost_used >= cost_limit_per_minute
或
cost_used >= cost_limit_per_hour
或
total_count >= task_count_limit_per_minute
或
error_rate >= error_rate_threshold
```

### 4.2 决策伪代码

```text
def decide(model_id):
    policy = get_model_policy(model_id)   # 从 SP/缓存读取
    stats  = get_current_stats(model_id)  # 从 Redis/SP 读取
    cb     = get_circuit_state(model_id)

    if stats.cost >= policy.cost_limit_per_minute:
        open_circuit(model_id, reason='cost_limit')
        return WAIT_OR_FALLBACK

    if cb.state == OPEN:
        if now >= cb.cooldown_until:
            half_open_circuit(model_id)
            return ALLOW_PROBE
        return WAIT_OR_FALLBACK

    if cb.state == HALF_OPEN:
        if stats.probe_success >= policy.probe_success_required:
            close_circuit(model_id)
            return ALLOW
        if stats.probe_failure > 0:
            open_circuit(model_id, reason='probe_failure')
            return WAIT_OR_FALLBACK
        return ALLOW_PROBE

    return ALLOW
```

## 5. 降级与等待

### 5.1 路由逻辑

```text
def route_task(task):
    decision = decide(task.model_id)

    if decision == ALLOW:
        dispatch(task.model_id)
        return

    if policy.degrade_mode == 'fallback':
        for fb_model in policy.fallback_chain:
            if decide(fb_model) == ALLOW:
                dispatch(fb_model)
                record_degraded(task, fb_model)
                return

    # 没有可用降级模型，或必须等待原模型
    enqueue_waiting(task)
```

### 5.2 等待任务写入

熔断期间，无法执行的任务写入 `waiting_task`：

```text
status = waiting
available_after = cooldown_until
```

如果降级模型也熔断，则 `available_after` 取所有候选模型的最晚冷却时间。

## 6. 恢复与自动补跑

### 6.1 恢复调度器

每隔一段时间扫描等待任务：

```sql
select *
from waiting_task
where status = 'waiting'
  and available_after <= now()
order by enqueued_at
limit #{batch_size}
for update skip locked;
```

### 6.2 补跑前检查

对每个等待任务：

```text
decision = decide(original_model_id)

if decision == ALLOW:
    dispatch(original_model_id)

elif decision == ALLOW_PROBE:
    # 用等待任务作为 half-open 探测请求
    dispatch_as_probe(original_model_id)

else:
    # 还没恢复，继续等待
    update available_after = circuit_state.cooldown_until
```

### 6.3 控制补跑速率

防止恢复瞬间打爆模型：

```text
batch_size = min(
  policy.probe_max,
  remaining_budget / avg_task_cost
)
```

## 7. 必须避开的坑

### 7.1 model_id 错配

- 新模型接入前，必须核对官方文档的完整 `model_id`。
- 禁止在代码里用 `if model == 'turbo'` 判断。
- 计数和熔断 key 只使用 `model_catalog.model_id`。
- 入口处校验：上报事件的 `model_id` 不在 catalog 中，直接拒收并告警。

### 7.2 熔断冷却配置不生效

- 所有冷却时间、阈值、降级链都从 `model_policy` 读取。
- 全局常量只做默认值兜底。
- 每次熔断决策记录 `policy_version` 和 `cooldown_used`，方便排查。
- 上线前测试：
  - 设置 `fuse_cooldown_seconds = 300`
  - 触发熔断
  - 断言 `cooldown_until - tripped_at == 300`

### 7.3 计数语义混乱

- 禁止使用一个通用 `count` 字段。
- 建表时用检查约束：

```sql
check (total_count = task_count + bonus_count)
```

- 每次写入必须携带 `event_type in ('task', 'bonus')` 和唯一 `event_id`。
- 历史数据回补必须标记 `is_backfill = true`，并且不计入实时熔断阈值。

---

## 8. 与既有认知锚定的衔接

- 本系统是“本地文件状态机”向“广域网分布式状态机”升维的一部分。
- CF 只作为本地事件日志；SP 是权威状态。
- 熔断状态、等待任务、计数事件都写入 SP。
- 8 月缺失对话如果补入 SP，必须先做语义清洗，避免“字面认知陷阱”污染成本统计；回填数据不计入实时熔断统计。

---

这套设计可以做到：**每个模型独立计数、到阈值自动熔断、熔断期间降级或记录等待任务、恢复后自动补跑**，并且能避免历史踩坑。
