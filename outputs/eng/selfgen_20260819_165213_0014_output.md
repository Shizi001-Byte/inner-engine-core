# 任务类型: eng

# 设计引擎产物三方同步自动化方案

## 0. 核心原则

- **单向同步**：设计引擎产物包是唯一事实源；Gitee、飞书、Supabase 都是下游存储，不做双向同步。
- **版本不可变**：同一版本号发布后内容不可变；内容变化必须升版本。这能大幅简化幂等和冲突处理。
- **幂等优先**：同一事件重复触发、同一文件重复上传，结果必须一致且不产生重复数据。

---

## 1. 触发机制

设计引擎完成一次“重大变更”后，生成产物包并发布事件：

```json
{
  "event_id": "evt_20260608_001",
  "version": "2.3.0",
  "release_type": "major",
  "artifacts_uri": "https://.../design-2.3.0.tar.gz",
  "manifest": {
    "artifacts": [
      {
        "path": "src/generated/api.py",
        "sha256": "abc...",
        "size": 1024,
        "targets": ["gitee"]
      },
      {
        "path": "docs/design.md",
        "sha256": "def...",
        "size": 2048,
        "targets": ["feishu", "supabase"]
      }
    ]
  }
}
```

同步编排器监听该事件，触发前先检查：

```sql
SELECT state_lock FROM sync_runs WHERE event_id = ?;
-- 只有 state_lock = 'released' 才允许接管任务
```

获取锁时使用原子操作：

```sql
UPDATE sync_runs
SET state_lock = 'locked', updated_at = now()
WHERE event_id = ? AND state_lock = 'released';
```

若影响行数为 0，说明已有同步任务在跑，直接返回“重试稍后”。

---

## 2. 同步编排流程

```
设计引擎
   │  发布 event
   ▼
同步编排器
   ├─ 1. 校验 event 签名 / state_lock
   ├─ 2. 拉取 manifest 与产物包
   ├─ 3. 按 targets 路由：
   │      code/*  → Gitee
   │      docs/*  → 飞书
   │      data/*  → Supabase
   │      默认     → Supabase
   ├─ 4. 对每个 (artifact, target) 生成幂等键
   ├─ 5. 执行同步 / 冲突处理
   └─ 6. 写入 sync_items / sync_conflicts
```

## 3. 幂等性设计

### 3.1 幂等键

```
idempotency_key = sha256(event_id + version + target + artifact_path)
```

`sync_items` 表对 `idempotency_key` 建唯一索引。  
同一 key 已存在且 `status = success`，直接跳过。

### 3.2 各目标端幂等策略

#### Gitee

- 使用 Gitee Contents API。
- 写入前先 `GET /repos/{owner}/{repo}/contents/{path}`。
  - 文件不存在 → 创建。
  - 文件存在且 `sha` 与上次记录一致 → 跳过。
  - 文件存在但 `sha` 不一致 → 冲突，不覆盖。
- 提交信息固定包含版本号和事件 ID：

```
chore(design): sync v2.3.0 [evt_20260608_001]
```

- 大文件（>1MB）不要走 Contents API，改用 `git push`。  
  幂等判断：检查本地/远端是否已有包含 `design-v2.3.0` 的 commit，有则跳过。

#### 飞书

- 使用飞书自建应用 API，避免扫码连接器绑定问题。
- 每次同步在 state store 中记录 `file_token` 作为 `remote_ref`。
- 同步前先查 state store：
  - 有 `file_token` 且文件仍存在、大小一致 → 跳过。
  - 无 `file_token` 或文件不存在 → 上传。
- 文件名带版本号，例如：

```
design_2.3.0.pdf
```

- 大文件使用分片上传，记录 `upload_id` 支持断点续传。

#### Supabase Storage

- 对象路径带版本号：

```
artifacts/2.3.0/src/generated/api.py
```

- 上传前检查对象是否存在：
  - 存在且 metadata 中 `sha256` 与源一致 → 跳过。
  - 存在但 metadata 缺失或 `sha256` 不一致 → 冲突。
  - 不存在 → 上传。
- 上传时写入 metadata：

```
sha256, source-event-id, sync-time
```

## 4. 冲突处理

### 4.1 冲突定义

- 目标端已存在同版本对象，但内容/校验和与源不一致。
- 或 state store 显示 `success`，但目标端对象被外部修改/删除。

### 4.2 默认策略：人工介入

不自动覆盖，记录到 `sync_conflicts` 表：

| 字段 | 说明 |
|---|---|
| event_id | 本次事件 |
| target | gitee / feishu / supabase |
| artifact_path | 产物路径 |
| source_sha256 | 源端哈希 |
| remote_sha256 | 远端哈希 |
| status | pending / resolved |

同时通过飞书消息或 Webhook 通知负责人。

### 4.3 可选策略：source-wins-with-backup

自动以源端为准，但必须先把远端旧对象备份：

```
backup/{version}/{target}/{path}.{timestamp}
```

备份完成后才允许覆盖。

### 4.4 可选策略：version-wins

不覆盖，直接报错并提示“内容已变化，请升版本后重新发布”。

### 4.5 冲突避免原则

- 三方同步只做“新增”，不主动覆盖已发布版本。
- 如果同一个版本内容发生变化，视为流程违规，必须升级版本号。
- 任何情况下不删除目标端多余文件。

## 5. 状态记录与失败重试

### 5.1 表结构

```sql
create table sync_runs (
  event_id text primary key,
  version text not null,
  release_type text not null,
  state_lock text not null default 'released',
  status text not null default 'pending',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table sync_items (
  id bigserial primary key,
  idempotency_key text unique not null,
  event_id text not null references sync_runs(event_id),
  target text not null,
  artifact_path text not null,
  sha256 text not null,
  status text not null,
  remote_ref text,
  attempts int not null default 0,
  last_error text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique(event_id, target, artifact_path)
);

create table sync_conflicts (
  id bigserial primary key,
  event_id text not null,
  target text not null,
  artifact_path text not null,
  source_sha256 text not null,
  remote_sha256 text not null,
  status text not null default 'pending',
  resolution text,
  created_at timestamptz not null default now(),
  resolved_at timestamptz
);
```

### 5.2 重试

- 每个 item 最多重试 5 次。
- 使用指数退避：1s、2s、4s、8s、16s + 随机抖动。
- 超时设置：
  - 普通 API 操作：30s
  - 文件上传/下载：300s
  - 大文件分片：600s
  - 若调用 AI 生成提交信息/摘要：B 模型 turbo 用 300s，A 模型用 600s

## 6. 落地避坑

1. **配置读取点必须同步修改**  
   所有 Gitee/飞书/Supabase 配置统一放 `sync_config.yaml`，由 `config_loader.py` 读取。  
   新增配置时必须同步修改 loader 的 schema，部署后立即跑：

   ```bash
   python -m sync_engine --check-config
   python -m sync_engine --smoke-test
   ```

2. **飞书连接器问题**  
   不要用扫码连接器绑定账号，直接使用自建应用 `app_id + app_secret` 获取 `tenant_access_token`，绕开客户端绑定失败问题。

3. **大文件传输**  
   Gitee Contents API 不适合大文件，Feishu 单文件上传有大小限制。  
   超过阈值自动切换为 `git push` 或飞书分片上传，避免超时。

4. **锁必须释放**  
   同步任务结束后在 `finally` 中释放 `state_lock`；若进程崩溃，利用 `lock_until` 过期自动释放，避免死锁。

5. **自动覆盖必须备份**  
   如果配置 `auto_resolve_conflict=true`，必须同时配置 `backup_before_overwrite=true`，否则拒绝启动。

## 7. 关键伪代码

```python
def handle_event(event):
    if not acquire_state_lock(event.id):
        raise BusyError("state_lock 未释放，稍后重试")

    try:
        manifest = load_manifest(event.artifacts_uri)

        for artifact in manifest.artifacts:
            for target in resolve_targets(artifact):
                sync_one(event, artifact, target)
    finally:
        release_state_lock(event.id)


def sync_one(event, artifact, target):
    key = idempotency_key(event.id, artifact.path, target)

    item = sync_items.get(key)
    if item and item.status == "success":
        return

    remote = adapter(target).get_remote_state(artifact)

    if remote is None:
        remote_ref = adapter(target).upload(artifact)
        mark_success(key, remote_ref)

    elif remote.checksum == artifact.sha256:
        mark_skipped(key)

    else:
        handle_conflict(event, artifact, target, remote)
```

---

以上方案可直接落地。核心是把“版本不可变 + 单向同步 + 幂等键 + 冲突记录”四件事做扎实，就能避免重复提交、重复上传和互相覆盖的问题。
