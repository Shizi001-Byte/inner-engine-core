# 任务类型: eng

推演：Supabase 记忆脑增量同步方案

一句话结论：**本地文件是事实源，Supabase 是事件日志 + 对象存储 + 全局索引**。  
每次本地修改先变成一条不可丢失的“决策事件”，同步时只传变更块；冲突不静默覆盖，而是进入“可检索差异”表，等后续 merge 事件解决。

---

## 1. 检测本地文件变化

用 `FileWatcher + PeriodicScanner` 双保险：

- `FileWatcher`：监听本地目录，`debounce 800ms`，避免编辑器连续保存触发多次。
- `PeriodicScanner`：每 5 分钟扫描一次全量文件，兜底 watcher 漏掉的场景（睡眠唤醒、网络盘、手动替换文件）。
- 自我写入标记：同步引擎写回文件时设置 `isSyncing` 标记，watcher 对这次事件直接忽略，防止同步回环。

本地维护一张 manifest：

```text
path          text
hash          text        # sha256
mtime_ns      int
chunk_hashes  text[]      # 当前文件由哪些 chunk 组成
base_seq      bigint      # 当前文件基于远端哪个事件
```

检测到文件变化后：

1. 计算新 `sha256`。
2. 与 manifest 中旧 hash 对比；相同则跳过。
3. 不同则重新分块，生成 event。
4. 把 event 写入本地 outbox，更新 manifest。

这个阶段的核心是：**不要把 watcher 原始事件当同步信号，必须经过 hash 去重。**

---

## 2. 只同步变更部分

同步单位不是“整个文件”，而是“内容寻址 chunk”。

分块策略：

- 小文本文件：整个文件作为一个 chunk。
- Markdown/长文本：按段落/标题/代码块切分成语义块。
- 大文件/二进制：用 FastCDC 或 buzhash 做内容定义分块，平均 4KB。

每个 chunk 用 `sha256` 做地址，内容存到 Supabase Storage：

```text
bucket: chunks
object: chunks/{sha256}
```

本地修改后，生成的事件结构如下：

```json
{
  "event_id": "uuid",
  "actor_id": "device-uuid",
  "doc_id": "doc-uuid",
  "base_seq": 12,
  "chunks_after": ["hash1", "hash2", "hash3"],
  "added": ["hash2"],
  "removed": ["hash1"],
  "parents": []
}
```

同步时：

1. 调 `missing_chunks(added)`，只查远端缺失的 chunk。
2. 只上传缺失的 chunk。
3. 调 `push_event` 写入事件日志。
4. 远端把 `chunks_after` 作为该文档新的 chunk 列表。

这就是“只同步变更部分”：  
**内容只传新增 chunk，结构只传 hash 列表，不传整个文件。**

## 3. Supabase 核心表结构

```sql
create table public.doc (
  id uuid primary key default gen_random_uuid(),
  path text unique not null,
  chunk_hashes text[] not null default '{}',
  applied_seq bigint not null default 0,
  updated_at timestamptz not null default now()
);

create table public.sync_event (
  seq bigint generated always as identity primary key,
  event_id uuid unique not null,
  actor_id uuid not null,
  doc_id uuid not null references public.doc(id) on delete cascade,
  base_seq bigint not null,
  chunks_after text[] not null,
  added text[] not null default '{}',
  removed text[] not null default '{}',
  status text not null default 'applied'
    check (status in ('applied', 'conflict', 'superseded')),
  parents uuid[] not null default '{}',
  created_at timestamptz not null default now()
);

create table public.chunk (
  hash text primary key,
  size integer not null,
  created_at timestamptz not null default now()
);

create table public.conflict (
  id uuid primary key default gen_random_uuid(),
  doc_id uuid not null references public.doc(id) on delete cascade,
  base_chunk_hash text,
  local_chunk_hash text,
  remote_chunk_hash text,
  local_event_id uuid,
  remote_event_id uuid,
  resolved boolean not null default false,
  resolution_event_id uuid,
  created_at timestamptz not null default now()
);
```

`sync_event.seq` 是全局顺序，由 Postgres identity 生成，不能人为重排。  
`conflict` 表是“可检索差异”的实体，不随解决而删除。

---

## 4. 处理冲突

### 冲突检测

服务端 `push_event` 时做原子判断：

- 如果 `event.base_seq == doc.applied_seq`：直接应用，`doc.applied_seq = event.seq`，状态为 `applied`。
- 如果 `event.base_seq < doc.applied_seq`：说明基于旧版本修改，状态为 `conflict`，写入 `conflict` 表。

注意：**冲突事件也必须写入 `sync_event`，获得全局 seq，不能丢弃。**

### 合并策略

客户端发现冲突后，用 diff3 三路合并：

```text
base_list   = 冲突发生前的 chunk_hashes
local_list  = 本地事件的 chunks_after
remote_list = 远端 doc.chunk_hashes
```

先对 chunk 列表做 diff3：

- 无结构冲突：继续。
- 有结构冲突：进 `conflict` 表，等待人工决策。

再对同一个 chunk 的文本内容做 diff3：

- 一方未改，取另一方。
- 双方改了但 diff3 干净合并：生成新 chunk，写 merge event。
- 双方改了且 diff3 冲突：不自动覆盖，把 `base/local/remote` 三个 chunk hash 写入 `conflict` 表。

### merge event

自动合并或人工解决后，必须生成新的决策事件：

```json
{
  "event_id": "new-uuid",
  "actor_id": "device-uuid",
  "doc_id": "doc-uuid",
  "base_seq": 15,
  "chunks_after": ["hash1", "merged-hash", "hash3"],
  "added": ["merged-hash"],
  "removed": ["hash2"],
  "parents": ["local-event-id", "remote-event-id"]
}
```

这个 merge event 是新的决策事件，继续进入事件日志。  
原来的冲突事件保留，`conflict.resolved = true`，但不删除。

## 5. 同步循环

整个系统是一个开放、有界、循环的负熵引擎：

```text
本地文件变化
    -> 分块
    -> 写 outbox
    -> push 事件到 Supabase
    -> pull 远端新事件
    -> apply / merge
    -> 写回本地文件
    -> 继续循环
```

- 开放：新设备生成 actor_id 后，拉取事件日志和 chunk 即可加入。
- 有界：同步范围被 `doc_id`、`chunk_hash`、`seq` 区间限制，不做全表扫描。
- 循环：事件日志不断从本地熵变为有序状态，冲突显式化而不是累积成混乱。

## 6. 防坑清单

1. **配置修改后必须热加载并验证生效**  
   `SyncConfig` 使用单一 ConfigStore，所有模块从同一对象读取。配置变更后立即更新 watcher ignore 规则、分块大小、merge policy、timeout，然后执行一次 `doctor` 自检，确认“读取点”和“写入点”一致。

2. **API 调用必须预设 timeout**  
   同步主链路的网络请求 timeout 建议 30s。  
   如果同步过程中触发 LLM 索引任务，按模型区分：  
   - B 模型（turbo）用 300 秒  
   - A 模型用 600 秒  
   超时进入重试队列，不阻塞同步主流程。

3. **废稿检测不能误杀 B 模型**  
   如果对新增 chunk 做 AI 质量过滤，B 模型（turbo）的 reasoning 占比 70-82% 是正常特性。  
   **B 模型必须跳过 reasoning 占比检测**，否则会被误判为废稿并自动重试。

4. **可以优化执行层，但不能优化掉决策事件和全局顺序**  
   并发上传、批量拉取、压缩、缓存都可以做。  
   但 `sync_event.seq` 的全局顺序、`event_id` 的决策链、`conflict` 的差异记录，都不能被省掉。

5. **本地优先是底线**  
   Supabase 只是远端存储和索引。本地文件永远是用户直接操作的事实源。  
   远端数据丢失，本地还能恢复；本地离线，照常读写，outbox 积累事件，恢复网络后继续同步。

---

这个方案不是“顶层设计出一个完美同步协议”，而是先让每次增量同步的摩擦都变成可检索的事件和冲突。  
制度和 merge policy，会从这些真实摩擦中慢慢长出来。
