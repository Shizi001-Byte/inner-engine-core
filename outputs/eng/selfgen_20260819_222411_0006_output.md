### 一、 引擎前置避坑与配置基座（严格遵循历史教训）

为防止“配置不生效”和“API超时”，引擎启动前必须遵循以下基座设计：

1. **配置中心与即时验证机制（避坑1）**
   - **设计**：所有配置（Webhook Secret、API Token、Bucket路径）统一存入Supabase的`engine_config`表。
   - **预防**：引擎新增`config_reload`接口，修改配置后自动触发Dry-Run（空跑）测试，若返回非200则自动回滚并告警，确保“修改即生效”。
2. **Timeout动态预设（避坑2）**
   - **设计**：根据触发动作的负载动态分配Timeout。
     - Gitee Webhook响应（轻量）：15秒。
     - 飞书文件上传API（中等，走Turbo通道）：300秒硬超时。
     - Supabase存储及大表更新（重量级，走A模型通道）：600秒硬超时。
3. **飞书连接器绑定前置检查（坑库预警1）**
   - **设计**：引擎初始化时自动执行`lark_connector_health_check()`，校验客户端版本、Token有效性，避免因账号未登录或页面缩放导致的假死。

### 二、 三方同步自动化工作流设计

**触发条件**：Gitee仓库发生“重大变更”（如：主分支Merge、Release打Tag、包含`[SYNC]`关键字的Commit）。

**执行链路（异步事件驱动模式）**：
1. **接收与分流**：Gitee Webhook打到引擎网关，网关生成全局唯一`trace_id`，立即返回200，后续异步处理（防止Gitee Webhook超时）。
2. **代码解析与抽取**：拉取Gitee Diff数据，提取变更的文档/产物文件（如.md, .json, 构建产物）。
3. **双写并行执行**：
   - **分支A**：调用飞书API，上传/覆盖对应文件夹下的文件，并更新索引表。
   - **分支B**：将文件流及元数据同步至Supabase Storage，并在DB中更新版本记录。
4. **状态收敛**：两端均成功后，在Supabase写入本次同步的最终成功状态。

---

### 三、 幂等性设计方案（核心防御价值：保底防错）

为保证边际效用衰减极慢的“防御价值”，必须杜绝重复Webhook导致的脏数据写入。

1. **全局幂等键**
   - 以 `{Gitee_Repo_ID}_{Commit_SHA}_{File_Path}` 作为唯一幂等键。
2. **状态机拦截**
   - 在Supabase建立`sync_tasks`表，包含字段：`id`, `trace_id`, `idempotency_key`, `status` (`PENDING`, `PROCESSING`, `SUCCESS`, `FAILED`), `payload`。
   - **处理逻辑**：引擎收到事件后，首先去Supabase `upsert`该幂等键。
     - 若状态为`SUCCESS`，直接拦截，返回“已处理”。
     - 若状态为`PROCESSING`，进入退避重试队列，不执行实际IO。
3. **操作级幂等**
   - **飞书**：使用飞书云文档的`file_token`作为版本锚点，采用“按版本号更新”而非“重新创建”，确保重复上传仅覆盖同名文件。
   - **Supabase**：利用Storage的`upsert`接口参数 `upsert: true`，确保同路径文件直接覆盖而不报错；DB层通过唯一索引 `(repo_id, commit_sha)` 防重。

### 四、 冲突处理方案（核心效率价值：高频协同）

遵循Gitee为“代码唯一可信源”的原则，处理三方同步中的版本与时序冲突。

1. **基准声明**
   - **Gitee = 唯一真理源**。飞书与Supabase的数据状态必须无条件向Gitee对齐，消除“飞书端被人工误改”带来的冲突。
2. **乐观锁与版本对齐**
   - Supabase的同步元数据表记录 `gitee_commit_timestamp`。
   - 若出现乱序到达的Webhook（如网络延迟导致旧Commit后到），引擎比较时间戳：若传入时间戳 `< 当前DB记录时间戳`，判定为**过期事件**，直接丢弃并记录日志，防止“旧数据覆盖新数据”。
3. **并发冲突处理（最后写入胜出 + 校验）**
   - 当多线程处理同一文件的不同Commit时（极少见但需防御），采用Supabase的 `UPDATE ... WHERE version = $expected_version` 乐观锁。
   - 若更新影响行数为0，说明被其他线程抢占，当前线程主动放弃，进入600秒（A模型）级别的退避重试队列，重新拉取最新状态计算Diff后再提交。
4. **最终一致性补偿**
   - 若飞书上传成功但Supabase写入失败：标记任务为`PARTIAL_FAILED`。
   - 触发补偿机制：启动Supabase超长Timeout（600秒）重试；若仍失败，通过飞书Bot发送告警给研发，人工介入。不进行自动回滚（因为代码已在Gitee，数据最终会被下一次Webhook纠正）。

### 五、 演化速率验证：Token驱动下的效率闭环

结合【已有认知锚定1】，本引擎的设计不仅解决工程问题，更是**“高频海量Token消耗碾压低频变异”**的实验场：

- **传统模式（低频）**：研发手动传文档到飞书，手动备份到Supabase，周期以“天/周”为单位，错误率高。
- **本引擎模式（高频）**：每次Commit自动触发，以API调用（Token消耗）作为代谢单位。
- **自演化闭环**：引擎在Supabase记录所有失败Cause（超时、冲突、绑定失败等）。每月通过AI模型分析这些失败日志，**自动生成新的配置规则或Timeout阈值**（如发现某类文件飞书必超时，则自动将其路由到A模型600秒通道）。
- **结论**：通过让引擎在真实研发流中高频“试错与纠正”（消耗API Token），实现了比人工修改架构代码快几个数量级的演化速率，直接拉升了【效率价值】的上限。
