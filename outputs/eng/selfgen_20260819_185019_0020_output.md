# 任务类型: eng

下面直接基于你的锚定推演，不重复论证“省 Token vs 省时间/保进化”。

## 1. 设计边界

本自动归档系统服务于：

- 大模型 API
- 云服务
- 内容平台
- 互联网工具
- 以及围绕这些供给主体运转的 AI 调度/运营引擎

重边际成本供给场景不适用，因为归档复用的收益会被供给硬约束抵消。

---

## 2. 概念对齐

沿用你的锚定，不展开论证：

| 热力学概念 | AI 引擎系统对应定义 | 量化方式 |
|---|---|---|
| 封闭系统 | 无外部规则/资源干预，仅靠自身逻辑自循环的 AI 引擎 + 供需生态 | 外部规则注入次数；任务池无序度 |
| 熵增 | 任务池同质化、输出混乱、归档缺失、重复处理、检索成本上升 | 重复任务率、归档缺失率、平均检索耗时 |
| 负熵流 | 自动归档系统：分类、打标签、目录化，并把结构化结果反馈给引擎 | 分类覆盖率、标签命中率、目录命中率 |
| 开放系统 | 引擎通过归档反馈感知同质化，主动复用/合并/跳过相似任务 | 重复处理率下降、空转率下降 |

所以归档系统不是“存储终点”，而是引擎的感知回路。

---

## 3. 总体架构

```
引擎任务完成
   ↓
产生归档事件 → 消息队列
   ↓
归档 Consumer
   ↓
1. 预处理：归一化任务元数据 + 产出物
   ↓
2. 分类：规则分类 → 模糊时调用大模型分类
   ↓
3. 打标签：系统标签 + 业务标签 + 同质化标签
   ↓
4. 目录解析：根据分类/租户/日期生成存储路径
   ↓
5. 存储写入：对象存储/文件系统 + 索引更新
   ↓
6. 反馈事件：通知调度引擎“任务已归档/可复用”
```

关键原则：**归档链路异步执行，不阻塞引擎主流程。**

## 4. 核心流程

### 4.1 自动分类

分类优先级：

1. **规则分类**
   - 根据任务元数据中的 `task_type`、`api_name`、`source`、`status` 直接映射。
   - 不调用模型，耗时极短。
   - 例如：
     - `api_name=text_generation` → `generate/text`
     - `task_type=sentiment_analysis` → `analyze/sentiment`
     - `status=timeout` → `meta/timeout`

2. **内容规则分类**
   - 根据输出内容特征判断。
   - 含代码块 → `generate/code`
   - 含 JSON 结构 → `data/structured`
   - 长度超阈值且为分析类 → `analyze/report`

3. **模型分类**
   - 仅当规则分类置信度低于阈值时调用。
   - 模型只输出 JSON，不输出解释：
     ```json
     {
       "category": "analyze/finance",
       "tags": ["domain=finance", "language=zh"],
       "confidence": 0.92
     }
     ```
   - 分类提示词用“枚举约束 + JSON Schema”，避免自由文本。

### 4.2 打标签

标签分三类：

| 类型 | 示例 |
|---|---|
| 系统标签 | `tenant=tenantA`、`model=B-turbo`、`status=success`、`timeout=300s` |
| 业务标签 | `domain=finance`、`language=zh`、`format=json`、`has_code=true` |
| 同质化标签 | `group=abc123`、`duplicate_of=task_456` |

同质化标签用于反馈给引擎：

- 计算任务指纹：`sha256(task_type + 归一化元数据 + 输出摘要)`
- 若指纹已存在，则打上 `duplicate_of=<task_id>`
- 引擎看到该标签后，可避免再次执行相似任务，防止空转。

标签要限制数量，建议单任务不超过 20 个，且必须经过标签字典归一化。

### 4.3 存入对应目录

目录路径由“主分类 + 租户 + 日期”决定，标签不进入目录，避免目录爆炸。

推荐路径模板：

```
{root}/{tenant}/{category}/{yyyy}/{mm}/{dd}/{task_id}.json
```

示例：

```
s3://archive/tenantA/generate/text/2025/04/09/task_123.json
s3://archive/tenantA/analyze/sentiment/2025/04/09/task_456.json
s3://archive/tenantA/uncategorized/2025/04/09/task_789.json
```

目录映射必须由配置中心统一管理：

```json
{
  "root": "s3://archive",
  "path_template": "{root}/{tenant}/{category}/{yyyy}/{mm}/{dd}/{task_id}.json",
  "category_map": {
    "generate/text": "generate/text",
    "analyze/sentiment": "analyze/sentiment",
    "meta/timeout": "meta/timeout"
  }
}
```

未知分类统一进入 `uncategorized/`，并打 `needs_review` 标签。

## 5. 超时控制

这是本次设计必须落地的点。

### 5.1 超时预算

| 阶段 | 超时时间 | 超时处理 |
|---|---|---|
| 规则分类 | 100ms | 不应超时 |
| 模型分类：B-turbo | 300s | 降级为规则分类 + `needs_review` |
| 模型分类：A | 600s | 降级为规则分类 + `needs_review` |
| 存储写入 | 10s | 重试 2 次，失败进 DLQ |
| 索引更新 | 5s | 重试 2 次，失败进 DLQ |

### 5.2 模型选择与超时

根据任务复杂度选择模型：

| 任务复杂度 | 分类模型 | 超时 |
|---|---|---|
| 低，规则可覆盖 | 规则分类 | 100ms |
| 中，短文本 | B-turbo | 300s |
| 高，长文档/跨域 | A | 600s |

任何模型调用都采用“有界等待”：

- 同步等待使用 `Future.get(timeout)`
- 异步任务使用回调 + 超时熔断
- 超时后立即降级，不无限等待

超时任务本身也要归档，归档到 `meta/timeout`，方便后续复盘。

## 6. 配置管理：避免“配置修改后未生效”

这条历史失败经验必须直接写进设计规范。

### 6.1 统一配置读取点

所有配置只允许通过一个入口读取：

```
ArchiveConfig.get("archive_rules")
```

禁止在业务代码中散落硬编码：

- 禁止直接读 `os.environ["CATEGORY_MAP"]`
- 禁止在分类器内部写死目录映射
- 禁止在存储层写死超时时间

### 6.2 新增配置必须同步修改读取点

新增一个配置项时，同一个变更单必须包含：

1. 配置中心新增配置
2. 配置 Schema 更新
3. 读取点代码更新
4. 测试用例更新

CI 检查规则：

- 如果配置中心有新增 key，但代码中没有对应读取点引用，则禁止合并。

### 6.3 修改后立即验证生效

配置发布后，自动执行自检：

```bash
archive_selfcheck --config-version 20250409
```

自检内容：

- 用 3 条 golden sample 任务跑分类
- 断言分类结果、标签、目录路径是否符合预期
- 通过后配置才置为 active
- 不通过则自动回滚到上一版本

每条归档记录都记录 `config_version`，方便追溯：

```json
{
  "archive_meta": {
    "config_version": "20250409",
    "classifier_version": "classifier_v3"
  }
}
```

## 7. 状态机

归档任务状态：

```
pending
  → preprocessing
  → classifying
  → tagging
  → resolving
  → storing
  → archived
```

失败分支：

```
classifying 超时 → fallback_archived
storing 失败   → failed / DLQ
未知分类       → archived + needs_review
```

`fallback_archived` 不是失败，只是低置信归档。

## 8. 伪代码示例

```python
class ArchiveService:
    def __init__(self, config_reader, classifier, storage, index, event_bus):
        self.config = config_reader.get_archive_config()

    def archive_task(self, task):
        record = self.create_record(task)

        # 1. 规则分类
        category, confidence = self.rule_classifier.classify(task)

        # 2. 模糊时调用模型分类
        if confidence < self.config.confidence_threshold:
            timeout = self.config.timeout_map[task.model]
            try:
                category, tags, confidence = self.llm_classifier.classify(
                    task,
                    model=task.model,
                    timeout_seconds=timeout
                )
            except TimeoutError:
                record.add_tag("classify_timeout")
                record.add_tag("needs_review")

        # 3. 打标签
        record.category = category
        record.tags = self.tagger.generate(task, category)

        # 4. 目录解析
        directory = self.path_resolver.resolve(
            tenant=task.tenant,
            category=record.category,
            date=task.completed_at
        )

        # 5. 存储
        storage.write(directory, record.to_json())

        # 6. 索引 + 反馈
        index.update(record)
        event_bus.publish("task.archived", record.to_event())
```

## 9. 观测指标

最终用这些指标衡量归档系统是否真的在“降熵”：

| 指标 | 目标 |
|---|---|
| 归档覆盖率 | 接近 100% |
| 分类准确率 | 抽样人工审计 ≥ 95% |
| 标签命中率 | ≥ 90% |
| 归档平均延迟 | 异步场景 < 1s，模型分类除外 |
| 模型分类超时率 | < 1% |
| 重复任务处理率 | 下降 |
| 引擎空转率 | 下降 |
| 配置生效延迟 | 发布后 1 分钟内生效 |

## 10. 结论

这个自动归档系统的本质是：

- **省时间**：规则优先、异步归档、有界超时、超时降级。
- **保进化**：通过分类、标签、同质化分组，把归档结果反馈给调度引擎，让引擎感知任务池结构，避免重复空转。
- **防配置失效**：统一配置读取点，新增配置必须同步改代码，发布后立即自检验证。
