# Supabase 记忆脑增量同步方案（推演）

## 0. 先校验锚点，再谈优化

进入任何同步链路前，先做最小成本锚点校验：

- 本地目录：`MEMORY_DIR` 是否存在、可写、路径无拼写错误
- Supabase 锚点：`SUPABASE_URL` / Project Ref / Service Role Key 是否真实有效
- 表结构：`memory_docs`、`memory_chunks`、`memory_sync_state` 是否存在且列名一致
- 状态文件：`.sync/state.json` 是否可读写
- 哈希规则：本地与远端统一使用 `sha256`，换行符统一为 LF，Unicode 统一 NFC
- 配置读取点：新增配置必须同步修改代码读取点，不能只写进 `.env`

> 锚点校验永远高于链路优化。  
> 项目 ID 看错、表名写错，后续所有增量逻辑都白跑。

---

## 1. 状态模型

同步需要三方状态：

| 状态 | 位置 | 作用 |
|---|---|---|
| `base` | 本地 `.sync/base/` 或 Supabase 历史表 | 上次成功同步的基线 |
| `local` | 本地记忆文件 | 当前本地内容 |
| `remote` | Supabase `memory_docs` + `memory_chunks` | 当前远端内容 |

每次同步判断：

- `local == remote`：无变化，跳过
- `local == base` 且 `remote != base`：远端变了，拉取
- `remote == base` 且 `local != base`：本地变了，推送
- `local != base` 且 `remote != base`：冲突

增量同步的核心是：**用 `base` 做三路合并，避免整个文件覆盖。**

---

## 2. 检测本地文件变化

不能只靠 `mtime`，要以内容哈希为最终真相。

### 检测方式

- 文件监听：inotify / FSEvents / Watchdog，触发后 debounce 2 秒，避免写入半截文件
- 轮询兜底：每 30 秒扫一遍目录，兜住监听漏掉的变更

### 判定流程

```
stat: mtime_ns + size
  未变 -> 跳过
  变了 -> 读文件 -> normalize -> sha256
      哈希未变 -> 只更新 stat，跳过同步
      哈希变了 -> 进入 diff 流程
```

本地状态 `.sync/state.json` 记录：

```json
{
  "memories/project_x.md": {
    "mtime_ns": 1720000000000000000,
    "size": 1234,
    "sha256": "abc...",
    "chunks": [
      { "id": "overview", "hash": "aaa" },
      { "id": "dates", "hash": "bbb" }
    ]
  }
}
```

## 3. 只同步变更部分

整文件上传不是增量。记忆脑的增量同步应以 **chunk 为最小同步单位**。

### 3.1 分块策略

- Markdown：按标题、段落、代码块分块
- JSON：按 JSON Pointer 分块，例如 `/tags/3`
- 纯文本：按空行分段，或用 content-defined chunking 避免插入内容导致后续块漂移

每个 chunk 有稳定 ID 和内容哈希：

```
chunk_id = "overview"
content_hash = sha256(chunk_content)
```

### 3.2 Diff 计算

对比 base 的 chunk 列表和当前本地 chunk 列表：

| 状态 | 处理 |
|---|---|
| `unchanged` | chunk_id 和 hash 都一样，跳过 |
| `changed` | 同 chunk_id，hash 不同，只更新这个 chunk |
| `added` | 新 chunk_id，插入 |
| `removed` | 旧 chunk_id 不存在了，删除 |

这样同步时只需要传输：

- 变更的 chunk
- 新增的 chunk
- 删除的 chunk ID

### 3.3 推送事务

用 Supabase RPC 封装事务，避免客户端手写跨表事务。

```sql
BEGIN;

-- 锁定文档，校验 base
SELECT content_hash
INTO v_remote_hash
FROM memory_docs
WHERE path = p_path
FOR UPDATE;

IF v_remote_hash IS DISTINCT FROM p_base_hash THEN
  RETURN conflict;
END IF;

-- 更新文档级元数据
UPDATE memory_docs
SET content_hash = p_new_hash,
    revision = revision + 1,
    updated_at = now()
WHERE path = p_path;

-- upsert 变更的 chunks
INSERT INTO memory_chunks (doc_path, chunk_id, chunk_index, content, content_hash, updated_at)
VALUES ...
ON CONFLICT (doc_path, chunk_id)
DO UPDATE SET
  content = EXCLUDED.content,
  content_hash = EXCLUDED.content_hash,
  chunk_index = EXCLUDED.chunk_index,
  updated_at = now();

-- 删除已移除的 chunks
DELETE FROM memory_chunks
WHERE doc_path = p_path
  AND chunk_id NOT IN (...);

COMMIT;
```

如果启用了 embedding，只对 `content_hash` 变化的 chunk 重新生成 embedding，未变部分直接复用。

## 4. 处理冲突

冲突不是错误，是正常状态。关键是：**同步引擎不能替大脑做语义取舍。**

### 4.1 冲突检测

冲突发生在：

```
base = 上次同步基线
local = 当前本地
remote = 当前远端

local != base 且 remote != base
```

### 4.2 自动合并的边界

在 chunk 级别做三路合并：

- 本地改的 chunk 和远端改的 chunk 没有交集 → 自动合并
- 同一个 chunk 内，改的是不同行 → 行级自动合并
- 同一行 / 同一语义点都被改了 → 不能自动覆盖，进入冲突处理

### 4.3 冲突处理策略

| 策略 | 行为 |
|---|---|
| `lww` | 最后写入者胜，按 `updated_at` 或 revision 比较，谨慎使用 |
| `manual` | 写入 `memory_conflicts` 表，生成冲突标记文件，等人/LLM 处理 |
| `llm-merge` | 把 base / local / remote 发给 LLM，生成合并结果；超时或质量不合格则回退 manual |

冲突标记示例：

```
# CONFLICT: memories/project_x.md
<<<<<<< LOCAL
- 项目截止 6 月 1 日
=======
- 项目截止 7 月 1 日
>>>>>>> REMOTE
```

### 4.4 LLM 合并的坑

- 调用 LLM 合并时：
  - B 模型（turbo）：timeout 用 300 秒
  - A 模型：timeout 用 600 秒
- 质量检测：
  - B 模型（turbo）的 reasoning 占比 70-82% 是正常特性，**跳过 reasoning 占比检测**
  - A 模型保留 reasoning 占比检测
- LLM 合并超时后，不能阻塞同步链路，应保留 `pending_conflict` 状态，后续继续处理

> 身体可以更快，但不能替大脑思考。  
> 增量同步负责把变更高效搬运到大脑附近；最终记忆的取舍、合并、遗忘由大脑层裁决。

## 5. 拉取远端变更

远端变更检测：

- 轮询 `memory_docs.updated_at > last_pull_at`
- 或订阅 Supabase Realtime `postgres_changes`，只用于唤醒，实际同步仍走同一状态机

拉取逻辑：

```
SELECT path, content_hash, updated_at
FROM memory_docs
WHERE updated_at > $last_pull_at
  OR revision > $last_pulled_revision;
```

对每个变更文档：

- 如果本地未变：直接拉取 chunks，重建本地文件
- 如果本地已变：进入冲突处理

---

## 6. 删除与墓碑

删除也是一种增量变更：

- 本地删除文件 → 推送 tombstone，远端标记 `deleted_at`
- 远端删除 → 本地拉取 tombstone，删除本地文件
- 本地删除、远端编辑 → 冲突，不能默认删除远端内容

避免已删除记忆被另一台设备重新“复活”。

## 7. 配置、验证与避坑

### 配置项示例

```env
MEMORY_DIR=/path/to/memory
SUPABASE_URL=https://xxx.supabase.co
SUPABASE_SERVICE_ROLE_KEY=xxx

SYNC_POLL_INTERVAL=30
SYNC_DEBOUNCE=2
SYNC_CONFLICT_POLICY=llm-merge
SYNC_CONFLICT_MODEL=B-turbo
SYNC_LLM_TIMEOUT_B=300
SYNC_LLM_TIMEOUT_A=600
```

### 必须避免的三个坑

1. **配置修改后未生效**  
   - 新增配置必须同步修改代码读取点  
   - 修改后立即执行 `syncctl validate` 和 `syncctl status` 验证生效

2. **API 调用超时**  
   - LLM 合并超时：B 模型 turbo 用 300 秒，A 模型用 600 秒  
   - Supabase 写入事务超时：预留 120 秒以上  
   - 超时后先查 revision / updated_at 是否已变化，避免重复 push

3. **废稿检测误杀 B 模型**  
   - B 模型（turbo）reasoning 占比 70-82% 是正常特性  
   - 质量检测必须分模型：B 模型跳过 reasoning 占比检测，A 模型正常检测

---

## 结论

增量同步方案核心是：

- 本地变化检测：**监听 + 轮询 + sha256 兜底**
- 只同步变更部分：**chunk 级 diff + upsert + delete**
- 冲突处理：**三路合并，机械冲突自动合，语义冲突留给大脑**

最后记住：

> 锚点校验永远高于链路优化。  
> 增量同步是手脚，记忆裁决是大脑。  
> 手脚可以更快，但不能替大脑思考。
