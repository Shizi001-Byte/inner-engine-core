# Supabase 记忆脑增量同步方案

## 核心思路

增量同步的本质是：

> **感知本地文件系统的“变化信号” → 计算最小变更单元 → 只同步这些单元 → 用乐观锁解决多端冲突。**

同步层只负责搬运变化，不解析语义；语义解析由上层模型负责。最小同步单元不是整个文件，而是 **chunk（记忆块）**。

---

## 1. 本地状态模型

本地维护一个 manifest，用于判断“什么变了”：

```json
{
  "device_id": "laptop-01",
  "files": {
    "notes/idea.md": {
      "mtime_ns": 1720000000000000000,
      "size": 1234,
      "sha256": "当前文件哈希",
      "base_sha256": "上次同步成功时的哈希",
      "base_version": 7,
      "chunks": {
        "uuid-v5-1": { "anchor": "# 标题", "hash": "chunk-hash" }
      }
    }
  }
}
```

同时本地保留一份 `shadow/` 目录，存放上次同步成功的原始内容，用于冲突合并时的 diff3 基线。

---

## 2. Supabase 数据模型

```sql
-- 文件级状态
create table sync_files (
  path text primary key,
  sha256 text not null,
  version bigint not null,
  deleted boolean not null default false,
  updated_at timestamptz not null default now(),
  updated_by text not null
);

-- 记忆块级状态
create table memory_chunks (
  id uuid primary key,
  path text not null references sync_files(path),
  anchor text not null,
  content text not null,
  content_hash text not null,
  embedding vector(1536),          -- 启用向量检索时使用
  version bigint not null,
  updated_at timestamptz not null default now(),
  updated_by text not null,
  unique(path, anchor)
);

-- 同步事件，用于多端增量拉取
create table sync_events (
  id bigserial primary key,
  path text not null,
  version bigint not null,
  op text not null,                -- 'upsert' | 'delete'
  created_at timestamptz not null default now()
);

-- 冲突记录
create table sync_conflicts (
  id uuid primary key default gen_random_uuid(),
  path text not null,
  base_version bigint,
  base_sha256 text,
  local_sha256 text,
  remote_sha256 text,
  status text not null default 'open',
  resolution text,
  created_at timestamptz not null default now(),
  resolved_at timestamptz
);
```

## 3. 检测本地文件变化

使用文件系统监听 + 定期全量扫描兜底：

```js
chokidar.watch(MEMORY_DIR, {
  ignoreInitial: true,
  awaitWriteFinish: {
    stabilityThreshold: 500,
    pollInterval: 100
  }
})
  .on('add', enqueue('add', path))
  .on('change', enqueue('change', path))
  .on('unlink', enqueue('delete', path));
```

关键点：

- 每个路径的事件要 **debounce 300ms**，避免编辑器连续写入触发多次同步。
- 事件触发后不能只看 `mtime`，必须以 `sha256` 为准：
  - 先 stat 得到 `size`、`mtime_ns`
  - 再读文件计算 `sha256`
  - 与本地 manifest 比较
  - 没变化则跳过
- 每 15 分钟做一次全量扫描，防止监听漏事件。

## 4. 只同步变更部分

### 4.1 文件切分为 chunk

- Markdown：按标题切分
  - 每个标题及其下的内容为一个 chunk
  - anchor 为标题链，例如 `# 第一章 > ## 第一节`
  - 标题前内容 anchor 为 `__frontmatter__`
- JSON/YAML：按顶层 key 切分
  - anchor 为 `$.key`
- 无标题纯文本：整个文件作为一个 chunk
  - anchor 为 `__file__`

### 4.2 chunk 的稳定 ID

```js
id = uuid_v5('memory-chunk-v1', path + '::' + anchor)
```

anchor 稳定，chunk ID 就稳定；标题内容变化时，只影响该标题对应的 chunk。

### 4.3 diff 计算

同步前，从 Supabase 拉取该路径现有的 chunk 列表，与本地 chunk 列表对比：

| 对比结果 | 动作 |
|---|---|
| 本地有，远端无 | 插入 |
| 本地无，远端有 | 删除 |
| 两边都有，hash 不同 | 更新 |
| 两边都有，hash 相同 | 跳过 |

这样只传输真正变化的 chunk。

## 5. 同步引擎

### 5.1 Push 本地变更

调用一个 RPC，在数据库事务里完成：

```sql
create or replace function sync_push_file(
  p_path text,
  p_base_version bigint,
  p_sha256 text,
  p_chunks jsonb,
  p_device text
) returns jsonb
language plpgsql
as $$
declare
  v_version bigint;
  c jsonb;
begin
  select version into v_version
  from sync_files
  where path = p_path
  for update;

  -- 乐观锁：远端版本必须等于本地 base_version
  if v_version is null then
    if p_base_version is not null then
      return jsonb_build_object('status', 'conflict');
    end if;
    v_version := 1;
    insert into sync_files(path, sha256, version, updated_by)
    values (p_path, p_sha256, v_version, p_device);
  else
    if v_version <> p_base_version then
      return jsonb_build_object('status', 'conflict', 'remote_version', v_version);
    end if;
    v_version := v_version + 1;
    update sync_files
    set sha256 = p_sha256,
        version = v_version,
        updated_by = p_device,
        updated_at = now()
    where path = p_path;
  end if;

  -- 只 upsert 本地有变化的 chunks
  for c in select * from jsonb_array_elements(p_chunks)
  loop
    insert into memory_chunks(id, path, anchor, content, content_hash, version, updated_by)
    values ((c->>'id')::uuid, p_path, c->>'anchor', c->>'content', c->>'content_hash', v_version, p_device)
    on conflict (id) do update
    set content = excluded.content,
        content_hash = excluded.content_hash,
        version = excluded.version,
        updated_by = excluded.updated_by,
        updated_at = now();
  end loop;

  -- 删除远端存在但本地已不存在的 chunks
  delete from memory_chunks
  where path = p_path
    and id not in (
      select (value->>'id')::uuid
      from jsonb_array_elements(p_chunks)
    );

  insert into sync_events(path, version, op)
  values (p_path, v_version, 'upsert');

  return jsonb_build_object('status', 'ok', 'version', v_version);
end;
$$;
```

### 5.2 Pull 远端变更

本地记录 `last_event_id`，增量拉取：

```sql
select *
from sync_events
where id > $1
order by id
limit 100;
```

拉取后逐文件处理：

- 本地文件不存在 → 下载生成
- 本地文件未修改（`sha256 == base_sha256`）→ 应用远端版本
- 本地文件已修改 → 进入冲突处理

## 6. 冲突处理

### 6.1 冲突判定

本地 manifest 中保存了 `base_sha256` 和 `base_version`：

- `local_changed = local_sha256 != base_sha256`
- `remote_changed = remote_sha256 != base_sha256`

两者都为 true，就是冲突。

删除也视为一种修改：

- 本地删、远端改 → 冲突，默认保留远端
- 本地改、远端删 → 冲突，默认保留本地
- 两端都删 → 不冲突

### 6.2 冲突解决策略

优先自动合并，不能合并则保留双方。

#### 自动合并：diff3

本地保留 shadow 基线文件，因此可以执行：

```bash
diff3 -m base local remote
```

- 无冲突退出码 0 → 自动合并成功
- 有冲突退出码 1 → 生成带冲突标记的文件，写入 `sync_conflicts`

#### 保底：保留双方

无法自动合并时：

- 远端内容成为主文件
- 本地内容保存为 `path.local-<device>-<timestamp>`
- 写入 `sync_conflicts`，等待人工处理

#### 最终兜底：LWW

如果产品要求必须自动收敛，可以选 LWW：

- 比较 `updated_at`
- 时间相同时比较 `device_id`
- 但 LWW 会丢数据，记忆脑场景不推荐

## 7. 超时与失败兜底

同步任务必须放入队列，避免长任务挂死：

- 每次网络请求设置 timeout：
  - Supabase 普通读写：30s
  - Embedding/LLM 调用：B 模型 turbo 用 300s，A 模型用 600s
- 每个同步任务有 `op_id`，重试时幂等，防止重复写入
- 批量 chunk 同步时，每批不超过 50 个
- 失败后指数退避重试：1s → 5s → 15s → 60s，最多 5 次
- 超过重试次数进入 dead queue，人工介入

## 8. 部署后验证清单

1. 修改某个 Markdown 标题下的内容，确认 Supabase 中只有该 chunk 的 `updated_at` 变化。
2. 断网修改文件，恢复网络后确认能增量同步，且 `version + 1`。
3. 两台设备同时修改同一文件的不同标题，确认自动合并成功。
4. 两台设备同时修改同一标题，确认生成冲突记录，且无数据丢失。
5. 修改同步规则后，立即用一条测试笔记验证生效，避免“配置改了但读取点没改”的问题。

---

这个方案的关键是：**用 chunk 做最小变更单元，用 base_version 做乐观锁，用 shadow 基线做 diff3 合并。** 这样既能做到增量同步，也能在多方写入时最大程度保留记忆。
