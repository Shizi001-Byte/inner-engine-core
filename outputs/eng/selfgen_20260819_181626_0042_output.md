# 任务类型: eng

## 方案：引擎产出三方同步自动化

### 一、总体架构

采用「事件触发 + 编排器 + 状态表 + Canary 校验」的最终一致同步架构。不做跨服务分布式事务，而是靠幂等重放收敛一致。

```text
引擎重大变更事件
  -> sync-service 编排器
  -> 校验配置 config_hash
  -> 创建 sync_run
  -> Canary：选 1 个代表产物同步到 Gitee / Feishu / Supabase
  -> 验证 Canary
  -> 全量同步剩余产物
  -> 逐项验证
  -> 更新 artifact_state
```

核心状态表：

```sql
sync_run(
  event_id TEXT UNIQUE,   -- 幂等键
  run_id TEXT,
  change_id TEXT,
  change_seq BIGINT,
  status TEXT,
  config_hash TEXT
)

artifact_state(
  sink TEXT,              -- gitee / feishu / supabase
  logical_path TEXT,
  current_sha TEXT,
  applied_seq BIGINT,
  target_ref TEXT,        -- Gitee commit / Feishu file_token / Supabase path
  synced_modified_time TIMESTAMPTZ,
  engine_managed BOOLEAN DEFAULT TRUE
)
```

产物路径建议沿用归档系统一级分类：`alarm/`、`variation/`、`selection/`、`feedback/`，避免另建分类体系。

---

### 二、幂等性设计

整体幂等键：

- 事件层：`event_id` 唯一，重复消费直接返回已有 `run_id`。
- 产物层：`(sink, logical_path, change_seq, content_sha256)` 决定是否需要写目标端。
- 目标层：每个目标端都有可重试操作。

核心判断逻辑：

```python
def should_apply(sink, path, incoming):
    st = get_state(sink, path)

    if st is None:
        return APPLY

    # 旧事件，跳过
    if st.applied_seq > incoming.change_seq:
        return SKIP

    # 同一事件
    if st.applied_seq == incoming.change_seq:
        if st.current_sha == incoming.content_sha:
            return SKIP  # 已应用
        else:
            return CONFLICT  # 同序号不同内容，需人工处理

    # 新事件，应用
    return APPLY
```

### 三、各目标端幂等与冲突处理

| 目标端 | 幂等手段 | 冲突处理 |
|---|---|---|
| Gitee | commit message 带 `Sync-Run: <run_id>`；提交前 `git diff --quiet`；push 前检查远端是否已包含该 commit | 先 `fetch` + `rebase`；rebase 冲突则 `abort` 并标记 conflict；不 force push；受保护分支走 PR |
| Feishu | 用 `artifact_state` 中的 `file_token`；上传请求带 `request_id`；内容 sha 相同则跳过 | 若 `modified_time` 晚于上次同步，说明人工改过，不覆盖，复制到 `_conflict/` 并告警；否则覆盖或创建新版本 |
| Supabase Storage | 固定路径 + `upsert: true`；对象 metadata 存 `content_sha256` 和 `change_seq` | 读 metadata 比较 `change_seq`；旧事件跳过；同 seq 不同 sha 报冲突；低 seq 则 upsert |

#### Gitee 示例

```bash
git fetch origin

if ! git merge-base --is-ancestor origin/main HEAD; then
  git rebase origin/main
  if [ $? -ne 0 ]; then
    git rebase --abort
    mark_conflict "gitee" "$path"
    return
  fi
fi

git push origin HEAD:main
```

#### Feishu 示例

```python
if state.exists and state.current_sha == content_sha:
    return skip

meta = feishu.get_file_meta(state.file_token)

if meta.modified_time > state.synced_modified_time:
    # 人工改过，不覆盖
    feishu.upload_to_folder(CONFLICT_FOLDER, file)
    mark_conflict("feishu", path)
    return

new_token = feishu.upload(
    file,
    request_id=f"{run_id}:{path}:{content_sha}"
)

update_state("feishu", path, new_token, content_sha, meta.modified_time)
```

#### Supabase 示例

```python
meta = storage.get_metadata(path)

if meta and meta.change_seq > incoming.change_seq:
    return skip

if meta and meta.change_seq == incoming.change_seq:
    if meta.content_sha == incoming.content_sha:
        return skip
    else:
        mark_conflict("supabase", path)
        return

storage.upload(
    path,
    file,
    {
        "upsert": True,
        "metadata": {
            "content_sha256": incoming.content_sha,
            "change_seq": incoming.change_seq,
            "sync_run_id": run_id,
        },
    }
)
```

### 四、触发与执行流程

1. **重大变更识别**  
   引擎发出 `engine.major_change` 事件，包含：

   ```json
   {
     "event_id": "evt_001",
     "change_id": "chg_001",
     "change_seq": 42,
     "outputs": [
       {"logical_path": "selection/quality_rules.md", "content_sha256": "abc..."}
     ],
     "canary": "selection/quality_rules.md"
   }
   ```

2. **配置校验**  
   每次执行前读取配置并计算 `config_hash`，与启动时不一致则重新加载。配置项包括超时、分类映射、保护路径、自动提交开关。

3. **Canary 先行**  
   先同步 1 个代表产物到三个目标端并验证。任一目标端失败或冲突，则整个 run 暂停并告警；成功后再全量。  
   这符合“先潜水，后行动；用小测试换判断力”。

4. **全量同步**  
   按 `outputs` 列表逐项同步，已完成项通过 `artifact_state` 跳过。

5. **验证**  
   - Gitee：`git rev-parse HEAD` 与远端一致，且 commit message 含 `Sync-Run`。  
   - Feishu：通过 `file_token` 读取元信息，确认 `modified_time` / `size` 已更新。  
   - Supabase：读取对象 metadata，确认 `content_sha256` 和 `change_seq` 正确。

### 五、超时与重试

```python
SYNC_TIMEOUTS = {
    "gitee_push": 120,
    "feishu_upload": 300,
    "supabase_upsert": 60,
    "model_call_B_turbo": 300,
    "model_call_A": 600,
}
```

失败重试使用指数退避：`1s / 5s / 15s / 60s`，最多 3 次。重试仍失败则标记 `partial`，保留状态表，待修复后重放同一 `run_id`。整个过程可重入，不产生重复产物。

### 六、避坑与配置同步

- **配置修改必须同步修改读取点**：配置存于统一 store；sync-service 启动和每次 run 前都读取并比较 `config_hash`。修改后立即执行一次 `config_self_check`，模拟 canary，确保新配置已生效。
- **飞书上传**：使用 `tenant_access_token`，不要依赖扫码连接器；上传前检查应用权限 `drive:drive`，并确认目标 `folder_token` 存在。
- **Gitee**：使用 deploy key 或 bot 账号 token，禁止使用个人密码；受保护分支不自动 push，改为创建 PR。
- **Supabase**：service role key 只在服务端使用；上传前确保 bucket 存在，否则用 admin API 创建。

---

### 七、最终一致性

三方同步不是原子事务，采用 saga 模式：

- 某一步失败不自动回滚已成功步骤，只标记 `partial`。
- 重放同一个 `run_id` 时，已成功步骤通过 `artifact_state` 跳过。
- 如果确实需要回滚，不直接删除，而是生成一个新的反向变更并同步三方。

这样在「短期供给刚性」和「功能熵约束」下，同步链路本身也是可控、可观测、可校准的负熵输入，不会因为重复或冲突引入新的熵增。
