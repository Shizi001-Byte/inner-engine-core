# 任务类型: eng

以下方案直接基于“同步单位是 block，不是 file；文件只是有序 block id 列表的索引”落地，不再重复论证。

## 一、系统定位

接收“任务完成事件”，自动完成：

- 任务自动分类
- 自动打标签
- 按规则存入对应目录
- 归档过程以 block id 列表为最小核对单位，支持差异分析、校验、回滚

---

## 二、总体流程

```text
任务完成事件
    → 采集任务产物与元数据
    → 自动分类
    → 自动打标签
    → 目录映射决策
    → block 级归档执行
    → SOP 校验
    → 更新索引 / 必要时回滚
```

---

## 三、Block 模型落地

每个文件切分为逻辑 block，block id 建议使用内容 hash，例如 `SHA256(block_content)`。

文件归档信息不是“文件路径 + 大小 + mtime”，而是：

```json
{
  "path": "designs/foo.sketch",
  "block_ids": ["b1", "b2", "b3"]
}
```

归档系统内部存储：

- `block_store`：保存所有 block 内容
- `file_manifest`：保存文件路径 → 有序 block id 列表

因此“文件”本质上是索引，block 才是真正的数据单位。

---

## 四、自动分类、打标签、目录映射

### 1. 自动分类

分类输入：

- 任务元数据
- 产物清单
- 任务类型
- 已有规则或模型输出

策略：

- 优先走确定性规则
- 规则未命中时调用模型分类

### 2. 自动打标签

标签分两类：

- 系统标签：`task_id`、`project`、`owner`、`date`、`source_engine`
- 语义标签：模型从任务内容中提取，如 `risk=high`、`type=bugfix`

### 3. 目录映射

目录由分类和标签共同决定，例如：

```text
/archive/{category}/{yyyy}/{mm}/{dd}/{task_id}/
```

同时生成 tag 索引目录：

```text
/archive/tags/{tag}/{task_id} -> 实际归档目录
```

目录映射规则必须配置化，并经过配置中心统一管理。

---

## 五、配置管理：避免“修改后未生效”

所有配置统一通过 `ConfigService` 读取，禁止业务代码中散落配置读取点。

新增配置时必须同步完成：

1. 在配置中心定义配置项
2. 在代码中新增 `ConfigKeys.XXX`
3. 通过 `ConfigService.get(ConfigKeys.XXX)` 读取
4. 发布后执行一次冒烟任务，验证配置真实生效

配置变更流程：

```text
配置中心发布
    → ConfigService reload
    → 推送新版本到实例
    → 自动跑 smoke test
    → 确认分类/标签/目录结果符合预期
```

---

## 六、超时控制：避免 API 调用挂死

模型调用超时按模型类型预设：

| 模型 | timeout |
|---|---|
| B 模型 turbo | 300 秒 |
| A 模型 | 600 秒 |

连接超时建议单独设置，例如 10 秒。

模型调用超时后：

- 最多重试一次
- 仍失败则降级到规则分类
- 任务标记为 `classify_source=rule_fallback`
- 不让归档任务一直阻塞

归档传输也按 block 级别设置超时，避免整个文件重传导致超时。

## 七、同步 / 差异分析 / 回滚判定

### 差异分析

比较源和目标时，只比较 `block_ids` 列表：

```python
source_block_ids = [b1, b2, b3]
target_block_ids = [b1, b3, b2]

if source_block_ids != target_block_ids:
    # 即使文件名、大小、mtime 相同，也是不同步
    return "DIFF"
```

差异结果包含：

- 缺失 block
- 多余 block
- 顺序不一致的 block

### 传输

修改一个 block 时，只传输该 block，并更新 file manifest。

例如：

```text
源文件 block_ids: [b1, b2_new, b3]
目标文件 block_ids: [b1, b2_old, b3]
传输日志中只出现：b2_new
```

禁止出现整个文件全量重传。

### 回滚

归档前保留上一版 manifest：

```text
manifest.json
manifest.prev.json
```

回滚时：

1. 读取 `manifest.prev.json`
2. 恢复旧 block id 列表
3. 从 block store 重新物化目标文件
4. 回滚判定同样以 block id 列表为准

## 八、认知质检 SOP 三条门禁

### 门禁 1

同步、差异分析、回滚判定，一律以 block id 列表为最小核对单位。

### 门禁 2

文件存在、大小、mtime、整体文件 hash，都不能替代 block 级校验。

### 门禁 3

自动化冒烟测试必须覆盖以下两个样本：

1. 构造“同文件名、同大小、同 mtime，但 block id 顺序不同”的样本，跑 SOP 必须判为不同步。
2. 修改一个 block 的内容/ID，运行同步，断言传输日志只出现该 block，不能出现整个文件全量重传。

## 九、核心数据模型

```text
block:
    block_id
    content_ref
    size
    created_at

file_manifest:
    path
    block_ids
    version
    task_id
    updated_at

archive_task:
    task_id
    category
    tags
    target_dir
    manifest_version
    status
    created_at

archive_config:
    config_key
    config_value
    version
    updated_at
```

## 十、落地效果

- 任务完成即可自动归档
- 归档产物分类清晰、标签完整、目录可预期
- 归档过程以 block 为最小单位，避免全量重传
- 配置修改可验证生效
- 模型调用超时可控
- 同步异常可基于 block id 列表准确回滚
