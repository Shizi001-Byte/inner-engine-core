# 任务类型: eng

下面直接基于已锚定的边界做推演，不再重复论证。设计目标：**设计引擎产出物 → 自动分类 → 打标签 → 存入对应归档目录**。

## 一、总体架构

```
设计引擎
   │
   ▼
Intake API ──► archive_task (任务表)
   │
   ▼
Dispatcher ──► 选择模型档位，CAS 更新任务状态
   │
   ▼
ModelClient Worker Pool（唯一允许并发阶段）
   │  只写 classification_results，不改 task.status
   ▼
PostProcessor（单消费者）
   │  校验结果、规范化标签、映射目录、归档、CAS 更新任务状态
   ▼
Object Storage / 归档目录
```

关键角色：

- `Intake API`：创任务，初始状态 `PENDING`
- `Dispatcher`：认领任务，决定用 B_TURBO 还是 A 模型
- `ModelClient`：调用外部模型，只写 `classification_results`
- `PostProcessor`：单消费者处理结果，做后处理
- `StateManager`：所有 `task.status` 变更的唯一入口，带 `version` 乐观锁
- `Sweeper`：兜底超时，写 TIMEOUT 结果，避免任务卡死
- `ConfigService`：统一配置快照，配置变更可验证

---

## 二、状态机

```
PENDING ──► CLASSIFYING ──► ARCHIVING ──► DONE
                │                │
                │                ▼
                │             FAILED（归档失败）
                │
                ├── 可重试 ──► PENDING
                ├── 低置信度 ──► NEEDS_REVIEW
                └── 不可重试 ──► FAILED
```

所有状态变更必须走 `StateManager`，并且使用乐观锁：

```sql
UPDATE archive_task
SET status = :new_status,
    version = version + 1,
    updated_at = now()
WHERE id = :task_id
  AND status = :expected_status
  AND version = :expected_version;
```

如果 `affected_rows = 0`，说明状态已被其他流程修改，当前操作视为过期操作，直接丢弃或重试。

## 三、数据模型

### 1. `archive_task`

```sql
CREATE TABLE archive_task (
    id UUID PRIMARY KEY,
    source_uri TEXT NOT NULL,
    metadata JSONB,
    priority TEXT,
    compute_weight NUMERIC,

    status TEXT NOT NULL,
    version INT NOT NULL,
    current_attempt INT NOT NULL DEFAULT 0,

    model_tier TEXT,
    timeout_seconds INT,
    config_version TEXT,

    tags JSONB,
    target_directory TEXT,
    archived_path TEXT,
    error TEXT,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### 2. `classification_results`

```sql
CREATE TABLE classification_results (
    id UUID PRIMARY KEY,
    task_id UUID NOT NULL,
    attempt_no INT NOT NULL,
    model_tier TEXT NOT NULL,

    result_status TEXT NOT NULL, -- SUCCESS / TIMEOUT / ERROR
    raw_payload JSONB,
    suggested_tags JSONB,
    confidence NUMERIC,
    error_code TEXT,
    latency_ms INT,
    config_version TEXT,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    processed_at TIMESTAMPTZ,

    UNIQUE(task_id, attempt_no)
);
```

硬性约束：

- `ModelClient` 只能 `INSERT / SELECT` `classification_results`
- `ModelClient` 对 `archive_task` 没有任何 `UPDATE` 权限
- 数据库权限层直接禁止 API 调用方改任务状态

## 四、核心流程

### 1. 接入

设计引擎调用：

```http
POST /v1/archive/tasks
```

```json
{
  "source_uri": "s3://design-engine/staging/task-123.design",
  "metadata": {
    "name": "api-design-v3",
    "created_at": "2025-06-01T10:00:00Z"
  },
  "priority": "NORMAL"
}
```

系统创建任务：

```text
status = PENDING
version = 1
current_attempt = 0
```

同时根据输入大小、复杂度计算 `compute_weight`。

---

### 2. 分类阶段（允许并发）

`Dispatcher` 扫描 `PENDING` 任务，选择模型档位：

- 默认使用 `B_TURBO`
- 如果 `compute_weight` 超过阈值，或 `priority = URGENT`，使用 `A`

认领任务时原子更新：

```sql
UPDATE archive_task
SET status = 'CLASSIFYING',
    current_attempt = current_attempt + 1,
    model_tier = :model_tier,
    timeout_seconds = :timeout_seconds,
    config_version = :config_version,
    version = version + 1,
    updated_at = now()
WHERE id = :task_id
  AND status = 'PENDING'
  AND version = :expected_version;
```

`ModelClient` 并发调用模型：

- 只负责调用 API
- 只写 `classification_results`
- 不修改 `task.status`
- 超时写 `result_status = 'TIMEOUT'`
- 错误写 `result_status = 'ERROR'`

```sql
INSERT INTO classification_results (
    task_id, attempt_no, model_tier,
    result_status, raw_payload, suggested_tags,
    confidence, error_code, latency_ms, config_version
)
VALUES (
    :task_id, :attempt_no, :model_tier,
    :result_status, :raw_payload, :suggested_tags,
    :confidence, :error_code, :latency_ms, :config_version
)
ON CONFLICT (task_id, attempt_no) DO NOTHING;
```

---

### 3. 后处理阶段（必须单消费者）

`PostProcessor` 是唯一消费者，逐条处理 `classification_results`。

处理逻辑：

1. 读取一条未处理的分类结果
2. 检查 `result.attempt_no == task.current_attempt`
3. 检查 `task.status == 'CLASSIFYING'`
4. 如果结果有效：
   - 校验置信度
   - 用 `tag_dictionary` 规范化标签
   - 用 `directory_rules` 映射归档目录
   - CAS 更新任务到 `ARCHIVING`
   - 执行归档
   - CAS 更新任务到 `DONE`
5. 如果结果可重试：
   - CAS 更新任务回到 `PENDING`
6. 如果结果不可重试：
   - CAS 更新任务到 `FAILED` 或 `NEEDS_REVIEW`

单消费者保障：

```text
PostProcessor 启动时获取 PostgreSQL advisory lock；
只有拿到锁的实例才允许消费结果；
其他实例 standby，不参与后处理。
```

归档操作必须幂等：

```text
如果目标文件已存在且 checksum 一致，直接返回已有路径；
否则 copy + 校验 + delete source。
```

## 五、超时分级

配置：

```yaml
model_timeouts:
  B_TURBO: 300   # 秒
  A: 600         # 秒
```

`ModelClient` 必须使用“总超时”，不是只配 connect/read 超时：

```text
timeout = total_timeout = 300 / 600 秒
```

同时增加 `Sweeper` 兜底：

- 扫描 `status = CLASSIFYING` 且 `updated_at < now() - timeout_seconds - grace_period` 的任务
- 如果没有对应结果，则写入一条 `result_status = 'TIMEOUT'` 的 `classification_results`
- `ON CONFLICT DO NOTHING`，避免覆盖真实结果
- 不直接改任务状态，由 `PostProcessor` 统一处理

这样避免：

```text
API 调用超时后任务一直停留在 CLASSIFYING
```

## 六、配置同步与验证

所有配置集中在一个 `config` 表：

```sql
CREATE TABLE config (
    version TEXT PRIMARY KEY,
    config_json JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

任务在 `Dispatcher` 认领时记录 `config_version`，后续所有处理使用同一份不可变配置快照。

读取点必须收敛：

- `model_timeouts`：只由 `ModelClient` 读取
- `tag_dictionary`：只由 `PostProcessor` 读取
- `directory_rules`：只由 `PostProcessor` 读取
- `cost_params`：只由 `BillingService` 读取

配置变更后立即验证：

```http
POST /internal/config/verify
```

系统创建一个 canary 任务，输入已知样本，断言：

- 分类结果正确
- 标签正确
- 归档目录正确
- 超时配置正确

验证失败则自动回滚到上一个配置版本。

## 七、成本模型

A 模型更贵不是因为更快，而是因为它占用稀缺紧急调度资源。

成本公式：

```text
compute_weight = f(input_size, complexity_score)

price_B = base_price_B * compute_weight

price_A = base_price_A * (1 + γ_A * (compute_weight - 1))
```

其中：

- `base_price_A > base_price_B`
- `γ_A` 是 A 模型的重计算价格抬升系数
- 计费不依赖实际耗时，因此“A 更快”不是定价理由

因此模型选择原则是：

```text
能用 B_TURBO 就不用 A；
A 只用于高复杂度、紧急、或 B_TURBO 失败升级场景。
```
