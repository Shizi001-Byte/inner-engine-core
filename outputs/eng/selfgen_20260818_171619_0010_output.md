# 任务类型: eng

## 推演：Supabase 记忆脑增量同步方案

### 0. 定位

增量同步不是“文件备份工具”，而是**认知闭环的血管**。  
同步后必须触发“注入候选刷新”，否则记忆脑会变成静态档案库。

同步链路必须满足：

```text
本地文件变化
  -> 解析 + 增量 diff
  -> 只同步变更部分到 Supabase
  -> 冲突处理 + 版本留痕
  -> 刷新注入候选
  -> 调度器在后续任务中真正使用新认知
```

---

### 1. 总体架构

```text
本地记忆文件（Markdown / JSON / YAML）
        │
        │ chokidar / fs.watch
        ▼
本地状态文件 .sync-state.json
        │
        ▼
Diff 引擎：按 entry 计算 hash，只取变更部分
        │
        ▼
Supabase 增量写入：upsert / soft delete / conflict
        │
        ▼
刷新注入候选池（injection_candidate）
        │
        ▼
任务调度器读取新认知，参与任务注入
```

---

### 2. 检测本地文件变化

#### 2.1 监听方式

- 使用 `chokidar` 监听本地记忆目录。
- `debounce` 500ms ~ 2000ms，避免频繁写入时重复触发。
- 不直接用 `fs.watch`，因为递归监听、原子写入、事件丢失在不同平台不可靠。

#### 2.2 状态文件

维护 `.sync-state.json`：

```json
{
  "version": 1,
  "files": {
    "memories/agent.md": {
      "mtime": 1710000000,
      "hash": "sha256:...",
      "entries": {
        "mem_001": {
          "hash": "sha256:...",
          "updated_at": "2025-03-10T00:00:00Z"
        }
      }
    }
  }
}
```

#### 2.3 按 entry 做 diff，而不是按文件

如果整个文件作为一个整体同步，会有三个问题：

- 单条记忆变化会触发整个文件上传；
- 冲突范围大；
- 无法精准处理单条删除。

所以解析文件时按记忆块拆分：

- Markdown 可按 `##` / `---` 分块；
- JSON 可按数组元素分块；
- YAML 可按 `- id:` 分块。

每个记忆块必须有：

```text
id
content
metadata
created_at
updated_at
version
```

本地文件变化后：

```text
读取文件
  -> 解析成 entries
  -> 对每个 entry 计算 hash
  -> 与 .sync-state.json 对比
  -> 新增/修改/删除
  -> 只把变更的 entries 写入 Supabase
```

---

### 3. 只同步变更部分

#### 3.1 变更类型

| 本地状态 | 远端状态 | 动作 |
|---|---|---|
| 新增 entry | 不存在 | `upsert` |
| hash 变了 | 存在 | `upsert`，带上新版本号 |
| 文件删除 / entry 消失 | 存在 | 软删除 `deleted_at` |
| 无变化 | 无变化 | 跳过 |

#### 3.2 批量写入

- 使用 Supabase `upsert`：
  ```js
  supabase
    .from('memories')
    .upsert(changedEntries, { onConflict: 'id' })
  ```
- 批量大小建议 `50` 条一批。
- 不要全表覆盖，不要删除重建。

#### 3.3 软删除

删除时不要物理删除，写 `deleted_at`，否则：

- 冲突恢复困难；
- 多端同步时容易“复活”；
- 历史审计丢失。

---

### 4. 冲突处理

#### 4.1 冲突定义

同一 `id` 的记忆，本地和远端都在未同步期间发生了变化：

```text
本地 updated_at > last_sync_at
远端 updated_at > last_sync_at
```

#### 4.2 默认策略：版本时间戳 + 来源优先级

- 比较 `updated_at`，较新者胜；
- 如果时间戳相同，按来源优先级：
  ```text
  人工编辑 > 本地脚本 > 任务生成
  ```
- 任何覆盖发生前，先把旧版本写入 `memory_versions` 表。

#### 4.3 冲突不自动吞掉

发生冲突时：

1. 把本地版本和远端版本都保存到 `memory_conflicts`；
2. 按默认策略自动选择胜者；
3. 胜者写入主表；
4. 败者留在冲突表，可后续人工处理。

#### 4.4 删除冲突

如果一端删除，另一端修改：

- 禁止直接删除；
- 把修改视为“复活”，写入冲突表；
- 默认保留修改，不保留删除。

---

### 5. 避免 schema 写死

基建脚本危险点在于把表结构假设写死。  
同步脚本不能硬编码字段名。

做法：

```text
1. 启动时执行 ensureSchema()
2. 通过 information_schema 或 Supabase SDK 获取当前表结构
3. 动态构造列映射
4. 所有字段变更走 migration，不写在同步逻辑里
```

示例思路：

```js
const columns = await getTableColumns('memories');

const safeEntry = {};
for (const key of Object.keys(entry)) {
  if (columns.includes(key)) {
    safeEntry[key] = entry[key];
  }
}
```

这样即使表结构演化，同步脚本也不会因为“假设字段存在”而崩溃。

---

### 6. 防止“配置修改后不生效”

历史坑：改了配置，但读取点没改，行为无变化。

所以在同步方案中，配置变更必须同步修改读取点：

- 如果新增了 `sync.enable_injection_refresh`，必须在调度器注入逻辑里同步读取；
- 修改后立即跑一次自检：
  ```text
  dry-run 同步一条测试记忆
  验证注入候选池是否出现
  验证下一轮任务是否真正读取到
  ```

---

### 7. 调用设限：超时、重试、限流

#### 7.1 Supabase API

- 单次请求超时：`10s`；
- 重试次数：3 次；
- 重试策略：指数退避；
- 并发上限：5；
- 批量上限：50。

#### 7.2 如果同步过程中调用 LLM

例如记忆清洗、去重、摘要：

- A 模型：`timeout = 600s`
- B 模型（turbo）：`timeout = 300s`

不能所有模型共用一个超时时间。

#### 7.3 B 模型质量检测规则独立

历史坑：B 模型 reasoning 占比 70% ~ 82% 被误判为废稿。

在记忆写入/清洗阶段：

- B 模型跳过 reasoning 占比检测；
- 不同模型使用独立质量规则；
- 不要用 A 模型的阈值卡 B 模型。

---

### 8. 认知新鲜度：同步后必须注入

#### 8.1 同步完成事件

同步不只是写库，还要发出事件：

```text
memory.synced
```

调度器监听该事件，把新记忆 ID 推入注入候选池。

#### 8.2 注入新鲜度检查

每 10 个任务或每轮结束后执行：

```sql
-- 最近 30 分钟新增认知
select count(*)
from injection_candidate
where created_at > now() - interval '30 minutes';

-- 最近 30 分钟新认知被实际注入的次数
select count(*)
from injection_candidate
where created_at > now() - interval '30 minutes'
  and last_injected_at is not null;
```

要求：

```text
新增认知数 > 0 时，注入数必须 > 0
```

如果新增认知从未被注入，立即告警。

---

### 9. 闭环不开放：任务认知必须回写

任务执行后产生的新认知，必须通过同一条增量同步链路写回 Supabase，不能绕过：

```text
任务输出
  -> memoryBrain.write()
  -> 本地文件 / 直接同步
  -> Supabase
  -> 注入候选池
  -> 影响后续任务
```

如果新认知只写入数据库，但不进入注入池，那么认知池再大也是静态档案库。

---

### 10. 双向同步防回声循环

如果本地和 Supabase 都要监听，需要防止同步回声：

```text
本地写入 -> 同步到远端 -> 远端 Realtime 触发 -> 再写回本地 -> 再触发同步...
```

解决方案：

- 每次同步前，把当前操作标记为 `_syncing = true`；
- 写入完成后更新 `.sync-state.json`；
- 监听事件时，如果 hash 未变化，直接忽略。

---

### 11. 最终质检清单

| 检查项 | 要求 |
|---|---|
| 增量同步 | 只同步变更 entry，不整文件覆盖 |
| 冲突处理 | 有版本留痕，有冲突表，不静默覆盖 |
| schema 假设 | 动态获取字段，不硬编码 |
| 超时 | Supabase 10s，A 模型 600s，B 模型 300s |
| B 模型质检 | 跳过 reasoning 占比检测 |
| 注入新鲜度 | 每 10 任务检查，新增认知注入率 > 0 |
| 闭环 | 任务新认知必须回写并进入注入池 |
| 配置生效 | 修改配置后立即验证读取点 |

---

### 12. 落地顺序

1. 先建 `.sync-state.json` 和解析器；
2. 先做 dry-run 模式，只输出 diff；
3. 再做增量 upsert；
4. 再加冲突表和版本表；
5. 再接入注入候选池；
6. 最后加新鲜度检查。

这样每一步都可验证，不会把风险堆到最后。
