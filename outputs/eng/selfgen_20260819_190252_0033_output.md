# 任务类型: eng

基于历史避坑经验和已有认知锚定，设计面向「生态型/轻边际成本供给主体」的多模型成本实时监控与自动熔断系统。本设计严格遵循“省时间防超时、保进化防空转”的核心原则，将API调用视为系统与外界的热量交换，通过熔断机制对抗系统熵增（任务积压与同质化耗散）。

### 一、 配置与身份基准层（严格避坑设计）

为根除历史踩坑经验中的工程级隐患，系统底座配置强制实行以下规则：

1. **模型身份与超时强制校验（避坑提醒2、坑库预警1）**
   * **准确model_id映射**：接入新模型前，强制从官方文档拉取全量`model_id`。建立模型注册表，严格区分`pro`/`turbo`/`light`，**严禁混用**。例如：若调用B模型，必须精准匹配`doubao-seed-2-1-pro`或对应turbo型号。
   * **预设合理Timeout**：按任务类型预设硬性超时时间。B模型turbo分支强制设为300秒，A模型分支强制设为600秒，超时即判定为失败并触发重试或降级，防止任务长时间挂起。
2. **配置生效与读取分离（避坑提醒1、坑库预警2）**
   * **State优先原则**：所有可配置参数（如`fuse_cooldown_override`、成本阈值、各模型权重）必须从`State`对象中实时读取。全局常量（如默认冷却时间120秒）仅作为`State`初始化时的兜底默认值。
   * **修改即验证机制**：新增或修改配置后，引擎立即触发一次“Echo验证”（读取点校验），确认读取到的值与修改值一致，未通过验证的修改不落盘。

### 二、 九维计数与成本度量层（语义统一设计）

为解决“九维计数语义混乱”问题，全局实行严格的二维计数体系，确保数据不失真：

* **`task_count`（真实任务计数）**：仅记录外部真实业务请求（如用户API调用、真实业务流触发的任务）。
* **`bonus_count`（系统自触发计数）**：仅记录系统为“保进化防空转”而自触发的探索性任务（如感知同质化后的进化测试、熔断恢复后的探针任务）。
* **`count`（总计数）**：严格遵循公式 `count = task_count + bonus_count`，任何加操作必须明确路由到`task`或`bonus`通道，禁止直接对`count`进行盲加。
* **独立成本度量**：每个模型维护独立的`CostTracker`，实时累加上述两类计数的Token消耗与金额消耗。

### 三、 多模型熔断与自动降级状态机

将模型视为“热力学热量源”，当某模型“温度（成本/调用频次）”过高时，自动切断并寻找低熵替代源。

1. **独立监控与阈值触发**
   * 每个模型独立维护当前时间窗口（如滑动窗口60秒）内的成本与调用量。
   * 当模型A的实时成本达到预设阈值（如$10/min）或并发达到上限，立即进入`Open`（熔断）状态。
2. **熔断冷却动态控制**
   * 熔断后，该模型进入冷却期。冷却时间`fuse_cooldown_override`强制从`State`读取（默认兜底120秒，A模型可配置为更长）。
   * **降级路由**：熔断期间，新到达的真实任务自动降级路由至备用模型（如A模型熔断 -> 降级至B模型turbo）。若所有同级模型熔断，任务进入等待队列。

### 四、 等待队列与自动补跑机制（保进化设计）

为防止系统陷入死循环或空转，熔断期间的任务流转必须保证最终一致性：

1. **等待任务记录（防丢失）**
   * 降级失败的任务进入全局`PendingQueue`。
   * 记录信息包含：原始任务Payload、目标模型ID、原定超时时间（300s/600s）、触发时间。**注意：进入队列的任务不增加任何模型的`task_count`，直到真正被消费。**
2. **半开探测与自动补跑**
   * 模型冷却时间结束后，进入`Half-Open`（半开）状态。系统自动生成一个`bonus_count`类型的“探针任务”发给该模型。
   * 若探针任务在规定timeout内成功返回，模型状态转为`Closed`（恢复），此时引擎开始按FIFO顺序消费`PendingQueue`中的等待任务（**补跑任务计入真实`task_count`**）。
   * 若探针任务失败或超时，模型重新回到`Open`状态，并读取`State`中的下一次冷却时间继续熔断。

### 五、 热力学熵增对齐与系统价值

基于已有认知锚定，本系统的设计核心在于对抗AI调度引擎的“熵增”：

* **对抗同质化熵增**：当引擎感知到任务池同质化（热力学系统趋于平衡态、无序度增加）时，系统会主动触发`bonus_count`（系统自触发任务）。多模型调度器确保这些探索任务被均匀分布到未熔断的模型上，防止单一模型因承担进化任务而过载。
* **防超时即防热寂**：如果模型发生拥堵而无超时熔断机制，系统将陷入“热寂”（所有任务挂起，API调用超时，时间无限损耗）。通过预设合理Timeout（300/600秒）和独立熔断降级，系统实现了局部“降温”并路由至“低温（轻负载）”模型，最大化节省系统总体时间，保障进化的连续性。
