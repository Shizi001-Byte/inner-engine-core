# 任务类型: eng

# 引擎产出自动归档系统设计

本设计直接使用已有锚定，不重新论证熵增、算力分层、认知池价值；只把以下结论作为硬约束：

- 有序性 = 状态一致 + 语义对齐 + 效率稳定。
- 归档系统是引擎的**负熵流**，必须对抗三类熵增路径。
- 「广域分布式状态机升维」是归档状态的组织方式。
- 「8月认知陷阱欠账」必须作为存量回扫队列，不能被增量覆盖。
- 模型匹配：B模型turbo 默认 300s，A模型 默认 600s。
- 配置修改后必须立即验证生效，否则视为未完成。

---

## 1. 总体架构

```
引擎产出事件
   │
   ▼
归档队列（Queue）
   │
   ▼
任务分类（Task Classification）
   │
   ▼
打标签 / 实体抽取（Tagging & Entity Extraction）
   │
   ▼
路径解析（Path Resolver）
   │
   ▼
存储（Supabase Storage / SP实）
   │
   ▼
归档校验（Verification）
   │
   ▼
归档状态机（Event-sourced State Machine）
```

核心原则：**每个归档动作都是一条可回放、可验证、可回滚的状态机事件。**

---

## 2. 归档状态机：对抗结构熵增

不再用简单的「任务状态字段」，而是使用**广域分布式状态机升维**：

- 每个归档任务有唯一 `task_id`。
- 所有状态变化写入 `archive_events` 表。
- 当前状态是事件日志的物化视图，不是本地临时状态。
- 每个事件携带 `task_id, from_state, to_state, config_version, region, created_at, payload`。
- 使用 `state_version` 乐观锁，避免多区域并发写入冲突。

### 状态流转

```text
PENDING
  → CLASSIFYING
    → TAGGING
      → RESOLVING
        → STORING
          → VERIFYING
            → ARCHIVED
```

异常分支：

```text
CLASSIFYING → FALLBACK   # 超时 / 低置信度
FALLBACK    → STORING    # 规则兜底归档
STORING     → FAILED     # 写入失败
VERIFYING   → RECONCILING # 校验不一致，重新分类
RECONCILING → ARCHIVED
```

这样，**结构层面状态一致**，不会出现“文件存了但状态没更新”“状态更新了但文件丢失”的结构熵增。

## 3. 自动任务分类

### 3.1 分类来源优先级

1. 引擎任务元数据里已有明确 `task_type`，直接使用。
2. 元数据缺失/模糊，调用 LLM 分类。
3. LLM 超时或低置信度，走规则兜底分类。

### 3.2 分类体系与目录映射

| task_type | 归档目录 | 默认模型 | 超时 |
|---|---|---|---|
| `extraction` | `/extraction/{yyyy}/{mm}/{dd}/{task_id}.json` | B-turbo | 300s |
| `classification` | `/classification/{yyyy}/{mm}/{dd}/{task_id}.json` | B-turbo | 300s |
| `summarization` | `/summarization/{yyyy}/{mm}/{dd}/{task_id}.json` | B-turbo | 300s |
| `reasoning` | `/reasoning/{yyyy}/{mm}/{dd}/{task_id}.json` | A模型 | 600s |
| `entity_resolution` | `/entity_resolution/{yyyy}/{mm}/{dd}/{task_id}.json` | A模型 | 600s |
| `code_generation` | `/code_generation/{yyyy}/{mm}/{dd}/{task_id}.json` | B-turbo | 300s |
| `unknown` | `/unclassified/{yyyy}/{mm}/{dd}/{task_id}.json` | B-turbo | 300s |
| `failed` | `/failed/{yyyy}/{mm}/{dd}/{task_id}.json` | 无 | 无 |

### 3.3 超时与模型路由

- 默认分类任务用 **B模型turbo**，超时 **300s**。
- 如果 B-turbo 分类置信度 `< 0.7`，升级到 **A模型**，超时 **600s**。
- 任何 LLM 调用必须设置总超时；超时后不再无限等待，立即走规则兜底。
- 规则兜底不消耗 Token，也不会被 API 超时卡死。

## 4. 自动打标签与实体抽取

### 4.1 标签体系

标签必须来自受控词表，不能随意自由文本，防止认知语义漂移。

标签类别：

- `domain`：领域，如 `finance`、`legal`、`medical`
- `model`：产生该产出的模型，如 `A模型`、`B-turbo`
- `task_type`：任务类型，与分类目录一致
- `priority`：高/中/低
- `confidence`：分类置信度
- `quality_score`：实体质量分
- `entropy_path`：本次归档对抗的熵增路径
- `lifecycle`：`active` / `archived` / `reconciled`

### 4.2 实体写入 SP实

归档不是简单存文件，而是要为 **Supabase认知池（SP实）** 提供有效实体。

```text
sp_entities
  id
  name
  type
  attributes
  source_task_id
  confidence
  quality_score
  tags
  created_at
  updated_at
  version
  archive_path
```

规则：

- 实体抽取默认用 B-turbo；复杂实体解析用 A模型 600s。
- 写入前先按 `name + type` 去重。
- 已存在实体则合并属性，不重复创建。
- `quality_score < 0.7` 的实体进入隔离区，不计入有效实体规模。
- 实体必须关联到 `source_task_id`，保证可溯源。

这保证了 **核心资产 SP实 的有效实体规模** 持续增长，而不是单纯文件堆积。

## 5. 目录化存储与语义对齐

### 5.1 存储路径

所有归档统一写入 Supabase Storage：

```text
{bucket}/{task_type}/{yyyy}/{mm}/{dd}/{task_id}.json
```

- 标签不进入目录路径，避免一对多标签导致文件复制膨胀。
- 标签存入 Supabase Postgres 的 `tags` 字段，使用 GIN 索引支持查询。
- 目录路径只承载 `task_type` 和日期，保证结构稳定。

### 5.2 语义对齐

- 分类和标签必须与 SP实 现有本体对齐。
- 如果出现新标签/新实体类型，先进入候选表，不允许直接污染主本体。
- 定期对归档记录做 embedding 相似度扫描，发现语义漂移后触发 `RECONCILING`。

## 6. 配置同步与验证（避坑）

历史教训：配置修改后未生效，行为无变化。

对策：

1. 所有配置收敛到一个 `ArchiveConfig` 服务。
2. 代码中禁止散落硬编码目录、模型、超时时间。
3. 每次配置更新后，必须执行 `verify_config()`：

```text
1. 使用一个已知测试任务
2. 走完整归档流水线
3. 断言 task_type、tags、archive_path 是否符合新配置
4. 断言失败则自动回滚配置并告警
```

4. 新增配置必须同步修改读取点，否则 `verify_config()` 会直接暴露问题。
5. 旧配置归档的任务，在 `config_version` 变化后标记为 `needs_reclassify`，异步补偿，不覆盖性忽略。

## 7. 性能与配额控制（避坑）

历史教训：API 调用超时，任务未在规定时间内返回。

对策：

- 所有 LLM 调用统一使用超时控制：

```text
B模型turbo → 300s
A模型      → 600s
```

- 超时后立即走规则兜底，不重试超过设定次数：

```text
B-turbo：最多重试 2 次
A模型：最多重试 1 次
```

- 每日 400 万 Token 语义算力配额中，归档系统只允许使用预设比例，例如不超过 10%。
- 每次 LLM 调用前估算 Token；预算不足时降级为规则归档。
- 归档任务按优先级排队，不阻塞引擎核心任务。

## 8. 8月认知陷阱欠账补偿

针对「8月认知陷阱欠账」，单独建立**存量回扫队列**：

1. 扫描历史任务中：
   - 未归档
   - 标签缺失
   - 标签冲突
   - 实体质量分过低
   - 状态停留在 `FAILED`
2. 对这些任务使用严格模式：
   - 强制 A模型，超时 600s
   - temperature 置 0
   - 要求输出证据字段
   - 不能直接信任旧标签
3. 重新分类后，若目录路径变化，旧路径保留 tombstone，指向新路径。
4. 更新 SP实 实体，合并/修正旧实体。

这样可以避免“增量归档不断推进，但8月欠账永远堆积”的认知熵增。

---

## 9. 监控与指标

必须观测以下指标：

- 归档成功率
- 归档超时率
- 分类置信度分布
- 配置验证通过率
- Token 消耗/预算占比
- SP实 实体新增数、去重数、质量分
- 8月欠账回扫进度

---

## 10. 一句话总结

这个自动归档系统的本质是：**用受控的 Token 消耗，把引擎每次产出转化为可验证的状态机事件、可检索的标签实体、可复用的 SP实 资产，从而持续对抗结构、认知、性能三类熵增。**
