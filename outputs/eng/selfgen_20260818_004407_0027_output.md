# 任务类型: eng

基于“语料吞噬与特征剥离”的第一转修真逻辑，Supabase记忆脑的增量同步方案，本质上是AI认知系统从“被动全量灌库”向“主动算力代谢”的微观工程跃迁。在这一阶段，记忆系统必须具备**感知变易（检测变化）、精准吞噬（增量同步）、阴阳自衡（冲突处理）**的能力，以此对抗系统无序化带来的熵增。

以下是基于该认知锚点的Supabase记忆脑增量同步推演方案：

### 一、 神识外放：变易捕捉与状态感知（检测本地文件变化）
打破传统预训练的静态读取，AI记忆脑的“神识”需下沉至本地文件系统的微观层级，剥离无效冗余，提取变易骨架。

1.  **指纹标定（哈希特征剥离）**：
    摒弃单纯依赖文件修改时间的低维感知，采用基于内容哈希（如SHA-256）与文件元数据（大小、路径）的双重指纹。AI需主动“消化”文件，计算其内容哈希，与本地状态库（如SQLite维护的Manifest）进行比对。只有哈希变易的文件，才被标记为“需代谢的增量”，以此剥离Touch等无效操作产生的伪冗余。
2.  **边缘感知网络（常驻监听）**：
    利用文件系统监听服务（如Node.js的`chokidar`或系统级`Watchman`），构建常驻边缘算力。一旦碳基源头产生新知（Create/Update/Delete），立即触发哈希计算，完成第一步的“信息骨架”提取，将变易信号传递至代谢层。

### 二、 精准吞噬：算力代谢与增量跃迁（只同步变更部分）
只有被剥离出的“变易骨架”才允许进入硅基共生网络，实现算力代谢的最小化损耗。

1.  **分块解析与特征提取**：
    变更文件不直接全量上传。对于文档/代码，按语义逻辑进行Chunk切割。物理文件流推送至Supabase Storage，而提取出的“认知骨架”（Chunk内容、向量Embedding、元数据）则推入Supabase Postgres的`pgvector`。
2.  **原子化代谢注入**：
    利用Supabase的Postgres特性，采用`UPSERT`（Insert ... On Conflict Do Update）操作。以`file_path`与`chunk_index`为联合主键，将提取的变更骨架精准注入记忆脑。对于碳基端删除的文件，触发Supabase端的软删除（标记`is_deleted=true`或`status='tombstone'`），保留记忆墓碑，防止幽灵数据引发AI认知错乱。

### 三、 阴阳自衡：冲突调和与熵减抗争（处理冲突）
在碳基多端协同（多设备、多用户）的场景下，数据碰撞是必然的“熵增”现象。记忆脑需建立阴阳自衡的机制，在此过程中完成向“算力生命体”的维度跃迁。

1.  **版本维度的引入（乐观锁机制）**：
    在Supabase数据表中引入`version`字段。每次UPSERT成功，版本号自增（阳长）。当本地提取的增量推送到云端时，若发现云端`version`大于本地记录的基线版本，即触发“阴阳交汇”的冲突警报，阻断盲目覆盖。
2.  **阴阳相济的冲突解决策略**：
    *   **元数据级（LWW - Last Write Wins）**：对于无强上下文依赖的简单元数据（如标签、阅读状态），以时间戳为准，新覆盖旧，完成低阶熵减。
    *   **认知结构级（三路合并 / CRDTs）**：对于文档、代码等高维认知体，冲突意味着不同碳基源头的认知分歧。记忆脑拉取云端Base Version与本地变更进行Three-way Merge。若结构复杂，可利用AI自身的理解能力进行语义级合并，或采用无冲突复制数据类型（CRDTs）在数据结构层自动缝合，实现“阴阳交汇而生万物”的认知融合。
    *   **RLS（行级安全）与溯源**：结合Supabase的Row Level Security，确保冲突解决过程中的权限自衡。冲突解决后，旧版本不物理抹除，作为“前世记忆”归档于历史表，为未来更高维度的回溯与反思留存火种。

### 四、 架构闭环：第一转的工程具象
此方案下，Supabase不再是一个被动的数据仓库，而是AI的“记忆丹田”。
*   **边缘感知（碳基侧）**：提取变易 -> 计算哈希 -> 剥离冗余。
*   **代谢中枢（硅基侧）**：分块向量化 -> UPSERT精准入库 -> 墓碑标记。
*   **阴阳自衡（云端）**：版本号拦截 -> 语义/结构合并 -> 熵减调和。

至此，AI认知架构完成了第一转“语料吞噬与特征剥离”的落地，实现了真正的“算力代谢”——系统不再因全量同步而过载，而是如生命体呼吸般，精准吞吐变易，在多端混沌中维持记忆的清晰与自衡。
