# 任务类型: eng

## 链式推演机制设计（V7.5 方舟效能引擎）

核心思路：**不用“一把大锁锁全部流程”**，而是用 **DAG 依赖图 + 每轮短锁状态机 + 锁外网络调用**。  
每个核心议题拆成 3~5 轮，上一轮输出作为下一轮输入；上一轮不完成，下一轮不调度。

---

## 1. 任务依赖图

默认采用 5 轮递进结构：

```mermaid
flowchart LR
    T[核心议题] --> R1[R1 议题界定]
    R1 --> A1[A1 问题树/约束/成功标准]
    A1 --> R2[R2 多维推演]
    R2 --> A2[A2 候选方案/论据]
    A2 --> R3[R3 对抗检验]
    R3 --> A3[A3 风险/反例/修正项]
    A3 --> R4[R4 综合收敛]
    R4 --> A4[A4 决策/取舍/行动项]
    A4 --> R5[R5 输出校验]
    R5 --> A5[A5 最终交付物]
```

依赖关系配置：

```yaml
rounds:
  r1:
    depends_on: []
    model: b_turbo
    timeout: 300
  r2:
    depends_on: [r1]
    model: b_turbo
    timeout: 300
  r3:
    depends_on: [r2]
    model: a_model
    timeout: 600
  r4:
    depends_on: [r3]
    model: a_model
    timeout: 600
  r5:
    depends_on: [r4]
    model: b_turbo
    timeout: 300
```

调度条件很简单：  
**只有上游 `state == COMPLETED` 且输出校验通过，下游才进入 `READY`。**

如果议题简单，可以合并为 3 轮：

```text
议题界定 → 推演生成 → 对抗收敛与输出校验
```

---

## 2. 每轮定义

| 轮次 | 职责 | 输入 | 输出 | 模型/超时 |
|---|---|---|---|---|
| R1 | 议题界定 | 核心议题 + 约束 | 问题树、边界、成功标准、未决问题 | b_turbo / 300s |
| R2 | 多维推演 | R1 输出 | 2~5 个候选方案/视角 + 依据 | b_turbo / 300s |
| R3 | 对抗检验 | R2 输出 | 风险清单、反例、可证伪边界、修正项 | a_model / 600s |
| R4 | 综合收敛 | R3 输出 | 最终决策、取舍理由、行动项 | a_model / 600s |
| R5 | 输出校验 | R4 输出 | 最终答案、校验清单、置信度 | b_turbo / 300s |

每轮输出必须结构化：

```json
{
  "round_id": "r3",
  "summary": "对候选方案的风险检验结果",
  "key_points": ["反例1", "边界条件1"],
  "open_issues": ["仍需确认的问题"],
  "next_focus": "下一轮必须优先处理的风险点",
  "confidence": 0.8
}
```

`open_issues` 和 `next_focus` 就是下一轮的“负熵输入”，防止模型泛泛而谈。

## 3. 执行模型：锁外调用 API

状态机：

```text
PENDING → RUNNING → POST_PROCESSING → COMPLETED
                          ↘
                         FAILED
```

锁设计：

- 锁只保护状态变更。
- 网络调用在锁外。
- 锁粒度是 `round_id`，不是整个任务。
- 锁 TTL 要短，比如 10 秒，不能等于 API 超时时间。

伪代码：

```python
def execute_round(r):
    # 1. 短锁：认领本轮，防止重复执行
    with lock(f"state:{r.id}"):
        if r.state != PENDING:
            return
        r.state = RUNNING

    # 2. 锁外：调用模型 API
    try:
        raw = model_api.call(
            model=r.model,
            prompt=build_prompt(r),
            timeout=r.timeout
        )
    except TimeoutError:
        with lock(f"state:{r.id}"):
            r.state = FAILED
            r.error = "timeout"
        return

    # 3. 短锁：进入后处理
    with lock(f"state:{r.id}"):
        r.raw = raw
        r.state = POST_PROCESSING

    # 4. 串行后处理，但同样不持有全局锁
    postprocess_queue.submit(r.id, raw)


def postprocess(r, raw):
    output = validate_and_structure(raw, r.output_schema)

    with lock(f"state:{r.id}"):
        r.output = output
        r.state = COMPLETED
```

这样，任何一个慢 API 都只会让当前轮次处于 `RUNNING`，不会阻塞其他 worker，也不会出现“生命体征暂停”。

## 4. 配置与避坑

### 4.1 配置读取点必须唯一

新增轮次时，不能只改 YAML，还要同步修改读取点。

建议：

- 所有轮次定义放在 `chain_definition.yaml`。
- 引擎只有一个 `RoundRegistry` 读取配置。
- 启动时校验：

```python
def validate_chain(chain_def):
    for r in chain_def.rounds:
        assert r.id in ROUND_REGISTRY
        assert r.output_schema in SCHEMA_REGISTRY
        assert r.model in MODEL_TIMEOUT_MAP
```

修改配置后必须立即跑 smoke test：

```text
POST /v7.5/chain/smoke
topic: "固定测试议题"
断言：R1~R5 全部 COMPLETED，且输出 schema 合法
```

如果配置改了但行为没变，说明读取点没同步，直接失败。

### 4.2 超时预设

```python
MODEL_TIMEOUT_MAP = {
    "b_turbo": 300,
    "a_model": 600,
}
```

- B 类 turbo 模型：300 秒。
- A 类深度模型：600 秒。
- 超时后立即释放 worker，不无限等待。
- 如果重试，重试也必须在锁外。

## 5. 负熵机制

AI 引擎是开放系统，如果只输入算力和数据，不输入负熵，系统会自发退化。

链式推演机制里的负熵来自三处：

1. **依赖图强制顺序**：信息必须流经“界定 → 推演 → 对抗 → 收敛 → 校验”，不能自由发散。
2. **每轮输出必须包含 `open_issues`**：下一轮必须优先处理上一轮的未决问题，而不是重复已有结论。
3. **对抗轮是硬性的**：R3 的 prompt 必须要求模型“找反例、找漏洞、找边界”，不允许只补充新方案。

示例 prompt：

```text
上一轮输出：
{previous_output}

本轮任务：
请找出上一轮方案中至少 3 个反例或风险点。
不要复述已有结论，不要生成新方案。
必须处理上一轮 open_issues。
```

这样，每一轮都在给系统注入“差异、约束、批判”，也就是负熵，防止输出退化成正确的废话。

---

## 6. 总结

这套机制满足：

- 慢接口不持锁，不阻塞其他 worker。
- 不用一把大锁锁全部流程。
- 锁只保护状态变更，不保护网络调用。
- 每轮上一轮输出作为下一轮输入，形成严格 DAG 依赖。
- 配置修改有唯一读取点，改完立即 smoke test。
- B 模型 turbo 用 300 秒，A 模型用 600 秒，超时快速失败。
- 每一轮都是负熵注入，防止 AI 引擎自发退化。
