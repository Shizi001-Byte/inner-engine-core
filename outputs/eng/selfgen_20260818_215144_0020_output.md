# 任务类型: eng

基于【已有认知锚定】与【避坑提醒】，针对V7.5方舟效能引擎在“多线程API调用 + 主线程串行后处理”架构下的状态一致性与竞态条件问题，我们直接运用**“精气神三元迁移框架”**进行推演，并给出完整的锁机制与状态闭环方案。

### 一、 竞态条件与状态一致性推演

在“决策串行、执行并发”的分层架构中，主线程（脑/决策层）需要将L4成品（sop/code/checklist）进行类型闭环，而工作线程（气/执行层）并发调用大模型API。此过程存在以下核心竞态与断流风险：

1. **类型撕裂竞态**：工作线程并发返回sop、code、checklist三类结果，若同时向同一个L4实体写入状态，会导致底层实体状态字段被相互覆盖（如code写完更新为“已完成”，但被并发的checklist未完成状态覆盖）。
2. **归档提前触发**：主线程串行后处理时，若仅校验了sop（历史遗留问题）就触发“自动归档系统”，会导致残缺的L4实体被归档（code/checklist未实现或未完成）。
3. **后处理断流**：主线程若采用阻塞式等待所有线程完成才进行后处理，一旦某个API线程因网络抖动或推理过长卡死，主线程将无限期阻塞，导致后续归档链路彻底断流。

### 二、 “精气神”三元框架映射与锁机制设计

为解决上述问题，严格贯彻**“先校准锚点再优化链路”**原则，设计如下锁机制与架构分层：

#### 1. 脑（决策层 / 主线程 / 串行）：负责锚点校准与类型闭环
**核心机制：Future聚合队列 + 归档写锁（Archive Write Lock）**
*   **防断流Future队列**：主线程不直接阻塞等待单个线程，而是将所有并发请求封装为Future对象放入`as_completed`队列。结合**避坑提醒**，预设合理timeout（B模型turbo用300秒，A模型用600秒）。超时即放弃该子任务，标记为降级状态，保证主线程流转不断流。
*   **类型闭环锁**：主线程从队列获取已完成的Future后，**串行**加锁执行状态合并。必须在一个锁周期内校验`len(completed_types) == 3`（sop, code, checklist均非空）。针对**坑库预警**，必须先单测验证content非空，若是空content则不计入闭环。只有三者齐备，才获取**归档写锁**，将状态推进至“可归档”。

#### 2. 气（执行层 / 工作线程 / 并发）：负责API交互与数据拉取
**核心机制：共享字典读写锁 + 直连无代理通道**
*   **无代理干扰执行**：根据**坑库预警**，工作线程统一使用`urllib`直连或显式设置`requests(proxies=None)`，从底层避免ProxyError导致线程异常退出产生死锁隐患。
*   **局部结果暂存锁**：工作线程不直接修改L4成品的主状态，而是将拉取到的结果暂存到线程安全的`ConcurrentHashMap`（或Python中的`dict`配合`threading.Lock`）中。键为任务ID，值为具体content。这隔离了网络I/O与状态决策，避免了并发写入撕裂。

#### 3. 神（状态层 / 自动归档系统）：负责持久化与一致性
**核心机制：乐观状态机锁（Optimistic State Machine Lock）**
*   **版本号控制**：自动归档系统在读取L4实体准备归档时，采用乐观锁（携带版本号version）。主线程在完成类型闭环更新状态时，version+1。若归档系统读取时version不匹配，则拉取最新状态重新校验。
*   **幂等归档锁**：归档动作必须是幂等的。通过分布式锁（如Redis的`SETNX`）锁定`L4_entity_id`，防止主线程在重试超时任务时，触发归档系统的并发重复归档。

### 三、 完整锁机制方案落地

基于上述推演，V7.5方舟效能引擎的完整锁方案实施步骤如下：

**Step 1: 执行层并发拉取（气）**
*   初始化线程池，每个线程分配独立任务（sop/code/checklist）。
*   **配置即时生效校验**：进入线程前，验证读取点配置已更新（防避坑提醒1）。
*   **超时与重试控制**：API调用强制注入timeout（300s/600s）。捕获ProxyError与Content空异常，记录日志并返回特定的降级标识，线程正常退出，不持有任何锁。

**Step 2: 决策层串行后处理（脑）**
*   主线程通过`concurrent.futures.wait(timeout=全局最大等待时间)`非死等模式轮询结果。
*   **引入`L4_Type_Closure_Lock`（互斥锁）**：
    *   获取锁 -> 校验当前实体三类结果是否都在暂存区且content非空 -> 若满足，更新主状态机为“L4闭环完成”，释放锁。
    *   若不满足（如超时降级导致缺失），更新为“L4部分闭环，待补全”，释放锁。
    *   此锁保证同一L4实体的状态合并是绝对串行的，解决类型撕裂问题。

**Step 3: 归档系统异步接管（神）**
*   **引入`Archive_Execution_Lock`（实体级锁）**：
    *   自动归档系统监听状态变更为“L4闭环完成”的实体。
    *   归档前，获取该实体ID的专属锁。
    *   再次查询实体的sop/code/checklist完整性（二次防御校准锚点）。
    *   确认无误后，执行归档I/O操作，完成后释放锁并推进状态为“已归档”。

**总结**：此方案通过**“执行层无锁暂存 + 决策层互斥闭环校验 + 状态层乐观归档锁”**的三级锁机制，彻底隔离了并发API的不确定性对L4类型闭环的破坏，同时确保主线程在后处理过程中不会因单一API超时或ProxyError而断流，严格保障了自动归档系统的状态一致性。
