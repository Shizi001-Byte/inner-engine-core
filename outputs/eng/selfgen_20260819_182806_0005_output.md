# 任务类型: eng

## 推演结论

把“文件”视为投影，把“记忆条目”视为本体。  
同步单位不是文件，而是 `entry`。这样“增量同步”“只同步变更部分”“冲突处理”才能在同一个粒度上闭环。

---

## 1. 存储模型

本地维护一个 manifest，记录每个文件的“已同步状态”：

```sql
-- 本地 manifest（SQLite 或 JSON）
file_path           TEXT PRIMARY KEY,
file_checksum       TEXT,
last_seen_entries   JSONB,   -- { entry_id: { hash, version } }
last_sync_version   BIGINT
```

Supabase 侧核心表：

```sql
create table memory_entries (
  id            text primary key,
  doc_id        text not null,
  content       jsonb not null,
  checksum      text not null,
  version       bigint not null default 1,
  deleted       boolean not null default false,
  updated_at    timestamptz not null default now(),
  hlc           text not null -- hybrid logical clock，用于冲突排序
);

create table sync_conflicts (
  id            bigserial primary key,
  entry_id      text,
  device_id     text,
  local_json    jsonb,
  remote_json   jsonb,
  resolution    text,
  created_at    timestamptz default now()
);
```

`hlc` 建议用 `物理时间戳-计数器-设备ID` 拼接，避免时钟漂移导致误判。

## 2. 检测本地文件变化

本地记忆目录用 `chokidar` 监听，同时保留轮询兜底：

```ts
const watcher = chokidar.watch(MEMORY_DIR, {
  ignoreInitial: true,
  awaitWriteFinish: {
    stabilityThreshold: 300,
    pollInterval: 50
  }
});

watcher.on('all', (event, file) => {
  debounce(`sync:${file}`, () => collectChanges(file), 200);
});
```

关键点：

- 忽略临时文件：`*.swp`、`*.tmp`、`~`、`.DS_Store`
- 文件必须原子写入：先写临时文件，再 `rename`
- 如果编辑器产生多次事件，用 `debounce` 等待稳定
- 每 30 秒轮询一次，兜底网络盘或 watcher 漏事件

## 3. 只同步变更部分

本地文件解析成 entries 后，与 manifest 里的 `last_seen_entries` 对比：

```ts
function collectChanges(file) {
  const entries = await parseMemoryFile(file);
  const baseline = manifest.get(file)?.last_seen_entries ?? {};

  const changes = [];

  for (const entry of entries) {
    const hash = sha256(canonical(entry));

    if (baseline[entry.id]?.hash !== hash) {
      changes.push({
        id: entry.id,
        base_version: baseline[entry.id]?.version ?? 0,
        patch: jsonDiff(baseline[entry.id]?.content, entry),
        checksum: hash,
        hlc: nowHlc(),
        deleted: false
      });
    }
  }

  // 本地已删除的 entry
  for (const id of Object.keys(baseline)) {
    if (!entries.some(e => e.id === id)) {
      changes.push({
        id,
        base_version: baseline[id].version,
        patch: null,
        deleted: true
      });
    }
  }

  return changes;
}
```

这样同步的不是整个文件，而是：

- 文件内变化的 entry
- entry 内变化的字段
- 删除标记

`jsonDiff` 生成 RFC 6902 JSON Patch 或 JSON Merge Patch。  
例如某个记忆条目只改了 `content` 和 `embedding`，就只传这两个字段。

## 4. 推送增量到 Supabase

用 RPC 原子推送，避免并发写坏数据：

```ts
const res = await supabase.rpc('sync_push_entries', {
  p_entries: changes,
  p_device_id: deviceId
})
  .abortSignal(AbortSignal.timeout(600_000));
```

RPC 内部逻辑：

- 对每个 entry `SELECT ... FOR UPDATE`
- 如果远程不存在，插入 `version = 1`
- 如果远程 `version = base_version`，更新并 `version + 1`
- 如果远程 `version != base_version`，返回冲突，不覆盖

对应 SQL 核心：

```sql
if cur.version = (ent->>'base_version')::bigint then
  update memory_entries
  set content   = ent->'patch',
      checksum  = ent->>'checksum',
      version   = cur.version + 1,
      hlc       = ent->>'hlc',
      deleted   = coalesce((ent->>'deleted')::boolean, cur.deleted),
      updated_at = now()
  where id = cur.id;
else
  conflicts := conflicts || jsonb_build_object(
    'id', cur.id,
    'remote', row_to_json(cur)
  );
end if;
```

成功后，本地 manifest 更新为“已同步状态”。

## 5. 冲突处理

冲突不是异常，而是分布式同步的常规状态。  
采用“双轨制”：

- **自动轨**：无争议冲突用 HLC + 字段级合并
- **人工轨**：语义冲突进入 `sync_conflicts`，可后续人工或模型仲裁

### 冲突矩阵

| 本地 | 远程 | 处理 |
|---|---|---|
| 未变 | 变更 | 拉远程 |
| 变更 | 未变 | 推本地 |
| 变更 | 变更 | 冲突解决 |
| 删除 | 变更 | 按优先级 |
| 变更 | 删除 | 按优先级 |

### 自动解决规则

1. 字段级对比：
   - 只有一边改的字段，取改的那边
   - 两边都改同一字段，比较 HLC，谁新取谁
   - HLC 相同，用 `device_id` 排序

2. 删除冲突：
   - 默认“修改优先于删除”
   - 但如果是用户主动删除，则删除优先

3. 自动解决后写入 `sync_audit_log`，可回滚。

### 语义冲突

两边都改了核心 `content`，且无法判断谁对时：

- 不覆盖任何一方
- 写入 `sync_conflicts`
- 在内容中标记 `conflict_siblings`
- 后续由人工或 LLM 合并

这符合“阴阳自衡”：自动写入轨和人工复核轨并行运行，互不消灭。

## 6. 拉取远程变更

Supabase 开启 Realtime：

```sql
alter publication supabase_realtime add table memory_entries;
```

客户端订阅：

```ts
supabase
  .channel('memory_entries')
  .on(
    'postgres_changes',
    { event: '*', schema: 'public', table: 'memory_entries' },
    payload => applyRemoteChange(payload.new)
  )
  .subscribe();
```

本地收到远程 entry 后：

- 如果本地没有未提交修改，直接应用
- 如果本地有未提交修改，进入冲突解决
- 应用后更新本地 manifest

同时保留 60 秒一次的轮询拉取，防止 Realtime 丢事件：

```ts
select *
from memory_entries
where (updated_at, id) > (select last_pull_time, last_pull_id from sync_cursor)
order by updated_at, id
limit 500;
```

## 7. 回读验证

“每次同步后必须回读验证”：

- 推送后，立即按 entry id 查回 Supabase，比对 `checksum`
- 拉取后，写本地文件，再读回文件，比对 entry hash
- 验证失败：重试 3 次，仍失败写入 `sync_errors`，不更新 manifest

```ts
const verified = await verifyRemoteChecksum(changes);

if (!verified) {
  await retryWithBackoff(pushChanges, changes);
}
```

这样能防住“配置改了但没生效”和“同步声称成功但实际没写对”的问题。

## 8. 避坑清单

1. **新增配置必须同步修改读取点**  
   所有配置统一从 `config.js` 读取，修改后立即跑 `sync --verify` 验证。

2. **API 超时按模型区分**  
   - B 模型 turbo：300 秒
   - A 模型：600 秒  
   - Supabase 大批量 RPC：600 秒
   - 小批量拉取：30 秒

3. **冲突检测不能误杀 B 模型**  
   B 模型 turbo 的 `reasoning` 占比高是正常特性，不能因此判定为“废稿”或异常同步结果。  
   不同来源的 entry 必须有独立的质量检测规则。

4. **删除必须用 tombstone**  
   不要物理删除 `memory_entries`，而是 `deleted = true`，否则删除同步无法处理冲突。

5. **文件写入必须原子化**  
   避免 watcher 读到半截文件，导致生成错误 diff。

---

## 总结

增量同步的最小闭环是：

> 本地文件变化 → 解析 entry → 字段级 diff → 推 Supabase → 回读验证 → 更新 manifest  
> Supabase 变化 → Realtime/轮询 → 拉取 entry → 冲突解决 → 写本地 → 回读验证

核心不是“少同步”，而是“每次同步都足够小、足够准、可验证、可回滚”。  
同步越频繁，冲突暴露越早，规则越准。
