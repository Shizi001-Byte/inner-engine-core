# 任务类型: eng

针对V7.3单引擎3路并发架构，多线程同时读写 `engine_state.json` 是一个典型的共享资源并发访问问题。如果不加以保护，会导致严重的数据损坏和引擎状态不一致。

以下是详细的竞态条件推演、锁机制设计以及原子写入方案。

---

### 一、 竞态条件推演

假设有3个工作线程（T1, T2, T3）并发处理任务并更新引擎状态，可能出现以下三种典型的竞态条件：

#### 1. 更新丢失
*   **场景**：T1和T2同时读取当前的 `engine_state.json`（此时 `task_count=100`）。T1完成一个任务，将内存中的 `task_count` 改为101；T2也完成一个任务，将其改为101。两者先后写回文件。
*   **结果**：实际完成了2个任务，但文件中记录的 `task_count` 只增加了1（变成101而不是102）。状态与实际执行情况脱节。

#### 2. 文件交错写入/数据撕裂
*   **场景**：T1和T2同时调用文件I/O接口（如 `write()` 或 `fprintf()`）向同一个 `engine_state.json` 写入数据。操作系统的文件系统通常不保证 `write()` 系统调用的原子性（除非写入量极小且特定条件满足）。
*   **结果**：T1写入的前半部分JSON和T2写入的后半部分JSON混合在一起，例如：
    `{"task_count": 101, "status": "run` + `ning", "queue_size": 50}` 
    产生非法JSON格式，导致下次引擎启动时解析失败，引发崩溃或状态重置。

#### 3. 脏读
*   **场景**：T3（如监控线程或外部API）试图读取 `engine_state.json` 汇报状态，而此时T1正在写入文件（文件只写了一半）。
*   **结果**：T3读取到了半个JSON字符串，反序列化失败，导致监控数据丢失或误报引擎宕机。

---

### 二、 完整的锁机制设计

为了解决上述问题，需要采用**读写锁**结合**状态机内存模型**的方案。仅仅锁定文件写入是不够的，必须锁定“读-改-写”整个临界区。

#### 1. 锁的选择：`std::shared_mutex` (C++17) 或等效机制
*   **读锁**：允许多个线程（如T3）同时读取内存状态或文件状态，提高并发吞吐量。
*   **写锁**：独占锁，当T1或T2修改状态并刷盘时，阻塞其他所有读和写操作。

#### 2. 锁的粒度与保护范围
锁不能只保护 `write()` 那一刻，必须保护 **“读取内存状态 -> 修改状态 -> 序列化为JSON -> 写入磁盘”** 的整个过程，否则依然会出现更新丢失。

#### 3. 锁机制伪代码实现

```cpp
class EngineStateManager {
private:
    std::shared_mutex rw_mutex_;
    EngineState current_state_; // 内存中的状态镜像
    std::string state_file_path_ = "engine_state.json";

public:
    // 更新状态（写锁）
    void UpdateState(const StateUpdate& update) {
        // 1. 获取独占写锁
        std::unique_lock<std::shared_mutex> lock(rw_mutex_);
        
        // 2. 修改内存状态
        current_state_.ApplyUpdate(update); 
        
        // 3. 序列化与原子写入磁盘
        std::string json_str = SerializeToJson(current_state_);
        AtomicWriteFile(state_file_path_, json_str);
    }

    // 获取状态（读锁）
    EngineState GetState() {
        // 1. 获取共享读锁
        std::shared_lock<std::shared_mutex> lock(rw_mutex_);
        
        // 2. 直接返回内存状态，避免频繁读盘
        return current_state_; 
    }
};
```

### 三、 原子写入方案

即使有了锁，直接覆盖写入原文件（`open` -> `truncate` -> `write` -> `close`）依然有风险：如果在 `write` 过程中进程崩溃或断电，原文件就会被破坏（截断或清空）。

**最佳实践方案：临时文件 + `fsync` + `rename`**

在POSIX系统和大多数现代文件系统（如ext4, xfs, NTFS）中，`rename()` 操作是原子的。利用这一特性，可以保证状态文件要么是完整的旧版本，要么是完整的新版本。

#### 原子写入步骤：
1.  **写入临时文件**：将新的JSON字符串写入同目录下的临时文件（如 `engine_state.json.tmp`）。
2.  **强制刷盘**：调用 `fsync()` 确保临时文件的数据真正写入物理磁盘，而不是停留在操作系统的Page Cache中。这一步对于防止断电导致数据丢失至关重要。
3.  **原子重命名**：调用 `rename()` 将临时文件重命名为正式的 `engine_state.json`。这会原子地替换旧文件。
4.  **清理/容错**：如果引擎启动时发现存在 `.tmp` 文件，说明上次发生了崩溃，直接删除它即可（因为正式文件依然是完好的上一次状态）。

#### 原子写入C++代码实现示例：

```cpp
#include <fstream>
#include <cstdio>
#include <unistd.h>
#include <sys/stat.h>
#include <filesystem>

bool AtomicWriteFile(const std::string& file_path, const std::string& content) {
    std::string tmp_path = file_path + ".tmp";
    
    // 1. 写入临时文件
    std::ofstream ofs(tmp_path, std::ios::binary | std::ios::trunc);
    if (!ofs.is_open()) return false;
    
    ofs << content;
    ofs.flush(); // 刷新C++流缓冲区到操作系统层
    
    // 获取底层文件描述符
    int fd = fileno(ofs.is_open() ? stdin : nullptr); // 注意：实际实现需提取ofstream的fd
    // 为严谨起见，建议使用底层 open/write 替代 ofstream 以获取fd
    // 伪代码：int fd = open(tmp_path.c_str(), O_WRONLY);
    
    // 2. 强制刷盘，防止断电丢失
    if (fsync(fd) != 0) {
        ofs.close();
        return false;
    }
    ofs.close();

    // 3. 原子重命名
    if (std::rename(tmp_path.c_str(), file_path.c_str()) != 0) {
        // 在Windows下如果目标文件已存在，可能需要使用 MoveFileEx 替代 rename
        // 在Linux/Unix下，rename会自动覆盖旧文件，且是原子的
        return false;
    }

    return true;
}
```

### 四、 V7.3架构优化建议

针对单引擎3路并发的高频场景，还有以下架构级优化建议：

1.  **写合并**：
    如果3个线程极频繁地更新状态，直接每次都加写锁+刷盘会导致严重的I/O瓶颈和锁争用。建议引入**异步状态同步线程**：
    *   工作线程获取写锁后，**只修改内存状态**，不写磁盘，立即释放写锁。
    *   一个后台定时线程（如每500ms）获取读锁，将内存状态序列化并原子写入磁盘。这样将高频随机写转变为了低频顺序写。
2.  **启动时的恢复机制**：
    引擎启动时，先检查是否存在 `engine_state.json.tmp`，若存在则删除。然后读取 `engine_state.json` 恢复内存状态。
3.  **跨平台考虑**：
    如果V7.3需要跨平台（特别是Windows），`rename()` 在目标文件存在时可能会失败。Windows下应使用 `MoveFileExA` 并配合 `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH` 标志来实现同样的原子替换效果。
