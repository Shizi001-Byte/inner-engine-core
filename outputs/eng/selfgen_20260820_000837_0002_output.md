# Supabase 记忆脑增量同步引擎 · 链式推演

## 一、约束矩阵与设计基线

| 硬约束 | 派生工程含义 | 增量同步场景下的具体表现 |
|---|---|---|
| 无记忆修改 | 节点重启后本地无任何持久索引 | 不能维护本地"上次同步时间戳/文件树快照"数据库 |
| 无全量扫描 | 拒绝 O(N) 遍历 | 重启后不能扫整棵目录树做 diff |
| 异构自适应 | 不同节点/模型不同策略 | 不同模型的记忆脑分区有不同同步频率、冲突策略 |

**核心矛盾**：传统增量同步依赖"本地基线快照"——但本约束下基线必须从远端（Supabase）现拉，又不能全量拉。这是推演要破解的工程死结。

---

## 二、核心架构：三层流水线 + 双侧哈希指纹

```
┌──────────────────────────────────────────────────────────┐
│  L1 检测层  (Watch Hook + 临时哈希表)                    │
│   - fsnotify/inotify 增量事件推送 (无全量扫描)            │
│   - 节点内存维护 hash→meta 映射 (重启即丢，不持久)        │
└─────────────┬────────────────────────────────────────────┘
              ↓ 仅变更文件入队
┌──────────────────────────────────────────────────────────┐
│  L2 同步层  (内容寻址 + 块级 Patch)                       │
│   - SHA-256 文件级指纹                                   │
│   - Rolling Hash 块级 diff (rsync 语义)                  │
│   - 同步单元 = ContentChunk(hash, offset, payload)       │
└─────────────┬────────────────────────────────────────────┘
              ↓ 带向量时钟
┌──────────────────────────────────────────────────────────┐
│  L3 冲突层  (CRDT + Supabase 权威仲裁)                   │
│   - 向量时钟 V[node_id]                                  │
│   - LWW + 三态合并 (ours/theirs/merged)                  │
│   - 失败回退到 adaptive degradation                       │
└──────────────────────────────────────────────────────────┘
```

## 三、L1 检测层：重启后的"无基线冷启动"破解

### 3.1 矛盾点
节点重启 → 本地哈希表丢失 → 如何在不全量扫描的前提下判断"哪些文件变了"？

### 3.2 破解：Content-Addressed On-Demand Rehydration
1. **Watch 接管实时变更**：fsnotify 监听新增/修改事件，事件触发即计算该文件 SHA-256，推入同步队列。
2. **冷启动惰性校验**：重启后**不主动扫描**，仅当文件被业务读取时，按需计算哈希并与 Supabase 远端 `file_hashes` 表比对。
3. **远端 hash 表作为虚拟基线**：Supabase 维护 `file_hashes(path, sha256, vector_clock, updated_at)` 表，节点通过 `path` 主键做**点查询**（O(1)），不扫全表。

### 3.3 工程级坑位预警（来自历史避坑）
- **配置修改后未生效**：fsnotify 的事件过滤规则若变更（如忽略 `.tmp`），必须同步修改 Watch 注册点，并立即用 `echo "test" > probe.tmp` 验证是否被正确忽略。
- **API 超时**：Supabase REST 单次 hash 比对查询预设 **15s timeout**（远小于模型推理 timeout，避免占用同步队列）。

## 四、L2 同步层：增量 Patch 与无记忆约束的兼容

### 4.1 块级 diff 策略
- 文件 > 64KB 时启用 rolling hash（Adler-32 风格），切分为 4KB 块。
- 仅上传强匹配 + 弱匹配变化的块，payload 为 `[(offset, hash, payload_bytes)...]`。
- 文件 ≤ 64KB 时直接整文件上传（避免 diff 计算开销大于传输收益）。

### 4.2 无记忆约束下的"上次同步状态"问题
节点不知道上次同步到哪个版本。解决：
- **远端为唯一真相源**：每次同步前向 Supabase 查询该文件的 `vector_clock` 与 `chunk_hashes[]`，作为 diff 基线。
- **节点本地不保存基线**：完全 stateless，任何一次同步都是"基于远端当前态 + 本地当前态"的合并。

### 4.3 同步单元数据结构
```python
@dataclass
class SyncDelta:
    path: str
    file_sha256: str
    vector_clock: dict[str, int]
    chunks: list[ChunkDelta]  # 仅变更块
    model_source: str          # 异构自适应用
    sync_strategy: Literal["lww", "crdt_merge", "three_way"]
```

## 五、L3 冲突层：向量时钟 + 模型分治

### 5.1 冲突判定
- 若 `local_vc` 与 `remote_vc` 存在并行分支（即 `local_vc[A] > remote_vc[A]` 且 `local_vc[B] < remote_vc[B]`），判定为冲突。
- 非冲突时：直接 LWW（按 `updated_at` 较大者胜出）。

### 5.2 模型分治策略（呼应"异构环境自适应"）
| 模型类型 | 冲突策略 | 理由 |
|---|---|---|
| A 模型 (推理型) | 三态合并 | 推理输出语义敏感，机械 LWW 易丢失关键步骤 |
| B 模型 (turbo) | LWW + 标记废弃 | turbo 输出可重生成，优先吞吐 |
| 守护进程写入 | CRDT 自动合并 | 日志类写入，可叠加不可覆盖 |

### 5.3 Supabase 仲裁函数
```sql
-- 存储函数 resolve_conflict(p_path, p_local_vc, p_remote_vc)
-- 返回: 'accept_local' | 'accept_remote' | 'needs_merge'
-- 关键: 使用行级锁 SELECT ... FOR UPDATE 防止并发仲裁
```

## 六、任务链式推演（关键步骤 + 验证锚点）

### Step 1: 节点启动注册
- 向 Supabase `nodes` 表 UPSERT `(node_id, model_type, last_seen)`
- **验证锚点**：执行 `SELECT * FROM nodes WHERE node_id = ?` 确认注册成功（防"配置修改后未生效"坑）

### Step 2: Watch 挂载
- 注册 fsnotify 到记忆脑目录，过滤规则从 `ConfigRegistry` 单例读取
- **验证锚点**：写探针文件 `__probe_<timestamp>.tmp`，确认事件触发且被正确过滤

### Step 3: 文件变更触发
- 计算文件 SHA-256，向 Supabase 查 `file_hashes[path]`
- 若 hash 一致 → 跳过（已同步）
- 若 hash 不一致或路径不存在 → 入同步队列

### Step 4: 增量 Patch 生成
- 文件 > 64KB：rolling hash diff
- 文件 ≤ 64KB：整文件上传
- **timeout 预设**：diff 计算本地无 IO 等待，无需 timeout；Supabase 写入预设 30s

### Step 5: 冲突仲裁
- 查远端 `vector_clock`
- 按模型类型分治（见 5.2）
- 冲突且需要三态合并时，触发 A 模型合并任务（**timeout 600s**，符合坑库预警）

### Step 6: 写入 Supabase + 版本推进
- 单事务内：UPDATE `file_hashes` + INSERT `file_versions`（保留历史版本用于回滚）
- **验证锚点**：事务后立即 `SELECT sha256, vector_clock FROM file_hashes WHERE path = ?` 确认版本号已推进

### Step 7: 自适应降级
- Supabase 连续 3 次 timeout / 冲突率 > 30% → 触发降级：
  - A 模型：切换为"只写本地缓冲 + 异步重试"
  - B 模型：切换为 LWW 强制覆盖（牺牲一致性保可用）
- **验证锚点**：降级触发后，向 `ConfigRegistry` 写入 `degraded=true`，下次任务读取该标志验证生效（防"配置修改后未生效"坑）

## 七、B 模型专属坑位规避（呼应坑库预警）

| 坑位 | 规避措施 |
|---|---|
| B 模型 reasoning 占比 70-82% 被误杀 | 同步质量检测规则按 `model_source` 分治；B 模型分支跳过 `reasoning_ratio` 检测 |
| B 模型高频写入导致 Supabase 限流 | B 模型分支启用 200ms 批量合并 + 本地环形缓冲 |
| B 模型 turbo timeout | API 调用预设 **300s**（坑库预警值） |

## 八、最终不变式

> **不变式 1（无记忆）**：杀死节点进程后立即重启，不依赖任何本地磁盘文件即可恢复同步能力——所有基线从 Supabase 现拉。
> 
> **不变式 2（无全量扫描）**：同步队列只由 fsnotify 事件与按需 O(1) 点查询驱动，绝不 `list_dir` 整树。
> 
> **不变式 3（异构自适应）**：同一个同步引擎，A 模型走三态合并 + 600s timeout，B 模型走 LWW + 300s timeout + 跳过 reasoning 占比检测，由 `ConfigRegistry` 单例按 `model_source` 路由。

## 九、待验证假设

1. ❓ Supabase 行级锁 `FOR UPDATE` 在 P2P 多节点并发仲裁时是否有死锁风险（需压测）
2. ❓ Rolling hash 在 4KB 块大小下，对 B 模型高频小文件写入的吞吐收益是否为正（需基准测试）
3. ❓ "按需惰性校验"会导致冷启动后第一次读取该文件的延迟增加——需评估是否影响首响应 SLA
