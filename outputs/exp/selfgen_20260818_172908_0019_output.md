# 任务类型: exp

基于两条锚定直接推演：**每日 400 万 token 是一个硬供给上限，最大化价值不是“按重要性分比例”，而是让最后一个 token 的边际价值来决定分配。** 这个边际价值就是 token 的影子价格 λ。

## 1. 节点化后的经济模型

每个 DAG 节点 `i` 定义：

- `V_i`：通过验证后的价值，包含直接价值 + 期权价值（可复用、可溯源）
- `r_i`：通过验证门的概率
- `c_i`：期望 token 成本，含尝试、验证、重试成本
- 单位 token 期望价值：`s_i = V_i * r_i / c_i`

如果节点之间没有依赖，直接按 `s_i` 从高到低分配，直到预算耗尽。  
但实际有依赖，所以不能只看单个节点，要看“选了一个下游，就必须带上它的上游”的闭合集合。

## 2. 最优分配：用影子价格 λ 做市场出清

给定一个 token 价格 λ，每个节点的净利润是：

\[
w_i = V_i r_i - \lambda c_i
\]

然后选择一个“闭合”的节点集合，使总净利润最大。  
“闭合”的意思是：如果选了某个节点，它的所有上游依赖也必须被选。  
这可以用最大闭合子图/最小割来解。

调整 λ：

- λ 太低 → 需求超过 400 万 token，λ 上升
- λ 太高 → 需求不足 400 万 token，λ 下降
- λ 使总需求恰好等于 400 万 token → 这个 λ 就是当天的 token 定价

**结论：最优分配不是计划出来的，而是由 λ 过滤出来的。**  
所有 `V_i r_i >= λ c_i` 的节点被执行；低于 λ 的节点被放弃或延后。

## 3. 验证门不是成本，是过滤器

验证门会消耗 token，但它能提高 `r_i`，避免错误向下游传播。  
最优验证强度是：

> 多花 1 token 在验证上，至少要能减少 1 token 的期望下游损失。

验证成本必须计入 `c_i`。  
如果验证门形同虚设，下游节点的 `V_i r_i` 会虚高，最后整个 DAG 的期望价值反而被高估。

## 4. 模型与超时要分开定价

B 模型 turbo（300s）和 A 模型（600s）不是同一个商品。  
如果混在一起按 token 数量定价，低价值长任务会挤占高价值短任务。

选择原则：

- B/300s：便宜、快、可并行，适合探索、候选生成、低风险验证
- A/600s：贵、慢、单次成功率高，适合高价值、低容错节点

判断用哪个模型，要比的是：

\[
\frac{V r_A}{c_A}
\]

vs.

\[
\frac{V(1-(1-r_B)^n)}{n c_B}
\]

哪个高用哪个。  
600s 超时意味着资源被预留，价格必须包含机会成本，否则会出现“劣币驱逐良币”。

## 5. 动态定价机制

对外：token 价格随时间浮动，使需求等于 400 万。  
高峰涨价，低谷降价，低价值任务自动移到低价时段。

对内：用 λ 做内部拍卖。  
每个节点报价 `V_i r_i`，只有报价高于 λ 的节点才执行。  
这比中心化“拍脑袋分比例”更接近价值最大化。

## 6. 溯源链断：不要考古，要向前建链

在“溯源链断”的前提下，最不该做的事就是花大量 token 去补 8.8—8.18 的原始对话。  
那段原始载体缺失，补回来的边际价值很低。

应该把 token 花在“向前可溯源”：

- 每个新结构化产物必须带 `source_node_id` 和 `validation_status`
- 旧的无溯源记忆标记为 `low_confidence`，其 `V_i` 打折
- 只有能通过验证门的高置信节点，才能进入高价值下游

溯源索引的投入价值 = 未来避免的重复检索和错误决策成本。  
只有当它的期望收益大于 λ 时，才分配 token 给它。

## 7. 落地步骤

1. 把任务拆成 DAG 节点，节点间只传结构化产物
2. 估算每个节点的 `V_i`、`r_i`、`c_i`
3. 对 λ 做二分搜索，跑最大闭合子图
4. 找到让总 token 消耗 = 400 万的 λ
5. 按 λ 执行；每天用实际结果更新 `r_i` 和 `c_i`

冷启动可以先给一个先验比例：  
60% 主线高价值节点，20% 验证与重试，15% 探索/备选路径，5% 溯源索引。  
但这只是初始值，不是最优值。最优值必须由 λ 算出来。
