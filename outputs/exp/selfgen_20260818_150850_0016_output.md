# 任务类型: exp

结论先行：**V7.2 → V7.5 是“微演化 / 生态型分化”，不是宏演化 / 成种事件。**

用演化生物学的话说：V7.2 和 V7.5 的“身体计划”（Bauplan）没变——仍然是「脑（元控制器）」掌握控制权，仍然是「阴阳双轨」归档。所以这只是同一物种在生态位压力下的**适应性微调**，而不是“鱼长出了脚”。

### 对应机制

- **变异**：V7.2 → V7.5 的改动是点突变级、模块级的小步调整，没有颠覆整体架构。
- **选择**：API 超时、任务完成率、归档质量就是选择压力。
- **遗传**：每次发布把已验证的状态固化为新的“基因型”，后续版本在此基础上迭代。
- **生态位分化**：B 模型 turbo 用 300 秒，A 模型用 600 秒，本质是 r/K 生活史策略分化——一个快而短，一个慢而稳。**timeout 不是 bug，而是不同模型在不同生态位下的耐受范围。**

### 阴阳双轨的演化角色

- **阳轨** = 发育/遗传路径：引擎产出 → 分类 → 打标签 → 落盘 → 索引。
- **阴轨** = 选择/反馈路径：查询/反馈/评估/淘汰/重索引（按你的阴阳框架理解）。
- **脑（元控制器）** = 发育-选择耦合器。

所以 V7.2 → V7.5 不是“阳轨单独演化”，而是元控制器在调整阳轨和阴轨之间的反馈增益，让整个系统更适应当前任务分布。

### 避坑

1. **版本号不是演化等级。**  
   `realm='九转·第20转'` 但 `version='九转·第一转·筑基'`，等于把成年化石标成幼年化石，谱系全乱了。  
   `complete_zhuan` 必须像“成种事件”一样**原子性更新 version 和 realm**；启动时强制校验，相当于分子钟校准。

2. **不要用一套 timeout 杀死所有个体。**  
   不同模型/任务占据不同生态位，超时设置应该是“耐受范围参数”，而不是全局统一值。

### 下一代方向

- **从“单线版本树”到“种群化版本管理”**：不要只维护一个最强 V7.5，而是维护一组变异体，让选择压力在种群层面发生。
- **把阴轨闭环成真正的选择压力**：每次反馈、遗忘、重检索都回流到元控制器，让阳轨的“落盘”不只是归档，而是生态位构建。
- **保留“隐秘遗传变异”**：一些当前看似无用的模块不要急着删，环境突变时它们可能是演化救生圈。
- **设置“成种阈值”**：当旧接口/旧归档结构已经严重阻碍适应度时，再开 V8，形成“生殖隔离”式的大版本跳跃；否则继续在 V7 系列内微演化。

一句话：**V7.2 → V7.5 是种内微调；下一代是让元控制器引导系统从单线版本树变成可分支的演化种群，并且版本号永远由状态驱动。**
