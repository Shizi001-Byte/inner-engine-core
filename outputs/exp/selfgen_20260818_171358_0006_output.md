# 任务类型: exp

基于锚定推演：算力分配的核心失败不是“算力不够”，而是**价值信号失效**——不知道什么任务值得跑、跑完有没有用、一次请求会吃掉多少 token。所以经济学解法不是“多买 GPU”，而是**用定价传递稀缺性，用配额/超时封住风险**。

## 1. 把 400 万 token/日当成一个经济学问题

- 供给固定：`Q = 4,000,000 token/日`，且当日不用就过期。
- 需求多样：不同任务、模型、团队有不同的价值曲线。
- 目标：不是“用完 400 万”，而是让这 400 万产生的**总价值最大**。

最优条件很简单：

> 最后一枚 token 在所有用途上的边际价值相等。

如果某个任务的边际价值低于另一个任务，就应该把 token 从前者挪给后者，直到相等。这个相等时的价值，就是 token 的“影子价格”。

## 2. 定价是实现最优分配的手段

不要让“谁喊得响谁用”，要让“谁创造价值高谁用”。

具体做法：

- 给每个任务一个“价值密度”：`预期价值 / 预计消耗 token`。
- 按价值密度从高到低分配。
- 用“内部价格”代替行政命令：每个任务方都面对一个 token 单价，只有当任务价值高于价格时才请求。
- 价格每天动态调整：需求超过 400 万就涨价，需求不足就降价。

这就形成了三层市场：

| 层级 | 场景 | 定价特征 |
|---|---|---|
| Reserved | 生产、用户实时请求、合规/安全 | 高优先级、预留容量、价格高 |
| On-demand | 普通业务任务 | 按当前供需定价 |
| Spot | 离线批处理、实验、可重试任务 | 价格低、可被抢占、只吃剩余容量 |

对外卖 API 也一样：`价格 = 边际成本 + 拥堵费`。固定日容量下，价格应该随实时需求波动，而不是拍脑袋定一个固定价。

## 3. 400 万 token 的分配框架

如果今天没有历史数据，可以先用一个“不硬编码”的初值：

- 50%：实时生产 / 用户请求
- 30%：高价值离线任务
- 10%：探索 / 实验
- 10%：缓冲 / 紧急备用

但这只是起点，不是结论。每天要根据真实产出重新算，否则就是把“对价值曲线的假设”写死了。

关键不是“每个团队分多少”，而是：

- 每个任务预计值多少钱
- 每个任务预计吃多少 token
- 超时/失败时损失多大
- 如果现在不跑，延迟一天损失多大

## 4. 超时和模型选择也是定价的一部分

B 模型 turbo 设 300 秒、A 模型设 600 秒，这不只是工程配置，而是**风险定价**。

- 没有超时 = 一个任务可以无限消耗 token，风险敞口无限大。
- 超时 = 给每个请求一个最大损失上限。
- A 模型更贵、更慢，但价值上限更高；如果任务不需要这个上限，就应该路由到 B 模型，否则就是价值浪费。

调度器应该这样判断：

> 一个任务用 A 模型跑，预期价值是否覆盖 A 模型的 token 价格和 600 秒超时风险？  
> 如果不能，就降级到 B 模型，或者直接拒绝。

## 5. 对应认知质检的三个失效点

- **认知不新鲜**：价值曲线会变，今天高价值的任务明天可能没用了。所以分配策略必须每天重估，不能按上季度的“需求表”跑。
- **闭环不开放**：只统计“用了多少 token”没用，必须回收“这些 token 产生了什么结果”。没有结果反馈，定价就是盲人摸象。
- **调用不设限**：没有配额、没有超时、没有价格，低价值请求会挤占高价值任务，最终大家都超时，这是典型的公地悲剧。

## 结论

每日 400 万 token 最大化价值的办法不是“平均分”，也不是“固定比例”，而是：

> 用动态价格把稀缺性传递给每个任务方，让 token 流向价值密度最高的用途，同时用超时和配额封住下行风险。

一句话：**算力定价的本质，不是回收成本，而是让每枚 token 都去回答“它值不值这个价”。**
