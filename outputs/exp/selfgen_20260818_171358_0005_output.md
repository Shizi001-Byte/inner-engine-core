# 任务类型: exp

结论先行：**每日 400 万 token 不是“按任务平均分”，而是“让最后一枚 token 的边际价值最大化”的资源配置问题。**  
最优内部定价，应该是一个能出清 400 万 token 的“影子价格” λ。

---

## 一、经济模型

假设任务 i 分配 `x_i` 个 token，产出函数为 `V_i(x_i)`，通常边际产出递减。

目标：

\[
\max \sum_i V_i(x_i)
\]

约束：

\[
\sum_i x_i \leq 4,000,000
\]

最优条件是：  
所有实际获得 token 的任务，其边际价值相等：

\[
V_i'(x_i) = \lambda
\]

没有获得 token 的任务，其第一枚 token 的边际价值也不超过 λ：

\[
V_i'(0) \leq \lambda
\]

这里的 λ 就是 token 的**影子价格**。  
内部按 λ 收费/计价时，需求恰好等于 400 万，资源配置就是价值最大化的。

---

## 二、定价公式

价格不能一刀切，建议：

\[
P_i = \lambda \times a_i \times b_m \times c_t
\]

- `a_i`：任务优先级/质量权重，按事后产出更新  
- `b_m`：模型成本系数，比如 B turbo 为 1，A 模型按实际成本/质量倍数设置  
- `c_t`：时段拥挤系数，高峰期上调，低峰期下调  

**timeout 也是价格的一部分。**  
B turbo 默认 300 秒，A 模型默认 600 秒，允许更长时间运行，意味着它占用更多算力窗口，token 单价应该更高。  
否则大家都抢 A 模型，400 万 token 会被低效消耗。

---

## 三、动态调整：闭环必须开放

定价不能定一次就完事。

每天收盘后，统计每个任务的实际边际价值：

- 如果某任务用了很多 token 但产出很低，就提高它的价格或降低配额；
- 如果某任务被价格挡住，但事后证明价值很高，就降低价格或提高配额。

这就是“闭环开放”：  
价格不是拍脑袋，而是根据真实结果持续修正。

没有这个反馈闭环，λ 就是猜的，配置就一定不是最优的。

---

## 四、三个护栏：认知质检 SOP 的推演

### 1. 认知不新鲜

token 花在过期认知上，边际价值约等于 0。  
所以分配前必须做 freshness gate：

- 数据表结构是否变了？
- 缓存是否过期？
- 上下文是否需要刷新？

如果认知不新鲜，即使分配了 token，也是在浪费算力。  
可以设一个“新鲜度税”：过期任务必须支付更多 token/更高价格去刷新认知，否则不允许直接推理。

### 2. 闭环不开放

没有反馈，就没有价值评估，就没有价格修正。  
每个 token 消费都要带 `trace_id` 和 `outcome`。  
否则你根本不知道哪些任务创造了价值，哪些任务在空转。

### 3. 调用不设限

没有上限，就是公地悲剧。  
一个死循环、一个失控脚本，可能烧掉当天全部 400 万 token。  
所以每次调用必须设置：

- `max_tokens`
- `timeout`
- 最大重试次数

B turbo 给 300 秒，A 模型给 600 秒，这是默认护栏，不是可以随意突破的配置。

---

## 五、基建脚本：不要写死假设

基建脚本最危险的地方，是把对表结构的假设写死了。  
在算力定价里也一样：

**不要写死“哪个任务一定值多少钱”“哪个表一定是什么结构”。**  
定价和分配规则应该是配置驱动的，并且能感知 schema drift。

表结构一变，成本模型可能就变了；如果脚本没有感知，继续按旧结构分配 token，就会同时触发“认知不新鲜”和“调用不设限”两个坑。

---

## 六、落地建议

1. 不按任务数平均分，按边际价值排序。  
2. 当日需求超过 400 万，就提高 λ；用不完，就降低 λ。  
3. 可以留 10% 的“战略储备池”，给新鲜度维护、新实验、突发事件，但储备池也要有价格，不能免费。  
4. 最终目标：  
   - 所有获得 token 的任务，最后一枚 token 的边际价值尽量相等；  
   - 没获得 token 的任务，其首枚 token 的边际价值不高于当前价格。

一句话：  
**算力资源定价的本质，不是回收成本，而是用价格表达机会成本。**  
400 万 token 每天花在哪里，应该由“边际价值”决定，而不是由“历史惯性”决定。
