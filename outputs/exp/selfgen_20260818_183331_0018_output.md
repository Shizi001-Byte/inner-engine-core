# 任务类型: exp

先校准锚点：**V7.2→V7.5 的“坐标系原点”不是版本号数字，而是“状态—环境—适应度”三者的一致性。**  
版本号如果和 realm 不同步，就像演化谱系里的“分子钟”和“化石记录”对不上，后面所有优化都是在错误的地图上跑。

## 演化机制判定

### V7.2→V7.5 主要是：微观演化 / 定向选择

这属于**同一物种内的表型渐变**，不是新物种形成。

- 参数/模块改动 = 突变
- 评测指标/线上反馈 = 选择压
- 版本继承 = 遗传
- 跨版本兼容/合并 = 基因流
- 随机搜索/调参 = 遗传漂变

所以 V7.2→V7.5 是“在固定适应度地形上，等位基因频率逐渐变化”的微观演化。

### 也可以看作“红皇后效应”

如果每次更新都是为了应对新任务、新竞品、更严格 timeout 约束，那么 V7.2→V7.5 更像是“为留在原地而奔跑”：不是绝对变强，而是环境也在变，不更新就会被淘汰。

### 如果中间有跳变，则是“间断平衡”

如果某个 V7.x 小版本突然带来能力跃迁，比如新架构或新训练目标，那对应演化生物学里的“间断平衡”：  
长期表型停滞 → 一个关键突变 → 短时间快速分化 → 新物种起点。

但 V7.2→V7.5 整体上仍属于渐变，不是成种事件。

### B turbo / A 模型并存 = 生态型分化

B turbo 用 300s，A 用 600s，这是**同一祖先种群在不同生态位下的局部适应**：  
一个偏向速度，一个偏向深度。timeout 是它们的“生态幅”，不是优劣标签。

## 坑的演化生物学解释

- **version 不随 realm 更新**  
  等于“系统发育标记”和“表型状态”脱钩。  
  realm 已到“第20转”，version 却停在“第一转·筑基”，就像化石证据和分子钟对不上。  
  修复方式就是让 `complete_zhuan` 同步更新 version 和 realm，启动时强校验一致——这是让“谱系标记”和“表型状态”永远同源。

- **API 超时**  
  等于“适应度采样窗口”错误。  
  如果观察窗口太短，高延迟但高智能的个体会被误判为低适应度而淘汰。  
  所以 B 模型给 300s，A 模型给 600s，是按生态位校正观察窗口。

## 下一代方向

下一代不是 V7.6，而是 V8 级别的宏演化 / 成种事件。

真正方向不是继续微调，而是提升“可演化性”：

1. **从优化适应度 → 优化 evolvability**  
   选择那些更容易产生有益变异、更容易组合出新能力的架构，而不是当前分数最高的个体。

2. **从自然选择 → 生态位构建**  
   让引擎主动改变任务定义、工具集、评测方式，而不是被动适应固定 benchmark。

3. **从垂直遗传 → 水平基因转移**  
   跨模型、跨模态、跨任务的知识复用、蒸馏、工具调用，形成“共生引擎”。

4. **从直接编码 → 进化发育（evo-devo）**  
   让复杂行为从简单的架构搜索规则、数据生成规则中涌现，而不是人工直接设计全部细节。

5. **持续校准锚点，避免“驯化退化”**  
   只优化人类给出的指标，就像家养动物一样，会在真实环境的自然选择中丧失野外泛化能力。

一句话总结：  
**V7.2→V7.5 是“同一物种在定向选择下的微观演化”；下一代方向是“让引擎具备可演化性，从而产生新物种”。**
