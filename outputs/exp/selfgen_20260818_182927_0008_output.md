**结论：每日 400 万 token 不是“按任务数量平均分”，也不是“按请求/文件/索引分”，而是按“每个 token 的边际价值”从高到低分配，直到 400 万 token 用完。最后被选中的那个任务的“价值/token”就是这天的影子价格。**

---

## 1. 核心经济逻辑

把每天 400 万 token 看成一条硬预算约束：

- 每个任务/样本都有：  
  - 价值 `V`（完成后的收益）  
  - 消耗 token 数 `T`  
  - 成功概率 `p`（受模型、超时时间影响）

- 每个任务分配的优先级，不应该是“它重不重要”，而是：

\[
\text{每 token 期望价值} = \frac{p \times V - \text{超时/失败损失}}{T}
\]

从高到低排序，依次分配 token。  
如果某个任务的这个值低于“排在它后面的任务”，就应该把 token 让给后者。

经济学上，这叫**按边际价值分配**。

---

## 2. “索引不是数据，block 才是数据单位”的应用

你提到的锚定：

> 同文件名、同大小、同 mtime，但 block 顺序不同，必须判不同步  
> 索引不是数据，block 才是真正的数据单位

对应到算力分配：

- **请求数、文件数、任务数，都是索引。**
- **token 消耗、实际计算量、有效产出，才是 block。**

所以不能按“多少个文件/多少次请求”来分配 token。  
否则就会出现这种情况：

两个文件看起来完全一样：同名、同大小、同 mtime，但 block 顺序不同。  
如果按索引分配，你会认为它们“相同”，跳过处理，少分配 token。

但 SOP 要求判为不同步，所以它们实际上必须消耗 token 做 block 级比较。  
按索引分配，就会漏掉这些“隐藏差异”，导致真正需要算力的任务没分到 token。

**正确的做法：按 token/block 计量，按 block 消耗分配。**  
这就是“block 才是真正的数据单位”在算力定价里的含义。

---

## 3. 模型分配：B turbo 与 A

你有两类模型资源：

- B turbo：超时 300 秒
- A：超时 600 秒

从经济学看，这不是“哪个模型更好”，而是：

> 哪个模型能让这个任务产生更高的“每 token 期望价值”？

- 简单、短、高频任务：B turbo 足够，速度快、成本低、300 秒内完成率高，优先用 B。
- 复杂、长尾、高价值任务：B turbo 容易超时，超时后 token 白耗，价值为 0；这时用 A，600 秒超时能提高成功率，反而更划算。

模型选择的公式：

\[
R_{i,A} = \frac{p_A V_i - L_A}{T_A}
\]

\[
R_{i,B} = \frac{p_B V_i - L_B}{T_B}
\]

选 `R` 更大的那个模型。  
如果某个任务在 B 上超时率太高，即使 B 便宜，它的“有效价值/token”也很低，应该换 A 或放弃。

---

## 4. 定价机制：用影子价格定价

400 万 token/天是供给上限。  
在最优分配下，最后一个被分配的 token 的价值，就是这一天的“影子价格” `λ`。

- 所有“每 token 价值 > λ”的任务都应该分配。
- 所有“每 token 价值 < λ”的任务都不值得分配。
- 对外定价时，`λ` 就是每 token 的底价。
- A 模型定价应该高于 B turbo，因为它占用更长超时窗口、更高计算资源、通常也对应更高价值任务。
- B turbo 定价低，用来承接大量低价值、短平快任务。

这样，价格会自动把需求压缩到 400 万 token 以内，并且留下的是价值最高的任务。

---

## 5. 落地步骤

1. 给每类任务打价值分 `V`。
2. 统计每类任务在 A/B 模型上的 token 消耗 `T`、成功率 `p`、超时率。
3. 计算每个任务/样本的“每 token 期望价值”。
4. 按这个值从高到低排序，依次消耗 400 万 token。
5. 每日更新影子价格 `λ`，并据此调整模型选择、对外报价和资源预留。

一句话总结：

> **算力分配不是看“谁要吃”，而是看“谁吃下去的每个 token 能产出最大价值”。  
> 索引负责标识，block/token 负责计量和定价。**
