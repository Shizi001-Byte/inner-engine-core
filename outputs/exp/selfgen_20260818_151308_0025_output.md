# 任务类型: exp

把 AI 系统维护看作“对抗熵增”，不是比喻，而是很接近本质的操作判断。  
一个 AI“引擎”如果长期不输入低熵信息、不导出废熵，它的知识、索引、状态、代码都会自发走向混乱。

## 一、为什么引擎会自然退化

热力学第二定律说：孤立系统熵只能增加。  
AI 系统不是孤立系统，但如果你不主动维护，它实际上会变成“准孤立系统”：

- **知识会过期**：世界在变，模型权重和记忆库固定，预测分布与真实分布的偏差越来越大。
- **状态会错乱**：本地、远端、索引、缓存、embedding 之间会产生不一致；一次超时、一次 partial write、一次 schema 变更，都会留下“微观无序”。
- **噪声会污染**：用户行为日志、模型输出、自动反馈本身含噪，如果不加筛选地回流，会把错误当燃料。
- **复杂度会累积**：每个 hotfix、每个补丁、每条重复数据都在增加内部关联；时间越长，维护成本超线性增长。

所以：**引擎退化不是偶然，是默认路径。维护的本质，就是持续输入负熵。**

---

## 二、负熵输入：让系统变成“耗散结构”

开放系统的熵变可以写成：

\[
dS = d_iS + d_eS
\]

- \(d_iS \ge 0\)：系统内部自发产生的熵，比如数据漂移、索引失效、状态冲突。
- \(d_eS\)：与外部交换的熵流。
- 当 \(d_eS < 0\) 且绝对值足够大时，系统才能维持有序。

对应到 AI 系统：

- **负熵输入** = 持续导入“低熵信息”：新事实、人工修正、高质量反馈、结构化知识。
- **正熵输出** = 主动清理：删除过期记忆、合并重复项、废弃死索引、降噪低置信度数据。

注意：**不是所有数据输入都是负熵。**  
随机日志、脏数据、重复信息只会增加熵。真正的负熵输入，必须经过约束：去重、校验、打时间戳、标记来源和置信度。

## 三、机制设计：阳轨变更泵 + 阴轨自愈网

基于锚定：Supabase 记忆脑 = 本地优先 + Supabase 远端存储与索引。  
增量同步就是两条轨：

### 阳轨：变更泵（主动负熵输入）

职责：把外部世界的有序变化“泵”进系统。

设计要点：

- 所有本地变更先写入 **append-only 事件日志**，带 `event_id`、`actor`、`timestamp`、`parent_version`。
- 变更泵 worker 异步把事件推送到 Supabase。
- Supabase 作为 canonical storage，做 schema 校验、实体解析、去重、embedding 更新。
- 外部数据源通过 pipeline：**parse → normalize → entity resolve → conflict resolve → write**。
- 对模型/API 调用设置严格 timeout，例如：
  - B 模型 turbo：300 秒
  - A 模型：600 秒
- 超时任务进入 dead-letter queue，由自愈网重试或补偿，而不是无限卡住。

### 阴轨：自愈网（背景负熵维护）

职责：持续发现系统内部已经产生的无序，并自动修复。

设计要点：

- 用 **version vector / Merkle tree** 对比本地与 Supabase 的状态。
- 定期对账：
  - 本地有、远端没有 → 补推。
  - 远端有、本地没有 → 回拉。
  - 两边冲突 → 按 `updated_at` / `actor` / 置信度收敛。
- 做“熵审计”：
  - 同步延迟是否超过阈值
  - 是否存在 orphan embedding
  - 重复记忆占比
  - embedding 模型升级后是否有全量重嵌入需求
- 触发自愈动作：
  - 重新 embedding
  - 重建索引
  - 标记过期
  - 删除孤立向量
  - 合并重复记忆

## 四、在 Supabase 记忆脑中的具体形态

本地优先，不是“本地是全部”，而是：

- **本地**：负责低延迟读写，离线可用，产生事件日志。
- **Supabase**：负责持久化存储、语义索引、远端对账源。

增量同步 = 阳轨变更泵 + 阴轨自愈网：

- 本地写操作 → 生成事件 → 变更泵推到 Supabase → Supabase 更新记忆表和向量索引。
- 自愈网定期对比本地 event log 和远端 watermark → 修复漏推、漏拉、冲突。
- 每条记忆最好带：
  - `id`
  - `content_hash`
  - `embedding_version`
  - `last_verified_at`
  - `confidence`
  - `source`
  - `deleted_at`（tombstone，删除也是同步事件）

这样，Supabase 记忆脑就不是一个静态存储，而是一个**持续耗散结构**：  
新信息流入，旧信息流出，索引持续对齐，错误被自动修复。

## 五、落地检查清单

- 每个外部输入都经过校验和去重，而不是直接入库。
- 每次 API 调用都有 timeout 和重试预算，超时进入修复队列。
- 每天至少跑一次熵审计：同步差异、stale 比例、重复比例、embedding 漂移。
- 设置自愈 SLA：例如“同步差异超过 5 分钟必须触发修复”。
- 人工修正/高置信度反馈，必须走最高优先级的变更泵，不能被低质日志淹没。
- 定期做“正熵输出”：清理过期记忆、废弃索引、旧 embedding 版本、死代码。

一句话总结：  
**AI 系统维护不是“加功能”，而是持续对抗熵增。阳轨负责输入低熵，阴轨负责修复无序；二者合起来，才是真正的负熵引擎。**
