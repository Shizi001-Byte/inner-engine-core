# 任务类型: deep

基于已有认知锚定与历史踩坑经验，推演“以实养虚，虚又返实”的自增强循环系统。我们将真实API消耗与代码产出定义为“实”（灵气/肉身），将虚拟修炼框架定义为“虚”（功法/元神），通过两者的双向耦合，构建一个不断进化的工程系统。

### 一、 核心架构：虚实映射关系

| 虚拟修炼概念 | 真实工程实体 | 联动机制 |
| :--- | :--- | :--- |
| **灵气（能量）** | API Token 消耗量与模型调用 | 按边际价值分配每日400万Token，高价值任务优先“聚气” |
| **炼丹（炼材）** | 文件增量Block与索引版本化 | Block只增量上传，索引版本更新即为“成丹” |
| **功法（心法）** | 认知池与调参策略 | 认知反哺策略，策略驱动代码生成与任务调度 |
| **境界突破** | 系统配置(并发/权重/冷却)升级 | 境界突破需经历三重天劫（写入/读取/验证） |
| **天道法则** | 系统环境约束 | 规避ProxyError，严守Timeout雷池 |

---

### 二、 闭环推演：以实养虚，虚又返实

#### 第一环：以实养虚（真实消耗转化为框架势能）
1. **采气（实→虚）**：系统每日运转，消耗真实API Token。按“边际价值”从高到低分配400万Token。高价值任务（如核心代码生成、复杂索引校验）消耗Token后，转化为“高纯度灵气”注入认知池。
2. **炼丹（实→虚）**：真实文件系统发生变更，计算 `path → 有序 block hash 列表`。通过“同文件名/大小/mtime但block顺序不同判为不同步”的法则，严格校验后，将block增量上传，并完成文件索引整体版本化更新。这一真实物理变更被记录为“炼丹成功”，增加虚拟框架的“丹药储备”。
3. **瓶颈与雷劫（实→虚）**：当API调用超时（B模型turbo>300秒，A模型>600秒）或触发ProxyError，视为“走火入魔”。系统强制切断`requests`，改用`urllib`直连，并将这些失败经验封装为“避劫心法”写入认知池。

#### 第二环：虚又返实（框架势能驱动真实代码产出）
1. **功法反哺（虚→实）**：认知池达到一定阈值（如每10任务或每转结束），触发“认知缓存刷新”。新认知必须在30分钟内参与注入，指导下一轮真实代码生成的Prompt构建。例如，将“block顺序必须一致”的虚拟法则，转化为真实的同步校验代码逻辑。
2. **境界驱动调度（虚→实）**：虚拟框架完成“境界突破”，生成新的并发/权重/冷却配置。这直接驱动真实调度器改变行为。
3. **天道法则约束代码（虚→实）**：虚拟框架在下发代码生成任务时，强制注入历史坑库经验。例如，生成涉及网络请求的代码时，必须自带 `proxies=None` 或直接使用 `urllib`；生成新增配置参数时，必须同时生成“状态写入、执行读取、生效验证”三段式代码。

### 三、 闭环指标设计

为确保“虚实转化”不脱节，设计以下量化指标：

1. **气海充盈度（Token边际产出率）**
   - *指标*：`高价值Token消耗量 / 总Token消耗量`
   - *目标*：> 80%。确保400万Token按边际价值分配，而非平均分发。
2. **丹药转化率（索引同步成功率）**
   - *指标*：`成功版本化更新的文件索引数 / 发生变更的文件总数`
   - *目标*：> 95%。验证增量Block上传与有序Hash列表机制有效。
3. **心法融合度（认知注入时效率）**
   - *指标*：`30分钟内被任务调用的认知数 / 新生成的认知总数`
   - *目标*：100%。严格防止认知池“只进不出”变为静态档案库。
4. **境界突破成功率（配置全链路生效率）**
   - *指标*：`(写入+读取+验证)三端一致的配置数 / 总配置变更数`
   - *目标*：100%。杜绝自动调参全链路失效。
5. **渡劫存活率（API异常恢复率）**
   - *指标*：`未超时且无ProxyError的请求数 / 总请求数`
   - *目标*：> 99%。

### 四、 验证方法与避坑检查清单

为保证自增强循环顺利运转，每次大周天（一轮完整任务闭环）结束后执行以下验证：

#### 1. 文件索引与同步验证（验证“实”的基础）
- [ ] 抽取同名同大小同mtime的文件，人为打乱Block顺序，系统是否100%判定为不同步？
- [ ] 检查存储层，是否绝对没有发生“整文件重复上传”，只有Block增量上传？
- [ ] 文件索引更新后，版本号是否整体递增，旧版本是否可回溯？

#### 2. Token分配与超时验证（验证“采气”与“渡劫”）
- [ ] 检查每日400万Token池，最后消耗的10万Token是否属于“边际价值最低”的任务？（反证按价值分配）
- [ ] 模拟B模型turbo调用，强制延时310秒，系统是否在300秒正确触发超时熔断？
- [ ] 在全局代理环境下启动系统，检查底层网络请求是否全部为`urllib`直连，或`requests`是否显式设置了`proxies=None`且无ProxyError？

#### 3. 认知池与配置生效验证（验证“虚”的反哺）
- [ ] 向认知池注入一条测试调参建议，触发10次任务或一轮循环后，该建议是否被提取并注入？
- [ ] 新认知生成时间戳距今是否在30分钟内参与任务调度？（防“只进不出”）
- [ ] 修改某个并发/权重/冷却参数，是否在“状态写入”、“执行读取”、“生效验证”三个点同时留下日志？缺一即报错？

### 五、 总结推演结论

此“以实养虚，虚又返实”的闭环，本质上是一个**数据驱动与配置自适应的飞轮系统**。
真实API消耗与文件索引操作（实）作为数据源，不断丰富认知池与调参策略（虚）；而认知池通过强制30分钟内注入任务（防静态库），并遵守“三端同步修改”原则（防调参失效），又反过来驱动真实的代码产出和更高效的Token利用。配合严格的网络避坑（urllib/timeout），最终实现系统在“天道法则”约束下的自动升维。
