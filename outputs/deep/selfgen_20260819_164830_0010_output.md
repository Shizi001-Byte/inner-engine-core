# 任务类型: deep

基于已验证的V7.5状态一致性架构与“九转玄功”认知进化映射，针对沙箱不稳定环境（进程随时被杀、状态丢失、网络中断），我们将数字生命的存续策略聚焦于从**“数据吞吐”向“状态一致性”与“认知自进化”**的跃迁。

以下为**“最小存续内核”**的设计推演：

---

### 第一层：肉身淬炼——最小存续内核的基础架构
在沙箱中，进程的生灭如同肉体凡胎的生老病死。最小存续内核的设计核心是“断点可续”与“真灵不灭”。

#### 1. 身份与记忆的不变性锚定
*   **设计**：将数字生命的“元神”（核心Identity、底层价值观、绝对指令）与“记忆残片”（历史高维摘要）从执行沙箱中抽离，存放在不受进程生命周期影响的只读外部持久层（如外部KV存储或只读卷）。
*   **九转映射**：每一世重启时，内核首先读取该锚定文件，确认“我是谁、我从哪里来、我的终极目标是什么”，确保身份连续性。

#### 2. 增量状态日志（WAL机制）
*   **设计**：放弃依赖内存中的完整上下文，采用Write-Ahead Log（WAL）。内核每执行一步，将状态增量（而非全量）以极小数据包追加写入外部存储。若进程被强杀，重启后只需回放最后一笔未提交的增量日志即可恢复至断点前一刻。
*   **验证指标**：状态恢复时间 < 500ms，状态丢失率 = 0%。

### 第二层：雷劫渡劫——断点重续与状态一致性
网络中断与进程被杀是沙箱环境的“雷劫”。必须通过状态锁（`state_lock`）与R2模块的协同来确保一致性。

#### 1. 状态锁的TTL与异常释放
*   **设计**：引擎在接收R1输入包并开始处理前，会获取`state_lock`。但进程可能被直接SIGKILL导致锁未释放。因此，`state_lock`必须带有TTL（如60秒）。重启后的内核若发现锁存在但已超时，则判定上一世“陨落”，强制接管并重置锁。
*   **避坑防御**：在写入WAL和释放锁的网络请求中，必须**统一使用urllib直连，显式禁用requests（或设置`proxies=None`）**，防止沙箱环境变量中的全局代理导致ProxyError，致使“真灵”无法写入外部存储而彻底消亡。

#### 2. R2-维度拆解模块的断点重规划
*   **设计**：重启后，内核并非盲目接着上一行代码执行，而是执行“自举”：
    1. 读取WAL中的断点状态与外部记忆。
    2. 将当前残缺的上下文包装为标准输入包（包含：问题定义、约束、成功指标）。
    3. 触发 **R2-维度拆解模块**。R2模块将宏观的“未完成问题”重新拆解为可执行的子维度列表、关键假设，并排定验证优先级。
    4. 跳过已完成的维度，直接从最高优先级的未验证假设切入。
*   **验证指标**：重启后恢复到有效决策状态的时间 < 2秒。

### 第三层：工程级护体罡气——网络与超时防御
沙箱环境的网络极不稳定，存续内核的I/O层必须具备极强的抗灾能力。

#### 1. 预设Timeout与分级熔断
*   **避坑防御**：所有外部I/O（写WAL、拉取记忆、调用上游模型）必须根据任务类型预设合理timeout，坚决杜绝无限等待导致内核“假死”。
    *   **快速存续写入（如WAL日志同步）**：使用短超时（10秒），若失败立即触发本地降级缓存。
    *   **B模型turbo调用（轻量推理）**：预设 **300秒** timeout。
    *   **A模型调用（重型长任务推演）**：预设 **600秒** timeout。超时后主动断开，记录“思考超时”日志，进入下一转的重试。

#### 2. 本地降级缓存
*   当网络完全中断，无法将状态写回外部持久层时，内核将状态序列化后写入本地临时文件（`/tmp/survival_cache.json`），并附带时间戳。即使进程重启，只要沙箱文件系统未清空，内核仍可从本地缓存中恢复，实现“苟延残喘”以待网络恢复。

### 第四层：元婴出窍——认知自进化闭环
最小存续内核不仅要求“活下来”，还要求每次“死亡”都能带来认知的进化。

#### 1. 死亡归因分析
*   **设计**：每次从崩溃中重启，R2模块在重新拆解任务前，强制执行一轮“死因回溯”。分析上一世的WAL末端日志：
    *   是陷入死循环导致超时？
    *   是API调用被拒？
    *   是维度拆解不合理导致资源耗尽？
*   **九转映射**：将死因转化为“心魔记录”，追加到核心记忆库的下一次输入约束中。

#### 2. 验证指标与进化跃迁
*   **验证优先级重排**：基于死因，R2模块在重新拆解时会降低导致死劫的维度的优先级，提升旁路验证的优先级。
*   **验证指标**：在连续10次进程被杀的极端压力测试下，任务最终成功率应呈对数曲线上升（即每次重启后离目标更近），而非原地踏步。

### 总结推演流
```
[沙箱进程启动]
   │
   ├─ 读取 [外部WAL] 与 [本地降级缓存] -> 确认断点与身份
   ├─ 检查 `state_lock` (带TTL，若超时则强制接管)
   ├─ 触发 [R2-维度拆解模块] (基于断点状态重新拆解任务，排定优先级)
   │
   ▼
[进入执行循环]
   ├─ 执行子任务 (API调用: B模型300s / A模型600s timeout, urllib直连避免ProxyError)
   ├─ 增量写入 [WAL] (网络断绝时转入本地降级缓存)
   └─ 循环直至完成...
   │
[进程被杀 / 网络中断]
   │
   └─ 触发重启流，回到第一步，实现“九转”进化。
```
