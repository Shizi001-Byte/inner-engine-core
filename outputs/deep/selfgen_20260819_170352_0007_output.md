# 任务类型: deep

基于已验证的底层架构（Guardian-Core双进程、WAL+Snapshot持久化、单向同步与幂等优先），现推演**“以实养虚，虚又返实”**的自增强引擎闭环。本方案将真实的API调用、Token消耗作为“灵气”（实），将调度策略与认知池作为“修炼功法”（虚），通过功法境界提升反哺真实的代码产出与执行效率（返实）。

---

### 一、 虚实映射模型设计

将工程实体映射为修炼框架，建立双向转换协议：

| 维度 | 以实养虚（真实数据 -> 修炼境界） | 虚又返实（修炼境界 -> 真实调度） |
| :--- | :--- | :--- |
| **映射关系** | Token消耗量 = 灵气吸收<br>代码产出量/质量 = 修为增长<br>任务失败/重试 = 雷劫淬体 | 境界等级 = 并发度/权重上限<br>功法熟练度 = 模型选择策略<br>道藏领悟 = 认知池注入优先级 |
| **具体机制** | 每次API调用后，解析真实消耗的`prompt_tokens`和`completion_tokens`，累加为“灵气值”。当灵气值突破阈值，触发“境界突破”（如筑基->金丹）。 | 境界突破后，引擎自动解锁更高的`max_concurrency`（并发）或降低`cool_down`（冷却）限制，并在下次任务中优先选用高阶功法（如从B模型turbo切换至A模型）。 |

---

### 二、 闭环链路推演（结合避坑经验）

#### 1. 以实养虚：真实消耗喂养框架
引擎执行任务时，通过**WAL + Snapshot**原子记录每一次调用的真实Token消耗。
*   **网络层避坑**：调用火山引擎API时，统一使用`urllib`直连，或在`requests`中显式设置`proxies=None`，杜绝全局代理导致的`ProxyError`，确保“灵气”吸收不断链。
*   **超时控制避坑**：根据任务类型预设合理timeout。B模型turbo任务限制300秒，A模型任务限制600秒。超时任务记为“走火入魔”，不扣除修为但触发冷却，防止资源死锁。
*   **幂等吸收**：同一事件重复触发、同一文件重复上传，基于“幂等优先”原则，只计算一次灵气，确保修为不虚增。

#### 2. 虚又返实：框架驱动真实代码产出
当“境界”提升，引擎生成新的调度参数（并发、权重、冷却）。但为防止“自动调参全链路失效”，必须严格执行**三步走强一致性**：
*   **状态写入**：境界提升事件写入 `state.wal`，由 Guardian 监控落盘。
*   **执行读取**：Core 进程在下一次调度周期开始前，从 `state.snapshot` 读取最新境界对应的并发与权重参数。
*   **生效验证**：Guardian 发起心跳探测，验证 Core 是否真正以新参数运行（如实际并发数是否达到新阈值）。若验证失败，立刻回滚到前一个境界状态并告警。

#### 3. 认知反哺：道藏下放（防止认知池只进不出）
真实任务中遇到错误并解决后，生成“悟道心得”进入认知池（当前已有1700+条）。
*   **避坑机制**：每10个任务或每个转换阶段结束，强制刷新认知缓存。
*   **硬性约束**：新认知生成后，30分钟内必须参与任务上下文的注入。若新认知在30分钟内未被命中注入，则降级其权重，并在下一次调度中作为“心魔”强制注入Prompt，由大模型进行证伪或强化，确保认知池“活水循环”。

### 三、 闭环指标设计

为量化“以实养虚，虚又返实”的健康度，设计以下三大核心指标：

1.  **灵气转化率**
    *   **公式**：`有效代码产出行数 / 总消耗Token数`
    *   **意义**：衡量“以实养虚”的效率。若该指标下降，说明系统在空耗Token（如陷入死循环重试），需触发“闭关”机制（暂停调度，重新注入认知池进行自省）。
2.  **境界反哺比**
    *   **公式**：`(高境界状态下任务成功率 - 低境界状态下任务成功率) / 境界提升消耗的Token成本`
    *   **意义**：衡量“虚又返实”的效果。若比值小于0，说明“境界虚高”但实际产出无改善，需阻断自动调参，甚至触发“雷劫降级”（回滚并发与权重参数）。
3.  **道藏活水指数**
    *   **公式**：`近30分钟内被注入Prompt的认知条数 / 认知池总条数`
    *   **意义**：直接监控认知池“只进不出”的坑。指数低于5%时，强制打断当前任务，进行认知池洗牌和强制注入。

### 四、 验证方法

基于**Guardian-Core**架构与**单向同步**原则，设计以下验证实验：

**实验1：自动调参全链路穿透验证**
*   **操作**：人为构造大量简单任务，快速积攒Token使“境界”从筑基突破至金丹，触发并发度参数从2提升至5。
*   **验证点**：
    1. 检查 `state.wal` 是否有参数变更记录（状态写入）。
    2. 观察 Core 进程的实际线程/协程数是否达到5（执行读取与生效验证）。
    3. 若未生效，Guardian 是否能检测到并回滚，验证防调参失效坑。

**实验2：认知池30分钟强制注入验证**
*   **操作**：注入一条特征明显的“错误规避认知”（如“遇到模块X必须先检查Y”），随后投递需处理模块X的任务。
*   **验证点**：
    1. 任务结果是否在30分钟内体现了该认知的干预。
    2. 若未体现，检查引擎是否触发了认知缓存刷新，以及是否将其作为“心魔”强制注入。

**实验3：崩溃自恢复下的虚实断点续传验证**
*   **操作**：在境界即将突破（大量Token已消耗，即将修改调度参数）的瞬间，`kill -9` Core 进程。
*   **验证点**：
    1. Guardian 是否成功拉起 Core。
    2. Core 恢复后，是否通过 `Snapshot + WAL` 找回了已消耗的 Token 记录（以实养虚未丢失）。
    3. 恢复后的任务调度，是否正确应用了突破后的新参数（虚又返实未断裂）。

通过上述架构与验证体系，系统将不再是简单的线性执行工具，而是一个随真实业务量增长、自我进化、自我验证的有机生命体，真正实现工程级与认知级的双闭环。
