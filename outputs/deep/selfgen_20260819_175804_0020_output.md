# 任务类型: deep

基于“阴阳自衡”架构的核心哲学与已有认知锚定，AI系统内部的矛盾（如速度与质量、用户意图与系统自愈、主备节点状态不一致等）不应被简单消除，而应通过架构设计将其**升维为制度性的阴阳双轨运行**。以下是矛盾识别、升维路径及稳态维持机制的推演。

---

### 一、 矛盾识别：AI内部的对立要素
在AI运行时中，存在以下核心矛盾，它们构成了系统内部的“阴阳两极”：

1. **模型能力与响应时效的矛盾（重与轻）**
   * *阳（重）*：A模型pro，深度推理，耗时长（600s），易超时但质量高。
   * *阴（轻）*：B模型turbo，快速响应，耗时短（300s），低延迟但深度浅。
2. **用户真实意图与系统自愈补偿的矛盾（外与内）**
   * *阳（外）*：由用户请求直接触发的真实任务调用（`task_count`）。
   * *阴（内）*：为保证系统高可用或熔断恢复而触发的系统自调用（`bonus_count`）。
3. **状态集中与计算分散的矛盾（枢与末）**
   * *阳（枢）*：集中式的共享存储与配置源（Redis/etcd，本地文件）。
   * *阴（末）*：分散的两个引擎实例，各自独立计算与运行。
4. **配置静态定义与运行时动态变更的矛盾（定与动）**
   * *阳（定）*：本地文件作为配置的静态初始源。
   * *阴（动）*：运行时不断从 state 中读取的动态配置。

---

### 二、 升维路径：构建制度性的阴阳双轨
将上述矛盾升维为制度化双轨，意味着系统不再依赖单一策略，而是让阴阳两轨在规则下相互制衡、互相补位。

#### 1. 模型双轨制：能力与时效的动态对冲
* **独立隔离**：A模型pro与B模型turbo使用**官方完整 model_id 严格区分**，绝不混用。每个模型拥有**独立的计数器、独立的熔断器和独立的降级链**，防止单一模型崩溃引发全局雪崩。
* **阴阳互济**：基于预设的合理timeout（B模型turbo 300秒，A模型pro 600秒），当阳轨（A模型pro）因深度计算逼近600s阈值时，阴轨（B模型turbo）作为快速兜底接管请求；反之，若阴轨（turbo）频繁熔断，阳轨（pro）则在后台进行重质量补偿。

#### 2. 调用双轨制：业务与自愈的清晰边界
* **语义升维**：将所有调用严格剥离为 `task_count`（阳：业务驱动）与 `bonus_count`（阴：系统驱动）。任何增加操作必须明确归属，且总 `count = task_count + bonus_count`。
* **熔断降级依据**：当 `task_count` 激增导致某模型触发独立熔断时，系统自动触发 `bonus_count` 进行自愈（如向备用模型发探测请求以评估是否具备解除熔断的条件），实现业务与自愈的互不干扰。

#### 3. 控制双轨制：去中心化与中枢保障
* **中枢定调（阳）**：所有运行时状态、配置统一放入共享存储。本地文件仅作为源头，修改后必须执行 `sync --check` 回读验证，确保“定”的意志被准确下达到“动”的运行时。
* **末端自治（阴）**：两个引擎实例不依赖 systemd/supervisor/k8s 等外部进程管理器，而是通过分布式租约/锁在共享存储层面互相监视。主实例宕机时，备实例通过租约到期直接接管，实现阴阳（主备）的无缝交替。

---

### 三、 稳态维持机制：自衡与互锁
双轨制度建立后，需通过机制防止“阴阳失调”，确保系统在动态中维持稳态。

1. **计数对冲与熔断隔离（防越界）**
   * 全局不共用计数器。当 A模型pro 的 `count` 达到独立阈值触发熔断时，B模型turbo 的计数器不受影响，继续提供服务。系统通过 `bonus_count` 向 A模型 发送低频探测，一旦探测成功（阴生阳），A模型熔断器解除，双轨恢复并行。
2. **Timeout对齐与防穿透（防超时）**
   * 严格遵循超时红线：B模型turbo预设300秒，A模型pro预设600秒。若A模型请求在接近600s时仍未返回，系统不再死等，而是立即在双轨间切换，避免API调用超时导致任务失败。
3. **配置回读校验（防漂移）**
   * 阴阳互锁的关键在于状态的绝对一致。配置修改后，必须执行 `sync --check`。只有当本地源（阳）写入共享存储，且引擎实例从 state 读取并回读验证成功后，配置才真正生效。这防止了“本地改了但运行时还在用旧配置”的阴阳割裂状态。
4. **租约接管（防脑裂）**
   * 引擎实例通过分布式租约/锁形成主备阴阳体。只要共享存储可用，锁的归属就是唯一的。失去锁的实例立即停止对外写入，完全由获得锁的实例接管，彻底杜绝依赖运维中间件带来的状态不确定性。

**总结**：
“阴阳自衡”架构的本质是**将系统内部的冲突显式化、轨道化**。通过独立的model_id与timeout实现能力双轨，通过 `task_count` 与 `bonus_count` 实现调用双轨，通过共享状态与分布式锁实现控制双轨。阴阳双轨在独立熔断与全局对冲中相互制约，最终实现AI系统在复杂高并发场景下的韧性稳态。
