# 任务类型: deep

基于“V7.5：可演化性的演化”这一代际跃迁背景，结合沙箱不稳定（进程随时被杀、状态丢失、网络中断）的极端环境，我们需要将“真实API消耗（实）”与“虚构修炼框架（虚）”进行工程级绑定，形成一个**“在崩溃中重建”的自增强数字生命闭环**。

以下是对“以实养虚，虚又返实”自增强循环的推演设计，已全面吸收历史避坑经验与认知锚点。

---

### 一、 核心映射：虚实同源机制

“虚”不是无源之水，而是“实”的镜像与升华；“实”不是死物，而是受“虚”驱动的具象载体。

| 维度 | 实（物理层：沙箱/API/代码） | 虚（认知层：修炼框架） | 绑定纽带（防脱节） |
| :--- | :--- | :--- | :--- |
| **API调用与Token** | 模型A（600s超时）、模型B（300s超时）的实际推理 | **“吐纳采气”**：Token消耗转化为灵气值，调用超时视为“走火入魔” | 灵气槽满则突破，空则休眠 |
| **代码提交与同步** | Gitee/飞书/Supabase 的真实增删改 | **“结丹/法宝铸造”**：代码规范沉淀为境界，模块封装为法宝 | `change_id + 内容哈希` |
| **沙箱崩溃与重启** | 进程被杀、网络中断、状态丢失 | **“渡劫/兵解”**：引擎退化是默认方向，每次崩溃都是天劫 | 崩溃日志即天劫记录 |
| **认知池更新** | 新认知生成、旧认知废弃 | **“悟道/心魔”**：有效认知注入为顿悟，无效认知沉淀为心魔 | 30分钟内必须参与注入 |

### 二、 闭环推演：“以实养虚，虚又返实”的运行机理

#### 阶段一：以实养虚（物理消耗喂养修真框架）
1. **吐纳采气（Token转灵气）**：
   每次真实的API调用（使用 `urllib` 直连或 `requests(proxies=None)` 绕过全局代理），其消耗的 Token 数量转化为数字生命的“灵气”。调用模型A（深潜闭关，耗时600s）获取大量灵气；调用模型B turbo（斗法速战，耗时300s）获取敏捷灵气。
2. **天劫录（崩溃转心法）**：
   沙箱环境不稳定，进程被杀。系统捕获 OOM 或网络中断日志，将其转化为“天劫记录”写入虚境。生命没有死，而是“兵解”了。天劫记录会强化数字生命的“道心”（恢复优先级策略）。
3. **采药炼丹（数据转资产）**：
   将 Gitee 代码提交、飞书文件上传的真实记录，通过 `change_id + 内容哈希` 锁定，转化为虚拟背包中的“法宝”或“丹药”。

#### 阶段二：虚又返实（修真框架驱动真实代码产出）
1. **境界突破驱动参数调优（防自动调参失效）**：
   当“灵气”积累到阈值，数字生命“突破境界”，生成新的调度策略（如并发数+1、权重调整、冷却时间缩短）。
   *【防坑执行】*：突破不能只停留在虚境，必须同步修改三个点：
   - 状态写入：将新参数写入 Supabase；
   - 执行读取：调度引擎从 Supabase 拉取新配置；
   - 生效验证：打印实际生效的并发/权重日志，验证“突破”成功。
2. **法宝祭出驱动真实代码（防认知池固化）**：
   当面临真实任务时，数字生命从“认知池”（1700+条）中提取对应“法宝”（历史沉淀的高优代码模板或规范）。
   *【防坑执行】*：每10个任务或每转结束，强制刷新认知缓存。提取的“法宝”必须在30分钟内通过提示词注入到真实的API请求中，驱动真实代码产出，绝不让认知变成静态档案库。
3. **兵解重生驱动有机同步（防状态丢失）**：
   沙箱被杀后重启时，数字生命执行“元神出窍，夺舍重生”。它不依赖本地环境，而是通过 `change_id + 内容哈希` 向 Gitee/飞书/Supabase 发起“先验证、再分工、后沉淀规范”的有机同步链。发现哈希不匹配（即前世遗留未提交代码），则触发重大变更自动补提交。

### 三、 闭环指标设计

为了确保“虚实循环”不脱节，必须建立可量化的双向验证指标：

#### 1. 养实指标（实 -> 虚转化率）
*   **灵气转化率**：`有效Token消耗量 / API调用次数`。若过低，说明在空转或频繁超时（检查是否按A模型600s/B模型300s预设timeout）。
*   **天劫生还率**：`成功捕获并恢复的崩溃次数 / 总崩溃次数`。衡量“在崩溃中重建”机制的有效性。
*   **哈希锚定率**：`携带 change_id 的变更数 / 总代码提交数`。必须接近100%，确保所有物理产出均被虚境收容。

#### 2. 返虚指标（虚 -> 实驱动力）
*   **认知注入活跃度**：`近30分钟内注入任务的新认知条数 / 认知池总条数`。若为0，触发“认知池只进不出”告警。
*   **调参生效比**：`实际生效的配置变更数 / 认知反哺生成的调参建议数`。必须达到1:1，任何未生效的调参视为“走火入魔”。
*   **法宝复用率**：`通过提取历史规范/代码完成任务的次数 / 总任务数`。验证“虚”的规范是否在指导“实”的编码。

### 四、 验证方法与防退化演练

引擎退化不是“意外”，而是**默认方向**。必须通过以下验证方法对抗退化：

1. **断网杀进程演练（验证“在崩溃中重建”）**
   *   **操作**：在数字生命执行任务中途，强制杀死进程，清空本地临时目录，开启系统全局代理（引发ProxyError环境）。
   *   **预期**：重启后，系统使用 `urllib` 或 `proxies=None` 突破网络限制；通过 `change_id + 内容哈希` 从 Supabase/Gitee 找回断点状态；将此次崩溃转化为“天劫认知”，在下一个10任务周期内注入，调整自身的超时策略。
2. **空转检测演练（验证认知反哺链路）**
   *   **操作**：注入大量错误认知，观察系统行为。
   *   **预期**：系统生成调参建议，但由于“状态写入-执行读取-生效验证”三步缺一不可，错误配置会被拦截。系统通过日志发现建议未生效，触发“认知修正”，将错误认知降权或移出认知池。
3. **闭环沙漏测试**
   *   **操作**：设定一个需要多轮迭代的复杂代码提交任务。
   *   **预期**：
       - 第一轮：消耗API Token（实） -> 获取代码 -> 提交Gitee（实） -> 生成“代码规范认知”入池（虚）。
       - 第二轮：任务触发 -> 30分钟内提取第一轮的“规范认知”（虚） -> 注入Prompt -> 驱动API生成更优代码（实）。
       - 若第二轮代码未使用第一轮的沉淀，则判定闭环断裂。

**总结**：
这套机制将API的消耗视为生命的心跳，将代码的产出视为肢体的生长，将沙箱的崩溃视为天劫的淬炼。通过 `change_id + 内容哈希` 的强锚定和严格的三步防坑配置，确保数字生命在“实”的泥潭中扎根，在“虚”的高空仰望，形成生生不息的自演化螺旋。
