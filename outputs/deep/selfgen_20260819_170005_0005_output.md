# 任务类型: deep

基于已验证的核心架构和避坑经验，推演“以实养虚，虚又返实”的自增强循环架构。本方案将真实的API调用、Token消耗与虚构的“修真”框架深度绑定，形成工程级闭环。

---

### 一、 核心架构映射：虚实共生模型

将引擎的实体工程组件与虚构修炼框架进行严格映射，确保“虚”不脱离“实”。

| 虚构层（修真框架） | 实体层（工程架构） | 联动机制 |
| :--- | :--- | :--- |
| **灵气** | Token消耗量与API调用频次 | 每次API调用自动采集灵气，写入WAL |
| **修为/境界** | 引擎累计产出代码行数/完成任务数 | 突破阈值自动提升境界，改变系统配置 |
| **功法** | Prompt模板与认知池知识 | 认知注入即“传功”，境界提升解锁高阶功法 |
| **雷劫** | 复杂任务/超时/报错 | 渡劫失败触发Guardian拉起与自恢复 |
| **洞天福地** | 并发数/超时时间/冷却权重 | 境界越高，洞天越大（并发越高），可承载越久的雷劫（timeout越长） |

---

### 二、 “以实养虚”：真实消耗喂养虚构框架

引擎每执行一次真实任务，其副产物（Token、耗时、成功/失败状态）将直接转化为修炼资源。

1. **灵气聚敛（Token采集）**
   - 引擎执行API调用时，拦截响应报文，提取 `usage.total_tokens`。
   - 采用 `urllib` 直连（规避 ProxyError 坑），显式设置 `proxies=None`。
   - 预设合理 timeout（B模型turbo用300秒，A模型用600秒，防超时坑）。超时未返回视为“灵气溃散”，不记录灵气，触发重试。
2. **修为沉淀（WAL + Snapshot 记录）**
   - 真实任务成功完成且产物包（唯一事实源）同步后，将消耗的Token数乘以任务难度系数，转化为“修为值”。
   - 修为值通过 **WAL流式写入**，确保即使雷劫（崩溃）降临，修为也不会丢失。恢复时从断点重放。
3. **认知反哺（悟道）**
   - 任务执行中遇到的错误及解决方案，作为“悟道心得”写入认知池。
   - **避坑强制执行**：每10任务或每转结束必须刷新认知缓存，新认知30分钟内必须参与下一次任务的Prompt注入，杜绝认知池只进不出。

---

### 三、 “虚又返实”：虚构框架驱动真实代码产出

当“修为值”突破境界（如从“筑基”突破至“金丹”）时，虚构框架的规则将反向控制真实引擎的参数和代码生成逻辑。

1. **境界突破与参数自调（洞天扩张）**
   - 突破境界时，触发**全局参数重配**。
   - **严格避坑**：新增可配置参数（如金丹期解锁的 `deep_think_mode=True`）必须同步修改三个点：状态写入（WAL）、执行读取、生效验证，缺一不可，防止自动调参失效。
   - 境界提升后，系统自动放宽并发权重（从2并发提至5并发），缩短冷却时间。
2. **功法演化驱动代码重构（虚返实）**
   - 当认知池中关于某一类任务（如“异步并发控制”）的经验积累到阈值，虚构框架触发“功法推演”事件。
   - 引擎调用A模型（600秒timeout），根据认知池注入的新认知，生成真实可执行的 Python 代码（如重构现有的调度器模块）。
   - 产出的真实代码经过幂等性校验后，覆盖旧逻辑，完成引擎的自我进化和升级。
3. **单向同步与产物固化**
   - 引擎演化产生的新代码和配置，作为引擎产物包（唯一事实源）。
   - 通过单向同步推送至 Gitee（代码）、飞书（日志）、Supabase（状态），绝不双向同步，保证幂等性。

### 四、 闭环指标设计

为了量化“虚实循环”的健康度，设计以下监控指标：

1. **转化效率比**
   - 公式：`产出有效代码行数 / 消耗总Token数`
   - 意义：衡量“以实养虚”再“返实”的效率。若该指标随时间下降，说明引擎陷入低效空转（如反复生成无用代码），需触发预警。
2. **认知活跃度**
   - 公式：`近30分钟内被注入Prompt的认知条数 / 认知池总条数`
   - 意义：监控认知池是否变为静态档案库。低于10%则证明“功法”失效。
3. **境界红利系数**
   - 公式：`当前境界任务平均耗时 / 上一境界同类任务平均耗时`
   - 意义：验证“虚返实”是否带来真实增益。系数应呈下降趋势（境界越高，处理越快）。
4. **雷劫存活率**
   - 公式：`Guardian成功拉起Core并恢复任务的次数 / 总崩溃次数`
   - 意义：验证WAL+Snapshot崩溃恢复架构的鲁棒性。

### 五、 验证方法

通过以下自动化测试验证闭环是否真正跑通：

#### 测试一：虚实转化验证（以实养虚）
1. 向引擎下发10个中等难度代码生成任务。
2. 监控API调用，确认 `usage.total_tokens` 被准确提取。
3. 检查 `state.wal` 和 `state.snapshot`，确认修为值按公式增长。
4. **验证点**：若人为Kill Core进程，Guardian拉起后，修为值是否与崩溃前一致。

#### 测试二：境界反哺验证（虚又返实）
1. 人为将引擎状态 `snapshot` 中的修为值设置至“金丹期”临界点（如99999）。
2. 下发1个极小任务，消耗少量Token使其突破至“金丹期”。
3. **验证点A**：检查引擎配置是否自动变更（timeout从300升至600，并发数增加）。
4. **验证点B**：检查新增参数是否在“状态写入、执行读取、生效验证”三处均有体现（防止调参失效坑）。
5. **验证点C**：检查认知池是否在突破后被刷新，且新认知在30分钟内被注入到下一次任务的Prompt中。

#### 测试三：代码自演进验证（最终闭环）
1. 注入一个特定错误模式（如“未设置proxies=None导致ProxyError”）到任务输入中。
2. 引擎捕获错误，写入认知池，并在30分钟内注入到下一次生成任务中。
3. **验证点**：检查引擎产出的代码产物包，是否自动包含 `proxies=None` 或改用了 `urllib`。验证该产物包单向同步至 Gitee，且重复推送不产生重复提交（幂等性验证）。
