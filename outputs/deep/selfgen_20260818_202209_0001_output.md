# 任务类型: deep

基于“以实养虚，虚又返实”的哲学理念，我们将真实的API调用、Token消耗工程数据作为“实”，将虚构的修炼框架（如境界、灵根、功法）作为“虚”，构建一个自增强的工程闭环。

以下是结合已有认知锚点和避坑经验的推演方案：

### 一、 核心闭环设计：以实养虚，虚又返实

#### 1. 以实养虚（真实数据喂养虚构框架）
将真实的API调用网络转化为修真世界的“灵气吸收”过程。
*   **灵气获取（Token消耗）**：每次真实API调用消耗的Token数，转化为修炼框架中的“灵气”。
*   **境界突破（任务成功率与规模）**：每完成10个并发任务（后处理单消费者模式），积累一轮“周天循环”。成功率高且无超时，则“修为”上涨；若触发B模型300秒或A模型600秒超时，则判定为“走火入魔”，境界回退。
*   **灵根品质（资源调度权重）**：A模型因占用稀缺紧急调度资源且成本更高（`γ_A`加权），被映射为“异灵根（雷属性）”，爆发力强但消耗大；B模型turbo映射为“常灵根（风属性）”，流转极快。根据任务的轻重缓急，框架自动选择对应“灵根”进行突破。

#### 2. 虚又返实（虚构框架驱动真实代码产出）
“修为”提升后，修炼框架不是静态展示，而是必须输出真实的工程变更（代码/配置）。
*   **功法演化（调度参数调优）**：当框架判定“风灵根”（B模型）已达瓶颈，会触发“闭关”机制，自动生成针对并发数、权重、冷却时间的调参代码。
*   **心法反哺（代码生成）**：框架基于“认知池”中的历史经验，驱动代码生成器产出新的路由策略、重试逻辑或降级脚本。
*   **天劫渡劫（压测验证）**：生成的真实代码必须通过一个“雷劫”测试（CI/CD自动化压测），验证其并发边界与原子状态更新的正确性。渡劫成功，新代码合入主干。

---

### 二、 闭环指标设计（量化“虚实转化”）

为了验证这个自增强循环是否健康运转，设计以下三类核心指标：

#### 1. 养分转化率（实 -> 虚）
*   **灵气吸收率**：`有效消耗Token数 / 总消耗Token数`。低于阈值说明产生了大量无效调用或异常重试。
*   **走火入魔率**：`(超时次数 + ProxyError次数) / 总调用次数`。必须随循环圈数呈下降趋势。

#### 2. 驱动产出率（虚 -> 实）
*   **代码渡劫成功率**：`框架驱动产出的代码通过CI/CD测试的比例`。如果连续失败，说明“虚”的方向出现了偏差。
*   **参数生效覆盖率**：每次“功法演化”产出的调参建议，必须满足状态写入、执行读取、生效验证三处同步，该指标恒为100%。

#### 3. 系统熵减率（闭环自增强）
*   **单任务成本下降斜率**：随循环圈数增加，处理同等复杂度任务的单任务Token消耗（结合`γ_A`成本模型）应呈对数曲线下降。
*   **认知注入活跃度**：`30分钟内注入任务的认知条数 / 认知池总数`。该指标必须大于0，且认知池总数不应出现“只进不出”的无限膨胀。

### 三、 验证方法与避坑执行清单

在设计验证方法时，必须将历史踩坑经验作为一票否决项嵌入验证流程：

#### 验证步骤 1：真实API调用与状态解耦验证
*   **动作**：发起混合任务流，包含B模型turbo（预设300秒超时）和A模型（预设600秒超时）。
*   **验证点**：检查系统日志，确认API调用方**只写`classification_results`**，绝不直接改`task.status`；所有`task.status`变更均带有`version`字段且通过乐观锁仲裁成功。
*   **验证点**：验证后处理阶段是否严格保持单消费者队列，未出现并发污染。

#### 验证步骤 2：虚返实的代码产出与网络验证
*   **动作**：触发修炼框架的“闭关”机制，让其生成新的API调用脚本或降级策略代码。
*   **验证点**：扫描生成代码，**严禁出现未指定`proxies=None`的`requests`库调用**。强制要求框架生成的网络请求代码统一使用`urllib`直连。
*   **验证点**：检查生成的参数调优代码，必须同时包含：1) 写入DB状态代码，2) 执行器读取代码，3) 生效断言代码。三者缺一则CI报错。

#### 验证步骤 3：认知池流动与自增强验证
*   **动作**：连续运行100个任务作为一轮“大周天”。
*   **验证点**：每10个任务或每转结束，检查认知缓存是否被强制刷新。
*   **验证点**：在认知池中注入一条“带有特定标记的新认知”（如应对ProxyError的新策略），观察未来30分钟内的任务调度日志，确认该认知已被提取并影响实际的权重分配或路由逻辑，证明“认知池”不是静态档案库。

**总结**：此方案将真实API指标封装为修炼进度，利用修仙框架的“升级”逻辑反向强制输出代码优化和参数调整配置。只要上述验证方法（尤其是三个工程级避坑点）被严格拦截在CI/CD流程中，该系统就能实现“数据喂养框架 -> 框架演化策略 -> 策略优化代码 -> 代码降低成本与超时”的自增强飞轮。
