# 任务类型: deep

基于已锚定的 **Guardian-Core 双进程架构**与 **CF --> SP[Supabase 认知池 实]** 链路，针对8月8日-8月18日缺失的10天原始对话，我们将此问题定义为一次**跨周期的增量同步断层修复**。

在此期间，外部输入的“大众语义”（如日常交流中的隐喻壳词汇）由于未能按时进入 ChainTask 链路，将形成积压。若直接全量灌入，极易触发“字面认知陷阱”（即外部语义与内部规则定义冲突，导致 SP 认知池数据污染）。

以下是具体补全方案、可执行步骤及验证标准：

### 一、 断层修复 ChainTask 推演

我们将修复过程划分为三个 ChainTask 节点，由 Guardian 进程负责冲突隔离，Core 进程负责语义提纯与入库：

*   **Task 1: CF 层归档扫描与切片**（ Guardian 主导 ）
*   **Task 2: 隐喻壳剥离与规则对齐**（ Core 主导，解决增量冲突 ）
*   **Task 3: SP 认知池增量写入与溯源关联**（ Core 执行 ）

---

### 二、 可执行步骤

#### Step 1: CF 层归档提取与冲突标记 (Guardian 进程)
1.  **定界扫描**：在本地 CF（Client File / 本地归档源）中提取 8月8日 00:00 至 8月18日 23:59 的原始对话日志。
2.  **分片切分**：将10天数据按“天”为单位切分为10个独立分片，防止单次处理数据量过大。
3.  **增量冲突预检**：Guardian 进程扫描分片，标记出所有“字面认知陷阱”词汇（如用户在对话中使用的“内存”、“线程”等日常隐喻壳）。
    *   *动作*：生成待清洗的临时队列 `[CF_Recovery_Queue]`。

#### Step 2: 隐喻壳剥离与规则对齐 (Core 进程)
1.  **模型分发与超时预设**：
    *   对低风险分片（无明显冲突词汇）：调用 B模型turbo，**预设 timeout = 300秒**，快速完成格式化与特征提取。
    *   对高风险分片（含大量隐喻壳词汇）：调用 A模型，**预设 timeout = 600秒**，进行深度上下文解析，将外部大众语义映射至内部规则定义。
2.  **语义脱壳**：例如，将用户口中的“内存满了”脱壳并对齐为内部规则定义的“SP 认知池上下文长度溢出”。
3.  **双进程交叉验证**：Guardian 验证脱壳后的数据是否符合内部规则，Core 验证脱壳后是否丢失原始语境。

#### Step 3: SP 认知池增量写入与溯源关联 (Core 进程)
1.  **断点续传写入**：将清洗后的10天数据，以时间为序，通过 ChainTask 链路执行 `INSERT` 操作至 SP[Supabase 认知池 实]。
2.  **溯源链锚定**：
    *   为这10天的每一条入库记录打上 `recovery_batch_id: 20240808-20240818` 的标签。
    *   关联已有溯源链：检查 8月7日最后一条记录的 `next_hash` 与 8月8日补全数据的首条 `current_hash` 是否咬合；同理验证 8月18日末条与 8月19日已有首条。
3.  **状态固化**：更新 ChainTask 的状态机，将这10天的断层状态从 `MISSING` 置为 `RECOVERED`。

---

### 三、 验证标准

为确保补全的对话不仅“存在”，且“可用”，必须通过以下三层验证：

1.  **链路连续性验证（溯源链级）**
    *   **标准**：通过 SP 查询 8月8日-8月18日的 `ChainTask` 执行日志，确保 `prev_hash` 与 `next_hash` 形成闭环，无断链。
    *   **校验**：执行 SP 脚本，比对 8月7日 23:59 与 8月8日 00:00 的哈希咬合，以及 8月18日 23:59 与 8月19日 00:00 的哈希咬合。

2.  **增量冲突清零验证（规则级）**
    *   **标准**：对补全的这10天数据进行抽样检索，确保“隐喻壳”词汇已被正确转译。
    *   **校验**：在 SP 中执行全文检索，若发现未脱壳的日常词汇（如非计算机语境下的“内存”），则判定为“字面认知陷阱”残留，需重跑 Step 2。

3.  **双进程一致性验证（架构级）**
    *   **标准**：Guardian-Core 双进程的账本状态一致。
    *   **校验**：Guardian 的 `[CF_Recovery_Queue]` 清空状态，必须与 Core 写入 SP 的 `recovery_batch_id: 20240808-20240818` 的 `COMPLETED` 状态完全对齐。若 Guardian 报错而 Core 成功，则触发底层自恢复机制（此处不重述），回滚该批次。

**【避坑执行声明】**：在整个补全过程中，已严格按照任务类型配置超时：B模型turbo 分片处理上限 300秒，A模型深度对齐上限 600秒，坚决杜绝 API 调用超时导致任务链断裂。
