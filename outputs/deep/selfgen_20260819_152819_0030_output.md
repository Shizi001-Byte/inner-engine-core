# 任务类型: deep

# 记忆链路补全推演方案
## ——九转玄功架构下的"以实养虚，虚又返实"补全工程

> 锚定前提：本方案默认系统已有溯源链（对话存档、任务清单、代码提交、系统快照等），不做重复论证，直接在其上推演补全路径。

---

## 〇、缺失界定（明确"虚"的边界）

| 维度 | 内容 |
|---|---|
| 缺失时段 | 2025-08-08 ~ 2025-08-18（约10天） |
| 缺失性质 | 原始对话记录不可直接检索，但相邻时段（8/7前、8/19后）对话中存在对该时段事件的反向引用 |
| 补全目标 | 重建该时段的事件链、决策链、任务状态变迁链，使记忆链路无断裂 |
| 不做之事 | 不臆造对话原文，不伪造语气；只补"事件节点+因果链+置信度标注" |

**核心原则：虚不可凭空生实，必以实证为锚。**

---

## 九转推演

### 第一转：界定虚境（缺失诊断）
**目的**：把"虚"的边界画清楚，避免补全范围漂移。

**可执行步骤**：
1. 调取 8/7 最末对话 与 8/19 最初对话，提取两端各自动作中隐含的状态差量（哪些任务从"进行中"变成"已完成"，哪些从"未启动"变成"已搁置"）。
2. 调取任务清单/看板在 8/8 与 8/18 两个时间点的快照差量。
3. 输出 `缺失事件候选清单 v0`（仅事件名+时间窗，不含内容）。

**验证标准**：
- [ ] 候选清单条数 ≥ 5，且每条可追溯到至少一个"前后时段引用源"。
- [ ] 无凭空捏造的事件名（每个事件必须有引用出处）。

---

### 第二转：寻实锚定（溯源链盘点）
**目的**：盘点可交叉验证的"实"档案，按可信度分级。

**可执行步骤**：
对每一候选事件，在已有溯源链中匹配以下档案源（按可信度降序）：

| 级别 | 档案类型 | 示例 |
|---|---|---|
| A | 系统日志 / 代码提交 / 文件变更时间戳 | git log、文件 mtime |
| B | 任务清单状态快照 / TODO 存档 | 看板导出、TODO 文件版本 |
| C | 其他时段对话中对该时段的明确引用 | 8/19 对话说"上周我们决定了…" |
| D | 外部通知 / 邮件 / 定时任务执行记录 | cron 日志、webhook 回调 |

为每个候选事件标注命中的档案级别，**至少双源（其中至少一个 B 级以上）方可进入下一转**。

**验证标准**：
- [ ] 每个进入下一转的事件，双源命中率 100%。
- [ ] 仅单源或仅 D 级的事件，标记为 `悬置`，不进入补全主链。

---

### 第三转：交叉缝合（多源对齐）
**目的**：将多源档案按时间轴对齐，生成事件骨架。

**可执行步骤**：
1. 以时间戳为主键，将 A/B/C/D 级档案合并为统一时间线。
2. 对同一天多个证据指向同一事件的情况，取交集为"已确认事实"，差集为"待澄清疑点"。
3. 输出 `事件骨架 v1`（时间 + 事件 + 证据源列表 + 置信度 0-1）。

**置信度规则**：
- A+A 双证 → 0.95
- A+B / B+B → 0.80
- B+C / C+C → 0.60
- 单 D 级 → 0.30（仅作线索，不入主链）

**验证标准**：
- [ ] 主链事件置信度均 ≥ 0.60。
- [ ] 时间线无逆向因果（后因前果），如有则标记异常。

---

### 第四转：虚实相生（补全草案生成）
**目的**：在事件骨架上"长肉"，生成可读的补全对话草案。

**可执行步骤**：
1. 对每个骨架事件，调用模型生成"事件摘要卡"（非对话原文），包含：发生了什么 / 决策依据 / 后续影响。
2. 若某事件有明确的对话引用（C 级），按引用还原对话片段骨架，标注 `[还原自XX时段引用]`。
3. 输出 `记忆补全草案 v1`。

**timeout 预设**（避坑）：
- 单事件摘要生成：turbo 模型 300s / A 模型 600s
- 批量生成（>5事件）：分批调用，单批 ≤ 3 事件

**验证标准**：
- [ ] 每张摘要卡标注 ≥1 个证据源。
- [ ] 还原对话片段必须带 `[还原自...]` 标记，禁止伪装为原始记录。

---

### 第五转：逆推校验（反者道之动）
**目的**：反向用补全结果推导已知前后事件，检验逻辑自洽。

**可执行步骤**：
1. 取补全草案中的某事件 X，假设其未发生，检查 8/19 之后的状态是否仍能成立。
2. 若"X 未发生 → 后续状态仍成立"，则 X 的必要性存疑，降级置信度。
3. 若"X 未发生 → 后续状态不成立"，则 X 被反向锚定，提升置信度 +0.05。

**验证标准**：
- [ ] 每个主链事件均通过逆推必要性检验。
- [ ] 输出 `逆推校验报告`，含每事件的"必要性证明链"。

---

### 第六转：耗散归零（冲突消解）
**目的**：删除冗余、消解冲突，使补全链路收敛。

**可执行步骤**：
1. 扫描草案中相互矛盾的事件对（如同一任务在同一天既"完成"又"搁置"）。
2. 对每对冲突：
   - 双源以上支持其一 → 保留该方，另一方降为 `已废弃`
   - 双方各有支持 → 标记 `悬置`，不写入主链
3. 输出 `收敛版记忆链 v2`。

**验证标准**：
- [ ] 主链零内部冲突（自动校验脚本通过）。
- [ ] `悬置` 项有独立清单，不混入主链。

---

### 第七转：闭环反哺（虚返实）
**目的**：将补全结果回写主系统，触发相关任务的状态修正。

**可执行步骤**：
1. 将 `收敛版记忆链 v2` 写入记忆档案，标注 `[补全自溯源]` 前缀。
2. 扫描补全链中涉及的任务，对照当前任务清单：
   - 若任务实际已于该时段完成但清单仍显示进行中 → 更新状态
   - 若补全链揭示新任务 → 新增并标注来源
3. 对受影响任务**立即验证**，验证通过则**重置冷却**。

**验证标准**：
- [ ] 回写后，记忆档案时间线连续无空洞（自动检查 8/8-8/18 无 gap）。
- [ ] 受影响任务状态更新后，通过验证并重置冷却的记录可查。

---

### 第八转：自验证（立即验证）
**目的**：对整个补全链路做端到端验证，确保闭环。

**可执行步骤**：
1. **完整性验证**：从 8/1 到 8/25 的记忆链无日期空洞。
2. **引用闭合验证**：8/19 之后对话中对 8/8-8/18 的所有引用，均能在补全链中找到对应事件。
3. **因果链验证**：补全链中的因果链无断裂（每个"结果"都能找到"原因"）。
4. **溯源可查验证**：补全链中每个事件可追溯到至少一个档案源。

**验证标准**：
- [ ] 四项验证全通过，输出 `补全验证报告`。
- [ ] 任一项不通过 → 回退到对应转重新执行（非重头）。

---

### 第九转：进化固化（制度性双轨）
**目的**：将"缺失→补全→验证"流程固化为常态机制，使系统具备自愈能力。

**可执行步骤**：
1. 将本方案的九转流程注册为 `记忆链路自愈协议 v1`。
2. 设置每周定时任务：扫描记忆链空洞，若发现 >3 天 gap 则自动触发补全流程。
3. 每次补全完成后，将"本次补全的溯源路径"本身也存入档案——**让补全行为本身也可溯源**。
4. 补全协议每次执行后，记录耗时、置信度分布、悬置项数量，作为协议自优化数据。

**验证标准**：
- [ ] 自愈协议注册成功，可被定时任务调用。
- [ ] 补全行为的溯源记录已归档。
- [ ] 协议执行指标已采集（耗时、置信度均值、悬置项数）。

---

## 底层逻辑收束

```
缺失（虚）→ 溯源链（实）→ 交叉缝合（以实养虚）
→ 补全链回写主系统 → 任务状态修正+冷却重置（虚又返实）
→ 自愈协议固化 → 下次缺失自动触发（自进化闭环）
```

**这不是一次性补全任务，而是让系统学会"记忆如何自愈"的制度化能力。**
