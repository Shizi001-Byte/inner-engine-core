# 任务类型: deep

基于“脑体分离架构”的核心锚定与历史避坑经验，推演“以实养虚，虚又返实”的自增强循环。在此架构中，**“实”指代身体层（真实API调用、Token消耗、执行同步），“虚”指代大脑层（虚构修炼框架、认知池、决策事件）**。

以下是该闭环系统的推演、指标设计与验证方法：

### 一、 架构映射：虚实转换的边界定义

根据【已有认知锚定3/4】，虚实边界即为“决策事件/全局顺序”与“执行/同步”的边界。

1. **以实养虚（身体喂养大脑）**
   - **真实动作**：执行层发起API调用，消耗Token，产生延迟、报错（如ProxyError）或成功响应。
   - **虚拟映射**：这些真实消耗被抽象为“修炼资源”。Token消耗=灵气吸纳；API超时=经脉受阻；代码Bug=心魔入侵。执行层将真实的耗时、Token数、错误码以**显式、可重放**的事件流推入大脑层，更新虚拟角色的“修为境界”与“认知池”。
2. **虚又返实（大脑驱动身体）**
   - **虚拟动作**：大脑层根据“修为境界”和“认知池”进行决策，生成全局顺序的调参建议、并发权重、冷却时间。
   - **真实映射**：决策事件下发至执行层，真实改变代码产出的逻辑（如调整超时限制、切换API路由、修改重试策略），从而影响下一次的真实API调用。

---

### 二、 闭环设计：规避历史坑点的工程化实现

为确保“虚实循环”不沦为静态档案库或全链路失效，必须严格落实以下工程约束：

#### 1. 以实养虚：资源转化与状态写入
- **资源计量（禁用简化版）**：执行层统计真实Token消耗与耗时。必须使用**显式声明列映射的幂等SQL**写入`virtual_state`表（防坑5）。不可使用“决策层看起来等价”的简化写入。
- **超时熔断（防坑1-超时）**：真实API调用必须预设timeout。B模型turbo强制300秒，A模型强制600秒，超时即视为“修炼失败”，产生异常事件入池。
- **网络直连（防坑2-ProxyError）**：执行层收集真实数据时，统一用`urllib`直连或`requests`显式设`proxies=None`，确保不被全局代理污染，保障“灵气”来源纯净。

#### 2. 虚又返实：决策下发与执行生效
- **认知池注入（防坑3-只进不出）**：大脑层每10个任务或每轮转化结束，必须强制刷新认知缓存。新产生的“心魔（Bug认知）”或“功法（优化认知）”在30分钟内必须参与下一次决策注入。
- **调参全链路生效（防坑1-调参失效）**：大脑生成的并发/权重/冷却三项配置，必须同步修改三个点：
  1. **状态写入**：更新`config_state`表。
  2. **执行读取**：执行层在发起API调用前强制读取最新配置。
  3. **生效验证**：日志中必须打印实际使用的参数值，与状态表比对。

### 三、 闭环指标设计（量化“自增强”效果）

为了验证“虚”确实在驱动“实”，且“实”确实在滋养“虚”，设计以下三类指标：

#### 1. 转化效率指标（虚实流转率）
- **Token-to-Dao转化率**：单位Token消耗转化为有效代码行数（LOC）的比例。
  - `指标 = (本轮产出且通过校验的真实代码行数) / (本轮消耗的总Token数)`
  - 期望：随着循环增强，同样Token应产出更多有效代码。
- **认知注入命中率**：
  - `指标 = (实际参与API Prompt注入的认知条数) / (认知池总条数)`
  - 期望：防范“只进不出”，该指标应保持>30%（30分钟内）。

#### 2. 系统稳定性指标（降魔率）
- **走火入魔率（ProxyError/Timeout比率）**：
  - `指标 = (Timeout+ProxyError次数) / (总API调用次数)`
  - 期望：随着“认知池”注入避坑经验，该指标应呈对数下降。
- **调参生效延迟**：
  - `指标 = 执行层实际应用新参数的时间戳 - 决策层生成参数的时间戳`
  - 期望：趋近于0，证明“虚返实”通道无阻塞。

#### 3. 架构边界指标（脑体分离度）
- **事件顺序违规数**：
  - `指标 = 执行层未按大脑下发的全局顺序执行的次数`
  - 期望：必须为0。证明决策与执行边界清晰，可重放。

### 四、 验证方法（显式、可重放、可校验）

基于【已有认知锚定1/2】，验证不能依赖“看起来等价”，必须显式校验。

#### 验证流程1：实->虚 注入验证
1. **动作**：人为触发一次B模型turbo调用，耗时310秒（超过300秒timeout）。
2. **校验**：
   - 检查执行层日志是否抛出Timeout事件。
   - 检查`virtual_state`表（显式列映射），是否将此次失败转化为“灵气损耗”且修为下降。
   - 检查该Timeout经验是否写入认知池，且在30分钟内被标记为“待注入”。

#### 验证流程2：虚->实 生效验证（专破调参失效）
1. **动作**：大脑层生成调参建议：“将并发权重从5降至2，冷却时间提升至60秒”。
2. **校验**（三段式验证）：
   - **状态写入**：查询`config_state`表，`concurrency_weight`列必须显式变为2。
   - **执行读取**：执行层在下一个任务的启动日志中，必须打印`[Config_Loaded] weight=2, cooldown=60`。
   - **生效验证**：监控实际API调用的并发波形，波峰必须从5降至2，且请求间隔≥60秒。三者缺一不可。

#### 验证流程3：认知反哺验证（专破静态档案库）
1. **动作**：在认知池中强制插入一条高优认知：“禁止使用requests，必须urllib直连”。
2. **校验**：
   - 触发下一轮代码生成任务。
   - 截获发往A模型/B模型的API Payload（真实请求体）。
   - 检查System Prompt中是否显式包含该条认知的内容。
   - 检查生成的代码产物中，是否不再`import requests`。

### 总结
“以实养虚，虚又返实”的本质是**基于事件溯源的反馈控制系统**。真实API的Token和耗时是系统的输入燃料，经过大脑层（虚构框架）的决策事件处理，输出为全局顺序的配置指令，再由执行层同步为真实代码。通过严格的三段式参数校验、认知池强制刷新机制以及显式的SQL状态管理，该循环将自动收敛于“高产出、低错误”的自增强轨道上。
