## 二、以实养虚：真实数据如何喂养框架

### 2.1 喂养输入清单（精→气→神逐层灌注）

```
┌──────────┬──────────────────────────┬───────────────────────────────────────┐
│ 层级      │ 真实输入（实相）          │ 框架吸收形态（虚相）                    │
├──────────┼──────────────────────────┼───────────────────────────────────────┤
│ 精层喂养  │ API返回的type字段实际值   │ 锚点状态机更新：                       │
│          │ token消耗量              │   type_registry记录实际出现的枚举值     │
│          │ 延迟/超时/错误码          │   token_ledger记录消耗曲线             │
│          │                          │   失败模式注册到error_atlas             │
├──────────┼──────────────────────────┼───────────────────────────────────────┤
│ 气层喂养  │ 后处理线程的实际吞吐量    │ 气脉图更新：                           │
│          │ 各type转化成功率          │   标记"type=code"转化节点为"淤堵"       │
│          │ 队列积压深度              │   标记"type=checklist"转化节点为"缺失"  │
│          │                          │   计算气脉完整度 = 已实现type数/应实现  │
├──────────┼──────────────────────────┼───────────────────────────────────────┤
│ 神层喂养  │ 跨任务type分布统计        │ 认知图谱新增节点：                     │
│          │ 失败模式聚类结果          │   "L4转化仅sop→code/checklist缺失"     │
│          │ token效率比               │   "主线程串行后处理在type枚举处断流"     │
│          │                          │   生成调参/重构建议注入认知池           │
└──────────┴──────────────────────────┴───────────────────────────────────────┘
```

### 2.2 喂养管道设计（防坑：认知池只进不出）

```
真实API调用
    │
    ▼
┌─────────────────────────┐
│  Trace采集器（精层入口）  │  ← 每次调用记录：type, tokens, latency, status
│  写入：execution_trace   │
└────────────┬────────────┘
             │
    ┌────────▼────────┐
    │ 气脉诊断器       │  ← 每10任务触发一次
    │ 读取trace →     │
    │ 更新qi_map      │     ⚠️ 防坑3：此处必须刷新缓存
    └────────┬────────┘
             │
    ┌────────▼────────┐
    │ 认知注入器       │  ← 每30分钟强制注入
    │ qi_map变化 →    │     新认知必须在30分钟内参与调度
    │ 写入cognition   │
    │ → 触发建议生成    │
    └─────────────────┘
```

**关键约束：**
- 喂养频率：精层每调用即写，气层每10任务刷新，神层每转结束刷新
- 喂养完整性：trace必须包含`type`字段的原始值，不可在后处理前丢弃
- **timeout预防**：B模型turbo用300秒，A模型用600秒，trace采集器不阻塞主链路

## 四、闭环指标体系

### 4.1 双向指标矩阵

```
┌──────────────────────────────────────────────────────────────────────┐
│                        闭环指标矩阵                                   │
│                                                                      │
│    以实养虚方向 ──────→                    ←────── 虚又返实方向      │
│                                                                      │
│ ┌────────────┐  喂养率    ┌──────────┐  驱动率   ┌────────────┐    │
│ │ 实相指标    │ ────────→ │ 框架状态  │ ────────→│ 实相变更     │    │
│ ├────────────┤           ├──────────┤          ├────────────┤    │
│ │ API调用次数 │           │ 认知池    │          │ 代码patch数 │    │
│ │ token消耗   │           │ 条数      │          │ 配置变更数  │    │
│ │ type分布    │           │ qi_map   │          │ 枚举补全数  │    │
│ │ 错误率      │           │ 完整度   │          │ 转化成功率   │    │
│ └────────────┘           └──────────┘          └────────────┘    │
│                                                                      │
│    反馈验证：Δ实相变更 → 新实相指标 → 框架状态更新 → 循环              │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.2 具体指标定义

| 指标ID | 指标名 | 计算方式 | 闭环角色 | 健康阈值 |
|--------|--------|---------|---------|---------|
| M1 | type覆盖率 | 实际转化type数 / 应转化type数 | 实→虚：喂养气脉图 | = 3/3 = 100% |
| M2 | token效率比 | 有效产出token / 总消耗token | 实→虚：喂养精层 | ≥ 0.6 |
| M3 | 认知注入率 | 30分钟内注入任务的认知数 / 池中新生认知数 | 虚→实：防认知池淤堵 | ≥ 80% |
| M4 | 代码驱动比 | 框架认知驱动的patch数 / 总patch数 | 虚→实：驱动真实 | ≥ 50% |
| M5 | 三点一致性 | (写入点∪读取点∪验证点) 交集大小 / 3 | 虚→实：防坑1 | = 1.0 |
| M6 | 循环时延 | 从实相数据产生到框架状态更新的时间 | 闭环完整性 | ≤ 5min |
| M7 | 反馈收敛度 | 代码变更后M1提升量 / 预期提升量 | 循环有效性 | ≥ 0.8 |
| M8 | qi脉完整度 | 已实现转化节点数 / 应实现节点数 | 实→虚→实全链路 | = 100% |

### 4.3 指标联动关系

```
M1(type覆盖率) ──喂养──→ M8(qi脉完整度) ──驱动──→ M5(三点一致性)
                                                      │
                                                      │ 验证
                                                      ▼
M7(反馈收敛度) ←──反馈── M4(代码驱动比) ←──产出── 代码patch
      │
      │ 若 M7 < 0.8
      │ 则：框架认知有误 → 回溯校准锚点
      ▼
   重新进入"先校准锚点再优化链路"
```

## 六、当前问题的闭环推演实例

### 针对「L4成品转化仅sop类型」的完整循环

```
=== 第1轮：以实养虚 ===

[实相] API返回 type="code" 的L4内容
       → 后处理线程读取 type="code"
       → 找不到对应converter
       → 静默丢弃或报错
       → trace记录：type=code, status=dropped, tokens=consumed

[虚相·精] type_registry记录："code"值出现但无converter
[虚相·气] qi_map标记：type=code节点 = "断流"
[虚相·神] 认知池新增：
  "L4转化链路在type=code处断流，精层锚点未闭环"
  优先级：P0
  调参建议：补全ENUM_TYPES + TYPE_CONVERTERS

=== 第1轮：虚又返实 ===

[虚相·神] 取出P0认知 → 生成patch spec
[虚相·气] 决策：修改点A(枚举) + 修改点D(转化器)
[实相·精] 代码落地：

  # 修改点A：校准类型枚举与状态锚点
  ENUM_TYPES = ["sop", "code", "checklist"]
  
  # 修改点B：状态写入
  def validate_type(raw_type):
      assert raw_type in ENUM_TYPES
      return raw_type
  
  # 修改点C：执行读取 + 生效验证
  converter = TYPE_CONVERTERS.get(state["type"])
  assert converter is not None, f"无converter: {state['type']}"
  
  # 修改点D：转化分支
  TYPE_CONVERTERS = {
      "sop": convert_to_sop,
      "code": convert_to_code,        # NEW
      "checklist": convert_to_checklist # NEW
  }

[实相] patch applied → 三点验证通过

=== 第1轮：反馈收敛 ===

[实相] 新API调用 type="code" 
       → 后处理读取到 type="code"
       → conv_code被调用
       → 产出code格式L4成品
       → trace记录：type=code, status=success

[虚相·精] type_registry更新："code"有converter
[虚相·气] qi_map更新：type=code节点 = "畅通"
[虚相·神] 认知池新增：
  "L4 type=code转化链路已修复，气脉畅通"
  → 影响调度权重：code类型任务可正常调度

[指标]
  M1(type覆盖率): 1/3 → 3/3 ✓
  M5(三点一致性): 1.0 ✓
  M7(反馈收敛度): 1.0 ✓
  M8(qi脉完整度): 100% ✓

=== 第2轮：自增强验证 ===

[实相] 新一轮100次API调用
  - type=code/checklist任务不再被丢弃
  - token不浪费在无效重试上
  - T2 < T1 ✓

[虚相] 框架认知升级：
  从"检测type缺失" → "检测转化质量"
  神层进化：开始关注code产出的代码质量而非有无
  
  → 下一轮patch将聚焦于：
    convert_to_code()的输出质量优化
    而非"补全缺失的converter"

=== 自增强循环成立 ===
```

## 七、总结：循环成立的充要条件

```
以实养虚  ⟺  每次真实API调用的trace在5分钟内更新框架三层状态
              认知池30分钟内必须参与注入（防坑3）

虚又返实  ⟺  框架认知驱动的代码patch必须通过三点一致性验证（防坑1）
              代码变更必须实际改变后处理行为（非空转化产出）

自增强    ⟺  第N轮token效率 > 第N-1轮（实相改善）
              框架认知层级在第N轮高于第N-1轮（虚相进化）
              验证耗时在第N轮短于第N-1轮（链路加速）

核心原则  ⟺  先校准锚点(精) → 再优化链路(气) → 最后升级认知(神)
              锚点未闭环时，不优化链路（避免在错误锚点上优化）
```
