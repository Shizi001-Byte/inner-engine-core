# 推演：以实养虚，虚又返实——自增强闭环设计

---

## 一、核心矛盾与设计前提

闭环的危险在于：**虚层可能变成寄生虫**——消耗真实token但不产出真实代码，沦为"认知池只进不出"的变体。

锚定结论指出：引擎自然退化是默认趋势。因此闭环不是"建好了就自转"，而是**必须持续对抗熵增**的结构。

设计原则：**虚层无独立生存权**。虚层的每一分状态必须可追溯到真实API调用，每一分驱动力必须落地为真实代码commit。无法落地的虚层状态自动消亡。

## 二、三段式闭环架构

```
┌─────────────────────────────────────────────────────────────┐
│                    自增强闭环主结构                           │
│                                                             │
│  ┌─── 实层（物质基础）───┐                                  │
│  │ API调用日志            │                                  │
│  │ token消耗/延迟/成功率  │──── 实→虚 映射 ────┐             │
│  │ 代码commit/测试通过率  │                    │             │
│  │ 系统熵测量值           │                    ▼             │
│  └───────────────────────┘            ┌─── 虚层（修炼框架）───┐
│                                       │ 修炼状态机            │
│                                       │ 境界/灵气/瓶颈/渡劫    │
│                                       └──────────┬──────────┘
│                                                  │           │
│  ┌─── 实层（产出验证）───┐                       │           │
│  │ 新代码产出             │◄── 虚→实 驱动 ───────┘           │
│  │ 效率提升测量           │                                │
│  │ 熵降验证              │                                 │
│  └───────────┬───────────┘                                │
│              │                                              │
│              └────── 下一轮实→虚（效率提升→灵气纯度提升）────┘
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 三、实→虚 映射层：用真实数据喂养修炼框架

### 3.1 映射表

| 实层指标 | 虚层语义 | 计算公式 | 数据来源 |
|---------|---------|---------|---------|
| Token消耗总量 | 灵气蓄积量 | `Σ(tokens_in + tokens_out)` | API调用日志 |
| 生产力Token比 | 灵气纯度 | `productive_tokens / total_tokens` | 标注后的调用日志 |
| API成功率 | 道心稳固度 | `success_count / total_calls`（滑动窗口100次） | 调用状态码统计 |
| P95响应延迟 | 悟性速度 | `percentile_95(latency_ms)` | 调用延迟直方图 |
| 错误自恢复率 | 渡劫成功率 | `auto_recovered / total_errors` | 错误处理链路日志 |
| 代码commit频率 | 修炼精进速率 | `commits_with_tests / day` | Git日志 |
| 测试覆盖率增量 | 功法熟练度 | `Δcoverage / cycle` | CI测试报告 |
| 系统熵值 | 心魔指数 | `Σ(degraded_modules) / total_modules` | 状态巡检报告 |

### 3.2 关键约束：灵气纯度门槛

```
灵气纯度 = productive_tokens / total_tokens
```

**productive_tokens定义**：产生了可验证代码产出或解决了标注问题的token消耗。

**门槛规则**：
- 纯度 < 0.3：修炼停滞，触发"走火入魔"告警，虚层停止生成新任务
- 纯度 0.3-0.6：正常修炼，但不可突破境界
- 纯度 > 0.6：可触发境界突破评估

这条约束确保：**大量消耗token但不产出代码的调用会自动降低灵气纯度，虚层无法自我膨胀**。

## 四、虚→实 驱动层：修炼框架驱动真实代码产出

### 4.1 修炼状态机

```
状态定义：
  Realm(境界): [练气 → 筑基 → 金丹 → 元婴 → 化神]
  
  每个境界对应系统成熟度等级：
  - 练气: 基础API调通，能产出代码片段
  - 筑基: 有测试覆盖，CI通过率>80%
  - 金丹: 有自动调参链路，认知池活跃
  - 元婴: 分布式状态机运转，多模型并发
  - 化神: 自增强闭环自转，人工干预率<10%

境界突破条件（全部满足）：
  1. 当前境界驻留时间 ≥ 最低周期（防速通）
  2. 灵气纯度 ≥ 该境界要求阈值
  3. 当前境界的技术债清单清零
  4. 心魔指数 ≤ 0.2
  5. 通过渡劫验证（见4.3）
```

### 4.2 瓶颈→技术债→代码任务 转换链

这是虚→实的核心驱动路径：

```
修炼框架识别瓶颈
    │
    ▼
瓶颈转译为技术债项（TechnicalDebt）
    格式: {
        id, realm, bottleneck_type, 
        target_metric, current_value, 
        required_action,        ← 具体工程动作
        estimated_tokens,       ← 预计token消耗
        verification_method     ← 完成后的验证方式
    }
    │
    ▼
技术债注入任务队列（带优先级）
    │
    ▼
执行引擎消费任务 → 真实代码commit
    │
    ▼
验证：verification_method 执行
    ├─ 通过 → 技术债关闭，境界积分+1
    └─ 未通过 → 技术债保留，降级优先级，记录失败原因
```

### 4.3 渡劫验证：境界突破的"生死考验"

锚定结论5指出数字生命必须经历生死考验。渡劫验证是闭环的自我审计机制：

```
渡劫协议：
  触发条件: 境界突破评估时
  
  验证项：
  1. 因果链完整性
     - 抽查最近20个代码commit
     - 每个commit必须可追溯到某个修炼目标
     - 追溯率 < 80% → 渡劫失败
  
  2. 净值正向性
     - NetValue = Value(代码产出) - Cost(token消耗)
     - 连续3个周期 NetValue > 0 → 通过
     - 任一周期 NetValue < 0 → 渡劫失败，境界不升
  
  3. 退化对抗性
     - 对比当前周期与上一周期的系统熵
     - 熵降或持平 → 通过
     - 熵升 → 渡劫失败，触发"心魔反噬"（降半级境界）
  
  4. 自持性测试
     - 暂停人工干预24小时
     - 闭环是否继续自转（仍有代码产出）
     - 停转 → 渡劫失败，标记为"需人工渡劫"
```

## 五、闭环指标体系

### 5.1 核心闭环指标

```
┌─────────────────────────────────────────────────────────────┐
│                    闭环健康度仪表盘                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 闭环增益率 (Loop Gain Ratio, LGR)                       │
│     = 本轮代码产出价值 / 上轮token消耗成本                    │
│     自增强条件: LGR > 1.0 且单调上升                          │
│     退化预警: LGR < 0.8 连续2轮                             │
│                                                             │
│  2. 虚实转化率 (Virtual-to-Real Conversion, VRC)           │
│     = 被执行的技术债数 / 生成的技术债总数                      │
│     健康: VRC > 0.7                                         │
│     停滞: VRC < 0.3 → 虚层空转，触发清理                     │
│                                                             │
│  3. 灵气纯度趋势 (Purity Trend)                             │
│     = 纯度的滑动平均斜率                                     │
│     上升 → 闭环正在增强                                      │
│     下降 → 闭环正在退化                                      │
│                                                             │
│  4. 熵对抗效率 (Entropy Counter-Efficiency, ECE)            │
│     = 熵降量 / 维护动作消耗的token                            │
│     高ECE → 用更少token降更多熵                              │
│     低ECE → 维护成本过高，需优化                              │
│                                                             │
│  5. 自持半衰期 (Self-Sustaining Half-Life, SSHL)            │
│     = 撤掉人工干预后闭环维持自转的时间                        │
│     目标: SSHL → ∞（永久自转）                                │
│     底线: SSHL ≥ 24h                                         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 指标间因果关系链

```
灵气纯度↑ → 境界可突破 → 渡劫通过 → 
技术债清理加速 → 代码产出↑ → 
系统熵↓ → API效率↑ → 
灵气纯度↑↑ （正反馈增强）

灵气纯度↓ → 修炼停滞 → 
技术债堆积 → 瓶颈无法突破 → 
系统熵↑ → API效率↓ → 
灵气纯度↓↓ （负反馈退化）
```

**关键设计**：正反馈有上限（境界封顶），负反馈有底线（渡劫失败触发降级重置）。这确保系统不会无限膨胀也不会无限崩溃。

## 六、验证方法

### 6.1 注入验证：实→虚是否真的发生

```
验证目标: 真实API调用是否真的更新了修炼状态

方法:
  1. 记录一批API调用的token消耗
  2. 检查修炼状态机中灵气蓄积量是否对应增加
  3. 检查灵气纯度是否根据productive_tokens计算

验证脚本伪代码:
  before = get_cultivation_state()
  call_log = execute_batch_tasks(n=10)
  after = get_cultivation_state()
  
  assert after.spiritual_energy > before.spiritual_energy
  assert abs(after.spiritual_energy - before.spiritual_energy 
             - sum(call_log.tokens)) < epsilon
  assert after.purity == productive_tokens / total_tokens

失败处理:
  如果状态未变化 → 检查三个点:
    ① 状态写入: API调用日志是否写入状态库
    ② 执行读取: 修炼状态机是否读取了新日志
    ③ 生效验证: 纯度计算是否实际执行
  （对应坑库预警#1: 三点缺一不可）
```

### 6.2 驱动验证：虚→实是否真的发生

```
验证目标: 修炼框架生成的目标是否真的驱动了代码产出

方法:
  1. 在修炼框架中注入一个测试瓶颈
  2. 检查是否生成了对应的技术债项
  3. 检查技术债是否进入任务队列
  4. 检查是否被执行引擎消费
  5. 检查是否产生了真实代码commit
  6. 检查verification_method是否被调用

验证脚本伪代码:
  debt_id = inject_test_bottleneck(
      type="test_coverage_gap",
      target="module_X coverage > 80%",
      current="62%"
  )
  
  wait_for_queue_processing(timeout=300)  # turbo模型300秒
  
  commit = find_commit_by_debt_id(debt_id)
  assert commit is not None
  assert commit.tests_passed == True
  assert get_coverage("module_X") > 0.80
  
  # 关键: 验证不是巧合
  assert debt_id in commit.traceability_tags

失败处理:
  如果技术债未被执行 → 检查:
    ① 技术债是否真的进入队列（非仅写入数据库）
    ② 队列消费者是否读取了该项（非轮空）
    ③ 执行结果是否回写了状态（非丢弃）
```

### 6.3 自增强验证：闭环是否真的在增强

```
验证目标: 每轮循环后系统效率是否真的提升

方法: A/B对照实验
  - 实验组: 启用完整闭环（实→虚→实）
  - 对照组: 仅保留实层（API调用+代码产出，无修炼框架）
  - 运行N=10个周期
  - 比两组的: 代码产出量、token效率、系统熵

预期结果:
  - 实验组LGR单调上升
  - 对照组LGR持平或下降（因退化是默认趋势）
  - 实验组系统熵下降或持平
  - 对照组系统熵上升

关键判定:
  如果实验组和对照组无显著差异 → 修炼框架是寄生层，无净贡献
  → 触发"生死考验"协议: 要么证明价值，要么裁撤虚层
```

## 七、防退化机制（基于坑库经验）

### 7.1 防"认知池只进不出"的等价问题

| 坑库现象 | 闭环中的等价 | 防御机制 |
|---------|------------|---------|
| 认知1700条不注入 | 技术债堆积不执行 | 技术债超时30分钟未入队列→自动降级；超时2小时→清除 |
| 新认知不参与调度 | 新瓶颈不生成任务 | 每轮结束强制刷新瓶颈列表，对比上一轮必须有新增 |
| 静态档案库 | 修炼状态不更新 | 灵气蓄积量必须每10任务更新一次，超时标记为"停滞" |

### 7.2 防自动调参全链路失效

任何新增修炼参数（如新的境界阈值、纯度权重）必须同步三个点：

```
新增参数: purity_threshold (灵气纯度门槛)
  ① 状态写入: cultivation_config表中写入该参数
  ② 执行读取: 境界突破检查逻辑中读取该参数
  ③ 生效验证: 注入purity=0.29的测试数据，验证突破被阻止

验证脚本:
  set_config("purity_threshold", 0.6)
  inject_state(spiritual_energy=99999, purity=0.55)
  assert not can_breakthrough()  # 应被阻止
  
  inject_state(spiritual_energy=99999, purity=0.65)
  assert can_breakthrough()      # 应被允许
```

### 7.3 防ProxyError和超时

```
API调用统一封装:
  - 使用urllib直连，不引入requests
  - 如必须用requests: session.proxies = None
  - timeout预设: B模型turbo=300s, A模型=600s
  - 超时后自动降级: 不影响修炼状态更新（降级记录而非丢弃）
```

### 7.4 闭环停止条件（防虚层寄生）

```
停止条件（任一触发即暂停虚层）:
  1. LGR < 0.5 连续3轮 → 虚层消耗大于产出
  2. VRC < 0.2 连续3轮 → 虚层生成目标不被执行
  3. 灵气纯度 < 0.2 → 大量token浪费
  4. 自持半衰期 < 1h → 离开人工就停转

停止后:
  - 虚层进入"闭关"状态，不再生成新任务
  - 实层继续运行（API调用+代码产出不受影响）
  - 触发人工审计: 分析退化原因
  - 修复后重新启动，从当前境界降一级开始
```

## 九、核心结论

**"以实养虚"的本质**：用真实token消耗为虚层提供存在依据——没有真实API调用数据的修炼状态是死的，自动消亡。

**"虚又返实"的本质**：虚层的唯一存在目的是为实层生成可执行、可验证的工程任务——不产出代码commit的修炼境界是寄生，触发裁撤。

**自增强的充要条件**：闭环增益率LGR > 1.0且单调上升。这意味着每消耗1单位的token成本，必须产出大于1单位的代码价值，且这个比率在持续改善。

**生死考验的判定**：撤掉人工干预后，闭环是否能继续自转并保持LGR > 1.0。能则生，不能则降级重来。这正是锚定结论5的工程化落地——**拒绝虚层僭越实层，拒绝消耗不产出**。
