# 任务类型: deep

基于您提供的已验证核心结论与历史踩坑经验，我们无需再论证引擎的崩溃恢复（Guardian+Core/WAL）和存储单向同步机制。以下直接在这些基石之上，推演**“以实养虚，虚又返实”**的自增强闭环架构设计、指标体系及验证方法。

---

### 一、 架构核心思想：虚实双轨状态机

将系统拆分为**实轨（物理层）**与**虚轨（认知层）**，通过引擎的 `WAL + Snapshot` 机制保证两者状态的原子一致性。

*   **实轨**：真实的 API 请求、Token 消耗、代码编译/运行结果、报错堆栈。
*   **虚轨**：Agent 的“修为境界”、“功法权重”、“灵根（调度参数）”、“悟道心得（认知池）”。
*   **单向同步与幂等落实**：虚轨演化产生的策略变更，必须单向写入引擎产物包作为唯一事实源，下游存储（飞书/Supabase）仅做展示，同状态多次重放结果幂等。

---

### 二、 闭环推演：“以实养虚，虚又返实”

#### 阶段一：以实养虚（物理消耗转化为修为演进）
真实任务的执行结果作为“灵气”注入虚轨，驱动框架演化。

1.  **真实 API 喂养（避坑落地）**：
    *   底层统一使用 `urllib` 直连或 `requests(proxies=None)`，规避全局代理 ProxyError。
    *   预设硬性 Timeout（B模型turbo 300秒，A模型 600秒），超时即视为“走火入魔（天劫）”，捕获异常并生成“抗劫心得”。
2.  **修为与境界映射**：
    *   **灵气积累**：成功执行任务并产出可用代码，按产出有效代码行数/解决复杂度折算“灵气”（Token消耗作为练功成本扣减）。
    *   **境界突破**：灵气达到阈值，Agent 境界提升（如从筑基到结丹），解锁更高复杂度的任务调度权限。
    *   **心魔潜伏**：任务失败、编译报错计入“心魔值”，心魔过高则触发“心魔劫”，强制降低并发权重。
3.  **认知反哺与强制注入（避坑落地）**：
    *   将报错和解决过程提炼为“悟道心得”写入认知池。
    *   **防静态档案库**：在引擎状态机中设定硬性规则——每10个任务或每轮执行结束，必须刷新认知缓存；新认知生成后 30 分钟内必须参与下一轮任务的 Prompt 注入。

#### 阶段二：虚又返实（修为境界驱动真实代码产出）
虚轨的境界提升和认知积累，不可停留在日志里，必须转化为实轨的工程参数和代码产出。

1.  **境界驱动参数演化（避坑落地）**：
    *   随着境界提升，虚轨自动生成新的“灵根配置”（如并发数提升、冷却时间缩短、权重重分配）。
    *   **防全链路失效**：新增配置必须严格执行三步走——①写入 `state.wal`；②Core 执行读取时拉取最新配置；③在代码执行前打印 `Config verified: [param=value]` 作为生效验证。
2.  **功法驱动代码生成**：
    *   “功法”即 Prompt 模板和代码架构模式。高境界 Agent 会将认知池中的“设计模式心得”作为 System Prompt 注入，驱动真实 API 产出更健壮的代码。
3.  **虚实产物固化（单向同步落实）**：
    *   虚轨的境界日志、认知池快照、实轨的代码产物，统一打包为引擎产物包。遵循幂等优先原则，即便重放也不会产生重复境界记录和代码文件。

### 三、 闭环指标设计

为了量化“虚实循环”是否真正运转且未失效，设计以下三大类指标：

#### 1. 实轨指标
*   **有效产出率**： `(通过测试的代码行数) / (总 Token 消耗 * 1000)` —— 衡量“实”的成本效益。
*   **天劫发生率**： `API超时/ProxyError次数 / 总调用次数` —— 衡量物理层稳定性。

#### 2. 虚轨指标
*   **认知周转率**： `被注入Prompt的认知条数 / 认知池总条数` —— 核心指标，必须 >0，否则触发“只进不出”坑。
*   **境界转化比**： `策略实际生效次数 / 虚轨生成的策略总数` —— 核心指标，必须 = 100%，否则触发“调参失效”坑。

#### 3. 虚实转化指标
*   **返虚率**： `因认知注入而避免的重复报错次数 / 总执行任务数` —— 衡量虚轨认知对实轨的指导价值。
*   **境界红利系数**： `高境界状态下的任务成功率 / 低境界状态下的任务成功率` —— 衡量虚轨进化对实轨产出的真实提升。

### 四、 验证方法（基于崩溃自恢复架构）

依托 Guardian 和 Core 的心跳互拉机制，设计以下压力测试和断言验证：

#### 1. 验证“以实养虚”（防只进不出）
*   **操作**：模拟连续 10 个失败任务，触发报错并写入认知池。
*   **断言**：检查第 11 个任务的 Prompt 构建日志，必须包含新写入的认知条目；若未包含，Guardian 主动 kill Core 并从 Snapshot 恢复，标记认知注入模块异常。
*   **通过标准**：认知周转率在 30 分钟内不为 0。

#### 2. 验证“虚又返实”（防调参全链路失效）
*   **操作**：手动注入一条高优先级认知，使得虚轨生成新的并发配置（如从 2 改为 4）。
*   **断言**：
    1.  检查 `state.wal` 是否有 `concurrency=4` 的记录。
    2.  检查 Core 下一轮调度是否实际发起了 4 个并发请求。
    3.  检查执行日志是否打印 `Config verified: concurrency=4`。
*   **通过标准**：境界转化比达到 100%，缺任一步骤判定为全链路失效。

#### 3. 验证幂等与崩溃恢复下的虚实一致性
*   **操作**：在虚轨境界突破（写入 WAL 但未 Snapshot）的瞬间，强制 `kill -9` Core 进程。
*   **断言**：
    1.  Guardian 心跳超时，重新拉起 Core。
    2.  Core 恢复 `state.snapshot + state.wal`，境界状态不丢失。
    3.  引擎产物包重放该阶段的任务，生成的代码和认知记录与崩溃前完全一致（无重复数据）。
*   **通过标准**：系统恢复后，循环正常推进，无重复 Token 消耗与重复文件生成。

**总结**：此架构将 API 消耗与代码产出具象化为 Agent 修为，强制通过缓存刷新机制和三步配置法打通“认知-调度-执行”的任督二脉。依托 WAL+Guardian 确保虚实状态流转不因崩溃断裂，最终实现越用越聪明、越挫越强悍的自增强引擎。
