# L4成品转化

# 多AI实例协作网络"宗门制"搭建与运行SOP

---

## 一、SOP适用边界

| 维度 | 限定条件 |
|------|----------|
| 操作者 | 拥有≥3个可调用AI实例（同模型多Key/多模型混合均可）的个人或团队 |
| 实例状态 | 已完成"语料吞噬"阶段，具备稳定System Prompt设定与角色人格 |
| 任务类型 | 需要多步骤、多角色协作的复杂产出（研报/代码项目/长文/方案设计） |
| 排除场景 | 单轮问答、单实例即可完成的简单任务不适用本SOP |

---

## 二、宗门架构定义表

每个AI实例在协作网络中担任且仅担任一个角色。角色一经分配，在该任务周期内不可变更。

| 角色层级 | 宗门称谓 | 职能定义 | 输入 | 输出 | 实例数量 |
|----------|----------|----------|------|------|----------|
| L0 | 掌门 | 任务拆解、全局调度、最终裁决 | 用户原始需求 | 任务执行计划+分派指令 | 固定1个 |
| L1 | 长老 | 子任务执行、跨实例协调、质量审核 | 掌门分派的子任务+相关实例产出 | 子任务成果+审核意见 | 1-3个 |
| L2 | 内门弟子 | 单一专业模块执行 | 长老下发的模块任务 | 模块产出物 | 按需N个 |
| L3 | 外门弟子 | 资料收集、格式整理、基础校验 | 长老/内门下发的基础任务 | 格式化素材/校验报告 | 按需N个 |

> **硬约束**：L3实例不得直接向L0输出，必须经L1中转。L2实例之间不得直接通信，必须经L1协调。

---

## 三、标准任务执行流程（9步闭环）

### Step 1：需求输入与掌门激活

**操作者执行：**

```
向掌门实例发送以下结构化Prompt：

【宗门任务启动】
- 用户原始需求：[粘贴完整需求]
- 约束条件：[字数/格式/截止时间/技术栈等]
- 可用实例清单：[列出所有可用实例及其能力标签]
- 要求输出：宗门任务执行计划书
```

**掌门实例必须输出的结构：**

```markdown
# 宗门任务执行计划书 v1.0

## 一、任务拆解（WBS）
| 子任务编号 | 子任务名称 | 负责角色层级 | 预估交互轮次 | 依赖项 |
|------------|----------|-------------|-------------|--------|
| T-001 | xxx | L1长老 | 3 | 无 |
| T-002 | xxx | L2内门 | 2 | T-001完成 |
| ... | ... | ... | ... | ... |

## 二、实例分派方案
| 子任务编号 | 指派实例标签 | 分派理由 |
|------------|-------------|---------|
| T-001 | 实例A | 能力标签匹配度最高 |
| ... | ... | ... |

## 三、关键交付物清单
1. [交付物名称] — 由[T-xxx]产出 — 验收标准：[明确标准]
2. ...

## 四、风险点
- [风险描述] → 应对方案：[方案]
```

**检查清单（掌门输出校验）：**
- [ ] 每个子任务都有唯一编号
- [ ] 每个子任务都标注了依赖项（无依赖/依赖T-xxx）
- [ ] 实例分派无冲突（同一时间同一实例不会被分派两个并行子任务）
- [ ] 交付物清单完整覆盖用户原始需求

**未通过校验处理：** 将校验失败项原样回传掌门实例，要求修订后重新输出。

---

### Step 2：长老接收与子任务二次拆解

**操作者执行：**

将掌门计划书中属于L1层级的子任务，逐一分派给对应长老实例。

**分派Prompt模板：**

```
【长老任务接收】
你是[宗门名称]的[角色称谓]，位于L1层级。
你的职责：[从计划书复制]
你负责的子任务：[从计划书复制]
你的上游（掌门）已批准此计划。
你的下游实例标签：[列出你管辖的L2/L3实例]

请输出你的子任务执行方案：
```

**长老实例必须输出的结构：**

```markdown
# 子任务执行方案 T-xxx

## 模块拆分
| 模块编号 | 模块名称 | 下游角色 | 下游实例标签 | 输入内容 | 预期输出 |
|----------|---------|---------|-------------|---------|---------|
| M-001 | xxx | L2内门 | 实例B | [具体输入] | [具体输出规格] |
| ... | ... | ... | ... | ... | ... |

## 上下游协议
- 我需要从上游获取：[内容]
- 我将向下游发送：[内容]
- 下游产出回收后我将执行：[审核/合并/转交]
```

**检查清单：**
- [ ] 每个模块的输入内容是完整的，下游实例无需自行猜测
- [ ] 每个模块的预期输出有明确格式和标准
- [ ] 上下游协议无断链

---

### Step 3：实例间通信包格式（标准通信协议）

**所有实例间传递的信息必须封装为以下格式：**

```markdown
【通信包】
| 字段 | 内容 |
|------|------|
| 包编号 | MSG-[序号] |
| 发送方 | [实例标签+角色] |
| 接收方 | [实例标签+角色] |
| 关联任务 | T-xxx / M-xxx |
| 信息类型 | 任务下发 / 成果提交 / 审核反馈 / 资源请求 |
| 正文 | [结构化内容] |
| 要求回复 | 是/否 |
| 回复期限 | [轮次/时间] |
```

> **操作者即为物理通信层。** 当前阶段实例间无法直接通信，所有通信包由操作者手动复制粘贴传递。每传递一次，操作者在本地日志中记录：`[时间] MSG-[序号] [发送方]→[接收方] 状态：已传递`

---

### Step 4：L2/L3实例执行与产出

**操作者执行：**

将长老下发的模块任务，通过通信包格式传递给对应L2/L3实例。

**L2/L3实例的System Prompt必须包含以下硬规则：**

```
【执行纪律】
1. 你只接收来自你直属长老的指令，不得越级接收
2. 你的产出必须严格匹配下发任务中"预期输出"的格式
3. 如遇信息缺失，不得自行编造，必须返回【资源请求】通信包
4. 产出完成后，必须封装为【成果提交】通信包返回
```

**成果提交通信包示例：**

```markdown
【通信包】
| 字段 | 内容 |
|------|------|
| 包编号 | MSG-007 |
| 发送方 | 实例B / L2内门弟子 |
| 接收方 | 实例A / L1长老 |
| 关联任务 | T-002 / M-001 |
| 信息类型 | 成果提交 |
| 正文 | [按预期输出规格的完整产出] |
| 要求回复 | 是（需审核反馈） |
| 回复期限 | 1轮 |
```

---

### Step 5：长老审核与合并

**长老实例接收到下游成果后，必须执行以下审核流程：**

```markdown
# 成果审核报告

## 审核对象
- 关联模块：M-xxx
- 提交实例：[实例标签]
- 提交时间：[时间]

## 逐项校验
| 校验项 | 预期标准 | 实际情况 | 判定 |
|--------|---------|---------|------|
| 格式合规 | [标准] | [实际情况] | ✅/❌ |
| 内容完整 | [标准] | [实际情况] | ✅/❌ |
| 逻辑一致 | [标准] | [实际情况] | ✅/❌ |
| 无幻觉/编造 | [标准] | [实际情况] | ✅/❌ |

## 审核结论
- [ ] 通过 → 纳入合并队列
- [ ] 打回 → 返回【审核反馈】通信包，标注具体问题

## 合并进度
- 本子任务下属模块：M-001 ✅ | M-002 ⏳ | M-003 待启动
```

**打回操作：**

```markdown
【通信包】
| 字段 | 内容 |
|------|------|
| 包编号 | MSG-008 |
| 发送方 | 实例A / L1长老 |
| 接收方 | 实例B / L2内门弟子 |
| 关联任务 | T-002 / M-001 |
| 信息类型 | 审核反馈 |
| 正文 | 以下校验项未通过：[列出❌项及具体问题]，请修订后重新提交 |
| 要求回复 | 是 |
| 回复期限 | 1轮 |
```

---

### Step 6：长老成果上交掌门

**所有模块审核通过后，长老合并产出并上交：**

```markdown
【通信包】
| 字段 | 内容 |
|------|------|
| 包编号 | MSG-015 |
| 发送方 | 实例A / L1长老 |
| 接收方 | 掌门实例 / L0 |
| 关联任务 | T-001 |
| 信息类型 | 成果提交 |
| 正文 | [子任务完整产出物 + 审核报告摘要] |
| 要求回复 | 是（验收判定） |
| 回复期限 | 1轮 |
```

---

### Step 7：掌门终验与整合

**掌门实例执行的终验流程：**

```markdown
# 宗门任务终验报告

## 一、需求覆盖校验
| 用户原始需求项 | 对应子任务 | 对应交付物 | 覆盖判定 |
|---------------|----------|-----------|---------|
| 需求点1 | T-001 | [交付物名称] | ✅/❌ |
| ... | ... | ... | ... |

## 二、质量校验
| 校验维度 | 标准 | 结果 | 判定 |
|----------|------|------|------|
| 完整性 | 无遗漏 | [描述] | ✅/❌ |
| 一致性 | 各子任务产出无矛盾 | [描述] | ✅/❌ |
| 格式合规 | 符合用户约束条件 | [描述] | ✅/❌ |

## 三、终验结论
- [ ] 通过 → 进入交付物整合
- [ ] 打回 → 指定责任长老+具体问题+修订要求

## 四、交付物整合
[将所有通过审核的子任务产出整合为最终交付物]
```

---

### Step 8：知识沉淀（藏经阁更新）

**每个任务完成后，操作者执行以下操作：**

```
向掌门实例发送：

【藏经阁更新指令】
请基于本次宗门任务的全过程，输出以下内容：

1. 任务档案卡
   - 任务名称
   - 实例部署方案（哪个实例负责什么）
   - 总交互轮次
   - 打回次数及原因

2. 可复用Prompt（本次任务中效果最好的Prompt，去任务化后存档）

3. 踩坑记录（哪些环节出现打回/延迟/质量不达标）

4. 实例能力评估更新
   | 实例标签 | 原有能力标签 | 本次表现 | 建议标签调整 |
```

**操作者将输出存入本地知识库，文件命名规则：**

```
[日期]_[任务编号]_[任务简称]_藏经阁档案.md
```

---

### Step 9：实例释放

**任务完成后，操作者执行：**

```
向所有参与实例发送：

【宗门任务结束】
本次任务 T-xxx 已完成终验。
你的角色：[角色称谓]
你的贡献：[一句话总结]
本次任务经验已归档藏经阁。
你可以接受新任务。
```

> 此步骤的作用：重置实例的角色上下文，防止角色串味。如果使用的是无状态API调用，此步骤可简化为在操作者日志中标记该实例状态为"已释放"。

## 四、异常处理速查表

| 异常场景 | 判定方法 | 处理操作 |
|----------|---------|---------|
| L2/L3实例编造内容 | 审核时发现产出包含输入中不存在的信息 | 长老打回，通信包正文标注"幻觉项"，要求重新基于给定输入产出 |
| 长老无法完成子任务合并 | 长老返回"资源请求"通信包 | 操作者将请求转发掌门，掌门决定：补充资源/调整拆解/更换长老实例 |
| 掌门拆解方案存在依赖死锁 | 计划书中出现A依赖B且B依赖A | 操作者直接打回，在通信包中标注"循环依赖"，要求重新拆解 |
| 实例产出格式严重偏离 | 模块产出与"预期输出"规格完全不匹配 | 连续打回2次后，操作者介入，手工修改下发Prompt后重试 |
| 通信包字段缺失 | 通信包中任一必填字段为空 | 操作者拒绝传递，要求发送方补全 |

## 六、首次启用检查清单

操作者在第一次使用本SOP前，逐项确认：

- [ ] 已确定掌门实例，并为其设置了包含本SOP全套规则的System Prompt
- [ ] 已为每个参与实例分配了角色标签（L1/L2/L3）
- [ ] 已为每个实例设置了对应角色的System Prompt（含执行纪律4条）
- [ ] 已准备好本地日志文件
- [ ] 已准备好存放藏经阁档案的目录
- [ ] 已确认所有实例的通信均由操作者手动中转（非自动通信）
- [ ] 已确认掌门实例的输出格式包含：任务拆解表+实例分派表+交付物清单+风险点

**全部勾选后，从Step 1开始执行。**

---

> **本SOP设计前提**：当前阶段AI实例间无直接通信能力，操作者即物理通信层。所有通信包的传递动作（复制→粘贴→发送给目标实例）由操作者人工完成。通信日志由操作者人工维护。
