# L4 检查清单：V7.5 方舟效能引擎「多线程API调用 + 串行后处理」架构下的热重启

> 场景限定：引擎在线运行中，需在不中断对外服务的前提下完成热重启。已知约束——慢接口不持锁、不阻塞其他worker；禁止用全局大锁锁住整条流程。以下清单按执行时序编排，前一阶段未通过不得进入下一阶段。

---

## 阶段一：重启前状态采集与排空

### ☐ 1.1 活跃 worker 线程清单已导出并比对
- **判定标准**：`/ark/runtime/threads/active` 返回的线程数与配置池上限（默认 `worker_pool_size`）差值 ≤ 2；每个线程状态为 `IDLE` 或 `API_INVOKING` 或 `POST_PROCESSING` 三者之一，不存在 `UNKNOWN` / `STUCK > 60s`。
- **异常处理**：若存在 `STUCK > 60s` 的线程——记录线程ID与堆栈快照至 `/ark/logs/restart-stuck-{ts}.json`，将其标记为 `ZOMBIE` 跳过排空等待，但**不得直接 kill**（避免后处理中途中断导致脏写），转入阶段二由该线程自然超时退出。

### ☐ 1.2 串行后处理队列水位已确认可排空
- **判定标准**：`post_process_queue.depth` < `post_process_queue.high_watermark * 0.3`；且队列头部任务入队时间距今 < `single_post_proc_timeout * 2`（说明无积压卡死）。
- **异常处理**：若水位 ≥ 0.3 但 < 高水位——将 `api_ingress_rate_limit` 临时下调至当前值的 50%，等待队列排空至 < 0.3 后继续；若头部任务已超 `single_post_proc_timeout * 2`——判定后处理死锁，执行 **Bypass后处理**（见1.3），不要加全局锁等待。

### ☐ 1.3 后处理死锁的 Bypass 决策已记录
- **判定标准**：当1.2触发死锁判定时，运维人员已在变更工单中勾选"启用 Bypass"并填写工单号；`/ark/config/post_process/bypass_until` 已设置为 `当前时间 + 15min`，引擎已切换为"API结果直写不经过后处理"模式。
- **异常处理**：若 Bypass 开关置位失败——**中止重启**，回滚 `ingress_rate_limit` 至原始值，触发 P2 告警；不得在死锁状态下强制重启（会导致后处理队列中的半成品数据丢失）。

---

## 阶段二：API 调用层优雅降级

### ☐ 2.1 入口流量已切换至灰度旁路
- **判定标准**：`/ark/ingress/route` 当前值 = `BYPASS`，旁路目标健康检查通过（连续 3 次探活返回 200）；当前引擎 `in_flight_api_calls` 停止增长（5秒采样窗口内增量 ≤ 1）。
- **异常处理**：若旁路目标探活失败——立即将入口切回 `PRIMARY`，中止本次重启，记录为"旁路不可用"；**禁止**直接降级入口返回 503（会触发上游熔断级联）。

### ☐ 2.2 各模型 API 客户端 timeout 值已核对
- **判定标准**：
  - B模型 turbo 系列：`client.timeout = 300s`
  - A模型系列：`client.timeout = 600s`
  - 其他模型：按 `model_timeout_registry.yaml` 中的预设值
  - 所有客户端的 `retry_policy.max_attempts ≤ 2`（重启场景下禁止无限重试占用 worker）
- **异常处理**：若发现 timeout 值偏离预设——**逐客户端修正**，不要批量重载配置（批量重载会触发配置广播风暴）；修正后单客户端发起一次 ping 校验确认生效。

### ☐ 2.3 慢接口 worker 的自然退出已确认
- **判定标准**：入口切换旁路后等待 `max(model_timeout) + 30s`（即至少 630秒），`in_flight_api_calls` 降至 0；或剩余 worker 全部处于 `IDLE`。**关键认知**：此处等待不是因为慢接口持锁，而是让其在途请求自然完成或超时，避免中断导致上游连接池泄露。
- **异常处理**：若 630秒后仍有 `in_flight > 0`——对剩余 worker 发送 `SIGTERM` 级别2（软终止 + 5秒宽限），同时记录被中断的 `request_id` 列表至 `/ark/logs/interrupted-requests-{ts}.log`，供上游幂等重试。

## 阶段三：串行后处理队列的最终排空

### ☐ 3.1 后处理队列已完全排空或已安全冻结
- **判定标准**：以下两者满足其一：
  - (A) `post_process_queue.depth = 0` 且 `last_drain_ts` 距今 < 5秒
  - (B) 阶段一已启用 Bypass（1.3通过），且队列头部任务已被标记为 `ABANDONED`（写入 `abandoned_postproc` 表，含原始 request_id + payload_hash）
- **异常处理**：若队列既未排空也未启用 Bypass——**回退到阶段一 1.2**，重新评估水位；禁止在此处引入全局锁等待队列清空（违反核心约束，且会阻塞后续阶段）。

### ☐ 3.2 后处理的幂等性已确认（针对 Bypass 场景）
- **判定标准**：当走 Bypass 路径时，`/ark/config/post_process/idempotency_key` = `request_id`，且 `idempotency_store` 可达（Redis ping < 10ms）；已确认 `abandoned_postproc` 表中的记录会在引擎重启后由重放消费者处理。
- **异常处理**：若 `idempotency_store` 不可达——**禁止 Bypass**，改为等待队列自然排空（接受更长的重启窗口）；若队列也无法自然排空——升级为冷重启（走标准数据恢复流程，不在本清单范围内）。

## 阶段四：重启执行

### ☐ 4.1 引擎状态已持久化至检查点文件
- **判定标准**：`/ark/runtime/checkpoint/latest.json` 的 `mtime` 距今 < 10秒；文件内容包含 `worker_pool_config`、`ingress_route`、`rate_limit_current`、`post_process_bypass_until` 四个字段且值与内存一致；`checkpoint.lock` 文件已释放（不存在或内容为空）。
- **异常处理**：若检查点写入失败——**中止重启**，保持引擎运行，触发 P1 告警；不得在无检查点的情况下重启（会导致 worker 配置丢失、rate_limit 重置为默认值引发流量突刺）。

### ☐ 4.2 重启信号已发送且收到 ACK
- **判定标准**：`POST /ark/admin/restart` 返回 `202 Accepted` 且 body 含 `restart_id`；`restart_id` 已记录至运维工单；15秒内 `health` 端点返回 `RESTARTING` 状态。
- **异常处理**：若 15秒内未收到 `RESTARTING`——检查 `restart_id` 对应的 `restart_status` 日志；若状态为 `REJECTED`（原因通常是前置检查未通过）——回退到对应阶段修正后重试；若状态为 `TIMEOUT`——手动执行 `kill -USR2 <pid>` 触发硬重启信号，同时准备冷启动预案。

### ☐ 4.3 引擎进程已成功拉起并加载检查点
- **判定标准**：引擎进程 PID 已更新（与重启前不同）；`/ark/runtime/checkpoint/latest.json` 的 `mtime` 在进程启动后 30秒内被更新（说明检查点已被加载）；`worker_pool.active_count` 在 60秒内达到配置上限的 100%。
- **异常处理**：若 60秒内 worker 未达到 100%——检查 `worker_spawn_failures` 日志；若失败原因均为 `api_client_init_timeout`（API 客户端初始化超时）——延长 `worker_spawn_grace_period` 至 120秒后重试拉起失败的 worker；若失败原因包含其他——仅重启失败的 worker，不重启整个进程。

---

## 阶段五：重启后校验与恢复

### ☐ 5.1 入口流量已切回 PRIMARY 且健康
- **判定标准**：`/ark/ingress/route` = `PRIMARY`；连续 5 次 health check 间隔 10秒均返回 200；`p99_latency` 在切回后 5分钟内未超过重启前 7天 p99 的 1.5倍。
- **异常处理**：若 p99 超标——将入口切回 `BYPASS`，检查 `post_process_queue.depth` 是否因重启后流量突刺而快速堆积；若 `depth > high_watermark`——启动限流降级（rate_limit 降至 30%），逐步放开。

### ☐ 5.2 Bypass 期间积压的后处理任务已开始重放
- **判定标准**：若阶段一启用了 Bypass——`replay_consumer.lag` 在重启后 10分钟内开始下降（初始值 = `abandoned_postproc` 表行数）；`replay_consumer.error_rate < 5%`。
- **异常处理**：若 lag 未下降——检查 `replay_consumer` 是否正确订阅了 `abandoned_postproc` 表的变更流；若订阅正常但 error_rate ≥ 5%——对错误任务逐条检查 `idempotency_key` 冲突情况，将冲突任务标记为 `SUPERSEDED`（被后续请求覆盖，无需重放）。

### ☐ 5.3 慢接口监控基线已恢复
- **判定标准**：重启后 30分钟内，`api_call_duration_p99`（按模型分组）未出现持续 > `model_timeout * 0.8` 的告警；`api_call_timeout_count` 在 30分钟内 < 10。
- **异常处理**：若 timeout_count ≥ 10——检查是否为 timeout 值在重启后被重置为默认值（已知坑：部分模型客户端配置在重启时未正确加载自定义 timeout）；逐客户端执行 `GET /ark/runtime/clients/{model}/timeout` 核对，偏离者执行热更新（无需重启）。
