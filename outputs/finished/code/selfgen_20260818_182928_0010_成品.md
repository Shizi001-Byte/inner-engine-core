# SOP：基于 Block 级别的文件同步一致性校验

## 1. 目的
解决文件同步系统中“同文件名、同大小、同 mtime，但底层数据 Block 顺序不同”导致的**假同步/静默数据撕裂**问题。杜绝仅凭元数据判定一致性带来的风险。

## 2. 适用范围
所有涉及跨节点、跨存储介质的数据同步、灾备恢复、增量对账任务。

## 3. 核心执行原则
- **文件仅为索引，Block 为真正数据单位**：禁止仅凭文件元数据判定同步成功。
- **假同步熔断机制**：遇到“同文件名、同大小、同 mtime，但 Block 顺序不同”的样本，一律判为**不同步**，必须触发重同步。
- **认知闭环机制**：发现的异常模式必须在30分钟内作为新认知注入调度系统，禁止认知只进不出。

---

## 4. 标准执行步骤

### 步骤 1：提取并比对文件元数据（索引层校验）
1. 在源端和目标端分别执行元数据提取命令：
   `stat -c '%n %s %Y' <file_path>` （输出：文件名、大小、mtime）
2. 比对输出结果：
   - 若元数据不一致：直接判定为**不同步**，跳转至步骤 4。
   - 若元数据完全一致：**严禁判定为同步成功**，必须继续执行步骤 2。

### 步骤 2：提取 Block 哈希序列（数据层校验）
1. 获取系统 Block 大小（通常为 4096 字节）。
2. 在源端，将文件按 Block 切片并计算每个 Block 的哈希值，生成序列文件：
   `dd if=<file_path> bs=4096 count=1 skip=<block_index> 2>/dev/null | sha256sum`
   （或使用自动化脚本遍历所有 Block，生成 `source_block_list.txt`）
3. 在目标端重复上述操作，生成 `target_block_list.txt`。

### 步骤 3：Block 序列一致性比对（核心熔断点）
1. 逐行比对 `source_block_list.txt` 与 `target_block_list.txt`。
2. **判定规则**：
   - 哈希值不同：内容被篡改，判定为**不同步**。
   - **Block 顺序不同**（哈希集合相同但序列索引不一致）：判定为**不同步**，记录为“高危假同步样本”。
   - 哈希与顺序完全一致：判定为**同步成功**。
3. 只要判定为不同步，立即终止当前文件的同步状态标记，跳转至步骤 4。

### 步骤 4：异常修复与认知池刷新
1. 对判定为不同步的文件触发强制重传（绕过 mtime 和 size 的增量判定逻辑，强制按 Block 重写）。
2. 将“同元数据不同步”的文件特征提取为新认知。
3. **强制刷新缓存**：将新认知推入认知池前端，并在未来 30 分钟内的任务调度中强制注入此校验规则。

---

## 5. 现场执行检查清单

执行人员/自动化脚本必须逐项打勾，全部通过后方可标记任务完成：

- [ ] **元数据初筛**：已比对文件名、大小、mtime。若一致，未直接判定为同步成功。
- [ ] **Block 切片**：已按系统 Block 大小对源端和目标端文件进行切片。
- [ ] **哈希生成**：已生成完整的源端与目标端 Block 哈希序列文件。
- [ ] **顺序比对**：已逐行比对哈希序列，确认不仅哈希值相同，且 Block 顺序完全一致。
- [ ] **熔断执行**：若发现“同元数据但 Block 顺序不同”的样本，已坚决判定为不同步并触发重传。
- [ ] **认知注入**：本次任务产生的异常模式已写入认知池。
- [ ] **缓存刷新**：认知池缓存已刷新，新认知已标记为“30分钟内强制注入调度”。
